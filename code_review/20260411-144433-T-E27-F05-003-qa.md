## Blocking Defects

### BUG-001: Access-Control-Allow-Methods and Access-Control-Allow-Headers absent on non-OPTIONS local-origin GET requests

**Severity:** High (spec mismatch — breaks browser CORS for non-preflight requests)
**File:** `internal/api/viewer/cors.go` lines 37-44
**Test Plan Reference:** TC-006, TC-007

**Task spec (lines 33-36) states:**
```
When origin is localhost/127.0.0.1:
- set Access-Control-Allow-Origin to the raw Origin value
- Set Access-Control-Allow-Methods: GET, OPTIONS
- Set Access-Control-Allow-Headers: Content-Type
- Set Vary: Origin
```

**Test plan TC-006 explicitly expects on a GET request:**
- `Access-Control-Allow-Methods` contains `GET`
- `Access-Control-Allow-Headers` contains `Content-Type`

**Current implementation:** `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers` are only set inside the `if r.Method == http.MethodOptions` block (lines 37-44 of `cors.go`). Non-OPTIONS requests from localhost receive only `Access-Control-Allow-Origin` and `Vary: Origin`.

**Impact:** Browsers require `Access-Control-Allow-Methods` in actual CORS responses (non-preflight) for some use cases, and the test plan explicitly mandates it. The automated test for TC-006 (`cors_test.go:31-36`) does not assert these headers and therefore gives a false PASS.

**Fix required in:** `internal/api/viewer/cors.go` — move `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers` header setting to apply to ALL local-origin requests (not just OPTIONS).

**Fix also required in:** `internal/api/viewer/cors_test.go` — TC-006 and TC-007 tests must be extended to assert `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers` on GET responses, and TC-007 must assert `Vary: Origin`.

---

### BUG-002 (Low): OPTIONS with empty Origin passes through to next handler instead of short-circuiting

**Severity:** Low (deviates from spec but has minimal real-world impact; no browser sends an OPTIONS without Origin in a CORS context)
**File:** `internal/api/viewer/cors.go` lines 24-28
**Spec reference:** Task spec line 37: "For OPTIONS requests: return 204 and do NOT call next.ServeHTTP"

**Current behavior:** When `Origin` is empty and method is OPTIONS, the early-return at line 28 calls `next.ServeHTTP` instead of returning 204.

**Strictly speaking**, the spec says OPTIONS always short-circuits regardless of origin. The implementation only short-circuits OPTIONS when Origin is present. This is a spec deviation, though it is a low-impact edge case (browsers always include Origin on OPTIONS).

**Fix required in:** `internal/api/viewer/cors.go` — check for OPTIONS method before or independent of the empty-Origin guard; return 204 for all OPTIONS regardless of Origin.
