## Red-Team Observations

### Observation 1: display_service.go passes nil for feature/epic relationship adapters

`internal/services/display_service.go` lines 481 and 669 pass `nil` for the `featureRelRepo` and `epicRelRepo` parameters to `FeaturePlaceholdersWithRelated` and `EpicPlaceholdersWithRelated` respectively, with comments "we don't have a feature/epic relationship repository yet."

The new `EntityRelFeatureKeyAdapter` and `EntityRelEpicKeyAdapter` exist and are registered in `internal/repository/aliases.go` but are not wired into the display service. REQ-F-003 requires template helpers source data from `entity_relationships` for features/epics.

**Assessment: Non-blocking for Task 001.** The spec §3.1.2 specifies wiring the adapters into "whatever interface `helpers.go` currently uses" — `helpers.go` gracefully degrades to empty string when `nil` is passed. The spec §4 implementation order and §3.5 call sites table do not list `display_service.go` as a required modification. The adapters exist and satisfy the interface; the call site wiring is not listed as a Task 001 deliverable. The QA report documents this as pre-existing behavior. However, this is a **semantic regression risk**: `related_features` and `related_epics` template placeholders silently return empty strings through the display service path. This should be tracked as a follow-up wiring task.

### Observation 2: viewer_service_test.go comments use legacy table names

Tests at lines 2057–2470 contain comments referencing "task_relationships" as the authoritative source. These tests test the viewer service's pre-Task-002 behavior (using `WithTaskRelRepo`). The comments are historically accurate but will become stale after Task 002 removes `WithTaskRelRepo`. This is cosmetic and does not affect correctness.

### Observation 3: dependency.go keeps legacy JSON blob fallback

Both `getTaskDependentsInTx` and `allDependenciesSatisfiedInTx` retain the `depends_on` JSON blob parsing path. This is correct behavior: the blob is a task field separate from the relationship tables. The spec targets removal of SQL queries to `task_relationships` (lines 311–319, 467–475), not the JSON field parsing. Both functions comment "checks both the legacy depends_on JSON field and the entity_relationships table" — accurate description of dual-source resolution, not a dual-path to a legacy SQL table.
