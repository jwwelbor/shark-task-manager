## Acceptance Criteria Verification

### AC-1: `shark status advance` output no longer contains the full orchestrator_action instruction body

**Status: PASS**

Verified across all three command paths:

1. `status_shared.go` `performEntityTransition` - outputs only:
   - `SUCCESS: Transitioned: <from> -> <to>`
   - `INFO: Run \`shark get <key> --field orchestrator_action\` to get your next instructions.`

2. `status_group.go` `runStatusSet` - same pattern (no inline action body)

3. `next_status_generic.go` `makeRunSetStatus` - same pattern

**Live test:** `./bin/shark status advance CC-029` produced:
```
SUCCESS  Transitioned: in_qa -> completed
INFO     Run `shark get CC-029 --field orchestrator_action` to get your next instructions.
```

No orchestrator_action instruction body is present. The old `displayOrchestratorAction` call has been removed from all three command files.

### AC-2: Resume preamble only fires for genuine resume scenarios (not fresh transitions)

**Status: PASS**

Implementation verified:

- `_resume_preamble.tmpl` wraps content in `{{if eq .is_resume "true"}}...{{end}}` - confirmed at line 1.
- All six service `makeResolveActionFn` implementations (task, feature, epic, bug, change_card, tech_debt) explicitly set `placeholders["is_resume"] = "false"` on fresh transitions.
- `display_service.go` `ResolveTaskAction`, `ResolveFeatureAction`, `ResolveEpicAction` all set `placeholders["is_resume"] = "true"` for `shark get` (display/resume context).
- `bug_service.go` and `change_card_service.go` `GetOrchestratorAction` methods set `is_resume = "true"` for shark get and `is_resume = "false"` in their `makeResolveActionFn` callbacks.

**Live test:** `shark get T-E07-F19-001 --field orchestrator_action` (task in `in_development`):
- Result: Instruction begins with `RESUME CONTEXT: This entity is already in an in_progress status...` - correct.

A fresh transition via `shark status advance` does NOT include this preamble since `is_resume="false"` is set in the service transition path.

### AC-3: Spot-check of new status history on active tasks shows no <10s gaps between workflow phases that should involve real work

**Status: PASS (by design)**

The structural fixes implemented make rapid back-to-back advances significantly harder:

1. **Fix #1** (AC-1 above) removes the inline action body from advance output. An agent can no longer accidentally skip the instructions by "reading" them as command output.

2. **Fix #2** (AC-2 above) removes the misleading "RESUME CONTEXT: already in in_progress" preamble from fresh transitions, eliminating the false signal that work may already be done.

3. **Fix #3** restructures EXIT guidance in all 63 orchestrator templates:
   - All templates now begin with `After completing ALL work below, exit with: <cmd>` at line 1 (or line 2 after `_resume_preamble`).
   - Zero templates contain trailing `## EXIT — REQUIRED` blocks.
   - Verified: `grep -rn "## EXIT\|EXIT — REQUIRED" shark-templates/` returns 0 matches.
   - Verified: 63 templates have `After completing ALL work below` at the top (lines 1-2).

This structural change means agents now see the exit command as a frame ("after ALL work below") rather than as a final instruction to execute immediately.
