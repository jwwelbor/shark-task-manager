## Defect Details

### DEFECT-1: Schema-Code Mismatch in `bugs` Table (CRITICAL / BLOCKER)

**Severity:** Critical — would cause runtime SQL failure on every DB operation

**Where:**
- Schema (`internal/db/db.go`, lines 1959–1961): creates `epic_id INTEGER`, `feature_id INTEGER`, `related_task_id INTEGER`
- Model (`internal/models/bug.go`): defines `LinkedEntityType *string`, `LinkedEntityKey *string`
- Repository (`internal/repository/bug_repository.go`, lines 24–26, 62–63): queries `linked_entity_type`, `linked_entity_key`, `context_data`

**Impact:** The columns the repository queries (`linked_entity_type`, `linked_entity_key`, `context_data`) do not exist in the DB schema. Any live DB call would fail with `"table bugs has no column named linked_entity_type"`.

**Why tests still pass:** All service tests mock the repository (no real SQL executed). No integration tests exist for E18.

**Fix required:**
```sql
-- Change bugs table schema from integer FKs to text entity key columns:
CREATE TABLE bugs (
    ...
    linked_entity_type TEXT,   -- e.g., "epic", "feature", "task"
    linked_entity_key TEXT,    -- e.g., "E18", "E18-F02", "E18-F02-001"
    context_data TEXT,         -- JSON for flexible metadata
    ...
    -- REMOVE: epic_id INTEGER REFERENCES epics(id),
    -- REMOVE: feature_id INTEGER REFERENCES features(id),
    -- REMOVE: related_task_id INTEGER REFERENCES tasks(id),
);
```

### DEFECT-2: `change_cards` Missing `type` Column (HIGH)

**Severity:** High — spec requires type-based filtering; no column or DTO field exists

**Where:**
- Schema (`internal/db/db.go`, line 2016–2035): no `type` column
- Model (`internal/models/change_card.go`): no `Type` field
- DTO (`internal/services/change_dto.go`): `CreateChangeCardInput` has no `type` field

**Impact:** Cannot create change cards with type `enhancement`, `configuration`, or `improvement`. Cannot filter by type. Spec scenarios 4 and 5 are untestable.

**Recommendation:** Add `type TEXT CHECK (type IN ('enhancement', 'configuration', 'improvement'))` as a real column (not `context_data`). The type is a first-class queryable attribute needed for filtering and display. Using `context_data` would require JSON_EXTRACT queries and prevent SQL-level indexing.

**Note on `change_cards` entity linking:** Unlike `bugs`, the change_cards schema/code ARE internally consistent (both use integer FKs throughout). However, users cannot specify integer IDs — they know entity keys. The service needs key→ID resolution logic before CLI commands can expose this.

### DEFECT-4: Change Card Key→ID Resolution Missing (MEDIUM)

**Where:** `internal/services/change_card_service.go`

**Impact:** `CreateChangeCardInput` accepts `EpicKey string` and `FeatureKey string`, but the `ChangeCard` model and repository use integer `EpicID *int64`. The service must resolve `"E18"` → `epic.ID` before creating a record. This lookup is not implemented.

## Root Cause Analysis

The core issue is that **E18-F01** (schema/migration) was designed with integer FK columns in the DB while **E18-F02** (Bug service/repository) was designed with text entity key columns — these were developed as separate tasks without cross-validation of the column contracts.

The tests passed because:
- All F02/F03 tests use mocked repositories (never execute real SQL)
- No integration tests exist to catch the schema-code mismatch
- Tasks for F04–F07 were advanced without CLI code existing

## Recommendations

### Return to Development

All 45 tasks should be moved back from `in_approval` → appropriate development status.

**Priority fixes before re-UAT:**

1. **Fix `bugs` table schema** — Replace `epic_id/feature_id/related_task_id` integer columns with `linked_entity_type TEXT, linked_entity_key TEXT, context_data TEXT` to match the model and repository
2. **Add `type` column to `change_cards`** — Add `type TEXT CHECK (type IN ('enhancement', 'configuration', 'improvement'))` column; update model, DTO, and repository
3. **Implement CLI commands** — F04 (`shark bug`) and F05 (`shark change-card`) are prerequisites for all other features
4. **Add integration test** — At minimum, one test that creates a real DB with the migration and performs a live CRUD operation to catch schema-code mismatches
5. **Implement key→ID resolution** for change card entity linking

### Scope assessment

F01 (schema) is partially correct for `change_cards` but wrong for `bugs`. F02 (Bug service) has correct service logic but relies on a broken DB schema. F03 (Change-card service) is internally consistent but lacks the `type` field.

F04–F07 have zero implementation.
