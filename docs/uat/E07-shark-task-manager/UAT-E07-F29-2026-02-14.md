## Feature Overview

This feature adds template variable support for related documents, tasks, features, and epics in orchestrator action instruction templates. When AI agents receive task instructions, they can now automatically see references to related documentation and dependencies.

**Key Capabilities:**
- `{related_docs}` placeholder populates with comma-separated file paths from database `task_documents` table
- `{related_tasks}` placeholder populates with comma-separated task keys from database `task_relationships` table (bidirectional queries)
- `{related_features}` placeholder populates with comma-separated feature keys from `feature_relationships` table
- `{related_epics}` placeholder populates with comma-separated epic keys from `epic_relationships` table

**Architecture:**
- All relationships stored in **database only**
- Frontmatter fields (`related_docs`, etc.) **do nothing** - they are NOT synced
- Relationships managed via database commands or direct SQL
- Template variables populated by querying database tables

### Task Relationships - Single Source Architecture

**Architecture Overview (Updated 2026-02-14):**

Task relationships use a **single-source architecture** with the `task_relationships` database table:

- **Only Source:** `task_relationships` table (formal, queryable, bidirectional)
- **No Fallback:** `context_data.related_tasks` JSON is **NOT used** for template population (removed in refactoring)
- **Placeholder Population:** Query table → return results or empty string
- **Bidirectional Queries:** Check both `from_task_id` and `to_task_id` columns
- **Deduplication:** Remove duplicate task keys from bidirectional results
- **Frontmatter has NO EFFECT:** Task frontmatter `related_tasks` field is NOT synced to database

**Why Single Source:**
- Table provides queryable relationships, analytics, and bidirectional queries
- Database constraints enforce data integrity (CASCADE DELETE, UNIQUE, CHECK)
- Simpler architecture with single source of truth
- Better performance (no JSON parsing fallback)
- **Migration Note:** Old `context_data.related_tasks` JSON data is ignored but not deleted (harmless)

**task_relationships Table Schema:**

```sql
CREATE TABLE task_relationships (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    from_task_id INTEGER NOT NULL,          -- Source task (foreign key to tasks.id)
    to_task_id INTEGER NOT NULL,            -- Target task (foreign key to tasks.id)
    relationship_type TEXT CHECK (          -- 7 valid types (CHECK constraint enforced)
        relationship_type IN (
            'depends_on',    -- from_task depends on to_task completing
            'blocks',        -- from_task blocks to_task from proceeding
            'related_to',    -- Tasks share common code/concerns (generic)
            'follows',       -- from_task naturally follows to_task (sequence)
            'spawned_from',  -- from_task created from bugs/UAT in to_task
            'duplicates',    -- Tasks represent duplicate work (merge candidates)
            'references'     -- from_task consults/uses output of to_task
        )
    ) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (from_task_id) REFERENCES tasks(id) ON DELETE CASCADE,
    FOREIGN KEY (to_task_id) REFERENCES tasks(id) ON DELETE CASCADE,
    UNIQUE(from_task_id, to_task_id, relationship_type)
);
```

**Indexes (for bidirectional query performance):**
- `idx_task_relationships_from` ON (from_task_id)
- `idx_task_relationships_to` ON (to_task_id)
- `idx_task_relationships_type` ON (relationship_type)
- `idx_task_relationships_from_type` ON (from_task_id, relationship_type)
- `idx_task_relationships_to_type` ON (to_task_id, relationship_type)

**Relationship Type Semantics:**

| Type | Meaning | Example Use Case |
|------|---------|------------------|
| **depends_on** | from_task cannot complete until to_task is done | "Implement API" depends on "Design schema" |
| **blocks** | from_task prevents to_task from starting | "Security audit" blocks "Production deploy" |
| **related_to** | Tasks share code, concerns, or context (generic) | "Update frontend" related to "Update backend" |
| **follows** | from_task logically follows to_task (sequence) | "Write tests" follows "Write code" |
| **spawned_from** | from_task created from UAT/bugs found in to_task | "Fix login bug" spawned from "UAT test session" |
| **duplicates** | Tasks represent same work (merge candidates) | "Implement auth" duplicates "Add login" |
| **references** | from_task uses output/results of to_task | "Write docs" references "API implementation" |

**Database Constraints:**
- **CASCADE DELETE:** Relationships auto-delete when either task is deleted (prevents orphaned relationships)
- **UNIQUE constraint:** Prevents duplicate (from_task_id, to_task_id, relationship_type) triples
- **CHECK constraint:** Enforces 7 valid relationship types at database level (rejects "invalid_type")
- **NO self-references:** Application SHOULD prevent from_task_id = to_task_id (not DB-enforced in MVP)

**Bidirectional Query Pattern:**

When querying task relationships, BOTH `from_task_id` and `to_task_id` must be checked:

```sql
-- Find all tasks related to T-E07-F29-002 (in either direction)
SELECT DISTINCT
    CASE
        WHEN tr.from_task_id = t_current.id THEN t_to.key
        ELSE t_from.key
    END AS related_task_key,
    tr.relationship_type
FROM task_relationships tr
JOIN tasks t_current ON (tr.from_task_id = t_current.id OR tr.to_task_id = t_current.id)
JOIN tasks t_from ON tr.from_task_id = t_from.id
JOIN tasks t_to ON tr.to_task_id = t_to.id
WHERE t_current.key = 'T-E07-F29-002'
AND (
    (tr.from_task_id = t_current.id AND t_to.key != t_current.key)
    OR (tr.to_task_id = t_current.id AND t_from.key != t_current.key)
)
ORDER BY related_task_key;
```

**Why bidirectional?** If task A relates to task B, the relationship can be stored as (from=A, to=B) OR (from=B, to=A). Queries must check both directions to find all relationships.
