# User Acceptance Testing Guide - E17-F07 Status Subcommand Group

## Feature Overview

This feature adds four subcommands to the existing `shark status` command, providing a unified interface for status management operations:

- `shark status set <key> <status>` - Set entity to a specific status
- `shark status advance <key>` - Advance entity to next workflow status
- `shark status options <key>` - Show available status transitions (read-only)
- `shark status history <key>` - Show task status change history

The existing `shark status <key>` dashboard command continues to work unchanged. The old top-level `shark history` command is hidden from help but still functional.

## Prerequisites

- Shark CLI built: `make build` or `make shark`
- Project initialized with advanced workflow: `shark init --non-interactive`
- At least one epic, feature, and task exist in the database
- Quality gates pass: `make fmt && make lint && make test`

## Test Scenarios

### Scenario 1: Status Set Command

**Tasks covered:** T-E17-F07-001, T-E17-F07-002

**Steps:**

1. Create a test task or identify an existing task in `todo` or `draft` status
   ```bash
   shark task list --json | head -20
   ```

2. Set the task to a specific status:
   ```bash
   shark status set <task-key> in_development
   ```

3. Verify the status changed:
   ```bash
   shark task get <task-key> --json
   ```

4. Test idempotency - set to same status again:
   ```bash
   shark status set <task-key> in_development
   ```
   Expected: Exit 0 with `"changed": false` in JSON output

5. Test JSON output:
   ```bash
   shark status set <task-key> ready_for_code_review --json
   ```
   Expected: JSON with `key`, `entity_type`, `old_status`, `new_status`, `changed` fields

6. Test with epic key:
   ```bash
   shark status set E17 active
   ```

7. Test with feature key:
   ```bash
   shark status set E17-F07 active
   ```

8. Test invalid status:
   ```bash
   shark status set <task-key> nonexistent_status
   ```
   Expected: Error message about invalid status/transition

**Success Criteria:**
- [ ] Status changes are applied correctly
- [ ] Idempotent when already at target status (exit 0, changed=false)
- [ ] Works for epics, features, and tasks (auto-detected from key)
- [ ] JSON output includes all required fields
- [ ] Invalid statuses produce clear error messages

### Scenario 2: Status Advance Command

**Tasks covered:** T-E17-F07-001, T-E17-F07-002

**Steps:**

1. Find a task with available transitions:
   ```bash
   shark status options <task-key>
   ```

2. Advance the task (interactive - picks first available):
   ```bash
   shark status advance <task-key>
   ```

3. Advance with specific target:
   ```bash
   shark status advance <task-key> --status=<next-status>
   ```

4. Test JSON output:
   ```bash
   shark status advance <task-key> --json
   ```
   Expected: JSON with transition details and orchestrator action

5. Test with epic:
   ```bash
   shark status advance E17
   ```

6. Test with feature:
   ```bash
   shark status advance E17-F07
   ```

**Success Criteria:**
- [ ] Advances to next valid workflow status
- [ ] `--status` flag allows specifying target
- [ ] JSON output includes transition details and orchestrator_action
- [ ] Works for all entity types
- [ ] Invalid transitions produce clear error messages
