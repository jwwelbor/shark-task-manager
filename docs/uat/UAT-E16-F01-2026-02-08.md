## Epic Context

**Epic Goal:** Extend Shark's workflow system to support independent status flows for epics, features, and tasks, enabling multi-level orchestration with configurable workflows at each entity level.

**This Feature's Role:** Implements the core workflow engine that enables multi-level workflow support. Introduces `MultiLevelWorkflow` config container, extends `workflow.Service` with level awareness (`ForLevel()`), creates `EpicService` and `FeatureService` with transition logic, adds CLI commands for epic/feature status transitions, and refactors validation to be workflow-driven.

**Related Features:**
- E16-F02: Orchestrator Actions (depends on F01 - uses `OrchestratorAction` placeholder added in T-008)
- E16-F03: Display and Aggregation Threshold
- E16-F04: Notes and Context for Epic and Feature
- E16-F05: Backward Transition and Escalation
- E16-F06: Workflow Visualization

**Integration Points:**
- `config.MultiLevelWorkflow` holds all three level configs (epic, feature, task)
- `workflow.Service.ForLevel()` creates level-specific service instances
- `EpicService` and `FeatureService` follow same patterns as existing task workflow
- `.sharkconfig.json` may optionally contain `epic_workflow` and `feature_workflow` sections

---

## Design Intent

**From Architecture Document:**
> Extend the existing `WorkflowConfig` / `workflow.Service` to support three independent status flows (epic, feature, task) while maintaining 100% backward compatibility with existing task workflows.

**Key Design Decisions:**
- `WorkflowConfig` is reused for all three entity levels (no separate types)
- `MultiLevelWorkflow` container with nil-means-default semantics
- Default epic workflow: draft -> active -> completed -> archived (4 statuses)
- Default feature workflow: draft -> active -> completed -> archived (4 statuses)
- `ForLevel()` creates new Service instances (immutable, does not modify receiver)
- Service constructors auto-scope to appropriate level
- Model validation refactored: no hardcoded status lists, only non-empty checks
- `OrchestratorAction` placeholder added for E16-F02 cross-feature dependency

## Test Scenarios

### Scenario 1: Epic Status Transitions (Default Workflow)
**Purpose:** Verify epic status transitions work with default 4-status workflow

**Steps:**
1. Run `shark epic next-status E16 --preview`
2. Verify output shows available transitions from current epic status
3. Run `shark epic next-status E16`
4. Verify epic advances to next status
5. Run `shark epic next-status E16 --json`
6. Verify JSON includes `entity_type: "epic"`, `entity_key`, `current_status`, `available_transitions`

**Expected:** Epic transitions follow draft -> active -> completed -> archived flow

**Validates:** AC-1, AC-2, AC-4

---

### Scenario 2: Feature Status Transitions (Default Workflow)
**Purpose:** Verify feature status transitions work with default 4-status workflow

**Steps:**
1. Run `shark feature next-status E16-F01 --preview`
2. Verify output shows available transitions
3. Run `shark feature next-status E16-F01`
4. Verify feature advances to next status
5. Run `shark feature next-status E16-F01 --json`

### Scenario 3: Direct Status Transition
**Purpose:** Verify `--status` flag allows jumping to specific target status

**Steps:**
1. Run `shark epic next-status E16 --status=active`
2. Verify epic transitions to "active" (or shows error if not a valid transition from current status)
3. Try an invalid transition: `shark epic next-status E16 --status=nonexistent_status`
4. Verify error message lists valid options

**Expected:** Valid targets succeed, invalid targets show helpful error

**Validates:** AC-3, AC-11

---

### Scenario 4: Force Flag Bypass
**Purpose:** Verify `--force` bypasses workflow validation

**Steps:**
1. Try an invalid transition: `shark epic next-status E16 --status=archived --force`
2. Verify transition succeeds despite being invalid in normal workflow
3. Verify a warning message about workflow validation bypass is shown

**Expected:** Force flag allows any transition with warning

**Validates:** AC-12

---

### Scenario 5: Workflow Validate Command (Multi-Level)
**Purpose:** Verify `shark workflow validate` reports all three levels

**Steps:**
1. Run `shark workflow validate`
2. Verify output includes validation for Epic, Feature, and Task levels
3. Verify format: `Epic workflow: valid (N statuses, custom/default)`
4. Run `shark workflow validate --json`
5. Verify JSON contains structured results for all three levels

**Expected:** All three levels validated, default workflows show "(N statuses, default)"

**Validates:** AC-7, AC-8

---

### Scenario 6: Backward Compatibility (Task Workflow Unchanged)
**Purpose:** Verify existing task commands work identically

**Steps:**
1. Run `shark task next-status T-E16-F01-001 --preview`
2. Verify task workflow transitions are unaffected
3. Run `shark task list E16 F01`
4. Verify task listing works normally
5. Run `shark workflow validate` and verify task workflow matches expected profile

**Expected:** Zero regressions in task workflow behavior

**Validates:** AC-10

---

### Scenario 7: Default Workflow Fallback (No Config)
**Purpose:** Verify that missing epic/feature workflow sections in config use defaults

**Steps:**
1. Verify `.sharkconfig.json` has no `epic_workflow` or `feature_workflow` sections
2. Run `shark epic next-status E16 --preview`
3. Verify default epic workflow (draft, active, completed, archived) is used
4. Run `shark feature next-status E16-F01 --preview`
5. Verify default feature workflow is used

**Expected:** Default workflows used silently without errors or warnings

**Validates:** AC-9

---

### Scenario 8: Error Handling - Not Found
**Purpose:** Verify proper error handling for non-existent entities

**Steps:**
1. Run `shark epic next-status E99`
2. Verify "not found" error with appropriate exit code
3. Run `shark feature next-status E99-F99`
4. Verify "not found" error

**Expected:** Clear error messages, exit code 1
