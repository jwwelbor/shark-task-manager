## 4. Independent Red-Team Findings

The UAT agent verified the following edge cases not explicitly covered by the QA report:

### 4.1 Atomicity of SetSprintCapacityDefault

- Pattern: `write temp (.tmp) → rename`. Verified at manager.go:326-333.
- On rename failure: `os.Remove(tmpPath)` is called (line 331) and error returned. Config file is left unchanged.
- On write failure: temp file write fails, function returns early before rename — config file is never modified.
- **Verdict:** Atomic write is correctly implemented. Config file is never left in a partial state.

### 4.2 Concurrent Write Safety

- `Manager` has no mutex. Concurrent calls to `SetSprintCapacityDefault` from different goroutines would race on `m.config.RawData` (an in-memory map) and on the file path.
- **Mitigation:** In CLI usage, `Manager` is created per command invocation via `config.NewManager(configPath).Load()` (root.go:365). The CLI is single-threaded per invocation. There is no shared Manager singleton exposed to concurrent goroutines.
- **Verdict:** No concurrent write risk in the actual CLI usage model. The config layer is not designed for concurrent access, and the CLI does not use it that way. This is acceptable for this layer.

### 4.3 Negative/Zero Capacity Values

- `SetSprintCapacityDefault(agentType string, points float64)` accepts any float64 including negative and zero.
- No validation at this layer. Spec §2.7 states validation lives at the CLI caller (`sprintCapacitySetCmd`), not in the manager method.
- AC-3 says `points > 0` is validated at the CLI command layer (`shark sprint capacity set --default --agent=backend --points=21`). That CLI command does not yet exist in this worktree (it is a future task).
- **Verdict:** Absence of validation in `SetSprintCapacityDefault` is correct per spec. Non-blocking observation recorded.

### 4.4 Empty-String agentType

- `SetSprintCapacityDefault("", 21)` would write `capacity[""] = 21` to the JSON. No guard.
- Again, this validation is the CLI caller's responsibility per spec.
- **Verdict:** Consistent with spec intent. Non-blocking.

### 4.5 NilSafe Test Adequacy

- `TestSprintDefaults_NilSafe` asserts `cfg.SprintDefaults == nil` but does NOT actually dereference the nil pointer (which would panic for field access on a nil struct pointer).
- The test comment says "Accessing SprintDefaults.Capacity on nil pointer must not panic" — this is slightly misleading. The test only verifies the pointer is nil; it does not exercise the described scenario.
- **Impact:** The spec documents that callers must nil-check before accessing SprintDefaults fields (spec line 602: `s.cfg.SprintDefaults != nil`). There is no nil-safe accessor method on the struct. Callers are responsible for the nil check. The test correctly confirms the pointer is nil when the section is absent.
- **Verdict:** Test is slightly misleadingly commented, but verifies the correct pre-condition. The actual nil-safety contract is enforced at the caller level, which is consistent with the codebase pattern. Non-blocking.

### 4.6 Schema Compliance Verification

The spec §2.3.1 defines:
```go
Capacity map[string]float64 `json:"capacity,omitempty"`
CarryoverBehavior string `json:"carryover_behavior,omitempty"`
AutoCreate bool `json:"auto_create,omitempty"`
```

The implementation at config.go:85-100 exactly matches this schema. JSON tags, types, and omitempty annotations are identical. The `SprintDefaults *SprintDefaultsConfig` field on `Config` uses `json:"sprint_defaults,omitempty"` — pointer semantics give nil-when-absent behavior as required by AC-1.

### 4.7 AC-3 — Wiring Status

`SetSprintCapacityDefault` exists in `manager.go` and is tested. It is NOT wired to any CLI command in this worktree. This is correct: the task scope is the config layer method only. The CLI command `shark sprint capacity set --default` is delivered in a later E19-F05 task.

### 4.8 Field Preservation on Write

`SetSprintCapacityDefault` operates on `m.config.RawData` (the raw `map[string]interface{}`), then marshals RawData back to JSON. This preserves all unknown/unrecognized config fields — the same pattern as `UpdateLastSyncTime`. Verified by examining manager.go:317-328.
