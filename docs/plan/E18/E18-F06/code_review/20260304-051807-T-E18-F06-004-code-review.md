## Summary

The implementation correctly extends `shark search` with full-text query mode covering bugs and change-cards alongside existing entity types. All acceptance criteria pass.

## Acceptance Criteria Verification

### AC1: `shark search "query"` routes to new full-text search
PASS. The `runSearch` dispatcher checks for `--file` flag; if absent, calls `runSearchQuery`.

### AC2: `--type=bug` and `--type=change` filtering
PASS. `SearchAll` accepts an `*string` entity type filter applied post-scan. `--type=bug` and `--type=change` correctly restrict results.

### AC3: `--type=invalid` errors with valid types listed
PASS. `validateSearchType` returns `invalid type "invalid": valid types are epic, feature, task, bug, change`. Verified via smoke test and unit tests.

### AC4: Bug results include `severity`, others omit it
PASS. `EntitySearchResult.Severity` is tagged `json:"severity,omitempty"`. The UNION SQL returns `CAST(severity AS TEXT)` for bugs and `'' AS severity` for all other types. Empty string is treated as zero-value, so `omitempty` suppresses the field in JSON output for non-bugs. Verified via JSON output inspection.

### AC5: `--file` mode still works
PASS. `runSearch` preserves the `runSearchFile` path when `--file` is set. Smoke test confirmed.

### AC6: `make shark` passes
PASS. Build completed without errors.

### AC7: `make test` passes with zero failures
PASS. All packages passed (30 packages, 0 failures). Repository tests use in-memory DB (`:memory:`), satisfying testing architecture rules.

### AC8: SQL injection security
PASS. The `SearchAll` method uses parameterized queries (`?` placeholders) throughout the UNION SQL. The `pattern` variable is passed as a bind parameter — it is never interpolated into the SQL string. SQLite's LIKE operator with a bound parameter is safe from SQL injection.

## Code Quality Assessment

### Repository (`search_repository.go`)

**Strengths:**
- Clean UNION SQL query with correct column alignment across all 5 tables
- Properly uses parameterized queries preventing SQL injection
- Empty query guard returns early without DB round-trip
- `rows.Err()` checked after iteration
- `rows.Close()` deferred
- Error wrapping provides useful context

**Minor Observations (non-blocking):**
- The entity type filter is applied in Go after fetching all rows rather than in the SQL `WHERE` clause. For large datasets this is slightly inefficient, but is simple and correct. At current scale this is acceptable.
- The comment says "FTS5" in the struct docstring but `SearchAll` uses LIKE-based matching — the comment is slightly misleading, but it does not affect correctness.

### CLI Command (`search.go`)

**Strengths:**
- Clear separation into `runSearchFile` (legacy) and `runSearchQuery` (new)
- `validateSearchType` extracted as testable pure function
- `printEntitySearchResults` correctly conditionally shows severity for bugs only
- Human-readable output handles zero-results gracefully

**Architecture Note:**
The `runSearchQuery` function accesses the repository directly rather than going through a service layer (`cli.GetDB()` + `repository.NewSearchRepository()`). The developer acknowledged this with a comment:

```go
// Step 2: Call repository (thin wrapper: direct repo access is acceptable here
// because there is no business logic — just data retrieval and formatting).
```

While this deviates from the preferred service-layer pattern, it is pragmatically acceptable for a pure read query with no business logic. The comment is honest. This is consistent with other legacy patterns in the codebase being tracked under Epic E15. No new business logic was embedded in the command.

### Tests

**Repository tests (`search_all_test.go`):**
- Uses in-memory DB (`":memory:"`) — correct per testing architecture
- 9 tests covering: all-entity results, empty query, type filters (bug, change, task), severity presence/absence, required fields, no-match scenario
- Uses `require.NoError` for setup, `assert` for verifiable conditions — correct pattern

**CLI tests (`search_query_test.go`):**
- 7 pure unit tests covering `validateSearchType` and `parseSearchQuery`
- No database access — correct
- `TestEntitySearchResult_BugHasSeverity` and `TestEntitySearchResult_ChangeCardNoSeverity` test struct behavior directly

## Security Review

No security issues found:
- All SQL parameters are bound via `?` placeholders
- No user input is concatenated into SQL strings
- The `pattern := "%" + query + "%"` construction is used only as a bind parameter value, not SQL structure
