# Task: Remove business logic from repositories and move to services

## Goal

Remove all business logic methods from FeatureRepository, TaskRepository, and EpicRepository and move the logic into corresponding service methods. This establishes repositories as pure data access objects (CRUD + queries only), completing the first phase of the service layer migration.

**Success Looks Like**: Repositories contain only Create, Get, Update, Delete, List methods. All progress calculations, health derivations, and status aggregations live in services. Code won't compile if removed methods are called (fail-fast validation).

## Requirements

### Functional Requirements

**REQ-F-001**: Remove `FeatureRepository.CalculateProgress()` and `FeatureRepository.GetHealthStatus()`
- Move logic to `FeatureService.GetProgress()` and `FeatureService.GetHealth()`
- Repository only performs data retrieval (GetByID, List)
- Service performs calculation logic (count completed tasks, derive health)

**REQ-F-002**: Remove `TaskRepository.GetStatusBreakdown()`
- Move logic to `TaskService.GetStatusSummary()`
- Repository only performs task queries (List by feature)
- Service performs aggregation logic (group by status, count)

**REQ-F-003**: Remove `EpicRepository.GetHealthStatus()`, `CalculateProgress()`, `CalculateProgressByKey()`
- Move logic to `EpicService.GetHealth()`, `GetProgress()`, `GetProgressByKey()`
- Repository only performs epic/feature queries
- Service performs aggregation logic (check for blocked tasks, average feature progress)

**REQ-F-004**: Validate no workflow validation in repositories
- Ensure no calls to `workflow.Service` in repository files
- All status validation must be in service layer
- Repository methods accept any valid status string (no validation)

### Non-Functional Requirements

**REQ-NF-001**: Zero behavioral changes
- Removed methods must be replaced with equivalent service methods
- Calculations must produce identical results
- Existing tests must continue to pass

**REQ-NF-002**: Compilation validation
- Code must not compile if removed methods are called
- Use Go compiler as validation gate (fail-fast)

## Implementation Plan

### Phase 1: Add New Service Methods (Foundation)

1. **Add FeatureService.GetProgress()**
   - Copy logic from `FeatureRepository.CalculateProgress()`
   - Accept `ctx context.Context, featureID int64` parameters
   - Call `taskRepo.List(ctx, featureID)` to get tasks
   - Calculate: `(completed_tasks / total_tasks) * 100`
   - Return `float64` (0.0-100.0)
   - Handle edge case: 0 tasks → return 0.0

2. **Add FeatureService.GetHealth()**
   - Copy logic from `FeatureRepository.GetHealthStatus()`
   - Accept `ctx context.Context, featureID int64` parameters
   - Call `taskRepo.List(ctx, featureID)` to get tasks
   - Check for blocked tasks → "critical"
   - Check for old approval tasks (>3 days) → "warning"
   - Default → "healthy"
   - Return `string`

3. **Add TaskService.GetStatusSummary()**
   - Copy logic from `TaskRepository.GetStatusBreakdown()`
   - Accept `ctx context.Context, featureID int64` parameters
   - Call `taskRepo.List(ctx, featureID)` to get tasks
   - Aggregate: `map[string]int` (status → count)
   - Return `map[string]int, error`

4. **Add EpicService.GetProgress()**
   - Copy logic from `EpicRepository.CalculateProgress()`
   - Accept `ctx context.Context, epicID int64` parameters
   - Call `featureRepo.List(ctx, epicID)` to get features
   - For each feature, call `FeatureService.GetProgress()`
   - Calculate average: `sum(feature_progress) / feature_count`
   - Return `float64` (0.0-100.0)
   - Handle edge case: 0 features → return 0.0

5. **Add EpicService.GetProgressByKey()**
   - Accept `ctx context.Context, key string` parameters
   - Call `epicRepo.GetByKey(ctx, key)` to get epic ID
   - Call `EpicService.GetProgress(ctx, epicID)`
   - Return `float64, error`

6. **Add EpicService.GetHealth()**
   - Copy logic from `EpicRepository.GetHealthStatus()`
   - Accept `ctx context.Context, epicID int64` parameters
   - Call `featureRepo.List(ctx, epicID)` to get features
   - For each feature, call `FeatureService.GetHealth()`
   - Aggregate health: "critical" if any feature critical, "warning" if any warning, else "healthy"
   - Return `string`

### Technical Approach

**Pattern**: Extract-Method Refactoring
1. Create new service method with identical logic
2. Test new method thoroughly (unit tests with mocks)
3. Remove old repository method
4. Fix compilation errors by calling new service method
5. Validate tests still pass (zero behavioral changes)

**Trade-offs**:
- **Pro**: Repositories become simple and predictable (pure data access)
- **Pro**: Service logic is testable without database (mock repositories)
- **Con**: Additional layer of abstraction (minimal performance overhead)
- **Mitigation**: Service layer overhead is negligible (<1ms per operation)
