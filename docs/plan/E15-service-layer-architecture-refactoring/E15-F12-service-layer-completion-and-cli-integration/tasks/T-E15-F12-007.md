# Task: Create global service accessors in internal/cli/services_global.go

## Goal

Create global service accessor functions (`GetTaskService()`, `GetFeatureService()`, `GetEpicService()`) in `internal/cli/services_global.go` to provide easy service access for CLI commands. This infrastructure enables CLI commands to call services with a single line (`svc := cli.GetTaskService()`) instead of manually wiring dependencies in each command.

**Success Looks Like**: CLI commands call `cli.GetTaskService()` and immediately have access to all service methods. Accessors reuse shared dependencies (DB connection, workflow service) for efficiency. Pattern matches existing `cli.GetDB()` and `cli.GetWorkflowService()`.

## Requirements

### Functional Requirements

**REQ-F-001**: Create file `internal/cli/services_global.go`
- New file in CLI package
- Contains 3 exported accessor functions
- Follows existing pattern from `db_global.go`

**REQ-F-002**: Implement `GetTaskService()` accessor
- Returns `*services.TaskService`
- Calls `GetDB(context.Background())` for database connection
- Calls `GetWorkflowService()` for workflow validation
- Creates `TaskRepository` from DB
- Constructs `TaskService` with dependencies: `services.NewTaskService(taskRepo, workflowSvc, nil, nil)`
- Panics on DB failure (fail-fast for CLI, matches existing pattern)

**REQ-F-003**: Implement `GetFeatureService()` accessor
- Returns `*services.FeatureService`
- Same dependency pattern as GetTaskService
- Creates `FeatureRepository` from DB
- Constructs `FeatureService` with dependencies

**REQ-F-004**: Implement `GetEpicService()` accessor
- Returns `*services.EpicService`

- Constructs `EpicService` with dependencies

### Non-Functional Requirements

**REQ-NF-001**: Reuse shared dependencies
- DB connection is singleton (created once via `GetDB()`, reused)
- Workflow service is singleton (created once via `GetWorkflowService()`, reused)
- Service instances are created per call (lightweight, no shared state)

**REQ-NF-002**: Fail-fast on errors
- Panic on DB initialization failure (matches `GetDB()` pattern)
- Panic message must be clear: "failed to get database: %v"
- CLI commands rely on fail-fast behavior (don't handle DB errors)

**REQ-NF-003**: Consistency with existing patterns
- Function signatures match `GetDB()` and `GetWorkflowService()` style
- Error handling matches existing CLI patterns (panic for unrecoverable errors)
- No lazy initialization caching (create service on every call, simple pattern)

    db, err := GetDB(context.Background())

### Technical Approach

**Pattern**: Global Accessor Functions (matches existing `GetDB()`, `GetWorkflowService()`)

**Dependency Wiring**:
```
GetTaskService()
├── GetDB(context.Background()) → *repository.DB (singleton, reused)
├── repository.NewTaskRepository(db) → *repository.TaskRepository (created per call)
├── GetWorkflowService() → *workflow.Service (singleton, reused)
└── services.NewTaskService(repo, workflow, nil, nil) → *services.TaskService (created per call)
```

**Trade-offs**:
- **Pro**: Simple pattern, no caching complexity, matches existing CLI patterns
- **Pro**: Service instances are lightweight (no caching needed)
- **Pro**: Reuses expensive dependencies (DB, workflow service are singletons)
- **Con**: Creates new service instance per command (acceptable for CLI - commands are short-lived)
- **Alternative Rejected**: Service caching (premature optimization, adds complexity)

**Existing Pattern Reference**: `internal/cli/db_global.go` demonstrates lazy singleton with panic on failure

## Notes

**Design Reference**: `02-architecture.md` - Decision 3 (Global Service Accessors for CLI Integration)

**Existing Pattern**: See `internal/cli/db_global.go` for similar accessor pattern with lazy singleton and panic-on-failure

**Simplicity Over Optimization**: No service-level caching because:
1. Service instances are lightweight (just struct with function pointers)
2. CLI commands are short-lived (create service, call method, exit)
3. Expensive dependencies (DB, workflow) are already singletons
4. Premature optimization adds complexity without measured benefit
