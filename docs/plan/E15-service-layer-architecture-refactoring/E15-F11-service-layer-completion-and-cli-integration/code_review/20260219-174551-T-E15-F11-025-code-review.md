The implementation partially migrates `history.go` to the thin-wrapper pattern. The command correctly avoids direct `repository` package imports and `cli.GetDB()` calls, and it properly invokes `cli.GetTaskServiceWithHistory()`. ## Blocker: Direct Repository Access via `svc.GetTaskRepository()`

### Location 1: `runHistory()` - line 174

```go
taskRepo := svc.GetTaskRepository()
var displayRecords []HistoryDisplay
for _, h := range histories {
    task, err := taskRepo.GetByID(ctx, h.TaskID)
    if err != nil {
        continue // Skip if task not found
    }
    // ...
}
```

### Location 2: `outputHistoryExport()` - lines 231-235

```go
func outputHistoryExport(ctx context.Context, histories []*models.TaskHistory, svc interface {
    GetTaskRepository() services.TaskRepository
}, format string) error {
    taskRepo := svc.GetTaskRepository()
    // ...
    task, err := taskRepo.GetByID(ctx, h.TaskID)
```

### Why This Is a Violation

The task specification states explicitly:

> "Check there are no backdoor repository access patterns (e.g., `svc.GetTaskRepository()` is NOT acceptable - that's still direct repo access through the service; service methods should be called instead)"
> "CRITICAL: If the implementation uses `svc.GetTaskRepository()` or similar methods to get raw repository access, that is a violation of the thin wrapper pattern and must be flagged as a blocker."

The purpose of the thin wrapper pattern is to ensure CLI commands interact with the system exclusively through service methods. When `runHistory()` calls `taskRepo.GetByID(ctx, h.TaskID)`, it is executing raw repository queries from the CLI layer. This:

1. Bypasses service-layer business logic and error wrapping
2. Creates a hidden repository coupling in the CLI that cannot be detected by examining imports alone
3. Makes the CLI command responsible for data retrieval logic that belongs in the service

The fact that `TaskService.GetTaskRepository()` (task_service.go line 1601-1604) exists and returns the raw repo does not make its use acceptable from a CLI command. That method was documented as being for "tree traversal functions," not for general CLI use.

---

## Root Cause

The underlying issue is that `TaskService.ListHistory()` returns `[]*models.TaskHistory` records with only a numeric `TaskID` field, but no `TaskKey`. To display the human-readable task key in the table or export, the command needs to resolve each `TaskID` to a task key. The developer resolved this by reaching back through the service to the repository.

The correct fix is to add a service method that encapsulates this resolution, or modify `ListHistory()` to return enriched records that include the task key, so the CLI command never needs to touch a repository.

---

## Required Changes Before Re-Review

### Option A: Add a service method `ListHistoryWithTaskKeys()`

Add a method to `TaskService` that returns history records already enriched with the task key string, so the CLI command receives a ready-to-display structure. The command then formats and renders it without any repo interaction.

### Option B: Add a `GetTaskByID()` service method

Add `func (s *TaskService) GetTaskByID(ctx context.Context, id int64) (*models.Task, error)` to `TaskService`. The command calls `svc.GetTaskByID()` instead of `taskRepo.GetByID()`. This keeps all repository interaction inside the service.

### Option C: Move enrichment into `ListHistory()`

Modify `ListHistory()` to also resolve task keys internally and return a richer result type that includes the key, so callers never need to look up tasks separately.

Either option A or C is preferred as they result in the cleanest command (pure parse-call-format). Option B is acceptable but still leaves the N+1 lookup loop in the CLI.

## Non-Blocking Observations

These are observations that do not block approval but should be noted for follow-up.

1. **Silent `continue` on task lookup failure (lines 178, 239):** When `GetByID` fails (task deleted, etc.), the record is silently skipped. This can produce misleading output with no indication to the user that some history entries were omitted. A warning log or a note in the summary would improve observability.

2. **`outputHistoryExport` parameter type uses an inline interface (lines 231-233):** The parameter type `interface { GetTaskRepository() services.TaskRepository }` is an inline structural interface. This is a code smell that makes the violation more explicit - the function's contract is literally typed around acquiring the repository. This signature will need to change as part of fixing the blocker.

3. **N+1 query pattern:** Both `runHistory` and `outputHistoryExport` call `GetByID` once per history record in a loop. For large result sets (e.g., default limit of 50 records), this is 51 database round-trips. The service-layer fix (Option A or C) should batch or join this lookup at the repository level.
