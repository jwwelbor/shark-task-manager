# Code Review: T-E15-F11-019

**Task**: Migrate task_next_status.go to thin wrapper calling TaskService next-status method
**Reviewer**: TechLead
**Date**: 2026-02-19

## Summary

`internal/cli/commands/task_next_status.go` has NOT been migrated to a thin wrapper. It remains a fat controller with substantial business logic, direct repository access, and direct workflow service usage. The file never delegates to `TaskService` at any point.

---

## Critical Violations

### 1. Direct Repository Creation (Lines 91, 131)

```go
// Line 91 - direct DB access
repoDb, err := cli.GetDB(cmd.Context())

// Line 131 - direct repository instantiation
taskRepo := repository.NewTaskRepositoryWithWorkflow(repoDb, workflowConfig)
```

**Required**: CLI commands must NEVER create repository instances. All data access must go through the service layer via `cli.GetTaskService()`.

### 2. Direct Repository Method Calls (Lines 132-139, 340)

```go
// Line 132 - direct data retrieval from repository
task, err := taskRepo.GetByKey(ctx, taskKey)

// Line 340 - direct status update via repository
err = taskRepo.UpdateStatusForcedWithUnblock(ctx, task.ID, models.TaskStatus(targetStatus), &agentPtr, &notes)
```

**Required**: Commands must not call repository methods. Business operations belong in the service layer.

### 3. Workflow Service Instantiation in CLI Command (Line 142)

```go
// Line 142 - workflow service created in command
workflowSvc := workflow.NewService(projectRoot)
```

**Required**: The workflow service should only be instantiated in the service layer or in the CLI wiring layer (`services_global.go`). CLI commands must not create their own workflow service instances.

### 4. Business Logic in CLI Command (Lines 142-233)

The command contains extensive business logic that belongs in the service layer:

```go
// Lines 146-147 - business rule evaluation in command
transitionInfo := workflowSvc.GetTransitionInfo(currentStatus)
currentMeta := workflowSvc.GetStatusMetadata(currentStatus)

// Lines 168-182 - terminal status handling logic
if transitionInfo.IsTerminal {
    // ... business rule enforcement ...
}

// Lines 207-233 - transition validation logic
validTransitions := transitionInfo.ValidNextStatuses
if len(validTransitions) == 0 {
    // ...
}
```

**Required**: All workflow validation, transition checking, and terminal status handling must live in `TaskService`.

### 5. performTransition Helper is a Fat Controller (Lines 280-360)

The local `performTransition` function is a fat helper that calls the repository directly and manages the status cascade:

```go
func performTransition(ctx context.Context, taskRepo repository.TaskRepositoryWithWorkflow,
    repoDb *repository.DB, task *models.Task, targetStatus string, ...) error {
    // ...
    err = taskRepo.UpdateStatusForcedWithUnblock(...) // Line 340 - direct repo call
    // ...
    triggerStatusCascade(ctx, repoDb, task.FeatureID) // Line 350 - cascade in command layer
}
```

**Required**: This entire function's logic must be inside `TaskService.TransitionStatus()` or `TaskService.GetNextStatus()`.

### 6. No TaskService Delegation

The file contains zero calls to `cli.GetTaskService()`. The entire operation bypasses the service layer entirely.

## Pre-existing Build Error

Running `go build ./internal/cli/commands/` reveals a compile error in the dependency:

```
internal/services/task_service.go:910:19: newStatusMeta.OrchestratorAction undefined
    (type workflow.StatusInfo has no field or method OrchestratorAction)
```

This error is in `TaskService.TransitionStatus()` at line 910 of `task_service.go`. The field `OrchestratorAction` does not exist on `workflow.StatusInfo`. This build error must be resolved as part of or prior to this task, since the thin wrapper migration requires `TaskService.TransitionStatus()` to compile.

Additionally, `TaskService.GetNextStatus()` at lines 923-939 of `task_service.go` returns `fmt.Errorf("not implemented")` — it is a stub. This method must be fully implemented to support the migration.

## What the Thin Wrapper Should Look Like

```go
func runTaskNextStatus(cmd *cobra.Command, args []string) error {
    // Step 1: Parse arguments
    taskKey := args[0]
    targetStatus, _ := cmd.Flags().GetString("status")
    agentID, _ := cmd.Flags().GetString("agent")
    notes, _ := cmd.Flags().GetString("notes")
    force, _ := cmd.Flags().GetBool("force")

    // Step 2: Call service
    svc := cli.GetTaskService()
    result, err := svc.TransitionStatus(cmd.Context(), taskKey, targetStatus, services.TransitionOptions{
        AgentID: agentID,
        Notes:   notes,
        Force:   force,
    })
    if err != nil {
        return err
    }

    // Step 3: Format output
    if cli.GlobalConfig.JSON {
        return cli.OutputJSON(result)
    }
    cli.Success(fmt.Sprintf("Task %s transitioned to %s", taskKey, result.NewStatus))
    return nil
}
```

## Required Changes

1. **Fix the build error in task_service.go** - Remove or replace the `OrchestratorAction` field reference at line 910.
2. **Implement `TaskService.GetNextStatus()`** - Replace the "not implemented" stub with real logic.
3. **Rewrite `task_next_status.go`** as a thin wrapper that calls `cli.GetTaskService()` and delegates to `svc.TransitionStatus()` or `svc.GetNextStatus()`.
4. **Remove all direct imports** of `repository`, `workflow`, and `config` packages from `task_next_status.go`.
5. **Remove `performTransition` helper** - this logic belongs in the service.
6. **Verify compilation** after changes: `make build`.
