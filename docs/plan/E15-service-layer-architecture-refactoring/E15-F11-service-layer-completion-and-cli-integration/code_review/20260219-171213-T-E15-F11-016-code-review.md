## Thin Wrapper Check

### Before (fat controller pattern)
```go
// BEFORE: Direct repository access in command
repoDb, err := cli.GetDB(cmd.Context())
dbConn := repoDb
historyRepo := repository.NewTaskHistoryRepository(dbConn)
histories, err := historyRepo.GetHistoryByTaskKey(ctx, taskKey)

// Also checked task existence via second direct repo call
taskRepo := repository.NewTaskRepository(dbConn)
_, err := taskRepo.GetByKey(ctx, taskKey)
```

### After (thin wrapper pattern)
```go
// AFTER: Thin wrapper calling service
svc := cli.GetTaskServiceWithHistory()
histories, err := svc.GetTaskHistory(cmd.Context(), taskKey)

// Task existence check also via service
_, err := svc.GetTask(cmd.Context(), taskKey)
```

The command is now a proper thin wrapper: parse arguments -> call service -> format output.

## Minor Observations (Non-blocking)

1. **Empty history fallback**: The two-step approach (try history, then verify task exists on empty result) is reasonable given the service interface. A unified `GetTaskHistoryOrNotFound()` could be cleaner, but the current approach works correctly and is readable.

2. **Format flag vs JSON flag**: The command has both `--format=json` (via `taskHistoryFormat`) and `--json` (global flag) which take slightly different paths. This pre-existed before this migration and is not introduced by this change.

3. **`formatStatus()` hardcodes status values**: The `formatStatus()` helper function has hardcoded status strings for coloring (`"todo"`, `"in_progress"`, `"ready_for_review"`, `"completed"`, `"blocked"`). This is presentation logic and acceptable in the command layer, though ideally it would use the config-driven color system. This is pre-existing behavior, not introduced by this migration.
