# Task: Implement TaskService CRUD operations (Create, Get, Update, Delete, List)

## Goal

Implement core CRUD and query methods for TaskService (internal/services/task_service.go) to extract basic task data access logic from CLI commands into the service layer. This includes:
- `CreateTask()` - Create new task with validation and file creation
- `GetTask()` - Retrieve task by key
- `UpdateTask()` - Update task fields (title, description, priority, agent type, etc.)
- `DeleteTask()` - Delete task by key
- `ListTasks()` - List tasks with filtering (epic, feature, status, agent type, etc.)

These are foundational operations that enable all downstream task lifecycle methods (StartTask, CompleteTask, etc.) implemented in subsequent features.

## Requirements

### Functional Requirements

**CRUD Operations:**
- [ ] `CreateTask(ctx, input)` - Create task with automatic key generation via creatorSvc, optional file creation, return created task
- [ ] `GetTask(ctx, key)` - Retrieve task by key (supports numeric and slugged formats), return task
- [ ] `UpdateTask(ctx, key, updates)` - Update non-nil fields in TaskUpdates struct, return updated task
- [ ] `DeleteTask(ctx, key)` - Delete task by key, error if dependencies exist
- [ ] `ListTasks(ctx, filters)` - List tasks matching filters (epic, feature, status, agent, show_all, blocked), return sorted task slice

**Input/Output Specifications:**
- [ ] `CreateTaskInput` DTO supports: epic_key, feature_key, title, agent_type, priority, execution_order, depends_on, file_path, create_file, force, description
- [ ] `TaskUpdates` DTO supports: title, description, priority, agent_type, execution_order, file_path (all optional pointers)
- [ ] `TaskFilters` DTO supports: epic_key, feature_key, status, agent_type, statuses (multi), show_all, blocked
- [ ] Tasks returned sorted by execution_order (ascending), then by priority (descending)
- [ ] Completed tasks excluded by default unless show_all=true

**Error Handling:**
- [ ] Return `NotFoundError` when task key doesn't exist
- [ ] Return validation errors for invalid inputs (empty title, priority out of range 1-10, missing epic/feature)
- [ ] Wrap repository and workflow service errors with business context (e.g., "failed to create task E07-F01-001: %w")
- [ ] Validate epic/feature exist before creating task
- [ ] Validate model via `task.Validate()` after creation

**Validation & Business Rules:**
- [ ] Priority must be 1-10 if provided (default: 5)
- [ ] Title required and non-empty
- [ ] Epic key and feature key required for creation
- [ ] Validate status via `workflowSvc.ValidateStatus()` after creation (status defaults to workflow default)
- [ ] Optional dependencies validation (don't validate existence, just store keys)

- [ ] Error messages include task keys for debugging (e.g., "task E07-F01-001 not found")

### Technical Approach

**Architecture Adherence:**
- Service methods call repository interface methods, never direct DB access
- No workflow validation in CRUD (that's for lifecycle methods like StartTask)
- Graceful degradation if creatorSvc is nil (CreateTask proceeds without file creation)
- Error wrapping at service layer adds business context (task key, operation name)
- DTOs (CreateTaskInput, TaskUpdates, TaskFilters) bundle related parameters to avoid parameter explosion

**Key Design Decisions:**
- `CreateTask` uses `creatorSvc.GenerateTaskKey()` to auto-generate key (no need to accept key as input)
- `ListTasks` filters and sorts in service layer (business logic), not repository layer
- Optional dependencies are stored as string keys without validation (validation is skipped for basic CRUD)
- Default priority is 5 if not provided in CreateTaskInput
- Status defaults to workflow service's default status (typically "todo")

**Error Handling Strategy:**
- Repository NotFoundError propagates with added context at service layer
- Validation errors (invalid priority) generated in service layer
- All errors wrapped with task key context for debugging
