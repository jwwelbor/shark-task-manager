# Task: Extract BlockTask UnblockTask ReopenTask orchestration from TaskRepository to TaskService

## Goal

Move `BlockTask()`, `BlockTaskForced()`, `UnblockTask()`, `UnblockTaskForced()`, `ReopenTask()`, and `ReopenTaskForced()` (~lines 1100-1260) from TaskRepository to TaskService. These methods contain workflow transition validation and orchestration logic.

## Requirements

### Functional Requirements

- [ ] Move `BlockTask()` / `BlockTaskForced()` orchestration to `TaskService.BlockTask()`
- [ ] Move `UnblockTask()` / `UnblockTaskForced()` orchestration to `TaskService.UnblockTask()`
- [ ] Move `ReopenTask()` / `ReopenTaskForced()` orchestration to `TaskService.ReopenTask()`
- [ ] Repository retains only the raw status update SQL operations
- [ ] Blocked reason setting moves to service layer
- [ ] All CLI commands calling these methods updated to go through service

### Non-Functional Requirements

- [ ] Existing block/unblock/reopen behavior preserved exactly
- [ ] All existing tests pass
- [ ] New service tests cover block, unblock, reopen scenarios

## Implementation Plan

### Steps

1. [ ] Read current implementations of all 6 methods in task_repository.go
2. [ ] Identify what's business logic vs data access in each
3. [ ] Add/update service methods: `BlockTask()`, `UnblockTask()`, `ReopenTask()` in TaskService
4. [ ] Service methods should: validate transition, call repo for raw update, handle notes/reasons

6. [ ] Update CLI commands (task.go block/unblock/reopen handlers) if they call repo directly
