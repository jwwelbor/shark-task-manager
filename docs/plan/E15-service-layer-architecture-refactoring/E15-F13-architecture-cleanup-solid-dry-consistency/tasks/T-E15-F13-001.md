# Task: Extract status transition orchestration from TaskRepository to TaskService

## Goal

Move the `updateStatusForcedInternal()` method (~144 lines, task_repository.go ~lines 885-1029) from TaskRepository into TaskService. This method currently contains: workflow validation, rejection reason validation, timestamp management (started_at, completed_at, blocked_at), history record creation, rejection note creation, and auto-unblock logic. All of this is business logic that belongs in the service layer.

## Requirements

### Functional Requirements

- [ ] Move orchestration logic from `TaskRepository.updateStatusForcedInternal()` to a new `TaskService` method
- [ ] TaskRepository should only expose a simple `UpdateStatusRaw(ctx, id, status, agent, notes)` that does the SQL UPDATE
- [ ] Timestamp management (setting started_at, completed_at, blocked_at based on target status) moves to service
- [ ] History record creation moves to service (call history repo directly)
- [ ] Rejection note creation moves to service (call note repo directly)
- [ ] Auto-unblock dependent tasks logic moves to service
- [ ] All callers of the old repository methods updated to call service instead

### Non-Functional Requirements

- [ ] No behavioral changes - all existing functionality preserved
- [ ] All existing tests pass after refactoring
- [ ] New service-level tests with mocked repos cover the extracted logic

## Implementation Plan

### Steps

1. [ ] Read and understand `TaskRepository.updateStatusForcedInternal()` completely
2. [ ] Create `TaskService.executeStatusTransition()` (or similar) with the same logic
3. [ ] Reduce `TaskRepository.UpdateStatus()` / `UpdateStatusForced()` / `UpdateStatusForcedWithUnblock()` to simple SQL operations
4. [ ] Update `TaskService.StartTask()`, `CompleteTask()`, `ApproveTask()` etc. to use the new orchestration method
5. [ ] Move `UpdateStatusWithAction()` / `getOrchestratorAction()` (~lines 1031-1098) to service layer
6. [ ] Update all callers (CLI commands, other services) to go through TaskService
7. [ ] Write service-level tests with mocked repos
8. [ ] Run `make fmt && make lint && make test`

### Technical Approach

- The new service method should accept the same parameters but orchestrate: validate transition -> update status -> set timestamps -> create history -> create rejection note -> auto-unblock
- Repository methods become thin: just `UPDATE tasks SET status=?, agent=?, notes=?, started_at=?, completed_at=? WHERE id=?`
- History and note repos already injected into TaskService (or add via setter if not)

## Acceptance Criteria

- [ ] `TaskRepository` has no workflow validation logic
- [ ] `TaskRepository` has no history/note creation logic
- [ ] `TaskRepository` has no auto-unblock logic
- [ ] `TaskService` handles all orchestration for status transitions
- [ ] All existing tests pass
- [ ] New service tests cover: successful transition, invalid transition, rejection note creation, auto-unblock

## Dependencies

- None (this is the first task in the sequence)
