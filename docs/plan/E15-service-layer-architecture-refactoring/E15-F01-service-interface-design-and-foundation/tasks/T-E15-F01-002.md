# Task: Design dependency injection patterns and service constructor pattern

## Goal

Establish standardized dependency injection patterns for the service layer, including service constructors, global service accessors, and lifecycle management. The patterns must support both CLI command usage (via global accessors) and HTTP API usage (via explicit wiring), without introducing external DI frameworks.

## Requirements

### Functional Requirements

- [ ] Design service constructor pattern matching existing Epic/FeatureService (explicit parameter injection)
- [ ] Create global service accessor pattern for CLI commands (e.g., `cli.GetTaskService()`)
- [ ] Design service lifecycle management (initialization, reuse, cleanup)
- [ ] Define service wiring pattern for HTTP API handlers (explicit construction at server startup)
- [ ] Document dependency graph (which services depend on which repositories and other services)
- [ ] Design mock/stub pattern for testing (interface-based dependency injection)

### Non-Functional Requirements

- [ ] No external DI framework dependencies (pure Go constructor injection)
- [ ] Thread-safe initialization using sync.Once pattern (matching existing cli.GetDB pattern)
- [ ] Compile-time safety (constructor signatures enforce required dependencies)
- [ ] Testability via interface substitution (services accept interfaces, not concrete types)
- [ ] Zero performance overhead (<1μs constructor call time as validated in feasibility review)

## Implementation Plan

### Steps

1. [ ] Document existing DI pattern from EpicService and FeatureService constructors
2. [ ] Create `internal/cli/services_global.go` for global service accessors (matching `db_global.go`)
3. [ ] Design `cli.GetTaskService()` function with lazy initialization and sync.Once
4. [ ] Design `cli.GetFeatureService()` and `cli.GetEpicService()` accessor functions
5. [ ] Document service dependency graph (TaskService → TaskRepo + WorkflowSvc + StatusSvc + CreatorSvc)
6. [ ] Create wiring example for HTTP API in `cmd/server/services.go` (explicit construction)
7. [ ] Design cleanup pattern using Cobra PersistentPostRunE hooks (matching DB cleanup)
8. [ ] Document testing pattern: how to inject mocks via interface substitution
9. [ ] Add service constructor validation tests (ensure all dependencies are non-nil)

### Technical Approach

- [ ] **Global Accessor Pattern**: Extend existing `cli.GetDB()` pattern to services (lazy init, singleton per CLI invocation)
- [ ] **Explicit Constructor Pattern**: `NewTaskService(repo, workflowSvc, statusSvc, creatorSvc *T)` with nil checks
- [ ] **Interface-Based Injection**: Services accept repository interfaces, not concrete *Repository types
- [ ] **Lifecycle Management**: Services initialized once per command, cleaned up in PersistentPostRunE
- [ ] **Testing Pattern**: Test code uses `NewTaskService(mockRepo, mockWorkflow, ...)` for isolation
- [ ] **HTTP API Pattern**: Server `main()` constructs all services explicitly, passes to handlers
- [ ] **Dependency Validation**: Constructors panic if required dependencies are nil (fail-fast)
