# Task: Design TaskService interface with CRUD, lifecycle, and query operations

## Goal

Design the complete TaskService interface that will serve as the foundation for extracting task business logic from CLI commands. The interface must support CRUD operations, lifecycle management (start, complete, approve, reopen, block/unblock), querying (next task, list, filters), and dependency validation.

## Requirements

### Functional Requirements

- [ ] Define TaskService struct with repository and service dependencies (workflow, status, taskcreation)
- [ ] Design CRUD method signatures (Create, GetTask, UpdateTask, DeleteTask)
- [ ] Design lifecycle method signatures (StartTask, CompleteTask, ApproveTask, ReopenTask, BlockTask, UnblockTask)
- [ ] Design query method signatures (GetNextTask, ListTasks with filters)
- [ ] Design dependency management method signatures (ValidateDependencies, GetDependencyTree)
- [ ] Define input/output DTOs (CreateTaskInput, TaskUpdates, TaskFilters, NextTaskFilters, DependencyTree)
- [ ] Document method contracts with Godoc comments including error cases

### Non-Functional Requirements

- [ ] All methods accept context.Context as first parameter (context-aware pattern)
- [ ] All methods return error as second value (explicit error handling)
- [ ] Interface follows existing EpicService and FeatureService patterns (consistency)
- [ ] Method signatures support transaction patterns (no concrete DB types leaked)
- [ ] DTOs are serializable to JSON for HTTP API compatibility

## Implementation Plan

### Steps

1. [ ] Review existing EpicService (232 LOC) and FeatureService (239 LOC) for pattern consistency
2. [ ] Analyze task.go CLI command (2,664 LOC) to identify all business logic methods needed
3. [ ] Create `internal/services/task_service.go` with struct definition and constructor
4. [ ] Define CRUD operation signatures (4 methods: Create, Get, Update, Delete)
5. [ ] Define lifecycle operation signatures (6 methods: Start, Complete, Approve, Reopen, Block, Unblock)
6. [ ] Define query operation signatures (2 methods: GetNextTask, ListTasks)
7. [ ] Define dependency management signatures (2 methods: ValidateDependencies, GetDependencyTree)
8. [ ] Create input/output DTOs in `internal/services/task_dto.go`
9. [ ] Add comprehensive Godoc comments documenting expected behavior and error conditions
10. [ ] Validate interface compiles and passes `make fmt && make lint`

### Technical Approach

- [ ] **Constructor Dependency Injection**: Use `NewTaskService(repo, workflowSvc, statusSvc, creatorSvc)` pattern
- [ ] **Repository Abstraction**: TaskService depends on TaskRepository interface, not concrete type
- [ ] **Workflow Integration**: Compose existing `workflow.Service` via `workflowSvc.ForLevel(workflow.LevelTask)`
- [ ] **Status Integration**: Compose existing `status.CalculationService` for progress calculations
- [ ] **Creation Integration**: Compose existing `taskcreation.Creator` for task key generation and file creation
- [ ] **Error Wrapping**: All errors wrapped with business context using `fmt.Errorf("context: %w", err)`
- [ ] **DTO Pattern**: Separate input DTOs (CreateTaskInput) from domain models (models.Task) for validation boundary
