## Summary

The task goal was to reduce `internal/cli/commands/feature.go` from ~2252 lines to ≤350 lines by making every handler a thin wrapper. The `feature.go` file itself passes the line count requirement (344 lines) and the prohibited pattern checks. However, the refactoring has moved the business logic and prohibited patterns into a companion file `feature_helpers.go` (1457 lines) rather than into the service layer. This is a partial refactoring that does not achieve the architectural goal.

## Blocking Issues

### Issue 1 (BLOCKING): `cli.GetDB` called directly in `runFeatureList` (feature.go:186)

`runFeatureList` calls `cli.GetDB(ctx)` directly, then passes the raw `*repository.DB` to helper functions. This is the deprecated anti-pattern that the E15 refactoring exists to eliminate.

```go
// feature.go lines 186-191 - PROHIBITED PATTERN
repoDb, err := cli.GetDB(ctx)
if err != nil {
    handleServiceError(err, "feature", "")
    return nil
}
featuresWithTaskCount, err := fetchFeaturesWithTaskCount(ctx, repoDb, epicFilter, statusFilter, showAll)
```

The database handle is then passed to `outputFeatureListJSON` and `renderFeatureListTable`, which create repositories directly from it. The handler must not touch the database — it should call a service method.

## Non-Blocking Issues (Should Fix)

### Issue 2 (SERIOUS): `feature_helpers.go` is a 1457-line fat controller in disguise

The refactoring moved business logic from `feature.go` into `feature_helpers.go`, which now contains:

- **17 `repository.New*` calls** — direct repository construction from raw DB handles
- **5 `cli.GetDB` calls** — direct database access bypassing the service layer
- Business logic for feature completion (`completeFeatureWithTasks`, `performFeatureComplete`)
- Business logic for feature deletion (`performFeatureDelete`)
- Business logic for feature update (`performFeatureUpdate`, `applyFeatureStatusUpdate`)
- Data fetching loops (`fetchFeaturesWithTaskCount`) that call `featureRepo` directly

Examples:

```go
// feature_helpers.go:803 - fat controller pattern
func fetchFeaturesWithTaskCount(...) {
    featureRepo := repository.NewFeatureRepository(repoDb)    // PROHIBITED
    epicRepo := repository.NewEpicRepository(repoDb)          // PROHIBITED
    // ...
}

// feature_helpers.go:1183 - performFeatureDelete - business logic in command layer
func performFeatureDelete(ctx context.Context, featureKey string, force bool) error {
    repoDb, err := cli.GetDB(ctx)                             // PROHIBITED
    featureRepo := repository.NewFeatureRepository(repoDb)    // PROHIBITED
    taskRepo := repository.NewTaskRepository(repoDb)          // PROHIBITED
    // ... 50+ lines of business logic ...
}

// feature_helpers.go:1242 - performFeatureUpdate - business logic in command layer
func performFeatureUpdate(ctx context.Context, featureKey string, cmd *cobra.Command) error {
    repoDb, err := cli.GetDB(ctx)                             // PROHIBITED
    featureRepo := repository.NewFeatureRepository(repoDb)    // PROHIBITED
    // ... 70+ lines of business logic ...
}
```

The architecture rule is: CLI command layer → service layer → repository layer. Business logic that goes through raw repository access in `feature_helpers.go` bypasses the service layer entirely.

### Issue 3 (SERIOUS): `buildFeatureGetData` in `feature_helpers.go` (lines 700-799) directly constructs 4 repositories

`buildFeatureGetData` creates `featureRepo`, `epicRepo`, `taskRepo`, and `documentRepo` directly from a raw DB handle obtained via `cli.GetDB`. This is 100 lines of fat controller code in the command layer:

```go
// feature_helpers.go:701-711
repoDb, err := cli.GetDB(ctx)
featureRepo := repository.NewFeatureRepository(repoDb)
epicRepo := repository.NewEpicRepository(repoDb)
taskRepo := repository.NewTaskRepository(repoDb)
documentRepo := repository.NewDocumentRepository(repoDb)
```

This should be a service method on `FeatureService`.

### Issue 4 (MODERATE): `renderFeatureListTable` and `outputFeatureListJSON` create repositories for display purposes

The comment in `feature_helpers.go` at line 229 acknowledges this:

> "Note: This function uses `repository.NewTaskRepository` for batch status breakdown fetching which is needed for health indicators. This is presentation data fetching (display only)."

While batch-fetching for display is a reasonable concern, the solution of accessing repositories directly from the command layer is not appropriate. The correct approach is to extend the FeatureService with a list method that returns features with pre-computed status breakdowns, or create a display-specific service method.

### Issue 5 (MINOR): `runFeatureList` passes `repoDb` to rendering functions

Even after fixing Issue 1 by removing `cli.GetDB`, both `outputFeatureListJSON(ctx, featuresWithTaskCount, repoDb)` and `renderFeatureListTable(featuresWithTaskCount, epicFilter, ctx, repoDb)` accept a `*repository.DB` argument. These rendering functions should not need a database handle — they should receive pre-computed display data from a service.

## Required Fixes Before Approval

1. **Remove `cli.GetDB` from `runFeatureList`** (feature.go:186). The list handler must call a service method instead of obtaining a raw DB handle.

2. **Move `performFeatureComplete`, `completeFeatureWithTasks`, `performFeatureCompleteEmpty` business logic into `FeatureService`**. The service already has `DeleteFeature`; it needs `CompleteFeature(ctx, key, force)`.

3. **Move `performFeatureDelete` business logic into `FeatureService`**. Currently `performFeatureDelete` calls `featureRepo.GetByKey`, `taskRepo.ListByFeature`, then `featureSvc.DeleteFeature` — the first two repository calls should be inside the service.

4. **Move `performFeatureUpdate` business logic into `FeatureService`**. The update handler constructs `featureRepo` directly for key validation and file path updates, which should be service-level operations.

5. **Move `fetchFeaturesWithTaskCount` data fetching into `FeatureService`**. Create a `ListFeaturesWithProgress` service method that returns features with computed task counts and status breakdowns, eliminating the need to pass `*repository.DB` to rendering functions.

6. **Remove `buildFeatureGetData` direct repository construction**. This should be a `FeatureService` method like `GetFeatureDisplayData(ctx, key)` returning a DTO.

---

## Architecture Compliance Verdict

The refactoring successfully reduced `feature.go` to 344 lines, but relocated the fat-controller patterns into `feature_helpers.go` rather than the service layer. The business logic is still in the command layer — it is just in a separate file. The E15 goal is to move business logic to `internal/services/feature_service.go`, not to `internal/cli/commands/feature_helpers.go`.

**Decision: REQUEST CHANGES**

The developer should continue the migration by moving the business logic from `feature_helpers.go` into `FeatureService` methods, following the same pattern already established for `featureSvc.GetFeature`, `featureSvc.CreateFeature`, and `featureSvc.DeleteFeature`.
