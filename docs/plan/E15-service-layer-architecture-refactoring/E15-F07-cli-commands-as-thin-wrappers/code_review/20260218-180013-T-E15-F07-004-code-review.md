## Review Criteria

The task goal: `feature.go` and `feature_helpers.go` must be thin wrappers — no `cli.GetDB`, no `repository.New*` calls in the command layer. All business logic must be in `FeatureService`.

### Previous Rejection Reasons

- `runFeatureList` was calling `cli.GetDB` directly at feature.go:186
- `feature_helpers.go` had 17 `repository.New*` + 5 `cli.GetDB` calls with business logic in `performFeatureComplete`, `completeFeatureWithTasks`, `performFeatureDelete`, `buildFeatureGetData`

PASS — `grep -n "repository.New" feature_helpers.go` returns no results.

The `repository` package is still imported in `feature_helpers.go` but is only used in the type signature of `getNextFeatureKey` (line 966):

```go
func getNextFeatureKey(ctx context.Context, featureRepo *repository.FeatureRepository, epicID int64, epicKey ...string) (string, error) {
```

This function is a shared helper called from `idea.go` (not from feature command handlers), so the import is legitimate and not a violation of the thin-wrapper rule. No `repository.New*` constructor calls exist anywhere in this file.

### Key Functions Now Using Service Layer

**`buildFeatureGetData` (was previously flagged):**
All data fetching now goes through `cli.GetFeatureService()`:
- `featureSvc.RecalculateAndSetProgress(ctx, feature.ID)`
- `featureSvc.ListTasksForFeature(ctx, feature.ID)`
- `featureSvc.GetEnrichedTaskStatusBreakdown(ctx, feature.Key)`
- `featureSvc.ResolveFeaturePath(ctx, feature.Key, projectRoot)`
- `featureSvc.ListRelatedDocuments(ctx, feature.ID)`

**`performFeatureComplete` (was previously flagged):**
Delegates entirely to `featureSvc.CompleteFeature(ctx, featureKey, force)`. No direct task queries.

**`performFeatureDelete` (was previously flagged):**
Uses `featureSvc.GetFeature()`, `featureSvc.ListTasksForFeature()`, `featureSvc.DeleteFeature()`. No direct repository calls.

**`fetchFeaturesWithTaskCount`:**
Uses `featureSvc.ListFeaturesByEpicKey()`, `featureSvc.ListFeatures()`, `featureSvc.RecalculateAndSetProgress()`, `featureSvc.GetFeature()`, `featureSvc.GetTaskCount()`.

**`renderFeatureListTable` and `outputFeatureListJSON`:**

## Code Quality Observations

### Positive

1. `feature.go` is now a clean thin wrapper (339 lines total including Cobra command definitions, flags, and 6 lean `runFeature*` handlers averaging ~10 lines each).
2. Every `runFeature*` handler follows the expected pattern: parse args/flags, delegate to helper or service, format output.
3. `buildFeatureGetData`, `performFeatureComplete`, `performFeatureDelete` all go through the service layer — the specific functions named in the previous rejection are now compliant.
4. The `db` package import in `feature_helpers.go` is used only for `db.BackupDatabase()`, which is a database utility function (not a repository constructor), so it is acceptable.

### Minor Observations (Non-Blocking)

1. `feature_helpers.go` at 1307 lines is large. This is a concern for long-term maintainability but is out of scope for this task's criteria. The task requirement was to remove `cli.GetDB` and `repository.New*` calls, which has been achieved.

2. `getNextFeatureKey` (lines 964-996) accepts a `*repository.FeatureRepository` parameter and is used from `idea.go`. This is an older interface; a future task could migrate this to use a service method. However, this is not a `repository.New*` call from the command layer — it receives the repo as a parameter from `idea.go`, which is a separate command file under its own refactoring scope.

3. The `performFeatureComplete` function performs a dry-run call to detect incomplete tasks before the real call. This two-phase pattern is reasonable for the backup/force flow, though it could be further optimized as service-layer logic in a future task.
