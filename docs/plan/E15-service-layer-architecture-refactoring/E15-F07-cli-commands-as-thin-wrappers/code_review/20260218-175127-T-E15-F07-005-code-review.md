## Detailed Findings

### Finding 1 — BLOCKER: `cli.GetDB` calls remain in `epic.go`

**Location**: `epic.go` lines 226, 236

**Code**:
```go
// Line 226 — planning path resolution
if repoDb, dbErr := cli.GetDB(ctx); dbErr == nil {
    info.ResolvedPath = resolveEpicPlanningPath(ctx, epic.Key, repoDb)
}

// Line 236 — main data fetch
repoDb, err := cli.GetDB(ctx)
if err != nil { ... }
data, err := buildEpicGetData(ctx, epic, repoDb)
```

**Why it fails**: The task specification states zero `cli.GetDB` calls in `epic.go`. The `GetEpicService()` and `GetDisplayService()` calls above these lines show the approach is already service-based. The path resolution and data-build calls need to either use service methods or be handled internally by the display/epic service.

**Note on acceptable technical debt**: The task prompt states path-resolution-only `cli.GetDB` calls (line 226) may be considered lower priority. However, line 236 is a clear business logic violation — it obtains DB access for `buildEpicGetData`, which does extensive data aggregation inline. Both need to be addressed.

### Finding 2 — BLOCKER: Business logic relocated to `epic_helpers.go`, not removed

The stated goal of the task is to move business logic from CLI commands into the **service layer** (`internal/services/`). The business logic from the original `epic.go` has been moved into `epic_helpers.go` instead, which is still in the CLI layer. This does not meet the architectural requirement.

Key examples:

**`performEpicComplete` (epic_helpers.go:927-1170)**:
- Calls `cli.GetDB` and constructs `epicRepo`, `featureRepo`, `taskRepo`
- Loops over all features to collect tasks
- Calculates status breakdowns manually
- Forces task completion via `taskRepo.UpdateStatusForced`
- Recalculates feature progress and updates feature status
- Updates epic status

This is 244 lines of business logic that must live in `EpicService.CompleteEpic()`.

**`performEpicCreate` (epic_helpers.go:671-923)**:
- Calls `cli.GetDB` and constructs repositories
- Generates next epic key via `getNextEpicKey` (itself a repo call)
- Validates custom file paths
- Renders templates
- Writes files
- Creates DB entries

This must live in `EpicService.CreateEpic()` receiving a `services.CreateEpicInput` DTO.

**`buildEpicGetData` (epic_helpers.go:440-616)**:
- Receives `*repository.DB` directly (anti-pattern)
- Constructs 4 repositories
- Calls `pathresolver.NewPathResolver` directly
- Aggregates feature details, rollups, impediments, notes, context

This aggregation must be a service method, likely `EpicService.GetEpicDetails(ctx, key)` returning an `EpicDetailsDTO`.

### Finding 3 — BLOCKER: Build failure in `feature_helpers.go`

**Location**: `internal/cli/commands/feature_helpers.go:706,719`

```
featureSvc.ListTasksForFeature undefined (type *services.FeatureService has no field or method ListTasksForFeature)
featureSvc.ListRelatedDocuments undefined (type *services.FeatureService has no field or method ListRelatedDocuments)
```

These methods are called in `feature_helpers.go` but do not exist on `*services.FeatureService`. This was likely introduced by a parallel task (T-E15-F07-004 — feature.go refactor) that added calls to service methods not yet implemented. The build must pass before this task can be approved.

### Finding 4 — Minor: `getNextEpicKey` still calls repository directly

**Location**: `epic_helpers.go:94-111`

```go
func getNextEpicKey(ctx context.Context, epicRepo *repository.EpicRepository) (string, error) {
    epics, err := epicRepo.List(ctx, nil)
    ...
}
```

This helper accepts a raw `*repository.EpicRepository`. It should not exist in the CLI layer — key generation is business logic that belongs in `EpicService.GenerateNextKey(ctx)`.

### Finding 5 — Minor: `status.NewCalculationService` called directly in `performEpicUpdate`

**Location**: `epic_helpers.go:1293`

```go
calcService := status.NewCalculationService(repoDb, cfg)
result, err := calcService.RecalculateEpicStatus(ctx, epic.ID)
```

A CLI command is instantiating an internal service directly with a raw DB handle. This calculation belongs in `EpicService.RecalculateStatus(ctx, key)`.

Extract epic existence check, feature check, backup, and delete into `EpicService.DeleteEpic(ctx, key string, force bool)`.

### P6 — Move `performEpicUpdate` business logic to `EpicService.UpdateEpic`

Extract all update logic including `status.NewCalculationService` usage into `EpicService.UpdateEpic(ctx, key string, updates services.EpicUpdates)`.

### P7 — Move `buildEpicGetData` aggregation to `EpicService`

Replace `buildEpicGetData(ctx, epic, repoDb)` with a service call returning an `EpicDetailsDTO`. The function must not receive a `*repository.DB`.
