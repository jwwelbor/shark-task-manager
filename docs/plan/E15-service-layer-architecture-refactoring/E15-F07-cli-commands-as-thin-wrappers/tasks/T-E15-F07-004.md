# Task: Refactor feature.go CLI commands to thin wrappers (2252→350 lines)

## Goal

Refactor `internal/cli/commands/feature.go` from 2,252 lines (fat controller with ~65% business logic) to at most 350 lines (thin wrappers calling `FeatureService`). Every command handler must follow the three-step pattern: parse args → call service → format output. Progress calculation, health derivation, and action item aggregation must all be delegated to `FeatureService`.

## Design Reference

- Architecture doc: `docs/plan/E15-service-layer-architecture-refactoring/E15-F07-cli-commands-as-thin-wrappers/02-architecture.md` Section 4 (feature.go handler mapping table)
- Feature doc FR-F07-003 and FR-F07-005/006
- Test plan AC3.1-3.6 and Integration Scenario 2

## Requirements

### Handler-to-Service Mapping

| Handler | Service Method | DTO/Input |
|---------|---------------|-----------|
| `runFeatureCreate` | `svc.CreateFeature(ctx, input)` | `services.CreateFeatureInput` |
| `runFeatureList` | `svc.ListFeatures(ctx, filters)` | `services.FeatureFilters` |
| `runFeatureGet` | `svc.GetFeature(ctx, key)` | string key |
| `runFeatureUpdate` | `svc.UpdateFeature(ctx, key, updates)` | `string, services.FeatureUpdates` |
| `runFeatureDelete` | `svc.DeleteFeature(ctx, key)` | string key |
| Feature status transitions | `svc.TransitionStatus(ctx, key, target, opts)` | transition options |

### Prohibited Patterns

After refactoring, none of these may appear in any handler:
- `repository.NewFeatureRepository(...)`, `repository.NewTaskRepository(...)`, `repository.NewEpicRepository(...)`
- `cli.GetDB(...)` followed by direct repository construction
- Progress calculation logic (e.g., `completed / total * 100`, direct math on task counts)
- Health status derivation (if/else chains based on blocked task counts)
- Action item aggregation (loops over tasks to find blocked or ready states)
- Work breakdown calculations

### Required Argument Parsing Helpers

- `parseCreateFeatureInput(cmd, args) services.CreateFeatureInput` - handles positional and flag syntax
- `parseFeatureFilters(cmd, args) services.FeatureFilters` - handles epic filter

## Implementation Plan

### Steps

1. Run `make build` and capture baseline output BEFORE any changes:
   ```bash
   ./bin/shark feature get <existing-key> --json > /tmp/baseline-feature-get.json
   ./bin/shark feature list --json > /tmp/baseline-feature-list.json
   ./bin/shark feature list E15 --json > /tmp/baseline-feature-list-epic.json
   ```

2. Read all of `feature.go` to identify every `func run*` handler and its current structure

3. Start with simple read-only handlers (get, list) - each becomes ~15-20 lines using `cli.GetFeatureService()`

4. Refactor create, update, delete handlers using `svc.CreateFeature()`, `svc.UpdateFeature()`, `svc.DeleteFeature()` (from T-E15-F07-006)

5. Identify any progress display or health display blocks in `runFeatureGet` - these should call `svc.GetProgress()`, `svc.GetHealth()`, `svc.GetActionItems()`

6. Extract `parseCreateFeatureInput()` helper

7. Use `handleServiceError(err, key)` for error handling

8. Remove unused imports

9. Run `make fmt && make lint && make test`

10. Verify: `wc -l internal/cli/commands/feature.go` ≤ 350

11. Verify: `grep -c "repository\.New" internal/cli/commands/feature.go` = 0

12. Compare JSON output with baseline
