# Task: Refactor epic.go CLI commands to thin wrappers (1938→300 lines)

## Goal

Refactor `internal/cli/commands/epic.go` from 1,938 lines (fat controller with ~60% business logic) to at most 300 lines (thin wrappers calling `EpicService`). Every command handler must follow the three-step pattern: parse args → call service → format output. Feature rollup aggregation, impediment analysis, progress calculation, and health derivation must all be delegated to `EpicService`.

## Design Reference

- Architecture doc: `docs/plan/E15-service-layer-architecture-refactoring/E15-F07-cli-commands-as-thin-wrappers/02-architecture.md` Section 4 (epic.go handler mapping table)
- Feature doc FR-F07-004 and FR-F07-005/006
- Test plan AC4.1-4.5, AC5.5, and Integration Scenario 3

## Requirements

### Handler-to-Service Mapping

| Handler | Service Method | DTO/Input |
|---------|---------------|-----------|
| `runEpicCreate` | `svc.CreateEpic(ctx, input)` | `services.CreateEpicInput` |
| `runEpicList` | `svc.ListEpics(ctx, filters)` | `services.EpicFilters` |
| `runEpicGet` | `svc.GetEpic(ctx, key)` | string key |
| `runEpicUpdate` | `svc.UpdateEpic(ctx, key, updates)` | `string, services.EpicUpdates` |
| `runEpicDelete` | `svc.DeleteEpic(ctx, key)` | string key |
| Epic status transitions | `svc.TransitionStatus(ctx, key, target, opts)` | transition options |

### Prohibited Patterns

After refactoring, none of these may appear in any handler:
- `repository.NewEpicRepository(...)`, `repository.NewFeatureRepository(...)`, `repository.NewTaskRepository(...)`
- `cli.GetDB(...)` followed by direct repository construction
- Feature rollup loops (`for _, f := range features { ... }`)
- Task rollup aggregation loops over epic tasks
- Impediment analysis inline logic
- Progress calculation math (`completed / total * 100`, direct division)
- Health status if/else chains based on blocked/ready counts

### Required Argument Parsing Helpers

- `parseCreateEpicInput(cmd, args) services.CreateEpicInput` - handles positional and flag syntax
- `parseEpicFilters(cmd, args) services.EpicFilters` - handles any filter flags

## Implementation Plan

### Steps

1. Run `make build` and capture baseline output BEFORE any changes:
   ```bash
   ./bin/shark epic get <existing-key> --json > /tmp/baseline-epic-get.json
   ./bin/shark epic list --json > /tmp/baseline-epic-list.json
   ```

2. Read all of `epic.go` to identify every `func run*` handler and its current structure

3. Start with simple read-only handlers (get, list) - each becomes ~15-20 lines using `cli.GetEpicService()`

4. Refactor create, update, delete handlers using `svc.CreateEpic()`, `svc.UpdateEpic()`, `svc.DeleteEpic()` (from T-E15-F07-006)

5. Identify any feature rollup display or impediment display blocks in `runEpicGet` - these should call `svc.GetFeatureRollup()`, `svc.GetImpediments()`, `svc.GetHealth()`

6. Extract `parseCreateEpicInput()` helper

7. Use `handleServiceError(err, key)` for error handling

8. Remove unused imports

9. Run `make fmt && make lint && make test`

10. Verify: `wc -l internal/cli/commands/epic.go` ≤ 300

11. Verify: `grep -c "repository\.New" internal/cli/commands/epic.go` = 0

12. Compare JSON output with baseline
