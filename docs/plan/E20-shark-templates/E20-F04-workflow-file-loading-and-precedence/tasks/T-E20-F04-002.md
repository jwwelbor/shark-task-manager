# Task: Implement workflow file loading and per-entity precedence resolution

## Goal

Implement the core two-file loading model in `LoadMultiLevelWorkflow()` within `workflow_parser.go`. The function must detect and load a `.sharkworkflow.json` file, parse entity workflow blocks from it, and resolve per-entity precedence so that workflow file definitions win over `.sharkconfig.json` inline definitions. When no workflow file exists, behavior is identical to the pre-E20-F04 system.

This is the primary implementation task for E20-F04 and covers the bulk of the new code.

## Success Criteria

- `.sharkworkflow.json` is detected and loaded from the same directory as `.sharkconfig.json`
- Per-entity precedence works: workflow file entities win, others fall through to config inline
- No workflow file present: behavior is identical to pre-change (zero breaking changes)
- Error handling: invalid JSON in workflow file returns error; missing file is silent fallback
- All file-source logic is contained within `internal/config/workflow_parser.go`
- All existing tests pass without modification (`make test`)

## Requirements

### Functional Requirements

- [ ] REQ-F04-001: `LoadMultiLevelWorkflow()` detects and loads `.sharkworkflow.json` from the config directory
- [ ] REQ-F04-002: When no `.sharkworkflow.json` exists, system behaves identically to pre-E20-F04
- [ ] REQ-F04-003 AC-1: Per-entity override -- workflow file entities win, others from config
- [ ] REQ-F04-003 AC-2: Full three-tier precedence chain (workflow file > config inline > defaults)
- [ ] REQ-F04-003 AC-3: Precedence resolution happens once inside `LoadMultiLevelWorkflow()`
- [ ] REQ-F04-007: All file-source logic confined to `workflow_parser.go` (no leakage to other packages)
- [ ] REQ-F04-011: Error messages from workflow file failures include the file path

### Non-Functional Requirements

- [ ] REQ-NF04-001: Zero breaking changes -- `make test` passes with no modifications
- [ ] REQ-NF04-003: Single code path -- no workflow-file-awareness outside `internal/config/`
- [ ] REQ-NF04-004: All new tests use `t.TempDir()` and fixture files

## Implementation Plan

### Key Files to Modify

1. `internal/config/workflow_parser.go` -- Add `resolveWorkflowFilePath()`, `loadWorkflowFile()` helpers; modify `LoadMultiLevelWorkflow()` to load workflow file first, then fill remaining nil levels from config

### Steps

1. [ ] Add `resolveWorkflowFilePath(configPath string, rawConfig map[string]json.RawMessage) string` helper -- determines workflow file path (default: `.sharkworkflow.json` in config dir; overridden by `workflow_config` key)
2. [ ] Add `loadWorkflowFile(path string) (map[string]json.RawMessage, error)` helper -- reads and parses workflow file; returns nil,nil if file does not exist; returns nil,error on parse failure
3. [ ] In `LoadMultiLevelWorkflow()`, after parsing `.sharkconfig.json` raw JSON, call the two helpers to load the workflow file
4. [ ] If workflow file data is present, iterate over entity levels (epic, feature, task, bug, change) and parse each block via `parseWorkflowSection()`, setting the corresponding `MultiLevelWorkflow` field
5. [ ] Guard existing `.sharkconfig.json` entity parsing with nil checks (`if result.Epic == nil { ... }`) so workflow-file-sourced values are not overwritten
6. [ ] Handle error cases: invalid JSON returns error with file path; empty file treated as `{}`; unknown keys ignored
7. [ ] Write comprehensive tests

### Technical Approach (from Architecture Doc)

Per ADR-F04-001: All logic lives inside `LoadMultiLevelWorkflow()`.
Per ADR-F04-002: Two-pass fill -- workflow file first, config file second, per-entity granularity.
Per ADR-F04-003: Existing single-key cache (`multiLevelCachePath`) is sufficient.
Per ADR-F04-005: Fail-fast on parse errors; silent fallback on file-not-found.
