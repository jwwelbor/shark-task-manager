# Research Report: B049

## Scope

B049 reports that `shark get --json` and `shark task get --json` only report task-to-task `blocks`/`blocked_by` relationships, silently omitting:
1. Cross-entity relationships (e.g., task blocking a feature, bug blocking an epic)
2. Non-standard relationship types (related_to, follows, spawned_from, duplicates, references, linked_to, question_blocks)

The bug affects reliability of UAT checks and automated gates that depend on `--json` output to assess blocking relationships. In production, a task-feature block (`T-E04-F03-017 blocks E04-F04`) was missed during UAT because `shark get --json` failed to surface it.

This research covers the SQL view architecture, affected data structures, JSON shape constraints, test coverage gaps, and the repair strategy.

- [x] `scope_vocabulary` — Evidence: `internal/db/db.go` lines 3778-3791 (entity_relationships table CHECK constraints define 9 relationship types and 5+ entity types).
- [x] `affected_implementation_or_contract` — Evidence: `internal/db/db.go` lines 2805-2865 (`task_display_data` view hardcodes task-to-task filters) and `internal/services/task_service.go` lines 1231-1237 (task-specific `RelationshipWithTask` struct).
- [x] `pattern_contract` — Evidence: `internal/cli/commands/link.go` lines 221-234 (`shark links` calls `svc.GetRelationships()` against the unrestricted `entity_relationships` table, the correct pattern the view should follow).

## Findings

### 1. SQL View Hardcoding (Root Cause)

The `task_display_data` view contains two hardcoded subqueries for relationship aggregation:

**blocked_by_json (line 2810-2816):**
- Filters: `er.from_entity_type = 'task' AND er.to_entity_type = 'task'`
- Relationship types: Only 'depends_on'
- Joins: Only to `tasks` table (`t2`)
- Result: Cannot show task blocking feature, feature blocking epic, etc.

**blocks_json (line 2819-2833):**
- Subquery 1: `er.from_entity_type = 'task' AND er.to_entity_type = 'task' AND er.relationship_type = 'depends_on'`
- Subquery 2: `er.from_entity_type = 'task' AND er.to_entity_type = 'task' AND er.relationship_type = 'blocks'`
- Result: Silently ignores all other relationship types

**Impact:** The view is an all-or-nothing filter — it cannot partially show relationships. Any cross-entity or non-standard relationship is completely omitted from `shark get --json` output.

### 2. JSON Shape Constraints

The `RelationshipWithTask` struct (internal/services/task_service.go line 1231) assumes the related entity is always a task:

```go
type RelationshipWithTask struct {
    RelationshipType string `json:"relationship_type"`
    Direction        string `json:"direction"`
    TaskKey          string `json:"task_key"`         // ← assumes task
    TaskTitle        string `json:"task_title"`       // ← assumes task
    TaskStatus       string `json:"task_status"`      // ← assumes task
}
```

This structure cannot represent:
- A feature (which has no status in task_status format)
- A bug (which has severity, not task-style status)
- An epic (which has phase-based status different from task lifecycle)
- Non-task entities in general

**Implication for Repair:** The JSON shape must be generalized to support any entity type. Fields like `entity_type`, `entity_key`, `entity_title` would work universally, but `task_key`/`task_status` do not.

### 3. Correct Alternative (shark links)

The `shark links` command (internal/cli/commands/link.go line 221-234) calls `svc.GetRelationships()` directly:
- No type-specific filters
- Returns all relationships regardless of entity type or relationship type
- Service correctly resolves related entity keys and types
- Output includes `entity_type` and `entity_key` fields (lines 216-218)

**Proof:** A task-feature blocking relationship visible via `shark links` is invisible via `shark get --json` because the latter uses the restricted view.

### 4. Real-World UAT False Positive

Bug report description (line 39-40):
> "Real-world instance: `T-E04-F03-017 blocks E04-F04` existed and was visible via `shark links`, but absent from `shark get T-E04-F03-017 --json`'s `blocks` field, causing a UAT check that relied on `shark get --json` to false-positive as 'no blocking relationship'."

This confirms the bug causes:
- Missed dependencies in automated checks
- Data inconsistency between different query paths
- Silent data loss (no error, just omission)

### 5. Database Schema Supports Cross-Entity

The `entity_relationships` table (internal/db/db.go line 3778-3795) was specifically designed to support all entity types and relationship types:
- CHECK constraints on from/to_entity_type: epic, feature, task, bug, change (question missing)
- CHECK constraint on relationship_type: 9 distinct types
- Indexes on from_entity_type/from_entity_id, to_entity_type/to_entity_id, relationship_type
- UNIQUE constraint on (from_entity_type, from_entity_id, to_entity_type, to_entity_id, relationship_type)

The view's restriction is artificial and contradicts the schema design.

### 6. Test Coverage Gaps

Existing tests (task_get_blocking_test.go, task_get_blocking_integration_test.go):
- Only test task-to-task blocking relationships
- Only test `blocks`/`depends_on` relationship types
- No cross-entity test cases
- No tests for related_to, follows, spawned_from, etc.

**Evidence:** grep results show tests only create relationships via entity_relationships with `from_entity_type = 'task'` and `to_entity_type = 'task'`.

### 7. Single-Query Design Intent is Valid

The view was created to avoid N+1 queries on Turso cloud (cost ~150-200ms per round-trip). The fix must preserve this by generalizing within the view, not delegating to separate queries.

**Evidence:** task_service.go line 1256-1257 comment: "reduces round-trips from ~5 to 1, critical for Turso cloud databases".

## Decisions

### D1: Generalize the View, Don't Bypass It
**Decision:** Fix the SQL view itself by removing entity-type and relationship-type restrictions, rather than changing `shark get` to call `shark links` query path.
**Rationale:** The view's single-query design is critical for cloud database performance. Bypassing it would add N+1 query overhead. The view is the right place to own this contract.

### D2: Introduce a Generalized Relationship Data Structure
**Decision:** Create a new `RelationshipWithEntity` struct that represents relationships to any entity type, superseding `RelationshipWithTask`.
**Rationale:** The current struct is task-specific and cannot generalize to other entity types. A new struct allows representation of cross-entity relationships without breaking existing task-only code paths.

**Proposed Structure:**
```go
type RelationshipWithEntity struct {
    RelationshipType string `json:"relationship_type"`
    Direction        string `json:"direction"`    // "incoming" or "outgoing"
    EntityType       string `json:"entity_type"` // "task", "feature", "epic", "bug", "change"
    EntityKey        string `json:"entity_key"`
    EntityTitle      string `json:"entity_title"`
    EntityStatus     *string `json:"entity_status,omitempty"` // nil for entities without status
}
```

### D3: Backward Compatibility via Dual Field Names
**Decision:** Keep `TaskKey`, `TaskTitle`, `TaskStatus` fields in JSON output for existing code, but populate from the generalized relationship data.
**Rationale:** Allows existing clients to continue working while new clients can use `EntityType` to handle any entity type.

### D4: Update the View Subqueries to Support All Types
**Decision:** Replace hardcoded type filters with UNION queries that aggregate relationships across all entity types and relationship types.
**Rationale:** Allows single query to handle all relationship scenarios without N+1 overhead.

## Work Breakdown

The repair extends the existing `task_display_data` view rather than creating new work:

- **Modify View SQL:** Generalize blocked_by_json and blocks_json subqueries (~30-40 lines, complex SQL with UNION)
- **Update JSON Struct:** Create RelationshipWithEntity struct (~15 lines)
- **Update Unmarshaling:** Adjust task_query_service.go to handle generalized JSON (~10 lines)
- **Add Test Coverage:** Create integration tests for cross-entity and non-standard relationship types (~200 lines)
- **Backward Compatibility:** Ensure task_key/task_title/task_status fields remain populated for existing clients (~5 lines)

**Scope Classification:** EXTEND existing capability + NEW test coverage. Not a breaking change if backward compatibility is maintained.
