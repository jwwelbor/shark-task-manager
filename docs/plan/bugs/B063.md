# Custom --key flag on feature/task create is silently ignored; duplicate-key errors don't suggest next available

## Description

shark epic create <title> --key=<key> works, but --key on feature/task create is broken:

- feature create: CLI defines --key (featureCreateKey) but never reads it after flag parsing; services.CreateFeatureInput (internal/services/epic_dto.go:66) has no CustomKey field; FeatureService.CreateFeature (internal/services/feature_service.go:1096) always calls s.nextFeatureKey(...) with no custom-key path. Command accepts the flag with no error and silently auto-generates a key instead.
- task create: no --key flag exists at all on the CLI (internal/cli/commands/task.go), even though taskcreation.CreateTaskInput already has a CustomKey field (internal/taskcreation/creator.go:97) that the creator likely honors — the plumbing exists at the service layer but was never exposed on the CLI.
- Duplicate-key handling only exists today for epic (EpicService.CreateEpic, internal/services/epic_service.go:513-520) and just errors 'epic with key already exists' without suggesting the next available key. Once feature/task support --key, they need the same duplicate check, and all three (epic/feature/task) should suggest the next available key in the error response.
- Verified out of scope: bug/change-card/tech-debt/idea entities have no --key flag and no custom-key concept (auto-numbered) — nothing to fix there, confirmed via grep across internal/cli/commands/{bug,change,change_card_commands,tech_debt,idea}.go.

Acceptance:
1. shark feature create <epic> <title> --key=<KEY> sets the feature's key to KEY (uppercase-normalized), following the same validation/uniqueness pattern as epic.
2. shark task create <epic> <feature> <title> --key=<KEY> flag added to CLI and wired to the existing CustomKey plumbing in taskcreation.CreateTaskInput.
3. Duplicate-key create errors for epic, feature, and task include the next available auto-generated key as part of the error/response so the caller can retry immediately.
4. Tests cover: custom key create success for each of epic/feature/task, duplicate-key rejection with suggested-next-key for each, and that bug/change/tech-debt/idea remain unaffected (no --key flag added there).

## Expected Behavior

`shark feature create` and `shark task create` should honor `--key=<KEY>` the same way `shark epic create` does: use the supplied key (uppercase-normalized) instead of auto-generating one, and reject it with a helpful error (including the next available key) if it's already taken.

## Actual Behavior

- `shark feature create <epic> "<title>" --key=<KEY>` is accepted with no error but the key is silently discarded — a feature is created with an auto-generated key instead.
- `shark task create <epic> <feature> "<title>" --key=<KEY>` fails with `unknown flag: --key` — the flag doesn't exist on the command at all.
- `shark epic create "<title>" --key=<KEY>` where `<KEY>` already exists returns `epic with key '<KEY>' already exists` with no suggested alternative.

## Steps to Reproduce

1. `shark feature create E01 "Test Feature" --key=F99` → feature is created but its key is the next auto-generated `F##`, not `F99`.
2. `shark task create E01 F01 "Test Task" --key=E01-F01-099` → `Error: unknown flag: --key`.
3. `shark epic create "Existing Title" --key=E01` (where `E01` already exists) → `epic with key 'E01' already exists`, no next-available suggestion.

## Fix Notes

Root cause locations:
- `internal/cli/commands/feature.go:180` — `featureCreateCmd.Flags().StringVar(&featureCreateKey, "key", ...)` declares the flag; `featureCreateKey` is never read again outside flag registration.
- `internal/cli/commands/feature_helpers.go:970-981` (`parseCreateFeatureInput`) — builds `services.CreateFeatureInput` without a key field.
- `internal/services/epic_dto.go:66` — `CreateFeatureInput` has no `CustomKey` field (unlike `CreateEpicInput` at line 20).
- `internal/services/feature_service.go:1096` (`CreateFeature`) — always calls `s.nextFeatureKey(...)`; no custom-key branch (contrast with `EpicService.CreateEpic`, `internal/services/epic_service.go:513-524`, which has the pattern to follow).
- `internal/cli/commands/task.go` — no `--key` flag registered at all, despite `taskcreation.CreateTaskInput.CustomKey` (`internal/taskcreation/creator.go:97`) already existing in the service layer.
- `internal/services/epic_service.go:513-520` — duplicate-key check returns a plain error; extend to compute and include the next available key (reuse `nextEpicKey`/`nextFeatureKey`/task-key-equivalent logic) once feature/task get their own custom-key branches.
