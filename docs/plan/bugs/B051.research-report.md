# Research report — `shark run` pauses a dispatchable tech-debt step

## Scope

B051 covers the `shark run` controller path for a tech-debt entity at
`in_progress`. The canonical tech-debt workflow declares
`check_or_resume` with a developer dispatch specification at that step. The
keyed `shark next` path treats that action as `spawn_agent`, but the run
controller groups it with manual pause actions and returns `paused`.

This report covers the action-routing contract, its immediate workflow and CLI
consumers, and the regression-test seam. It does not change workflow semantics,
claims, or session-resume behavior. The repair extends the existing runner
dispatch capability; it does not create a new capability.

## Research checklist

- [x] `scope_vocabulary` — Evidence: `docs/plan/bugs/B051.md`, `internal/sharkdata/default_data/workflow/tech-debt.yaml`, and `docs/architectural-overview.md` define the affected entity, `in_progress` step, action names, and the intended resume-or-spawn meaning.
- [x] `affected_implementation_or_contract` — Evidence: `internal/runner/controller.go` lines 341-350 and 493-521 route run actions; lines 496-500 currently return `paused` for `check_or_resume`. `internal/cli/commands/next.go` lines 1175-1198 maps the same action to `spawn_agent`.
- [x] `pattern_contract` — Evidence: `internal/runner/controller.go` lines 774-853 and its `handleSpawnAgent` helper own the shared dispatch, transition, provider, prompt-assembly, and outcome path. `internal/cli/commands/next_normalize_test.go` lines 44-54 is the existing wire-normalization guard.

## Findings

1. **The defect reproduces directly from the run action switch.** At
   `in_progress`, the tech-debt workflow supplies `check_or_resume`, developer,
   provider, model, skills, prompt, and outcomes
   (`internal/sharkdata/default_data/workflow/tech-debt.yaml` lines 31-49).
   `RunController.Run` retrieves that populated action, then its switch matches
   `ActionCheckOrResume` in the pause branch and returns `Outcome: "paused"`
   without calling a dispatcher (`internal/runner/controller.go` lines 493-500).
   The runner test baseline passes because no runner test mentions
   `CheckOrResume`; the existing pause test proves only the deliberate pause
   branch.

2. **`shark next` establishes the contrary, dispatchable contract.**
   `normalizeWireAction` converts both `spawn_agent` and `check_or_resume` to
   the wire action `spawn_agent` (`internal/cli/commands/next.go` lines
   1175-1188), and `TestNormalizeWireAction` asserts that mapping
   (`internal/cli/commands/next_normalize_test.go` lines 44-54). A tech-debt
   caller therefore receives a dispatchable prompt from `next` but a paused
   result from `run` at the same workflow step.

3. **The workflow action is intentional and should remain distinct.**
   Architecture documentation defines `check_or_resume` as resuming an
   in-progress session or spawning one when none exists
   (`docs/architectural-overview.md` lines 191-201). The workflow action
   validator and provider validation also classify `check_or_resume` as a
   dispatch action (`internal/config/action/orchestrator.go` lines 43-63 and
   `internal/cli/commands/workflow_validate_actions.go` lines 258-268). Changing
   the YAML to `spawn_agent` would conceal the runner defect and discard the
   declared resume-aware intent.

4. **The repair has one production seam.** `handleSpawnAgent` already owns
   prompt assembly, provider selection, dispatch, semantic outcome parsing,
   guarded transition, stage logging, and dry-run handling. Route
   `ActionCheckOrResume` to that helper with `ActionSpawnAgent`; leave only
   `ActionPause` and `ActionWaitForTriage` in the pause branch. This preserves
   the action name for downstream worker/session behavior while making the run
   controller consistent with keyed dispatch.

5. **A focused runner regression test is missing.** Add a controller test with
   a populated `ActionCheckOrResume`, an `anthropic` mock dispatcher, and a
   forward transition. Assert that the dispatcher receives the assembled
   prompt, the provider and agent metadata pass through, the transition uses
   the worker's outcome, and the result is not `paused`. This test fails under
   the current switch and protects the run/next parity without requiring an
   external AI process or a real database.

## Decisions

1. Fix the run controller, not the tech-debt workflow. Add
   `config.ActionCheckOrResume` to the dispatch case that calls
   `handleSpawnAgent`, and remove it from the pause case.
2. Preserve the existing `check_or_resume` action and its dispatch
   specification. Its semantic distinction remains available to the worker or
   session layer; the controller must not reinterpret it as a manual stop.
3. Add a focused unit test at the runner boundary. Reuse the existing mock
   transitioner, populated action service, and provider-keyed dispatcher. Do
   not introduce a new session subsystem, workflow validation rule, or
   integration-only test for this repair.
4. Verify the implementation with the targeted runner package and the normal
   formatting, lint, and full-test gates required for Go changes.
