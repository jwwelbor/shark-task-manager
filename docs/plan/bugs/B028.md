# next.go/cascade.go ship hardcoded terminal-status lists, regressing T-E07-F26 workflow.Service migration

## Description

Code review of commit 6492e45 ("shark 2 updates, big commit with internalization") found two hardcoded terminal-status lists `{"completed","cancelled","archived","done"}` shipped in new CLI command files:

- `internal/cli/commands/cascade.go` — `isTerminalStatus()` (originally split as `isTerminalTaskStatus` / `isTerminalFeatureStatus`; the simplify pass collapsed them but the static list remained)
- `internal/cli/commands/next.go:379-386` — `isArchivedStatus()`

Both should delegate to `workflow.Service.IsTerminalStatus()` — the config-driven helper already used by `feature_progress_service.go`, `sprint_service.go`, `task_service.go`, `cascade_reopen.go`, and others. `workflow.Service` is a global singleton; the perf reasoning the author cited (avoid action-service round-trips) does not apply to it.

This is a direct regression of:
- T-E07-F26-004 — Replace hardcoded status validation with `workflow.Service`
- T-E07-F26-006 — Replace direct status string comparisons in commands

…both of which deliberately removed this anti-pattern from the codebase, and both of which were merged before commit 6492e45.

## Expected Behavior

Terminal/archived-status detection in `cascade.go` and `next.go` consults `workflow.Service.IsTerminalStatus()` (and the workflow's configured terminal/archived statuses) rather than a hardcoded literal list. Custom workflows that rename or reorder terminal statuses behave correctly.

## Actual Behavior

A custom workflow that renames `"completed"` to something else (entirely supported per the config-driven design) silently misbehaves: cascade resolution recurses into entities that should be filtered out, and dispatches `pause` for siblings that should have been `spawn_agent`. The architectural rule "Status values are config-driven. Never hardcode status names" (`.claude/rules/go/patterns.md`) is violated.

## Steps to Reproduce

1. Configure a custom workflow that uses, e.g., `"shipped"` instead of `"completed"` as the terminal status for tasks.
2. Mark a child task `shipped`; leave a sibling task in `todo`.
3. Run `shark next <parent-feature-key>`.
4. Observe that cascade resolution treats the `shipped` task as non-terminal (recursing into it) instead of filtering it out, and may return `pause` instead of `spawn_agent` for the sibling.

## Fix Notes

- `cascade.go`: replace `isTerminalStatus(s string) bool` with a call to `cli.GetWorkflowService().ForLevel(entityType).IsTerminalStatus(status)`. The entity type is already known at the call site (we're iterating tasks for a feature parent, or features for an epic parent).
- `next.go`: `isArchivedStatus` should keep its suffix-match behavior for legacy `_archived` patterns but consult `workflow.Service` for the canonical terminal/archived set.
- Companion fat-controller bug (B029) overlaps in scope — coordinate the two fixes.
- Closely related: TD-011 (same idiom in sprint service).
