# B077 Research Report

## Scope

Research the Rider host-adapter handoff after keyed `shark next <key> --json` for native Codex worker launches: whether Shark's requested provider/model is mapped to the worker launch and whether the effective route can be verified. The affected terms are distinct: `agent_type` is the Shark persona, the host worker class selects a native execution profile, provider/model identifies the requested runtime, and `effort` is a reasoning setting. Prompt rendering and benchmark-only routing are adjacent capabilities, not the target behavior.

## Findings

### Reproduction and affected capability

Metadata-only reinspection of all six sampled Codex worker session logs named in B077 confirms each records `gpt-5.6-luna` with `xhigh` effort. The retained parent-session evidence in B077 records native spawn calls without model overrides. This reproduces the observed inherited-model symptom. The separate B101/B100 Shark inspection metadata is not keyed to these six launches, so it does not prove that a particular Anthropic route was replaced by Luna.

The affected operational entry point is Rider's `spawn_agent` path in `skills/shark-rider/verbs/run.md`. `internal/cli/commands/next.go` copies the populated provider, model, and effort into the wire response. Rider describes provider values including `openai` and `codex`, but its concrete host mapping selects a model only for the Claude Code Agent tool when the provider is `anthropic`; it also says not to pass a non-Claude model to that tool. The Codex native launch mapping and a check of the effective worker model are absent from this contract. Therefore the route gap is reproducible from the tracked dispatch contract even though the historical request-to-session causality remains unproven.

### Existing patterns and dependencies

`skills/shark-rider/context/host-adapter-contract.md` already transports requested `provider`, `model`, and `effort` alongside the exact prompt and its hash/byte count. Its result fields identify the worker/session and returned envelope, but do not attest requested versus effective provider/model. This is the nearest existing capability to extend.

There is an explicit Codex model-selection pattern in `internal/runner/codex_dispatcher.go`: when `input.Model` is present, the `codex exec` dispatcher passes it with `-m`. That is a separate CLI runner, not evidence that Rider's native Codex host launch accepts or applies the same setting. The Codex provider reference is explicitly scoped to Codex CLI. E34-F01's hybrid-routing decision likewise assigns final model and execution-profile selection to the client/harness, while E40-F13's routing work is limited to benchmark execution. Neither closes the native Rider route gap.

The boundary crosses Shark's dispatch response, Rider's host-specific spawn adapter, and the worker session that reports its effective model. If the adapter treats effort or worker class as model selection, silently omits the model, or records only the request, parent inheritance can appear as a successful dispatch. A repair must preserve the exact `response.prompt` bytes and keep persona, worker class, provider/model, and effort separate. Current repository sources do not establish which model identifiers the native Codex host API accepts; that host capability must be verified as part of implementation.

## Decisions

1. Repair extends the existing E38-F09/Rider host-adapter capability; it does not create a new provider or a separate model-routing feature.
2. Add provider-specific mapping for native Codex only where the host adapter can select the requested model and verify the resulting worker identity. Record requested and effective provider/model separately from Shark persona, host worker class, and effort. If a requested route is unsupported or cannot be verified, report that route as unsupported/unverified instead of silently using the parent's model.
3. Keep `response.prompt` byte-for-byte unchanged. Verify a future keyed dispatch by correlating its requested route and prompt hash with the native launch arguments and that worker's session metadata; do not infer correlation from separate entity inspection metadata.
4. Treat `internal/runner.CodexDispatcher` as a feasible alternative execution path only if Rider is deliberately routed through that CLI adapter. Its `-m` support alone does not repair or attest a native Codex launch.
5. The observed S010 worker model is supported, but the specific Shark request that led to each sampled session remains unknown. Do not attribute S010 failures to model substitution without that correlation.
