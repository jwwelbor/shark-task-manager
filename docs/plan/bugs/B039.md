# Sprint analytics can overcount completions and hide summary or burndown errors

## Description

Full code review on 2026-07-07 found GetSummary counts every status transition as a completion instead of terminal outcomes, runSprintSummary swallows errors and ignores json mode, GetVelocityData failures are discarded, burndown uses local today against UTC sprint dates, and non-task completions never reduce remaining work. See dev-artifacts/2026-07-07-full-code-review/code-review-report.md sections C2, M12, and M15.

## Expected Behavior

Sprint summary and burndown should count only terminal completions, surface real
errors to the caller, and compute "today" and remaining work consistently across
entity types and timezones.

## Actual Behavior

Summary builds its completed set from every status transition row, not terminal
statuses. The CLI summary path swallows errors and ignores `--json`, velocity
fetch failures are discarded, burndown uses local "today" against UTC dates, and
completed non-task entities do not reduce actual remaining work.

## Steps to Reproduce

1. Advance a sprint task from `todo` to `in_progress` without completing it.
2. Run `shark sprint summary <sprint-key>` and observe it counted as completed.
3. Compare burndown behavior around local-midnight or with completed non-task
   entities present in the sprint.
