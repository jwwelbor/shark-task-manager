# B083 repair plan

## Diagnosis

The E40 benchmark path preserves workflow route fields until it reaches the
provider adapter, but it does not resolve the selected harness against those
routes. On the declared review baseline, the Codex branch of
`lifecycle-worker-adapter.sh::command_for()` drops `request.model`; the
read-only `bench-working` comparison forwards `-m` but also forwards an
incompatible Claude/Sonnet model unchanged. `load_routing_profile()` and
`apply_routing_profile()` exist in `e40_benchmark.py`, but research found only
their definitions and test callers. Profile selection is not wired into the
production run path, and current route digests describe the workflow before
any profile application.

Codex route preparation needs two separate facts: which model identifiers the selected Codex CLI advertises, and whether a particular run can use the selected route. The supported app-server `model/list` RPC supplies model identifiers, display names, descriptions, and supported reasoning efforts. The installed CLI returned the models shown in the user's picker, plus additional catalog entries. OpenAI's app-server documentation cautions that `model/list` may be bundled or cached, so it proves advertised CLI compatibility, not account entitlement. Use it as a dynamic catalog, never as a hardcoded allow-list. Let an actual dispatch establish whether the selected account can use the route. Do not read an undocumented token store, call `/v1/models`, or start inference during preflight.

## Proposed repair

1. Wire the existing E40-F13 versioned routing profile mechanism into the
   production benchmark run as an explicit `routing_profile` selection, kept
   distinct from the existing baseline/variant comparison `profile`. A
   selected routing profile is the operator's explicit harness switch and
   supplies the provider and route intent for every live workflow stage. For a
   Codex route, an explicit model pin stays exact; if the model is omitted,
   resolve the single model marked `isDefault` by the live catalog. If effort
   is omitted, use that model's `defaultReasoningEffort`. Extend the profile
   schema to allow these omissions for Codex only. Keep other providers'
   current explicit route requirements. Validate complete stage coverage before
   dispatch. Do not infer routes from `capability_profile`, inherit a parent
   model, or silently replace an explicit model pin. If no routing profile is
   selected, preserve explicit workflow route fields; resolve a missing Codex
   model or effort by the same documented catalog-default rule.
2. Apply the selected profile to a run-scoped copy of the workflow bundle.
   Never call the current in-place profile helper on the shared source bundle.
   Reject invalid profiles, missing stage routes, or a route whose provider
   does not match the selected harness before starting a worker. Preserve the
   profile version, source digest, and exact effective provider/model/effort
   tuple in the run manifest and adapter request.
3. Add a read-only Codex catalog preflight. Resolve the same CLI executable,
   configuration, and environment that the adapter will use. Start that CLI's
   supported app-server interface, initialize it, and read every page of
   `model/list`. Never query one Codex installation and dispatch through a
   different executable or configuration. Exclude hidden entries. Use the
   returned `model` identifier as
   the exact CLI route value and use each entry's `supportedReasoningEfforts`
   to validate any explicit effort. If model or effort is omitted, resolve it
   only from a unique catalog `isDefault` model and that entry's
   `defaultReasoningEffort`. An explicit model pin that is absent from the
   catalog fails; it never falls back to the default. Never embed, copy, or
   maintain real Codex model identifiers as code constants, supported-model
   lists, sample Codex profiles, or test fixtures. Use synthetic identifiers
   in tests. Keep the catalog source, CLI version, and catalog digest with the
   route evidence without copying credentials or secret configuration. If the
   catalog is unavailable, malformed, has no unique
   default when needed, or does not contain the selected model or effort,
   record a named unresolved route and fail before adapter dispatch. Reuse the
   existing `resolution: failed`, `cause_class: route_defect` ledger contract.
4. Do not require a separate account-specific model-list request during route
   preparation. `model/list` is catalog evidence, not proof of account access.
   Once a catalog-advertised route is selected, dispatch that exact provider,
   model, and effort tuple. If Codex rejects the request for access, quota, or
   service reasons after the attempt starts, record the failure against that
   exact route. Do not silently substitute another model or provider.
5. Fix Codex command construction to pass the selected route model using the
   CLI model option, including when a configured executable override is used.
   Reject an opaque command override if it cannot preserve the provider/model/
   effort tuple. Bind routing identity after profile materialization, then pass
   the same effective tuple and routing digest to each adapter request and
   manifest entry.

The existing route preview already separates stage resolution from adapter
execution. Extend that boundary to read or inject the dynamic model catalog
without starting inference. A listed model is not evidence of account
entitlement or successful service; only a real attempt can establish that, and
any failure must retain the exact attempted route in the evidence.

## Scope and preserved behavior

**Complexity M.** The repair spans benchmark configuration, profile
materialization, route preflight, identity capture, and the adapter boundary.
Implementation is limited to E40's `bench/` production path and its tests.

- Extend the existing E40-F13 profile/schema and run configuration rather than
  creating a parallel router. Preserve explicit stage `provider`, `model`, and
  `effort`; only an explicitly selected routing profile may replace them.
- Preserve `identity.provider_routing`'s provider/model/effort digests and
  comparison identity, but compute them from the effective run-scoped workflow
  after the selected profile is applied. The adapter request, manifest, and
  route evidence must identify that same effective tuple.
- Preserve source workflows, profiles, and repository files byte-for-byte
  during materialization. Preserve the current Claude and Copilot adapter
  contracts, measurement normalization, scratch-root isolation, and cost
  honesty. Do not change native Shark Rider launch behavior or claim B077 is
  fixed; B077 is a separate boundary.
- Preserve the existing parent-owned Shark claims, heartbeats, transitions,
  and releases. This repair changes E40 route preparation and adapter command
  construction only.
- Do not run a live provider or account canary as part of unit, contract, or
  route-preview tests. Use fake CLI/catalog/adapter seams. A later live
  benchmark requires its own explicit authorization and evidence.

## Review baseline and rework rules

The immutable review baseline is
`bbf490c6ec2bd597d6f3e6e4cdd93e68ca54fa50` (the B084 merge on `origin/main`;
tree `0764bb9a04abc4c8001bd1ec9cc88d709bcc2ad5`). It is an ancestor of the
assigned branch and predates B083's research commits and this plan. Independently
reconfirm this full commit at plan review and carry the same baseline through
development, code review, and QA. Do not substitute a later mainline tip.

Use the committed project document for planning and independent plan review.
Register the plan and its separate mutable evidence record as related documents.
After approval, the parent supplies the approved snapshot path and digest for
downstream work. Update only the evidence record as verification evolves; a
material diagnosis, scope, approach, or assertion change requires a new plan
revision and independent review. Candidate changes invalidate code review and
QA. Retain all findings and route to the earliest invalidated stage. A missing or malformed runtime CLI catalog is `blocked`, never acceptance. A catalog-advertised route proceeds to the exact adapter attempt; account or service rejection is recorded against that attempted route.

## Verification design

Use deterministic fixtures for selected profiles, workflow copies, a paginated
fake Codex app-server catalog, CLI argv, manifests, adapter call counts, and
route-ledger records. Bind discovery and dispatch to the same executable and
effective configuration; reject catalog evidence from a different CLI identity. Use only synthetic fixture identifiers, never current
production model IDs. Add paired green/red assertions: a listed explicit pin
with a supported effort reaches the adapter unchanged; an omitted Codex model
resolves to one unique catalog default; an omitted effort resolves to that
model's advertised default; an unsupported explicit pin, missing/ambiguous
default, unsupported effort, malformed catalog, or failed catalog request
blocks before dispatch. A changed effective route changes identity, and source
configuration stays unchanged. Simulate a post-start provider access denial
and verify that the attempt ledger retains the exact route and does not fall
back. Do not run an account query or inference as part of these checks. Run the
applicable E40 routing, adapter, identity, and route-preview suites after
implementation, then the project's required quality gate. Record commands and
results in the mutable evidence record.
