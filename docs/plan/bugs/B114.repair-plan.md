## Diagnosis

`taskcreation.Creator.CreateTask` records `fileExists` during custom-path
preflight; generated task paths leave that value false. Later,
`EntityFileWriter.WriteEntityFile` can encounter a path created after
preflight and return `Written=false, Linked=true`. If the task transaction's
commit then fails, cleanup based only on `!fileExists` treats that stale
preflight result as proof of ownership and removes a file this invocation did
not create. The same stale-false condition also removes a pre-existing file at
a generated path. The database transaction rolls back, but the unrelated file
is lost.

The ownership fact needed for cleanup is the writer result and the identity of
the file it created. A preflight `Stat`, another `Stat`, or `Linked` alone
cannot establish that this invocation owns the path.

## Accepted approach

On transaction commit failure, compensate only when the writer returned a
non-nil result with `Written=true`. Pass its `CreatedFileInfo` to the existing
task-file cleanup helper. The helper checks the current path with `Lstat` and
compares it to the captured identity with `os.SameFile`; remove the path only
when the identity still matches. Preserve and warn when identity is absent,
the path is missing, the stat fails, or a replacement is detected. Linked
results (`Written=false, Linked=true`) and pre-existing custom paths skipped
by the writer receive no cleanup.

This applies the later B114 Architect decision, Shark B114 note 3630. It
refines the earlier research recommendation to gate on `Written=true` by also
checking `CreatedFileInfo` before removing the path. It does not claim an
atomic conditional unlink: the check and `os.Remove` are separate operations.

## Preserved behavior

- Existing task-file linking stays available for custom and generated paths.
- `WriteResult.Written` and `WriteResult.Linked` retain their existing
  meanings; no writer API or CLI contract is introduced.
- A failed task commit returns an error and does not publish task or
  task-history rows.
- A file created by this invocation is removed after commit failure only when
  its captured identity still matches the target path.
- Successful linking preserves the existing bytes, commits the task, and
  returns `FileWasLinked=true` with the same task file path.
- Transaction ordering, dependency and history insertion, the aggregate hook,
  task-key generation, and caller error propagation remain unchanged.
- `TaskService.CreateTask` attaches tags and updates the search index only
  after `Creator.CreateTask` succeeds; the CLI continues to surface errors
  from the service.

## Constraints and accepted boundary

The compensation guarantee covers cooperating task creators using
no-replace publication. `Lstat`/`SameFile` followed by `os.Remove` is not
atomic. A non-cooperating process can replace or edit the target in the
check-to-remove interval; that interval is an accepted limitation under
Architect decision note 3630. Preserve the file and warn when a replacement
is observed before cleanup. Orphan reconciliation remains manual. Do not
claim protection for Force writers or cross-store atomicity.

No conflict remains between the earlier B115 research note 3626 and the later
B114 Architect decision note 3630: note 3626 required an explicit ownership
boundary; note 3630 records the accepted cooperating-writer boundary and
manual-reconciliation trade-off. If a reviewer finds a newer accepted
decision that changes this authority, stop at the plan gate and route the
conflict to its owner; do not silently broaden this plan.
