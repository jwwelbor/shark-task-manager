# B056 Research Report: postrun scratch-cleanup race

## Scope

B056 concerns the single-run benchmark driver's transition from the completed
or capped `shark run` invocation into its postrun artifact and measurement
pipeline. The affected vocabulary is the parent `run-one.sh` process, its
background timeout watchdog, the parent-owned scratch directory and fixture
checkout, and the postrun steps that use that checkout to produce `post/*` and
`record.jsonl`.

This is not a change to the pinned toolchain-guard, LOC, quality, ledger-diff,
or F2P ordering contract. Those stages are consumers of a checkout that must
remain available until the parent finishes postrun. The related E40-F02 driver
tasks establish the existing capability and its contract.

## Findings

1. The original race is in ownership of the scratch-cleanup EXIT trap, not in
   an ordering race among toolchain guard, ledger construction, and collection.
   `run-one.sh` starts the watchdog as a background subshell, then cancels and
   waits for it immediately before printing `phase=postrun`. A child shell
   inherits the parent's EXIT trap. If cancellation made that watchdog run the
   inherited cleanup, it could remove the scratch directory and its checkout
   while the parent was about to consume them.

2. The resulting symptom matches B056. The first postrun filesystem operation
   that needs the deleted checkout is the intent-to-add `git add`, whose output
   is deliberately redirected. Under `set -e`, a missing checkout can end the
   parent directly after `phase=postrun` without a useful diagnostic. Later
   operations (`git diff`, Go quality checks, `build-ledgers.sh`,
   `diff-ledgers.sh`, F2P injection, and `collect-run.sh`) all likewise depend
   on that checkout or the artifacts it produces.

3. This repair is already present in the current capability. Commit
   `779527d7` added a top-level `cleanup_owner_pid` guard so only the parent
   can remove scratch state, and clears the inherited EXIT trap in both the
   invocation child and watchdog. TC-014l deliberately holds the stubbed run
   long enough to make watchdog cancellation relevant, then requires a
   successful record; its comments name the pre-fix deletion before postrun
   collection as the failure it prevents.

4. `bench/fixture-repo` is initialized in this worktree. The focused
   `tc014_run_one_smoke_test.sh` passed, including TC-014l's delayed watchdog
   cancellation case and its required postrun record. Historical serialized
   evidence also records that an earlier TC-014 failure was associated with
   overlapping benchmark processes, rather than a reproducible isolated
   postrun failure; retain serialized and overlap stress verification before
   declaring concurrent-run reliability proven.

## Decisions

1. Treat the root cause as an inherited-cleanup ownership race. Do not change
   the documented postrun stage ordering or add synchronization between its
   individual commands; that would address the symptom at the wrong boundary.

2. Retain the existing repair: bind destructive cleanup to the top-level Bash
   process and reset inherited EXIT traps in every child whose cancellation can
   occur before the parent consumes scratch evidence. TC-014l is the local
   regression pattern for that contract.

3. The repair extends the existing `run-one.sh` capability; it creates no new
   command, artifact schema, or workflow. The focused
   `bench/scripts/tests/tc014_run_one_smoke_test.sh` now passes in this
   initialized fixture worktree. Before closing B056, retain serialized and
   overlapping-process stress evidence. A serial pass alone must not be used
   as proof of concurrent-run reliability.
