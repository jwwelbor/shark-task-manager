# shark question resolve/full give no way to discover the required --owner or --resolution-kind values

## Description

shark question resolve <key> --owner=<x> fails with 'resolution owner does not match configured owner' but there is no CLI path to discover the correct value: shark question full <key> and shark question blocking-for both refuse with 'not authorized' for any actor that doesn't already match, so a user is forced to read question_state.resolution_owner directly out of the SQLite context_data JSON column to find it. Separately, resolve also silently requires a prior 'shark claim <key> --by=<owner>' + 'shark question respond' (undocumented in resolve --help), and --resolution-kind only accepts local_clarification|feature_change|product_decision|architecture_decision|follow_up_work|no_lasting_consequence, each with its own pointer-format rule (e.g. product_decision requires docs/product/progress.md#<anchor>; architecture_decision requires 2+ semicolon-separated paths) that --help never surfaces. Found while resolving a Question in a consuming project (wwgm), had to grep this repo's own source (internal/services/question_workflow_service.go:201-238,326-328; internal/models/question.go:68) to work out the actual required flow and values.

## Expected Behavior

Either `shark question resolve <key> --owner=<x>` should say what value it
expected on failure, or `shark question full <key>` / `blocking-for` should
let an unauthorized caller see at least the workflow metadata
(`resolution_owner`, `resolution_kind`, responder list/status) needed to
retry correctly, without exposing the full narrative content those commands
otherwise gate.

## Actual Behavior

- `shark question resolve <key> --owner=<guess>` fails with "resolution
  owner does not match configured owner" — no hint of the correct value.
- `shark question full <key> --actor=<guess>` fails with "full Question
  read for <key> is not authorized" for the same reason — no way to
  discover the value through this path either.
- The only way found to recover the value was reading
  `question_state.resolution_owner` directly out of the SQLite
  `context_data` JSON column for the question row.
- Once the owner value is known, `resolve` still fails
  ("Question must be ready for resolution with all responders completed")
  until `shark claim <key> --by=<owner>` then
  `shark question respond <key> --responder=<owner> --session=<claim-session>`
  are run first — this ordering isn't documented in `resolve --help`.
- `--resolution-kind` then rejected `product_decision` ("product decision
  pointer must be a docs/product/progress.md anchor") and
  `architecture_decision` ("architecture decision pointer must include an
  ADR and affected reference") before `feature_change` finally validated —
  none of these per-kind rules are in `--help`.

## Steps to Reproduce

1. `shark question create "..."` then `shark question configure-workflow
   <key> --resolution-owner=<owner> --responder=<owner>` (as would happen
   during normal Question setup).
2. As a different session/agent that doesn't already know `<owner>`, run
   `shark question resolve <key> --owner=<any-guess> --resolution-kind=... --resolution-pointer=...`.
3. Observe the opaque failure, then try `shark question full <key>
   --actor=<any-guess>` to discover the correct owner — also fails, with no
   value surfaced.

## Fix Notes

See `internal/services/question_workflow_service.go:326-328` (owner check)
and `:201-238` (resolution-kind/pointer validation), and
`internal/models/question.go:68` (`QuestionState.ResolutionOwner`, set once
via `configure-workflow --resolution-owner`). Related, broader flag-surface
cleanup filed as TD-158.
