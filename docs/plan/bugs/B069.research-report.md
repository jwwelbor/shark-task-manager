# B069 research report

## Scope

B069 covers human-readable advice emitted after a successful status transition.
The affected capability is the shared `performEntityTransition` helper, which
serves the generic `next-status` and `set-status` commands for epics and
features. The report also compares that helper with the already-correct
`shark status set` path. The repair should update the advice contract only; it
should not remove `orchestrator_action` from entity JSON inspection output or
change workflow transition semantics.

## Findings

1. The defect reproduces in both generic transition callers. Running
   `go test ./internal/cli/commands -run 'TestPerformEntityTransition_(FeatureSuccess|Success)' -count=1 -v`
   passes, but the output includes:

   ```text
   INFO  Run `shark get E16 --field orchestrator_action` to get your next instructions.
   INFO  Run `shark get E16-F01 --field orchestrator_action` to get your next instructions.
   ```

   The test passes because it checks the transition result and does not assert
   the human-readable dispatch advice.

2. `performEntityTransition` is the shared production seam. It is called by
   `makeRunNextStatus` for the automatic and explicit generic `next-status`
   routes, and by `makeRunSetStatus` for generic entity `set-status` routes.
   Its non-JSON success branch is therefore the single place to repair both
   reported locations; no separate per-entity implementation is needed.

3. `runStatusSet` already establishes the intended local output contract. At
   `internal/cli/commands/status_group.go:375-385`, it prints
   `Run \`shark next <key> --json\` to get your next instructions.` after a
   successful transition. This is the reusable implementation pattern for
   B069.

4. The canonical dispatch documentation agrees with that output. The keyed
   dispatch API is `shark next <key> --json`, and the returned `response.prompt`
   is the assembled execution payload. The documentation explicitly says that
   `shark get ... orchestrator_action` is an inspection surface rather than the
   dispatch API (`docs/architecture/shark-dispatch-prompt-assembly.md:7-10`;
   `skills/shark-rider/verbs/run.md:22-29`).

5. Git history shows a related repair in B059. Commit `c4ea9e17` changed the
   `runStatusSet` advice from the same obsolete `orchestrator_action` command to
   `shark next <key> --json` while wiring route-based sprint dispatch. B069 is
   the remaining shared-helper copy of that output-contract drift, not a new
   dispatch mechanism.

6. The repair extends the existing status-transition output capability. It
   requires a small shared-helper change and regression assertions for the
   human-readable advice; it does not require a new workflow status, service
   interface, persistence field, or API.

## Decisions

1. Repair `performEntityTransition` in `internal/cli/commands/status_shared.go`
   to use the same `shark next <key> --json` advice already used by
   `runStatusSet`. This extends an existing capability rather than creating a
   new dispatch path.

2. Add focused output assertions to the existing shared-helper tests. Keep the
   current transition-result assertions, and verify both the canonical command
   and absence of the obsolete `orchestrator_action` advice. The test should
   cover the shared path rather than duplicate one test per entity command.

3. Leave `orchestrator_action` available where it remains an intentional JSON
   inspection field. B069 is about stale user guidance after transitions, not
   removal of the broader legacy-compatible data field.

4. No new related capability is needed. The recommended implementation is an
   extension of the existing CLI output contract and keyed dispatch API.
