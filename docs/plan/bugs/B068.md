# B066 fix never implemented the plan's stable-fingerprint requirement for non-blocker dedup

## Description

dev-artifacts/2026-09-15-review-triage-and-agent-attention-plan/plan.md's Workstream 1 explicitly required: 'Each item should include a stable fingerprint so reruns update or link the same record instead of multiplying it.' B066's fix (1f7be955) and B067's follow-up fixed the direct-tech-debt-mapping language but never added this fingerprint field -- non_blockers_to_triage had no fingerprint field in review-code.md's output contract, consolidator.md's Triage Summary, or triage/SKILL.md's duplicate-search step. Confirmed via grep: zero hits for 'fingerprint' in review-code.md/consolidator.md before this fix. Fixed: added a fingerprint field (format <relative_file_path>#<rule>#<slug>, computed from inputs that survive line-number drift across review rounds) to review-code.md's output contract and self-verification checklist, consolidator.md's Triage Summary and self-verification checklist, and triage/SKILL.md's Step 3 dedup search (checks the fingerprint first before the broader keyword search). Added two permanent regression tests: TestEmbedded_NonBlockersCarryStableFingerprint (internal/sharkdata) and TestConsolidatorNonBlockersCarryStableFingerprint (internal/cli/commands). Regenerated rendered-prompt goldens.

Rebased on top of a concurrent commit (2566999b, "consolidate triage prose") that shortened the same lines this fix touches to reference a new shared "Routing contract" section in triage/SKILL.md -- reapplied cleanly against that structure rather than the original one.

## Expected Behavior

A non-blocking finding rediscovered in a later review round links or
updates the tracker entity an earlier round already filed for it, per the
plan's explicit acceptance criterion ("Repeated reviews link by stable
fingerprint instead of creating duplicates").

## Actual Behavior

`non_blockers_to_triage` items carried no fingerprint at all before this
fix -- only `finding_id` (a per-run label), `file_line` (drifts across
rounds), `rule`, `summary`, and `fix_suggestion`. Nothing in
review-code.md, consolidator.md, or triage/SKILL.md computed or searched
on a stable identifier, so a rerun rediscovering the same defect had no
mechanism to avoid filing a second tracker entity for it.

## Steps to Reproduce

1. `grep -n fingerprint internal/sharkdata/default_data/skills/quality/workflows/review-code.md`
   (before this fix) -> no matches.
2. `grep -n fingerprint skills/shark-rider/skills/deep-review/references/consolidator.md`
   (before this fix) -> no matches.

## Fix Notes

Added `fingerprint` (`<relative_file_path>#<rule>#<slug>`, computed from
inputs that survive line-number drift) to review-code.md's output
contract and self-verification checklist, consolidator.md's Triage
Summary and self-verification checklist, and triage/SKILL.md's Step 3
dedup search (checks the fingerprint first). Added
`TestEmbedded_NonBlockersCarryStableFingerprint` and
`TestConsolidatorNonBlockersCarryStableFingerprint` as permanent
regression gates. Regenerated the three affected rendered-prompt
goldens. Verified: `go build ./...` and `go test ./internal/...` both
pass with no failures (74 packages ok).
