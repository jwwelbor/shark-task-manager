The change-card fallback is a second implementation with the same defect. ### F2. Starting a transaction can mask the repository’s input errors

The E21-F08 data model requires a recognized entity type and a positive parent ID. T-E21-F08-003 AC-10 and EC-2 require validation before SQL. Its architecture review, signed by the Architect Agent, explicitly verified the pre-SQL type guard. The shipped `EntityDocumentRepository.Unlink` enforces both guards. Rows 4, 5 and 9 use valid repository arguments. Row 11 covers an unset service dependency, one layer earlier. The existing repository tests use an available database and inspect the returned errors. Beginning a transaction before validating, then returning the correct validation error when begin succeeds, passes those tests. An unavailable database exposes the ordering change. [Architecture approval and repository requirements](../E21-entity-polymorphism-and-duplication-reduction/E21-F08-polymorphic-data-model-unification/tasks/T-E21-F08-003.md) · [E21 data model](../E21-entity-polymorphism-and-duplication-reduction/E21-F08-polymorphic-data-model-unification/tech/03-data-models.md) · [Existing repository tests](../../../internal/repository/entitydoc/repository_test.go#L319)

I called the shipped repository directly against a closed database. Type `project` with ID 452 returned `invalid entity type: "project"`. Type `task` with IDs 0 and −1 returned `entity_id must be positive, got 0` and `entity_id must be positive, got -1` respectively. Valid `task,452,563` reached storage and returned `sql: database is closed` in its error chain. Require the existing diagnostics at this boundary for invalid type, zero ID and negative ID with zero transaction or query attempts. A valid-argument control must reach the instrumented storage failure. Reuse the existing test cases where they cover the same inputs.

### F3. The transaction checks allow a delete that ignores caller cancellation

Repair step 4 specifies a context-bound transaction. Rows 4 and 5 exercise storage outcomes and independently injected begin, execution, verification and commit failures. Those assertions can all pass with a live background context substituted for the caller throughout the operation. The shipped repository passes the caller’s context into its write. The project Go rules and coding standards explicitly require propagating context for cancellation. [Production repository](../../../internal/repository/entitydoc/repository.go#L65) · [Context rules](../../../.claude/rules/go/patterns.md#context-usage) · [Coding standards](../../architecture/coding-standards.md)

With an existing `(task,452,563)` association, a direct call on an already-cancelled context returned an error matching `context.Canceled`. A fresh database reader counted one retained association. Repeating the same call with a live context succeeded and the fresh reader counted zero. Require that paired observation at the changed repository entry point. This distinguishes cancellation propagation from injected database errors and catches a detached transaction that deletes the link after its caller cancels.
