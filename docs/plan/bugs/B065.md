# UAT approval gate unconditionally requires a QA report even for STANDARD-tier features that never produce one

## Description

feature/approval.md's UAT prompt requires reading a feature-scoped qa-*.md report as evidence before verifying acceptance. But feature.yaml's code_review step explicitly states, for SIMPLE/STANDARD tier: 'this is the ONLY same-model verification gate — perform ALL FOUR parts below in this single pass... there is no separate QA pass behind you.' The qa status/step is only reachable via the COMPLEX tier's deep_verify outcome. So for any SIMPLE/STANDARD feature, no qa-*.md can ever exist, yet UAT's checklist treats its absence as a HIGH blocking finding. Reproduced on E40-F11 (COMPLEXITY: STANDARD, score 15/27): UAT rejected citing 'required QA evidence is absent' even though code-review had already run all 4 parts (craft review, AC+wiring verification, scoped test run, caller-path compliance) per the STANDARD-tier contract. Fix: either make the UAT prompt tier-aware (skip/waive the QA-report requirement when the code-review report itself declares STANDARD/SIMPLE tier and covers all 4 parts), or correct test-plan.md instructions that imply QA always precedes UAT regardless of tier. See docs/review/E40-shark-bench-workflow-benchmarking-harness/E40-F11-six-family-lifecycle-benchmark-readiness-and-cover/uat-20260907-uat.md (finding UAT-F1) and the passing code-review-20260907-003416-E40-F11.md report for reproduction evidence.

## Expected Behavior

The UAT approval gate (`internal/sharkdata/default_data/prompts/feature/approval.md`) should be tier-aware: for a SIMPLE/STANDARD-tier feature, it should not treat the absence of a `qa-*.md` report as a blocking finding, since `feature/code_review.md`'s own STANDARD/SIMPLE-tier contract states that gate is the only same-model verification pass and there is no separate QA step for that tier.

## Actual Behavior

UAT unconditionally requires a feature-scoped QA report as evidence and files a HIGH-severity blocking finding when one is absent, regardless of the feature's complexity tier.

## Steps to Reproduce

1. Run a SIMPLE or STANDARD-tier feature through `/shark-rider run <key>` to completion of its code-review gate (PASS).
2. Let the workflow dispatch the `approval` step's UAT gate.
3. Observe UAT reads `feature.md`/`test-plan.md`, finds no `qa-*-<feature>.md` file (correctly — none should exist for this tier), and rejects with a "required QA evidence is absent" blocking finding.

Concretely reproduced on E40-F11 (COMPLEXITY: STANDARD, score 15/27) on 2026-09-07 — see `docs/review/E40-shark-bench-workflow-benchmarking-harness/E40-F11-six-family-lifecycle-benchmark-readiness-and-cover/uat-20260907-uat.md` (finding UAT-F1) and the passing `code-review-20260907-003416-E40-F11.md` report showing the STANDARD-tier 4-part gate already ran.

## Fix Notes

Two candidate fixes (pick one, or both):
1. Make `feature/approval.md`'s UAT prompt read the code-review report's declared tier before requiring a QA artifact; skip/waive the QA-report requirement when the tier is SIMPLE/STANDARD and the code-review report already declares all 4 parts ran.
2. Audit `test-plan.md`'s template/instructions for any language implying QA always precedes UAT regardless of tier, and correct it to match the actual STANDARD/SIMPLE merged-gate behavior.
