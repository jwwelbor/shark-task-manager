# B071 research report

## Scope

B071 covers the documentation contract for viewing and searching notes. The
reported invocation is `shark note list B072`; the related generic guidance is
`shark notes list` or `shark notes <key>`. This research compares those forms
with the shipped Cobra command tree, the existing entity-specific note
commands, and the maintained CLI references. It does not propose a new note
storage or service capability.

## Findings

1. The reported failure reproduces in the current executable. `./bin/shark
   note list B072` exits with an unknown-command error because the root command
   registers `notes`, not `note`. `./bin/shark notes list B072` and `./bin/shark
   notes B072` print the `notes` parent help and do not list notes; the former
   exits successfully while performing no listing operation.

2. The generic `shark notes` namespace has exactly two registered children:
   `add` and `search`. `notes_add_dispatch.go` defines `shark notes add <KEY>`
   with key-based entity detection, while `notes_search.go` defines `shark
   notes search <query>` with entity, type, and date filters. No generic `list`
   child or positional-key handler is registered
   (`internal/cli/commands/notes_search.go:12-40,178-189`;
   `internal/cli/commands/notes_add_dispatch.go:12-57`).

3. Entity-specific note listing is an existing capability and is the correct
   pattern when the reader already knows the entity type. The shared
   `makeNotesCmd` helper implements `<entity> notes <key>` and delegates to
   `NoteService.ListNotes`; bug, task, feature, epic, change, and tech-debt
   command groups register that helper. Therefore `shark bug notes B072` is an
   existing supported shape, while `shark note list B072` is not an alias for
   it (`internal/cli/commands/note_generic.go:83-101,149-180`;
   `internal/cli/commands/bug.go:186-197`; `internal/cli/commands/task_note.go:175-181`).

4. Maintained documentation is inconsistent. `docs/cli-reference/README.md:81`
   says `shark notes <key>` views entity notes, which contradicts the generic
   command implementation. The detailed discovery reference correctly
   documents `shark notes search <query>` and its filters
   (`docs/cli-reference/discovery-commands.md:7-13,70-108`), and Rider guidance
   correctly uses `shark task notes <key>` for entity-scoped listing alongside
   generic `shark notes search` (`skills/shark-rider/context/notes-context-docs.md:30-40`).

5. Several planning artifacts describe proposed or historical unified forms,
   including `shark note list` in E17 and the CX review, and generic
   `shark notes {ENTITY_KEY}` in the E19 retro-sprint plan. Those documents are
   related drift sources, not evidence that the forms are currently shipped:
   the live command tree and current detailed reference establish the contract.

6. The repair extends an existing documentation and command-guidance
   capability. It does not create a new CLI, service, persistence, API, or note
   query operation. A documentation sweep should make generic search explicit,
   use the entity-specific `<entity> notes <key>` pattern for keyed listing,
   and label any future unified `note list` proposal as unimplemented.

## Decisions

1. Choose documentation alignment over adding a generic `shark note list`
   command. The current runtime already supports generic note creation and
   search, plus entity-specific listing; adding a new root command would expand
   scope beyond B071 and conflict with the established command split.

2. Treat `shark notes search "<query>"` as the generic cross-entity pattern.
   For a known bug key, use the existing `shark bug notes <key>` shape; use the
   corresponding entity prefix for other entity types. Use `shark get <key>`
   for entity details, not as a substitute for an undocumented notes-list
   command.

3. Update the existing CLI reference summary and any maintained workflow
   consumers that use `shark notes <key>` or `shark notes list`. Keep E17/CX
   proposal text clearly marked as unimplemented unless a separate feature
   authorizes that runtime change.

4. This is an extension of the existing documentation contract, not new work
   in the notes service or persistence layer. The related planning references
   are follow-up documentation consumers to reconcile; they do not block this
   research conclusion.
