# B058 Research Report: Sprint Readiness Treats Completed External Dependencies as Unsatisfied

## Scope

Sprint readiness scoring penalizes tasks with unmet external dependencies via the "Dependency satisfaction" factor (Factor 2). The bug is in `computeDependencySatisfactionFactor` (line 2794 in `internal/services/sprint_service.go`): it treats a dependency as satisfied **only when the dependency task is assigned to the current sprint**, ignoring the dependency's actual terminal status.

**Concrete impact:** A task assigned to sprint S006 with six prerequisites all completed in prior sprint S002 registers as having six unsatisfied external dependencies and loses six readiness points, because none of those prerequisites are in S006's assignment set.

**Expected behavior:** A dependency should be satisfied if its task has reached a terminal status (regardless of sprint membership), not merely if it's assigned to the current sprint.

## Findings

### 1. Root Cause Mechanism

The function implements this literal algorithm (lines 2811–2816):
```go
for _, dep := range deps {
    if !assignedKeys[strings.ToUpper(dep)] {
        unsatisfied++
    }
}
```

**Key problem:** This check has two failure modes:
1. Dependency task is completed in prior sprint S002, not assigned to S006 → counted unsatisfied (false negative)
2. Dependency task doesn't exist (typo'd key) → counted unsatisfied (correct)

### 2. Available Data Flow

**In `GetSprintReadiness(ctx, key string)` (line 2709):**
- `s.assignmentRepo` — query assignments with sizes (line 2722)
- `s.workflowSvc` — access to `IsTerminalStatus()` for any entity level
- `s.db` — database connection available (optional, already wired)
- No TaskRepository currently wired

**Missing:** TaskRepository to fetch external (non-assigned) dependency tasks by key and retrieve their status.

### 3. Terminal Status Infrastructure Already in Place

- `workflow.Service.IsTerminalStatus(status string) bool` exists (`internal/workflow/service.go`)
- Checks case-insensitive match against `GetTerminalStatuses()` list (workflow-driven, config-aware)
- Used throughout the codebase for exactly this use case (e.g., `internal/cli/commands/task_deps.go`)
- Returns true for any status in the workflow's terminal step set (typically "completed" + any custom terminal statuses)

### 4. Batch Lookup Method Exists

`TaskRepository.GetByKeys(ctx context.Context, keys []string)` returns `(map[string]*models.Task, error)`:
- Returns only existing tasks (missing keys omitted from map)
- Case-insensitive key lookup built-in
- Efficient: single parameterized query with IN clause, no N+1
- Already tested and in production (`internal/repository/bulk_operations_test.go:144–202`)

### 5. Function Signature Impact

**Current:**
```go
func computeDependencySatisfactionFactor(
    assignments []sprint.AssignmentWithSize,
    assignedKeys map[string]bool,
) ReadinessFactor
```

**Needed changes:**
- Accept optional task repository (to avoid breaking pure-computation contract when not needed)
- Accept workflow service for terminal-status check
- OR: Move logic into `GetSprintReadiness` and keep factor computation pure (preferred per separation of concerns)

### 6. Caller's Responsibility Context

`GetSprintReadiness` already:
- Has `s.workflowSvc` (guaranteed non-nil, enforced in constructor)
- Has `s.db` available
- Can create `repository.NewTaskRepository(s.db)` if needed (lightweight)
- Can pass these to a modified computation function

---

## Decisions

1. **Keep `computeReadinessFromData` as a pure in-memory kernel** — It takes only aggregated data already fetched by the caller. No new dependencies.

2. **Add dependency-status lookup as a separate step in `GetSprintReadiness`** — Before calling `computeReadinessFromData`, fetch all external dependency tasks and enrich the assignments with their terminal-status information.

3. **Modify `computeDependencySatisfactionFactor` signature minimally** — Accept an optional map of dependency-key → is-terminal to avoid N database calls within the factor function.

4. **Never hardcode "completed"** — Use `s.workflowSvc.ForLevel(workflow.LevelTask).IsTerminalStatus(dep.Status)` to remain config-driven.

5. **Treat missing dependency keys as unsatisfied** — If a dependency key doesn't exist in the database (typo), count it unsatisfied (safe default, consistent with current behavior).

---

## Pattern Contract

**Service Layer Responsibility (per `.claude/rules/services/service-design.md`)**
- Business logic (dependency satisfaction rules) lives in services
- Status derivation must use `workflow.Service`, not hardcoded lists
- Repositories are data-access only; service orchestrates queries and applies rules

**Application:**
- `GetSprintReadiness` is the correct place to fetch dependency tasks and compute their terminal status
- The readiness factor computation can then reference a pre-computed satisfaction map
- The workflow service is guaranteed available (non-nil) in SprintService constructor

**No circular dependencies:**
- SprintService does not depend on TaskService
- TaskRepository is used directly (data-access layer only)
- Workflow checks are via workflow.Service, not task lifecycle methods

---

## Alternatives

### Alt A: N+1 Lookups (Rejected)
Fetch each external dependency task individually in the factor function. O(D) database calls where D = count of external dependencies.
- **Rejected:** Inefficient, violates batch-lookup pattern, no benefit over Alt B

### Alt B: Single Batch Lookup + Map (Recommended — Chosen)
In `GetSprintReadiness`, fetch all external dependency keys as one batch via `TaskRepository.GetByKeys()`. Store terminal-status in a map. Pass map to factor function.
- **Benefit:** O(1) database call, clean separation of concerns, reusable pattern
- **Cost:** Small preprocessing step before `computeReadinessFromData`

### Alt C: Modify Factor Function Signature to Accept TaskRepository (Considered)
Pass `taskRepo` directly into `computeDependencySatisfactionFactor` so it can fetch on-demand.
- **Rejected:** Violates pure-computation contract of factor functions, tightly couples to task repository, harder to test in isolation

## Fix Plan (Minimal, Concrete)

### Step 1: Modify `GetSprintReadiness` (internal/services/sprint_service.go:2709)

After fetching assignments (line 2722) and before calling `computeReadinessFromData` (line 3092):

```go
// Collect all dependency keys that are NOT in the current sprint's assignment set
var externalDeps []string
depKeysSeen := make(map[string]bool)
for _, a := range assignments {
    if a.EntityType != "task" || a.DependsOn == "" {
        continue
    }
    var deps []string
    if json.Unmarshal([]byte(a.DependsOn), &deps) != nil {
        continue // Skip malformed
    }
    for _, dep := range deps {
        depUpper := strings.ToUpper(dep)
        if !assignedKeys[depUpper] && !depKeysSeen[depUpper] {
            externalDeps = append(externalDeps, depUpper)
            depKeysSeen[depUpper] = true
        }
    }
}

// Batch-fetch external dependency tasks
extDepTerminal := make(map[string]bool)
if len(externalDeps) > 0 {
    taskRepo := repository.NewTaskRepository(s.db)
    extDepTasks, err := taskRepo.GetByKeys(ctx, externalDeps)
    if err != nil {
        // Log but don't fail (graceful degradation)
        // Unsatisfied deps will default to false (unsatisfied)
    } else {
        for key, task := range extDepTasks {
            extDepTerminal[strings.ToUpper(key)] = 
                s.workflowSvc.ForLevel(workflow.LevelTask).IsTerminalStatus(string(task.Status))
        }
    }
}

// Pass external dependency terminal map to computation
return computeReadinessFromDataWithExtDeps(assignments, capacities, assignedKeys, extDepTerminal), nil
```

```go
            unsatisfied++
        }

    // ... rest unchanged ...
}
```
