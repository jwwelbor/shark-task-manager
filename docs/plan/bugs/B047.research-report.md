# B047 Research Report: Progress-Affecting Writes State Coherency

## Scope

**Entity**: Bug B047  
**Title**: Progress-affecting writes can leave task, feature, and epic state incoherent  
**Investigation Date**: 2026-08-27  
**Status**: CLOSED — fix shipped and production-wired  

### Scope Vocabulary

- **Progress-affecting write**: Any operation that changes a task status, creates/deletes a task or feature, or explicitly updates a feature status. These cascade upward to invalidate feature progress caches and epic status derivations.
- **Coherency violation**: A condition where `features.progress_pct` (cached) no longer reflects the actual task status breakdown, or epic status doesn't match the aggregated feature statuses.
- **Transactional hierarchy refresh**: A single SQLite transaction that encompasses the child write, parent progress recalculation, and ancestor status recalculation, such that either all succeed or all roll back.
- **Coordinator**: `AggregateMutationCoordinator`, a service-layer component that owns post-mutation aggregate maintenance within a caller-provided transaction.

## Pattern Contract

**Transactional Aggregate Refresh Pattern:**

Each coordinator method operates within a single SQLite transaction owned by the caller:

```
BEGIN TRANSACTION
  ├─ Task/Feature/Epic mutation (status, create, delete)
  ├─ Feature progress recalculation (if needed)
  ├─ Feature status derivation (if progress changed)
  ├─ Epic status derivation (from feature breakdown)
  └─ EntityHistory records for any status changes
COMMIT OR ROLLBACK (atomic)
```

**Coordinator Guard:**

All services check `if s.aggregateCoordinator != nil` before invoking it. If nil, a fallback best-effort path (logging-only) applies. In production CLI code, the coordinator is always wired (verified at lines 288, 293, 246 in service_accessors.go).

## Cross-Boundary Risks

1. **TaskService ↔ FeatureService**: TaskService.DeleteTask refreshes its parent feature; FeatureService.CompleteFeature independently refreshes its parent epic. No circular calls; hierarchy is unidirectional (task → feature → epic).

2. **CLI ↔ Service**: CLI commands call service methods; services manage transactions. The coordinator is wired into services, not CLIs, so all CLI commands benefit transitively.

3. **EntityService ↔ TaskService/FeatureService**: EntityService.TransitionStatus is generic and delegates to the entity-specific service (via EntityRegistry). The entity service then routes through the coordinator if it's a progress-affecting transition.

## Decisions

1. **Coordinator is optional at compile time** (nullable field on services) but mandatory in production wiring. This design allows for testing scenarios where the coordinator is deliberately absent (to test fallback paths) without forcing restructuring. Production CLI code wires it unconditionally.

2. **Feature progress is persisted** (`features.progress_pct` column) rather than derived on read. The coordinator keeps this cache current. Epic progress remains derived on read (no `epics.progress_pct` column), so epic display does not depend on cache coherency.

3. **Reopen cascades are transactional**. When a task regression causes a feature to reopen from a terminal status, the epic ancestor is also reopened in the same transaction. This ensures a feature cannot be terminal while its parent epic is completed.

4. **File atomicity is preserved**. If a task creation fails during aggregate refresh, only the task's newly-created markdown file is removed; already-linked files are left untouched.
