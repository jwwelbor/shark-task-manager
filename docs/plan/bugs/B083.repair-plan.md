# B083 repair plan

## Diagnosis

The E40 benchmark path preserves workflow route fields until it reaches the
provider adapter, but it does not resolve the selected harness against those
routes. On the declared review baseline, the Codex branch of
`lifecycle-worker-adapter.sh::command_for()` drops `request.model`; the
read-only `bench-working` comparison forwards `-m` but also forwards an
incompatible Claude/Sonnet model unchanged. `load_routing_profile()` and
`apply_routing_profile()` exist in `e40_benchmark.py`, but research found only
their definitions and test callers. Profile selection is not wired into the
production run path, and current route digests describe the workflow before
any profile application.

The defect has two distinct questions: whether the selected CLI can represent
and accept the pinned model, and whether that model is listed for the same
account the run will use. Neither the CLI's general model catalog nor a
successful route-flag construction proves account availability. The official
Codex app-server guide says `model/list` may return a bundled or cached catalog
and must be treated as catalog data, not an entitlement check. Its account
catalog guidance uses `GET /v1/models` with the selected account's same access
token; a completed inference turn is the evidence that a particular request
worked. This plan adds no account probe or inference call during preparation.

## Proposed repair

1. Wire the existing E40-F13 versioned routing profile mechanism into the
   production benchmark run as an explicit `routing_profile` selection, kept
   distinct from the existing baseline/variant comparison `profile`. A
   selected routing profile is the operator's explicit harness switch and
   supplies the provider plus a pinned model and optional effort for every
   live workflow stage. Validate complete stage coverage before dispatch. Do
   not infer routes from `capability_profile`, inherit a parent model, or
   silently substitute another model. If no routing profile is selected, the
   explicit workflow provider/model/effort remains authoritative and is
   validated as-is.
2. Apply the selected profile to a run-scoped copy of the workflow bundle.
   Never call the current in-place profile helper on the shared source bundle.
   Reject invalid profiles, missing stage routes, or a route whose provider
   does not match the selected harness before starting a worker. Preserve the
   profile version, source digest, and exact effective provider/model/effort
   tuple in the run manifest and adapter request.
3. Add a read-only route preflight with two separately reported checks:
   (a) selected CLI/model compatibility, using an identified CLI-supported
   catalog or equivalent documented compatibility source; and (b) presence in
   a current account-specific model catalog obtained only through an already
   authorized, safe credential interface proven to be the same account and
   credential context used by that route. A Codex app-server `model/list`
   result may inform the first check but must never satisfy the second. Use
   `/v1/models` only when the implementation can obtain and use the same
   selected-account token safely; do not scrape an undocumented CLI token
   store, copy credentials into artifacts, or assume an API key and CLI login
   represent the same account. If no supported same-account catalog source is
   available, or the catalog is stale, malformed, unreachable, or lacks the
   pinned model, record a named unresolved route and fail before adapter
   dispatch. Reuse the existing `resolution: failed`,
   `cause_class: route_defect` ledger contract.
4. Fix Codex command construction to pass the effective route model using the
   CLI's model option, including when a configured executable override is
   used. Reject an opaque command override if it cannot preserve the selected
   provider/model/effort contract. Bind routing identity only after profile
   materialization, then pass the same effective tuple and routing digest to
   every corresponding adapter request and manifest entry.
5. Keep the catalog preflight read-only: it does not start an adapter, create an
   inference request, or claim that a listed model is temporarily serviceable.
   If a real provider attempt later begins and fails because of access, quota,
   or service availability, record that attempt against the exact pinned
   route. Do not retry through a different model without a separately selected
   and recorded profile.

The existing route preview already separates stage resolution from adapter
execution. Extend that boundary for deterministic route checks and injected
catalog fixtures while retaining its no-inference property. Account catalog
lookup is only enabled when the safe credential/source condition above is
proven; otherwise the preview reports `failed/route_defect` and zero adapter
calls. The current `--mode resolve-route` behavior does not establish account
availability by itself.

## Scope and preserved behavior

**Complexity M.** The repair spans benchmark configuration, profile
materialization, route preflight, identity capture, and the adapter boundary.
Implementation is limited to E40's `bench/` production path and its tests.

- Extend the existing E40-F13 profile/schema and run configuration rather than
  creating a parallel router. Preserve explicit stage `provider`, `model`, and
  `effort`; only an explicitly selected routing profile may replace them.
- Preserve `identity.provider_routing`'s provider/model/effort digests and
  comparison identity, but compute them from the effective run-scoped workflow
  after the selected profile is applied. The adapter request, manifest, and
  route evidence must identify that same effective tuple.
- Preserve source workflows, profiles, and repository files byte-for-byte
  during materialization. Preserve the current Claude and Copilot adapter
  contracts, measurement normalization, scratch-root isolation, and cost
  honesty. Do not change native Shark Rider launch behavior or claim B077 is
  fixed; B077 is a separate boundary.
- Preserve the existing parent-owned Shark claims, heartbeats, transitions,
  and releases. This repair changes E40 route preparation and adapter command
  construction only.
- Do not run a live provider or account canary as part of unit, contract, or
  route-preview tests. Use fake CLI/catalog/adapter seams. A later live
  benchmark requires its own explicit authorization and evidence.

## Review baseline and rework rules

The immutable review baseline is
`bbf490c6ec2bd597d6f3e6e4cdd93e68ca54fa50` (the B084 merge on `origin/main`;
tree `0764bb9a04abc4c8001bd1ec9cc88d709bcc2ad5`). It is an ancestor of the
assigned branch and predates B083's research commits and this plan. Independently
reconfirm this full commit at plan review and carry the same baseline through
development, code review, and QA. Do not substitute a later mainline tip.

Use the committed project document for planning and independent plan review.
Register the plan and its separate mutable evidence record as related documents.
After approval, the parent supplies the approved snapshot path and digest for
downstream work. Update only the evidence record as verification evolves; a
material diagnosis, scope, approach, or assertion change requires a new plan
revision and independent review. Candidate changes invalidate code review and
QA. Retain all findings and route to the earliest invalidated stage. Unavailable
same-account catalog evidence is `blocked`, never acceptance; at runtime the
preflight must fail closed before dispatch.

## Verification design

Use deterministic fixtures for selected profiles, workflow copies, route
catalogs, CLI argv, manifests, adapter call counts, and route-ledger records.
Add paired green/red counterfactual assertions: correct profile and catalog
produce the exact pinned route; absent or incompatible catalog blocks before
the adapter; a changed route changes identity; source configuration stays
unchanged. Use a mock account catalog only. Do not run an account query or
inference as part of these checks. Run the applicable E40 routing, adapter,
identity, and route-preview suites after implementation, then the project's
required quality gate. Record commands and observed results in the mutable
evidence record, including any external catalog source that remains unavailable.
