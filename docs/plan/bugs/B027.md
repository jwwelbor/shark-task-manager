# shark create note rejects `--type=review` for bugs

## Description

`shark create note <bug-key> "..." --type=review` is rejected by the validator. Other entity types appear to accept `review` (and the canonical code-review workflow tells the tech-lead agent to file a `review` note at PASS verdicts), so the bug-entity note-type allowlist has a semantic gap.

During /shark run B025, the tech-lead code-review agent had to fall back to `--type=decision` to record its PASS verdict, which loses the semantic distinction between a decision and a code-review outcome.

## Expected Behavior

`shark create note <bug-key> "<message>" --type=review` succeeds and files the note with type `review` — matching what other entity types (tasks, features) allow, and what the canonical code-review workflow emits.

## Actual Behavior

The validator rejects `--type=review` for bug entities. The tech-lead falls back to `--type=decision`, which conflates code-review notes with general decision notes in the audit trail.

## Steps to Reproduce

1. Pick any bug (e.g., one created via `shark create bug "test" --severity=low`).
2. Run `shark create note <bug-key> "Code review PASS" --type=review`.
3. Observe the rejection (the validator names `review` as not in the allowed list).
4. Compare with `shark create note <task-key> "Code review PASS" --type=review` on a task — verify whether `review` is allowed there.

## Fix Notes

Two valid resolutions:
1. Add `review` to the bug-entity note-type allowlist so the same workflow note types work for all entity types that go through code review.
2. Update the tech-lead agent prompt (and the canonical code-review workflow) to use `decision` consistently — but this loses semantic specificity.

Option 1 is the cleaner fix since the code-review workflow is meant to be entity-agnostic.

Probable location: `internal/models/validation.go` (the `ValidateNoteType` function or equivalent allowlist map) or wherever bug-specific note-type rules diverge from the shared list.
