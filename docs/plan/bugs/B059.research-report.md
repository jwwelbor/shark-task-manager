# B059 Research Report: Sprint Workflow Implementation Gaps

## Scope

**Entity:** Bug B059 — "Sprints cannot advance past 'planning' with the shipped default sprint workflow"

**Vocabulary:**
- **Route-based workflow**: Entity status lifecycle defined as discrete steps with outcome-driven routing (E35 design pattern). Each step defines `outcomes` map that routes to next steps based on semantic result (pass/fail/blocked).
- **Planning phase entities**: Sprints and features marked with `is_planning: true` (gates research validation before leaving planning).
- **Workflow transitioner**: CLI layer (run.go:657) that maps entity types to service methods implementing `runner.EntityTransitioner` interface (`TransitionStatus`, `GetNextStatus`).
- **Active sprint**: Executes assigned entities; identified by execution-phase status lookup (currently "active" in default workflow).
- **Research gate**: Mandatory intermediate step (planning → research → active) in the shipped default `sprint.yaml` workflow.

**Affected Contract:**
- Sprint lifecycle commands: `shark sprint start`, `shark next <sprint-key>`, `shark status set <sprint-key>`, `shark status advance <sprint-key>`
- Service interface: `SprintService` does not implement `runner.EntityTransitioner` (missing `TransitionStatus()`, `GetNextStatus()`)
- CLI dispatch: `buildTransitioner()`, `dispatchTransition()`, `dispatchNextStatus()` in status_group.go lack sprint case

## Findings

### F1: Workflow Shipped Without CLI Support (High Impact)

**Finding:** PR #101 (commit 1e038453) shipped `internal/sharkdata/default_data/workflow/sprint.yaml` with a fully route-based lifecycle (planning → research → active → closing → completed → archived), each step declaring `action: spawn_agent` for orchestrator dispatch. However, the CLI transitioner layer (`buildTransitioner()`, `dispatchTransition()`, `dispatchNextStatus()`) was not updated to recognize entity type `"sprint"`.

**Evidence:**
- `internal/sharkdata/default_data/workflow/sprint.yaml:1-104` — Full route-based workflow with research step (line 39-56) as mandatory intermediate between planning (line 4-21) and active (line 22-38). Each declares outcomes (e.g., research `outcomes: {pass: active, fail: planning, blocked: on_hold}`).
- `internal/cli/commands/run.go:657-676` — `buildTransitioner()` switch only handles `[task, feature, epic, bug, change, tech_debt, question]`; returns "unsupported entity type: sprint" on line 674.
- `internal/cli/commands/status_group.go:235-254` — `dispatchTransition()` switch (line 236-253) omits sprint.
- `internal/cli/commands/status_group.go:257-276` — `dispatchNextStatus()` switch (line 258-272) omits sprint.
- `internal/cli/commands/workflow_show_action.go:228-229` — `getPlaceholders()` default case returns "unsupported entity type" for sprint.
- **Gap Impact:** No CLI path exists to dispatch sprints through the route-based workflow, leaving sprints permanently stuck in planning.

### F2: SprintService Does Not Implement EntityTransitioner Interface (Design Incompleteness)

**Finding:** The `SprintService` struct and interface are not designed to support the `runner.EntityTransitioner` contract required by the CLI workflow dispatcher. The service lacks `TransitionStatus()` and `GetNextStatus()` methods that every other domain service (TaskService, FeatureService, EpicService, BugService, ChangeCardService, TechDebtService) implements.

**Evidence:**
- `internal/services/sprint_service.go:40-92` — `SprintRepository` interface defines CRUD and assignment methods; no mention of transition/dispatch methods.
- `internal/services/sprint_service.go:1-510` — `SprintService` struct and methods: `StartSprint()` (line 467), `CloseSprint()` (line 543), `ArchiveSprint()` (line 616) exist but are bespoke lifecycle methods, not the generic `TransitionStatus(ctx, key, targetStatus, opts) (*services.TransitionResult, error)` signature.
- Compare to `internal/services/task_service.go` — TaskService implements `TransitionStatus()` and `GetNextStatus()` as public methods for CLI dispatch.
- `internal/cli/commands/run.go:653-656` — Comment explicitly states "All five service types (TaskService, FeatureService, EpicService, BugService, ChangeCardService) directly satisfy runner.EntityTransitioner" — sprint is not mentioned and is missing these methods.
- **Gap Impact:** Even if CLI dispatch is wired for sprint, SprintService cannot satisfy the transitioner interface without new methods.

### F3: StartSprint Validates Hardcoded planning→active Transition, Conflicts with Workflow (Behavioral Incompatibility)

**Finding:** `SprintService.StartSprint()` validates and executes a direct transition from planning status to the configured execution-phase status (default "active") via `workflowSvc.ValidateTransition(string(sprint.Status), activeStatus)` on line 485. The shipped default workflow no longer permits this direct transition; it requires planning → research → active. The service has no knowledge of intermediate steps and cannot auto-advance through research.

**Evidence:**
- `internal/services/sprint_service.go:467-511` — `StartSprint()` method:
  - Line 481: `activeStatus, err := s.executionPhaseStatus()` (lookup "execution" phase status, default "active")
  - Line 485: `s.workflowSvc.ValidateTransition(string(sprint.Status), activeStatus)` validates direct planning→active
  - Line 499: Direct status update to activeStatus
  - No intermediate research validation; assumes single-hop transition.
- `internal/sharkdata/default_data/workflow/sprint.yaml:39-56` — Research step explicitly requires pass outcome to route to active; no direct planning→active transition defined.
- Test case B059.md §Steps to Reproduce, step 3: Error message "cannot start sprint S007 in status planning: invalid transition from 'planning' to 'active'. Fix: valid transitions from 'planning': research, on_hold. Use --force to override"
- **Gap Impact:** `shark sprint start` is blocked even on valid sprints because the command assumes a workflow the shipped default no longer supports.

### F4: Research Gate Validation Implemented but Unused (Code-Service Mismatch)

**Finding:** The sprint service already implements research-phase validation (`research.ValidateEntity()` on line 493) for sprints transitioning FROM research to active, but this code is unreachable in the default workflow because sprints cannot enter research in the first place via any CLI command.

**Evidence:**
- `internal/services/sprint_service.go:488-496` — After validating the transition, the code checks if the *current* status is in research phase and validates entities if present. This code runs when transitioning FROM research, but never runs because no CLI path leads to research.
- `internal/research/` — Entire research validation package (research/validate.go, etc.) exists and is imported but only reachable through `shark feature` or other entities that can enter research via `shark next`.
- **Gap Impact:** Dead code path; design for research gating exists but cannot be triggered for sprints.

### F5: Three-Way Solution Space Identified; No Consensus on Preferred Path (Design Decision Pending)

**Finding:** Bug B059.md §Fix Notes (line 87-98) outlines three architectural choices:

**(a) Full Route-Based Support** — Wire SprintService into CLI transitioner (consistent with E35 design pattern and the shipped workflow's structure). Requires:
- Add `TransitionStatus()` and `GetNextStatus()` methods to SprintService
- Add sprint case to `buildTransitioner()`, `dispatchTransition()`, `dispatchNextStatus()`, `workflow_show_action.go`
- Ensures sprint workflow can be driven end-to-end via `shark next <sprint-key>` and `shark status <sprint-key>`
- **Alignment:** Consistent with E35 unified route-based model; leverages existing outcome-routing infrastructure
- **Cost:** Modest (~80 lines of glue code + ~20 lines per transitioner switch)

**(b) Sprint-Specific Bypass** — Enhance `StartSprint()` to detect research-phase gates and auto-advance through research. Requires:
- Detect if current status is planning and next status requires research gate
- Auto-transition through research without intermediate command invocation (or require explicit `shark sprint research` call)
- Leave `shark next` unsupported for sprint
- **Alignment:** Preserves sprint as a special-case lifecycle (not fully route-based)
- **Cost:** ~30 lines; breaks uniformity with other entity types

**(c) Workflow Simplification** — Revert sprint.yaml to direct planning→active transition with optional intermediate manual commands. Requires:
- Modify `internal/sharkdata/default_data/workflow/sprint.yaml` to remove or make research optional
- Document new CLI flow (e.g., `shark sprint start` direct to active, or add `shark sprint research` to bridge)
- Accept that research is no longer first-class in sprint lifecycle
- **Alignment:** Simplest implementation; reduces feature surface; may conflict with sprint-planning skill (E19-F08) expectations
- **Cost:** Minimal code changes; risk of design regression if research was intentional

**Evidence:**
- B059.md lines 87-98 enumerates the three choices with justification for each
- sprint.yaml structure (route-based, outcome-driven) suggests (a) was the intended design
- sprint-planning.md prompt (E19-F08) and sprint-execution.md prompt may clarify intent (assumed research is planned before execution begins)
- No explicit ADR or design doc found in docs/plan/ committing to a solution

### F6: Multiple Hardcoded Entity-Type Switch Statements Create Maintenance Burden (Pattern Debt)

**Finding:** Sprint support gaps exist in three independent switch statements across the CLI layer:
1. `buildTransitioner()` in run.go:657-676
2. `dispatchTransition()` in status_group.go:235-254
3. `dispatchNextStatus()` in status_group.go:257-276
(Plus workflow_show_action.go:172-230 for placeholders)

This pattern repeats elsewhere (e.g., idea_detect.go, formatters). Adding a new entity type requires 3+ edits.

**Evidence:**
- `internal/cli/commands/run.go:657-676` — 18 lines for single switch
- `internal/cli/commands/status_group.go:235-254` — 20 lines for dispatch switch
- `internal/cli/commands/status_group.go:257-276` — 20 lines for next-status switch
- `internal/cli/commands/workflow_show_action.go:172-230` — 58 lines for type-to-placeholder dispatch
- Pattern repeats in multiple files (investigate with grep entity-type dispatch)
- **Gap Impact:** Prone to incomplete updates when adding entity types (as evidenced by sprint being missed in PR #101)

## Decisions

### D1: Recommend Solution (a) — Full Route-Based Support for Sprint

**Rationale:**
- **Consistency:** Aligns sprint with E35 unified route-based model for all entities (tasks, features, epics, bugs, changes, tech-debt already use this pattern)
- **Workflow Authority:** The shipped sprint.yaml is already fully route-based with outcome routing; supporting it end-to-end validates the design
- **Scalability:** Reduces maintenance burden vs. special-casing; any new entity type can follow the same wiring checklist
- **Minimal Scope:** Requires only CLI dispatch wiring (~100 lines) + SprintService interface additions (~40 lines); no schema or DB changes
- **Evidence:** sprint.yaml structure (40+ lines of route-based YAML) suggests this was the intended design post-PR #101

**Implementation Steps (derived from research):**
1. Add `TransitionStatus()` and `GetNextStatus()` methods to SprintService (implement runner.EntityTransitioner interface)
2. Add `"sprint"` case to `buildTransitioner()` in run.go:657-676
3. Add `"sprint"` case to `dispatchTransition()` in status_group.go:235-254
4. Add `"sprint"` case to `dispatchNextStatus()` in status_group.go:257-276
5. Add `"sprint"` case to `getPlaceholders()` in workflow_show_action.go:172-230
6. Add regression test: `shark sprint create`, then `shark sprint start` should advance to research (or next valid status), not fail

### D2: Validate Sprint Workflow Intent with E19 / E35 Stakeholders

**Rationale:** The sprint.yaml structure strongly suggests full route-based design was intended, but no explicit ADR was found. Before committing to solution (a), confirm that:
- Research phase is intentional (should be gated in sprint lifecycle, not optional)
- Outcome routing (pass/fail/blocked on research) aligns with sprint-planning skill expectations
- "Planning" and "Research" phases are both marked `is_planning: true`; confirm this gating model is desired

**Evidence:** Absence of design doc; E19-F08 commits don't include ADR; sprint.yaml changes shipped without CLI wiring update

### D3: Plan Maintenance Pattern Improvement (Follow-Up Work)

**Rationale:** The hardcoded switch statements in CLI dispatch are a recurring source of drift (as seen with sprint). Recommend a follow-up story to centralize entity-type registration:
- Single map/struct defining supported entity types + their service getters (DI-style)
- Auto-generate or simplify the switch statements
- Reduces friction for adding new entity types in future

**Evidence:** Found 4+ independent switch statements; sprint gap appeared because PR #101 didn't update all of them

## Summary

**Root Cause:** PR #101 shipped a route-based sprint workflow without updating the CLI transitioner layer (3 switch statements + 1 placeholder lookup) to recognize entity type `"sprint"`. As a result, `shark sprint start` fails because it attempts a hardcoded planning→active transition that the workflow no longer permits, and no alternative CLI path (`shark next`, `shark status advance`) is available to dispatch sprints through the research gate.

**Recommended Fix:** Implement solution (a) — add SprintService methods and CLI dispatch wiring to make sprint a first-class route-based entity. This aligns with E35 design and requires ~140 lines of glue code. Confirm intent with E19/E35 stakeholders and consider a follow-up maintenance story to centralize entity-type registration and reduce future drift.

**Scope Determination:** Fix is bounded to CLI command layer + service interface; no database schema, workflow YAML, or business logic changes needed. Estimated effort: **SMALL** (straightforward wiring + testing).
