# tags.md missing 'unavailable' error class in canonical mapping and exit code summary

## Description

`internal/cli/commands/tags.go::tagsErrorCode` (lines 259-301) returns **nine** distinct internal error classes:

| Class | Exit | Service error |
|---|---|---|
| `not_found` | 1 | `*services.NotFoundError` |
| `unauthorized` | 3 | `*maintainer.UnauthorizedError` |
| `conflict` | 3 | `*services.ConflictError` |
| `in_use` | 3 | `*services.TagInUseError` |
| `validation` | 3 | `*services.ValidationError` |
| `unregistered_tag` | 3 | `*services.UnregisteredTagError` |
| `tag_required` | 3 | `*services.TagRequiredError` |
| `unavailable` | 3 | `*services.TagFilterUnavailableError` |
| `db_error` | 2 | catch-all (default) |

But `docs/cli-reference/tags.md` only documents **eight** of those classes. `unavailable` is missing from every canonical list:

1. **Overview block (line 9):**
   > "The mapping is: **`not_found` → 1**, **`db_error` → 2**, and **`unregistered_tag` / `tag_required` / `unauthorized` / `conflict` / `in_use` / `validation` → 3**."
   …and:
   > "Callers that need to distinguish error classes should parse the JSON envelope's `error` field (`unregistered_tag`, `tag_required`, `not_found`, `conflict`, `in_use`, `validation`, `unauthorized`, `db_error`) rather than rely on `$?` alone."
   `unavailable` is absent from both enumerations.

2. **JSON Error Envelope reference table (lines 327-334):**
   The "`error` code (inner) → Condition" table lists `unauthorized`, `not_found`, `conflict`, `in_use`, `validation`, `db_error`. No row for `unavailable`.

3. **Exit Code Summary (lines 368-376):**
   The "Process exit / Internal class / Meaning / Common cause" table lists `not_found`, `db_error`, `unauthorized`/`validation`/`conflict`/`in_use`, `unregistered_tag`, `tag_required`. No row for `unavailable`.

A caller (CI script, AI agent, downstream tool) that uses these tables as the source of truth will not know that `unavailable` is a possible JSON `error` value, even though it is reachable from `shark search` and `shark <entity> list --tag <name>` whenever the underlying service is wired with a nil `tagSvc` (e.g., a build of `shark` without tag support compiled in, or a test/dev wiring that intentionally omits the tag service per REQ-F-011).

## Expected Behavior

`tags.md` enumerates the same set of internal error classes that `tagsErrorCode` actually emits. Specifically:

- The Overview "Process-level exit codes" sentence at line 9 includes `unavailable` in both the exit-code-3 grouping and the JSON-envelope enumeration.
- The "JSON Error Envelope" reference table (lines 327-334) has a row for `unavailable` with a clear description of when it fires.
- The "Exit Code Summary" table (lines 368-376) has a row mapping exit 3 to `unavailable` with the trigger (e.g., "Search/list with `--tag` when tag service is not wired").

## Actual Behavior

`unavailable` is silently absent from every canonical list, even though `tagsErrorCode` returns it (line 297) and the underlying error type is exported and stable (`*services.TagFilterUnavailableError` at `internal/services/tag_errors.go:88-99`).

A row at line 887 of `tags.md` does mention `*TagFilterUnavailableError` in the AC-coverage matrix:

> | F05 AC-30 | Nil `tagSvc` permits tag-free lists; `Tags: non-empty` returns `*TagFilterUnavailableError` | Internal — graceful-degradation fallback |

…but this is internal acceptance-criteria language and is not connected to the user-facing exit-code/envelope tables that callers actually consult.

## Steps to Reproduce

1. Read `docs/cli-reference/tags.md` line 9, lines 327-334, and lines 368-376.
2. Read `internal/cli/commands/tags.go` lines 259-301 (the `tagsErrorCode` function).
3. Compare the documented error-class lists to the function's actual return values. The `unavailable` class is in the function (line 297) but absent from every documented list.
4. (Optional runtime confirmation) Construct a code path that triggers `*services.TagFilterUnavailableError` — e.g., by running a `shark search "..." --tag <name>` against a build that wires `SearchService` with `tagSvc == nil`. The CLI prints `Error: exit code 3: ...` and the JSON envelope `{"error":"unavailable","message":"..."}`.

## Fix Notes

This is a documentation-completeness bug; no Go code changes are needed.

Three places in `docs/cli-reference/tags.md` must be updated:

### 1. Overview "Process-level exit codes" sentence (line 9)

Add `unavailable` to both enumerations:

> The mapping is: `not_found` → 1, `db_error` → 2, and `unregistered_tag` / `tag_required` / `unauthorized` / `conflict` / `in_use` / `validation` / **`unavailable`** → 3. […] Callers that need to distinguish error classes should parse the JSON envelope's `error` field (`unregistered_tag`, `tag_required`, `not_found`, `conflict`, `in_use`, `validation`, `unauthorized`, **`unavailable`**, `db_error`) rather than rely on `$?` alone.

### 2. JSON Error Envelope reference table (lines 327-334)

Add a new row:

| `error` code (inner) | Condition |
|---|---|
| `unavailable` | Tag filter requested (`--tag <name>`) on a code path whose service was wired with a nil `tagSvc` (graceful-degradation fallback per REQ-F-011 / AC-T3 / AC-30). Returned by `*services.TagFilterUnavailableError`. |

### 3. Exit Code Summary table (lines 368-376)

Add a new row:

| Process exit | Internal class | Meaning | Common cause |
|---|---|---|---|
| 3 | `unavailable` | Tag filter unavailable | `--tag <name>` on `shark search` or `shark <entity> list` when the SearchService/ListService instance was constructed with a nil `tagSvc`. |

### 4. (Optional polish)

Consider adding a brief paragraph in the "Unregistered Tag Errors" / "Authorization and Password Cache" area that explains when `unavailable` actually surfaces, so a caller seeing it for the first time knows it is a wiring-state error, not a user-input error.
