# B061 research report

## Scope

B061 covers the contract between `shark sprint summary --detailed --json` and
the `/retro-sprint` Carryover Analysis note lookups. It does not add a
`rejected` summary field or change sprint completion semantics.

The affected summary contract is `carryover_entities[]`: each item must provide
the canonical Shark key required by its notes command and its `entity_type`.
The current workflow correctly uses `entity_type` for dispatch, but the summary
provider supplies a synthetic `type-id` string as `key`.

## Findings

### Reproduction

1. `SprintAnalyticsService.GetSummary(..., true)` obtains assignment rows with
   `entity_type` and numeric `entity_id`.
2. For every incomplete, active assignment, it emits
   `CarryoverEntity.Key = fmt.Sprintf("%s-%d", entityType, entityID)`.
   A task whose database ID is `42` therefore appears as `key: "task-42"`.
3. `/retro-sprint` reads `SUMMARY.carryover_entities[]`, uses its
   `entity_type: task`, and issues `shark task notes task-42`.
4. The notes command accepts a task key, not the synthetic assignment identity.
   The lookup cannot retrieve that task's notes, so the workflow records empty
   notes under its error-handling rule.

The currently shipped workflow has already incorporated B045's type-routing
repair: it reads `carryover_entities`, does not infer type from key shape, and
states that `rejected` is absent. B061 therefore remains valid as the provider
key-contract defect, while its older description of pattern-matching dispatch
is historical.

`SprintSummaryResult` has `carryover_entities` but no `rejected` field. The
workflow explicitly treats rejected work as empty. Adding rejected-work
semantics is separate new work and is not required to restore carryover notes.

The repository already joins each supported entity table in its `UNION ALL`
query. Each branch can select that table's canonical `key` alongside `size`.
The two adapters currently transfer only the existing fields into
`AnalyticsAssignedEntity`, so a canonical key must pass through the repository
row, both adapters, the service DTO, and `CarryoverEntity`.

Existing tests do not protect the production path. The DTO serialization test
constructs a `CarryoverEntity` with a canonical-looking task key directly, while
the service builds production values from numeric IDs. A regression test must
exercise the latter path.

## Decisions

Repair this by extending the existing detailed sprint-summary capability. Add a
canonical entity-key field to the assignment-query row and its service adapter
DTO, select `t.key`, `b.key`, `cc.key`, or `td.key` in the corresponding
`UNION ALL` branch, and assign it to `CarryoverEntity.Key`. Preserve
`entity_type` for note-command selection and preserve the existing
`(entity_type, entity_id)` composite identity used only for completion
calculation.

Do not add `rejected` as part of B061. The current workflow's explicit empty
handling is accurate. A future rejected-work feature must define its source,
disposition, and canonical-key contract before it is added to the summary.

Validate the repair with:

- repository coverage that returns canonical keys for task, bug, change-card,
  and tech-debt assignments;
- service coverage that produces canonical carryover keys from real assignment
  rows rather than a hand-built `CarryoverEntity`;
- JSON coverage for `carryover_entities[].key` and `entity_type`; and
- workflow-content coverage that keeps the embedded and Rider
  `retro-sprint.md` copies byte-identical and routes by `entity_type`.

Alternatives considered:

1. Keep synthetic keys and use `entity_type` only. Rejected because every notes
   command still requires a canonical key.
2. Add numeric-ID note lookups or resolve each ID during the workflow. Rejected
   because it creates a new CLI contract and duplicates the provider's
   polymorphic resolution work.
3. Omit notes when the summary provides synthetic keys. Rejected because it
   preserves the user-visible failure.
