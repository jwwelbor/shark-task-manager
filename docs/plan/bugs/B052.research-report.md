# B052 Research Report: Cascading Shark Run Sibling Transcript Collision

## Scope

**Problem statement:** With `CaptureAgentTranscripts` enabled, cascade children share the parent's `RunID` unchanged, each with independent `stageN` counters (reset to 1 per child). The transcript filename formula `.shark/runs/{runID}/{stageN}-{status}-{provider}.log` produces collisions when siblings dispatch in the same status/provider combination (e.g., two research tasks both dispatching as `stage 1` to `anthropic` in `research` status), causing silent file truncation. Additionally, `StageLog` entries are flattened into the parent's `result.Stages` without entity-key attribution, making per-child metrics unattributable after aggregation.

**Root causes:**
1. **Filename collision:** `relTranscriptPath` (internal/runner/transcript.go:50–52) receives `runID` and `stageN` but no entity identifier. Cascade children inherit the parent's `RunID` via `childOpts := opts` (controller.go:603–604) without modification. Each child's `Run()` loop has its own `iteration` counter (line 402) starting at 0, incremented before use (line 402). When child-1 and child-2 both reach their first dispatch, both use `stageN=1`, yielding identical filenames.
2. **Stage attribution loss:** Line 617 (`result.Stages = append(result.Stages, childResult.Stages...)`) flattens per-child stages into the parent's result. `StageLog` struct (lines 112–135) carries no `EntityKey` field, so after flattening, the source (which cascade child) becomes unrecoverable.

## Research Checklist

- [x] `scope_vocabulary` — Evidence: Cascade children are dispatched via `handleCascade` (lines 563–700); each child runs through its own `Run()` method (via `c.runChild`, line 605), starting a fresh iteration counter. Collision occurs when `relTranscriptPath(runID, stageN, status, provider)` is invoked without entity-key context. Flattening occurs at line 617. Key terms: `RunID` (correlation ID stable across cascade tree, unchanged per child), `stageN` (per-child iteration counter, independent reset), `EntityKey` (entity being run, available in `Run()` signature and handlers).

- [x] `affected_implementation_or_contract` — Evidence: `relTranscriptPath` (transcript.go:50-52) builds `.shark/runs/{runID}/{stageN}-{status}-{provider}.log` with no entity context; `writeTranscript` (transcript.go:79-106) writes via `os.WriteFile` (line 101), which silently overwrites on collision (no O_EXCL/atomic semantics); `key` (entity key) is already in scope at every `maybeWriteTranscript` call site (lines 993, 1200, 1253, 1456); `handleCascade` flattens child stages into the parent at line 617, and `StageLog` (lines 112-135) has no `EntityKey` field; cascade child setup at lines 603-604 copies `RunOptions` and sets `EntityType` only, `RunID` is never modified, and `RunID` is emitted unchanged in observability events (`emitStageStart` line 433, `emitStageDispatch` line 1075, `emitStageTransition` line 761).

- [x] `pattern_contract` — Evidence: `RunID` is the stable per-invocation correlation ID for observability across the whole cascade tree (all `stage.*` events emit it, and it names the `.shark/runs/{runID}` directory) -- changing it per child would break cross-cascade correlation. The `iteration` counter is 1-based per-entity-run semantics (initialized 0, incremented at loop top, line 402) -- the first stage of any entity's run is legitimately "stage 1", so per-child independence is intentional and correct; only the transcript-path formula fails to also carry entity identity. `os.WriteFile` has no atomicity guarantee and the writer treats overwrites as non-fatal (only MkdirAll/WriteFile errors surface a `run.transcript.warning`).

- [x] `dependency_impact` — Evidence: `runner/transcript.go` has no service/repo/config dependencies beyond file I/O and `RunOptions`, so adding an `entityKey` parameter to `relTranscriptPath`/`writeTranscript` is self-contained; it doesn't touch event emission (events already carry `RunID` for correlation, independent of file layout). `StageLog` is JSON-encoded inside `RunResult` (exercised in `internal/runner/controller_test.go`); adding an exported `EntityKey` field is additive/backward-compatible under Go's default unknown-field-tolerant JSON handling, and no external service parses `StageLog` by strict schema.

- [x] `cross_boundary_risks` — Evidence: `.shark/runs/` is gitignored, ephemeral, cleaned between runs, and not a stable API, so restructuring the path (adding an `{entityKey}/` subdirectory) is low-risk even though external glob-based tooling would need a depth update; `run.stage.*` events emit `transcript_path` as an opaque project-relative string, so path-format changes don't break consumers that only log/archive the value; manual CLI transcript inspection is user-visible but not a breaking CLI-flag change.

- [x] `alternatives` — Evidence: Rejected changing `RunID` per child (breaks cross-cascade observability correlation, since all `stage.*` events key on it). Rejected hashing `{runID}-{entityKey}` into an opaque per-child ID (obscures entity identity, complicates event emission which would then need to carry both the correlation ID and the hash). Accepted: nest the transcript path as `.shark/runs/{runID}/{entityKey}/{stageN}-{status}-{provider}.log` (collision-free, entity identity recoverable from path structure, minimal signature change, preserves RunID stability) over the alternative of embedding entityKey mid-filename (harder to scan, worse for variable-length keys). Separately, accepted adding an `EntityKey` field to `StageLog` for post-flattening attribution (trivial, additive, backward-compatible).

## Findings

### 1. Filename Collision Mechanism Confirmed

**Location:** `relTranscriptPath` (transcript.go:50–52), `writeTranscript` (transcript.go:79–106, writes via `os.WriteFile` line 101).

**Scenario:** Cascade action spawns two children (e.g., E07 → [E07-F01, E07-F02]). Parent calls `handleCascade` (line 563), which iterates children and calls `c.runChild(ctx, string(child.EntityType), child.Key, childOpts)` (line 605). Both children:
- Receive `childOpts.RunID` = parent's `RunID` (unchanged from line 603)
- Execute independent `Run()` loops, each with `iteration` starting at 0
- On first dispatch: `stageN=1`, `status` may be identical (e.g., both in "research"), `provider` identical (e.g., both "anthropic")
- Both invoke `maybeWriteTranscript(..., stageN=1, status="research", provider="anthropic", ...)`
- Both call `relTranscriptPath(runID, 1, "research", "anthropic")` → `.shark/runs/{runID}/1-research-anthropic.log`
- Both call `writeTranscript`, which calls `os.WriteFile(abs, content, 0o644)` (line 101)
- **Result:** Second write silently overwrites the first (no atomic semantics, no error on collision).

**Evidence:** No entity key is passed to or used by `relTranscriptPath` or `writeTranscript`. At the call site (`maybeWriteTranscript` calls, line 1200, 1253, 1456), `key` (the entity key) is in scope but is not forwarded.

### 2. Caller Has Access to Entity Key at Transcript Write Time

**Location:** `handleSpawnAgent` method (lines 993–1519); `maybeWriteTranscript` call sites (lines 1200, 1253, 1456).

**Evidence:** All three call sites are within methods that receive `key` as a parameter (e.g., `handleSpawnAgent` line 994). The entity key is fully known and available without additional lookups. No async/defer context would be lost; the entity key is local and stable within each dispatch handler.

### 3. StageLog Lacks Entity Attribution

**Location:** `StageLog` struct (lines 112–135), flattening at line 617.

**Evidence:** 
```go
type StageLog struct {
    Status string
    Action string
    AgentType string
    Provider string
    Duration time.Duration
    ExitCode int
    OutputSummary string
}
```
No `EntityKey` field. After flattening, the parent's `result.Stages` is a flat `[]StageLog` with no way to determine which child produced each entry.

### 4. RunID Stability Constraint

**Location:** `RunID` usage in observability events.

**Evidence:**
- Line 433: `emitStageStart(..., RunID: opts.RunID)`
- Line 437: Similar pattern in `emitStageDispatch`, `emitStageTransition`, `recordStageFailure`
- All handlers preserve `opts.RunID` as passed to `Run()`
- Cascade child setup (line 603) does NOT modify `opts.RunID`, maintaining correlation

**Impact:** `RunID` is the key for grepping logs and correlating stages across a single cascade tree. Changing it per child would fragment the run into uncorrelated pieces, breaking observability tools that expect one `RunID` per `shark run` invocation.

### 5. Backward Compatibility: StageLog JSON

**Evidence:** `RunResult` (lines 84–109) includes `Stages []StageLog` and is JSON-serialized for CLI output (e.g., `shark run --json`). Adding a field to `StageLog`:
- Go's `encoding/json` includes all exported fields in marshaling
- Clients using `json.Unmarshal` into `RunResult` default to ignoring unknown fields (unless `json.Number` or strict tags are used)
- Existing external consumers (if any) will silently ignore the new field
- **No breaking change.**

### 6. Test Coverage Gap

**Evidence:**
- `transcript_test.go` tests single-entity runs (no cascade)
- `controller_test.go` has cascade tests (e.g., `TestRunController_CascadeAction_RunsDispatchableChildrenAndAutoAdvancesParent`, line 925) but does NOT verify transcript file contents or collisions
- Existing tests would NOT catch this bug because they do not check filesystem artifacts or verify per-child transcript isolation

## Decisions

### Decision 1: Implement Alternative 3 (entity-key-based directory nesting) for filename collision

**Rationale:**
- Cleanest namespace per entity, collision-proof
- Preserves `RunID` stability for observability correlation (no breaking changes)
- Minimal code changes
- Backwards-compatible with event emission

**Specification:**
- Change `relTranscriptPath(runID, stageN, status, provider)` → `relTranscriptPath(runID, entityKey, stageN, status, provider)`
- Change return value from `.shark/runs/{runID}/{stageN}-{status}-{provider}.log` to `.shark/runs/{runID}/{entityKey}/{stageN}-{status}-{provider}.log`
- Thread `entityKey` through all call sites: update `writeTranscript`, `maybeWriteTranscript`, and handlers to pass entity key
- **No change to `RunID` semantics or observability events**

### Decision 2: Add EntityKey field to StageLog struct for attribution

**Rationale:**
- Recovers source entity after flattening
- Backward-compatible JSON serialization
- Trivial to implement (new field, populate at emission)
- Enables post-mortem analysis and debugging

**Specification:**
- Add `EntityKey string` field to `StageLog` struct (after `Status` for clarity)
- Populate at construction time wherever `StageLog` is created (e.g., lines 736, 847, 1038, 1131, etc.)
- In cascade children, `EntityKey` is the child's entity key (same as the entity passed to `runChild`)

## Pattern Contract

**Transcript path naming:** The current pattern `.shark/runs/{runID}/{stageN}-{status}-{provider}.log` is documented in `transcript_test.go` line 9 and the docstring at `transcript.go:20–22`. The new pattern `.shark/runs/{runID}/{entityKey}/{stageN}-{status}-{provider}.log` must be reflected in:
- Updated docstring in `transcript.go:20–22`
- Updated test fixture `relPathFor()` (currently `transcript_test.go:75–77`)
- All existing tests that verify transcript paths must be updated to expect the new layout

**RunID stability:** `RunID` remains a per-invocation correlation ID; cascade children do NOT receive a modified `RunID`. This is enforced by NOT modifying `opts.RunID` in `handleCascade()`.

**StageLog serialization:** The new `EntityKey` field is exported and JSON-included by default; no `json` tag or special handling needed.

## Dependency Impact

**Observability events:** No change. `run.stage.*` events continue to emit `RunID` for correlation; the `transcript_path` attribute value is updated to the new path format, but the attribute name remains the same.

**Workflow/Status transitions:** No change. Cascade children continue to use the same `Transitioner` and status workflow contracts; no modifications needed.

**Repository/Database layer:** No change. Transcripts are purely filesystem artifacts; no database schema or queries are affected.

**CLI contracts:** No change to command-line flags or output formats (transcripts are internal observability artifacts).

## Cross-Boundary Risks

**Tool compatibility:** External scripts that glob `.shark/runs/{runID}/*.log` to find transcripts must be updated to `.shark/runs/{runID}/**/*.log` or similar. This is **low-risk** because:
- `.shark/runs/` is added to `.gitignore` (confirmed in `transcript_test.go:504`)
- Transcripts are transient; not part of the stable project repository
- Documented as internal observability artifacts, not public API

**Event consumers:** Systems that read the `transcript_path` attribute from `run.stage.*` events will receive the new path format. This is **backward-compatible** because:
- The path remains a valid string; consumers that only log or archive it are unaffected
- No schema change in the event structure (still an attribute named `transcript_path`)
- Go's default JSON unmarshaling ignores unknown fields; consumers are resilient
