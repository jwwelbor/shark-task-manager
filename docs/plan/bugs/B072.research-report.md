# B072 research report

## Scope

B072 covers the `shark related-docs list` command contract for resolving an
entity from a key. The research reproduces the reported failure, traces the
current selector and document-service paths, and compares them with the
existing generic key-inference pattern. The immediate supported surface is
epic, feature, task, bug, change, and question keys; tech-debt and sprint
document support are not currently exposed by this command and should not be
silently added as part of this repair.

## Findings

1. The defect reproduces in the current executable. `./bin/shark related-docs
   list B072` exits 1 with `one of --epic, --feature, --task, --bug, --change,
   or --question must be specified`. The explicit workaround,
   `./bin/shark related-docs list --bug B072 --json`, exits 0 and returns `[]`.

2. The list command declares `Use: "list"` and does not accept a positional
   argument. `runRelatedDocsListList` reads only the six selector flags and
   rejects the request when all are empty. `dispatchListDocs` already routes
   each explicit selector to the corresponding key-based service method for
   epic, feature, bug, change, question, or task. The missing behavior is
   selector inference, not document retrieval.

3. The shipped help and CLI reference describe only epic, feature, and task
   selectors even though the implementation registers bug, change, and
   question flags as well. This is an adjacent documentation-contract drift
   that should be corrected when the positional-key form is documented.

4. Key inference is an established CLI capability. `DetectEntityType` is the
   shared key-format detector and covers bug, change, tech-debt, sprint, epic,
   feature, and task forms. The generic `links <key>` command uses
   `resolveEntityKeyToTypeAndID`, which normalizes the key, detects its type,
   maps it to `models.EntityType`, and resolves it through the entity registry.
   The parity test keeps command-level detection aligned with the key service.

5. Related-document retrieval is already implemented behind entity services:
   epic, feature, bug, change-card, question, and task services expose
   key-based document-list methods. Existing related-doc command tests cover
   explicit epic, feature, and task flags and JSON output, but do not cover a
   positional key, selector/positional ambiguity, or inferred bug/change/
   question dispatch.

6. The v2 universal catalog requires scope and affected-contract evidence and
   permits standard rigor with either a local pattern or dependency-impact
   analysis. No separate related-work item or new persistence boundary was
   discovered; the useful related pattern is the already-shipped generic key
   dispatcher.

## Decisions

1. Extend the existing related-document listing capability. Accept one
   positional entity key as the canonical shorthand while preserving the
   existing explicit selector flags for compatibility and clarity.

2. Reuse the established key vocabulary and detection path rather than adding
   a second parser. The implementation should normalize and classify the
   positional key with the shared detector, then dispatch to the existing
   entity service methods. It should reject a positional key combined with an
   explicit selector and return a clear unknown/unsupported-type error for
   keys outside the related-document service surface.

3. Keep tech-debt and sprint keys explicitly out of this repair unless a
   separate capability decision adds their document relationships. The
   universal recipe catalog names those entity types, but the current
   related-docs command has neither matching selector flags nor a complete
   dispatch contract for both types.

4. Update command help and the maintained CLI reference alongside the runtime
   contract. Add positional-key examples, retain explicit-flag examples, and
   make the documented supported entity types match the implementation.

5. Add focused command coverage for positional bug, epic/feature/task, change,
   and question keys, invalid keys, and mixed positional-plus-flag input. This
   is an extension of existing CLI behavior, not new storage or document
   linking work.
