# B115 Repair Plan: Publish Entity Files Without Partial Targets

## Purpose and approval state

This plan defines the B115 repair for failed atomic entity-file publication. It
uses the diagnosis in [B115.md](B115.md), the linked
[research report](B115.research-report.md), accepted Shark decisions, and the
production caller sweep recorded there and in Shark.

Plan revision: 1. This revision is pending independent plan review. After

## Diagnosis

At the declared review baseline, `EntityFileWriter.writeFileExclusive` opens
the final entity path with `O_CREATE|O_EXCL|O_WRONLY`, writes directly to that
visible path, and then syncs it. A write or sync error returns without removing
the path. The call reports an error without a `WriteResult`, while a partial
file can remain and block a retry or be mistaken for an existing document.
`O_EXCL` prevents another creator from opening an already claimed path; it does
not stage the content or make publication atomic.

The shared writer has four production paths that call it with
`UseAtomicWrite: true`: task creation, non-Force bug creation, change-card
creation, and tech-debt creation. Task creation and tech-debt creation already
return writer errors before committing their database rows. Bug and change-card
creation insert rows first and currently need rollback when atomic publication
fails. Their tag and index work must follow successful publication. The
non-atomic epic, feature, sprint, and forced-bug paths have separate existing
behavior and are not part of this repair.

## Accepted approach

1. Extend the existing `EntityFileWriter`; do not add a second file-writing
   path. For `UseAtomicWrite: true`, create a unique sibling staging file,
   write the complete byte slice, sync it, check close, and capture its file
   identity before publication. On any staging failure, remove only that
   staging path and return the error. Do not open or remove the final path as
   failure cleanup.
2. Publish without replacing a target that appeared during staging. Use the
   native no-replace rename on Linux, macOS, and Windows with the existing
   `golang.org/x/sys` dependency. Use `os.Link` only when native publication is
   unavailable. If neither operation is supported, remove the staging file and
   fail closed. Never fall back to writing directly to the visible target.
3. Preserve a target that wins the publication race. Return the existing-file
   result only after verifying with `Lstat` that the target is a regular file.
   Return created-file identity for successful publication so B114 transaction
   compensation can use its accepted ownership check.
4. Keep the atomic preflight and raced-target checks scoped to atomic writes.
   Preserve legacy `os.Stat` behavior for non-atomic calls. Keep the
   `BugService` and `ChangeCardService` rollback and side-effect changes limited
   to their atomic publication path. Share their rollback error handling and
   perform compensating deletion with
   `context.WithTimeout(context.WithoutCancel(requestCtx), 5*time.Second)` so
   cancellation does not suppress cleanup and the cleanup remains bounded.
5. Add deterministic writer-failure and concurrent-target tests, caller
   regressions, architecture wording, and a CI package-test step in the
   existing Linux, macOS, and Windows matrix.

This approach follows Architect decision B115 note 3642. It supersedes the
initial hard-link-only approach in note 3627; the later decision selected
native no-replace rename with a hard-link fallback and fail-closed behavior.

## Preserved behavior

- A regular pre-existing file can still be linked without being rewritten;
  `WriteResult.Written`, `WriteResult.Linked`, paths, and created-file identity
  continue to describe the operation.
- New entity files keep mode `0644`.
- `UseAtomicWrite: false` keeps existing `os.Stat` and direct-write behavior.
  This includes the current epic, feature, sprint, and forced-bug paths.
- Bug creation with `Force: true` keeps its existing best-effort file-write
  behavior and tag/index ordering. Its replacement behavior is tracked by
  B119.
- Tech-debt creation continues to write before inserting its database row.
  Its Force retry continues to reuse a regular file only when its bytes match
  the expected document exactly.
- Task creation continues to commit its database transaction only after file
  publication succeeds. Its separate commit-failure compensation remains
  bounded by B114 decisions 3630 and 3652.
- The repair adds no database schema and no new platform or dependency choice.

## Scope and production callers

The B115-owned surface is the shared atomic publication contract and its four
atomic caller paths. The expected code and test surface includes:

- `internal/fileops/writer.go`, `internal/fileops/doc.go`,
  `internal/fileops/rename_linux.go`, `internal/fileops/rename_darwin.go`,
  `internal/fileops/rename_windows.go`, and
  `internal/fileops/rename_other.go`;
- `internal/fileops/writer_atomic_test.go`, `internal/fileops/writer_test.go`,
  and `internal/fileops/writer_umask_unix_test.go`;
- `internal/taskcreation/creator.go` and its writer/commit tests, including
  the B114 ownership boundary;
- `internal/services/bug_service.go`,
  `internal/services/change_card_service.go`, the shared publication rollback
  helper, and caller failure/success tests;
- `internal/services/tech_debt_service.go` only if the caller sweep finds a
  required compatibility correction; its current order already propagates a
  write error before row insertion;
- `docs/architecture/architecture-overview.md`,
  `docs/architecture/patterns-catalog.md`, and
  `.github/workflows/ci.yml` for the three-platform runtime test gate.

Because the shared writer also participates in B114, freeze and review the
combined candidate. Keep B114 transaction-compensation requirements distinct
from B115's failed-publication cleanup.

### Exclusions

- B117 symlink containment and dangling-symlink behavior outside this atomic
  publication contract.
- B118's Force check/remove race.
- B119's forced-bug replacement behavior and atomic Force collision behavior.
- External edits or replacement after successful publication during B114's
  later database-commit compensation interval; the accepted B114 decisions do
  not claim an atomic check-and-remove boundary for non-cooperating tools.
- TD-599, the existing writer-context standard gap.

## Constraints and accepted boundaries

- Use only the already accepted same-directory staging and no-replace
  publication strategy. Do not choose a new filesystem platform, library, or
  persistence model within this repair.
- Atomic failure cleanup may remove only the staging sibling created by this
  call. It must preserve the final target whether that target was pre-existing
  or appeared during write, sync, close, or publication.
- The atomic path must link only regular files. The non-atomic path retains its
  prior target checks and behavior.
- Do not claim that local Linux tests validate the macOS or Windows adapters.
  The `internal/fileops` package suite must run in each existing OS matrix job.
  Until those external CI jobs pass for the frozen candidate, report the gate
  as blocked rather than accepted.

## Review baseline and gate rules

The immutable review baseline is Shark Task Manager commit
`6fe03c740cb7d1ab1ab743dfb6c675b69ee38de9`. B115's R14–R25 candidate
records use this full commit as their base. The plan reviewer must independently
resolve this exact commit and inspect `internal/fileops/writer.go` there to
confirm that the final path is opened directly and that write or sync failure
does not clean it up. Do not substitute a later candidate or the current branch
tip. The separate evidence record contains the plan-preparation confirmation;
it does not replace independent review.

For code review and QA, freeze the combined B114/B115 candidate and verify its
tree, diff digest, and full base-to-candidate manifest against the same review
baseline. Review the complete candidate rather than only the latest commit.
Keep the approved plan digest unchanged. A diagnosis change returns to research;
a material approach, omission, or scope change requires a new plan revision and
independent plan review; a coding defect returns to development. Any candidate
change invalidates candidate-bound review and QA unless the unchanged evidence
can be proven to cover the new candidate. Unavailable external CI evidence is
blocked, not acceptance.
