# Sprints cannot advance past 'planning' with the shipped default sprint workflow

## Description

PR #101 (`feat(E19-F08): sprint workflow YAML with first-class lifecycle and
agent routing`) shipped `internal/sharkdata/default_data/workflow/sprint.yaml`
with a full route-based lifecycle
(`planning -> research -> active -> closing -> completed -> archived`), each
step declaring `action: spawn_agent` for dispatch. But `shark next` /
`shark status` were never wired up for entity type `"sprint"`, and
`shark sprint start` still performs the old direct `planning -> active`
transition, which the new workflow graph no longer allows. As shipped, on the
default workflow a sprint cannot leave `planning` through any documented CLI
command.

## Expected Behavior

One of:

- (a) `shark next` / `shark status` support entity type `sprint`, so the
  shipped route-based workflow (with its `spawn_agent` steps for `planning`,
  `research`, `closing`) can actually be driven end to end like any other
  entity type, or
- (b) `shark sprint start` bypasses/collapses the `research` gate the way the
  pre-PR#101 simple lifecycle did, or
- (c) the default `sprint.yaml` ships with a documented, working CLI path
  from `planning` to `active` (e.g. a `shark sprint research` or
  `shark sprint advance` command).

Whichever is chosen, a fresh project using CLI defaults (no custom
`shark-data` workflow override) must be able to start a sprint.

## Actual Behavior

`shark sprint start <key>` on a sprint in `planning` fails:

```
cannot start sprint S007 in status planning: invalid transition from 'planning' to 'active'.
Fix: valid transitions from 'planning': research, on_hold. Use --force to override
```

The suggested `--force` flag does not exist on `shark sprint start`
(`Error: unknown flag: --force`). There is also no other CLI path to move a
sprint into `research`:

- `shark next <sprint-key> --json` → `failed to build transitioner for sprint: unsupported entity type: "sprint"` (`buildTransitioner()`, `internal/cli/commands/run.go:657-676`, only handles `task/feature/epic/bug/change/tech_debt/question`).
- `shark status set <sprint-key> research` / `shark status transitions <sprint-key>` → `unsupported entity type: sprint` (`internal/cli/commands/status_group.go:252,274`).
- Same gap in `internal/cli/commands/workflow_show_action.go:229`.

`SprintService.StartSprint` (`internal/services/sprint_service.go:467-511`)
validates the `planning -> active` transition directly against the loaded
workflow's transition graph (`s.workflowSvc.ValidateTransition`), which is
correct given the shipped `sprint.yaml`, but nothing in the CLI can dispatch
or advance a sprint through the intervening `research` step, so the sprint is
permanently stuck.

**Impact:** any project relying on the shipped default workflow (no custom
`shark-data/workflow/sprint.yaml` override) cannot start a sprint at all via
the documented `shark sprint start` command.

## Steps to Reproduce

1. In a project using the CLI's built-in default workflow (no
   `shark-data/workflow/sprint.yaml` override — confirm via
   `shark admin workflow list --json`, sprint level `"source": "default"`).
2. `shark sprint create "Test Sprint" --start=2026-09-03 --end=2026-09-10`
   → sprint created in status `planning`.
3. `shark sprint start <key>` → fails with the transition error above.
4. `shark sprint start <key> --force` → `Error: unknown flag: --force`.
5. `shark next <key> --json` → `unsupported entity type: "sprint"`.
6. `shark status set <key> research --json` → `unsupported entity type: sprint`.

Observed on `shark version dev (10e63ce8) built 2026-08-27`, reproduced from
`wwgm` project sprint `S007`.

## Fix Notes

Root cause: `sprint.yaml`'s workflow graph and the CLI's supported
entity-type list diverged after PR #101 added agent-routed sprint lifecycle
steps without updating `buildTransitioner()` /
`internal/cli/commands/status_group.go` /
`internal/cli/commands/workflow_show_action.go` to recognize `"sprint"`, and
without updating `SprintService.StartSprint` to route through `shark next`
instead of a direct hard-coded `planning -> active` set. Fix should decide
whether sprints are meant to be full route-based entities (wire up (a) above,
consistent with the `spawn_agent` steps already in `sprint.yaml`) or keep the
simple start/close lifecycle (fix (b)/(c) above and simplify `sprint.yaml`
back to a direct `planning -> active` transition) — and add a regression test
covering `shark sprint start` on a fresh `planning` sprint under the default
workflow.
