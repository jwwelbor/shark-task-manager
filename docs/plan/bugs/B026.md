# shark status advance rejects valid bug transitions from draft/in_development

## Description

`shark status advance <bug-key>` errors with `WARNING: No valid transitions from status '<status>'` when the bug is at `draft` or `in_development`, even though `shark-data/workflow/bug.yaml`'s `status_flow:` block lists those exact transitions:

```yaml
status_flow:
  draft:
    - ready_for_development
    - cancelled
    - on_hold
  in_development:
    - ready_for_code_review
    - blocked
    - on_hold
```

`shark next <bug-key>` reads the same yaml and works correctly — only the `status advance` path is inconsistent. The workflow loader / validator used by the status-advance code path is not picking up bug-entity transitions.

## Expected Behavior

`shark status advance B026` on a bug in `draft` advances to `ready_for_development` (the first entry in the status_flow list) without requiring `--force`.

## Actual Behavior

```
$ shark status transitions B026
Bug: B026
Current status: draft
WARNING No valid transitions from current status

$ shark status advance B026
Error: failed to set bug status: status 'draft' is not defined in workflow.
Fix: add this status to workflow config or use --force to override
```

Workaround: `shark status set <key> <next-status> --force` (bypasses workflow validation entirely — undermines the safety the workflow file was meant to provide).

## Steps to Reproduce

1. With any bug in `draft` (e.g., a freshly-created one): `shark create bug "test bug" --severity=low`
2. Run `shark status advance <bug-key>` and observe the "No valid transitions" warning.
3. Run `shark status transitions <bug-key>` and observe the same warning.
4. Compare with `shark next <bug-key> --json` — that path reads the same yaml and works.

## Fix Notes

Likely fix surface: `internal/config/workflow/` loader/validator code path used by `shark status advance` / `shark status transitions`. Compare with the code path used by `shark next` (which reads bug.yaml correctly) — find the divergence and align.
