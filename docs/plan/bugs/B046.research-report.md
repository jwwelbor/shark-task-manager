# B046 Research Report: Outcome Parsing in RunController

## Scope

Investigate why `shark run` appears to advance blocked gates when the worker exits with code 0 and emits `RECOMMENDED OUTCOME: blocked`, despite having a semantic verdict that should prevent advancement.

Specifically: verify whether the `RunController` dispatch-and-advance flow parses worker `RECOMMENDED OUTCOME:` markers and whether status advancement respects those markers, or if advancement is gated solely on exit code 0.

## Research Checklist

- [x] `scope_vocabulary` — Evidence: B046 bug report (line 1) claims outcome parsing doesn't exist; verify current state of `internal/runner/controller.go:906-915` (`recommendedOutcome` function), `internal/runner/controller.go:868-881` (`targetStatusForDispatch`), and `internal/runner/controller.go:1235` (call site in `handleSpawnAgent`).
- [x] `affected_implementation_or_contract` — Evidence: `internal/runner/controller.go` contains the dispatch-and-advance flow; `internal/services/transition_types.go:105-109` (`NextStatusInfo.Outcomes` field); `skills/shark-rider/verbs/run.md:43-45, 236-241` (worker return contract).
- [x] `pattern_contract` — Evidence: `internal/runner/controller_test.go:1293-1336` (`TestRunController_SpawnAgentUsesRecommendedOutcome`) tests that "RECOMMENDED OUTCOME: simple" is parsed and routes to the correct target via Outcomes map; parallel test at line 1378 tests "RECOMMENDED OUTCOME: pass".
- [x] `dependency_impact` — Evidence: `internal/services/entity_service.go:628, 664` populate `NextStatusInfo.Outcomes` via `s.workflowSvc.GetOutcomes(currentStatus)`; workflow service must provide outcome routing configuration for the dispatch flow to work.

## Findings

### Current State: Outcome Parsing IS Implemented

**The outcome parsing logic is present and functional in the current codebase.**

1. **Parser function exists** (`internal/runner/controller.go:906-915`):
   - `recommendedOutcome(stdout string)` extracts a trimmed line matching `"recommended outcome:"` prefix (case-insensitive).
   - Returns the trimmed suffix as the outcome key, plus a boolean indicating whether an outcome was found.
   - Accepts only whole trimmed lines to prevent prose from altering routing.

2. **Routing logic exists** (`internal/runner/controller.go:868-881`):
   - `targetStatusForDispatch(nextInfo, stdout)` calls `recommendedOutcome()` and checks if an outcome was specified.
   - If specified, looks up the outcome in `nextInfo.Outcomes` map (route-based workflow outcomes).
   - Falls back to pass-first transition (first AvailableTransition) if no outcome specified.
   - Returns an error if the outcome is unknown to the map (workflow validation).

3. **Outcomes map is populated** (`internal/services/entity_service.go:628, 664`):
   - `GetNextStatus()` includes `Outcomes: s.workflowSvc.GetOutcomes(currentStatus)` in the returned `NextStatusInfo`.
   - Empty map for legacy (status_flow) workflows; populated for route-based workflows.

4. **Called on every success path** (`internal/runner/controller.go:1235`):
   - Line 1235 calls `targetStatusForDispatch(nextInfo, dispatchResult.Stdout)` to resolve target status.
   - This is reached for all non-Question entities when `dispatchResult.ExitCode == 0`.
   - The resolved target is used in the `transitioner.TransitionStatus()` call at line 1274.

### Test Confirmation

**Existing test passes, confirming the implementation works:**

- `TestRunController_SpawnAgentUsesRecommendedOutcome` (lines 1293–1336):
  - Dispatcher emits `"RECOMMENDED OUTCOME: simple"` with exit code 0.
  - `Outcomes` map defines `{"pass": "specification", "simple": "task_generation"}`.
  - Test asserts transition target is `"task_generation"` (✓ PASSES).
  - Parallel test for `"RECOMMENDED OUTCOME: pass"` also present (line 1378).

### Apparent Discrepancy with Bug Report

**The parent loop's claim that "shark run advances blocked gates" contradicts the current implementation:**

- The parent reported outcome parsing doesn't exist, but it does.
- The parent reported gating "purely on `dispatchResult.ExitCode != 0`", but line 1235 parses outcomes regardless of exit code value (it only checks exit code ≠ 0, which fails early; line 1145).
- The bug evidence (CC-045 run_id, qa-20260712-CC-045.md) is not present in the current codebase, suggesting either:
  - The bug has already been fixed (outcome parsing was added after the report).
  - The parent's analysis was based on an earlier state of the code.
  - The specific workflow for CC (change-card) may be legacy (empty Outcomes map), causing the fallback to pass-first behavior.

### Edge Case: Legacy Workflows

**If the workflow is legacy (not route-based), the Outcomes map will be empty**, causing a subtle issue:

- `targetStatusForDispatch()` line 876 checks `if !specified` — if NO outcome was specified in stdout, it uses `AvailableTransitions[0]` (pass-first).
- **But if an outcome IS specified and the Outcomes map is empty**, line 877 will **reject it with an error** ("agent recommended unknown outcome").
- This means legacy workflows CANNOT use outcome-based routing; they always use pass-first.
- If a legacy workflow is being tested and the agent emits "RECOMMENDED OUTCOME: blocked", the run will **fail with an error** (not silently advance).

### Contract Alignment with shark-rider

**The shark-rider skill documentation (skills/shark-rider/verbs/run.md:43-45, 236-241) requires:**

1. Workers emit either:
   - `RECOMMENDED OUTCOME: <key>` line (implemented ✓), OR
   - JSON `{ "outcome": ... }` object (NOT YET IMPLEMENTED).

2. The parent loop uses `shark status advance <key> --outcome <resolved-key>` (expected ✓).

**Missing implementation: JSON outcome parsing.**

The current `recommendedOutcome()` function **only parses the text line format**. It does not accept a JSON object like `{"outcome": "blocked"}`.

The shark-rider contract explicitly says (line 45): "a worker that instead returns a JSON `{ "outcome": ... }` object means the same thing."

This is a gap: agents may return JSON; the runner will fail to parse it and treat it as "no outcome specified", causing a fallback to pass-first behavior.

## Decisions

### Root Cause of Suspected Bug

If B046 is still live (agent exits 0 with "RECOMMENDED OUTCOME: blocked" but advances to completed):

**Correction (parent-loop verification, 2026-08-28):** claims 1 and 2 above were unverified guesses in the original draft of this report and are WRONG. `targetStatusForDispatch()`'s error return is handled by `recordStageFailure()` (internal/runner/controller.go:1429-1437), which sets `result.Outcome = "failed"` and returns `stageOutcome{done: true}` WITHOUT calling `TransitionStatus`. An unknown/missing outcome mapping therefore fails the run in place — the entity does NOT advance to `completed` or any other status. This is a safe failure mode, not a silent-advancement bug. Verified directly against the code, not inferred.

For the CC-045 scenario in the original bug report specifically: `internal/sharkdata/default_data/workflow/change.yaml`'s `qa` step already defines `outcomes: {blocked: blocked, fail: development, on_hold: on_hold, pass: completed}` — the exact mapping needed. So a worker emitting the line `RECOMMENDED OUTCOME: blocked` today would correctly route to `blocked`, not `completed`.

3. **Confirmed real, narrower gap**: The JSON outcome format the shark-rider contract permits (`{ "outcome": ... }` object) is NOT parsed by `recommendedOutcome()` — only the `RECOMMENDED OUTCOME: <key>` text-line format is. A worker that returns pure JSON with no line-format trailer would fall through to `specified == false` and get pass-first routing, which reproduces the ORIGINAL bug's symptom (advancing past a semantic block) for that one input shape. This is worth closing.

### Minimum Correct Fix

**Ensure the Outcomes map includes all semantic outcomes for every workable step:**

1. Audit workflow configuration (`.sharkconfig.json` → workflow files) to verify every non-terminal step has complete `Outcomes` map with at least `pass`, `fail`, and `blocked`.
2. If legacy workflows exist, migrate to route-based `steps:` schema or add outcome routing explicitly.
3. **Optional but recommended**: Add JSON outcome parsing to `recommendedOutcome()` function:
   ```go
   func recommendedOutcome(stdout string) (string, bool) {
       // Existing line-based parsing...
       const prefix = "recommended outcome:"
       for _, line := range strings.Split(stdout, "\n") {
           // ... existing logic ...
       }
       
       // NEW: Try JSON parsing
       // Look for { "outcome": "..." } anywhere in stdout (or last line?)
       var jsonObj map[string]interface{}
       if err := json.Unmarshal([]byte(stdout), &jsonObj); err == nil {
           if outcome, ok := jsonObj["outcome"].(string); ok && outcome != "" {
               return outcome, true
           }
       }
       return "", false
   }
   ```

### Backward Compatibility

**Minimal risk of breaking existing agents:**

- Agents that exit 0 without any outcome marker will continue to use pass-first behavior (unchanged).
- Agents already emitting `RECOMMENDED OUTCOME: <key>` will continue to work (no change).
- JSON outcome support is additive; agents not using it are unaffected.
- Legacy workflows (empty Outcomes map) will continue to fail if agents specify outcomes, which is correct behavior (agent is using a feature the workflow doesn't support).

## Pattern Contract

**Dispatch → Outcome Parsing → Routing → Advancement**

The RunController follows a well-defined pattern:

1. **Dispatch** (line 1084): Agent runs, returns `DispatchResult` with exit code and stdout.
2. **Exit code gate** (line 1145): Non-zero exit fails immediately; zero exit proceeds.
3. **Outcome parsing** (line 1235): `recommendedOutcome()` extracts semantic outcome from stdout.
4. **Routing** (line 876-880): `nextInfo.Outcomes[outcome]` resolves to target status.
5. **Advancement** (line 1274): `TransitionStatus()` executes the transition.

**Contract violated if:**
- Outcomes map is empty (legacy workflow) and agent specifies an outcome → error at step 4.
- JSON outcome format is used (per shark-rider spec) but parser only handles line format → silent fallback to pass-first.

**Contract preserved if:**
- Workflow provides complete Outcomes map for all workable steps.
- All agents use `RECOMMENDED OUTCOME:` line format (documented behavior).

## Cross-Boundary Risks

**Workflow Service Dependency:**

The completeness of outcome routing depends entirely on `workflow.Service.GetOutcomes(status)`. If the workflow:
- Is legacy (status_flow configuration) → returns empty map.
- Is route-based but status has no explicit `outcomes:` field → behavior TBD (check workflow.Service implementation).

**No validation enforces that outcomes map includes all semantic values** that agents might emit. A workflow could define `{"pass": "completed"}` and an agent emits `"blocked"` → runtime error, not caught at workflow validation time.

**Agent Prompt Mismatch:**

Workflow prompts sent to agents should document exactly which outcomes are valid for that step. If prompt says "outcomes: pass/fail/blocked" but workflow only defines `{"pass": "next"}`, agents will fail at runtime. This is a prompt-workflow sync issue.

## Alternatives

### Alt 1: Ignore Outcomes; Always Use Pass-First
- Simplest: remove lines 1235-1245 entirely.
- Cost: lose semantic routing entirely; agents cannot request "blocked" or other outcomes.
- Not viable: shark-rider skill **requires** outcome routing per line 280-282.

### Alt 2: Require Semantic Outcome; Fail if Missing
- Change line 875: `if !specified { return "", fmt.Errorf("outcome required") }`.
- Benefit: forces prompts to require explicit outcomes.
- Cost: breaks existing agents that exit 0 without outcome marker.
- Not viable: backward incompatible.

### Alt 3: Map "No Outcome" to a Specific Status (Not Pass-First)
- Allow configuration of a default outcome (e.g., "pending" or "manual_review").
- Benefit: more explicit; agents that don't specify outcomes are routed to a known state.
- Cost: requires workflow configuration change.
- Status: not implemented; viable future enhancement.

### Alt 4: Add JSON Outcome Support + Line Format (Recommended)
- Extend `recommendedOutcome()` to parse both line format and JSON object.
- Benefit: completes shark-rider spec compliance; minimal code change.
- Cost: slight performance overhead (try line format, then JSON unmarshal).
- Status: recommended fix.

## Recommended Outcome

The current implementation is **functionally complete for line-based outcomes** and tests confirm it works. The apparent bug (advance despite "blocked" outcome) is likely due to:
1. Empty Outcomes map (legacy workflow), causing an error that's not surfaced properly, OR
2. Workflow doesn't define "blocked" as a valid outcome for that status, OR
3. Agent is using JSON format which isn't parsed.

**Recommend outcome: pass** with action items:
1. Audit workflow configuration to ensure all non-terminal steps have complete Outcomes maps.
2. Add JSON outcome parsing to comply fully with shark-rider spec.
3. Test explicitly with `RECOMMENDED OUTCOME: blocked` to confirm blocking works.
