# shark next warns that literal <br> is an unresolved placeholder

## Description

Confirmed in B145 development dispatch on 2026-11-25: the approved repair plan uses literal <br> in a Markdown coverage cell. internal/templates/agent_body.go:30-35 regex matches it despite the adjacent comment saying <br> must not match. internal/cli/commands/next.go:1572-1586 reports the match as unresolved, although it remains ordinary prompt text and the rendered prompt is not changed. Reproduction: shark next B145 --workdir <worktree> --json; unresolved_placeholders contains <br> and stderr warns, while the complete approved plan remains present in response.prompt. Fix the detector or its context-aware scanning and prove genuine unresolved template tokens still warn.

## Expected Behavior

Literal HTML tags such as `<br>` inside rendered plan content remain part of the prompt and do not appear in `unresolved_placeholders`. Genuine unresolved workflow placeholders remain listed and produce the existing warning.

## Actual Behavior

The placeholder scanner matches the literal `<br>` table separator, adds it to `unresolved_placeholders`, and emits `[shark-stats] WARN: B145 has 1 unresolved placeholders`. The response prompt is not truncated or altered, so the warning falsely suggests missing instructions.

## Steps to Reproduce

1. In the WWGM project context, run `shark next B145 --workdir <B145 worktree> --json` while the committed plan contains the literal `<br>` table separator.
2. Observe `unresolved_placeholders: ["<br>"]` and the stderr warning; verify the full plan remains present in `response.prompt`.

## Fix Notes

Keep detection of actual unresolved workflow tokens while excluding ordinary markup in rendered content. Do not rewrite or normalize the prompt bytes to suppress this warning.
