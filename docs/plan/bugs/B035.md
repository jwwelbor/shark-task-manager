# shark run --dry-run infinite-loops on any multi-stage entity (re-queries live DB status instead of tracking simulated status)

## Description

internal/runner/controller.go handleSpawnAgent (line ~531) and handleAdvanceStatus (line ~391) dry-run branches both call c.transitioner.GetNextStatus(ctx, key), which re-reads the entity CURRENT REAL status from the database rather than deriving transitions from the in-memory simulated currentStatus. Since dry-run never persists a real TransitionStatus call, every loop iteration after the first re-derives 'next status' from the same unchanged DB row, so the simulation gets stuck forever repeating the second stage's target status. Discovered while manually verifying B034 (shark next/run for change-cards): running 'shark run CC-041 --dry-run' after the B034 fix (which lets change-cards progress past the first status lookup) spun for 290+ iterations stuck at status=code_review because the real DB row stayed at development and GetNextStatus(development) always returns code_review as the first-priority transition target. This affects any entity type/workflow where a dry-run traverses 2+ stages, not just change-cards -- B034's fix does not touch this code path (internal/runner/controller.go) at all. Reproduce: point a draft-status change-card (or any multi-stage entity) through 'shark run <key> --dry-run --verbose' and watch shark.log run.stage.start events repeat the same status indefinitely. Fix should track the simulated status locally (e.g. compute the next transition from the workflow config for the in-memory currentStatus) rather than re-querying the live entity from GetNextStatus during dry-run stage simulation.
