# retro-sprint Carryover Analysis: SUMMARY.carryover/.rejected key shape never matches any note-lookup dispatch

## Description

Discovered during B045's second code-review pass (docs/review/bugs/b045/code-review-20260828-0344-B045.md): retro-sprint.md Step 2a assumes SUMMARY.carryover/SUMMARY.rejected contain real entity keys (E07-F01-001, B001, CC-001, TD-001) to dispatch through the shark <entity-type> notes <key> lookup table B045 just fixed. But runSprintSummary marshals the DTO directly, and CarryoverEntity.Key is actually built as fmt.Sprintf("%s-%d", entityType, entityID) -- e.g. "task-42", not a real key. There is also no "rejected" field at all in the summary output; the actual field is "carryover_entities", not "carryover". So no real summary value ever matches any dispatch-table row -- the Carryover Analysis section falls through to the fallback clause every time, rendering empty at runtime regardless of B045's fix.

This is pre-existing (inherited from the rider source's original abstract wording, which made the identical wrong assumption) and outside B045's sync scope -- B045 fixed the dispatch table's correctness but not this upstream data-shape mismatch.

Suggested fix direction (not verified/designed, needs its own research pass): read carryover_entities[].entity_type directly from the summary JSON instead of sniffing key shape from a key that's actually just "<type>-<id>", or fix the underlying summary key-building to emit real entity keys.

Evidence: internal/services/sprint_service.go CarryoverEntity.Key construction (fmt.Sprintf("%s-%d", entityType, entityID)); runSprintSummary DTO marshaling; internal/sharkdata/default_data/skills/sprint-analytics/workflows/retro-sprint.md Step 2a (post-B045).
