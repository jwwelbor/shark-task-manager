## Findings

### The emitted command is not accepted

The maintained solo workflow constructs “shark sprint next {SPRINT_KEY} --json” and its --agent variant at lines 77-79. The CLI defines sprint next with no positional arguments (cobra.NoArgs); help shows “shark sprint next [flags]”. Reproduction on the B081 worktree with “go run ./cmd/shark sprint next S010 --json” exits 1 and returns “unknown command \"S010\" for \"shark sprint next\"”. The error occurs before selection or dispatch.

The top-level sprint-execution skill already documents “shark sprint next --json” without a sprint key. The maintained and embedded nested workflows nevertheless both emit the unsupported keyed form in both branches.

### Removing the key alone would not preserve sprint scope

The no-argument sprint-next command calls SprintService.GetNextTask with only the agent filter. GetNextTask uses selectExecutionSprintCandidates, which gathers and sorts candidates across every sprint whose status is in the configured execution phase. The returned entity includes sprint_key, but the selection is not scoped to the S### passed to /run-sprint.

The database deliberately permits multiple concurrent active sprints: migrateDropSprintActiveIndex removes the single-active constraint, and TestMigrateSprintTables_SingleActiveSprintIndex inserts two active sprints. Therefore checking only that the requested sprint is active does not prove that keyless sprint next will select from it. In the current project database, “go run ./cmd/shark sprint list --status=active --json” returned an empty list on 2026-11-18; the cross-sprint selection risk is established by the current service and schema behavior, not by a live pair of active sprints in this database.

The existing exact-key selector is “shark plan <SPRINT_KEY> --json” with optional --agent. runPlanSprintSelection passes an explicit sprint key to SprintService.SelectSprint, which loads that sprint's backlog, applies workflow/claim/admission filters, sorts the candidates, and returns the selected sprint_key with an entity or ordered entities. A solo loop can consume the first ordered candidate per iteration and validate the response sprint_key before dispatch.

The maintained host workflow at skills/shark-rider/skills/sprint-execution/workflows/run-sprint.md and the embedded workflow at internal/sharkdata/default_data/skills/sprint-execution/workflows/run-sprint.md have the same SHA-256: 645ca6007103686b046ac24fc6aaaba1f5555d18444a349d5251bdf595607b4d. This installed path is a symlink to the shared checkout, not a separate file to edit in the B081 worktree.

The host and embedded top-level Sprint Execution SKILL.md files both document the keyless sprint-next form and direct the reader to workflows/run-sprint.md. The embedded active-sprint prompt includes the embedded skill and also invokes sprint next without a positional key. internal/sharkdata/default_data is embedded in the binary; shark admin install-shark-data materializes that bundle for project customization. B045 describes earlier content drift; the relevant run-sprint workflow files are byte-identical now, and all three contain the same command-contract mismatch. The CLI reference also incorrectly advertises a positional sprint key and positional examples.

B080 is a separate finding about treating an empty selection as a drained backlog. Correcting B081's selection scope must preserve that boundary and must not turn an empty or paused result into completion evidence.

## Decisions

1. Keep “shark sprint next” keyless; its CLI contract explicitly rejects positional arguments. For /run-sprint S###, use the existing exact-key “shark plan S### --json” selection, pass through --agent when set, consume the single entity or first ordered candidate, and confirm response.sprint_key equals S### before calling /shark-rider run. This extends existing selection behavior and does not require a new CLI argument.
2. If the workflow retains keyless sprint next instead, it must verify that the requested sprint is the only execution-phase sprint before selection and must reject a returned entity whose sprint_key differs from S### before dispatch. A per-sprint plan selection is preferred because Shark permits multiple active sprints.
3. Update the maintained workflow, embedded workflow, the two top-level Sprint Execution skills, the embedded active-sprint prompt, and docs/cli-reference/sprint-commands.md together so each consumer describes the same supported per-sprint selection contract. The user-level skill symlink follows the maintained repository tree; a project-materialized shark-data bundle follows the embedded source.
4. Leave B080's no-selection outcome rules to its separate bug. B045's historical bundle-copy issue is not evidence that these currently matching workflow files are up to date semantically.
