# B078 Research Report

## Scope

B078 concerns the `shark related-docs delete <title> --task=<key>` contract: remove the selected task's document association, or return an error when the operation fails, and report success only when the requested link is absent. The document record and file are preserved when a link is removed. This research traces the CLI through the shared entity-document service and SQLite repositories, checks the existing idempotency contract, and identifies callers that share the path.

The reported WWGM reproduction is recorded in `docs/plan/bugs/B078.md`: deleting “S010 current continuation” twice returned exit 0 with `status: unlinked`, while task T-E10-F02-013 still listed document 563. Document 542 has the same title, and document 564 is the valid project-root continuation pointer. I did not rerun commands against the WWGM database from this checkout; the local diagnosis below is based on the recorded observation and the current implementation.

## Findings

1. **The false-success response is guaranteed when a standard entity unlink returns an error.** `runRelatedDocsDelete` discards `UnlinkDocument` errors for epic, feature, task, bug, and change, then calls `printDocUnlinked`. The task branch at `related_docs.go:181-183` therefore returns success even when the task service reports an entity lookup, configuration, or database error. The question branch at lines 193-197 already propagates its service error, providing a local CLI pattern for the required behavior.

2. **The shared unlink path can also retain a link without returning an error when titles are duplicated.** `documents` permits the same title at different paths because its uniqueness constraint is `(title, file_path)` (`db.go:339-349`). `DocumentRepository.GetByTitle` selects by title alone and specifies no ordering (`document/repository.go:109-133`). `EntityDocumentService.UnlinkDocumentByKey` then unlinks only the returned document ID from the selected entity (`entity_document_service.go:130-138`). The repository delete is scoped to that exact ID and returns nil when no row matched (`entitydoc/repository.go:73-83`). Thus, if the title lookup returns another same-title record, the intended association can remain while the service and CLI both report success. This matches the duplicate IDs noted in the B078 observation, but the specific ID returned by the WWGM database was not verified here.

3. **Lookup failures are also conflated with an absent document.** The service treats every `GetByTitle` error as an idempotent no-op (`entity_document_service.go:130-134`), although the repository distinguishes “document not found” from other query errors. The CLI then suppresses any error that does escape the service. The result is a second path by which a database failure can be reported as successful deletion.

4. **Idempotency is an established behavior, but it is narrower than swallowing failures.** The command help and CLI reference say delete succeeds when the document is not linked to the parent. The service and repository also describe missing-document and missing-link cases as no-ops. These are valid no-change outcomes; an invalid parent, a repository failure, or an ambiguous title must not be converted into a success response.

5. **The underlying capability is shared across production callers.** `TaskService`, `EpicService`, `FeatureService`, `BugService`, and `ChangeCardService` delegate to `EntityDocumentService`. The generic CLI delete command ignores returned errors for all five types. The same title-only lookup affects the shared service path for those entity types. The question branch has a separate service wiring path and currently propagates errors. The impact is confined to link mutation and its success/error contract; list operations read the association and expose document IDs and paths.

6. **Existing coverage does not protect the production command boundary.** Service tests verify missing-document idempotency and that a link-repository error is returned. The CLI delete tests use a separate `createRelatedDocsDeleteCmd` helper that ignores the title and calls a mock repository with document ID `0`; they do not exercise `runRelatedDocsDelete` or assert that service errors reach the caller. A regression should cover the actual task command branch, the duplicate-title case, and error propagation while retaining the missing-link no-op.

7. **Related findings are distinct.** B072’s research concerns positional key inference for `related-docs list`; it does not address delete selection or error handling. Its existing list flow is useful because it returns the entity’s linked document records, including IDs and paths, but it does not define how delete should behave when multiple linked records share a title. B079 concerns registering research reports for tech-debt entities and is unrelated to task-link deletion.

## Decisions

1. **Extend the existing related-document capability.** Do not create a new storage model or delete the document record/file. Repair the existing unlink path so it targets the selected entity’s association and reports the operation’s real outcome.

2. **Preserve idempotency only for an absent document or association.** Distinguish a not-found result from other lookup errors, let unexpected service/repository errors reach the CLI, and return success for a no-op only after confirming the requested association is absent.

3. **Resolve deletion against the selected entity’s linked documents.** Prefer an exact linked document ID. Keep title-based deletion for an unambiguous match; if more than one document linked to that entity has the requested title, return an explicit ambiguity error or require an exact path/ID. Do not use an unordered global title lookup to choose an association.

4. **Apply consistent error propagation across supported entity types.** The task, epic, feature, bug, and change branches should return contextual errors rather than discard them. Keep the question branch’s existing propagation behavior.

5. **Add regression coverage at the production boundary.** Verify that task delete removes the intended ID when duplicate titles exist; a missing link remains idempotent; entity lookup, title lookup, and unlink failures do not print/return success; and list immediately reflects successful deletion. Cover the shared entity branches or factor their common error-handling contract so sibling types cannot drift.
