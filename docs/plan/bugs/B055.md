# Correct reverse dependency rendering in shark get

## Description

Reported from WWGM TD-242: human-readable shark get renders an incoming depends_on edge as though it were the task's outgoing dependency, making a one-way relationship appear circular. shark links and the JSON dependency data confirm the actual edge direction; dependency enforcement and dispatchability are unaffected. Reproduce with an incoming depends_on relationship and compare the Depends On and Blocks rows. Source tracker: /home/jwwel/projects/wwgm, TD-242.

## Expected Behavior

`shark get <task>` must show `Depends On` only for outgoing `depends_on`
relationships owned by that task. An incoming `depends_on` relationship belongs
only in the reverse/`Blocks` view and must not make a one-way edge appear
circular.

## Actual Behavior

The human-readable `shark get` output renders an incoming `depends_on` edge
under both `Depends On` and `Blocks`. This is silent wrong display data: the
actual relationship graph and dispatch checks remain one-directional.

## Steps to Reproduce

1. Create two tasks with a single `depends_on` relationship from task B to task A.
2. Run `shark get <task-A>` in human-readable mode.
3. Observe task B under both `Depends On` and `Blocks`, although task A has no
   outgoing dependency.
4. Compare with `shark links <task-A>` and JSON output to confirm the graph
   contains only the single incoming edge.

## Fix Notes

Reported from WWGM `TD-242`, where this made `T-E04-F02-007` look mutually
dependent with `T-E04-F04-010`. The task was actually dispatchable; no real
cycle or blocking relationship existed.
