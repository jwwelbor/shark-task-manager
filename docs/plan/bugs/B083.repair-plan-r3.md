# B083 repair plan

## Diagnosis

The E40 benchmark path preserves workflow route fields until it reaches the
provider adapter, but it does not resolve the selected harness against those
routes. On the declared review baseline, the Codex branch of
`lifecycle-worker-adapter.sh::command_for()` drops `request.model`; the
read-only `bench-working` comparison forwards `-m` but also forwards an
incompatible Claude/Sonnet model unchanged. `load_routing_profile()` and
`apply_routing_profile()` exist in `e40_benchmark.py`, but research found only
their definitions and test callers. Profile selection is not wired into the
production run path, and current route digests describe the workflow before
any profile application.

Codex route preparation needs two separate facts: which model identifiers the selected Codex CLI advertises, and whether a particular run can use the selected route. The supported app-server `model/list` RPC supplies model identifiers, display names, descriptions, and supported reasoning efforts. The installed CLI returned the models shown in the user's picker, plus additional catalog entries. OpenAI's app-server documentation cautions that `model/list` may be bundled or cached, so it proves advertised CLI compatibility, not account entitlement. Use it as a dynamic catalog, never as a hardcoded allow-list. Let an actual dispatch establish whether the selected account can use the route. Do not read an undocumented token store, call `/v1/models`, or start inference during preflight.

## Proposed repair

1. Wire the existing E40-F13 routing-profile mechanism into the production
   benchmark run as an explicit `routing_profile`, separate from the comparison
   `profile`. Preserve each explicit provider/model/effort route. For Codex
   routes only, allow model and effort to be omitted so the runtime catalog can
   supply them. Apply the same rule to explicit workflow routes when no profile
   is selected. Keep explicit pins exact and require model fields for other
   providers. Validate complete stage coverage
   before dispatch; do not infer a route from `capability_profile` or inherit a
   parent model.
2. Apply the selected profile to a run-scoped workflow copy. Never mutate the
   shared source bundle. Reject invalid profiles or a route whose provider does
   not match the selected harness. Freeze the effective provider/model/effort
   tuple before calculating route identity, then pass that same tuple to the
   manifest and adapter request.
3. Add a read-only Codex catalog preflight. Resolve the same CLI executable,
   configuration, and environment that the adapter will use. Initialize that
   CLI's supported app-server interface and read every page of `model/list`;
   exclude hidden entries. Use the returned `model` field as the exact route
   value. Never query one Codex installation and dispatch through another.
4. Resolve model and effort using these four cases:
   - Explicit model and explicit effort: require that exact model and effort in
     the catalog.
   - Explicit model and omitted effort: keep the exact model and use that
     entry's `defaultReasoningEffort`.
   - Omitted model and explicit effort: require one unique `isDefault` model
     and verify that its `supportedReasoningEfforts` includes the explicit
     effort.
   - Omitted model and omitted effort: require one unique `isDefault` model
     and use its `defaultReasoningEffort`.

   An explicit model pin that is absent from the catalog fails; it never falls
   back to the default. Missing or malformed data, an absent or ambiguous
   default when required, or an unsupported effort records a named
   `resolution: failed`, `cause_class: route_defect` result before adapter
   start. Never maintain real Codex model identifiers as constants, allowlists,
   sample Codex profiles, or test fixtures. Store the catalog source, CLI
   version and catalog digest as provenance without recording credentials or
   secret configuration.
5. Do not require a separate account-specific model query during preparation.
   `model/list` proves only that the CLI advertises the route. Once the route
   passes discovery, attempt that exact provider/model/effort tuple. If Codex
   rejects it for account, quota or service reasons, record the failure against
   that route. Do not silently substitute another model or provider.
6. Pass the effective model through the Codex CLI model option, including with
   an executable override. Reject an opaque override if it cannot preserve the
   selected route. Keep the route digest based on the effective tuple and keep
   the catalog digest as separate provenance.

Use the existing route-preview boundary for discovery and deterministic
catalog fixtures. Do not start inference, read a token store, or query an
account model endpoint during route preparation.
## Scope and preserved behavior

**Complexity M.** The repair spans benchmark configuration, profile
materialization, route preflight, identity capture, and the adapter boundary.
Implementation is limited to E40's `bench/` production path and its tests.

- Extend the existing E40-F13 profile/schema and run configuration rather than
  creating a parallel router. Preserve explicit stage `provider`, `model`, and
  `effort`; only an explicitly selected routing profile may replace them.
- Preserve `identity.provider_routing`'s provider/model/effort digests and
  comparison identity, but compute them from the effective run-scoped workflow
  after the selected profile is applied. The adapter request, manifest, and
  route evidence must identify that same effective tuple.
- Preserve source workflows, profiles, and repository files byte-for-byte
  during materialization. Preserve the current Claude and Copilot adapter
  contracts, measurement normalization, scratch-root isolation, and cost
  honesty. Do not change native Shark Rider launch behavior or claim B077 is
  fixed; B077 is a separate boundary.
- Preserve the existing parent-owned Shark claims, heartbeats, transitions,
  and releases. This repair changes E40 route preparation and adapter command
  construction only.
- Do not run a live provider or account canary as part of unit, contract, or
  route-preview tests. Use fake CLI/catalog/adapter seams. A later live
  benchmark requires its own explicit authorization and evidence.

before development. After approval, the parent supplies the committed plan path

catalog is blocked; a catalog-advertised route proceeds to the exact adapter
attempt, with access/service failures recorded against that attempted route.
## Verification design

Exercise the real route materializer in both selected-profile and explicit
workflow modes with a fake Codex app-server and recording adapter. Use
synthetic model identifiers only. The catalog fixture must paginate, place the
requested pin on page two, include a hidden-only match, and support a failed or
incomplete second-page response. Bind the app-server and adapter to the same
fake executable and effective configuration; vary the environment with the
same executable and prove a catalog from a different identity is rejected.

Cover all four model/effort presence combinations in the proposed repair. Use
two synthetic models with different default efforts so a route cannot borrow
the wrong model's default. Assert explicit pins stay exact, omitted fields use
only the documented catalog default, unsupported values fail before adapter
start, and malformed or incomplete discovery produces zero starts. Verify the
manifest records the selected model metadata, source, CLI version, and catalog
digest while excluding a synthetic secret. Check the adapter request and
manifest have the same tuple; changing only the effective model or effort
changes route identity. A simulated access denial after start must retain the
exact attempted route and must not invoke another model or provider.

Keep the preview free of account queries and inference. Run the applicable E40
routing, adapter, identity, and route-preview suites after implementation,
then the project's required quality gate. Record commands and results in the
revision 3 evidence record.
