# shark get --json blocked_by/blocks fields only show task-to-task relationships, hiding cross-entity blocks and other relationship types

## Description

task_display_data SQL view (internal/db/db.go ~line 2805) hardcodes from_entity_type='task' AND to_entity_type='task' in every blocked_by/blocks subquery, so shark get/shark task get --json only ever surfaces task-to-task depends_on/blocks relationships. It silently drops cross-entity-type relationships (e.g. a task blocking a feature) and every other relationship type (related_to, follows, spawned_from, duplicates, references, linked_to, question_blocks). shark links <key> queries the generic entity_relationships table directly with no such restriction and shows everything correctly -- shark get --json is the one that's wrong. Caused a real false-positive during UAT: checking blocks/blocked_by via shark get --json missed a genuine T-E04-F03-017 blocks E04-F04 relationship that shark links surfaced. Fix should rework the task_display_data view itself (generalize its subqueries to the entity_relationships table across entity types/relationship types) rather than changing shark get to just delegate to the shark links query path -- the view is the right place to own this so JSON output stays a single efficient query.

## Expected Behavior

`shark get <key> --json` / `shark task get <key> --json` should report every `blocks`/`blocked_by`
relationship recorded for that task in `entity_relationships`, regardless of the related entity's
type (task, feature, epic, bug, change, tech-debt, question) or relationship type, so it is a
reliable source of truth for automated checks (UAT, gates, agents).

## Actual Behavior

`shark get`/`shark task get --json` only reports `blocked_by`/`blocks` entries where both sides of
the relationship are type `task` and the relationship type is `depends_on`/`blocks`. Any
cross-entity-type relationship (e.g. a task `blocks` a feature) or any other relationship type
(`related_to`, `follows`, `spawned_from`, `duplicates`, `references`, `linked_to`,
`question_blocks`) is silently omitted, even though it exists in `entity_relationships` and is
correctly shown by `shark links <key>`.

## Steps to Reproduce

1. Create a task-to-feature `blocks` relationship: `shark link <task-key> <feature-key> --type=blocks`.
2. `shark links <task-key>` shows the relationship.
3. `shark get <task-key> --json` (or `shark task get <task-key> --json`) — the relationship is
   absent from `blocked_by`/`blocks`.

Real-world instance: `T-E04-F03-017 blocks E04-F04` existed and was visible via `shark links`, but
absent from `shark get T-E04-F03-017 --json`'s `blocks` field, causing a UAT check that relied on
`shark get --json` to false-positive as "no blocking relationship".

## Fix Notes

Fix belongs in the view, not the command: generalize the `blocked_by_json`/`blocks_json`
subqueries in `taskDisplayDataViewSQL` (`internal/db/db.go`, ~line 2805) to query
`entity_relationships` across entity types and relationship types, instead of delegating
`shark get` to the same query path `shark links` uses. Keep the single-query-view design intent
(`task_display_data` exists specifically to avoid the N+1 round-trips a separate relationship
lookup would add, per the view's own comment about Turso round-trip cost). Needs a JSON shape
decision for cross-entity entries (currently `task_key`/`task_title`/`task_status` assume a task on
the other end) and test coverage for cross-entity and non-blocks/depends_on relationship types.
