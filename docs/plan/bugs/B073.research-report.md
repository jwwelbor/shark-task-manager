# B073 research report

## Scope

B073 covers the relationship-type contract exposed by the generic `shark link`
command and the documentation that explains how to express a blocker. The
reported invocation is `shark link T-E10-F02-005 B073 --type=blocked_by`.

The scope includes the generic link allowlist and help text, the relationship
model and service semantics, the task-facing blocked-by projection, and the
maintained CLI/Rider guidance. It does not include a new relationship storage
type or a change to workflow status behavior.

Shared vocabulary:

- **`depends_on`**: a directed relationship from the blocked/dependent entity
  to the prerequisite entity.
- **`blocks`**: a directed relationship from the blocker to the entity it
  prevents from proceeding.
- **`blocked_by`**: a derived display/query label for entities this entity
  depends on; it is not an accepted relationship type for `shark link`.
- **Relationship type**: one of the values in the model's explicit allowlist.

## Findings

1. The reported failure reproduces in the current executable. `./bin/shark
   link T-E10-F02-005 B073 --type=blocked_by` exits with `invalid relationship
   type "blocked_by"` and prints the valid allowlist. The rejection occurs
   before entity resolution or persistence. The same directional scenario is
   accepted when expressed as `depends_on` with the dependent first; the
   probe-created edge was removed after verification.

2. `blocked_by` is intentionally absent from the relationship model's valid
   type set. The generic link command validates `--type` against
   `models.ValidEntityRelationshipTypeSet`, whose dependency values are
   `depends_on` and `blocks`. The service also treats those two values as the
   cyclic dependency types, so accepting `blocked_by` would require deciding
   whether it is an alias or a third persisted semantic.

3. The existing read-side contract explains the source of the confusion. The
   entity relationship service implements `GetTaskBlockedBy` by reading
   outgoing `depends_on` edges, while `GetTaskBlocks` reads incoming
   `depends_on` plus outgoing `blocks`. The JSON reference likewise defines
   `blocked_by` as entities the task `depends_on` and `blocks` as entities
   blocked by the task. Therefore `blocked_by` is a view label, not a valid
   write-side relationship type.

4. The established authoring pattern already gives the intended direction:
   Rider entity guidance shows `shark link <consumer> <producer>
   --type=depends_on`, and the breakdown workflow describes `depends_on` as a
   hard completion barrier. The task command reference separately defines
   `depends_on` as “task depends on another completing” and `blocks` as “task
   blocks another from proceeding.” These sources support clarification rather
   than a new relationship type.

5. Documentation is not fully uniform. The generic command help and model use
   underscore forms, while `docs/WORKFLOW_GUIDE.md:1148` still shows older
   hyphenated/relational aliases (`depends-on`, `relates-to`) that are not the
   current generic `--type` allowlist. This is a directly related source of
   syntax ambiguity and should be reconciled in the repair's documentation
   sweep.

6. A related shipped fix establishes the needed distinction between persisted
   relationship types and display projections. B049 expanded cross-entity
   `blocked_by`/`blocks` JSON output while explicitly keeping non-blocking types
   out of those projections. That pattern supports preserving `blocked_by` as
   read-side vocabulary while making the write-side direction explicit.

## Decisions

1. **Keep `blocked_by` rejected as a write-side type.** Do not add it to the
   persisted relationship allowlist unless a separate product decision defines
   alias normalization and migration semantics. The current fail-closed
   validation prevents a guessed type from being stored with unclear meaning.

2. **Make the directional mapping explicit at the error and documentation
   boundaries.** For “A is blocked by B,” use `shark link A B
   --type=depends_on`. Equivalently, use `shark link B A --type=blocks` when
   expressing the inverse direction. Explain that `blocked_by` is the read
   label returned by task/entity views, not a `--type` value.

3. **Align maintained syntax examples.** Update the stale workflow guidance
   to the current underscore spellings and ensure generic help, task help,
   Rider guidance, and JSON documentation use the same directional wording.
   Add focused regression coverage for the rejected `blocked_by` input and the
   documented `depends_on`/`blocks` mapping.

4. **Classify the repair as an extension of an existing capability.** The
   relationship model, validation, service projections, and CLI are already
   present. The work extends their user-facing contract and documentation; it
   does not create a new relationship type, persistence path, or workflow
   capability.
