# B065 Research Report — Tier-aware UAT QA evidence

## Scope

B065 concerns the feature-level UAT approval prompt's evidence requirement.
`internal/sharkdata/default_data/skills/quality/context/tier-matrix.md` is the
canonical tier contract; this report records only B065's prompt-specific
conclusion.

The historical report describes a STANDARD E40-F11 UAT rejection for a missing
QA report. Its named review artifacts are not present in this checkout, so the
historical rejection is retained as the bug-report evidence; the current
rendering contract is reproducible locally.

## Findings

1. The directly affected capability is the rendered `feature/approval.md` UAT
   prompt. Its QA-report read instruction is now conditional on
   `complexity_tier == "COMPLEX"`; SIMPLE and STANDARD renders omit that
   requirement. `TestRender_ApprovalPromptReadsQAReportOnlyForComplexFeatures`
   exercises all three tiers and passed locally with `go test ./internal/templates
   -run 'TestRender_ApprovalPromptReadsQAReportOnlyForComplexFeatures' -count=1 -v`.

2. Executable routing agrees with that rendering: `feature.yaml` reaches `qa`
   only through `code_review`'s `deep_verify` outcome, and `feature/code_review.md`
   assigns the merged verification work for SIMPLE/STANDARD. The approval
   step's universal `QA passed` label is imprecise for those tiers, but does not
   alter routing or the approval prompt's tier-conditional evidence requirement.

3. The pre-development test-planning prompt and its included workflow use
   “QA phase” for verification activities. For SIMPLE/STANDARD that term is
   ambiguous because verification is merged into code review; it does not
   require a feature-scoped `qa-*.md` artifact or prescribe a QA-before-UAT
   sequence for every tier. This report does not expand B065's prompt-repair
   scope to alter that adjacent workflow wording.

4. Git history identifies commit `740a38ee` as the repair: it changed the
   formerly unconditional approval-template QA line to the COMPLEX conditional
   and added the three-tier renderer regression test. The working tree is
   therefore already repaired; B065 is a historical workflow-contract defect,
   not an unimplemented capability.

## Decisions

1. Treat B065's repair as an extension of the existing template and
   complexity-tier contract, not new workflow work. Do not add a QA gate or
   synthesize QA reports for SIMPLE/STANDARD features.
2. Retain the conditional in `feature/approval.md` and the existing renderer
   regression test as the structural guard. Refer to the tier matrix rather
   than restating its policy when later edits affect tier routing or approval
   evidence.
3. The research result is **pass**: the current implementation matches the
   expected behavior and the historical defect's precise repair is present.
