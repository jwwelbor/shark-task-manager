# shark search short-circuits tag validation when full-text query yields zero results

## Description

`SearchService.SearchAll` (internal/services/search_service.go:42) validates `--tag` names lazily — only by calling `tagSvc.EntityIDsByTags` per entity-type bucket built from the FTS result set. When the FTS query returns zero rows, the `byType` map is empty, the per-bucket loop never executes, and `EntityIDsByTags` is never called. The unregistered-tag error path (AC-19, returns `*UnregisteredTagError`) is therefore skipped.

This makes `shark search` behave inconsistently:

- `shark search "matches-something" --tag bogus` → returns `*UnregisteredTagError` (exit code mapped to "unregistered tag").
- `shark search "matches-nothing" --tag bogus` → returns empty result set, exit 0.

Same invalid tag name, two different outcomes, depending solely on whether the FTS query happens to match anything. A user who fat-fingers a tag name will silently get no results instead of a "tag does not exist" error.

## Expected Behavior

Tag-name validation should be eager (independent of FTS hit count). When `len(tags) > 0`, each tag name should be validated against the registered vocabulary before — or independently of — the FTS results scan. An unregistered tag must always produce `*UnregisteredTagError`, regardless of whether the FTS query returned any rows.

## Actual Behavior

When the FTS query returns zero rows, the validation loop is skipped, and unregistered tag names are silently accepted. The CLI returns an empty result set with exit 0 instead of the "unregistered tag" error.

## Steps to Reproduce

1. Initialize a shark project with at least one registered tag (e.g. `shark tags add backend`).
2. Run a search whose FTS query matches at least one entity, with a bogus tag:
   ```bash
   shark search "shark" --tag bogus-not-registered
   ```
   Expected: `*UnregisteredTagError` is returned (per AC-19), CLI prints an "unregistered tag" error.
3. Run the same search with an FTS query that matches **no** entities:
   ```bash
   shark search "qwertyuiop-no-such-string-anywhere" --tag bogus-not-registered
   ```
   Observed: empty result set, exit 0 — no error.
4. Compare the two outcomes. The validation contract is inconsistent: the same invalid input gives an error or silent success depending only on the FTS hit count.

## Fix Notes

Two viable approaches in `internal/services/search_service.go`:

1. **Validate tag names up front (preferred).** Before bucketing results, iterate `tags` and resolve each via the tag service (`tagSvc.GetByName` / `tagSvc.ResolveAll` if available, or a single batched call). Return `*UnregisteredTagError` immediately on the first unknown name. This mirrors how `BugService` / `ChangeCardService` validate tags via `EntityIDsByTags` in their list paths.
2. **Force at least one `EntityIDsByTags` call when `len(tags) > 0` and `len(results) == 0`.** Pick a sentinel entity type (e.g. the first non-empty bucket, or `models.EntityTypeTask` as a default) and run validation through that. Slightly less explicit but minimally invasive.

Either way, add regression tests next to the existing AC-19 test in `internal/services/search_service_test.go`:

- `TestSearchService_SearchAll_UnregisteredTag_WithEmptyFTS` — FTS returns `[]`, `tags=["bogus"]`, expect `*UnregisteredTagError`.
- Confirm the existing AC-19 test still passes (FTS returns rows + unknown tag).
- Confirm AC-T3 (tagSvc nil) still triggers `*TagFilterUnavailableError` regardless of FTS hit count.

Quality gate: `make fmt && make lint && make test`.
