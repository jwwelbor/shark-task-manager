## Scope

B055 is limited to the human-readable task detail rendered by `shark get
<task>`. A directed `depends_on` relationship means its source task depends on
its target task. For a displayed task, the `Depends On` row must contain only
outgoing `depends_on` edges. An incoming `depends_on` edge is a reverse
relationship and belongs in `Blocks`, which lists work waiting on the displayed
task.

The bug is display-only. The relationship record, `shark links`, JSON
relationship fields, cycle detection, and dispatch/dependency enforcement are
out of scope because the report and existing edge contract show that they retain
the directed edge correctly.

## Findings

1. Reproduction is deterministic from the view definition. For a single edge
   `B --depends_on--> A`, the `dependencies_json` subquery in
   `internal/db/db.go` joins task `A` when it appears on either the `from` or
   `to` side of `entity_relationships`. `GetTaskDisplayData` unmarshals that
   array into `TaskDisplayData.Dependencies`, and `buildTaskBasicInfo` renders
   every member as `Depends On`. Therefore `shark get A` renders `B` under
   `Depends On` despite `A` having no outgoing dependency.

2. The same view already computes the correct reverse projection. Its
   `blocks_json` includes incoming `depends_on` edges, and the human renderer
   prints those rows as `Blocks`. This is why the same task can appear in both
   rows and look circular.

3. The existing service contract agrees with the requested behavior:
   `GetTaskBlockedBy` selects outgoing `depends_on` edges, while
   `GetTaskBlocks` selects incoming `depends_on` plus outgoing `blocks` edges.
   The plan-edge regression test preserves the same distinction for scheduling
   output. B055 must align the task-detail dependency projection with that
   established contract.

4. B049 is related prior work. It generalized task-detail relationship
   aggregation across entity types without changing the `blocked_by`/`blocks`
   meanings, and it added a real-database regression test around the display
   view. Its migration path is the appropriate pattern for this bug.

## Decisions

1. Repair the existing `task_display_data` view rather than adding a second
   command-layer filter. The view is the source for both human and JSON
   task-detail data, so correcting the projection there prevents the two
   formats from diverging and preserves the single-query design.

2. Change only `dependencies_json` so it selects outgoing task-to-task
   `depends_on` relationships. Do not alter `blocks_json`, which intentionally
   exposes incoming `depends_on`, or the all-relationship JSON surface.

3. Add a real-database regression test using one `B --depends_on--> A` edge.
   Assert that task A's display data has an empty `Dependencies` list, contains
   B once in `Blocks`, and does not add B to the human `Depends On` rows. Keep a
   companion assertion that an outgoing dependency still appears under
   `Depends On`.

This repair extends the existing task-detail capability; it does not create a
new relationship type, dependency rule, command, or workflow behavior.
