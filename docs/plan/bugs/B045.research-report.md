# B045 Research Report: Embedded Shark Sprint Skills Stale Content Sync

## Scope

Bug B045 tracks embedded Shark sprint skill divergence from the maintained rider implementations. The bug's original description (2026-07-09) compared `internal/sharkdata/default_data/skills/sprint-{planning,execution,analytics}` against `skills/shark/skills/` (now renamed `skills/shark-rider/skills/`), reporting stale command forms, missing guidance sections, and an incorrect buffer calculation formula.

**Scope resolution:**
- There is no `skills/shark/skills/` directory in the current repo. The git history shows a directory rename from `skills/shark/` to `skills/shark-rider/` in a recent refactor.
- The actual comparison is between:
  - **Embedded canonical** (source of truth per project memory): `internal/sharkdata/default_data/skills/sprint-{planning,execution,analytics}`
  - **Maintained implementation** (rider host-side): `skills/shark-rider/skills/sprint-{planning,execution,analytics}`
- Per project rules (feedback_embedded_sharkdata_canonical.md), the embedded bundle IS the canonical source for redistribution; `skills/shark-rider/` is the maintained/tested implementation that feeds corrections back INTO the embedded bundle.

### Critical Finding: Pre-Condition Guard for Division by Zero

**Embedded version (current):**
```markdown
**Rule 3 — High carryover rate** (signal: high if carryover > 30% of planned):
- **Condition**: `SUMMARY.carryover_count / SUMMARY.planned_count > 0.30`
```

**Rider version (correct):**
```markdown
**Rule 3 — High carryover rate** (signal: high if carryover > 30% of planned):
- **Pre-condition guard**: if `SUMMARY.planned_count == 0`, skip Rule 3 entirely (no planned entities → carryover rate undefined).
- **Condition**: `SUMMARY.carryover_count / SUMMARY.planned_count > 0.30`
```

If a sprint has zero planned entities, the embedded workflow would attempt division by zero. The rider version guards against this. This is a safety regression.

### Formula Status (Partially Fixed)

The bug's original claim about buffer_pct computing from "inverse completion rate" was accurate at the time of filing (2026-07-09). Commit a411eef8 (2026-07-17) fixed this in the embedded version to use the correct formula:

**Old (wrong, pre-2026-07-17):**
```
buffer_pct = (1 - completed_count/planned_count) * 100
```

**Current (correct, since 2026-07-17):**
```
buffer_pct = carryover_count / planned_count * 100
```

The formula is now correct in the embedded version, but the pre-condition guard to prevent division by zero was never added.

## Decisions

### 1. Sync Direction is Unambiguous

The fix is to sync **FROM** `skills/shark-rider/skills/sprint-*` **INTO** `internal/sharkdata/default_data/skills/sprint-*`, not the reverse.

**Rationale:**
- Project memory (feedback_embedded_sharkdata_canonical.md) establishes embedded as canonical for distribution, but rider as actively maintained.
- Bug description (lines 21–22) explicitly frames the embedded bundle as having "drifted" and calls for repair of "the embedded source," not deletion of rider content.
- Rider version is more recent, more complete (344 vs. 215 lines for plan-sprint), and includes safety improvements.
- Rebuild of the Go binary is the distribution mechanism; syncing rider into embedded ensures all downstream deployments receive the corrected content.

### 2. Scope of Required Sync

Full content sync is necessary, not incremental fixes, because:

1. **Safety**: The division-by-zero guard in retro-sprint is a runtime safety issue, not optional.
2. **Command stability**: Stale slash-command forms will break user workflows; they must be normalized across all three skills.
3. **Feature completeness**: The tech-debt landmine step in plan-sprint represents owner-ratified guidance that should not be withheld from new deployments.

### 3. Verification After Sync

After syncing, verify:
- Embedded and rider workflows are byte-identical (or differ only by comments/metadata that should be documented).
- A rebuild of the Go binary correctly embeds the new content.
- An automated test validates that embedded skills do not contain bare `/shark-rider` command forms (existing bundle validator test can be extended).

## Pattern Contract

**Embedded Bundle as Distribution Snapshot:**
The pattern established in prior refactors (E32 "Single-Artifact Consolidation") is that `internal/sharkdata/default_data/` is a compile-time snapshot of "content that ships in the binary." Once the Go binary is built, that content is immutable until the next rebuild. The `shark-data/` deployed to user projects is extracted from that snapshot and may be overridden locally.

**Rider as Active Maintenance:**
`skills/shark-rider/` is the active development tree where features are added, bugs are fixed, and guidance is iterated. It is tested, versioned, and used by the Rider orchestration layer. Commits to rider represent validated changes.

**Sync Pattern:**
When rider is updated with safety fixes or new features, the sync INTO embedded is manual (as opposed to automated). This is deliberate: it allows for controlled release cycles and lets teams choose when to rebuild and redeploy the binary. The sync is not one-way; rider can receive feedback from embedded users and iterate, but the canonical distribution always flows from rider into embedded.

## Dependency Impact

**Direct code impact:** None. This is purely content/skill procedural guidance, not Go code or database schema.

**User-facing impact:**
- Fresh deployments via `shark admin install-shark-data` will extract the embedded bundle to disk. If the embedded content is stale, users receive stale guidance.
- Users following embedded skill files (e.g., someone reads `docs/plan/skills/sprint-planning/SKILL.md` after extraction) will follow outdated procedures.
- Users accessing rider skills via symlinks (e.g., `~/.claude/skills/shark-rider → repo copy`) get the correct version but project-local deployments do not.

**Operational impact:**
- Sprints using embedded procedures that reference deleted slash-commands will fail with command-not-found errors.
- Retro workflows with zero-entity sprints will encounter division-by-zero errors (rare but critical when it happens).

## Cross-Boundary Risks

1. **Partial Fix Confusion:** The buffer_pct formula was already fixed in commit a411eef8, which means casual inspection of the current embedded file will show the correct formula. This could lead to the false conclusion that "the bug is already fixed." The division-by-zero guard is the outstanding issue that was never back-ported.

2. **Directory Rename Fallout:** Memory and documentation may still reference `skills/shark/skills/` (old path). Any automated tooling that assumes that path will fail silently. Cross-check references in .claude/rules, CLAUDE.md, and git-hook validation scripts.

3. **Stale Symlink Assumptions:** The project's skill symlink pattern relies on `skills/shark-rider/` being the source. If someone manually edited the embedded tree as if it were the source of truth, a later sync would overwrite those edits. This is unlikely but possible if guidance was unclear.

## Alternatives

1. **No-sync / Accept Divergence**: Declare embedded and rider as independent trees and stop syncing. **Not recommended** — violates the established pattern and abandons the distribution guarantee.

2. **Selective Sync (Safety Only)**: Copy only the critical fixes:
   - Add the `planned_count == 0` guard to retro-sprint Rule 3.
   - Replace all `/shark-rider query: *` command forms with their plain equivalents.
   - Do NOT add the new Step 1.5 tech-debt landmine section or other enhancements.
   
   **Pros:** Addresses immediate safety and command stability issues. **Cons:** Users do not receive updated guidance for best practices (tech-debt landmine checking); leaves the project in a partially-fixed state.

3. **Full Sync (Recommended)**: Copy the entire rider skill tree into the embedded bundle and rebuild the Go binary.
   
   **Pros:** Restores complete canonical distribution integrity, delivers all updates in one operation, aligns with project distribution pattern. **Cons:** Requires Go binary rebuild and re-release; larger changeset to validate.
