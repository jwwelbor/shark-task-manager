# Hierarchy endpoint embeds full task data violating lazy-load spec

## Description

`GET /api/v1/viewer/hierarchy` loads all tasks with full 27-column data plus pre-resolved relationships JSON via the `viewer_task_relationships` view, then embeds them as `HierarchyFeature.Tasks []*ViewerTask` in the response payload.

The E27-F02 spec explicitly requires tasks to **not** be in the hierarchy payload — only `task_count` and `blocked_count` per feature — with task details lazy-loaded via `GET /api/v1/viewer/features/{key}/tasks` when a feature is expanded.

The frontend (`internal/viewer/assets/viewer.html`) was built against the broken implementation and reads `feature.tasks` in approximately 15 places: rollup sections, search, donut charts, work breakdown, action items, etc. The lazy endpoint (`/features/{key}/tasks`) is wired up but only used for post-mutation refreshes, not initial load.

Both layers must change together — this is not a safe backend-only fix.

## Expected Behavior

- `GET /api/v1/viewer/hierarchy` returns epics → features with `task_count` and `blocked_count` per feature only. `HierarchyFeature.Tasks` is absent from the response.
- The frontend fetches task details lazily via `GET /api/v1/viewer/features/{key}/tasks` when a feature is clicked or expanded.
- Initial dashboard load time is significantly reduced (no bulk task fetch on page open).

## Actual Behavior

- `GET /api/v1/viewer/hierarchy` fetches every task row (27 columns + relationships JSON) in a single bulk query and serialises all of them into the response under each feature.
- The frontend reads `feature.tasks` directly from the hierarchy payload everywhere — lazy loading never happens on initial load.
- For large projects the hierarchy response is megabytes of task data the page doesn't need until a feature is opened.

## Steps to Reproduce

1. Run `shark web` and open the dashboard.
2. In browser DevTools → Network, inspect the `GET /api/v1/viewer/hierarchy` response.
3. Observe that every feature contains a `tasks` array with full task objects, not just counts.
4. Compare with the E27-F02 spec (`docs/plan/E27-.../E27-F02-.../spec.md` REQ-F-002) which states tasks are not included and are fetched lazily.

## Affected Files

- `internal/services/viewer_service.go` — `Hierarchy()` method (loads all tasks, builds `viewerTasks` slice, sets `he.Features[i].Tasks`)
- `internal/services/viewer_service.go` — `HierarchyFeature` struct (`Tasks []*ViewerTask \`json:"tasks"\``)
- `internal/viewer/assets/viewer.html` — reads `feature.tasks` in ~15 locations instead of calling `/features/{key}/tasks`

## Fix Notes

Two coordinated changes required:

**Backend:**
1. Remove `Tasks []*ViewerTask` field from `HierarchyFeature` (or omit from JSON with `json:"-"`).
2. Remove `ListWithViewerRelationships` call from `Hierarchy()` — `task_count` and `blocked_count` can be derived from a single `SELECT feature_id, COUNT(*), COUNT(blocked_reason) FROM tasks GROUP BY feature_id` query instead of loading full objects.

**Frontend:**
1. Replace all `feature.tasks` reads with a lazy fetch to `/api/v1/viewer/features/{key}/tasks`.
2. Trigger the fetch on feature expand/click; show a loading state while in flight.
3. Cache the result on the feature object so repeated opens don't re-fetch.

The `/features/{key}/tasks` endpoint already exists and returns the correct shape — the frontend plumbing just needs to use it for initial load rather than only for refresh.
