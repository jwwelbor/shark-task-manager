# Transaction boundaries are inconsistent in migrations, task creation, and force-complete

## Description

Full code review on 2026-07-07 found legacy FK repair migrations issue PRAGMA foreign_keys OFF after Begin, task creation calls GenerateTaskKey before opening a transaction, and epic feature force-complete loops updates without a transaction. These paths can fail on orphaned legacy rows, collide under concurrent creates, or leave partially completed hierarchies. See dev-artifacts/2026-07-07-full-code-review/code-review-report.md sections M2, M6, and M10.

## Expected Behavior

Migration repair paths, task-key allocation, and force-complete flows should each
execute inside coherent transaction boundaries so they either succeed atomically or
fail without partial side effects.

## Actual Behavior

The FK-repair migrations disable foreign keys after `Begin`, which SQLite ignores.
Task creation allocates keys before opening a transaction, and epic or feature
force-complete updates children one by one without rollback protection. During
triage intake on 2026-07-07, parallel `shark create bug` calls also collided on
`bugs.key` with a `UNIQUE constraint failed` error, which is evidence of the same
key-allocation defect class outside task creation.

## Steps to Reproduce

1. Run the FK-repair migrations on a legacy database with orphaned rows.
2. Create concurrent tasks under the same feature and observe key collision risk.
3. Inject a mid-loop failure during force-complete and inspect the partially
   completed hierarchy.
