# B062 research report: Question resolution discovery

## Scope

B062 concerns the recovery path for a caller that has a Question key but does
not know its configured resolution owner. The repair must make the required
`--resolution-owner` discoverable without exposing the narrative-only fields
protected by the full Question read. It also covers whether the documented
resolution-kind and prerequisite workflow gaps remain in the current checkout.

## Findings

1. The original report accurately identifies the persisted source of truth:
   `QuestionState.ResolutionOwner` is configured once and
   `loadClosableQuestion` rejects any other owner. Its error is still only
   `resolution owner does not match configured owner`, so a caller holding
   only the Question key cannot correct the required value from that failure.

2. The other reported discovery gaps have already been repaired by
   `af347262` (PR #228). `shark question resolve --help` now states the
   claim-to-response-to-resolution sequence, uses `--resolution-owner` as the
   canonical flag while preserving `--owner`, and lists all six resolution
   kinds with their pointer formats. The focused CLI regression test locks in
   those help contents.

3. `question full` intentionally remains unavailable to any actor other than
   the current responder or configured resolution owner. Its full projection
   includes responder identities, response summaries, evidence pointers, and
   resolution provenance, so loosening that authorization would exceed B062's
   metadata-discovery need.

4. `question blocking-for <entity-key>` currently emits a block's resolution
   owner without an actor argument, but it requires the caller to already know
   a linked non-Question entity. It cannot recover the owner from a standalone
   Question key and is therefore not a complete B062 recovery path.

5. TD-158 records the broader, still-open option of a credential-independent
   workflow-state read. That is related work, but it needs a separate
   disclosure-policy decision and is not required to fix the narrow opaque
   mismatch in B062.

## Decisions

1. B062 is an extension of the existing Question workflow contract, not a new
   Question capability. Keep `ReadQuestionFull` and its authorization policy
   unchanged.

2. Prefer the smallest repair allowed by B062's expected behavior: when
   `loadClosableQuestion` rejects a supplied owner, return an actionable
   error that names the configured `--resolution-owner` value and directs the
   caller to retry with it. Add a service regression test for that exact
   diagnostic; retain the existing CLI help regression test for the static
   workflow and resolution-kind guidance.

3. Do not add a general workflow-state read in this bug. Keep that larger
   metadata-disclosure design under TD-158, where its authorization and field
   policy can be decided explicitly.
