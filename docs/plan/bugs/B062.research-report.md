# B062 research report: Question resolution discovery

## Scope

B062 concerns the recovery path for a caller that has a Question key but does
not know its configured resolution owner. It must reveal the retry value
without exposing the narrative-only fields protected by the full Question
read. This research also verifies the already-landed resolution-kind and
prerequisite-workflow guidance.

## Findings

1. The persisted source of truth remains `QuestionState.ResolutionOwner`, set
   by workflow configuration and checked by `loadClosableQuestion`. The
   parent of the current B062 commit reproduced the reported opaque error.
   Current `0b36e9f3` instead returns
   `retry with --resolution-owner=<configured-owner>`. The executable
   `TestQuestionServiceResolveOwnerMismatchNamesConfiguredOwner` reproduces
   that mismatch path, asserts the retry value, and confirms that no write
   occurs.

2. The other discovery gaps were repaired by `af347262` (PR #228). Current
   `shark question resolve --help` states the claim-to-response-to-resolution
   sequence, uses `--resolution-owner` as the canonical flag while preserving
   `--owner`, and lists all six resolution kinds with their pointer formats.
   `TestQuestionResolveHelpDocumentsWorkflowAndResolutionKinds` locks in
   those help contents.

3. `question full` intentionally remains unavailable to any actor other than
   the current responder or configured resolution owner. Its full projection
   includes responder identities, response summaries, evidence pointers, and
   resolution provenance, so loosening that authorization would exceed B062's
   metadata-discovery need.

4. `question blocking-for <entity-key>` currently emits a block's resolution
   owner without an actor argument, but it requires the caller to already know
   a linked non-Question entity. It cannot recover the owner from a standalone
   Question key and is therefore not a complete B062 recovery path.

5. TD-158 records the broader, still-open option of a credential-independent
   workflow-state read. That is related work, but it needs a separate
   disclosure-policy decision and is not required to fix the narrow opaque
   mismatch in B062.

## Decisions

1. B062 extends the existing Question workflow contract; it does not create a
   new capability. The current owner-mismatch diagnostic satisfies the narrow
   repair. Keep `ReadQuestionFull` and its authorization policy unchanged.

2. Retain the service regression test for the actionable diagnostic and the
   CLI regression test for static workflow and resolution-kind guidance.
   No further B062 implementation work is indicated by the current checkout.

3. Do not add a general workflow-state read in this bug. Keep that larger
   metadata-disclosure design under TD-158, where its authorization and field
   policy can be decided explicitly.
