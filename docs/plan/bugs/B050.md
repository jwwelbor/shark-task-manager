# task update --depends-on flag is registered but unwired (silent no-op)

## Description

Discovered during E38-F09 task_generation pass 8: `shark task update <key> --depends-on ...` on the entity-first path registers the depends-on flag but parseTaskUpdates (internal/cli/commands/task_helpers.go:274-314) never reads it, so the command reports SUCCESS while silently not updating the legacy tasks.depends_on column. `shark task link --depends-on` is the only working surface for post-creation dependency changes. Dispatch gating is unaffected (GetTaskDependencies and readiness checks union the legacy column with entity_relationships, internal/repository/task/dependency.go:179-229, :571-613), but `shark get <task> --json` echoes the stale legacy depends_on snapshot, and the SUCCESS-but-no-op behavior is a latent trap. Fix: wire the flag in parseTaskUpdates or remove it from the entity-first surface (and per feedback rule, keep verb-first `shark update` parity in mind).

## Expected Behavior

`shark task update <key> --depends-on <keys>` updates the task's dependency set (or the flag is removed from the entity-first surface so the command rejects it).

## Actual Behavior

The command reports SUCCESS but `parseTaskUpdates` never reads the `depends-on` flag, so nothing is written. `shark get <task> --json` continues to echo the stale legacy `depends_on` snapshot.

## Steps to Reproduce

1. Pick a task with an empty dependency list.
2. Run `shark task update <key> --depends-on <other-task-key>` — observe SUCCESS output.
3. Run `shark get <key> --json` and `shark task deps <key>` — the dependency was not added.
4. Contrast with `shark task link <key> --depends-on <other-task-key>`, which works.

## Fix Notes

**Status: RESOLVED (Commit bfd879d1)**

This bug has been fully fixed. The three wiring sites are all connected and operational:

1. **CLI Layer** (`internal/cli/commands/task_helpers.go` lines 314-319): `parseTaskUpdates` calls `parseDependsOnUpdateFlag()`, which implements the three-way dispatch (absent=no-op, empty=clear, present=set).

2. **Service Input** (`internal/services/task_dto.go` lines 64-70): `TaskUpdates` struct has `DependsOn` and `ClearDependsOn` fields.

3. **Service Application** (`internal/services/task_service.go` lines 597-605): `UpdateTask` correctly applies both fields to the task model.

**Test Coverage**: 14 CLI tests + 4 service tests, all passing. See `B050.research-report.md` for full analysis.

**Recommendation**: Close as RESOLVED. No code changes needed.
