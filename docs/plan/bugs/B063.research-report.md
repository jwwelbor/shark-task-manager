# B063 Research Report: Custom --key Flag on Feature/Task Create

## Scope

Bug B063 impacts the CLI and service layer for custom key assignment across multiple entity types:

- **Feature create**: CLI flag `--key` exists but is never read; feature always gets auto-generated key
- **Task create**: CLI flag `--key` exists in flag registration but is never read; task creator service support exists but is unreachable
- **Epic create**: Already works correctly (pattern to follow)
- **Duplicate-key errors**: All three entity types need improved error messages with suggested next-available key

The bug affects user experience in custom key workflows and error recovery. No out-of-scope impact on bug/change-card/tech-debt/idea entities (confirmed via grep across `internal/cli/commands/`).

## Findings

### 1. Feature Create: Flag Exists But Unused

**Location:** `internal/cli/commands/feature.go:180`, `internal/cli/commands/feature_helpers.go:970-981`

**Finding:** The `--key` flag is registered but never read. The `parseCreateFeatureInput()` helper builds a `CreateFeatureInput` struct without populating a CustomKey field (line 970-981 shows construction but no key assignment).

**Impact:** Users can supply `--key=F99` with no error, but the feature is created with the next auto-generated key instead.

### 2. Feature Service: No Custom-Key Code Path

**Location:** `internal/services/epic_dto.go:66`, `internal/services/feature_service.go:1127`

**Finding:** `CreateFeatureInput` struct (line 66-95) lacks a `CustomKey` field (contrast with `CreateEpicInput` line 20 which has it). The service always calls `s.nextFeatureKey(...)` with no conditional branch for custom keys.

**Impact:** Even if the CLI flag were read and passed to the DTO, the service would ignore it.

### 3. Task Create: Flag Registered But Unused

**Location:** `internal/cli/commands/task_helpers.go:404`, `internal/cli/commands/task_helpers.go:266-271`

**Finding:** The `--key` flag IS registered on line 404 (`cmd.Flags().String("key", "", "Custom task key")`), but `parseCreateTaskInput()` (lines 213-272) never reads it. The returned struct (lines 266-271) omits CustomKey entirely.

**Impact:** Users typing `shark task create E07 F01 "Task" --key=E07-F01-099` get `unknown flag` error? No—the flag is silently accepted and ignored.

### 4. Task Service: Infrastructure Exists But Unreachable

**Location:** `internal/taskcreation/creator.go:97`, `internal/taskcreation/creator.go:140-146`

**Finding:** The `taskcreation.Creator.CreateTaskInput` struct has a `CustomKey` field (line 97) and the creator has a branch to use it (lines 140-146: `if input.CustomKey != ""` with uniqueness check). This plumbing is production-ready but is never wired from the CLI.

**Impact:** The service layer is capable; the CLI simply doesn't expose it.

### 5. Duplicate-Key Error Messages Lack Suggestions

**Location:** `internal/services/epic_service.go:513-520`, `internal/services/epic_service.go:527`

**Finding:** Duplicate-key detection exists (e.g., `if err == nil && existing != nil { return nil, fmt.Errorf("epic with key '%s' already exists", epicKey) }`), but the error does not suggest the next available key. Users must re-run manually to discover the next available key.

**Impact:** User must retry with trial-and-error after a duplicate-key failure.

### 6. Pattern Contrast: Epic Implementation Is Complete

**Location:** `internal/services/epic_service.go:513-524`, `internal/cli/commands/epic.go:180` (not shown but implied)

**Finding:** Epic create correctly:
1. Registers `--key` flag (line 180 context)
2. Reads the flag in CLI parsing
3. Passes `CustomKey` in `CreateEpicInput` (line 20 in epic_dto.go)
4. Checks uniqueness and validates in `EpicService.CreateEpic` (lines 513-520)

This is the established pattern to extend feature and task.

### 7. Dependency Chain: All Three Layers Involved

**Finding:** The issue spans three tightly coupled layers with misaligned type contracts:

## Decisions

### Extension vs. New Work

**Decision: EXTEND**

This is brownfield repair of existing, incomplete infrastructure. All three entity types share the same CLI pattern (flag exists); epic is complete; feature and task need plumbing completed. Duplicate-key suggestions are new in context but extend existing error handling.

### Fix Scope

Three distinct repairs:
1. **Feature create**: Add `CustomKey` to DTO, read flag in CLI helper, add service path
2. **Task create**: Read `--key` flag in CLI helper, plumb to service (service code already exists)
3. **Duplicate-key errors**: Extend error messages to suggest next available key for all three entity types

### Why This Matters

- **UX**: Users expect `--key` to work consistently across all createable entities (like epic)
- **Error Recovery**: Without suggested next key, users must manually trial-and-error or re-run the command
- **Completeness**: Service layer is ready; CLI is the gap for task; DTO is the gap for feature
