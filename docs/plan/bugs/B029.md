# cascade.go regresses fat-controller compliance — new CLI command creates repositories directly

## Description

Commit 6492e45 added a new CLI command file, `internal/cli/commands/cascade.go`, that creates three repositories directly from a command handler:

```go
taskRepo := repository.NewTaskRepository(db)
epicRepo := repository.NewEpicRepository(db)
featureRepo := repository.NewFeatureRepository(db)
```

This is the classic fat-controller anti-pattern explicitly forbidden by:

- `.claude/rules/architecture.md` — "CLI commands must NOT create repositories directly or contain business logic. They call services."
- `.claude/rules/cli/commands.md` — "DEPRECATED ... Do NOT add new commands that follow this pattern."
- `.claude/rules/services/cli-integration.md` — the three-step pattern: parse args → call service → format output.

The work in `listDispatchableChildren` is not pure data access either: it does terminal-status filtering (cross-cutting business rule — see B028) and relies on ordering invariants from the repository query. That's business logic, not formatting.

This regresses E15-F11 ("Verify all migrated CLI files pass lint, tests, and fat-controller compliance check"), which was the dedicated compliance feature for exactly this issue. T-E15-F11-025 caught the same violation in `history.go` during its run; this one made it past review into a shipped commit.

A broader companion concern lives in the same file: `next.go:144-329` — `resolveNext` is a 200+ line CLI handler mixing argument parsing, service-graph construction, status reading, cascade recursion, verb normalization, and agent-body inlining. The refactor is tracked separately as TD-017.

## Expected Behavior

CLI commands in `internal/cli/commands/` parse arguments, call a service method, and format output. Repository construction, cross-entity queries, and business-rule filtering live in services (`internal/services/`).

## Actual Behavior

`cascade.go` constructs repositories at the command layer, performs cross-entity queries (resolve epic by key → list features → filter; or list tasks by feature key → filter), and applies a terminal-status filter directly in the loop — all behaviors that the layered architecture assigns to a service.

## Steps to Reproduce

1. Read `internal/cli/commands/cascade.go`.
2. Observe `listDispatchableChildren` creating `repository.New{Task,Epic,Feature}Repository` and iterating results with inline `isTerminalStatus` calls.
3. Run any rule that enforces the no-direct-repo-access pattern in CLI commands (e.g., the audit performed during E15-F11) — `cascade.go` violates it.

## Fix Notes

- Extend `FeatureService` and `EpicService` (or introduce a `CascadeService`) with a method like `DispatchableChildren(ctx, parentKey) ([]ChildRef, error)`. Service owns: child fetch, terminal filter (delegating to `workflow.Service` per B028), ordering pass-through.
- `cascade.go` reduces to: parse args → call service → return result. No repository imports.
- Coordinate with B028 (hardcoded terminal-status fix) — same code path.
- Closely related: TD-017 (split `resolveNext`), which extends the same architectural cleanup to the broader command.
