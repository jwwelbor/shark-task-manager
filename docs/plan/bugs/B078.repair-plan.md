# B078 repair plan — delete the selected document link

**Contract.** `shark related-docs delete <title> --task <key>` may report success after removing the intended association, or after establishing that the selected parent already lacks it. A specific error must reach the caller if selection or removal fails. The same contract applies to each supported delete selector.

**Review baseline.** Use `bbf490c6ec2bd597d6f3e6e4cdd93e68ca54fa50` for the complete B078 change. The parent recorded it in Shark B078 note 3556. It is the parent of the first repair commit, `932dd5080aaa592e24a427ce1a999ee34603f554`, and the base recorded in all four prior reviews. The branch already contains development. Compare its entire candidate to this baseline, including work that predates this plan.

## Diagnosis

WWGM recorded two successful deletes followed by a list that still contained task document 563. On the owning project's database, document 542 has the same title and belongs to bug B107. Task T-E10-F02-013 links both 563, whose task-relative path is malformed, and 564, the valid root continuation under a different title. The original title-only SQL selects 542 on the inspected snapshot. WWGM note 3043 explicitly corrects note 3041's claim that the bad link had been removed. The historical invocations did not record the selected SQL row. [Bug intake](B078.md) · [Research findings 1–7](B078.research-report.md) · [Owner records and observations](B078.repair-plan-evidence.md#consumer)

Three baseline behaviors explain the false success. First, `documents` identifies a document by ID and allows the same title at different paths. `GetByTitle` uses an unordered global query. The service could therefore request a delete for the triple (task, 452, 542), which never existed, and leave (task, 452, 563) intact. Second, the service converted every document lookup error to a successful no-op, and the CLI discarded errors from five entity services. Third, delete accepted zero selectors or chose the first of several, so it could acknowledge a request without establishing which parent the caller intended. The production question branch already returned contextual errors. [Baseline command](../../../internal/cli/commands/related_docs.go) · [Shared service](../../../internal/services/entity_document_service.go) · [Title lookup](../../../internal/repository/document/repository.go) · [Association SQL](../../../internal/repository/entitydoc/repository.go)

## Proposed decision

1. Keep the existing title argument and require exactly one explicitly supplied, nonempty parent selector before service dispatch. Count presence even when a supplied flag is empty. Return selection and flag-reading errors to Cobra. Retain the public spelling `--change` and the output label `change-card`.
2. Resolve the parent through its existing service. In `EntityDocumentService.UnlinkDocumentByKey`, use `ListForEntity` on the resolved type and numeric ID. Compare exact titles. Zero matches is an idempotent success. Two or more is an ambiguity error naming the title and parent with zero mutations. One match supplies the exact document ID for `Unlink`. A path or ID syntax, global deduplication and a schema migration are outside this repair.
3. Require an observable success condition for that exact association. A scoped delete affecting one row establishes removal. If the database reports zero affected rows, check the exact triple and succeed only for verified absence. Surface a retained row, an indeterminate result or any lookup/write error. Use bound parameters and the caller's context. This preserves retries when another unlink won the race. A later independent relink is a new operation.
4. Print the existing JSON or human confirmation only after the service succeeds. Preserve wrapped causes and the existing question-key diagnostic. Keep CLI parsing and formatting in the command, title resolution in the shared service, and persistence checks in the association repository. The normal path loads only one parent's links and deletes by its unique association key.

Reuse the repair already present where it meets the assertions below. The mutable record identifies outstanding proof and a fixture correction. The scope includes delete dispatch, the shared service and repository, affected test doubles, focused regression tests and the delete help/reference where it describes selection and ambiguity. Add, list, workflow configuration, WWGM records/files, and document creation, path normalization and migration are outside the change.
