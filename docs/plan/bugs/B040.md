# Dependency checks can dispatch blocked work and auto-unblock on truncated reads

## Description

Full code review on 2026-07-07 found ValidateDependencies is effectively unused in dispatch, checks dependents instead of dependencies, cascade dispatch ignores depends_on, and repository dependency scans fall through without rows.Err checks. A truncated read can therefore report all dependencies satisfied and auto-unblock dependents incorrectly. See dev-artifacts/2026-07-07-full-code-review/code-review-report.md sections M1 and M3.

## Expected Behavior

Dispatch and auto-unblock logic should honor `depends_on` relationships, check
dependencies rather than dependents, and fail closed on repository scan errors.

## Actual Behavior

Dependency validation is not wired into the dispatch path, the helper that exists
checks dependents instead of dependencies, and dependency scans can return
"satisfied" after a truncated read because `rows.Err()` is not checked.

## Steps to Reproduce

1. Create a task that depends on another open task.
2. Run `shark next` or the relevant cascade path for the dependent task.
3. Observe that the dependent task can still dispatch, or that an interrupted
   dependency scan can incorrectly unblock dependents.

## Fix Notes

Review source points:
- `internal/services/task_service.go`
- `internal/services/cascade_service.go`
- `internal/repository/task/dependency.go`
- report sections M1 and M3
