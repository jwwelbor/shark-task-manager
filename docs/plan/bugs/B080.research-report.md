# B080 Research Report

## Scope

Research the solo sprint-execution loop's interpretation of an empty `shark sprint next` result. The target question is whether “no candidate is selectable now” proves that every assigned item is terminal. Keep selection, dispatch, completion, and sprint-goal acceptance distinct: `sprint next` selects; keyed `/shark-rider run` dispatches; an all-assignment status check can establish whether work is terminal; the owner and accepted Sprint Goal Review remain separate close gates. B081's unsupported positional argument is adjacent but separate.

## Findings

### Reproduction and affected capability

The solo workflow's Step 2 breaks when `NEXT_ENTITY` is null or empty and labels that branch “backlog drained”; its loop-exit list repeats that an empty result is normal completion. The top-level sprint-execution skill says the loop runs “until empty,” and `docs/cli-reference/sprint-commands.md` also calls a `null` result a drained backlog. These statements reach three consumers of the same decision.

The classification is false for valid selector outcomes. `SprintService.GetNextTask` returns `nil, nil` when the shared candidate set is empty. The candidate set starts with assigned, nonterminal workflow items and is narrowed by optional `--agent` workflow-role eligibility, active claims, open Question gates, and roadmap admission. The production `GetSprintService` wires claim, Question, and roadmap-admission readers. Errors loading claims or evaluating admission are surfaced as errors; a successful empty result means only that no candidate survived the configured filters.

The source-level reproduction is specific: `TestGetNextTask_E38F06_NoMatchingRoleReturnsNil` supplies two nonterminal assignments and asks for the `qa` role; `GetNextTask` returns nil because neither assignment is eligible for that role. `runSprintNext` serializes a nil item as JSON `null`, which the solo recipe calls a drained backlog. A second existing fixture, `TestSelectSprint_B044_BatchClaimLookup`, returns an empty candidate set when all assigned candidates have active claims. Question-blocked candidates and roadmap-admission failures are filtered at the same service boundary. The selector's `excluded_by_reason` records roadmap reasons, but `sprint next` returns before attaching that map when there is no winner; role, claim, and Question exclusions are not represented in its empty response.

There is a separate command-shape mismatch: the solo recipe builds `shark sprint next {SPRINT_KEY} --json`, while live `shark sprint next --help` accepts flags only and no positional sprint key. That B081 issue can cause the literal recipe command to fail before reaching the empty-result branch. It does not remove B080: the supported keyless selector can still return `null` after a role, claim, Question, or admission filter removes every candidate.

### Existing completion checks and related patterns

The team-mode procedure already states the needed invariant: “A no-candidate result is never itself success.” For sprint runs it directs the coordinator to inspect the all-status sprint backlog and require every assigned item to be terminal; otherwise it reports paused, blocked, claimed, or Question-gated work. `shark sprint backlog --help` confirms `--all` includes terminal-status items. Team mode uses the canonical topology adapter rather than the solo loop, so it is a reusable pattern, not a fix to the affected solo recipe.

The selector contract offers partial diagnostics. `shark plan sprint` returns `action: pause` when it has no candidates and preserves `excluded_by_reason` for roadmap admission. That map does not explain role, claim, or Question filtering. `shark sprint backlog <key> --all --json` can establish whether assigned work remains nonterminal, but exact cause reporting for each hidden candidate would require richer selector diagnostics. The `shark claims` help states that listing claims sweeps expired leases first, so it is not a side-effect-free probe for this recipe.

The solo workflow has an explicit user confirmation and a Sprint Goal Review gate before close, which prevents automatic closure. Those gates do not establish that the backlog is drained. `CloseSprintWithCarryover` separately classifies incomplete assignments and can reassign them to the next sprint or remove their assignments according to the carryover mode. An empty selector result therefore must not be presented as full sprint completion or as evidence that no unfinished assignment will be affected by a later close.

## Decisions

1. The repair extends the existing solo sprint-execution capability; no new selector or sprint scheduler is needed for the core correction.
2. Treat an empty result as “no eligible candidate returned.” Before reporting the sprint backlog drained, verify the active sprint's complete assignment set with the supported all-status backlog view and require every assigned entity to be terminal under its entity workflow. If unfinished assignments remain, report the held work and do not present the selector result as normal completion. If an `--agent` filter is active, distinguish that role slice being empty from the whole sprint being drained.
3. Reuse `parallel-team.md`'s no-candidate rule. If the solo workflow needs to name each exclusion cause automatically, extend the existing selection response: the current `sprint next` null loses cause information, and `plan sprint` exposes only roadmap exclusion counts. Avoid using `shark claims` as a read-only diagnostic because its documented command sweeps expired leases.
4. Keep owner confirmation and accepted Sprint Goal Review as independent close gates. A close with carryover can affect incomplete assignments, so neither gate should be inferred from an empty pull result.
5. Keep B081's unsupported positional argument separate. The supported CLI is keyless `shark sprint next [flags]`; the recipe's positional-key issue needs its own disposition.
6. When editing the workflow later, follow the current embedded-canonical/repo-mirror contract, and account for the installed symlink. B045 is prior distribution-drift work, not evidence that the current empty-result text is already fixed.
