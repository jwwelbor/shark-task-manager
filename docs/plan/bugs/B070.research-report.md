# B070 research report

## Scope

B070 covers the user-facing contract for the `shark status` command family:
whether the parent command displays a dashboard or serves as a namespace for
status operations. The research compares the reported documentation with the
current Cobra command tree, the dashboard and entity-inspection commands, and
the E17 migration artifacts that established the current split.

## Findings

1. The defect reproduces in the current executable. `./bin/shark status` and
   `./bin/shark status B070` both print the parent help page, including the
   guidance to use `shark progress` for dashboards and `shark get <key>` for
   entity details; neither invocation renders a dashboard or entity record.
   `./bin/shark progress` renders the project dashboard, and
   `./bin/shark get B070 --field status` returns `research`.

2. The implementation deliberately makes `status` a Cobra parent with no
   `RunE` handler (`internal/cli/commands/status.go:8-30`). Its only registered
   children are `set`, `advance`, `transitions`, and `history`
   (`internal/cli/commands/status_group.go:225-230`). This is the affected
   capability and is internally consistent with the current runtime behavior.

3. Dashboard behavior is now owned by `progress`. Its command contract is
   `progress [EPIC] [FEATURE]`, and its implementation calls
   `StatusService.GetDashboard` (`internal/cli/commands/progress.go:19-39,
   49-79`). The filter is hierarchical, not a universal entity-key lookup:
   `./bin/shark progress B070` rejects `B070` as an invalid list key. The
   report therefore should not replace the stale syntax with an unconstrained
   `shark progress [key]` claim.

4. `get` is the canonical inspection dispatcher for epic, feature, task, bug,
   change, tech-debt, idea, sprint, and question keys
   (`internal/cli/commands/get.go:9-37, 45-84`). For standalone entities such
   as B070, documentation should direct users to `shark get <key>` or
   `shark get <key> --field status`; dashboard documentation should use
   `shark progress` with its supported project/epic/feature forms.

5. The stale claims are present in `.claude/rules/quickref.md:61-64`,
   `docs/cli-reference/README.md:27,49`, and
   `docs/cli-reference/status-commands.md:13-64`. The current `CLAUDE.md`
   points readers to these references but does not contain a matching command
   table in this checkout. The status reference also describes the removed
   dashboard behavior as distinct from `progress`, contradicting the runtime
   help and the command implementation.

6. Related E17 work explains the drift. E17-F07 established the status
   subcommand namespace, while E17-F06 moved the dashboard command to
   `progress`; commit `4fcb120c` explicitly removed the dashboard from bare
   `status`. The implementation and migration decision are already available
   and should be reused rather than adding a second dashboard route.

## Decisions

1. Choose the documentation-alignment option in B070. The runtime behavior is
   intentional and already implements the E17 split: `status` is strictly a
   status-operation namespace, `progress` is the hierarchy dashboard, and
   `get` is the general entity-inspection path.

2. Repair the existing documentation capability rather than adding a new
   runtime dispatcher. Update the stale bare-status dashboard examples and
   `status [key]` table entry across the affected references. Describe
   `progress` using its actual `[EPIC] [FEATURE]` scope, and use `get` for
   standalone entity details/status fields.

3. This is an extension of the existing CLI documentation contract, not new
   dashboard functionality. A focused documentation change plus command-help
   or reference checks is sufficient; no service, persistence, workflow, or
   API change is indicated by the current evidence.
