# B082 research report — Unified change creation drops an explicitly supplied required size

## Scope

Trace `--size` from the two existing change-card creation commands into the shared service when `.sharkconfig.json` lists `change` in `size_required_for`. Here, size is the optional numeric value in `CreateChangeCardInput.Size`; an omitted flag must remain nil, while an explicit `--size=3` must arrive as 3. The research is limited to CLI dispatch, input construction, and the existing service contract. No implementation files were changed.

## Findings

### Reproduction

I built the current checkout with `go build -o <temporary-project>/shark ./cmd/shark` and ran both commands from a disposable project configured with `{"size_required_for":["change"]}`:

- `shark create change "B082 unified repro" --size=3` exited 1 with `size is required for change`.
- `shark change create "B082 entity-specific repro" --size=3` exited 0 and created `CC-001`; `shark change get CC-001 --json` reported `"size": 3` and `"size_label": "M"`.

This isolates the same explicit size and required-size policy in the two command paths. The historical B082 capture also records two failures and the entity-specific command succeeding with the `E19-F06` anchor while configuration stayed unchanged (`docs/plan/bugs/B082.md:8-16`). The isolated reproduction omitted the anchor; it was sufficient to reproduce the size-forwarding failure without touching the assigned checkout's database or files.

### Affected path and cause

`shark create change` is registered with `RunE: runChangeCardCreate` (`internal/cli/commands/create.go:105-118`). Its unified flags include `--size` (`create.go:406-418`), but `runChangeCardCreate` reads the description, justification, requester, epic, feature, and content flags without reading `size`; the `CreateChangeCardInput` it constructs therefore leaves `Size` nil (`internal/cli/commands/change_card_commands.go:32-53`). The normal service accessor wires size enforcement (`internal/cli/services_global.go:483-492`), and `ChangeCardService.CreateChangeCard` rejects a nil size when `change` is required (`internal/services/change_card_service.go:134-145`).

The entity-specific `shark change create` handler reads `--size`, validates it with `models.ParseSize`, and assigns the parsed value to `input.Size` before calling the same service (`internal/cli/commands/change.go:276-295`). The service and persistence path already support the size; the defect is the unified CLI adapter dropping the supplied value before service validation.

### Existing coverage and related work

`TestCreateUnifiedSubcommands_SizeFlagRegistered` checks only that unified commands expose a string `--size` flag (`internal/cli/commands/create_test.go:177-212`). The entity-specific create tests verify that numeric and label values reach the service DTO (`internal/cli/commands/size_flag_create_test.go:214-260`). This leaves a gap between flag registration and unified-command forwarding.

CC-048 and CC-049 are adjacent recovery intake, not fixes for this CLI behavior. The linked recovery plan explicitly assigns B082 an independent CLI fix and calls for verifying that both create paths forward the same size without relaxing `size_required_for` (`docs/plan/2026-10-15-sprint-integration-recovery-plan.md:31-40`). The existing entity-specific size parser and shared enforcement are the relevant patterns to reuse.

## Decisions

1. Repair the unified CLI handler so an explicit `--size` is parsed with the existing `models.ParseSize` behavior and assigned to `CreateChangeCardInput.Size`. Keep required-size enforcement in the service unchanged; do not make `change` optional in configuration or accept a nil size.
2. Add regression coverage that executes `shark create change` through its handler and verifies the explicit size reaches the service. Include the `change-card` alias because it shares this handler, and retain a required-size configuration case to prove the original failure is fixed without weakening enforcement.
3. This extends the existing change-card creation capability. It does not require a new service, data field, or creation workflow. Research outcome: `pass`.
