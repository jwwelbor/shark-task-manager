# Verify .claude/rules/database-critical.md skip_migrations toggle requirement against ApplySchemaIfNeeded behavior

## Description

`.claude/rules/database-critical.md` (and the duplicated callout in `internal/db/db.go:3283-3286`) instructs developers to **(1) flip `skip_migrations: false`** in `.sharkconfig.json` before running the next shark command and **(2) also bump `CurrentSchemaVersion`** when adding a migration. Verification of the actual code in `internal/dbinit/init.go:200-208` and `internal/db/db.go:444-463` shows the two steps are **not both required** — bumping `CurrentSchemaVersion` alone is sufficient.

### Code under test

```go
// internal/dbinit/init.go (lines 200–208)
if dbConfig.SkipMigrations {
    if _, err := db.ApplySchemaIfNeeded(sqlDB); err != nil {
        return nil, fmt.Errorf("failed to apply schema (fast-path): %w", err)
    }
} else {
    if err := db.ApplySchemaAndMigrations(sqlDB); err != nil {
        return nil, fmt.Errorf("failed to apply schema and migrations: %w", err)
    }
}
```

```go
// internal/db/db.go (lines 444–463)
func ApplySchemaIfNeeded(db *sql.DB) (bool, error) {
    version, err := getSchemaVersion(db)
    if err != nil {
        if err2 := ApplySchemaAndMigrations(db); err2 != nil {
            return false, err2
        }
        return true, nil
    }
    if version >= CurrentSchemaVersion {
        return false, nil // Already up to date
    }
    if err := ApplySchemaAndMigrations(db); err != nil {
        return false, err
    }
    return true, nil
}
```

When `skip_migrations: true` AND `CurrentSchemaVersion` was bumped (say 13 → 14), the existing DB still records `version = 13`. `ApplySchemaIfNeeded` reads `version = 13`, sees `13 < 14`, and calls `ApplySchemaAndMigrations` — exactly what the toggle path does. So the toggle is redundant on the version-bump path.

The toggle is only meaningful in two narrow cases:

1. The developer added a migration but **forgot** to bump `CurrentSchemaVersion`. In that case, `ApplySchemaIfNeeded` short-circuits at `version >= CurrentSchemaVersion` and the migration never runs. Toggling to `false` forces `ApplySchemaAndMigrations` regardless. The rule's "checklist" already mandates the version bump as a separate item, making the toggle a belt-and-braces fallback for that mistake.
2. A migration was added that mutates schema in a way `ApplySchemaAndMigrations` cannot rerun idempotently — but every shipped migration in this codebase uses `IF NOT EXISTS` and is idempotent (see `migrateAddTagsAndEntityTags` at `internal/db/db.go:3289` and similar functions throughout `db.go`).

So in normal practice, **bumping `CurrentSchemaVersion` is sufficient and the toggle instruction misleads.**

## Expected Behavior

`.claude/rules/database-critical.md` should accurately describe how `ApplySchemaIfNeeded` works and what the developer is actually required to do. The rule should:

- State plainly that **bumping `CurrentSchemaVersion` is sufficient** to re-run the migration on an existing database, even when `skip_migrations: true`.
- Treat the `skip_migrations: false` toggle as an **optional fallback** for "I forgot to bump the version" scenarios, not a hard requirement.
- The duplicate developer callout at `internal/db/db.go:3283-3286` (the `migrateAddTagsAndEntityTags` comment block) should be brought in line with the same correction, or removed in favour of the rule file.
- Optionally, `ApplySchemaIfNeeded` could log a one-line "applying schema migrations (version X → Y)" message so developers can see when the fast path triggers a real migration. This would make the behaviour observable without re-reading the source.

## Actual Behavior

The rule states the toggle is mandatory:

> 1. **Tell the developer:** _"This change adds a migration. Set `skip_migrations: false` in `.sharkconfig.json` before running the next shark command, then set it back to `true`."_
> 2. **Also bump `CurrentSchemaVersion`** in `internal/db/db.go` — this ensures `ApplySchemaIfNeeded` re-runs on databases that already recorded the old version.

…and the explanatory paragraph reinforces the requirement:

> If you add a migration without bumping the version, the migration **never runs** on existing databases.

The rule does not explain that step 2 alone (bump `CurrentSchemaVersion`) is enough on the `skip_migrations: true` path. A developer following the rule literally is asked to perform an unnecessary configuration round-trip on every migration.

## Steps to Reproduce

1. Set `skip_migrations: true` in `.sharkconfig.json`.
2. Take a database with `schema_version` = `CurrentSchemaVersion - 1` (i.e. one schema version behind).
3. Add a new idempotent migration to `runMigrations()` in `internal/db/db.go` and bump `CurrentSchemaVersion` accordingly. Do **not** flip `skip_migrations`.
4. Run any shark command (e.g. `shark task list`).
5. Observe that `ApplySchemaIfNeeded` reads the old version, takes the `version < CurrentSchemaVersion` branch, calls `ApplySchemaAndMigrations`, and runs the migration. The toggle was never needed.

## Fix Notes

This is a documentation-accuracy bug, not a code bug. Two recommended changes:

### 1. Rewrite the migration section in `.claude/rules/database-critical.md`

Replace the current "When You Add a Migration" checklist with something like:

> **When you add a new migration:**
>
> 1. Add the migration function to `internal/db/db.go` and call it from `runMigrations()`.
> 2. Bump `CurrentSchemaVersion` in `internal/db/db.go`. This is the only step required to make the migration run on existing databases — `ApplySchemaIfNeeded` reads the recorded `schema_version` and calls `ApplySchemaAndMigrations` whenever the recorded version is below `CurrentSchemaVersion`, regardless of `skip_migrations`.
> 3. (Optional belt-and-braces) If you suspect step 2 was missed in a previous migration or you want to force a full reapply, set `skip_migrations: false` in `.sharkconfig.json` for one run, then set it back to `true`.
>
> **Why:** With `skip_migrations: true`, the entry point calls `ApplySchemaIfNeeded`. That function compares the stored `schema_version` to `CurrentSchemaVersion` and runs `ApplySchemaAndMigrations` if the stored version is behind. Bumping the constant is therefore both necessary and sufficient. The toggle exists as a manual fallback, not a per-migration step.

### 2. Update or remove the duplicate callout at `internal/db/db.go:3283-3286`

The current comment in `migrateAddTagsAndEntityTags` (and any other migration functions that copy the pattern) repeats the misleading toggle requirement. Either:

- Reword to align with the rule, e.g. "This function adds schema version 14. `CurrentSchemaVersion` must be bumped accordingly so `ApplySchemaIfNeeded` re-runs migrations on existing databases."
- Or remove the per-function callout entirely and let the central rule file own the guidance.

- [ ] The migration callout in `internal/db/db.go` (currently at `migrateAddTagsAndEntityTags`, lines 3283-3286) is either updated to match the rule or removed.
