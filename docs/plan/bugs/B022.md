# shark next exits 1 on legacy task statuses (in_approval, ready_for_approval) instead of degrading

## Description

The dispatcher crashes (exit 1) when it encounters a task or descendant whose status is not defined in the workflow YAML. In the wormwoodGM trial this surfaced as two legacy statuses still present in the database: `in_approval` and `ready_for_approval`. Neither is defined in `shark-data/workflow/task.yaml` (defined statuses: draft, ready_for_development, in_development, completed, cancelled, blocked, on_hold).

This makes **any** feature or epic containing even one child in a legacy/unknown status entirely undispatchable.

## Expected Behavior

The cascade should either:
- **Option A (graceful degradation):** Treat unknown statuses as a terminal `pause` node and continue evaluating siblings. The unknown status surfaces as a warning, not a crash.
- **Option B (migration aid):** Provide a documented migration path (`shark migrate statuses` or similar) that maps legacy values onto the canonical set and refuses to leave the DB in a half-migrated state.

Either way, `shark next` on a feature with mixed legacy/canonical children must not exit non-zero.

## Actual Behavior

```
$ shark next E01-F24 --json --preview
exit 1
{ "error": true, "code": "COMMAND_ERROR",
  "message": "failed to populate action for status \"in_approval\":
              status 'in_approval' not found in workflow configuration" }

$ shark next E01 --json --preview
exit 1
{ "error": true, "code": "COMMAND_ERROR",
  "message": "failed to populate action for status \"ready_for_approval\":
              status 'ready_for_approval' not found in workflow configuration" }
```

## Steps to Reproduce

1. In a database with at least one task in status `in_approval` or `ready_for_approval` (or any status not in `shark-data/workflow/task.yaml`)
2. Run `shark next <parent-feature-or-epic> --json --preview`
3. Observe exit 1 with the populate-action error

Look at `internal/config/action/orchestrator.go` (or wherever `populate action for status` is wired) — the error path should fall through to a `pause` action rather than returning an error. Also need to decide on the policy question: do we keep legacy statuses around or write a migration?
