# Progress Coherency Violation

## Problem

`features.progress_pct` is a persisted cache, while epic progress is derived from feature rows on read. Several progress-affecting task, feature, and batch operations do not maintain that cache and the upward status rollup as one operation. Some existing refresh calls only log failures, so a mutation can return success after leaving parent state stale. Feature presentation also mixes cached and live progress values.

A local `TaskService.CreateTask` point fix was investigated and rejected because
it ran after commit and could only log aggregate-refresh failures. The systemic
fix must replace that best-effort path rather than landing it independently.

Investigation: `dev-artifacts/2026-07-17-progress-coherency-investigation/analysis/progress-coherency-investigation-note.md`.

## Required Invariant

Every successful progress-affecting write leaves the hierarchy coherent before control returns:

`task mutation -> feature progress cache and derived feature status -> epic derived status`

If any required parent update, reopen cascade, or history write fails, the entire SQLite transaction must roll back. Do not retain best-effort refreshes, repair-on-read behavior, or a new persisted epic progress cache.

## Implementation Plan

1. Add an internal transactional aggregate-mutation coordinator with narrow, transaction-aware repository interfaces. Wire it into task, feature, and epic services; it owns post-mutation aggregate maintenance only, while `EntityService.TransitionStatus` remains generic.
2. Execute task writes, feature-progress recalculation, epic-status derivation, and upward reopen cascades in one caller-owned SQLite transaction. Make cascade failures return errors rather than only logging them.
3. Route task create, delete, and status transitions through the coordinator. Each must refresh the parent feature cache/status; when that status changes, recalculate the parent epic status.
4. Route feature create, delete, direct status update, workflow transition, and force completion through the coordinator. Each must recalculate its parent epic status after the feature mutation.
5. In `EpicService.CompleteEpic`, complete child tasks/features, refresh every affected feature cache, and persist epic completion in the same transaction. Remove the compensating CLI-side progress-recalculation loop.
6. Keep metadata-only task/feature updates outside the coordinator unless they later change membership, status, or progress semantics. Epics have no parent and retain live-on-read progress.
7. Preserve task-file atomicity: if a newly created task file precedes a failed aggregate transaction, remove only that newly-created file; never delete an already-linked file.
8. Make each feature read path use one computed progress source for displayed progress, readiness messaging, JSON values, and progress sorting. Retain the coherent persisted cache for epic analytics and configured fallback behavior.

## Acceptance Criteria

- Task create, delete, and status changes leave `features.progress_pct` and derived feature status current before returning.
- Feature create, delete, status changes, and completion leave the parent epic status current before returning.
- Epic completion leaves every child feature cache current without CLI assistance.
- A failed aggregate refresh, epic recalculation, reopen cascade, or history write rolls back the child mutation and cleans up only a file newly created by that failed task creation.
- Feature list display and sort order use the same progress value; feature get readiness messaging uses computed progress rather than a stale cached field.
- Existing workflow-configured behavior, manual feature status overrides, and explicit epic-completion semantics remain intact.
- Service tests use mocks for orchestration and repository transaction tests cover real SQLite atomicity. The full gate passes: `make fmt && make lint && make test`.

## Scope

Forward-only enforcement. Do not add a reconciliation command, automatic read-time writes, an `epics.progress_pct` column, new user-facing flags, or a schema migration.
