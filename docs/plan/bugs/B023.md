# shark validate silently accepts missing workflow YAMLs and falls back to hardcoded defaults

## Description

When one of the workflow YAML files under `shark-data/workflow/` is missing, `shark validate` does not flag it as an issue. The dispatcher silently falls back to hardcoded defaults, which changes runtime behavior (e.g., features stuck in `active` end up pausing instead of cascading). The validator's job is precisely to catch this kind of config drift before a worker hits the silent fallback at runtime.

## Expected Behavior

`shark validate` should:
- **Error** (or at minimum **warn loudly**) when any of the expected per-entity workflow YAMLs is missing: `task.yaml`, `feature.yaml`, `epic.yaml`, `bug.yaml`, `change.yaml`
- Make it explicit when the engine is running on built-in defaults rather than the project's own workflow definitions

## Actual Behavior

Moving `shark-data/workflow/feature.yaml` aside produces no new output from `shark validate` (only the pre-existing UAT-SKILL informational warning fires). `shark next E01-F41 --json --preview` then quietly pauses at the feature node because the fallback defaults have no `orchestrator_action` for feature status `active`.

## Steps to Reproduce

1. In a project with a full set of workflow YAMLs:
   ```
   mv shark-data/workflow/feature.yaml /tmp/feature.yaml.bak
   shark validate                     # exits 0, no new warning
   shark next <any-feature-key> --json --preview   # silently pauses
   mv /tmp/feature.yaml.bak shark-data/workflow/feature.yaml
   ```

## Fix Notes

Likely fix in `shark validate` (entry point under `internal/cli/commands/sharkdata_cmd.go` or `internal/config/workflow/yaml_loader.go`) — after loading, check that every expected per-entity workflow file was present and report each missing one. Decide whether silent-fallback-to-defaults should remain (with a loud warning) or whether missing files should hard-fail validation.
