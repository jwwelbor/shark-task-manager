# B083 research report — Codex route selection and worker outcomes

## Scope

**A correctly routed Codex worker can finish successfully and still be recorded as a failure.** On candidate `3d7f2c77`, an explicit workflow route and a selected routing profile both reached the requested executable. The E40 adapter lost the final worker message while decoding stdout. This extends the diagnosis in approved repair plan R6, which covered discovery and command construction. Shark's development return to research records the new cause in notes 4409–4410.

The **requested route** comes from the workflow or profile. The **effective route** is the provider, model and effort materialized for a stage. The **observed attempt** is the executable, arguments, start count and outcome at the worker boundary. Codex catalog membership establishes an advertised route. Service access can only be observed on an actual attempt. B083 covers E40 from preview through the retained lifecycle outcome. B077 owns native Rider dispatch attestation.

## Findings

### Reproduction and production consequence

I ran `python3 -B -m pytest -p no:cacheprovider -q --tb=short bench/scripts/tests/test_b083_codex_dispatch_result.py` in the assigned checkout. The pre-existing working-tree regression has SHA-256 `07431ccc0b6bf7af10c865156e48a345a3bc8f5024f10580fc65dc08f543173e`. In each case the real materializer resolved the page-two model, made zero exec calls during preparation, and the real adapter launched the same synthetic Codex executable once with the exact model, high effort and prompt. Only the representation of the successful worker result varied.

| Output from the synthetic executable (exit 0) | Explicit workflow | Selected profile |
|---|---|---|
| Bare JSON control envelope, kind `final`, outcome `pass` | Adapter exit 0, returned pass with parent session | Same |
| Identical envelope as text in a completed Codex agent message, followed by a completed turn | Adapter exit 2, empty stdout | Same |

The diagnostic in both failing cases was `provider output does not contain a control envelope`. A minimal replay against the committed adapter needs only an echoing executable selected via `E40_CODEX_COMMAND` and a valid adapter request with matching prompt length and digest. Set the prompt to the following two lines so the executable emits them verbatim. Using just the inner JSON control envelope as the prompt gives the passing control. I verified both cases separately from the working-tree regression.

```jsonl
{"type":"item.completed","item":{"type":"agent_message","text":"{\"kind\":\"final\",\"recommended_outcome\":\"pass\",\"evidence\":[]}"}}
{"type":"turn.completed","usage":{}}
```

I also checked the two retained development batch records and their exec receipts. With Claude absent, the selected profile dispatched the page-two pin at high effort once. The explicit workflow with both fields omitted dispatched the advertised default at low effort once. Both records contained one dispatch, `outcome.terminal=worker_failure`, `partial_evidence=true` and `publication_eligible=false`. The earlier batch replay exited zero in each mode. Its shell exit alone cannot verify a successful benchmark pair. The profile and workflow ledger hashes were respectively `4a709ee55d4fd73a3e2d1b978ab81e5a0679dcd459a62a91c3f0da0f54a4349b` and `b287fc33ece1a26756db852845d6f608aab0e54e94b3f5034a5541a113afeccd`. ### Where the failure enters the lifecycle

1. The original capture at `f4b03228` found that the default adapter built `codex exec --json` for either requested model. The benchmark branch forwarded `-m` even for a Claude model. E40-F13 provided stage profiles and routing digests. An intermediate repair added production profile application but required a second, unavailable account catalog, blocking advertised routes before dispatch. These describe earlier revisions.
2. On `3d7f2c77`, the operator's `execute_profile()` path and batch preflight use run-local workflow materialization. The Codex client consumes paginated app-server `model/list` results. Both profile and explicit workflow routes feed the selected tuple into identity and the adapter request. The default Codex command adds `exec --json -m <model>` and the selected effort. The repro reached that executable. [Operator](../../../bench/scripts/lib/e40_benchmark.py) · [Catalog client](../../../bench/scripts/lib/codex_model_catalog.py) · [Materializer](../../../bench/scripts/materialize-routing-profile.py) · [Batch runner](../../../bench/scripts/run-lifecycle-batch.sh)
3. After a zero process exit, the adapter calls `decode_envelope()`. Its JSONL scan recognizes Copilot's `assistant.message/data.content`. Its fallback takes the last non-result object, which here is `turn.completed`. That record carries usage. The preceding `item.completed` with `item.type=agent_message` carries the worker's final text in `item.text`. The fallback never reads that text. A single Codex event object also misses the existing top-level wrapper keys. Parsing stops before `project_result()` can validate the worker outcome. [Adapter](../../../bench/scripts/lifecycle-worker-adapter.sh) · [Codex JSONL event contract](https://developers.openai.com/codex/noninteractive/#make-output-machine-readable)
4. The controller's `adapter_result()` receives a nonzero adapter exit. Its dispatch error path records the attempted stage as a worker failure. The older TC-123 recording adapter manufactured its own success or denial and counted adapter calls. That fixture could pass with zero Codex exec starts. The development record reports 162 passing Python checks alongside green Go gates using the earlier coverage. ## Decisions

1. **Extend the existing E40 adapter.** Select the terminal completed agent message of the successful Codex turn and decode only its text for workflow authority. Exercise multiple messages, command/tool output containing envelope-like text, malformed/missing final text and failed or incomplete turns. Preserve direct envelopes, supported text outcomes and structured questions through existing projection. Keep nonzero process exits decisive. A feasible alternative is `--output-last-message` with a private per-attempt file. It adds argv, file handling and cleanup to every attempt. The JSONL contract and branch experiment support handling the stream E40 already requests. [Codex transport reference](../../../skills/shark-attack/providers/codex.md)
2. **Verify at the lifecycle record.** Drive both the selected-profile and explicit-workflow modes through one synthetic executable for discovery and exec, with the active scratch route supplying the request. Assert exact provider, model, effort, prompt, session and execution count. Assert a valid final message reaches the expected workflow outcome. An advertised route denied by the process should retain its exact tuple and one failed attempt. Invalid discovery should leave a named route defect and zero worker starts. Check the manifest and retained pair even when the batch exits zero.
3. Preserve dynamic IDs, display names and descriptions, explicit pins, model-specific efforts, unique advertised defaults and credential-free provenance. The route digest follows execution identity and the catalog digest records discovery evidence. Keep preview free of inference, non-Codex omitted-effort behavior intact, and unresolved Codex usage/cost explicitly unmapped. A trailing usage event supplies no worker outcome or verified USD cost. Owner notes 3849, 3959 and 4008 govern Claude optionality, runtime selection and removal of fixed built-in Codex defaults. [Usage mapping](../../../bench/evidence/usage-mapping.yaml)
4. **Return to repair planning.** R6's fresh independent approval (note 4293) covers its committed scope. Row 6 tested pre-dispatch failure and post-start denial but omitted successful native result decoding. A successor plan should bind that new cause and the open review findings to actual process and ledger evidence before fresh independent approval, code review and QA. Decision 4275 requires fresh gates. CC-044 governs committed plan identity and parent-owned workflow transitions. [Revision 6](B083.repair-plan-r6.md) · [CC-044 decisions](../changes/CC-044-integration-decisions.md)

The diagnosis is supported offline. The synthetic runs establish what E40 does with a documented successful stream. Live service availability, account entitlement, model inventory and provider billing remain unmeasured and are unnecessary to reproduce this failure.
