# Research report: E40 harness switching does not resolve compatible model routes

## Scope

This research traces how an E40 benchmark harness selects a provider and model, materializes profiles, and dispatches workers. The contract is the expected behavior in Shark bug record B083: switching harnesses must produce compatible, available model routes before dispatch, retain explicit route identity, and report unresolved choices instead of silently passing them through.

I inspected the assigned checkout at `bbf490c6ec2bd597d6f3e6e4cdd93e68ca54fa50` and compared the current `bench-working` branch read-only at `2708dcc0`. I evaluated the embedded `command_for()` function using synthetic request dictionaries. No provider CLI was started. The B083 bug capture is an untracked file in the shared root checkout at `/home/jwwel/projects/shark-task-manager/docs/plan/bugs/B083.md`; this report does not modify or commit it.

**Vocabulary:** A workflow route is a Shark stage's `provider`, `model`, and `effort`. A routing profile maps stage names to those route fields. A harness is the provider-specific command adapter used to execute a route. Model support by a CLI, account authorization, and temporary account availability are separate facts.

## Findings

### Production dispatch preserves a requested route but does not resolve it

The production path starts in `execute_profile()` in `bench/scripts/lib/e40_benchmark.py`, which runs `run-lifecycle-batch.sh`. For live runs, the batch driver invokes `run-lifecycle.sh` for each scenario. When Shark returns a `spawn_agent` response, `run-lifecycle.sh` copies that response into the adapter request without changing its `provider` or `model`, then `adapter_result()` starts the configured lifecycle adapter. `lifecycle-worker-adapter.sh` calls `command_for()` to build provider-specific argv.

The separate `--mode resolve-route` preview traces Shark status transitions and records stage/provider-call counts. Its implementation explicitly omits the adapter subprocess; this route trace does not validate provider/model compatibility or account availability (`run-lifecycle.sh:2008-2013`; `run-lifecycle-batch.sh:500-508`).

### Current main drops the requested Codex model

On the inspected main snapshot, `command_for()` passes `request["model"]` to Claude and Copilot command construction, but the `openai`/`codex` branch returns only `codex exec --json` (`bench/scripts/lifecycle-worker-adapter.sh:157-204`). An offline call to the embedded function with `{provider: codex, model: sonnet}` and `{provider: codex, model: gpt-6-luna}` returned the same argv, `codex exec --json`, for both. The requested model is lost before the Codex process starts.

The read-only `bench-working` comparison adds a non-empty check and `-m <model>` to the Codex command. It still forwards `{provider: codex, model: sonnet}` unchanged. Its Codex tests check the pinned `gpt-5.6-luna` argv, not rejection or resolution of an incompatible model. Thus the branch fixes transport of a model string but does not establish that the string is supported or available. The compared changes are branch-only and are not present in `origin/main`.

### Routing profiles exist, but production does not apply them or validate model compatibility

`bench/scripts/lib/e40_benchmark.py` defines `load_routing_profile()` and `apply_routing_profile()`, and the Copilot profile tests call them. A source search for those names outside tests found only their definitions. No production harness-selection path loads or applies a profile before `run-lifecycle.sh` dispatches stages.

The profile schema accepts a root provider from a fixed vocabulary, validates non-empty model strings, and validates effort values. It has no provider-specific model compatibility or availability field (`bench/profiles/schema.yaml`; `e40_benchmark.py:194-263`). The workflow route identity helper hashes the declared provider, model, and effort values (`e40_benchmark.py:137-186`); production manifest construction records those digests (`e40_benchmark.py:3779`). It describes route identity but does not select a compatible model.

E40-F13 adds Copilot command construction, explicit profile examples, model identity capture, and route-identity tests. Its `apply_routing_profile()` tests prove that route edits change digests, but do not show a production caller. The feature does not provide automatic provider-specific model resolution. Its earlier live model catalog is a historical Copilot host observation, not proof of current account authorization or Codex compatibility.

### Related findings and sibling risk

The CC-044 architect consultation records the requested behavior: selecting a harness should resolve compatible available models, and switching to Codex must not leave a Claude/Sonnet route active. It also distinguishes CLI support, account authorization, and temporary provider availability, and says not to silently substitute a model. The tracked CC-044 workflow plan preserves explicit `provider`, `model`, and `effort` routes and says not to introduce an unsupported `difficulty` or `capability_profile` field as a model mapper (`docs/plan/changes/CC-044-workflow-plan.md:69-98`).

B077 covers native Shark Rider worker launches and their requested-versus-effective model evidence. It is related vocabulary and a boundary check, but it is a separate production path from E40's benchmark adapter. Fixing B083 in the E40 adapter will not establish B077's native launch behavior (`docs/plan/bugs/B077.md:8-65`).

The central sibling risk is a transport-only fix: forwarding a model flag can still send a model that the selected harness cannot run. A second risk is hashing a route before harness selection changes it, which would make the benchmark manifest describe a different route from the dispatched worker. No current account model catalog was queried, so this report makes no claim about models available to an account today.

## Decisions

1. The diagnosis is supported: current main loses the model in the Codex adapter branch, and no production path applies E40 routing profiles or validates provider/model compatibility.
2. Treat B083 as an extension to E40-F13's profile and adapter capability, with a new production compatibility-resolution step inside that path. Keep one route source and one adapter boundary.
3. Keep explicit workflow `provider`, `model`, and `effort` values authoritative unless an operator selects a routing profile. When a harness is selected, materialize the compatible route before dispatch and bind that exact route into the run identity.
4. Do not silently rewrite an incompatible model name. If compatibility or availability cannot be established, return a named unresolved/blocked result before the provider starts. Keep CLI model support, account authorization, and temporary availability distinct.
5. Keep B077 separate. B083 evidence must describe E40 benchmark dispatch and must not claim to fix native Rider worker selection.
6. Before implementation, identify the source of provider-specific compatibility and availability data. The offline code confirms the dispatch defect, but it cannot establish current account availability; an authorized preflight or a documented fail-closed route is required for that check.
