# B083 research report — E40 harness switching and model selection

## Scope

When an E40 benchmark selects Codex, each live stage needs a model and reasoning effort that the selected harness advertises. B083 covers the path from the workflow or routing profile through discovery, manifest identity, adapter invocation and the outcome of that attempt. Owner decision **3959** on November 20, 2026 makes Codex app-server `model/list` the discovery source. Catalog membership is enough to attempt the selected route. Only the attempt can establish whether the service accepts it. Claude is optional when a compatible Codex route is available.

A **requested route** is the stage's configured provider, model and effort. An **effective route** is the exact tuple selected for execution. An **advertised route** has matching evidence in the CLI catalog. Keep the source request, selected tuple and observed execution outcome distinguishable even when their model identifiers agree. B077 covers native Rider worker launches separately.

## Findings

### Current main drops the requested Codex model

I evaluated the embedded Python `command_for()` from each adapter revision with `provider=codex`, `effort=low`, no command override, and two model inputs. The first input, `sonnet`, reproduces the cross-harness error in the bug capture. The second, `fixture-route`, is an invented identifier. The probe inspected argv in memory and never executed it.

| Source inspected | Result for the two inputs |
|---|---|
| Local `origin/main` at `f4b03228` | Both returned exactly `codex exec --json`. Changing the requested model had no effect. |
| `bench-working` at `2708dcc0`, containing `caf8fe3a` and `90e44690` | Each command carried its input after `-m`, including `-m sonnet`. Forwarding the name alone permits an incompatible route. |
| Assigned worktree, including edits on top of `980a6342` | Each command carried the exact input after `-m` and the requested reasoning effort. The remaining production failure occurs before this adapter runs. |

### Routing profiles exist but production does not apply them or validate model compatibility

This finding applies to the inspected **main** revision. Searching its non-test `bench/` sources for `load_routing_profile(` and `apply_routing_profile(` returned only the two definitions. E40-F13 already defines per-stage assignments and deterministic provider, model, effort and combined routing digests in REQ-F-009. The branch commits `966b59a0`, `ef62735a` and `980a6342` built on those contracts. The assigned worktree now has production profile materialization and model-pinned argv. Reimplementing those pieces would duplicate work.

### Production dispatch preserves a requested route but does not resolve it

In the assigned worktree, `execute_profile()` calls the batch runner. Both route preview and live dispatch in `run-lifecycle-batch.sh` invoke `materialize-routing-profile.py` on a workflow copy. For a selected profile, `_materialize_profile()` calls `apply_selected_routing_profile()`. Without a profile, `_materialize_explicit_routes()` validates the workflow's Codex models directly. Both paths reach `validate_codex_catalogs()` without a CLI catalog. Even if a model passes the helper's CLI membership test, the function unconditionally raises an unavailable same-account catalog error. This prevents an advertised route from reaching dispatch and leaves actual access unknown.

**Reproduction.** Run `python3 -B bench/scripts/materialize-routing-profile.py --workflow-root <workflow.yaml>` with a single `steps.research` entry containing `action: spawn_agent`, `provider: codex`, `model: fixture-route` and `effort: low`. Repeat with `--profile <profile.yaml>` using a schema 1.0 Codex profile with the same stage and tuple. I observed exit **1** in both cases. Each JSON result preserved the requested tuple and reported `resolution=failed`, `cause_class=route_defect`, `dispatch_count=0` and the reason “Codex CLI compatibility catalog and trusted same-account catalog source are unavailable”. As a positive membership control, calling `validate_codex_catalogs("fixture-route", {"models": ["fixture-route"]})` still raised “trusted same-account catalog source is unavailable for the selected Codex route”.

TC-123 explains how the route can appear to work in tests. Its positive Codex case replaces the materializer and explicitly skips catalog validation. Its production-path case expects the missing account catalog to block dispatch. Those tests demonstrate route propagation and the old refusal respectively. Neither exercises successful discovery through the real materializer.

### The installed CLI provides the discovery contract

I inspected the stable protocol emitted by local `codex-cli 0.171.0` using `codex app-server generate-json-schema --out <temporary-directory>`. In `v2/ModelListResponse.json`, `data` contains model records and `nextCursor` signals another page. Records expose `id`, `model`, `displayName`, `isDefault`, `hidden`, `defaultReasoningEffort` and `supportedReasoningEfforts[].reasoningEffort`. `v2/ModelListParams.json` accepts a continuation `cursor`. The worktree's helper expects a flat `{"models": [string]}` and discards the metadata needed to validate an effort for a particular model.

The repair can discover candidates using the selected CLI's initialized app-server session and consume every page. Use the selected record's model value for invocation and retain its catalog identity. For an explicit pin, resolve that exact selection and check its effort. If selection is delegated to the harness, use advertised selection metadata such as its default and record which route was chosen. An unknown pin, unsupported effort or incomplete discovery should yield an actionable pre-dispatch cause. An access denial after dispatch belongs to the attempted tuple. Switching models after that denial would invalidate comparison identity.

This research inspected the protocol and exercised deterministic local fixtures. Account access, the live picker inventory and service availability were not measured.

## Capability map

| Capability | Decision | Evidence and consequence |
|---|---|---|
| E40-F13 profiles and workflow copies | EXTEND | Use the existing batch materializer for selected profiles and explicit routes. Add Codex discovery at their shared validation boundary. |
| Pinned adapter argv, route digests and failure ledger | REUSE | Carry the selected tuple into `identity.provider_routing`, the adapter request and the recorded attempt. Preserve the original request when a harness switch changes the tuple. |
| E40 consumer of Codex app-server `model/list` | NEW | The CLI supplies the protocol. E40 needs the client and the mapping from paginated model metadata to stage routes. A picker snapshot or checked-in list would drift. |
| Separate account catalog as a dispatch prerequisite | CONTRADICTS | The November 18 plan and TC-123 production assertion require this check. Owner decision 3959 authorizes attempting a catalog-advertised route and recording its actual access outcome. |
| Native Rider routing evidence, B077 | REUSE | Use the requested/effective distinction. Native launch behavior has a separate owner and verification path. |

## Decisions

1. **Extend E40-F13.** Preserve the workflow/profile selection, isolated copy, adapter and manifest contracts. The new work is dynamic Codex discovery and model-specific validation. Static model allow-lists, copying picker IDs into tests or configuration, and a string-only `-m` fix all miss the owner's requirement.
2. Use the same resolved tuple for preview, run identity and dispatch. Freeze the choice before hashing it. A changing catalog must never cause a different model to run under an earlier digest. Allow Codex-only operation without a Claude prerequisite.
3. Exercise the real materializer with a stub app-server and a recording adapter. Use invented catalog IDs, including a requested model on page two. Assert exact model and advertised effort in argv and manifest. Vary the response to cover a missing pin, incompatible effort and catalog failure with zero dispatches. Then simulate an access denial for an advertised route and assert one attempt with the same identity and no fallback.
4. **Revise and independently review the repair plan before development resumes.** Its mandatory second catalog, its pre-dispatch refusal assertions and the corresponding open development findings reflect the earlier contract. Preserve the historical evidence. Use note 3959 as the authority for the replacement assertions and retain the earlier requirement to record the effective worker route.
