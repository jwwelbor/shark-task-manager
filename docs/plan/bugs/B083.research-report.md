# B083 research report — E40 harness switching and worker outcomes

## Scope

R24 development returned B083 to research because a valid route could finish two structured gates while losing every returned finding. Both E40 routing modes launched the selected model and reported a complete benchmark. The operator therefore could not distinguish a clean review from one whose findings the parent discarded. This revision traces the loss from the provider result to Shark's notes and the benchmark's publication flag. Architect decision 5292 settles which parent operation owns the transition. The earlier investigations below remain the basis for the other R24 coverage rows. [R24 paired scratch evidence](B083.repair-plan-r24-evidence.md#paired-scratch-observations) · [R24 plan](B083.repair-plan-r24.md#coverage-index)

R22 development returned B083 to research after two advertised Codex models reached the intended executable. E40 rejected one successful result while generating a worker ID. It accepted the other result and shortened the model in the dispatch and stage records. Both causes are downstream of catalog selection. The R22 investigation extended the diagnosis to those producers, the readers of their records and the behavior a successor repair must preserve. The benchmark's existing materializer, adapter and lifecycle controller own the repair. [R22 development evidence](B083.repair-plan-r22-evidence.md) · [R22 independent approval](../../review/bugs/b083/plan-review-r22-c60a412b.md)

The original harness switch lost or forwarded the wrong model. The delivered E40 materializer selects from the active CLI catalog. Earlier investigations at `ab7ef3b8` traced a changed effort in keyed dispatch and loss of a successful Codex JSONL result. Owner-directed decision 5055 settled the Copilot fallback. Those findings remain relevant to R22. [R17 evidence](B083.repair-plan-r17-evidence.md)

**Earlier keyed-dispatch investigation.** On the R10 development tree, the real scratch Shark can change a catalog-validated effort between the written workflow and the keyed dispatch. Even with an ordinary lowercase effort, the adapter can turn a successful Codex final message into a worker failure. Both failures reproduced offline in explicit-workflow and selected-profile modes. Development note 4601 returned R10 to research. Findings 4604 and 4607 identify the outbound and return boundaries respectively. [R10 development replay](B083.repair-plan-r10-evidence.md#development-replay-at-the-real-shark-request-boundary)

The **requested route** comes from the workflow or profile. The **effective route** is the provider, model and effort materialized for a stage. The **observed attempt** is the executable, arguments, start count and outcome at the worker boundary. Codex catalog membership establishes an advertised route. Service access can only be observed on an actual attempt. B083 covers E40 from preview through the retained lifecycle outcome. B077 owns native Rider dispatch attestation.

**Finding 5187.** For every recognized control kind, `project_result` chooses the envelope's worker ID, then `LIFECYCLE_WORKER_ID`, then the literal provider, a hyphen and the requested model. It passes the chosen string to `safe_identity`, which requires a nonempty, whitespace-free, nonsensitive token of at most 256 characters. The six characters in `codex-` leave room for 250 model characters. The catalog accepts longer model identifiers. The first rejection is after the successful child exits and before the adapter emits a result. The same projector handles questions and the `openai` alias. An independent question probe failed already at 250 characters with `openai-`; it accepted a short host ID for the long Codex pin, preferred a supplied worker ID over the host ID, and rejected an oversized supplied ID even with a valid host ID present. The generated ID describes a route and carries no independent proof of host identity. [Catalog validation](../../../bench/scripts/lib/codex_model_catalog.py) · [Result and session projection](../../../bench/scripts/lifecycle-worker-adapter.sh#L750) · [Short fallback contract](../../../bench/scripts/tests/tc060_lifecycle_runner_contract_test.sh#L147)

**Finding 5188.** The controller builds the worker request from the original keyed response. Independently it runs the entire response through `bounded`, a generic projection that keeps up to 32 entries and the first 512 characters of each string. It removes the prompt and stores that copy in `dispatches[].response`. The I-07 stage writer then reads its model from that shortened copy. The ordered identity writer reads the original response. Thus two fields lose the same suffix at one producer, while the field used for ordered comparison retains it. The preview stage also reads the original model. The same generic projection can shorten a long effort or omit a later field. The separate bounded worker-usage copy can shorten provider-observed model IDs in lists. Preserve their measurement provenance separately from the selected route. In these Codex runs I-05 reported unmapped usage. [Dispatch projection](../../../bench/scripts/run-lifecycle.sh#L2529) · [Stage usage](../../../bench/scripts/run-lifecycle.sh#L569) · [Ordered identity](../../../bench/scripts/run-lifecycle.sh#L2236) · [Worker usage](../../../bench/scripts/run-lifecycle.sh#L2596)

To isolate model consistency, I used the valid, single-dispatch I-07 fixture and varied only the ordered model from 512 to 513 characters, holding the dispatch and stage model at the shared 512-character prefix.
