# Sprint add and bulk-add can panic or swallow renumber failures

## Description

Full code review on 2026-07-07 found RenumberAssignmentsTx in internal/repository/sprint/repository.go dereferences tx unconditionally while AddEntityToSprint and BulkAddToSprint pass nil, so ordered sprint insertion can panic when shifting rows. The same surface also swallows renumber errors during gap repair with _ = in sprint_service.go. See dev-artifacts/2026-07-07-full-code-review/code-review-report.md sections C1 and M12.

## Expected Behavior

Ordered sprint insertion and bulk-add repair should either execute inside a valid
transaction or use a non-transactional path explicitly, and renumber failures
should be returned to the caller instead of panicking or being dropped.

## Actual Behavior

`RenumberAssignmentsTx` calls `tx.ExecContext` unconditionally. Service paths for
`AddEntityToSprint` and `BulkAddToSprint` pass `nil`, so ordered insertion can
panic. Gap-repair renumbering also ignores returned errors in one service path.

## Steps to Reproduce

1. Create a sprint with existing ordered assignments at or after a target slot.
2. Run `shark sprint add S001 <entity-key> --at 2`.
3. Observe the nil-transaction panic when the service shifts existing rows.

## Fix Notes

Review source points:
- `internal/repository/sprint/repository.go`
- `internal/services/sprint_service.go`
- report sections C1 and M12
