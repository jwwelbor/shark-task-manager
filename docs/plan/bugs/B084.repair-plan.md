# B084 repair plan

Revision 2 addresses the independent review of revision 1. The review confirmed
the diagnosis and baseline and returned the plan to repair planning because a
listed preservation obligation could be checked by an assertion that stayed
green after the protected behavior was lost. The revised assertions require
independent review of this revision. [Revision 1 review](../../review/bugs/b084/plan-review-r1-b7e0f0a2.md)

## Diagnosis

The default bug workflow lets an applicable decision escape verification if the
decision is discoverable through a related-document link or explicit reference and
absent from the repair plan. CC-044 introduced independent plan review, an approved
snapshot, and coverage-based development gates. At the review baseline, the three
worker prompts refer to decisions generally without prescribing lookup and
reconciliation. Development can therefore verify every row in an incomplete plan
and still miss an accepted obligation. Parent admission authenticates the plan and
its approval history. Completeness of the coverage index is a review judgment.

## Proposed repair

1. Define one decision-discovery rule in the existing embedded prompt partials.
   Use it in `bug/repair_plan.md`, `bug/plan_review.md`, and `bug/development.md`.
   Require `shark related-docs list <bug-key> --json` in the rendered parent
   project command context. Follow explicit references in the bug, research, and
   applicable plan even on a successful empty lookup. Resolve paths in the owning
   project and read the required decision briefs and relevant prior findings.
   Determine authority from the source and its approval. Record supersession and
   inapplicability with reasons, and send unresolved conflicts to the authority
   owner. Treat failed lookup or unreadable required evidence as `blocked`.
2. In repair planning, map each applicable constraint to the single coverage index.
   In plan review, repeat source discovery independently and reconcile it with the
   entire index. For each row without an authorized disposition, ask whether its
   assertion would fail if the protected behavior were removed at the named
   caller while adjacent behavior still passed. For preservation constraints,
   compare the expected value or observable behavior at every affected caller.
   Route omissions and assertions that could pass despite a violation to
   `replan`. A complete inventory with no applicable decisions satisfies the
   decision-specific check.
3. In development, reconcile the sources with the parent-supplied approved snapshot
   before accepting any new, existing, or resumed fix. Record verification and
   observed results in the linked evidence record. For any disposition, cite the
   decision owner and their authorization. Require evidence or disposition for
   each applicable constraint alongside the regression, project quality gate, and
   scope check. A new, changed, or omitted constraint requiring a material plan
   update routes to `replan` even when the project gate is green.

This approach reuses the existing keyed read command and the boundary where the
worker interprets decisions. It keeps prompt growth bounded by shared instructions
and leaves document selection with the authorized worker. Automatic document
inclusion would introduce unbounded content and ownership problems. Digest-only
admission cannot establish whether an omitted decision applies. The cost of the
proposed approach is a read and completeness check at each of the three stages.

## Scope and preserved behavior

**Complexity M.** The repair is bounded to prompt content and verification
across the parent project, worker checkout, and approval snapshot.

- Production edits cover the three bug prompts and one shared partial under
  `internal/sharkdata/default_data/prompts/`. Verification covers their three
  rendered goldens and scoped dispatch tests. In `bug/plan_review.md`, require
  the reviewer to reject an assertion that could pass with the protected
  behavior missing at the affected caller. The branch already contains
  implementation commit `f5001d7275085a74d5b3585bb78c252705d19c9f`. Treat it as
  a candidate to verify after independent plan approval and preserve its history.
- The production read path is `related-docs list` → `dispatchListDocs` →
  `BugService.ListRelatedDocumentsByKey`. The dispatch paths are keyed `next` →
  `enrichBugNextPrompt` and in-process `run` → `RunController.handleSpawnAgent`.
  Both use the existing renderer, parent command guidance, and approved-plan
  loader. Preserve stage selection, keyed substitution, exact prompt pass-through,
  and prompt hash semantics. Preserve existing project config, database selection,
  prompt override precedence, and worker `--workdir`.
- Preserve bug workflow statuses, aliases, outcome roles and targets, provider and
  model metadata, skills, defect-class rework, separate code review and QA, and
  parent ownership of leases, result admission and transitions. Preserve existing
  snapshot provenance and the behavior of paths with no applicable decisions.
  The repair changes worker instructions. Its production scope ends at those
  instructions, leaving the CLI, runner, storage, feature policy, WWGM application
  code, and provider execution contracts outside the repair.

## Preservation assertion fixture

Create one linked decision in the disposable project. It requires a single-part,
non-retryable malformed receipt to preserve a known model and cost from its
input. Use a synthetic input with model `fixture-model` and USD 0.12. The intact
receipt reports those values, `failed_content`, and one call. Remove the model,
the cost, and both fields in separate variants. Hold the disposition and call
count constant and keep the chunked sibling receipt intact.

1. Keep the decision link, accounting row, and affected caller identical in the
   two plans. In the first plan, assert only disposition and call count. These
   assertions pass on all four receipts. At the rendered plan-review boundary,
   the required outcome is `replan` because the row cannot detect the loss.
2. In the second plan, also assert the exact model and cost at the single-part
   receipt. The assertions pass on the intact receipt and fail for each field
   loss. The accounting row satisfies plan review. The rest of the coverage index
   still determines whether the plan passes. Inspect the `next` and recording
   dispatcher instruction for this review requirement.
3. In a development walkthrough with the second plan supplied as the approved
   snapshot, use each field-loss receipt as a candidate result. Require `fail`
   for implementation rework even with a green generic gate. Record the failing
   fields and check that the retained snapshot still matches its approved digest.

The exact values are synthetic. WWGM's historical failure supplies the caller
shape and CC-044 supplies the Shark acceptance requirement. Store the decision,
lookup result, plan fragments, captured instructions, assertion outputs, and
observed dispositions in the [mutable evidence record](../../../dev-artifacts/2026-11-17-b084-repair-plan/evidence.md#preservation-assertion-pair).
