# shark run advances blocked gates on worker exit code 0

## Description

When `shark run` dispatches a worker and the worker exits with code 0 while emitting `Verdict: BLOCKED` and `RECOMMENDED OUTCOME: blocked`, the entity is still advanced from its current status to a completed/next status instead of respecting the explicit blocked outcome.

Evidence: CC-045 QA gate produced `qa-20260712-CC-045.md` with explicit blocked verdict, but entity advanced from `qa` to `completed`.

## Root Cause

RunController gated status advancement only on subprocess exit code 0, never parsing the worker's own semantic verdict marker (`RECOMMENDED OUTCOME: <key>` or JSON `{ "outcome": ... }`). The dispatch-and-advance flow ignores the agent's stated outcome and uses a default "pass" routing.

## Related Issue

Related to E34-F05 (structured gate results and parent-owned persistence). B046 and B052 may be fixed in the same sprint with unified outcome handling.

## Investigation Status

See `B046.research-report.md` for detailed analysis. Current implementation includes outcome parsing logic (internal/runner/controller.go:906-915, line 1235) and tests confirm line-based parsing works. Issue may be:
1. Workflow uses legacy configuration (empty Outcomes map)
2. Outcomes map doesn't include "blocked" for that status
3. Agent uses JSON outcome format which isn't parsed
4. Error in outcome lookup isn't surfaced properly

## Fix Notes

Minimum fix:
1. Audit workflow configuration to ensure all non-terminal steps have complete Outcomes maps
2. Add JSON outcome parsing to recommendedOutcome() function
3. Test with RECOMMENDED OUTCOME: blocked to confirm blocking works
