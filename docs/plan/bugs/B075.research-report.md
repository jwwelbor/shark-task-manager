# B075 research report

## Scope

B075 covers the lease lifetime between a long-running workflow worker and the
later `shark run --apply-result` call. The research includes claim TTL and
heartbeat renewal, the adapter-facing result-application contract, the shared
gate-result persistence coordinator, and the zero-write authorization boundary.
It does not authorize applying a result under an expired or reissued session,
changing the claim store, or disabling TTL globally as a workaround.

Vocabulary used here:

- **claim/session lease**: the entity-scoped authorization held by the parent
  while work is in flight.
- **lease heartbeat**: `ClaimService.Heartbeat`, which renews the claim for a
  specific entity and session.
- **apply-result**: the adapter-facing `shark run <key> --apply-result ...`
  ingestion path.
- **result envelope**: the worker's structured `gate_result_v1` response that
  the shared ingestion boundary validates and persists.

## Findings

1. The reported failure reproduces at the existing authorization boundary.
   `TestVerifyClaimSession_ExpiredClaimRejected` supplies a matching session
   whose last heartbeat is one hour old against a one-minute TTL and proves
   that authorization fails with an expiry error. The same test file proves a
   live matching session is accepted. The targeted command tests passed on
   2026-09-21:
   `go test ./internal/cli/commands -run
   'TestVerifyClaimSession_ExpiredClaimRejected|TestRunApplyResult_MismatchedSessionProducesZeroWrites|TestRunApplyResult_NoActiveClaimProducesZeroWrites|TestRunApplyResult_OversizedEnvelopeFileRejectedAfterAuthorization' -count=1`.

2. `runApplyResult` checks the session before opening the envelope file,
   constructing the coordinator, or invoking shared ingestion. An expired,
   missing, or mismatched session therefore fails closed before any notes,
   kickbacks, or workflow transition can be written. This is intentional
   ownership enforcement, not an accidental parser failure.

3. The normal in-process `shark run` path already renews its acquired lease.
   `acquireRunLease` starts `startRunHeartbeat`, whose ticker runs at one-third
   of the configured TTL (with a one-second floor), and `activeRunLease.Release`
   stops and joins that goroutine before session-scoped release. The
   `--apply-result` path short-circuits before that acquisition path and is a
   separate one-shot entry point, so an external adapter can retain the
   original session without any built-in renewal between worker start and
   result application.

4. Claim renewal is already a narrow, session-safe capability. The service
   delegates to repository `Renew`, which updates `last_heartbeat` only for
   the exact entity/session pair; a missing row or failed update returns an
   error. The default TTL is 15 minutes, and stale rows are reclaimable by the
   repository's crash-recovery sweep. A heartbeat failure therefore must be
   treated as loss of authorization, not as a warning that permits applying
   the worker's result.

5. The shared gate persistence coordinator closes the second authorization
   window. `buildGateCoordinator` wires the claim service as `ClaimVerifier`,
   and `Coordinator.Persist` re-checks the session after acquiring the per-run
   lock and before `CreateResult`, note/kickback writes, or the guarded
   transition. The coordinator regression tests prove that an expired claim or
   a session reclaimed by another caller produces zero writes, including when
   the initial CLI check had observed a live session. The targeted
   `internal/gatepersist` tests passed on 2026-09-21.

6. The adapter contract currently requires the session to be the active lease
   at application time and documents `--resume-run` as using the same
   authorization boundary. This preserves parent ownership and replay safety,
   but it leaves a lifecycle gap for external workers whose execution time
   can exceed the TTL. The documented “re-claim immediately before applying”
   workaround changes the session and can be unsafe if the original worker's
   result races with a different claimant; it should remain an explicit
   recovery action, not an automatic stale-result exemption.

7. The E40 liveness recorder's ten-second `heartbeat` events are an
   observability stream and are explicitly separate from lease renewal. They
   do not call `ClaimService.Heartbeat`; wiring or naming them as the lease
   supervisor would create a false guarantee. The existing run heartbeat and
   liveness recorder should remain separate responsibilities.

## Decisions

1. Repair B075 by extending the existing claim-heartbeat capability to the
   external adapter lifecycle. The parent/adapter that owns the active session
   should start a bounded renewal loop when long-running work begins, renew at
   a cadence safely below the configured TTL, stop it before final result
   application, and surface any renewal failure as a lost lease. A result must
   not be applied after that failure unless an explicitly authorized recovery
   path establishes a new session and its provenance policy permits the handoff.

2. Keep both current authorization checks. The initial CLI check prevents
   unauthorized file reads and work, while the coordinator re-check prevents a
   claim expiry or force-reclaim between authorization and persistence. Do not
   weaken either check to accept a non-empty, expired, or previously valid
   session.

3. Treat this as an extension of an existing workflow/lease capability, not
   new result storage or a new transition mechanism. The normal `shark run`
   heartbeat loop, `ClaimService.Heartbeat`, and shared gate coordinator are
   the implementation precedents.

4. Alternatives considered: re-claiming immediately before application is a
   manual recovery workaround with stale-result and ownership ambiguity;
   accepting an expired session during a grace period contradicts the
   fail-closed authorization and TOCTOU protections; setting TTL to zero
   removes crash-recovery semantics for every caller. None is the primary
   repair.

5. Add regression coverage for the external lifecycle: a long-running
   adapter renews successfully, a renewal failure stops result application,
   an expiry/reclaim between heartbeat and persistence remains zero-write, and
   a terminal result still releases the current session exactly once.
