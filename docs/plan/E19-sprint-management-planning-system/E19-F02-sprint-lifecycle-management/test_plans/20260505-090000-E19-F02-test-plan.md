## Part 3: ISTQB Test Design Techniques (Per AC)

### AC-1: Sprint Creation (REQ-F-001)

**Techniques Applied:**
- **Equivalence Partitioning** — Valid dates vs invalid date ranges (start ≥ end)
- **Boundary Value Analysis** — Date boundaries (same day, 1 day apart, long sprint)
- **Decision Table** — Presence/absence of optional --goal flag

**Test Cases Generated:** TC-001 through TC-009

**Rationale:**
- Date ranges form two equivalence classes: start < end (valid) and start ≥ end (invalid)
- BVA covers: start = end (boundary), start > end (invalid), 1 day apart (minimum), 365+ days (long sprint)
- Two conditions (has --goal, has --json) produce 4 combinations

### AC-2: Sprint Read - Get (REQ-F-002)

**Techniques Applied:**
- **Equivalence Partitioning** — Existing sprint key vs non-existent key
- **Contract Surface Enumeration** — Output field completeness (key, name, status, dates, goal, timestamps)

**Test Cases Generated:** TC-010 through TC-015

**Rationale:**
- GetByKey has two partitions: found vs not-found
- Response structure has 8 required fields; test must verify all are present and correctly populated
- JSON vs human output are separate partitions

### AC-3: Sprint Read - List (REQ-F-002)

**Techniques Applied:**
- **Equivalence Partitioning** — No sprints, single sprint, multiple sprints with filtering
- **Decision Table** — Status filter combinations (all statuses, single status, multiple statuses)

**Test Cases Generated:** TC-016 through TC-023

**Rationale:**
- List has three volume partitions (empty, single, multiple)
- Status filter creates independent decision tree; each status value is a partition
- JSON output must be array; human output must be table

### AC-4: Sprint Update (REQ-F-003)

**Techniques Applied:**
- **Equivalence Partitioning** — Valid updates vs invalid (end date before start)
- **Boundary Value Analysis** — Date boundaries when changing end_date
- **Decision Table** — Update combinations (name only, goal only, date only, multiple fields)

**Test Cases Generated:** TC-024 through TC-033

**Rationale:**
- Update has validation boundary: new end_date must remain > current start_date
- Multiple optional fields create 2^3 combinations; decision table ensures no combination is overlooked
- Some combinations are invalid (changing end to before start); must be tested explicitly

### AC-5: Sprint Delete (REQ-F-003)

**Techniques Applied:**
- **State Transition** — Delete only valid in planning status; invalid from active, closing, completed, archived
- **Equivalence Partitioning** — Planning status vs non-planning

**Test Cases Generated:** TC-034 through TC-040

**Rationale:**
- Delete is a constraint-gated operation; state transition technique ensures all invalid states are tested
- Each of 6 sprint statuses should be tested (planning allowed, 5 others forbidden)
- Equivalence partition: deletable (planning) vs protected (all others)

### AC-6: Sprint Status Transitions (REQ-F-004)

**Techniques Applied:**
- **State Transition** — Every legal transition and every illegal transition
- **Boundary Value Analysis** — State transition timing (immediate, with delay, concurrent)
- **Decision Table** — Constraint combinations (one active sprint exists, attempt to activate another)

**Test Cases Generated:** TC-041 through TC-065

**Rationale:**
- State machine has 6 states and 9 edges (planning→active, active→closing, closing→completed, completed→archived, multiple→cancelled, any→archived, etc.)
- Test coverage: all 9 valid transitions + tests for all invalid pairs
- One-active-sprint constraint requires decision table: (sprint_A_active, attempting_B_active) → error

### AC-7: Performance (REQ-NF-001)

**Techniques Applied:**
- **Boundary Value Analysis** — Operation latency at scale (1 sprint, 100 sprints, 1000 sprints)

**Test Cases Generated:** TC-066 through TC-070

**Rationale:**
- Performance is testable via latency assertion; <100ms CRUD, <200ms list
- Scale boundary: typical (10-50 sprints), high (100-500), extreme (1000+)

### AC-8: Consistency & Atomicity (REQ-NF-002)

**Techniques Applied:**
- **State Transition** — Verify transitions are atomic (no partial states visible)
- **Attack-class Enumeration** — Concurrent activation attempts, parallel status updates

**Test Cases Generated:** TC-071 through TC-076

**Rationale:**
- Atomicity requires concurrent access testing; attack classes: race condition on status update, dual activation
- One-active-sprint constraint must survive concurrent attempts (tested via transaction isolation)

## Part 6: Caller-Path Contracts (Per Test Case)

This section specifies the production caller signature each test must drive and the lowest-allowed mock seam, ensuring tests exercise the contract that production code actually uses.

### Contract for TC-001 (Create with valid dates)

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.CreateSprint(ctx context.Context, input CreateSprintInput)` where `CreateSprintInput{Name, Goal, StartDate, EndDate}` (no optional ID or key)
- **Lowest allowed mock seam:** `SprintRepository.Create()` — the test must instantiate a real SprintService and call CreateSprint; may mock the repository at the CRUD boundary
- **Forbidden mocks:** Do NOT mock `SprintService.CreateSprint` itself; the test must exercise the service's validation logic. Do NOT mock `workflow.Service` — must call the real workflow service to get default status.
- **Counter-factual:** Against an impl that skips date validation, a test with start_date > end_date would succeed when it should fail with a validation error.

### Contract for TC-010 (Get existing sprint)

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.GetSprint(ctx context.Context, key string)` (no ID variant)
- **Lowest allowed mock seam:** `SprintRepository.GetByKey()` — may mock the repository
- **Forbidden mocks:** Do NOT call `SprintService.GetSprintByID()` if it exists (that's the helper); production code calls GetByKey. Do NOT mock key normalization (case-insensitive lookup).
- **Counter-factual:** Against an impl that returns nil on not-found without error wrapping, a test for missing key would pass (nil) when it should fail with NotFoundError.

### Contract for TC-016 (List with status filter)

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.ListSprints(ctx context.Context, filters *SprintListFilters)` where `SprintListFilters{Status: "active", ...}` (filters is pointer)
- **Lowest allowed mock seam:** `SprintRepository.List()` — may mock the repository
- **Forbidden mocks:** Do NOT call a helper like `ListSprintsByStatus()` if it exists; production uses the generic List(filters). Do NOT mock the filter parsing logic.
- **Counter-factual:** Against an impl that ignores the status filter, ListSprints(..., {Status: "active"}) would return all sprints when it should return only active ones.

### Contract for TC-024 (Update name and goal)

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.UpdateSprint(ctx context.Context, key string, updates UpdateSprintInput)` where `UpdateSprintInput{Name, Goal, EndDate}` (nil fields mean no change)
- **Lowest allowed mock seam:** `SprintRepository.Update()` — may mock the repository
- **Forbidden mocks:** Do NOT mock `GetSprint()` as a helper within UpdateSprint; the test must call UpdateSprint and let it call GetSprint internally (or GetSprint is already tested separately). Do NOT skip validation of new dates.
- **Counter-factual:** Against an impl that updates fields unconditionally without checking nil, UpdateSprint(..., {Name: nil, Goal: "new"}) would clear the name when it should leave it unchanged.

### Contract for TC-034 (Delete in planning status)

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.DeleteSprint(ctx context.Context, key string)` (no cascading-aware variants)
- **Lowest allowed mock seam:** `SprintRepository.Delete()` — may mock the repository
- **Forbidden mocks:** Do NOT mock `GetSprint()` inside DeleteSprint; must call the real GetSprint to trigger status validation. Do NOT skip the status check.
- **Counter-factual:** Against an impl that deletes regardless of status, DeleteSprint(..., S024_active) would succeed when it should fail with a validation error.

### Contract for TC-041 (Start sprint, planning → active)

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.StartSprint(ctx context.Context, key string)` (no ID variant)
- **Lowest allowed mock seam:** `SprintRepository.UpdateStatus()` — may mock the repository
- **Forbidden mocks:** Do NOT mock `workflow.Service.ValidateTransition()`; must call the real workflow service. Do NOT call a private helper like `_checkSingleActiveSprint()`; must verify the constraint check is wired into StartSprint's public logic. Do NOT mock GetSprint(); the test must exercise the real GetSprint call within StartSprint.
- **Counter-factual:** Against an impl that skips the one-active-sprint check, StartSprint(S025) while S024 is active would succeed when it should fail with a constraint error.

### Contract for TC-051 (Transition atomicity)

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.StartSprint(ctx context.Context, key string)` — must call the public StartSprint, not a lower-level UpdateStatus
- **Lowest allowed mock seam:** Database transaction boundary — may NOT mock `SprintRepository` at the method level; must exercise the real repository and real DB transaction semantics
- **Forbidden mocks:** Do NOT mock the transaction; atomicity is only testable with real DB transactions. Do NOT mock the status update itself.
- **Counter-factual:** Against an impl that performs GetSprint, validates, and UpdateStatus without a transaction, a concurrent call to StartSprint on the same sprint would see a race condition (both might see status = planning and both transition).

### Contract for TC-062 (Constraint violation: dual activation)

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.StartSprint(ctx context.Context, key string)` called on two sprints concurrently
- **Lowest allowed mock seam:** Database constraint enforcement — may NOT mock the constraint; must verify the DB partial unique index or CHECK constraint actually prevents dual active sprints
- **Forbidden mocks:** Do NOT mock the constraint check in the service; it must actually hit the database and get rejected. Do NOT call a helper mock that simulates "is another sprint active?"; must let the real query run.
- **Counter-factual:** Against an impl that checks for other active sprints in-memory and skips the DB constraint, a race condition where both threads see no other active and both insert status=active would succeed when one should fail.
