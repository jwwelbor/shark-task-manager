# Service: ReorderAssignment and four-tier GetNextTask sort with selection_reason

## Goal
Add `SprintService.ReorderAssignment` (with `ReorderTarget` struct) that computes a
dense-renumber plan and applies it inside a service-owned transaction. Replace the
`GetNextTask` sort comparator with the four-tier stable sort (`sprint_order →
ExecutionOrder → priority → assigned_at`) using `sort.SliceStable`. Add the private
`selectionReason` helper and populate `SprintOrder`, `SprintKey`, `SelectionReason`
on the returned `BacklogItemView`.

## Scope
- Files to modify:
  - `internal/services/sprint_service.go` — add `ReorderTarget` type, add
    `ReorderAssignment` method, replace `GetNextTask` comparator with stable
    four-tier sort, add `selectionReason` private helper, populate new
    `BacklogItemView` fields
- Files to create/extend:
  - `internal/services/sprint_service_test.go` — tests for TC-001 through TC-004
    (GetNextTask sort) and TC-013 through TC-016 (ReorderAssignment) using
    `MockSprintRepository`

## Acceptance Criteria
See spec.md §1.3 REQ-F-001 and REQ-F-003 ACs, §3.2 `ReorderAssignment` signature,
§3.4 sort algorithm pseudocode.
Additional task-specific criteria:
- AC-T1: `sort.SliceStable` used (not `sort.Slice`) — `sort.Slice` is a regression
- AC-T2: `selectionReason` returns `"assigned_at"` for single-candidate case
  (no index-out-of-bounds on `candidates[1]`)
- AC-T3: `ReorderAssignment` with entity not in sprint returns error
  `"entity %q is not assigned to sprint %s"`
- AC-T4: Entity-level repo methods (`TaskService.Update` etc.) NOT called by
  `ReorderAssignment` (REQ-F-008)
