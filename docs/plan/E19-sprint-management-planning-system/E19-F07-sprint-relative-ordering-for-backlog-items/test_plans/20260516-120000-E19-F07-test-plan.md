## Acceptance Criteria Review

### Ambiguity Findings

**REQ-F-001 "stable comparator"**: The spec correctly identifies `sort.Slice` → `sort.SliceStable` as the required change. The AC says "comparator is stable (insertion order preserved)". This is testable: create two candidates with identical sort keys, assert the one inserted first (lower `id`) is always returned first across multiple calls. TC-003 handles this.

**REQ-F-002 `--at=N where N == count+1`**: The AC says this "is equivalent to no flag (append)". The test must confirm no error is returned and the item lands at position `count+1`, not that a "no flag" code path is taken. TC-006 handles this boundary.

**REQ-F-004 `selection_reason` defaults to `"assigned_at"`**: The spec says "when there is only one candidate". The test must verify the single-candidate case returns `"assigned_at"` even when `sprint_order` is the sort key that would have selected it. TC-016 handles this.

**REQ-F-005 `position` vs `sprint_order` in JSON**: The spec distinguishes: `position` is the 1-based dense rank computed at view time; `sprint_order` is the raw stored value. When unordered items are present, `position` and `sprint_order` diverge. TC-019 verifies this distinction.

**REQ-F-009 warning omitted in `--json` mode**: Confirmed — CLI contract states the JSON payload is unchanged. TC-024 must assert that `shark sprint start <key> --json` output does NOT contain a `warning` field (or equivalent) when NULL orders exist.

### Missing Coverage

None identified. All feature.md ACs trace to spec REQ-F requirements, all of which have explicit acceptance criteria in the spec.

## Acceptance Test Cases

### REQ-F-001: Sort Precedence in `GetNextTask`

---

#### TC-001: sprint_order takes precedence over ExecutionOrder

**Feature Requirement:** REQ-F-001 — sort precedence: sprint_order ASC NULLS LAST, then ExecutionOrder, priority, assigned_at.
**Task Acceptance Criterion:** "An item with a lower sprint_order is selected over an item with lower ExecutionOrder when both are present."
**Technique Applied:** Decision Table — four sort tiers, one condition active (sprint_order set on one candidate, ExecutionOrder set on the other).
**ISO 25010 Characteristic(s):** Functional Suitability.

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.GetNextTask(ctx context.Context, agentType string)` — agentType="" (no filter); this is how the production CLI calls the service.
- **Lowest allowed mock seam:** `MockSprintRepository.ListBacklog` — returns a fixed candidate list. The sort comparator and candidate-selection logic must run for real inside the service.
- **Forbidden mocks:** Do NOT mock the sort comparator. Do NOT call `GetNextTask(ctx, "")` via the CLI handler; call the service method directly.
- **Counter-factual:** A buggy impl that uses the old sort order (ExecutionOrder first) would return the item with ExecutionOrder=1 instead of the item with sprint_order=1; the assertion `result.Key == "E07-F01-002"` would fail.

**Preconditions:**
- Active sprint S001 with two candidates:
  - Item A: key=`E07-F01-001`, sprint_order=nil, ExecutionOrder=1, priority=5, assigned_at=T-10m (older)
  - Item B: key=`E07-F01-002`, sprint_order=1, ExecutionOrder=nil, priority=5, assigned_at=T-5m

**Input:** `GetNextTask(ctx, "")`

**Expected Output:**
- Returns `BacklogItemView` with `Key="E07-F01-002"` (sprint_order=1 wins over ExecutionOrder=1 on item A)

**Observability Evidence:** `DEBUG sprint.next.selection reason=sprint_order` logged.

**Edge Cases:**
- Both items have sprint_order set: winner is the lower sprint_order value.
- Item A has sprint_order=2, Item B has sprint_order=1: returns Item B.

**Negative Cases:**
- Agent filter excludes Item B: Item A is returned (sprint_order filter does not apply when the candidate is filtered out by agent type before sorting).

#### TC-002: ExecutionOrder falls back when sprint_order ties (both nil)

**Feature Requirement:** REQ-F-001 — tier 2: ExecutionOrder ASC NULLS LAST.
**Task Acceptance Criterion:** Sort falls back to ExecutionOrder when sprint_order is equal (both nil counts as a tie).
**Technique Applied:** Decision Table — sprint_order tier is a tie; ExecutionOrder tier breaks it.
**ISO 25010 Characteristic(s):** Functional Suitability.

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.GetNextTask(ctx, "")`
- **Lowest allowed mock seam:** `MockSprintRepository.ListBacklog`
- **Forbidden mocks:** Same as TC-001.
- **Counter-factual:** A buggy impl that skips tier 2 and falls straight to priority would return Item C (priority=1) instead of Item A (ExecutionOrder=1, priority=5).

**Preconditions:**
- Item A: sprint_order=nil, ExecutionOrder=1, priority=5
- Item B: sprint_order=nil, ExecutionOrder=nil, priority=1 (lower number = higher priority)
- Item C: sprint_order=nil, ExecutionOrder=2, priority=1

**Input:** `GetNextTask(ctx, "")`

**Expected Output:** Item A returned (ExecutionOrder=1 beats ExecutionOrder=nil and ExecutionOrder=2).

**Edge Cases:**
- All three tiers tie: oldest assigned_at wins (TC-002c below).
  - TC-002c: A: priority=1, assigned_at=T-10m; B: priority=1, assigned_at=T-5m → returns A.

**Negative Cases:** N/A (this is purely a sort correctness test; the empty-candidates case is covered by GetNextTask returning nil).

#### TC-003: Stable sort — identical keys always return same item

**Feature Requirement:** REQ-F-001 — "comparator is stable (insertion order preserved by sort.SliceStable)".
**Task Acceptance Criterion:** "When two candidates tie on every factor, the comparator is stable."
**Technique Applied:** State Transition — same inputs, same system state must produce same output across multiple invocations.
**ISO 25010 Characteristic(s):** Functional Suitability, Reliability (determinism).

**Caller-Path Contract:**
- **Entrypoint:** `SprintService.GetNextTask(ctx, "")` called 10 times in sequence.
- **Lowest allowed mock seam:** `MockSprintRepository.ListBacklog` — returns the same list in the same order each call.
- **Forbidden mocks:** Do NOT shuffle the mock's return slice between calls. The sort must be the source of any permutation.
- **Counter-factual:** A `sort.Slice` (unstable) impl would permute equal-key candidates on successive calls when the underlying slice order changes; the assertion `results[i].Key == results[0].Key for all i` would eventually fail.

**Preconditions:**
- Items A and B: sprint_order=nil, ExecutionOrder=nil, priority=5, assigned_at=same time. Item A has lower DB id (inserted first).

**Input:** `GetNextTask(ctx, "")` called 10 times.

**Expected Output:** All 10 calls return the same item (the one with lower DB insertion ID, matching `sort.SliceStable`'s tie-breaking by original slice position).

**Edge Cases:** Same setup with N=5 candidates all tied on every key — assert same item returned each call.

**Negative Cases:** N/A.

**Feature Requirement:** REQ-F-001 — "The agent-type filter still applies before sorting."
**Task Acceptance Criterion:** Items excluded by agent filter do not compete in the sort.
**Technique Applied:** Decision Table — agent filter active × sprint_order present on excluded item.
**ISO 25010 Characteristic(s):** Functional Suitability.

**Caller-Path Contract:**
