## Blockers

### B1 — `runBugList` not implemented

The list command is a core CRUD operation. It is entirely absent from the file. No handler function, no Cobra command variable, no flag declarations for `--status`, `--severity`, `--link`, `--epic`, `--feature`.

Acceptance criteria: "runBugList handler calls svc.ListBugs(ctx, BugFilters{...}) and renders a table"
Status: NOT MET

### B2 — `runBugUpdate` not implemented

The update command is entirely absent. No handler function for `--title`, `--description`, `--severity` flags.

Acceptance criteria: "runBugUpdate calls svc.UpdateBug(ctx, key, BugUpdates{...})"
Status: NOT MET

### B3 — Wrong flag names in `runBugCreate`

**Spec (PRD `prd.md` and API contracts `03-api-contracts.md`):** Single `--link` flag, value format `entity-type:entity-key` (e.g., `--link task:E18-F04-001`)

**Actual implementation:**
```go
linkedType, _ := cmd.Flags().GetString("linked-type")
linkedKey, _ := cmd.Flags().GetString("linked-key")
```

The implementation uses two separate flags `--linked-type` and `--linked-key` instead of the single `--link` flag. This diverges from the API contract and would produce a different CLI interface than documented.

The `CreateBugInput` DTO uses `LinkedEntityType` and `LinkedEntityKey` as separate fields, which is the service-level representation. The CLI layer is responsible for accepting the human-friendly `--link entity-type:entity-key` format and splitting it before calling the service.

### B4 — DTO field name mismatch in create handler

The spec defines `CreateBugInput` with field `LinkKey string`. The actual service DTO uses `LinkedEntityType string` and `LinkedEntityKey string`. The handler maps directly to the actual service fields, which is acceptable at the service boundary, but the CLI must accept `--link` and split it into those fields.

The current code passes `LinkedEntityType` and `LinkedEntityKey` directly without any `--link` parsing logic.

### B5 — Missing confirmation prompt in `runBugDelete`

The delete handler calls `svc.DeleteBug(ctx, key)` immediately without asking the user to confirm. The spec and API contracts (`03-api-contracts.md`) require:

```
Are you sure you want to delete bug B001? (y/N):
```

The handler must:
1. Print the confirmation prompt
2. Read stdin input
3. Abort if anything other than "y" or "yes" is entered
4. Proceed with deletion only on confirmation

The `confirmBugDelete` helper function referenced in the API contracts must be implemented.

### B6 — `runBugCreate` hardcodes default severity in CLI

```go
severity, _ := cmd.Flags().GetString("severity")
if severity == "" {
    severity = "medium"
}
```

Default values belong in the service layer, not the CLI. The CLI should pass the empty string (or omit the field) and let `BugService.CreateBug` apply the default severity. Hardcoding "medium" in the CLI bypasses service validation and couples presentation to business logic.

### B7 — Error wrapping adds redundant context in get handler

```go
return fmt.Errorf("bug %s not found: %w", key, err)
```

The `NotFoundError` already contains the entity key in its message. Double-wrapping with the key adds noise: "bug B001 not found: bug not found: B001". The command layer should check the error type and map to an exit code, not re-wrap with redundant information. Follow the exit code pattern from `error-handling.md`.

## Minor Issues

### M1 — `renderBugDetails` prints to stdout but does not check `cli.GlobalConfig.JSON`

The helper `renderBugDetails` always prints human-readable output. It should check `cli.GlobalConfig.JSON` and call `cli.OutputJSON(bug)` when in JSON mode, matching the pattern in all other command files.

### M2 — Unused `time` import

The file imports `"time"` but it is only used in `renderBugDetails` via `bug.ReportedAt.Format(time.RFC3339)`. This is technically used but worth noting that if `renderBugDetails` is extracted to a proper JSON-aware function, this import may change.

### M3 — `context` import unnecessary

The `"context"` package is imported but the handlers use `cmd.Context()` directly. The import is unused and will cause a lint error once commands are wired up properly.
