# Task: Fix 4 Dispatch Gaps for C### Keys

## Overview

During the dispatch inventory verification performed in T-E18-F06-006, four dispatch points were found that handle the legacy `CC-###` key format (`"change_card"` entity type string) but are missing a `case "change":` branch for the current short-form `C###` key format (`"change"` entity type string). When a user runs `shark delete C001`, `shark status set C001 approved`, `shark status advance C001`, or `shark status options C001`, the command falls through to the default error branch and returns `"unsupported entity type: change"`.

This task adds the four missing `case "change":` branches so that C### keys are fully supported in all four dispatch points. The fix in each case mirrors the existing `case "change_card":` branch, because C### keys and CC-### keys both refer to records in the `change_cards` database table and are served by the same `ChangeCardService`.

---

## Problem Statement

The key detection system correctly resolves C### keys:

- `ParseGetArgs([]string{"C001"})` returns `entityType = "change"`, `key = "C001"`.
- `DetectEntityType("C001")` returns `"change"`.

However, four switch statements still only enumerate `"change_card"` (the CC-### format) and not `"change"`:

| Gap ID | File | Function | Missing case |
|--------|------|----------|--------------|
| GAP-001 | `internal/cli/commands/delete_dispatch.go` | `runDelete()` switch | `case "change":` |
| GAP-002 | `internal/cli/commands/status_group.go` | `dispatchTransition()` | `case "change":` |
| GAP-003 | `internal/cli/commands/status_group.go` | `dispatchNextStatus()` | `case "change":` |
| GAP-004 | `internal/cli/commands/status_group.go` | `dispatchAdvance()` | `case "change":` |

These gaps were documented in `e18_dispatch_gaps_test.go` by `TestGAP001_DeleteDispatch_ChangeEntityTypeFallsThrough` and `TestGAP002_StatusGroup_ChangeEntityTypeFallsThrough`.

---

## Business Context

This task directly implements requirements from the F06 feature PRD:

- **F06-REQ-006**: All `shark status` subcommands (advance, set, options, history) must dispatch to change-card workflow services for C### keys.
- **F06-REQ-007**: The `shark delete` command must dispatch to the change-card service for C### keys.
- **F06-REQ-NF-004**: Every entity-type dispatch point must handle bugs and change-cards. No dispatch point may silently fall through to a default case.

As a developer using `shark delete` to remove a change card,
I want `shark delete C001` to delete the change card with key C001,
so that I can manage change card records using the same key format recognized everywhere else in the CLI.

## Business Rules

**BR-001: C### and CC-### map to the same service**
Both `"change"` (C### format) and `"change_card"` (CC-### format) resolve to the same `ChangeCardService`. There is no separate service, repository, or database table for C### vs CC-### keys. The entity type string differs based on input key format, but all calls go to `cli.GetChangeCardService()`.

**BR-002: Entity type string in output matches input key format**
When a C### key is used, the `EntityType` field in `TransitionResult` and `NextStatusInfo` must be `"change"`, not `"change_card"`. This ensures output is consistent with how the key was entered, matching the F06-REQ-NF-001 output consistency requirement.

**BR-003: No silent fallthrough**
No dispatch function may silently fall through to a default case that produces incorrect or confusing behavior. Every default case that currently returns "unsupported entity type: %s" must be reached only when an unrecognized entity type is passed, which C### keys must not trigger after this fix.

**BR-004: Fix applies only to missing `"change"` cases**
This task scope is limited to adding `case "change":` branches. It does not modify the existing `case "change_card":` branches. Both cases must remain in the switch statements after the fix.

**BR-005: No new service methods required**
The fix delegates to existing `ChangeCardService` methods already used by the `"change_card"` cases. No new service methods, repository methods, or database queries are introduced by this task.

## Edge Cases

**EC-001: Mixed-case C### keys**
- `c001` and `C001` both resolve to entity type `"change"` via `DetectEntityType()` (case-insensitive).
- After normalization, the key passed to `ChangeCardService` is the uppercased form `"C001"`.
- The ChangeCardService must already accept `"C001"` as a valid key (since the same service handles CC-### keys via the existing case). Verify this at integration time.

**EC-002: C0 and single-digit C### keys**
- `C0`, `C1` are valid key patterns (one or more digits after C).
- These should route through the `"change"` case and be handled by `ChangeCardService`.
- The ChangeCardService `GetByKey` method determines whether such a key exists; if not, it returns a not-found error.

**EC-003: `--force` flag in delete**
- `shark delete C001 --force` must propagate the `--force` flag through to `runChangeCardDelete` exactly as `shark delete CC-001 --force` does.
- No special handling of `--force` is needed in the dispatch switch itself.

**EC-004: Error message in default branch**
- The `default:` case in `runDelete()` currently shows `"CC-###"` in the format hint. After adding `case "change":`, the default error message must include `C###` in the valid formats list.
- Current message: `"Expected format: E## (epic), E##-F## (feature), E##-F##-### (task), B### (bug), or CC-### (change-card)"`
- Updated message: `"Expected format: E## (epic), E##-F## (feature), E##-F##-### (task), B### (bug), C### (change card), or CC-### (change card)"`

**EC-005: `dispatchAdvance` fallthrough behavior**
- `dispatchAdvance()` uses `default: return nil, nil` to signal "fall through to generic path" for epic/feature/task. This behavior must not change. Only the `"change"` case is added; the default remains `return nil, nil`.
- The added `case "change":` must return `(result, nil)` or `(nil, err)` — never `(nil, nil)`.

### Architecture Decisions

**ADR-T007-001: EntityType string in output must match input key format**

The `"change_card"` cases set `EntityType: "change_card"`. The new `"change"` cases must set `EntityType: "change"` — not `"change_card"`. This is mandated by BR-002 and ADR-F06-003 from the feature architecture. The entity type in the output must reflect how the key was entered.

**ADR-T007-002: No new service methods needed**

The `"change"` cases call the identical service methods as the `"change_card"` cases:
- `cli.GetChangeCardService().SetChangeCardStatus(ctx, key, targetStatus)`
- `cli.GetChangeCardService().GetChangeCard(ctx, key)`
- `cli.GetChangeCardService().AdvanceChangeCardStatus(ctx, key)`

This is correct because both `"change"` (C### format) and `"change_card"` (CC-### format) refer to records in the `change_cards` table and are served by the same `ChangeCardService`. No new service methods, repository changes, or database queries are introduced.

**ADR-T007-003: SetChangeCardStatus does not accept opts.Force**

The `dispatchTransition` bug case passes `opts.Force` to `SetBugStatus`. The change_card case does not pass `opts.Force` to `SetChangeCardStatus` (the method signature does not accept it). The new `"change"` case must match `"change_card"` and omit `opts.Force`. This is a difference between bug and change-card services — do not copy the bug case pattern for this parameter.

**ADR-T007-004: Test file naming correction for GAP-004**

The gap test constant at line 251 says `"GAP-004: status_group.go dispatchOptions missing case \"change\""`. The function name in the source is `dispatchAdvance()`, not `dispatchOptions()`. The test update for GAP-004 must reference `dispatchAdvance()` in any comments or log messages to be accurate. The `TestDispatchInventory_FullStatus` inventory row for `"#4"` references `"status_group.go dispatchTransition()"` as GAP and does not have a separate row for `dispatchAdvance` — see the inventory table and update accordingly.
