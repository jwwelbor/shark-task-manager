## Code Quality Assessment

### Correctness
The dispatch logic is sound. Each entity type routes to the correct service method. The `dispatchAdvance` function for bug/change_card correctly short-circuits before the generic info-based advance path that applies to epic/feature/task. The idempotency check in `runStatusSet` calls `dispatchNextStatus` first to read current status, which now works for all five entity types.

### Consistency with Existing Patterns
All new code follows established patterns:
- Service accessors in `services_global.go` follow the same structure as existing task/feature/epic accessors.
- Dispatch switch cases are consistent with the existing epic/feature/task pattern.
- `toModelEntityType()` in `context.go` correctly mirrors how other entity type conversions are handled.

### Principle of Least Surprise
The combined `"change", "change_card"` case in `update_dispatch.go` and `"change_card", "change"` in `context.go` follows a reasonable aliasing pattern. The key "CC-###" will be detected as "change_card" by the key parser, and the combined case handles both internal string representations cleanly.

### Minor Observations (Non-Blocking)
1. `dispatchNextStatus()` for "bug" and "change_card" returns `AvailableTransitions: nil`. This means `shark status transitions B001` will show no transitions but will not error. This is acceptable given these entities use their own workflow service paths. A future enhancement could populate the available transitions list.
2. `status_group.go` `dispatchTransition` for "change_card" does not propagate `opts.Force` or `opts.Reason` to `SetChangeCardStatus`. The service signature takes only `(ctx, key, targetStatus)`. If force/reason are needed in future, that would be a service-layer change, not a command-layer issue.
3. The `delete_dispatch.go` command `Short` description (line 11) already says "bug, or change-card" - consistent with the new entity types.

None of these observations are blocking issues.
