# Task: Optimize AdvanceStatus triple-GetByKey efficiency

## Goal

Reduce the 2-3 redundant `GetByKey` database queries per `AdvanceStatus` and `SetStatus` call in BugService and ChangeCardService. Currently every `shark status advance B001` does 3 SELECT queries when 1 would suffice.

## Problem

The delegation to `EntityService.TransitionStatus` introduced redundant round-trips:

### AdvanceBugStatus flow (3 SELECTs):
1. `GetNextStatus` -> `repo.GetByKey(key)` to determine current status
2. `SetBugStatus` -> `EntityService.TransitionStatus` -> `repo.GetByKey(key)` again for validation
3. `SetBugStatus` -> `repo.GetByKey(key)` a third time to re-fetch the typed model

### SetBugStatus flow (2 SELECTs):
1. `EntityService.TransitionStatus` -> `repo.GetByKey(key)` for validation + update
2. `SetBugStatus` -> `repo.GetByKey(key)` to re-fetch the typed model

Same pattern applies to ChangeCardService.

## Requirements

### Functional Requirements

- [ ] `AdvanceBugStatus` performs at most 1 GetByKey + 1 UpdateStatus per call
- [ ] `AdvanceChangeCardStatus` performs at most 1 GetByKey + 1 UpdateStatus per call
- [ ] `SetBugStatus` / `SetChangeCardStatus` eliminate the post-transition re-fetch
- [ ] All existing tests pass without modification (behavioral equivalence)
- [ ] All CLI commands (`shark status advance`, `shark status set`) produce identical output

### Non-Functional Requirements

- [ ] No new public API surface on EntityService (internal optimization)
- [ ] TaskService adapter pattern not regressed

## Implementation Plan

### Approach A: Return entity from TransitionResult (preferred)

Have `EntityService.TransitionStatus` return the fetched entity (with status updated in-place) in the `TransitionResult`. The typed service can then type-assert the entity from the result instead of re-fetching.

```go
type TransitionResult struct {
    // ... existing fields ...
    Entity models.Entity  // The entity post-transition (status updated in-place)
}
```

Then in `SetBugStatus`:
```go
result, err := s.entitySvc.TransitionStatus(ctx, adapter, ...)
if err != nil { return nil, err }
// Type-assert from result instead of re-fetching
if bug, ok := result.Entity.(*models.Bug); ok {
    return bug, nil
}
```

### Approach B: Accept pre-fetched entity

Add a `TransitionStatusWithEntity` method that accepts an already-fetched entity, skipping the internal GetByKey. This helps `AdvanceBugStatus` which already has the entity from `GetNextStatus`.

## Design Considerations

### Round-trip cost vs. payload size

With Turso cloud backend, **network round-trip latency dominates** — row counts and client-side processing are negligible by comparison. A single query returning 50 rows is far cheaper than 3 sequential queries returning 1 row each. This means:

- **Prefer fewer, broader queries** over multiple narrow ones. Fetching an entity with its children in one query (or a small number of parallel queries) is better than sequential GetByKey calls.
- **Cascading views** (e.g., epic status with feature rollups, feature status with task breakdown) should batch their data retrieval rather than issuing per-child queries. Even if the result set is larger, the round-trip savings outweigh any extra transfer cost.
- **The AdvanceStatus triple-GetByKey is particularly costly** on Turso because each GetByKey is a separate network round-trip. Reducing 3 sequential round-trips to 1 is roughly a 3x latency improvement for the most common CLI operation.

This principle should guide the implementation: when choosing between "fetch once and pass through" vs. "re-fetch for type safety," always prefer passing through.

### N+1 in DisplayService epic views

`populateEpicPlanningInfo` (line 377) and `populateEpicAggregationInfo` (line 496) both loop over features and call `GetTaskCountForFeature(ctx, feature.ID)` per feature — a classic N+1 pattern. An epic with 10 features issues 10 separate COUNT queries.

**Fix:** Add a bulk `GetTaskCountsByFeatureIDs(ctx, featureIDs []int64) (map[int64]int, error)` repository method that does a single `SELECT feature_id, COUNT(*) FROM tasks WHERE feature_id IN (?) GROUP BY feature_id`. Replace the loop calls with a single batch query.

- `internal/services/display_service.go` (lines 377, 496)
- `internal/repository/task_repository.go` (new batch method)
