# Remove Legacy Document Repository Methods and Dead Code

## Goal

Remove the 16 entity-specific Link/Unlink/List methods from `document_repository.go` (lines 146-449, approximately 304 lines), migrate all remaining callers of legacy `ListForEpic`/`ListForFeature`/`ListForTask` to the polymorphic `EntityDocumentRepository.ListForEntity()`, update interfaces and mocks, and add deprecation markers to `TaskHistoryRepository`.

## Why

After T-005 (service simplification) and T-008 (CLI updates), the polymorphic repositories (`EntityDocumentRepository`, `EntityHistoryRepository`) are the canonical approach. However, **codebase analysis reveals 7 live production callers and 5 interface definitions still referencing legacy methods**. These must be migrated before the legacy methods can be removed. Keeping dead code creates confusion about which approach is canonical.

**Business Value**: Eliminates maintenance burden of 300+ lines of dead code. Prevents developers from accidentally using legacy methods instead of the canonical polymorphic API. Completes the repository consolidation goal from Feature PRD REQ-F-004.

## Architecture Decisions

### ADR-1: Migrate Remaining Callers Before Removal (Not Just Remove)

**Decision**: This task must migrate 7 live production callers, not just delete methods. T-005 did NOT migrate all callers as originally expected.

**Rationale**: Codebase analysis on 2026-03-21 found the following callers are STILL using legacy methods in production code:
- `display_service.go:418` -- `s.deps.DocumentRepo.ListForEpic(ctx, info.Epic.ID)`
- `display_service.go:555` -- `s.deps.DocumentRepo.ListForEpic(ctx, epicID)`
- `display_service.go:608` -- `s.deps.DocumentRepo.ListForFeature(ctx, info.Feature.ID)`
- `display_service.go:723` -- `s.deps.DocumentRepo.ListForFeature(ctx, featureID)`
- `epic_service.go:339` -- `s.docRepo.ListForEpic(ctx, epicID)`
- `feature_service.go:494` -- `s.docRepo.ListForFeature(ctx, featureID)`
- `task_service.go:1116` -- `s.docRepo.ListForTask(ctx, task.ID)`

The `display_service.go` uses `*repository.DocumentRepository` directly (line 104), not an interface. The other services use the `config.DocumentRepository` interface from `internal/config/template_helpers.go`.

**Consequence**: BR1 (stop if tests fail) remains the safety valve, but we now EXPECT to need migration work. The developer should migrate callers first, then remove the legacy methods.

### ADR-2: Deprecate TaskHistoryRepository (Option B)

**Decision**: Add `// Deprecated:` godoc comments to `TaskHistoryRepository` rather than rewriting it to delegate.

**Rationale**: `TaskHistoryRepository` has 35+ callers across services, CLI wiring, status calculation, and tests. Full delegation would require changing the `TaskHistoryRepository` interface in `task_service.go` (line 133), `task_history_service.go`, `internal/status/status.go`, `internal/cli/services_global.go`, `cmd/server/services.go`, and all test files. This is a large cross-cutting change that is better handled as a separate task. The `task_history` table is still being actively written to and read from. Deprecation markers communicate intent without breaking anything.

**Consequence**: `TaskHistoryRepository` remains functional. A future task should migrate callers to `EntityHistoryRepository` and eventually remove `TaskHistoryRepository`.

### ADR-3: Update config.DocumentRepository Interface to Use Polymorphic Pattern

**Decision**: Replace the `config.DocumentRepository` interface (which defines `ListForTask`, `ListForFeature`, `ListForEpic`) with a polymorphic-aware adapter or update the interface contract.

**Rationale**: The `config.DocumentRepository` interface in `internal/config/template_helpers.go` (line 377) defines per-entity `ListFor*` methods. This is the interface that `epic_service.go`, `feature_service.go`, `task_service.go` and `display_service.go` depend on. It must be updated to use `EntityDocumentRepository.ListForEntity()` or an adapter that wraps it.

**Approach**: Create a thin adapter struct that implements the old `config.DocumentRepository` interface by delegating to `EntityDocumentRepository.ListForEntity()`. This minimizes changes across callers while still eliminating the per-entity methods from `document_repository.go`.

## Edge Cases and Business Rules

### BR1: If Tests Fail After Migration, Fix the Migration

Unlike the original spec which assumed all callers were already migrated, this task now explicitly includes caller migration. If a test fails, fix the migration rather than stopping.

### BR2: Migration Code Is Exempt

References to legacy table names in these files are expected and must NOT be removed:
- `internal/db/db.go` -- Schema creation and migration functions
- `internal/db/migrate.go` -- Data migration logic
- `internal/db/migration_polymorphic_test.go` -- Migration tests

### BR3: Core Document CRUD Must Be Preserved

The following methods in `document_repository.go` are NOT legacy and must NOT be removed:
- `CreateOrGet(ctx, title, filePath)` -- Creates or retrieves a document record
- `GetByID(ctx, id)` -- Retrieves document by primary key
- `getByTitleAndPath(ctx, title, filePath)` -- Private helper for CreateOrGet
- `GetByTitle(ctx, title)` -- Retrieves document by title
- `Delete(ctx, id)` -- Deletes a document record

These operate on the `documents` table (not the join tables) and remain needed.

### BR4: Interface Contracts Must Stay Consistent

The `config.DocumentRepository` interface (template_helpers.go:377) defines `ListForTask`, `ListForFeature`, `ListForEpic`. This interface is KEPT -- it is satisfied by the new `PolymorphicDocRepoAdapter` instead of by `*repository.DocumentRepository`. This preserves type safety while eliminating the legacy implementation.

### BR5: Adapter Pattern Minimizes Blast Radius

The `PolymorphicDocRepoAdapter` maps entity-specific calls to polymorphic calls:
- `ListForEpic(ctx, epicID)` -> `entityDocRepo.ListForEntity(ctx, models.EntityTypeEpic, epicID)`
- `ListForFeature(ctx, featureID)` -> `entityDocRepo.ListForEntity(ctx, models.EntityTypeFeature, featureID)`
- `ListForTask(ctx, taskID)` -> `entityDocRepo.ListForEntity(ctx, models.EntityTypeTask, taskID)`

This means callers (services, template helpers) do NOT need to change their calling code.

### EC1: TaskHistoryRepository Is Not Removed

`TaskHistoryRepository` has 35+ callers across 8 files. Full removal is out of scope. Only deprecation markers are added.

### EC2: Integration Test Fixtures Using Legacy Methods

Integration tests in `internal/cli/commands/` use `*repository.DocumentRepository` for fixture setup. These call `LinkToEpic`, `LinkToFeature`, etc. They must be updated to use `EntityDocumentRepository.Link()`.

Files affected:
- `epic_get_integration_test.go` (6 calls at lines 631-826)
- `feature_get_integration_test.go` (5 calls at lines 573-706)
- `related_docs_test.go` (9 calls at lines 391-508)
- `task_reason_doc_test.go` (1 call at line 80)
- `display_service_test.go` (3 calls at lines 539-572)

### EC3: config.DocumentRepository Interface Remains

The `config.DocumentRepository` interface in `template_helpers.go` and its test mocks in `template_helpers_test.go` (lines 615-629) are PRESERVED. They define the adapter contract. The test mocks already implement the right signature.

## Notes

- Original spec assumed T-005 migrated all callers. Codebase analysis proves 7 production callers and 5 interfaces still reference legacy methods. The task scope has been expanded accordingly.
- The adapter pattern is the lowest-risk approach: callers keep their current API, only the underlying implementation changes.
- `TaskHistoryRepository` deprecation is cosmetic-only in this task; a follow-up task should handle the full migration.
- The Go compiler remains the primary safety net -- removing a method that is still called will cause a compile error.
