# Schema Migration: Create Polymorphic Tables and Migrate Data

## Goal

Create the `entity_documents` and `entity_history` polymorphic tables, migrate existing data from 5 per-entity document join tables and `task_history`, verify row counts, and drop old tables. This is the foundational schema change that all other F08 tasks depend on.

## Why

Six tables are consolidated into 2 polymorphic tables, enabling document linking and history for all entity types without per-entity schema changes. See [feature.md - Problem](../feature.md#problem) for full rationale.

**Feature PRD Traceability**:
- REQ-F-001 (Polymorphic Entity Documents Table) -- this task creates the table
- REQ-F-002 (Polymorphic Entity History Table) -- this task creates the table
- REQ-F-003 (Data Migration) -- this task performs the migration
- REQ-NF-001 (Migration Safety) -- this task implements verification-before-drop

## Architecture Decisions

### ADR-T001-1: Migration function lives in `internal/db/db.go`, not `migrate.go`

**Decision**: The `migrateToPolymorphicTables` function and its helpers are added to `internal/db/db.go` and called from `runMigrations()`, which is also in `db.go`.

**Rationale**: All migration functions called by `runMigrations()` are defined in `internal/db/db.go` (e.g., `migrateTaskDocumentsLinkType` at line 1340, `migrateEntityNotes` at line 1516, `migrateBugAndChangeCardTables` at line 1944). The separate `internal/db/migrate.go` file only contains the standalone exported `MigrateAddExecutionOrder` function, which is NOT part of the `runMigrations()` chain. Following the established pattern means this migration goes in `db.go`.

### ADR-T001-2: Inline table existence check (no `tableExists()` helper)

**Decision**: Use the inline `var tableExists int; db.QueryRow(...).Scan(&tableExists)` pattern to check table existence, not a helper function.

**Rationale**: The codebase does NOT have a `tableExists()` helper function. All 12+ table existence checks in `db.go` use the inline pattern:
```go
var tableExists int
err := db.QueryRow(`SELECT COUNT(*) FROM sqlite_master WHERE type='table' AND name='table_name'`).Scan(&tableExists)
```
The developer MAY extract a private `tableExists(db *sql.DB, name string) bool` helper within this migration for DRY (checking 7 tables), but it must remain unexported and local. This is an optional refactoring -- using the inline pattern is equally acceptable.

### ADR-T001-3: History re-run guard via row count check

**Decision**: Before copying `task_history` data, check whether `entity_history` already has rows with `entity_type='task'`. If it does AND the count matches `task_history`, skip the copy. Otherwise, proceed with the copy.

**Rationale**: `entity_history` has no UNIQUE constraint (multiple status transitions per entity are valid), so `INSERT OR IGNORE` cannot be used. On re-run after partial completion (new tables exist, old tables still present), blindly re-copying would duplicate history records. The count check prevents this while still allowing the copy if it was not completed previously.

**Implementation**:
```go
var existingCount int
db.QueryRow("SELECT COUNT(*) FROM entity_history WHERE entity_type = 'task'").Scan(&existingCount)
if existingCount == 0 {
    // Safe to copy -- no data exists yet
    _, err := db.Exec(`INSERT INTO entity_history (...) SELECT ... FROM task_history`)
}
// If existingCount > 0, data was already copied; skip
```

### ADR-T001-4: Fresh database schema: old tables NOT created

**Decision**: For fresh databases (no existing tables), the `createSchema` DDL in `db.go` creates `entity_documents` and `entity_history` instead of the 5 per-entity document tables and `task_history`. The old table DDL is removed from `createSchema`.

**Rationale**: Fresh databases have no data to migrate. Creating old tables only to have the migration immediately drop them is wasteful and confusing. The migration function handles the case where old tables do not exist (early return).

**Important note on existing tests**: Some existing tests may create databases using `createSchema` and expect the old tables to exist. These tests must be updated to work with the new schema. The migration tests (which create old tables manually for testing) are separate and unaffected.

### ADR-T001-5: EC-3 verification approach -- use `new >= old`

**Decision**: Use `new >= old` for verification, accepting that old tables with duplicates are a pre-existing data quality issue.

**Rationale**: The old document tables use `PRIMARY KEY (entity_id, document_id)`, so duplicates should not exist. If they somehow do, `INSERT OR IGNORE` will deduplicate correctly. The verification `new >= old` will fail only if `new < old`, which indicates the insert failed for a genuine reason (e.g., FK violation). Using `COUNT(DISTINCT ...)` adds complexity for a theoretical scenario that the PK constraint prevents.

## Data Models

### New Table: `entity_documents`

```sql
CREATE TABLE IF NOT EXISTS entity_documents (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    entity_type TEXT NOT NULL,
    entity_id INTEGER NOT NULL,
    document_id INTEGER NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    link_type TEXT DEFAULT 'general',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(entity_type, entity_id, document_id)
);

CREATE INDEX IF NOT EXISTS idx_entity_documents_lookup
    ON entity_documents(entity_type, entity_id);

CREATE INDEX IF NOT EXISTS idx_entity_documents_document
    ON entity_documents(document_id);
```

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | Row identifier |
| entity_type | TEXT | NOT NULL | 'epic', 'feature', 'task', 'bug', 'change' |
| entity_id | INTEGER | NOT NULL | ID in the entity's own table |
| document_id | INTEGER | NOT NULL, FK documents(id) ON DELETE CASCADE | Linked document |
| link_type | TEXT | DEFAULT 'general' | Document link classification |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | When link was created |

**Indexes**: `idx_entity_documents_lookup` on (entity_type, entity_id), `idx_entity_documents_document` on (document_id)

**Unique Constraint**: (entity_type, entity_id, document_id) -- prevents duplicate links

### New Table: `entity_history`

```sql
CREATE TABLE IF NOT EXISTS entity_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    entity_type TEXT NOT NULL,
    entity_id INTEGER NOT NULL,
    from_status TEXT,
    to_status TEXT NOT NULL,
    changed_by TEXT,
    notes TEXT,
    forced INTEGER NOT NULL DEFAULT 0,
    rejection_reason TEXT,
    changed_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_entity_history_lookup
    ON entity_history(entity_type, entity_id);

CREATE INDEX IF NOT EXISTS idx_entity_history_time
    ON entity_history(changed_at);

CREATE INDEX IF NOT EXISTS idx_entity_history_entity_time
    ON entity_history(entity_type, entity_id, changed_at);
```

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | Row identifier |
| entity_type | TEXT | NOT NULL | 'epic', 'feature', 'task', 'bug', 'change' |
| entity_id | INTEGER | NOT NULL | ID in the entity's own table |
| from_status | TEXT | nullable | Previous status (NULL for initial creation) |
| to_status | TEXT | NOT NULL | New status after transition |
| changed_by | TEXT | nullable | Agent ID or "user" |
| notes | TEXT | nullable | Transition notes |
| forced | INTEGER | NOT NULL, DEFAULT 0 | 1 if forced, 0 otherwise |
| rejection_reason | TEXT | nullable | Reason for backward/forced transition |
| changed_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | Transition timestamp |

**Indexes**: `idx_entity_history_lookup` on (entity_type, entity_id), `idx_entity_history_time` on (changed_at), `idx_entity_history_entity_time` on (entity_type, entity_id, changed_at)

## Migration SQL

### Document Migration (per entity type)

```sql
-- Epic documents
INSERT OR IGNORE INTO entity_documents (entity_type, entity_id, document_id, link_type, created_at)
SELECT 'epic', epic_id, document_id, 'general', created_at
FROM epic_documents;

-- Feature documents
INSERT OR IGNORE INTO entity_documents (entity_type, entity_id, document_id, link_type, created_at)
SELECT 'feature', feature_id, document_id, 'general', created_at
FROM feature_documents;

-- Task documents (preserves link_type)
INSERT OR IGNORE INTO entity_documents (entity_type, entity_id, document_id, link_type, created_at)
SELECT 'task', task_id, document_id, COALESCE(link_type, 'general'), created_at
FROM task_documents;

-- Bug documents
INSERT OR IGNORE INTO entity_documents (entity_type, entity_id, document_id, link_type, created_at)
SELECT 'bug', bug_id, document_id, 'general', created_at
FROM bug_documents;

-- Change card documents
INSERT OR IGNORE INTO entity_documents (entity_type, entity_id, document_id, link_type, created_at)
SELECT 'change', change_card_id, document_id, 'general', created_at
FROM change_card_documents;
```

### History Migration

```sql
INSERT INTO entity_history (entity_type, entity_id, from_status, to_status, changed_by, notes, forced, rejection_reason, changed_at)
SELECT 'task', task_id, old_status, new_status, agent, notes,
       COALESCE(forced, 0), rejection_reason, timestamp
FROM task_history;
```

## Implementation Algorithm

```
function migrateToPolymorphicTables(db):
    // Step 0: Check if already fully migrated
    if entity_documents exists AND epic_documents does NOT exist:
        return nil  // Already done

    // Step 1-3: Create new tables and indexes (IF NOT EXISTS)
    createPolymorphicTables(db)

    // Steps 4-8: Migrate document data (per old table, skip missing)
    for each (oldTable, entityType, fkColumn) in documentMappings:
        if oldTable exists:
            INSERT OR IGNORE INTO entity_documents SELECT ... FROM oldTable

    // Step 9: Migrate history data (with re-run guard)
    if task_history exists:
        existingCount = COUNT(*) FROM entity_history WHERE entity_type='task'
        if existingCount == 0:
            INSERT INTO entity_history SELECT ... FROM task_history

    // Step 10: Verify row counts
    for each (oldTable, entityType) in allMappings:
        if oldTable exists:
            oldCount = COUNT(*) FROM oldTable
            newCount = COUNT(*) FROM new_table WHERE entity_type=entityType
            if newCount < oldCount:
                return error("verification failed: oldTable had N, new has M")

    // Step 11: Drop old tables
    DROP TABLE IF EXISTS epic_documents
    DROP TABLE IF EXISTS feature_documents
    DROP TABLE IF EXISTS task_documents
    DROP TABLE IF EXISTS bug_documents
    DROP TABLE IF EXISTS change_card_documents
    DROP TABLE IF EXISTS task_history

    return nil
```

## User Stories

### Story 1: Polymorphic Document Table Creation

As a developer building the polymorphic data model,
I want the `entity_documents` table created with the correct schema,
so that all entity types can share a single document linking table.

### Story 2: Polymorphic History Table Creation

As a developer building the polymorphic data model,
I want the `entity_history` table created with the correct schema,
so that status change history can be tracked for all entity types.

### Story 3: Lossless Data Migration

As a project maintainer with existing document links and task history,
I want all existing data migrated to the new polymorphic tables without data loss,
so that existing workflows are preserved after the schema change.

### Story 4: Safe Destructive Cleanup

As a project maintainer,
I want old per-entity tables dropped only after migration verification passes,
so that there is no risk of data loss from premature table removal.

## Business Rules

1. **Verification-before-drop**: Old tables are NEVER dropped unless the row count verification passes. This is the primary safety mechanism for data integrity.

2. **INSERT OR IGNORE for documents**: Document migration uses `INSERT OR IGNORE` because the UNIQUE constraint on `(entity_type, entity_id, document_id)` prevents duplicate links. This makes re-runs safe.

3. **History re-run safety**: History migration checks `COUNT(*) FROM entity_history WHERE entity_type='task'` before copying. If count > 0, the copy is skipped (data was already migrated). If count is 0, the copy proceeds. Once old tables are dropped, no re-insertion is possible regardless.

4. **NULL normalization**: `task_history.forced` may be NULL in existing data (column defined as `BOOLEAN DEFAULT FALSE`, which SQLite stores as NULL in some cases). The migration normalizes NULL to 0 via `COALESCE(forced, 0)`. Similarly, `task_documents.link_type` NULL is normalized to 'general'.

5. **Entity type values**: The entity_type discriminator values must exactly match the constants in `internal/models/entity_note.go:12-17`: `'epic'`, `'feature'`, `'task'`, `'bug'`, `'change'`. Using any other value would break polymorphic lookups.

6. **skip_migrations flag**: Per `database-critical.md`, the developer MUST set `skip_migrations: false` in `.sharkconfig.json` before running the next shark command after this change is deployed, then set it back to `true`. This MUST be documented in the PR description.

## Edge Cases

### EC-1: Missing Old Tables
Some old tables may not exist (e.g., `bug_documents` or `change_card_documents` were added in E18 and might not be present on all databases). The migration must check table existence (via `SELECT COUNT(*) FROM sqlite_master WHERE type='table' AND name=?`) before querying or copying from each old table. Missing old tables are not an error -- they are silently skipped.

### EC-2: Empty Old Tables
Old tables may exist but contain zero rows. The migration must handle this gracefully: row count verification succeeds (0 >= 0), and the empty old table is dropped normally.

### EC-3: Duplicate Document Links in Source Tables
The old document tables use `PRIMARY KEY (entity_id, document_id)`, so duplicates should not exist. If they somehow do (corrupt data), `INSERT OR IGNORE` silently deduplicates. The verification uses `new >= old`. If duplicates caused `new < old`, the verification fails and old tables are retained, alerting the developer to the data quality issue.

### EC-4: Foreign Key Integrity (document_id)
If `document_id` values in old tables reference documents that no longer exist in the `documents` table, the FK constraint on `entity_documents` will cause the INSERT to fail for those rows. Since we use `INSERT OR IGNORE`, these FK-violating rows are silently skipped. This means `new < old` could happen, causing verification to fail. To prevent this, the document migration SQL should filter: `WHERE document_id IN (SELECT id FROM documents)`. This ensures only valid references are migrated and verification passes cleanly.

**Updated document migration SQL pattern:**
```sql
INSERT OR IGNORE INTO entity_documents (entity_type, entity_id, document_id, link_type, created_at)
SELECT 'epic', epic_id, document_id, 'general', created_at
FROM epic_documents
WHERE document_id IN (SELECT id FROM documents);
```

The corresponding verification must also account for this: compare against `SELECT COUNT(*) FROM old_table WHERE document_id IN (SELECT id FROM documents)`.

### EC-5: Large Datasets
For databases with many thousands of history records, the migration uses `INSERT INTO ... SELECT FROM ...` pattern, which is efficient in SQLite (single pass, no row-by-row overhead).

### EC-6: Concurrent Access During Migration
SQLite WAL mode allows reads during writes, but the migration involves DDL (DROP TABLE). The migration runs inside `InitDB()` which is called at startup before any commands execute, so concurrent access is not a concern for CLI usage. For the HTTP server, the migration runs at server startup before accepting requests.

### EC-7: createSchema changes breaking existing tests
Some tests may call `createSchema` (or use `test.GetTestDB()`) and expect the old `task_history`, `epic_documents`, etc. tables to exist. After the schema change (removing old table DDL), these tests will fail. The developer must check for and update any tests that depend on the old table names. Migration tests should create old tables manually using explicit DDL in the test setup.

## Security and Performance Considerations

### Security
- No user input is interpolated into SQL -- all entity type strings are hardcoded literals in migration SQL
- FK constraint on `document_id` enforced by SQLite engine
- Application-level validation of `entity_type` values (same approach as `entity_notes`)

### Performance
- `INSERT INTO ... SELECT FROM ...` is a single-pass bulk operation in SQLite
- Composite index `(entity_type, entity_id)` ensures O(log n) lookups for polymorphic queries
- Three indexes on `entity_history` support time-range, entity-specific, and combined queries
- Dataset sizes in this project are small (typically < 1000 rows per table), so performance is not a concern
- Migration adds ~200ms to startup on first run (one-time cost)
