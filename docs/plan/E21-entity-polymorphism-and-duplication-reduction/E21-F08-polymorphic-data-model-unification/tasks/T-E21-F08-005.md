# Simplify EntityDocumentService to Use Polymorphic Repository

## Goal

Refactor `EntityDocumentService` to replace the callback pattern (`linkFn`, `unlinkFn`, `listFn`) with a direct dependency on the `EntityDocumentLinkRepository` interface. The polymorphic repository (built in T-E21-F08-003) handles all entity types via `entity_type + entity_id` parameters, making per-entity callbacks unnecessary. Also wire the new repository into `services_global.go` for CLI access.

## Why

The current `EntityDocumentService` (178 lines, `internal/services/entity_document_service.go`) uses function callbacks to abstract over per-entity document tables. With the polymorphic `entity_documents` table and `EntityDocumentRepository` now in place (T-E21-F08-003, completed), the callbacks are redundant -- the service can call the repository directly with `entityType` and `entityID`. This simplifies:

- The service constructor (from 6 parameters to 3)
- The 5 callers that wire callbacks (EpicService, FeatureService, TaskDependencyService, BugService, ChangeCardService)
- Test setup (mock one interface instead of constructing 4 callback functions)

**Feature PRD Traceability**: REQ-F-004 (Repository Consolidation), Story 1 (Link documents to any entity type via same API).

## User Stories

### Story 1: Simplified Service Constructor

As a developer maintaining the document service,
I want the `EntityDocumentService` constructor to accept an `EntityDocumentLinkRepository` interface instead of 4 callback functions,
so that adding document support for new entity types requires zero wiring changes.

### Story 2: Unified Code Path for All Entity Types

As a developer agent,
I want document linking for all 5 entity types (epic, feature, task, bug, change) to flow through the same polymorphic repository call,
so that there is one consistent code path instead of 5 entity-specific callbacks.

### Story 3: Simplified Caller Wiring

As a developer modifying entity services,
I want the entity service `SetWritableDocRepo` methods (on EpicService, FeatureService, BugService, ChangeCardService, TaskDependencyService) to pass the new `EntityDocumentLinkRepository` instead of constructing per-entity callback closures,
so that service wiring code is shorter and less error-prone.

### Story 4: CLI Wiring

As a developer using shark CLI commands,
I want `services_global.go` to construct `EntityDocumentRepository` and inject it into the `EntityDocumentService` constructor,
so that CLI commands can use the simplified service without manual wiring.

## Business Rules

1. **entityLookupFn signature change**: The lookup function must return `(int64, models.EntityType, error)` instead of just `(int64, error)`. This is because the service no longer has a fixed `entityType` field -- it needs the lookup to tell it what type the entity is. This is a breaking change to the lookup function signature that must be propagated to all 5 callers.

2. **Default link_type**: When `LinkDocumentByKey` calls `linkRepo.Link`, it passes `"general"` as the `linkType` parameter. The repository handles the SQL default via `COALESCE(NULLIF(?, ''), 'general')`, so passing `"general"` explicitly is equivalent but more explicit.

3. **Backward compatibility of old per-entity methods**: The old per-entity Link/Unlink/List methods in `document_repository.go` (e.g., `LinkToEpic`, `ListForEpic`) are NOT removed in this task. They remain available for any callers outside the 5 entity services. Removal is deferred to T-E21-F08-009.

4. **No FK enforcement on entity_id**: The polymorphic `entity_id` column has no SQL-level foreign key. The `entityLookupFn` is the application-level mechanism for verifying entity existence. If the lookup succeeds, the entity exists; if it fails, the service returns an error before any repository call.

5. **Non-nil empty slice contract**: `ListDocumentsByKey` must return `[]*models.Document{}` (non-nil empty slice) when no documents exist, matching the current contract and the `EntityDocumentRepository.ListForEntity` behavior.

## Edge Cases

### EC-1: entityLookupFn Returns Error (Entity Not Found)

**Given** the `entityLookupFn` returns an error for the provided key
**When** any of `LinkDocumentByKey`, `UnlinkDocumentByKey`, or `ListDocumentsByKey` is called
**Then** the method returns an error wrapping the lookup error with context (e.g., "entity not found: <original error>"). No repository methods are called.

### EC-2: writableRepo.CreateOrGet Fails During Link

**Given** `entityLookupFn` succeeds but `writableRepo.CreateOrGet` returns an error
**When** `LinkDocumentByKey` is called
**Then** the method returns an error: "failed to create or get document: <original error>". `linkRepo.Link` is never called.

### EC-3: linkRepo.Link Fails (e.g., FK Violation on document_id)

**Given** `entityLookupFn` and `writableRepo.CreateOrGet` both succeed, but `linkRepo.Link` returns an error
**When** `LinkDocumentByKey` is called
**Then** the method returns an error: "failed to link document to <entityType> <entityKey>: <original error>".

### EC-4: linkRepo.ListForEntity Returns nil Slice

**Given** `linkRepo.ListForEntity` returns `(nil, nil)` (nil slice, no error)
**When** `ListDocumentsByKey` is called
**Then** the method returns `([]*models.Document{}, nil)` -- converts nil to empty non-nil slice.

### EC-5: linkRepo.Unlink Fails

**Given** `entityLookupFn` and `writableRepo.GetByTitle` both succeed, but `linkRepo.Unlink` returns an error
**When** `UnlinkDocumentByKey` is called
**Then** the method returns an error: "failed to unlink document from <entityType> <entityKey>: <original error>".

### EC-6: Multiple Entity Types in Same Service Instance (Not Applicable)

The refactored service no longer has a fixed `entityType` field. The entity type comes from `entityLookupFn` at call time. If the same service instance is shared across entity types (future optimization), it must work correctly because each call resolves its own type.

## Design Decisions

### DD-1: entityLookupFn Returns EntityType

The current `entityLookupFn` signature is `func(ctx, key) (int64, error)`. The refactored version must return `(int64, models.EntityType, error)` because the service no longer stores a fixed `entityType`. This is the minimal change that enables the service to be entity-type-agnostic.

**Alternative considered**: Keep a fixed `entityType` on the struct. Rejected because it would still require creating separate `EntityDocumentService` instances per entity type, which defeats the purpose of the polymorphic repository.

**Alternative considered**: Have the service accept `entityType` as a method parameter. Rejected because the `ByKey` methods already receive a key that implies the entity type, and the lookup function naturally knows the type.

### DD-2: EntityDocumentLinkRepository Interface Location

The `EntityDocumentLinkRepository` interface is defined at point of use in `internal/services/entity_document_service.go`, following the project's "define interfaces at the consumer" pattern. The concrete `repository.EntityDocumentRepository` implements this interface.

#### 4. Methods to simplify

**LinkDocumentByKey** -- current flow: lookupFn -> LinkDocument(entityID, ...) -> linkFn(entityID, docID)
**Target flow**: lookupFn -> writableRepo.CreateOrGet -> linkRepo.Link(entityType, entityID, docID, "general")

**UnlinkDocumentByKey** -- current flow: lookupFn -> UnlinkDocument(entityID, ...) -> unlinkFn(entityID, docID)

#### 5. Caller SetWritableDocRepo changes (5 callers, all verified)

Each caller currently constructs per-entity callback closures. After refactoring, each `SetWritableDocRepo` method changes to accept `EntityDocumentLinkRepository` as an additional parameter (or changes its existing parameter type).

**Recommended approach: Change `SetWritableDocRepo` signature to accept both repos.**

The 5 per-entity `*WritableDocumentRepository` interfaces (`EpicWritableDocumentRepository`, `FeatureWritableDocumentRepository`, `TaskWritableDocumentRepository`, `BugWritableDocumentRepository`, `ChangeCardWritableDocumentRepository`) currently include `LinkToX`/`UnlinkFromX`/`ListForX` methods. After this refactoring, those methods are no longer needed by the service callers. However, removing them from the interfaces is safe only if no other code depends on them.

**Decision: Simplify the per-entity WritableDocumentRepository interfaces to only include `CreateOrGet` and `GetByTitle`, and add a separate `linkRepo EntityDocumentLinkRepository` parameter to `SetWritableDocRepo`. This keeps the interfaces minimal (only what the caller needs).**

Alternatively, since `CreateOrGet` and `GetByTitle` are the same methods across all 5 interfaces, they can all use the existing `EntityDocumentRepository` interface that already defines exactly those methods (entity_document_service.go:12-15).

**Concrete recommended `SetWritableDocRepo` signature (all 5 callers):**

```go
func (s *EpicService) SetWritableDocRepo(writableRepo EntityDocumentRepository, linkRepo EntityDocumentLinkRepository) {
    s.docSvc = NewEntityDocumentService(
        writableRepo,
        linkRepo,
        func(ctx context.Context, key string) (int64, models.EntityType, error) {
            epic, err := s.repo.GetByKey(ctx, key)
            if err != nil {
                return 0, "", err
            }
            return epic.ID, models.EntityTypeEpic, nil
        },
    )
}
```

This eliminates the need for `EpicWritableDocumentRepository`, `FeatureWritableDocumentRepository`, etc. -- all callers accept the same `EntityDocumentRepository` + `EntityDocumentLinkRepository` pair.

**Note on EpicService/FeatureService fallback:** `EpicService.ListRelatedDocumentsByKey` and `FeatureService.ListRelatedDocumentsByKey` have a fallback that calls `GetRelatedDocuments`/`ListRelatedDocuments` when `docSvc` is nil. This fallback path uses `s.docRepo` (the old read-only document repo). The fallback is only triggered when `SetWritableDocRepo` has NOT been called. After this refactoring, the fallback path remains valid because `docSvc` is still nil when `SetWritableDocRepo` is not called.

#### 6. services_global.go wiring changes

Current pattern (4 locations: GetTaskServiceWithDeps, GetEpicService, GetBugService, GetChangeCardService + GetFeatureService):
```go
docRepo := repository.NewDocumentRepository(db)
svc.SetWritableDocRepo(docRepo)
```

**Target pattern:**
```go
docRepo := repository.NewDocumentRepository(db)
entityDocRepo := repository.NewEntityDocumentRepository(db)
svc.SetWritableDocRepo(docRepo, entityDocRepo)
```

The `EntityDocumentRepository` can be constructed once per `Get*Service()` call and passed to `SetWritableDocRepo`. Since the `*repository.DocumentRepository` still satisfies `EntityDocumentRepository` (it has `CreateOrGet` and `GetByTitle`), either `docRepo` or a separate instance works as the `writableRepo` parameter.

After this task, the following interfaces become smaller:
