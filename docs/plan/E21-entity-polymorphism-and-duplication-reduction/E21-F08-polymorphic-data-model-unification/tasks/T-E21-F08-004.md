# EntityHistoryRepository: Polymorphic History CRUD

## Goal

Create `EntityHistoryRepository` providing polymorphic history Create and query operations for the `entity_history` table. This repository supports both history recording (used by EntityService in T-E21-F08-006) and history querying (used by EntityHistoryService in T-E21-F08-007).

## Why

Status change history is currently task-only (`task_history` table, `TaskHistoryRepository`). The new polymorphic repository enables history for all 5 entity types through one code path, fulfilling Feature Story 2 ("status change history for all entity types") and REQ-F-004 (Repository Consolidation).

The existing `TaskHistoryRepository` (360 lines, 7 methods) is task-specific by design: it has `TaskID int64` parameters, joins through `tasks -> features -> epics` for scope-based filtering, and returns `*models.TaskHistory` structs. The new `EntityHistoryRepository` uses `EntityType + EntityID` parameters and returns `*models.EntityHistory` structs, following the proven `entity_notes` pattern (645 lines, parameterized by `EntityType`).

**Feature PRD Traceability**:
- REQ-F-002 (Polymorphic Entity History Table) -- this task provides the Go repository for the table
- REQ-F-004 (Repository Consolidation) -- this repository replaces `TaskHistoryRepository` for new code paths
- Feature Story 2 ("status change history for all entity types") -- this repository enables querying history for any entity type

## User Stories

### Story 1: History Recording Interface

As a developer implementing EntityService history recording (T-E21-F08-006),
I want an `EntityHistoryRecorder` interface with a single `Create` method,
so that EntityService can record status change history without depending on the full repository API.

### Story 2: History Query Interface

As a developer implementing EntityHistoryService (T-E21-F08-007),
I want an `EntityHistoryQuerier` interface with `ListByEntity`, `ListRecent`, and `ListWithFilters` methods,
so that history can be queried for any entity type with flexible filtering, ordering, and pagination.

### Story 3: Dual Interface Satisfaction

As a developer wiring dependencies,
I want `EntityHistoryRepository` to satisfy both `EntityHistoryRecorder` and `EntityHistoryQuerier` interfaces,
so that one concrete struct serves both EntityService (minimal) and EntityHistoryService (full) needs.

## Business Rules

1. **Append-only semantics**: `EntityHistory` records are append-only. The repository provides `Create` but no `Update` or `Delete` methods. This is enforced by the repository API surface, not database constraints.

2. **Validation before insert**: The `Create` method calls `history.Validate()` before executing the INSERT statement. This matches the established `EntityNoteRepository.Create` pattern (line 25 of `entity_note_repository.go`). Validation failure returns an error immediately without touching the database.

3. **Entity type validation scope**: The repository validates entity types via `EntityHistory.Validate()` (which checks `models.ValidEntityTypes`). It does NOT validate that the `entity_id` references an existing row in the corresponding entity table. This is consistent with the `entity_notes` approach -- polymorphic tables cannot have SQL-level FKs to multiple parent tables.

4. **Default ordering**: Both `ListByEntity` and `ListRecent` return results ordered by `changed_at DESC` (most recent first). This matches the existing `TaskHistoryRepository.ListByTask` ordering.

5. **Default limit**: `ListWithFilters` applies a default limit of 50 when `Limit` is 0 or unset. This matches the `TaskHistoryRepository.ListWithFilters` default behavior.

6. **Separation from TaskHistoryRepository**: The existing `TaskHistoryRepository` is NOT modified or deprecated in this task. Both repositories coexist. `TaskHistoryRepository` continues to work with the `entity_history` table (formerly `task_history`, migrated in T-E21-F08-001) for backward compatibility. The backward-compatibility delegation layer is created in T-E21-F08-007.

7. **No scope-based filtering (epic/feature)**: Unlike `TaskHistoryRepository.ListWithFilters` which supports `EpicKey` and `FeatureKey` filters by joining through `tasks -> features -> epics`, the `EntityHistoryRepository.ListWithFilters` does NOT support scope-based joins. Scope-based filtering is entity-type-specific logic that belongs in the service layer (EntityHistoryService, T-E21-F08-007), not the repository.

## Edge Cases

### EC-1: Forced Field Scanning

The `entity_history.forced` column is `INTEGER NOT NULL DEFAULT 0`. Go's `database/sql` Scanner converts SQLite integers to Go `bool` (0 -> false, non-zero -> true). The repository must use `&history.Forced` directly in Scan -- no manual conversion needed. Test that both `forced=0` and `forced=1` records scan correctly.

### EC-2: Empty Result Sets

All List methods (`ListByEntity`, `ListRecent`, `ListWithFilters`) return an empty non-nil slice `[]*models.EntityHistory{}` when no records match, not `nil`. This follows Go conventions and prevents nil-pointer dereferences in callers who iterate without checking.

### EC-3: All Filters Nil in ListWithFilters

When `ListWithFilters` is called with a zero-value `EntityHistoryFilters{}` (all pointer fields nil, Limit=0, Offset=0), it should return the 50 most recent records across all entity types, ordered by `changed_at DESC`. This is the "unfiltered" query with default limit.

### EC-4: Concurrent Inserts

`Create` does not need explicit transaction management because it executes a single INSERT statement. SQLite serializes writes via its locking mechanism. Multiple concurrent `Create` calls on separate goroutines are safe.

### EC-5: Large changed_at Precision

SQLite stores DATETIME as TEXT in ISO 8601 format. Go's `time.Time` has nanosecond precision, but SQLite's `CURRENT_TIMESTAMP` provides only second precision. Records created via the migration (from `task_history.timestamp`) retain their original timestamp precision. Records created by the Go repository use `changed_at` from the `EntityHistory.ChangedAt` field (set by the caller, typically `time.Now()`) or the database default. The repository should allow the database to set `changed_at` via DEFAULT if `ChangedAt` is the zero value, OR always insert the Go-provided value. Decision: always insert the Go-provided value for consistency, matching the `TaskHistoryRepository.Create` pattern which does not specify `timestamp` in the INSERT (it relies on the DB default). For `EntityHistoryRepository`, include `changed_at` in the INSERT and let the caller set it. If the caller does not set it, the Go zero time will be stored, which is acceptable because callers (EntityService) will always set it.

### EC-6: EntityID=0 with Valid EntityType

If a caller passes `EntityID=0` to `ListByEntity` or via `EntityHistoryFilters.EntityID`, the query will return records where `entity_id=0`. Since `Create` validates `EntityID > 0` (via `EntityHistory.Validate()`), no records with `entity_id=0` should exist. The List methods do NOT validate inputs -- they execute the query as-is. This is consistent with `EntityNoteRepository` behavior.

- Dataset sizes in this project are small (typically < 1000 history records), so performance is not a concern

## Architecture Decisions (Verified 2026-03-20)

### ADR-T004-1: EntityHistoryFilters Defined in Repository Package

**Decision**: Define `EntityHistoryFilters` in `internal/repository/entity_history_repository.go`, not in the services package.

**Rationale**: The filters struct is a parameter to a repository method (`ListWithFilters`). Following the established pattern (`HistoryFilters` in `task_history_repository.go`, lines 13-22), filter structs belong in the repository package. Service-side interfaces that reference `ListWithFilters` will import `repository.EntityHistoryFilters` -- this is acceptable because interfaces are defined at the consumer site but their parameter types come from the implementation package.

**Alternatives Considered**: Defining filters in a shared `models` package was rejected because (a) it couples models to repository concerns, and (b) the existing codebase consistently puts filter structs in repository files.

### ADR-T004-2: Interfaces Defined at Point of Use, Not in Repository

**Decision**: `EntityHistoryRecorder` and `EntityHistoryQuerier` interfaces are NOT defined in the repository file. They are defined at point of use: `EntityHistoryRecorder` in `entity_service.go` (T-E21-F08-006) and `EntityHistoryQuerier` in `entity_history_service.go` (T-E21-F08-007).

**Rationale**: Go best practice ("accept interfaces, return structs") and project convention. The `EntityNoteRepository` does not define its own interface -- consumers define the interface they need. Compile-time assertion `var _ EntityHistoryQuerier = (*EntityHistoryRepository)(nil)` is placed in the consumer file, not the repository.

### ADR-T004-3: Always Insert Go-Provided changed_at Value

**Decision**: The `Create` method always inserts the `ChangedAt` value from the Go struct, even if it's the zero value. It does NOT rely on the database `DEFAULT CURRENT_TIMESTAMP`.

**Rationale**: The caller (EntityService in T-E21-F08-006) will always set `ChangedAt = time.Now()` before calling `Create`. This gives the Go layer control over timestamp precision and avoids ambiguity about whether the DB or Go timestamp is authoritative. The existing `TaskHistoryRepository.Create` does NOT include `timestamp` in its INSERT (relies on DB default), but this is a deliberate improvement: polymorphic history records may be created from multiple code paths, and explicit timestamps prevent timezone/precision confusion.

### ADR-T004-4: Empty Slice (Not Nil) for No Results

**Decision**: All List methods return `make([]*models.EntityHistory, 0)` when no records match, never `nil`.

**Rationale**: Prevents nil-pointer dereferences in callers who iterate with `for range` without nil-checking. The `EntityNoteRepository.GetRejectionHistory` (lines 638-641) follows this pattern. Note: the `append`-based pattern used in most list methods naturally returns nil when no rows exist. The repository must explicitly initialize with `make` or check after the loop. Following `GetRejectionHistory`, the check-after-loop pattern is preferred:
```go
if histories == nil {
    histories = make([]*models.EntityHistory, 0)
}
```

### ADR-T004-5: Scan Pattern for Nullable Fields

**Decision**: Use `*string` directly in `rows.Scan` for nullable TEXT columns (`from_status`, `changed_by`, `notes`, `rejection_reason`). The `forced` column (INTEGER NOT NULL) scans directly into `bool`.

**Rationale**: Go's `database/sql` package handles NULL TEXT -> `*string` (nil) and non-NULL TEXT -> `*string` (pointer to value) natively. No `sql.NullString` wrapper needed because the model already uses `*string`. This matches how `EntityNoteRepository` scans nullable `created_by` and `metadata` fields. SQLite INTEGER 0/1 -> Go `bool` also works natively via `database/sql` Scanner.
