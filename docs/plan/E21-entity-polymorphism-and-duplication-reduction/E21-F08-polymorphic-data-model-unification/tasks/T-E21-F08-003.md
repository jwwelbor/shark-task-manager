## Goal

Create `EntityDocumentRepository` providing polymorphic document linking operations (Link, Unlink, ListForEntity) that work with any entity type via the `entity_documents` table. This replaces the 15 entity-specific Link/Unlink/List methods currently in `document_repository.go` (approximately 300 lines) with 3 polymorphic methods (approximately 120 lines).

## Why

The current `DocumentRepository` contains 15 per-entity methods (`LinkToEpic`, `LinkToFeature`, `LinkToTask`, `LinkToBug`, `LinkToChangeCard`, `UnlinkFromEpic`, `UnlinkFromFeature`, `UnlinkFromTask`, `UnlinkFromBug`, `UnlinkFromChangeCard`, `ListForEpic`, `ListForFeature`, `ListForTask`, `ListForBug`, `ListForChangeCard`) that differ only by table name and FK column name. A single polymorphic repository eliminates this duplication and makes adding document support for future entity types a zero-code operation. See [02-architecture.md Section 2.1](../tech/02-architecture.md#21-component-diagram) for the before/after comparison.

**Feature PRD Traceability**:
- REQ-F-004 (Repository Consolidation) -- this task creates the polymorphic document repository
- Story 1 (Link documents to any entity type) -- this repository enables polymorphic linking

## Architecture Decisions

### ADR-T003-1: Follow entity_note_repository.go as reference pattern

**Decision**: The `EntityDocumentRepository` follows the same structural patterns as `internal/repository/entity_note_repository.go`.

**Rationale**: The `entity_note_repository.go` (645 lines) is the established, battle-tested polymorphic repository pattern in this codebase. It uses `models.EntityType` for discrimination, validates entity types against `models.ValidEntityTypes`, and uses `*repository.DB` as its only constructor dependency. Following this pattern ensures consistency and reduces the learning curve for developers familiar with the codebase.

**Specifics to replicate**:
- Constructor: `NewEntityDocumentRepository(db *DB) *EntityDocumentRepository`
- Entity type validation before every query
- `context.Context` as first parameter on all methods
- Error wrapping with `fmt.Errorf("failed to <operation>: %w", err)` pattern

### ADR-T003-2: ListForEntity returns `[]*models.Document`, not link records

**Decision**: `ListForEntity` returns `[]*models.Document` (full document objects) by JOINing `entity_documents` with the `documents` table.

**Rationale**: Callers (the `EntityDocumentService` and CLI commands) need document metadata (title, file_path) to display results. Returning only IDs would require an additional round-trip. The existing per-entity `ListForEpic`, `ListForFeature`, etc. methods all JOIN with `documents` to return `[]*models.Document` -- this maintains API compatibility for the downstream refactor (T-E21-F08-005).

### ADR-T003-3: link_type defaults to "general" at the SQL level

**Decision**: The `Link` method accepts a `linkType string` parameter. If the caller passes an empty string, the INSERT uses the SQL DEFAULT (`'general'`).

**Rationale**: The `entity_documents` table has `link_type TEXT DEFAULT 'general'` (per T-E21-F08-001 schema). The existing `LinkToTaskWithType` method in `document_repository.go` passes explicit link types. The new method must support both: callers that care about link types pass them explicitly, and callers that do not can pass `""` to use the default. This preserves task document link type data migrated in T-E21-F08-001.

## User Stories

### Story 1: Polymorphic Document Linking

As a developer building the document management system,
I want a single repository that links documents to any entity type via `entity_type` + `entity_id`,
so that adding document support for a new entity type requires zero repository code changes.

### Story 2: Idempotent Link Creation

As a developer using the document linking API,
I want the Link method to be idempotent (no error on duplicate links),
so that callers do not need to check for existing links before creating them.

### Story 3: Safe Document Unlinking

As a developer managing document associations,
I want the Unlink method to silently succeed when the link does not exist,
so that callers do not need to verify link existence before removal.

### Story 4: Full Document Retrieval

As a developer building the related-docs CLI command,
I want ListForEntity to return complete `Document` objects (title, file_path, created_at),
so that the CLI can display document details without additional database queries.

## Acceptance Criteria

### AC-1: Repository Struct and Constructor

**Given** the `entity_documents` table exists in the database (created by T-E21-F08-001)
**When** `NewEntityDocumentRepository(db *repository.DB)` is called
**Then** it returns a non-nil `*EntityDocumentRepository` struct with the DB reference stored internally

**Measurable verification**: The constructor compiles and returns a valid struct. The struct type is exported from the `repository` package.

### AC-2: Link Method -- Successful Association

**Given** a valid entity type (any of: `models.EntityTypeEpic`, `models.EntityTypeFeature`, `models.EntityTypeTask`, `models.EntityTypeBug`, `models.EntityTypeChange`), a valid entity ID, and a valid document ID referencing an existing `documents` row
**When** `Link(ctx, entityType, entityID, documentID, linkType)` is called
**Then**:
- A row is inserted into `entity_documents` with the specified `entity_type`, `entity_id`, `document_id`, and `link_type`
- The method returns `nil` error
- The `created_at` column is automatically populated by the database default

**Measurable verification**: After calling Link, `SELECT COUNT(*) FROM entity_documents WHERE entity_type=? AND entity_id=? AND document_id=?` returns 1.

### AC-3: Link Method -- Idempotency (Duplicate Link)

**Given** a link already exists between entity (type, id) and document (id)
**When** `Link(ctx, entityType, entityID, documentID, linkType)` is called again with the same parameters
**Then**:
- The method returns `nil` error (no duplicate key error surfaced)
- The `entity_documents` table still contains exactly one row for that (entity_type, entity_id, document_id) combination
- This behavior is achieved via `INSERT OR IGNORE`

**Measurable verification**: After calling Link twice with identical parameters, `SELECT COUNT(*) FROM entity_documents WHERE entity_type=? AND entity_id=? AND document_id=?` returns exactly 1.

### AC-4: Link Method -- Empty link_type Defaults to "general"

**Given** a valid entity and document
**When** `Link(ctx, entityType, entityID, documentID, "")` is called with an empty string for link_type
**Then**:
- The row is inserted with `link_type = 'general'` (using the SQL column default or explicit COALESCE)
- The method returns `nil` error

**Measurable verification**: `SELECT link_type FROM entity_documents WHERE entity_type=? AND entity_id=? AND document_id=?` returns `'general'`.

### AC-5: Link Method -- Custom link_type Preserved

**Given** a valid entity and document
**When** `Link(ctx, entityType, entityID, documentID, "specification")` is called
**Then**:
- The row is inserted with `link_type = 'specification'`
- The method returns `nil` error

**Measurable verification**: `SELECT link_type FROM entity_documents WHERE entity_type=? AND entity_id=? AND document_id=?` returns `'specification'`.

### AC-6: Unlink Method -- Existing Link Removed

**Given** a link exists between entity (type, id) and document (id)
**When** `Unlink(ctx, entityType, entityID, documentID)` is called
**Then**:
- The row is deleted from `entity_documents`
- The method returns `nil` error
- The `documents` row itself is NOT deleted (only the association is removed)

**Measurable verification**: After Unlink, `SELECT COUNT(*) FROM entity_documents WHERE entity_type=? AND entity_id=? AND document_id=?` returns 0. `SELECT COUNT(*) FROM documents WHERE id=?` still returns 1.

### AC-7: Unlink Method -- Non-existent Link is No-op

**Given** no link exists between entity (type, id) and document (id)
**When** `Unlink(ctx, entityType, entityID, documentID)` is called
**Then**:
- The method returns `nil` error (no "not found" error)
- No rows are affected

**Measurable verification**: The method returns nil. No rows change in `entity_documents`.

### AC-8: ListForEntity Method -- Returns Full Document Objects

**Given** entity (type='task', id=42) has 3 linked documents
**When** `ListForEntity(ctx, models.EntityTypeTask, 42)` is called
**Then**:
- Returns a slice of exactly 3 `*models.Document` objects
- Each Document has `ID`, `Title`, `FilePath`, and `CreatedAt` fields populated from the `documents` table (via JOIN)
- Results are ordered by `entity_documents.created_at DESC` (most recently linked first)
- The method returns `nil` error

**Measurable verification**: `len(docs) == 3`. Each doc has `doc.ID > 0`, `doc.Title != ""`, `doc.FilePath != ""`, `doc.CreatedAt.IsZero() == false`. `docs[0].CreatedAt >= docs[1].CreatedAt >= docs[2].CreatedAt`.

### AC-9: ListForEntity Method -- Empty Result for No Links

**Given** entity (type='epic', id=99999) has no linked documents
**When** `ListForEntity(ctx, models.EntityTypeEpic, 99999)` is called
**Then**:
- Returns an empty (non-nil) slice `[]*models.Document{}` and `nil` error
- Does NOT return `nil` slice (callers should be able to check `len(result)` without nil guard)

**Measurable verification**: `docs != nil && len(docs) == 0 && err == nil`.

### AC-10: Entity Type Validation -- All Methods Reject Invalid Types

**Given** an entity type string that is NOT in `models.ValidEntityTypes` (e.g., `"invalid"`, `""`, `"project"`)
**When** any of `Link`, `Unlink`, or `ListForEntity` is called with that entity type
**Then**:
- The method returns a non-nil error containing the text "invalid entity type"
- No database query is executed (validation happens before SQL)

**Measurable verification**: `err != nil && strings.Contains(err.Error(), "invalid entity type")`.

### AC-11: Cascade Delete Behavior

**Given** a document with `id=7` is linked to entity (type='task', id=42) via `entity_documents`
**When** the document is deleted from the `documents` table (`DELETE FROM documents WHERE id=7`)
**Then**:
- The corresponding `entity_documents` row is automatically deleted via the `ON DELETE CASCADE` FK constraint
- `ListForEntity(ctx, models.EntityTypeTask, 42)` no longer includes that document

**Measurable verification**: After deleting the document, `SELECT COUNT(*) FROM entity_documents WHERE document_id=7` returns 0.

### AC-12: No Per-Entity Branching in Repository Code

**Given** the `entity_document_repository.go` source file
**When** the code is reviewed
**Then**:
- There are zero `if` or `switch` statements that branch on specific entity type values (no `if entityType == "epic"` or `case models.EntityTypeTask`)
- The only entity-type-specific logic is the validation against `models.ValidEntityTypes`
- All SQL queries use parameterized `entity_type = ?` placeholders, not table-name interpolation

**Measurable verification**: `grep -c 'EntityTypeEpic\|EntityTypeFeature\|EntityTypeTask\|EntityTypeBug\|EntityTypeChange' entity_document_repository.go` returns 0 (entity type constants are NOT referenced in the repository; only `models.ValidEntityTypes` map is used for validation).

## Business Rules

1. **Pure data access only**: The repository contains no business logic, no progress calculation, no workflow validation. It executes SQL queries and returns results. Validation is limited to structural checks (entity type validity, required parameters).

2. **INSERT OR IGNORE for Link**: The UNIQUE constraint on `(entity_type, entity_id, document_id)` combined with `INSERT OR IGNORE` provides idempotent linking. This matches the pattern used by the migration SQL in T-E21-F08-001.

3. **Application-level entity type validation**: The `entity_documents` table has no CHECK constraint on `entity_type` (same as `entity_notes`). Validation happens in the repository via `models.ValidEntityTypes` before any SQL is executed.

4. **No FK enforcement on entity_id**: Like `entity_notes`, the polymorphic `entity_id` column cannot have SQL-level foreign keys to multiple parent tables. The service layer (T-E21-F08-005) is responsible for verifying entity existence before calling Link.

5. **Entity type values**: Must use exactly the values defined in `internal/models/entity_note.go:12-17`: `'epic'`, `'feature'`, `'task'`, `'bug'`, `'change'`.

6. **Non-nil empty slice**: `ListForEntity` returns `[]*models.Document{}` (empty slice), never `nil`, when no documents are linked. This prevents nil-pointer issues in callers and matches the convention in `entity_note_repository.go`.

## Edge Cases

### EC-1: Invalid document_id (FK violation)

**Given** `documentID` references a non-existent document
**When** `Link` is called
**Then** the database returns an FK constraint violation error. The repository wraps this error with context: `fmt.Errorf("failed to link document: %w", err)`. The caller receives a non-nil error. This is correct behavior -- the service layer should validate document existence before calling Link. The `INSERT OR IGNORE` only ignores UNIQUE constraint violations, NOT FK violations.

### EC-2: entity_id = 0 or negative

**Given** `entityID <= 0`
**When** any method is called
**Then** the method returns a validation error: "entity_id must be positive". This validation happens before any SQL query.

### EC-3: Concurrent duplicate Link calls

**Given** two goroutines call `Link` with the same (entityType, entityID, documentID) simultaneously
**When** both execute
**Then** both succeed without error due to `INSERT OR IGNORE`. Exactly one row exists afterward. SQLite WAL mode handles the concurrency safely.

### EC-4: Large result set from ListForEntity

**Given** an entity has 1000+ linked documents
**When** `ListForEntity` is called
**Then** all documents are returned. There is no built-in pagination in this method. If pagination is needed in the future, it should be added at the service layer or as a new method, not by modifying this one.

### EC-5: Unlink after document cascade delete

**Given** a document was cascade-deleted (entity_documents row already gone)
**When** `Unlink` is called for that document
**Then** the method returns nil (no-op, zero rows affected). This is safe because DELETE with non-matching WHERE clause affects 0 rows, which is not an error.

## SQL Queries

### Link

```sql
INSERT OR IGNORE INTO entity_documents (entity_type, entity_id, document_id, link_type)
VALUES (?, ?, ?, COALESCE(NULLIF(?, ''), 'general'))
```

Note: `NULLIF(?, '')` converts empty string to NULL, then `COALESCE(..., 'general')` replaces NULL with the default. This handles both empty string and explicit link type cases.

### Unlink

```sql
DELETE FROM entity_documents
WHERE entity_type = ? AND entity_id = ? AND document_id = ?
```

### ListForEntity

```sql
SELECT d.id, d.title, d.file_path, d.created_at
FROM documents d
INNER JOIN entity_documents ed ON d.id = ed.document_id
WHERE ed.entity_type = ? AND ed.entity_id = ?
ORDER BY ed.created_at DESC
```
