# Wire History Recording into EntityService.TransitionStatus

## Goal

Add an optional `EntityHistoryRecorder` dependency to `EntityService` and insert a history recording step after every successful status transition. This enables automatic status change audit trails for all 5 entity types through a single code path.

## Why

Currently only Tasks have status change history (via database triggers on `task_history`). By recording history in `EntityService.TransitionStatus` -- the centralized transition entry point -- all entity types get audit trails without per-entity code. See [02-architecture.md ADR-3](../tech/02-architecture.md#adr-3-history-recording-in-entityservicetransitionstatus-centralized) for the centralization decision.

**Feature PRD Traceability**:
- REQ-F-005 (History Recording in TransitionStatus) -- this task implements the service-layer recording
- Feature Story 2 ("status change history for all entity types") -- this task is the mechanism that enables it
- Feature Story 4 ("agent/user who made the change") -- `changed_by` populated from `opts.Agent`

---

## User Stories

### Story 1: Automatic History Recording on Status Transition

As a developer using `EntityService.TransitionStatus` for any entity type,
I want a history record to be automatically created after each successful status transition,
so that I have a complete audit trail without writing per-entity history code.

### Story 2: Nil-Safe Optional Dependency

As a developer wiring `EntityService` during incremental rollout,
I want the history recorder dependency to be optional (nil-safe),
so that existing code paths continue to work without modification until the recorder is wired.

### Story 3: Non-Blocking History Recording

As a developer performing status transitions,
I want history recording failures to be logged but NOT block the transition,
so that a database error in history recording does not prevent a valid status change.

### Story 4: Forced and Backward Transition Metadata

As a developer reviewing audit trails,
I want forced transitions to be recorded with `forced=true` and backward transitions to include the rejection reason,
so that I can distinguish normal transitions from exceptional ones.

## Business Rules

1. **History recording is non-blocking**: If `historyRepo.Create` returns an error, `TransitionStatus` must still return the successful `TransitionResult`. The rationale: the status update has already committed to the database (Step 7). Failing the overall operation would leave the caller believing the transition failed while the status was actually changed. History is supplementary audit data.

2. **History recording is opt-in via setter**: The `historyRepo` is set via `SetHistoryRepo`, not via the constructor. This matches the existing `SetNoteRepo` pattern and enables incremental rollout. During the transition period, some `EntityService` instances may not have history recording wired.

3. **FromStatus from entity's current status**: The `FromStatus` field is populated from `entity.GetStatus()` captured at the beginning of `TransitionStatus` (the `currentStatus` variable at line 129 of the current code). This is the status BEFORE the transition, not after.

4. **ChangedBy from opts.Agent**: The `changed_by` field maps directly to `TransitionOptions.Agent`. If `Agent` is empty, `ChangedBy` is nil (not a pointer to empty string). This avoids storing semantically meaningless empty strings in the database.

5. **Notes from opts.Reason**: The `notes` field maps to `TransitionOptions.Reason`. Same nil-for-empty rule as `ChangedBy`.

6. **RejectionReason for backward transitions only**: `RejectionReason` is populated from `opts.Reason` when `isBackward == true` (non-forced backward transitions). For forced transitions, the reason goes into `Notes`, not `RejectionReason`. This distinguishes "why was this rejected" from "why was this forced".

7. **Forced field**: `Forced` is set to `opts.Force`. If the transition was forced (bypassing workflow validation), `Forced == true`. Normal transitions have `Forced == false`.

8. **ChangedAt set by service**: The service sets `ChangedAt = time.Now()` before calling `Create`. The repository does NOT rely on database defaults for this field (per ADR-T004-3 from T-E21-F08-004).

9. **ForLevel propagation**: `ForLevel` must copy `historyRepo` to the scoped instance (same as it copies `noteRepo`). Otherwise, entity-specific services that call `ForLevel` would lose the history recorder.

## Edge Cases

### EC-1: Transition That Fails Validation Does NOT Create History

If `ValidateAndNormalize` returns an error (Steps 3-4), `TransitionStatus` returns early. No status update occurs, and no history record is created. This is correct: only successful transitions deserve audit records.

### EC-2: Transition That Fails Status Update Does NOT Create History

If `repo.UpdateStatus` (Step 7) returns an error, `TransitionStatus` returns the error immediately. History recording (Step 7.5) is skipped. This is correct: history records should reflect actual state changes, not attempted ones.

### EC-3: Backward Transition That Requires Reason But Has None

If `DetectBackward` returns a `BackwardReasonError` (reason required but not provided), `TransitionStatus` returns early with the error. No status update and no history. Correct behavior.

### EC-4: Forced Backward Transition

When `opts.Force == true` and the transition happens to be backward, `isBackward` may be true or false depending on `DetectBackward` behavior (force=true suppresses error but may still detect backward). The history record has `Forced == true`. Whether `isBackward` is also true is determined by the existing `DetectBackward` logic; the history recording step should use both `isBackward` and `opts.Force` independently.

### EC-5: All Optional Fields Nil Simultaneously

A transition with `opts.Agent == ""`, `opts.Reason == ""`, `isBackward == false`, `opts.Force == false` produces an `EntityHistory` with `ChangedBy == nil`, `Notes == nil`, `RejectionReason == nil`, `Forced == false`. This is valid and represents a simple status advance with no metadata.

### EC-6: Existing task_history Database Trigger

The existing `task_history` table has a trigger that creates records on task status changes. During the transition period (before T-E21-F08-007 removes/refactors the trigger), Task transitions may create duplicate history records: one from the trigger (in `task_history`) and one from `EntityService` (in `entity_history`). This is acceptable as a temporary coexistence -- the two tables serve different consumers during migration. T-E21-F08-007 addresses cleanup.

### EC-7: History Recording With Context Cancellation

If the context is cancelled between Steps 7 (status update succeeds) and 7.5 (history recording), the history Create call may fail due to context cancellation. Per Business Rule 1, this is non-blocking: the transition result is still returned successfully.

- **Interface location**: `EntityHistoryRecorder` defined in `internal/services/entity_service.go` (point-of-use, per Go best practice and ADR-T004-2 from T-E21-F08-004)
