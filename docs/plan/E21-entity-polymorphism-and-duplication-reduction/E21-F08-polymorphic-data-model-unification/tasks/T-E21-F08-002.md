# EntityHistory Model and Validation

## Goal

Create the `EntityHistory` model struct in `internal/models/entity_history.go` with structural validation, and optionally the `EntityDocumentLink` struct. This model represents status change audit trail entries for any entity type and is consumed by EntityHistoryRepository (T-E21-F08-004) and EntityService (T-E21-F08-006).

## Why

The existing `TaskHistory` model is task-specific: it has `TaskID int64` and validates against task-only status values via `ValidateTaskStatus()`. A new polymorphic `EntityHistory` model is needed with `EntityType` + `EntityID` fields to support history for all 5 entity types (epic, feature, task, bug, change). See [02-architecture.md ADR-2](../tech/02-architecture.md#adr-2-new-entityhistory-model-not-extending-taskhistory) for the decision rationale.

**Feature PRD Traceability**:
- REQ-F-002 (Polymorphic Entity History Table) -- this task provides the Go model for the table
- Feature Story 2 ("status change history for all entity types") -- EntityHistory is the domain model backing this story

## User Stories

### Story 1: Polymorphic History Model

As a developer implementing EntityHistoryRepository (T-E21-F08-004),
I want an `EntityHistory` struct with `EntityType` and `EntityID` fields that mirrors the `entity_history` table schema,
so that I can use it for database read/write operations on polymorphic history records.

### Story 2: Structural Validation

As a developer integrating history recording into EntityService (T-E21-F08-006),
I want `EntityHistory.Validate()` to reject structurally invalid records before they reach the database,
so that the repository layer does not need to handle malformed data.

### Story 3: JSON Serialization

As a developer building the `shark status history` CLI output,
I want all `EntityHistory` fields to have JSON tags with appropriate `omitempty` for nullable fields,
so that JSON output renders cleanly for both CLI and API consumers.

## Business Rules

1. **Separation from TaskHistory**: The `EntityHistory` struct is a new, independent type. The existing `TaskHistory` struct in `internal/models/task_history.go` is NOT modified. Both structs coexist. Per ADR-2, this avoids breaking existing callers and conflating two concepts.

2. **Structural validation only**: `Validate()` checks field presence and type constraints (non-empty, positive, valid enum). It does NOT validate that status values are valid workflow statuses. Status value validation is the service layer's responsibility via `workflow.Service`.

3. **EntityType reuse**: The `EntityType` type alias and `ValidEntityTypes` map already exist in `internal/models/entity_note.go`. The `EntityHistory` struct reuses these directly -- it does NOT define its own entity type constants. This ensures consistency across `entity_notes`, `entity_history`, and `entity_documents`.

4. **Append-only semantics**: `EntityHistory` records are append-only in the database. The model does not need an `Update` or `Delete` method. However, this is a database/repository concern -- the model itself does not enforce this.

5. **Forced field default**: `Forced` defaults to `false` (Go zero value for `bool`). When constructing an `EntityHistory` without setting `Forced`, it naturally defaults to the correct value. The database column uses `INTEGER NOT NULL DEFAULT 0`, which aligns.

## Edge Cases

### EC-1: Empty String vs Nil for FromStatus

`FromStatus` is `*string`. An initial status assignment (entity just created) has `FromStatus = nil`. A transition from an explicit status has `FromStatus` pointing to a non-empty string. The case of `FromStatus` pointing to an empty string (`""`) is structurally allowed by `Validate()` but should be avoided by callers -- the repository or service layer should set `nil` for initial transitions, not `""`. The model does not enforce this distinction.

### EC-2: Whitespace-Only ToStatus

`Validate()` checks `ToStatus == ""` (empty string). A value like `"  "` (whitespace only) passes structural validation. The service layer is responsible for ensuring status values are meaningful via `workflow.Service.ValidateStatus()`. This is consistent with how `EntityNote.Validate()` uses `strings.TrimSpace` for content but not for entity_type.

**Decision**: Do NOT use `strings.TrimSpace` on `ToStatus` in the model. Status strings are identifiers (e.g., "in_progress") that never contain leading/trailing whitespace in practice. Adding TrimSpace would create an inconsistency with `TaskHistory.Validate()` which also uses direct `== ""` comparison.

### EC-3: All Nullable Fields Nil Simultaneously

An `EntityHistory` with `FromStatus = nil`, `ChangedBy = nil`, `Notes = nil`, `RejectionReason = nil` is valid. This represents an initial status assignment with no agent, no notes, and no rejection reason. `Validate()` accepts this.

### EC-4: JSON Omitempty Behavior

Nullable fields tagged with `omitempty` will be omitted from JSON output when nil. Non-pointer fields (`ID`, `EntityType`, `EntityID`, `ToStatus`, `Forced`, `ChangedAt`) are always included, even at zero values. This means `Forced: false` appears as `"forced": false` in JSON (not omitted), which is the desired behavior for a boolean flag.

### EC-5: Package Import Constraints

`entity_history.go` must import only: `errors`, `fmt`, `time`. It must NOT import `workflow`, `config`, or any other package that would create a dependency on runtime configuration. This aligns with the project rule that models contain structural validation only.
