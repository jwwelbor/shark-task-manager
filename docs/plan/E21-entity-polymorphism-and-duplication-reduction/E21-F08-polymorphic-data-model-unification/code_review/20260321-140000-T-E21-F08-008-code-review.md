## Code Quality Assessment

### Thin Wrapper Pattern (AC-11)
The `runStatusHistory` function follows the correct thin wrapper pattern:
1. **Parse arguments** (lines 558-568): `ParseGetArgs` + entity type normalization
2. **Call service** (lines 571-579): `cli.GetEntityHistoryService().GetHistory()`
3. **Format output** (lines 582-641): Limit truncation, mapping, JSON/table output

No repository imports, no workflow checks, no business logic in the command. This is clean.

### ADR-1: change_card Normalization
Line 564: `if entityType == "change_card" { entityType = "change" }` -- correctly normalizes before calling the service. This matches the pattern used elsewhere in the codebase (e.g., `dispatchTransition` has separate `case "change":` and `case "change_card":` branches).

### ADR-2: Legacy Task History Untouched
The old `shark task history` subcommand (which queries `task_history` table) is unmodified. The `shark status history` command now uses the polymorphic `entity_history` table for all entity types including tasks. This is the correct design -- two paths coexist.

### EntityHistory to StatusHistoryEntry Mapping (BR-2)
Lines 586-601 correctly map:
- `ChangedAt` -> `Timestamp` via `time.RFC3339` format
- `FromStatus` -> `OldStatus` with nil dereference (empty string if nil)
- `ToStatus` -> `NewStatus` direct copy
- `ChangedBy` -> `Agent` with nil dereference
- `Notes` -> `Notes` with nil dereference

### Command Metadata
Lines 126-151: `statusHistoryCmd` metadata updated to reflect all 5 entity types with key format examples. The old "only available for tasks" messaging is gone.

### Error Handling
- Not-found errors correctly exit with code 1 (line 576)
- General errors wrapped with context (line 578)
- Service accessor `GetEntityHistoryService` verified to exist at `services_global.go:410`

## Issues Found

None blocking. The implementation is clean, follows the thin wrapper pattern, and all acceptance criteria are met.

### Minor Observations (Non-Blocking)

1. **os.Exit(1) in command handler** (line 576): The project has a documented preference for returning typed errors over calling `os.Exit()` directly. However, this matches the pattern used by `handleStatusTransitionError` and other commands in the same file, so it is consistent with the existing codebase.

2. **Test approach**: The status history tests verify mapping/serialization logic inline rather than invoking the Cobra command with mocked services. While full command-level tests with mock injection would be more comprehensive, the chosen approach adequately tests the new mapping logic and is consistent with the existing test patterns in this file.
