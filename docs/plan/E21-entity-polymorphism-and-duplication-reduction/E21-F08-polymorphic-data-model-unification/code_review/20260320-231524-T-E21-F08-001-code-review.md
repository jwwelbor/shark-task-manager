## Architectural Deviations (Acceptable)

### 1. task_history TABLE Retained (Deviation from AC-7/AC-9)

The spec states that `task_history` should be dropped (AC-7) and not created on fresh databases (AC-9). The implementation keeps `task_history` TABLE for backward compatibility with existing `TaskHistoryRepository` code, deferring the drop to T-E21-F08-004.

**Assessment**: This is a REASONABLE deviation. Dropping `task_history` before the repository code is migrated would break existing functionality. The developer documented this decision clearly in code comments and the test validates the current behavior. Data is correctly copied to `entity_history` as required.

### 2. Compatibility Views and INSTEAD OF Triggers (Enhancement)

The spec did not specify backward-compatible views. The implementation creates views for the old table names (`epic_documents`, `feature_documents`, etc.) with INSTEAD OF INSERT/DELETE triggers that redirect operations to `entity_documents`.

**Assessment**: This is an EXCELLENT addition. It provides a gradual migration path so that existing repository code continues working without modification until downstream tasks refactor it. This prevents the need to update all repository code in a single task, which would have been risky.

### 3. Display Data View Updates

The display data views (`epic_display_data`, `feature_display_data`, `task_display_data`) were updated to query `entity_documents` instead of the old per-entity tables. This was not explicitly listed in the scope but is necessary for correctness.

**Assessment**: Required for correctness. The display views would break if they referenced dropped tables.

## Code Quality Assessment

### Strengths

1. **Migration function decomposition**: Clean separation into `createPolymorphicTables`, `migrateDocumentDataToPolymorphic`, `migrateHistoryDataToPolymorphic`, `verifyPolymorphicMigration`, `dropOldDocumentAndHistoryTables` -- each function has a single responsibility.

2. **Idempotency guards**: Proper early return when migration is complete, INSERT OR IGNORE for documents, COUNT check for history.

3. **EC-4 FK filter**: Document migration correctly filters by `WHERE document_id IN (SELECT id FROM documents)`, and the verification counts use the same filter. This prevents phantom FK violations.

4. **Existing migration functions updated**: `migrateTaskHistoryRejectionReason`, `migrateTaskDocumentsLinkType`, and `migrateBugAndChangeCardDocuments` all correctly skip when old tables no longer exist.

5. **Error wrapping**: Consistent `fmt.Errorf("context: %w", err)` pattern throughout.

6. **Test isolation**: Each test creates its own in-memory database, no test data leakage.

### Minor Observations (Non-Blocking)

1. **Duplicate table/index creation**: The `createPolymorphicTables` function duplicates DDL that already exists in `createSchema`. On a fresh DB, both are executed (harmless due to `IF NOT EXISTS`). This is acceptable for migration safety but could be refactored in a future cleanup.

2. **Compatibility trigger duplication**: `createPolymorphicCompatibilityTriggers` and `createPolymorphicCompatibilityViews` both create the same triggers. The former runs early in `ApplySchemaAndMigrations` and checks if views exist (skipping if not), while the latter runs as part of the migration. This ordering ensures triggers exist regardless of entry path. Correct but slightly complex -- well-documented.

3. **`fmt.Sprintf` for table names in DROP/CREATE**: Table names are hardcoded string literals, not user input, so there is no SQL injection risk. This matches existing patterns in the codebase.

## Security Assessment

- No user input is interpolated into SQL; all entity_type values are hardcoded string literals.
- FK constraint on `entity_documents.document_id` is maintained via REFERENCES clause.
- No new attack surface introduced.

## Performance Assessment

- `INSERT INTO ... SELECT FROM` is a single-pass bulk operation (efficient for SQLite).
- Composite indexes on `(entity_type, entity_id)` ensure O(log n) lookups.
- Three indexes on `entity_history` support all expected query patterns.
- Migration runs once at startup (~200ms for typical datasets).
