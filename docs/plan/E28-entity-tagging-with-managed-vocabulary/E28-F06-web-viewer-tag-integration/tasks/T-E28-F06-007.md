# Add tag chips and filter control to viewer.html UI

## Goal
Add inline CSS and vanilla JS to `viewer.html` that: (1) fetches the vocabulary
from `GET /api/v1/viewer/tags` on boot via `loadVocabulary()`; (2) renders
`.tag-chip` elements on each of the six entity detail views via
`renderTagChips(entity)`; and (3) mounts a multi-select filter control in the
hierarchy sidebar via `renderTagFilterControl()`. No new external dependencies.
No mutation controls. Graceful empty-vocabulary state. This task covers UI-only
changes; no automated test is written (manual UAT per test-plan.md §1 AC-11
through AC-13).

Note: This task is the one exception to TDD co-location — `viewer.html` is a
single-file UI asset with no Go test infrastructure; AC-11 through AC-13 are
manual UAT items per spec.md §2.6 item 5.

## Scope
- Files to modify:
  - `internal/viewer/assets/viewer.html`

- AC-T2: `renderTagChips(entity)` returns null when `entity.tags` is empty;

- AC-T5: No "add tag", "rename tag", or "delete tag" control anywhere in the
  added markup or JS.

## UAT Rejection (2026-04-25)

**Classification:** AC Violation
**Unmet criteria:** AC-12 / REQ-F-017 — "User-selected chips are appended to
subsequent list fetches as `?tag=<name>` repeated params" on "every list view
(hierarchy sidebar and any list-like surface that reads from
`GET /api/v1/viewer/hierarchy` or `GET /api/v1/viewer/features/{key}/tasks`)."

**What happened:** The hierarchy filter wiring is correct. But the
feature-tasks list path is not tag-aware:
- `apiGetFeatureTasks(key)` at `internal/viewer/assets/viewer.html:1928-1933`
  takes only `key` and calls `/features/${key}/tasks` with no query string.
- Chip clicks at `viewer.html:4842-4855` only call `applyTagFilter(...)` which
  only refetches hierarchy via `apiGetHierarchy(...)` (`viewer.html:2044-2055`).
- No call site forwards `activeTagFilter` into a feature-tasks fetch.

**Fix required:**
1. Extend `apiGetFeatureTasks(key, tags)` to accept an optional `tags` array
   and append repeated `?tag=` params (mirror the helper used at
   `viewer.html:1835` for hierarchy).
2. Update the feature-tasks render path (every place that calls
   `apiGetFeatureTasks`) to pass `Array.from(activeTagFilter)` when the filter
   is non-empty.
3. Ensure `applyTagFilter()` (or a sibling) refetches the visible feature
   tasks list — not only the hierarchy — when chips toggle.
4. Add a manual UAT note in the test plan covering the feature-tasks
   refetch path so the regression cannot reappear silently.
