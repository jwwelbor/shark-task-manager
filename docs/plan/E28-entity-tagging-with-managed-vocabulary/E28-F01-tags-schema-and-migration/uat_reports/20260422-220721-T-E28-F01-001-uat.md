## Red-team findings (independent probes)

I wrote and executed three additional tests inside `internal/db/` that the supplied QA suite did not include. All passed; probe files were removed after verification.

### RT-1: Cascade correctness for ALL SIX entity types (not just epic)

The shipped functional trigger test (`TestMigration_EntityTagsCascadeDeleteTriggers_FunctionalEpic`) only verifies epic. I inserted parents of every type (epic, feature, task, bug, change_card, idea), attached a tag to each, deleted each parent, and asserted `entity_tags` reached zero rows. **Result: PASS.** All six triggers fire on direct `DELETE FROM <parent>`.

### RT-2: Trigger fires on FK-cascade chains (epic → feature → task)

The existing FKs `features.epic_id ON DELETE CASCADE` and `tasks.feature_id ON DELETE CASCADE` propagate deletes. I verified that a single `DELETE FROM epics WHERE id=?` with feature+task children and tags attached at all three levels results in **all three** `entity_tags` rows being deleted via the trigger chain. **Result: PASS.** SQLite's `PRAGMA foreign_keys = ON` plus `recursive_triggers` defaults are sufficient; no manual configuration is needed in the migration.

### RT-3: `tag_id` FK `ON DELETE CASCADE` and `tags.name UNIQUE COLLATE NOCASE`

Deleting a `tags` row cascades to every `entity_tags` row referencing it (FK behavior — not a trigger). `INSERT INTO tags (name) VALUES ('Voice')` after `'voice'` correctly fails UNIQUE. **Result: PASS.** Matches ADR-4's canonical-lowercase guarantee at the storage layer.

### Gaps considered and cleared

- **Schema version mismatch on Turso vs local.** `ApplySchemaIfNeeded` reads `version < CurrentSchemaVersion` and re-runs migrations (`db.go:454`). Bumping the constant to 14 forces re-migration on any existing database that recorded 13. Idempotent DDL means a v14 DB double-running the function is a no-op (verified by `TestMigration_DirectMigrateAddTagsAndEntityTags`). Turso `skip_migrations: true` path is correctly handled because the version-gate still re-triggers when the stored version is behind.
- **CHECK constraint values match the 6 entity types exactly.** `db.go:3317–3318`: `('epic', 'feature', 'task', 'bug', 'change', 'idea')` — exact match to architecture.md §3.1 and ADR-10. Note that the `entity_type` value for change-cards is the string `'change'`, not `'change_card'`; this is consistent across triggers (line 3374 uses `entity_type = 'change'`) and the CHECK constraint, so internal consistency is preserved. Downstream repositories must use `'change'` when writing; that is a concern for F02/F03 tasks, not this one.
- **Index naming.** Architecture.md §3.1 specifies `idx_tags_name`, `idx_tags_created_at`, `idx_entity_tags_entity`, `idx_entity_tags_tag`, `idx_entity_tags_tag_entity`. Implementation uses these exact names (`db.go:3304, 3307, 3327, 3332, 3337`). PASS.
- **SQL injection surface.** Migration uses only static DDL strings with no parameter interpolation from external input. No injection surface.
- **Adversarial input paths.** The migration function takes only `*sql.DB`. No attacker-controlled input. DDL runs against a trusted local/Turso database. The `entity_type` CHECK acts as a second-line defense for malformed writes at the data layer regardless of service-layer validation.
- **Integration with existing `InitDB`/`runMigrations`.** `ApplySchemaAndMigrations` → `createSchema` → `createPolymorphicCompatibilityTriggers` → `runMigrations` → `setSchemaVersion(14)` (lines 412, 419, 424, 429). Parent tables (`epics`, `features`, `tasks`, `ideas`) exist in `createSchema` (baseline). `bugs` and `change_cards` are created by `migrateBugAndChangeCardTables` (line 750), which runs BEFORE `migrateAddTagsAndEntityTags` (line 827). Therefore every parent table referenced by a cascade trigger exists at trigger-creation time. PASS.
