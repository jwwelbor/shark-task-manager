## 2. Red-Team Probes (Beyond AC Literalism)

### 2.1 Regex exactness against ADR-4

ADR-4: `^[a-z0-9][a-z0-9-]{0,63}$`. Implementation (`tag.go:14`):
`regexp.MustCompile(`^[a-z0-9][a-z0-9-]{0,63}$`)` — **byte-for-byte identical**.

### 2.2 Trailing-hyphen permissiveness

The regex permits names like `voice-`, `a-`, `voice-auth-`. I confirmed this
with a scratch script (`"voice-"` → true, `"a-"` → true, `"voice-auth-"` → true).

ADR-4 is silent on trailing hyphens; the rationale mentions URL-slug interop
but does not explicitly forbid trailing hyphens. The regex in ADR-4 (which is
the normative statement) explicitly allows them. Implementation matches spec.
**Not a defect.** Noted as a follow-up consideration if future ADRs revisit
display-name rules.

### 2.3 Lowercase-before-regex — intent check

`strings.ToLower("Tag")` → `"tag"` → matches regex. This is the **explicit**
ADR-4 behavior: "Input is lowercased via `strings.ToLower` before validation."
The test case `uppercase_input_passes_after_lowercasing` (`tag_test.go:100-104`)
codifies the same intent. Correct.

### 2.4 Unicode edge cases

Scratch-tested:
- `"voiçe"` → rejected (correct — `ç` is not in `[a-z0-9-]`)
- `"İ"` (Turkish capital I-dot) → `strings.ToLower` yields `"i"` in Go's default
  mapping → passes as a single-char slug. This is a non-issue because the
  result is a valid ASCII slug; the caller only ever sees lowercase-ASCII
  output. **No security or consistency concern.**
- Control chars, tabs, newlines — all rejected by the regex.

### 2.5 EntityTypeIdea integration side-effects

Consumers of `ValidEntityTypes` audited end-to-end:

| Consumer | Call shape | Effect of adding `idea` |
|---|---|---|
| `internal/models/entity_note.go:47` (`EntityNote.Validate`) | gate check | Now accepts `idea` at Go layer |
| `internal/models/entity_history.go:36` (`EntityHistory.Validate`) | gate check | Now accepts `idea` at Go layer |
| `internal/models/entity_relationship.go:86,89` (`EntityRelationship.Validate`) | gate check | Now accepts `idea` at Go layer |
| `internal/repository/entitydoc/repository.go:24` | gate check | Now accepts `idea` at Go layer |
| `internal/cli/commands/notes_search.go:98` | gate check | Now accepts `idea` at Go layer |
| `internal/cli/commands/notes_search_integration_test.go:262` | gate check in test helper | Now accepts `idea` at Go layer |

**Critical observation:** The DB-level CHECK constraints do **not** yet include `idea`:
- `entity_notes` CHECK: `('epic', 'feature', 'task', 'bug', 'change')` (`db.go:2272`)
- `entity_relationships` CHECK: `('epic','feature','task','bug','change')` (`db.go:2991-2997`)

An attempt to insert `idea` into either table would pass Go-level validation
but fail at SQL execution with a CHECK-constraint violation. This divergence
is **explicitly blessed by ADR-10**:

> The CHECK constraint on `entity_notes.entity_type` does **not** need to grow
> for E28 — entity_tags has its own … CHECK constraint.

Since this task scope is "models only" and no repository code calls any of
these entity-note / entity-relationship INSERTs with `entity_type=idea`, there
is **no runtime regression** from this change. The divergence is contained to
the model layer and matches the documented design intent.

### 2.6 Regression check on test enumeration

Concern: does any test count or enumerate `ValidEntityTypes` in a way that
would fail when a new entry is added?

Grep findings: all existing tests check for presence of **specific** entity
types (`ValidEntityTypes[EntityTypeChange]`, etc.) — none count map length or
compare against a closed set that excludes `idea`. The new test
`TestValidEntityTypes_ContainsAllExpected` (`tag_test.go:191-207`) uses a
closed list that includes `EntityTypeIdea`, which is the correct pin. **No
regression risk.**

### 2.7 Struct-tag consistency

Both `Tag` and `EntityTagLink` use `json:"..." db:"..."` ordering — identical
to `EntityNote` (`entity_note.go:35-43`) and existing models. ✓

### 2.8 Log-injection / error message safety

control characters (newlines, ANSI escapes, etc.). Log-injection-safe per

## 3. Findings Summary

**Blockers:** None.

**Advisories (documented, deferred):**
1. DB CHECK constraints for `entity_notes` and `entity_relationships` do not
   include `idea`. This is per ADR-10 and intentional; any future task that

   CHECK or avoid those tables. Recommend adding a follow-up note on the
   F02 schema task (which creates `entity_tags` with the correct wider CHECK).
2. Regex allows trailing hyphens. ADR-4 permits this; if the epic later wants
   strict URL-slug conformance, this can be tightened in a follow-up ADR
   without data migration (it only narrows the accepted set).
3. Spec path reference to non-existent `internal/models/entity_type.go` —
   minor documentation improvement for future task specs.
