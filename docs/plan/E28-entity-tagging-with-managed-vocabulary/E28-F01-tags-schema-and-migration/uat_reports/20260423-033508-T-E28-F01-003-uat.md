### Probe 2 — ADR-9 transaction ordering (entity_tags deleted BEFORE tag row)

**By inspection** (`tag_repository.go` lines 217–264):

| Step | Line | SQL | Inside tx? |
|---|---|---|---|
| BEGIN | 217 | `BeginTxContext` | — |
| existence check | 225 | `SELECT COUNT(1) FROM tags WHERE id = ?` | yes |
| usage count | 234 | `SELECT COUNT(1) FROM entity_tags WHERE tag_id = ?` | yes |
| delete entity_tags rows (force=true branch) | 244 | `DELETE FROM entity_tags WHERE tag_id = ?` | yes |
| delete tag row | 250 | `DELETE FROM tags WHERE id = ?` | yes |
| COMMIT | 262 | `tx.Commit()` | — |

Ordering is correct: **entity_tags rows are deleted first, tag row second,
both in the same transaction.** `defer tx.Rollback()` on line 221 guarantees
atomicity on any error.

**By test** (transient probe, since removed): inserted 8 `entity_tags` rows
across all 6 entity types (epic, feature, task, bug, change, idea) for a
single tag_id; called `Delete(force=true)`; counted remaining rows. Result:
**0 orphans.** Tag row also gone.

**Observation (non-blocking):** even if ordering were inverted, the
`entity_tags.tag_id REFERENCES tags(id) ON DELETE CASCADE` FK (db.go:3320)
would cover it. The current explicit ordering is belt-and-suspenders, which
is good practice. No issue.

### Probe 3 — ADR-8 Rename does NOT rewrite entity_tags rows

**By inspection** (`tag_repository.go` lines 165–197): the method issues
exactly one statement — `UPDATE tags SET name = ?, updated_at = CURRENT_TIMESTAMP WHERE id = ? RETURNING ...`.
There is no SQL touching `entity_tags`.

**By test** (transient probe, since removed): inserted an `entity_tags` row,
captured its `id` and `created_at`; called `Rename`; re-read the row. Result:
both `id`, `tag_id`, and `created_at` are byte-identical. The row was **not
rewritten**. `TestTagRepository_Rename` already asserts `renamed.ID == original.ID`.

### Probe 4 — SQL injection resistance (parameterized queries only)

Searched `internal/repository/tag/` for SQL concatenation antipatterns:

```bash
grep -n "fmt.Sprintf\|format.Sprintf\|\"[^\"]*\" +\|+ \".*FROM\|+ \".*WHERE" internal/repository/tag/*.go

```

Every SQL statement in both `tag_repository.go` and `entity_tag_repository.go`
uses `?` positional placeholders. The only `fmt.Errorf` / `fmt.Sprintf` calls
build error messages, not SQL. **Zero injection surface.**

### Probe 6 — Attach idempotency (no duplicate rows, no error)

**By inspection:** `Attach` uses `INSERT OR IGNORE INTO entity_tags ...`
(line 44). The `UNIQUE(entity_type, entity_id, tag_id)` constraint
(db.go:3322) guarantees the second insert is a no-op; `OR IGNORE` suppresses
the conflict error.

**By test:** `TestEntityTagRepository_Attach_Idempotent` attaches the same
tuple twice, asserts no error on second call, then asserts `ListByEntity`
returns exactly 1 link. Passes.

### Probe 7 — All 6 entity_type values accepted by CHECK constraint

Schema (db.go:3317–3318):
```sql
entity_type TEXT NOT NULL CHECK (entity_type IN
    ('epic', 'feature', 'task', 'bug', 'change', 'idea'))
```

**By test** (transient probe, since removed): direct SQL insert of each of
the 6 declared types succeeds. Also verified negative cases: `'bogus'` is
rejected (CHECK fires) and — importantly — `'tech_debt'` is rejected. The
`entity_tags` CHECK correctly excludes `tech_debt` even though the Go enum
contains `EntityTypeTechDebt`. This matches architecture.md ADR-10's careful
statement: "The CHECK constraint on `entity_notes.entity_type` does **not**
need to grow for E28 — entity_tags has its own (looser, for now, or
identical) CHECK constraint."

**Observation (non-blocking):** `models.EntityType` enumerates
`tech_debt` but `entity_tags` CHECK rejects it. The repository does not guard
against this; a service passing `EntityTypeTechDebt` would receive a
constraint error. This is acceptable for a repository layer (enforcement at
service layer per architecture §1.3), but `TagService` (F02) should
explicitly validate the tag-specific entity-type set before calling the repo.
This is a **note for F02**, not a defect here.

### Probe 9 — Sentinel error propagation through fmt.Errorf("…: %w", err)

Three sentinels declared: `ErrTagInUse`, `ErrTagConflict`, `ErrTagNotFound`.

Each is always wrapped with `%w`:
- `ErrTagConflict`: lines 67 (Create), 192 (Rename) — both wrapped.
- `ErrTagNotFound`: lines 93 (GetByName), 120 (GetByID), 188 (Rename), 229 (Delete existence check), 259 (Delete rows==0) — all wrapped.
- `ErrTagInUse`: line 239 (Delete) — wrapped.

Tests use `errors.Is(err, tag.ErrTagXxx)` exclusively — this is the correct
check for `%w`-wrapped sentinels (e.g.,
`TestTagRepository_Rename_ConflictReturnsErrTagConflict` line 268,
`TestTagRepository_Delete_InUse_ForceFalse_ReturnsErrTagInUse` line 323).
Propagation works.

### Non-Blocking (informational, for downstream tasks)

1. **`isUniqueConstraintError` uses substring match** (tag_repository.go:269).
   Already flagged by code review; acceptable because the fallback returns
   the wrapped raw error (no data-integrity risk). Consider replacing when a
   typed sentinel becomes available from the driver.

2. **`tech_debt` is in `models.EntityType` but rejected by `entity_tags`
   CHECK.** Repository is type-agnostic and does not guard. `TagService` (F02)
   should validate the tag-specific 6-type set (epic, feature, task, bug,
   change, idea) before calling the repo, so users see a clean service-layer
   error rather than a raw SQL CHECK violation. **Flag for F02 design.**

3. **Polymorphic CHECK coverage.** The shipped tests only exercise `epic`
   through fixtures; the other 5 types are only exercised through direct SQL
   in the red-team probes (which were removed after verification). Not a
   defect in T-003 — F02–F06 will exercise the remaining types naturally as
   they wire up each entity type.

None. All ACs have explicit code + test evidence.
