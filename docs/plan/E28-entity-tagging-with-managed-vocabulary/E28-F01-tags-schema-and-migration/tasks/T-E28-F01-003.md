# Implement TagRepository and EntityTagRepository

## Goal

Create the new `internal/repository/tag/` package with two repository types: `TagRepository` for vocabulary CRUD and `EntityTagRepository` for polymorphic join-table operations. These are the only data-access components that F02–F06 build on; no business logic lives here.

## Scope

- Files to create: `internal/repository/tag/tag_repository.go`, `internal/repository/tag/entity_tag_repository.go`, `internal/repository/tag/interfaces.go`

## Acceptance Criteria

See architecture.md §1.1 (repository layer), §1.3 (service layering — repositories own SQL only), ADR-1 (polymorphic join), ADR-8 (rename semantics), ADR-9 (remove with usage check).

Additional task-specific criteria:
- AC-T1: `TagRepository` implements Create, GetByName, GetByID, List, Rename, Delete methods using parameterized queries exclusively.
- AC-T2: `EntityTagRepository` implements Attach, Detach, ListByEntity, ListByTag, CountByTag methods.
- AC-T3: `TagRepository.Delete` accepts a `force bool` parameter; when `false` and `CountByTag > 0`, returns a typed `ErrTagInUse`; when `true`, deletes `entity_tags` rows in the same transaction (per ADR-9).
- AC-T4: `TagRepository.Rename` issues a single `UPDATE tags SET name = ?` with no touch to `entity_tags` (per ADR-8); returns typed `ErrTagConflict` if target name already exists.
- AC-T5: Package exports interface types in `interfaces.go` so `TagService` depends on interfaces, not concrete structs.
- AC-T6: No business logic, no config reads, no password checks in either repository.

## Test Cases

Integration tests in T-E28-F01-004 exercise all methods against the real test DB. Unit-level: none required here beyond compiler satisfaction (business rules belong in service tests using mocks).

## Design Reference

See architecture.md §1.3 (layering diagram), §3.1 (table + index shapes for query construction), ADR-5 (AND-join SQL shape for `ListByTag` with multiple tags), ADR-8, ADR-9.
