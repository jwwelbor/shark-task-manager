# E40-F01 — Benchmark corpus v1: fixture repo and screened tasks

This specification is incremental over the [epic PRD](../epic.md) (§2 goals G1/G4/G5/G7, §3 Phase 1 scope, §4 constraints) and the [epic architecture](../architecture.md), whose [Corpus and oracle contract](../architecture.md#corpus-and-oracle-contract) already pins the I-01 payload this feature implements rather than invents. Mechanics context lives in [shark-bench-design.md](../shark-bench-design.md) §2–§4. The [research report](research-report.md) Capability map governs what is reused: the I-01 contract and the "new lint issues only" diff are **NEW**; the `fmt`/`vet`/`lint`/`test` gate sequence is **REUSE (pattern)**; `internal/reporting` and `internal/sharkdata/default_data/manifest.yaml` are **CONTRADICTS** and are not touched.

| `bench/corpus/negative/<item_id>/` | New. Same layout; deliberately broken candidates for the rejection path. |
| `bench/corpus/ledgers/<base_sha>/tests.json` | New. Base-SHA test ledger (REQ-F-008) plus its toolchain block. |

| `bench/scripts/checkout-fixture.sh` | New. `checkout-fixture.sh <base_sha> <dest_dir>` — clones `bench/fixture-repo` locally into a temporary path and checks out `base_sha`. Shared by the gate, the ledger builder, and (later) E40-F02. Its exit path invokes `verify-clean-checkout.sh` **unconditionally** on every checkout it produces, so the held-back-test invisibility guarantee reaches every current and future caller structurally rather than by convention. |
| `bench/scripts/verify-clean-checkout.sh` | New. `verify-clean-checkout.sh <checkout_dir> <corpus_yaml_path>` — derives every held-back F2P file name and test name across all admitted and negative items in `<corpus_yaml_path>`, greps `<checkout_dir>` for each, fails naming the first hit, and prints `CLEAN` on stdout on success. Executes AC-001. |
| `bench/scripts/build-ledgers.sh` | New. `build-ledgers.sh <checkout_dir> <output_dir>` — runs the fixture's own `fmt`/`vet`/`lint`/`test` targets at the base SHA and writes both ledgers. It **records** the current toolchain into each ledger it writes and never **compares** one; toolchain comparison belongs solely to `diff-ledgers.sh --toolchain-guard`. |
| `bench/scripts/diff-ledgers.sh` | New. Two invocation shapes. `diff-ledgers.sh --kind=<lint\|test> --base=<base-ledger.json> --post=<post-ledger.json>` implements REQ-F-011's exact semantics — multiset difference over the REQ-F-009 identity floored at zero for `--kind=lint`; pass→fail as regression and present-then-absent as removed, reported in separate fields, for `--kind=test`. It takes two ledger-shaped JSON files and needs no fixture checkout, so it is drivable from hand-authored synthetic data. `diff-ledgers.sh --toolchain-guard --base=<ledger.json>` reads that ledger's toolchain block and the live environment and exits non-zero naming the mismatched field(s) *before* either diff mode runs. This script is the **single named owner** of the toolchain guard (REQ-F-010) and the executable E40-F02 invokes instead of re-deriving the method from prose. Executes AC-008, AC-009, AC-010. |
| `bench/scripts/admit.sh` | New. `admit.sh <corpus_yaml_path> [--item <id>]` — runs the five admission checks per candidate; emits a machine-readable verdict and a named failing check on rejection. |
| `bench/README.md` | New. Documents the manifest schema, the `p2p_set` resolution rule, and the REQ-F-011 diff method — the document E40-F02 reads instead of re-deriving semantics. |
| `tests/contracts/e40_i01_corpus_contract_test.go` | New, test-only. Validates the committed manifest and ledgers against the I-01 shape; follows the artifact-reading style of `tests/contracts/e39_interactions_test.go` in `package contracts`. |

### Data model changes

None. Per ADR-002, JSONL and committed files are the only store; no shark table, migration, or `CurrentSchemaVersion` bump is involved.

### Key technical decisions

**ADR-F01-01 — The fixture is a standalone git repository, wired in as a submodule; not a vendored directory.** `feature.md` and `architecture.md` both defer this to implementation, so it is closed here rather than left open. A vendored directory fails two hard constraints, not merely a preference. First, Epic PRD §4 forbids held-back tests entering the repo the agent sees; a vendored fixture makes the agent's `--workdir` a subdirectory of a shark checkout that also contains `bench/corpus/`, so the oracle is visible to the agent. Second, a vendored directory has no independent commit SHA — the manifest's pinned `fixture_base_sha` would be a *shark* commit, checking out at it would revert the corpus and harness with it, and `git diff --numstat <base_sha>` (architecture Metric collection) would span the whole shark repository instead of the fixture. A submodule is git's standard mechanism for exactly this: an independent SHA the parent pins, a working tree containing only fixture content, normal reviewable history, and clean-checkout reproducibility enforced by git. Accepted cost: a second repository must exist and be reachable once, at `git submodule update --init` — the same class of dependency as `go mod download`. The `test-fixtures/uat-test-project/` precedent named in research Finding 4 therefore does not transfer; it holds shark project state, not an independently-versioned Go module. Rejected alternatives: a git bundle committed as one binary blob (offline and self-contained, but the fixture source stops being reviewable in a diff), and a deterministic `git init` from committed sources at gate time (reproducible only under fragile assumptions about git version, file modes, and fixed author dates).

**ADR-F01-02 — Go-tool invisibility is structural, not conventional.** REQ-NF-002 is satisfied by two mechanisms rather than by discipline: the fixture's nested `go.mod` excludes it from the shark module's `./...` patterns (so `go build`, `go vet`, `go test`, and root `golangci-lint run` all skip it), and held-back F2P sources sit under a `testdata/` path segment, which the go tool ignores outright. This matters because F2P sources are *designed* to fail and generally will not even compile outside the fixture; without structural invisibility, committing the corpus turns CLAUDE.md's mandatory gate red on day one.

**ADR-F01-03 — Lint identity excludes line and column.** Any agent patch shifts line numbers. Including position in issue identity would report every pre-existing issue in a touched file as new, and `lint_new_issues` would measure diff size rather than quality. The tuple in REQ-F-009 is the smallest identity stable under position shifts; multiset counting keeps a genuinely duplicated issue from being masked by an identical pre-existing one.

**ADR-F01-04 — Ledgers are toolchain-pinned and fail closed.** Lint and test output are version-sensitive; `golangci-lint` is pinned at `v2.9.0` in `Makefile:108` and the Go toolchain at `go 1.25.0` in `go.mod`. A ledger diffed under a different toolchain produces noise indistinguishable from signal, and G7 replay reaches these ledgers transitively through E40-F02 (research Finding 5). Recording the toolchain and refusing to diff on mismatch converts a silent corruption into a loud failure — the same posture ADR-004 takes toward the `shark run` surface.

**ADR-F01-05 — The I-01 validator is a Go test in `tests/contracts/`, a deliberate narrow deviation from "zero Go changes".** Epic PRD §4 constrains F01–F03 to no changes to shark itself. A test-only file adds nothing to the shipped binary and changes no behaviour, and it buys something the alternative does not: the corpus contract runs under the repository's own `make test`, so manifest or ledger drift fails the standard gate rather than waiting for a bench run. It also reuses the established `tests/contracts` convention that E38 and E39 already set, giving E40-F02 a pointer in the shape the interaction map expects. A shell validator was rejected because nothing would run it.

Two consequences follow and are binding. First, **TC-001 must read only in-repo artifacts** — `bench/corpus/corpus.yaml`, the item directories, and `bench/corpus/ledgers/<base_sha>/*.json` — and must never require `bench/fixture-repo/` to be populated. `.github/workflows/ci.yml` checks out with `actions/checkout@v4`, which does not initialise submodules, so a TC-001 that touched the fixture tree would fail in CI and force a workflow change this feature otherwise does not need. AC-001, which does inspect the fixture tree, is therefore verified by `bench/scripts/` instead. Second, TC-001 goes red until the corpus artifacts it reads exist, so it is sequenced with or after them, never ahead of them.

### Integration with existing code

Nothing in `internal/` is called, extended, or imported. The three integration surfaces are conventions, not code paths:

- **Quality-gate sequence** — the fixture's `Makefile` mirrors this repository's `fmt`/`vet`/`lint`/`test` targets (`Makefile:86-121`) rather than inventing a check sequence, per research Decision 2. `.golangci.yml` is modelled on the root config and pinned to the same `golangci-lint v2.9.0`.
- **Contract-test convention** — `tests/contracts/e40_i01_corpus_contract_test.go` joins `package contracts` and follows the repository-root-relative artifact-reading helper style already used in `tests/contracts/e39_interactions_test.go` and `tests/contracts/e38_f12_parallel_team_topology_test.go`.
- **Scratch-environment discipline** — corpus tooling creates only temporary fixture checkouts and never invokes shark project initialisation, so `scripts/shark-scratch-env.sh` remains E40-F02's concern and the config-guardrail hook stays satisfied.
