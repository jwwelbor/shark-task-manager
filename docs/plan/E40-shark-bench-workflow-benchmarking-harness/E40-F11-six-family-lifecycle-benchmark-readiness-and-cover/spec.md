### 1.2 Functional requirements and acceptance criteria

Each row names the requirement, the observable behavior that closes it, and the
test case that proves it. Test case numbering continues the existing
`bench/scripts/tests/` sequence, whose current maximum is `tc098`.

#### REQ-F-001 — Preserve failed-run evidence

**AC-F11-01.** A retention-root guard rejects **every** operator subcommand
invoked against a registered retention root, **unconditionally** — regardless of
the retained result's recorded `status`, regardless of whether
`candidate_identity.head` matches the current candidate HEAD, and regardless of
which subcommand is used. The guard fires on all nine seams that acquire the
operator-root lock or write under the operator root: `setup`, `preflight`,
`prepare-replay`, `pilot`, `baseline`, `variant`, `validate-variant`, `compare`,
and
`demo` — CLI subcommand names, not Python function names — plus
`--retry-incomplete` on any of them. It names the registered
root and the registry entry that matched; it does not delete, move, or rewrite a
byte. Exit is non-zero with `OperatorError`.

*Supersedes the pre-rework criterion*, which fired only on
`status != completed` **and** a differing `candidate_identity.head`. That
conjunction left the registered root writable the moment either clause turned
false — a completed result, or a re-run at the same HEAD, would have passed the
guard while `feature.md` REQ-F-001 freezes the root unconditionally.

**AC-F11-01a.** The guard reads a committed retention registry
(`bench/retention-registry.yaml`), keyed by an opaque `registry_id`, whose entry
carries `root_path`, `registered_at`, `classification`, and
`tree_manifest_path`. No operator-specific absolute path appears anywhere in
`bench/` **source**; the path lives in the registry data file only. A registry
entry whose `root_path` resolves inside `REPO_ROOT` is itself a validation
error. A registry entry whose `root_path` does not exist on the current host is
a **no-match** and the guard allows the invocation: retention roots are
machine-local operator evidence, and a registry shared across machines must not
block a host that never held the root. Manifest verification for such an entry
reports `not_present_on_host`, distinct from both `match` and `mismatch`.

**AC-F11-01b.** Whole-tree digest invariance: registration records a
`tree_manifest` of every regular file under the root as sorted
`<relative-path> <sha256>` lines, plus the file count and total byte size.
Recomputing the manifest after any F11 validation run must reproduce the
registered manifest **byte-identically**. A single changed, added, removed, or
renamed file — anywhere in the tree, not only in `operator-result.json` — fails
the check with the differing path named. Symlinks are recorded by link target,
not followed.

**AC-F11-02.** The retained root is registered as feature evidence by path and
SHA-256 (values verbatim from `feature.md` §Observed evidence) in
`evidence/2026-09-04-retained-root.md`, classified `incomplete`, and cross-linked
to its `registry_id`. No F11 validation run writes into it; every F11 run uses a
new external operator root.

Test: `tc099_retained_root_immutability_test.sh` — see the decision table in
§7.3.1 for the full seam x condition enumeration.

#### REQ-F-003 — Spend-gated I-06 replay preparation

**AC-F11-06.** `e40-benchmark.sh prepare-replay --config <cfg> --scenario <id>`
without `--acknowledge-provider-spend` prints the proposed provider calls, model,
provider, effort, and every resource ceiling, makes **zero** provider calls,
writes nothing outside its preview directory, and exits non-zero. This argv
carries **no ceiling flags**, which is why they are parser-optional on this
subcommand (§7.2): under `required=True` the invocation would exit 2 at argparse
and the preview this criterion specifies could never run.

**AC-F11-06a.** The fourth ceiling is `--max-provider-calls`, and it is
**threaded end to end**, not merely accepted by `prepare-replay`.

*What exists today* (read 2026-09-04): `add_execution_arguments`
(`bench/scripts/lib/e40_benchmark.py:4436-4448`) declares exactly three
ceilings — `--max-cost-usd`, `--max-wall-clock-seconds`, and
`--max-generated-tasks`, each `required=True`. `grep -rn
'max_provider_calls\|max-provider-calls' bench/` returns **nothing**: the
provider-call ceiling is absent from every layer. The previous revision named
it only on the planned `prepare-replay` subcommand and then justified it with
generated-task reasoning, which described a ceiling that already existed. That
confusion is the defect; this criterion replaces it.

*What this feature adds.* `max_provider_calls` appears at each of the eight
seams the three existing ceilings already occupy, and F11 is not satisfied by
any subset:

| # | Seam | File:line (current) | Required change |
|---|---|---|---|
| S1 | Execution arg parser | `e40_benchmark.py:4445-4447` | Add `--max-provider-calls`, `required=True` — so `pilot`, `baseline`, and `variant` all inherit it |
| S2 | `prepare-replay` parser | new (§2.3.6) | Same four flag **names**, but **parser-optional and handler-required** — mandatory only under `--acknowledge-provider-spend`, so the ceiling-free preview of AC-F11-06 can run (§7.2). This is the one deliberate divergence from S1's `required=True`; §2.3.6 states the same rule |
| S3 | Ceiling key allowlist | `e40_benchmark.py:788-790` | Add `"max_provider_calls"` to `batch_authority_projection`'s projected key set |
| S4 | Demo/setup config defaults | `e40_benchmark.py:1041-1043` | Add a strictly positive default alongside the existing three |

It additionally appears in `call_plan.totals` (§2.3.3), in
`resource_policy_digest` (so it is part of comparison identity, AC-F11-46
component (iv)), in epic gate **G12** (`../epic.md:86`, which today names only
"provider-cost, wall-time, and generated-task ceilings"), and in the parent UAT
safety language (`../uat-plan.md` UAT-12, UAT-15, UAT-21).

*Negative case per seam.* Each of S1-S8 is individually reverted while the
other seven are present; each revert must produce a distinct, named failure —
**eight** negatives, not one. A ceiling accepted at S1 but dropped before S8 is
precisely the "approved but unenforced ceiling" defect this criterion exists to
prevent, and only the per-seam negatives can detect it.

**AC-F11-06b.** Ceiling validation rejects the non-finite and lossy inputs the
current helper accepts.

`require_positive` (`bench/scripts/lib/e40_benchmark.py:754-763`) computes
`float(value)` (or `int(value)`) and rejects only `parsed <= 0` plus `bool`.
Because `nan <= 0` and `inf <= 0` are both `False`, **NaN and positive infinity
are accepted as valid ceilings today.** This was verified by direct execution
against the live helper on 2026-09-04, not inferred:

| Input | `integer=` | Current result | Required result |
|---|---|---|---|
| `"nan"`, `"NaN"`, `float("nan")` | `False` | **accepted**, returns `nan` | `OperatorError`: `<label> must be a finite number` |
| `"inf"`, `"infinity"`, `float("inf")` | `False` | **accepted**, returns `inf` | `OperatorError`: `<label> must be a finite number` |
| `"1e400"` (overflows to `inf`) | `False` | **accepted**, returns `inf` | `OperatorError`: `<label> must be a finite number` |
| `2.5` | `True` | **accepted**, silently truncated to `2` | `OperatorError`: `<label> must be a whole number, got 2.5` |
| `" 3 "` (surrounding whitespace) | `False` | accepted, returns `3.0` | accepted — documented, not incidental |
| `"1_0"` (PEP 515 separator) | `False` | accepted, returns `10.0` | accepted — documented, not incidental |
| `10**30` | `True` | accepted | accepted; magnitude is bounded by S3-S8 policy, not by the parser |
| `"-inf"` | `False` | rejected | rejected (unchanged) |
| `0`, `-1` | either | rejected | rejected (unchanged) |
| `True` | either | rejected | rejected (unchanged) |
| `"abc"` | either | rejected | rejected (unchanged) |
| `"2.5"` | `True` | rejected | rejected (unchanged) |

The direction chosen is **reject**, not document-the-accept: a NaN ceiling
compares false against every consumption check, so it silently disables the
ceiling it appears to set — indistinguishable in the artifact from an approved
limit. An infinite ceiling is an unbounded one wearing a bound's label. Silent
`2.5 -> 2` truncation records an operator approval the operator did not give.

Two lexical variants (`" 3 "`, `"1_0"`) are **accepted deliberately** and are
recorded here so their acceptance is a specified property rather than an
unexamined artifact of `float()`.

The change is confined to `require_positive`, so all four ceilings inherit one
rejection semantics at one site (`§2.1.2`). §7.3.2 carries the full per-ceiling
matrix: 12 input classes x 4 ceilings.

*No committed data regresses.* Because the helper is shared by the three
existing ceilings, hardening it could in principle reject values that pass
today. Every committed and test-supplied ceiling value was enumerated on
2026-09-04: `max_cost_usd` ∈ {0.01, 5.0, 8.0}, `max_wall_clock_seconds` ∈
{60, 600, 900}, `max_generated_tasks` ∈ {10, 20, 30}, plus the CLI-supplied
values in `tc079`/`tc080`/`tc087`/`tc094`. All are finite, and every
`integer=True` value is whole, so **none is newly rejected**. A regression test
re-runs this enumeration so a future non-finite or fractional value is caught at
authoring time rather than at operator time.

**AC-F11-07.** With `--acknowledge-provider-spend` and all four strictly positive
operator-supplied ceilings, the flow invokes the genuine replay producer (X-10, the Rider
product-design action wrapped by E40-F07), retains transcript, result, usage,
limits, and validation output under
`<operator_root>/replay/<scenario_id>/<attempt_id>/`, runs
`bench/scripts/verify-replay-result.sh` against the package's admitted
`replay_reference` bundle, and prints the verified absolute result path.

**AC-F11-08.** `e40-benchmark.sh preflight` never creates a replay result and
never makes a provider call, in any argument combination. Attempting to reach
the preparation path from `preflight` is not expressible in the CLI surface.

Tests: `tc101_replay_preparation_spend_gate_test.sh` (AC-F11-06, AC-F11-08),
`tc102_replay_preparation_verified_result_test.sh` (AC-F11-07, offline via the
existing `bench/scripts/testdata/replay` stub producer).

#### REQ-F-004 — Fail-closed preflight

**AC-F11-09.** `preflight-result.json.status == "pass"` requires **all** of:
every selected scenario present in the structured resolution ledger with
`resolution == "resolved"`; every resolved scenario's `terminal` in the
package's declared success set; `provider_ready == true`;
`missing_real_runtime_inputs == []`; every selected scenario's replay
requirement satisfied; every fixture checkout verified; every evaluator
collection succeeding. Any other combination yields `status == "blocked"` with
a non-empty `blockers[]` naming requirement, scenario, and cause.

**AC-F11-10.** `pass_with_dry_run_limitations` is removed from the status
vocabulary. A dry-run limitation is reported as a typed
`diagnostics[].dry_run_limitation` entry that never coexists with
`status == "pass"` unless the limitation's own `spend_eligible` field is `true`.

**AC-F11-11.** A scenario whose `root_key`/`scratch_root` is unconfigured, or
whose `scratch_root` does not exist, produces `resolution == "skipped"` in the
ledger and is a **blocker**, not a silent omission. (This closes the second half
of the 2026-09-04 defect class: `run-lifecycle-batch.sh:601,604` print
`stage resolution: skipped` and `continue`, which the current
`re.findall(r"stage resolution: FAILED", …)` scrape at
`bench/scripts/lib/e40_benchmark.py:2004` cannot see.)

**AC-F11-12.** Replaying the exact 2026-09-04 conditions — feature scenario
without a replay result, two scenarios failing evaluator collection, one scenario
ending `terminal=error` — yields `status == "blocked"` with four distinct
blockers and `provider_ready == false`.

Tests: `tc103_preflight_fail_closed_test.sh` (AC-F11-09, AC-F11-10, AC-F11-12),
`tc104_preflight_skipped_scenario_blocker_test.sh` (AC-F11-11).

#### REQ-F-005 — Stage resolution without live-worker artifacts

**AC-F11-13.** `run-lifecycle.sh --mode resolve-route` traces the configured
success route for a scenario without requiring any artifact only a live worker
can produce, and emits, per stage: `stage_id`, `route`, `provider`, `model`,
`effort`, `terminal`, and `artifact_dependencies_deferred: true`.

**AC-F11-14.** A genuine route defect (an outcome target naming an undefined
step, a missing dispatch resolution) is reported as
`resolution == "failed"` with `cause_class == "route_defect"`; an absent
live-only artifact is reported as `cause_class == "artifact_deferred"` and does
**not** fail route resolution.

**AC-F11-15.** No file written by `--mode resolve-route` is accepted by
`bench/scripts/verify-stage-evidence.sh` as live stage evidence: every record
carries `evidence_mode: "route_resolution_only"`, which that verifier rejects.
Live pilot and baseline runs keep `evidence_required: true` enforcement
unchanged.

Test: `tc105_route_resolution_without_live_artifacts_test.sh`.

#### REQ-F-006 — Honest provider-call plan

**AC-F11-16.** `preflight-result.json.call_plan` contains, per scenario and in
aggregate, four separately labelled integers — `fixed_prelude_calls`,
`fixed_root_lifecycle_calls`, `review_gate_calls`, `bounded_descendant_calls` —
plus `worst_case_total_calls`, `max_cost_usd`, `max_wall_clock_seconds`, and
`max_generated_tasks`.

**AC-F11-17.** `bounded_descendant_calls` is computed by the §2.3.3a formula —
the **sum** over `expected_entity_graph.descendants[]` of
`max * calls_per_entity(family)`, with `calls_per_entity` resolved from the
workflow file named in evidence — or by the §2.3.3a fallback when the block is
absent. It is labelled `bound: true`. No field in `call_plan` presents a bounded
figure as an exact count. Negative cases: a maximum-based computation (which
would return 18 rather than 32 on the §2.3.3a worked example) is rejected; a
`calls_per_entity` read from a harness literal rather than from the evidenced
workflow file is rejected by mutating that workflow file and requiring the
computed total to change.

**AC-F11-18.** `call_plan.evidence[]` names, for every derived limit,
**eight** fields: the `limit` it explains, the package path and package digest,
the workflow file and workflow-routing digest, the model, the provider, and the
resource-policy digest it was derived from. The previous revision enumerated
only seven, omitting `limit` — which is the field that binds an evidence record
to the figure it justifies, so without it the remaining seven explain nothing in
particular. The negative set is therefore **eight** cases: each field blanked in
turn must produce a rejection naming that field.

Test: `tc106_provider_call_plan_test.sh`.

**AC-F11-21.** `bench/scripts/admit-scenario.sh` (lines 322–355) accepts the same

**AC-F11-22.** `bench/README.md` (§96, §385, §414, §421, §435),

#### REQ-F-009 — Declare expected entity graphs

#### REQ-F-012 — Isolate every scenario root

**AC-F11-38.** `setup_config` keys `scenario_roots` by `scenario_id` and reads
`root_key` from a per-`scenario_id` seed record, never from a family-keyed
dictionary. Two packages sharing an `entity_family` receive two distinct roots.

**AC-F11-38a.** Duplicate-family isolation is proven, not merely implied by the
six packages happening to carry six distinct families. A synthetic seventh
testdata package,
`bench/scripts/tests/testdata/duplicate-family/py-bug-second-scenario/`
(`entity_family: bug`, distinct `scenario_id`, otherwise a copy of
`py-bug-due-date-boundary`), is admitted into a test-only scenario index. Setup
must assign it a `root_key` distinct from `py-bug-due-date-boundary`'s. Under the
pre-rework family-keyed `roots[family]` lookup the two collide on one root; under
AC-F11-38's per-`scenario_id` lookup they do not. The synthetic package is
test-only and is never added to `bench/scenarios/scenarios.yaml`.

**AC-F11-39.** Setup seeds six independent hierarchies: a dedicated epic for the
epic scenario; a dedicated host epic + target feature for the feature scenario;
a dedicated host epic + host feature + target task for the task scenario; and
three dedicated standalone roots for bug, change card, and tech debt. No epic or
feature is shared between scenarios.

**AC-F11-40.** Every assigned key is captured from the `shark ... --json`
response; no key is constructed, guessed, or passed in by the harness.

**AC-F11-41.** Setup, preflight, replay preparation, pilot, baseline,
verification, and reporting all run against the external scratch project, and no
seam writes the repository's `shark-tasks.db`.

**No test may write, corrupt, or attempt to write the live repository
database — not even to demonstrate that a write would be detected.** The live
file is production data (`.claude/rules/database-critical.md`) and is not a test
fixture. The positive assertion is a non-mutation witness; the negative
assertion is proven against a **disposable surrogate**, never the real file:

1. *Positive (syscall observation — the live file is never opened by the
   test).* Across the full §7.2 sequence, **no `openat`/`open`/`rename`/`unlink`
   record names** `shark-tasks.db` or its `-wal`/`-shm` siblings, observed by the
   §7.7.2 tracer with `strace` as the parent.

   *This replaces the previous `(mtime_ns, size, SHA-256)` before/after
   comparison, which was itself the defect.* That check read every byte of the
   file whose non-reading AC-F11-41a asserts, so the two criteria directly
   contradicted each other. It was also incapable of detecting a read at all: an
   unchanged digest is equally consistent with "never opened" and "opened, read,
   left alone". Syscall observation decides between exactly those two cases,
   which is the property both criteria actually need, and it touches the live
   file zero times.
2. *Negative (surrogate, proves the witness can fail).* A disposable copy is
   created at a temp path, registered as the witness target, and deliberately
   mutated. The witness must report the mutation, naming the changed path.
   This proves the assertion in (1) is capable of failing — the thing a
   pure "nothing observed" check cannot establish on its own — **without the
   live file participating**. The surrogate is created independently by the test
   (`shark admin init` into a scratch root via `scripts/shark-scratch-env.sh`),
   **never by copying the live database**, and is deleted on every exit path.
   Copying would reintroduce the read that (1) forbids.

   This surrogate doubles as the §7.7.2 positive control: a run whose trace
   contains neither the surrogate nor the live path means the observer was
   broken, and must fail rather than pass.

A test that mutates the repository database to demonstrate detection is a
**defect in the test**, not evidence of isolation, and is rejected at review.
The same prohibition binds §7.4's escape cases, §7.5's Portability column, and
every ISO cell: the denied-write property is always demonstrated against a
surrogate or by a path assertion (AC-F11-41a), never by a real write.

**AC-F11-41a.** The repository's `shark-tasks.db` is not **read** either — a
property an mtime/digest assertion cannot establish, since a read leaves both
unchanged. Proven two ways, both required:

1. *Config-level.* For every seam invocation, the resolved database path is
   asserted to be under the scratch project. The existing `isolated_environment()`
   (`bench/scripts/lib/e40_benchmark.py:825`) pins `SHARK_DB_BACKEND=sqlite` and
   strips **17** names, all of which the test asserts are absent from the child
   environment on every seam: `SHARK_DB_URL`, `SHARK_AUTH_TOKEN`,
   `SHARK_AUTH_TOKEN_FILE`, `SHARK_BIN`, `LIFECYCLE_ADAPTER`,
   `LIFECYCLE_ADAPTER_PATH`, `LIFECYCLE_PROVIDER_COMMAND`, `RUN_LIFECYCLE_BIN`,
   `EVALUATE_LIFECYCLE_BIN`, `ENTITY_HISTORY_EXPORT_BIN`, `LIFECYCLE_SCHEMA`,
   `I05_SCHEMA`, `I07_SCHEMA`, `E40_RUN_LIFECYCLE_BATCH_BIN`,
   `E40_AGGREGATE_LIFECYCLE_BIN`, `E40_REPORT_LIFECYCLE_BIN`,
   `E40_VERIFY_RETENTION_ROOT_BIN`. *(Corrected in this rework: the previous
   text named only the first four, understating the surface the escape class
   E9 in §7.4 attacks.)* The effective `--db` must resolve outside `REPO_ROOT`
   on every seam.
2. *Counterfactual.* The complete offline path (§7.2) is re-run with the
   **resolved** database path aimed at a non-existent temporary path. Every step
   must still pass, because no step should ever resolve to it. If any step falls
   back to the repository database, the resolved-path assertion in (1) fails and
   names the offending seam.

   **The live `shark-tasks.db` is never renamed, moved, chmod-ed, copied over, or
   otherwise touched by this or any other F11 test** — see
   `.claude/rules/database-critical.md`. A `trap`-based restore is not an
   acceptable mitigation: it does not survive `SIGKILL`. A mode-`000` placeholder
   is also rejected — it proves nothing when the suite runs as root. The property
   is proven by path resolution, never by making the real file unavailable.

Test: `tc111_scenario_root_isolation_test.sh`; escape-class enumeration in §7.4.

#### 2.3.3a Call-plan arithmetic (ADR-F11-12)

**Calls per entity.** `calls_per_entity(family)` is the number of steps in that
family's resolved workflow whose `action` is `spawn_agent`. It is **read from
the workflow file identified by `call_plan.evidence[].workflow_file` and
digested as `workflow_routing_digest`** — never from a literal table in the
harness. This matters because the benchmark compares candidate configurations
whose workflows differ; a hardcoded count would silently misprice a variant.

For the shipped default bundle
(`internal/sharkdata/default_data/workflow/*.yaml`, read 2026-09-04) the
resolved values are:

| Family | `spawn_agent` steps | `calls_per_entity` |
|---|---|---|
| `task` | `development` | 1 |
| `feature` | `research`, `assessment`, `specification`, `test_planning`, `task_generation`, `task_review`, `code_review`, `qa`, `approval` | 9 |
| `epic` | `research`, `assessment`, `refinement`, `design`, `decomposition`, `feature_review` | 6 |
| `bug` | `research`, `development`, `code_review`, `qa` | 4 |
| `change_card` | `research`, `development`, `code_review`, `qa` | 4 |
| `tech_debt` | `research`, `triaged` | 2 |

This table is a **worked example of the derivation, not the source of truth.**
A test asserting these six integers against the default bundle is asserting the
derivation is wired correctly; a test that would still pass if the workflow file
changed is not testing the derivation at all.

**The four components.**

```
fixed_prelude_calls        = | { s in stage_matrix.prelude :
                                   s.applicable == true
                                   AND s has no versioned response
                                       in the package's replay bundle } |
fixed_root_lifecycle_calls = calls_per_entity(root_family)
review_gate_calls          = | enabled_gates(workflow_policy_identity)
                               \ spawn_agent_steps(root_family) |
bounded_descendant_calls   = SUM over d in descendants[] of
                                 d.max * calls_per_entity(d.family)
worst_case_total_calls     = fixed_prelude_calls
                           + fixed_root_lifecycle_calls
                           + review_gate_calls
                           + bounded_descendant_calls
```

**All four components are derived, none is a literal.** The previous revision
defined only `bounded_descendant_calls` and left the other two as prose
("calls consumed by D01-D05 replay", "calls contributed by enabled review
gates"), then set both to 0 in the worked example without saying why. Two of
four terms of the spend ceiling were undefined arithmetic — the same class 8
defect, in the components the descendant fix did not reach.

- **`fixed_prelude_calls`** counts D01-D05 prelude stages that are `applicable`
  **and** have no versioned response to replay — those are the only ones that
  would reach a provider. A stage with a response is replayed, not called, so it
  contributes 0. It follows that a package passing AC-F11-04's replay
  requirement always yields **`fixed_prelude_calls == 0`**: preflight blocks on a
  missing or invalid replay bundle, so a scenario reaching the call plan has a
  response for every applicable prelude stage. A non-zero value here is a
  **preflight inconsistency** and is itself a blocker, not a priced call.
- **`review_gate_calls`** is the set difference between the gates enabled in the
  workflow-policy identity and the root family's own `spawn_agent` steps —
  counting only gates not already priced by `fixed_root_lifecycle_calls`,
  so no gate is double-counted. Both operands are evidenced:
  `enabled_gates` from the workflow-policy identity (AC-F11-46 component (iii)),
  `spawn_agent_steps` from the file named in
  `call_plan.evidence[].workflow_file`.

*Negative cases:* a prelude stage stripped of its replay response must move
`fixed_prelude_calls` off 0 **and** raise a preflight blocker; adding a review
gate outside the root's `spawn_agent` set must increment `review_gate_calls` by
exactly one; adding a gate that **is** in that set must leave it unchanged
(proving the set difference, not a raw count).

**Summation, not maximum.** `descendants[]` declares one maximum *per family*,
and those maxima are **independent** — a graph may realize all of them at once.
`{feature: max 2, task: max 8}` therefore admits 2 features and 8 tasks
simultaneously. Summing is the only operation that keeps
`worst_case_total_calls` an upper bound; taking a maximum understates it, which
is the unsafe direction for a spend gate (ADR-F11-12).

**Worked example** (the `py-epic-task-organization` package of §2.3.5, under the
default bundle):

```
root_family = epic                    -> fixed_root_lifecycle_calls = 6
prelude: D01-D05 applicable = false for epic (AC-F11-33), so the
         applicable-and-unreplayed set is empty
                                      -> fixed_prelude_calls        = 0
descendants: feature max 2 -> 2 * 9 = 18
             task    max 8 -> 8 * 1 =  8
                                         bounded_descendant_calls   = 26
enabled_gates(policy) \ spawn_agent_steps(epic) = {} — every enabled
         gate for this package is already one of epic's 6 steps
                                      -> review_gate_calls          = 0
                                         ------------------------------
                                         worst_case_total_calls     = 32
```

Both zeros are **computed from the stated rules**, not assumed: the first
because epic declares D01-D05 non-applicable, the second because this package's
enabled gates are a subset of the root workflow's own dispatching steps. A test
must recompute them rather than assert the literal 0.

A maximum-based reading would have produced 18 and under-approved by 14 calls.

**Fallback when the block is absent (AC-F11-25a).** With no
`expected_entity_graph`, the descendant family is not declared, so
`calls_per_entity` cannot be resolved per family. The fallback is

```
bounded_descendant_calls = resource_policy.max_generated_tasks
                           * calls_per_entity("task")
```

because `max_generated_tasks` counts generated **tasks** specifically. This
fallback is labelled `bound: true`, carries `resource_policy_digest` in
evidence, and names `resource_policy.max_generated_tasks` as its source.

**Both sources present.** When a package carries `expected_entity_graph` *and*
a `resource_policy.max_generated_tasks`, the two are **not** compared as
interchangeable scalars — they measure different things. The graph bound is
computed as above; `max_generated_tasks` is applied as an independent runtime
cap on generated task entities. If the graph's declared task maxima exceed
`max_generated_tasks`, that is a **package defect** and admission rejects it
(`expected_entity_graph declares up to N task descendants, exceeding
resource_policy.max_generated_tasks = M`), rather than one value silently
overriding the other.

**Relation to the fourth ceiling.** `worst_case_total_calls` is compared against
the operator-approved `--max-provider-calls` (AC-F11-06a) at preflight. Exceeding
it is a `blocker`, not a warning: a plan whose own worst case breaches the
approved ceiling cannot authorize spend.

#### 2.3.6 `e40-benchmark.sh prepare-replay`

`prepare-replay --config <cfg> --scenario <id> [--acknowledge-provider-spend] [--max-cost-usd N] [--max-wall-clock-seconds N] [--max-provider-calls N] [--max-generated-tasks N]`.
All four ceilings are mandatory under `--acknowledge-provider-spend` (AC-F11-06a);
each is parsed by `require_positive` (`integer=True` for provider-calls and

**The previewed "proposed provider calls" figure reuses §2.3.3a's
`fixed_prelude_calls` term**, and is not separate arithmetic. It is the count of
`stage_matrix.prelude` stages that are `applicable` **and** have no versioned
response in the package's replay bundle — exactly the set `prepare-replay`
exists to produce. This is the one context where that term is **non-zero**: the
bundle does not yet exist, so every applicable D01-D05 stage is unreplayed and
must be genuinely called. Once `prepare-replay` succeeds the bundle is complete
and the same term evaluates to 0 at `preflight` (§2.3.3a), which is why a
passing preflight always prices the prelude at zero. The term is therefore not
vestigial — it is the quantity this subcommand spends against, and
`--max-provider-calls` bounds it.

Without `--acknowledge-provider-spend`: preview only, zero provider calls, non-zero exit.

transcript/result/usage/limits/validation, runs

### 2.4 Key technical decisions

**ADR-F11-01 — Single supported I-04 schema version; no dual-version window.**
Every package is in-repo and migrates atomically in the same commit, so
`e40I04SupportedSchemaVersion`, `scenarios.yaml`, and all six `package.yaml`
files move together and the validator accepts exactly one version. *Rationale:*
dual-version support would require the Go validator and
`bench/scripts/admit-scenario.sh` to branch on version, creating exactly the
Go/Python divergence risk `research-report.md` §cross_boundary_risks names. The
version digit itself is cosmetic; the invariant — one supported version — is
what matters. *Deviation:* none; this follows the existing single-version
pattern already used for `e40I01SupportedSchemaVersion`.

**ADR-F11-02 — One authoritative family vocabulary; every other reference is a
consumer.** `tests/contracts/e40_i04_scenario_contract_test.go` remains the
single source of truth (`research-report.md` Decision 2).
`bench/scripts/admit-scenario.sh` and `bench/README.md` are updated as
consumers, and `tc107` asserts the two enforcement points agree. *Rationale:*
prevents the Go and Python checkers from silently diverging on what "six
families" means.

**ADR-F11-03 — One immutable fixture checkout per `(fixture_id, base_sha)` per
operator run, shared across scenarios.** All six packages currently pin the same
`base_sha`, so per-scenario checkouts would clone the same tree six times
without adding isolation. The checkout is marked read-only and verified before
any collector runs. *Rationale:* determinism and cost; the isolation property
that matters (evaluator-only material never reachable from an agent-visible
root) is enforced by `verify-evidence-roots.sh`, not by checkout multiplicity.

**ADR-F11-04 — Two new `final_predicate` kinds, preserving the kind→family 1:1
invariant.** `e40I04FinalPredicateFamilies` gains
`"task_acceptance_tests": "task"` and `"descendant_oracles_union": "epic"`.
*Rationale:* the existing map is kind→exactly-one-family; adding two entries
keeps that invariant and lets the existing
`case-14-predicate-kind-not-permitted-for-family.yaml` guard cover the new kinds
without new mechanism. The absolute P2P clause is unchanged for both.

**ADR-F11-05 — Fail-closed preflight consumes a structured ledger, not stdout
text.** The current `re.findall(r"stage resolution: FAILED", …)` scrape
(`bench/scripts/lib/e40_benchmark.py:2004`) cannot see the two `skipped`
`continue` paths at `bench/scripts/run-lifecycle-batch.sh:601,604`, so an
unconfigured or missing scratch root passes preflight invisibly — the same
defect class as the 2026-09-04 `unresolved_gate`. Widening the regex would ship
the hole again. `run-lifecycle-batch.sh --mode preview` therefore emits
`resolution-ledger.jsonl` and preflight requires one `resolved` record per
selected scenario; absence is a blocker. *Rationale:* absence-is-failure is only
expressible against an enumerated ledger, never against a text scrape.

**ADR-F11-06 — REQ-F-012's seeding block is rewritten, not patched.** The
existing `_cmd_setup_locked` seed block builds a four-entry family-keyed `roots`
dict; six independent hierarchies (including a dedicated epic root and a
three-level task hierarchy) cannot be expressed by adding entries to it.
*Rationale:* patching would preserve the family-keying defect REQ-F-012 exists to
remove. Every assigned key is captured from `shark ... --json`, per the standing
cloud-DB rule that Shark assigns keys.

**ADR-F11-07 — E40-F11 carries the I-04 consumer updates in-place.**
*Status: **provisional working assumption**, not a settled decision — Q007 owns
the call and is open.* It governs how this feature sequences its own work; it
does not authorize writing a resolved ownership record into the parent map
(§2.1.7), and it must not be cited downstream as though Q007 were answered. If
Q007 resolves to option (b) or (c), this ADR is withdrawn and F11's I-04 slice
is re-scoped rather than merely re-attributed. E40-F05
through E40-F10 are all `completed` (read live from Shark, 2026-09-04). Revising
I-04 therefore cannot route consumer updates back to F06/F07/F08. Under the
interaction map's own boundary rule, F11 updates the architecture source, the
I-04 map row, every named consumer surface, and the matching UAT scenarios
before passing feature review. *Open decision:* whether absorbing the revision

**ADR-F11-08 — No production Go change.** Every requirement is satisfiable in

**ADR-F11-09 — `expected_entity_graph` is required only for `epic`.** Making the
block required for `feature` too would force `py-feature-recurring-tasks` — a
package whose `fixture.base_sha` is frozen and whose `reference.patch` was
already rebased once during T-E40-F05-014 — to be re-admitted, and `tc034`
requires byte-identical re-admission. The one thing the block is needed for on a
feature root is REQ-F-006's `bounded_descendant_calls`, and
`resource_policy.max_generated_tasks` (already `30` on that package) is an
equally evidence-backed ceiling for it (AC-F11-25a). *Rationale:* keeps the four
frozen packages at a pure version bump while leaving the block available to any
future feature package that wants a tighter structural oracle. *Trade-off:* the
feature scenario's descendant ceiling is policy-derived rather than
topology-derived, so it is looser than the epic scenario's — acceptable because
it is still a ceiling, still `bound: true`, and still evidence-named.

**ADR-F11-10 — The retention guard attaches to `ensure_external_operator_root`,
not to each subcommand.** *Re-verified 2026-09-04 per seam*, by inspecting each
`cmd_*` body rather than asserting it in aggregate:

| Seam | Reaches `ensure_external_operator_root` via |
|---|---|
| `setup` | direct call |
| `preflight` | direct call |
| `validate-variant` | direct call |
| `compare` | direct call |
| `pilot` | `execute_profile` |
| `baseline` | `execute_profile` |
| `variant` | `execute_profile` |
| `demo` | `cmd_setup` delegation (`cmd_demo` builds a `setup` namespace and calls `cmd_setup`, then `cmd_preflight`) — it holds no direct call of its own |

All eight reach the choke point at `bench/scripts/lib/e40_benchmark.py:815`, so
one guard covers all of them and `prepare-replay` inherits it by using the same
resolver. The two read-only-intent seams the trade-off below concerns
(`validate-variant`, `compare`) are confirmed **direct** callers, so the
nine-seam guarantee in AC-F11-01 does not depend on an indirect path for either.
`demo`'s coverage is delegated, not direct — a test asserting the guard on
`demo` is therefore also asserting `cmd_setup` delegation remains intact, and
must fail if `cmd_demo` is ever changed to resolve its own root. Any seam added later inherits it too. *Rationale:* nine per-command
guards is exactly the "second source of truth" failure ADR-F11-02 rejects for
the family vocabulary; a new subcommand would silently miss one. *Trade-off:* the
guard also blocks read-only-intent seams (`compare`, `demo`, `validate-variant`).
Accepted deliberately — those seams still take the operator-root lock, which
writes a byte, and REQ-F-001's freeze is unconditional. Inspecting a frozen root
is done with `verify-retention-manifest.sh` and ordinary file reads, neither of
which resolves an operator root.

**ADR-F11-11 — `required_terminal_states` is a mapping family->status, not a
flat list.** *Decision:* the mapping form wins; §2.3.5 and AC-F11-25's previous
flat-array rendering is the error and is corrected. *Discriminator (evidence,
not taste):* terminal statuses are **per-family** in this repository. Read from
`internal/sharkdata/default_data/workflow/*.yaml` on 2026-09-04, the terminal
step sets are:

| Family | Terminal statuses |
|---|---|
| `task`, `feature`, `epic`, `bug`, `change` | `cancelled`, `completed` |
| `tech_debt` | `cancelled`, `resolved`, `wont_fix` — **no `completed`** |

A flat `required_terminal_states: [completed]` therefore cannot express a
mixed-family graph containing a `tech_debt` descendant: the single literal is
simultaneously correct for five families and unsatisfiable for the sixth. The
mapping states one status per declared descendant family and is checked for key
completeness by AC-F11-25b. *Second reason:* a flat literal `completed` is the
hardcoded-status antipattern the project rules forbid
(`.claude/rules/` — status names are workflow-config-driven, resolved per level
through the workflow service, never written into a validator). The mapping keeps
the status bound to the family whose workflow defines it. *Trade-off:* the
mapping is more verbose for the common all-`completed` case, and it must be
kept in sync with `descendants[]`. Accepted: AC-F11-25b makes the sync a
validated invariant rather than an authoring convention, so drift fails
admission instead of passing silently. *Blast radius:* §2.3.5, AC-F11-25,
AC-F11-25b, §7.3.6, and the Y-table's Y7/Y8 rows, which already assumed the
mapping and are now the consistent side.

**ADR-F11-12 — Provider-call arithmetic is defined per descendant family, and
descendant maxima are summed, not maximized.** *Problem:* the previous text said
`bounded_descendant_calls` derives from
"`expected_entity_graph.descendants[].max` and `resource_policy.max_generated_tasks`,
whichever binds tighter". `descendants[].max` is a **list** — one maximum per
declared descendant family — so "whichever binds tighter" compared a list to a
scalar and left the descendant-to-provider-call conversion entirely undefined.
A test plan cannot invent that formula, which is why class 8 blocked. *Decision:*
the formula is fixed in §2.3.3a. *Rationale:* a graph declaring
`{feature: max 2, task: max 8}` can produce 2 features **and** 8 tasks — ten
entities, not eight. Taking a maximum understates the ceiling, which is the
unsafe direction for a spend gate. Summation over declared families is the only
choice that keeps `worst_case_total_calls` a genuine upper bound. *Trade-off:*
the bound is loose — a real run typically produces far fewer entities. Accepted:
`bound: true` labels it a ceiling and AC-F11-17 forbids presenting it as an
exact count; a loose ceiling costs an operator an over-large approval, while a
tight-but-wrong one costs unbudgeted spend.

**`prepare-replay`'s ceilings are parser-optional and handler-required — a
deliberate divergence from `add_execution_arguments`.** The execution seams mark
their ceilings `required=True` because `pilot`/`baseline`/`variant` have **no
preview mode**: every invocation is an attempt to spend. `prepare-replay` does
have one, and AC-F11-06 requires that the ceiling-free invocation *previews and
refuses*. Under `required=True` that invocation would instead die at argparse
with exit 2 before the handler ran, so the preview AC-F11-06 specifies could
never execute and its negative case would pass for a parsing reason.

The rule is therefore: **the four ceilings are optional at the parser and
mandatory in the handler whenever `--acknowledge-provider-spend` is present.**

| Invocation | Result |
|---|---|
| no ack, no ceilings | preview printed (proposed calls, model, provider, effort, and the ceilings that *would* be required); exit non-zero (AC-F11-06) |
| no ack, some or all ceilings | same preview; still refuses — supplying ceilings never substitutes for acknowledgement (§7.1 row 06) |
| ack, any ceiling absent | `OperatorError` naming the missing `resource_policy.<field>`; **not** an argparse error (AC-F11-06a, gate G-7) |
| ack, all four present and finite-positive | proceeds (AC-F11-07) |

acknowledgement must produce an `OperatorError` naming the field, so a test

### 7.7 Independent proof of zero provider calls (class 9)

**The reported counter is not evidence.** `provider_calls` is emitted as a
hardcoded literal — `"provider_calls": 0,` at
`bench/scripts/lib/e40_benchmark.py:2033` — not as a measurement. Asserting
`provider_calls == 0` therefore proves only that the literal is still there. Any
AC or UAT step whose zero-call claim rests on that field alone is
**unsubstantiated**, which is the class 9 finding. Every zero-call assertion in
this specification (AC-F11-06, AC-F11-08, REQ-NF-002, UAT-15, UAT-21) is
redefined to require the two independent proofs below.

**Precedent:** this is not a new mechanism. `tc053_live_egress_denial_test.sh`
already proves a negative this exact way — "a PATH-stubbed dispatcher recording
ZERO invocations, not merely inferred from the exit code" — and
`bench/scripts/testdata/stubs/claude` already logs `{"argv":[…],"cwd":…}` JSONL
to `STUB_CLAUDE_LOG`. F11 reuses both rather than inventing a counter.

**Proof 1 — PATH-stubbed provider executable with an invocation counter
(required).**

- *Setup:* prepend a stub directory to `PATH` containing an executable named for
  every provider binary any seam could exec (`claude`, plus each name reachable
  through `LIFECYCLE_PROVIDER_COMMAND`). Point `STUB_CLAUDE_LOG` at a
  test-owned path. The stub appends one JSONL record per invocation and exits 0.
- *Observable:* after the zero-call seam completes, the log file is **absent or
  zero-length**. Non-empty is a hard failure, and the failure message prints
  every recorded `argv` so the offending call is identifiable.
- *Positive control (required — an always-empty log proves nothing):* the same
  stub, same harness, run against a seam that **is** expected to invoke the
  provider (the acknowledged `prepare-replay` path, AC-F11-07) must produce a
  **non-empty** log. Without this control the counter could be broken and the
  test would still pass.

**Correction — `tc053` is not an egress monitor.** The previous revision
directed Proof 2 at "the existing `tc053_live_egress_denial_test.sh`
egress-denial fixture". No such fixture exists. Read on 2026-09-04, `tc053`
proves its negative by **argv construction and retained-transcript parsing**
(its own header: "real argv construction by the real script, real
transcript-file parsing"). It never denies or observes network activity at the
OS level. Building a zero-call proof on it would have asserted at the same layer
Proof 1 already covers, leaving the actual gap open. Proof 2 is replaced.

**Proof 2 — syscall observation of process execution (required).**

- *Setup:* run the seam under
  `strace -f -qq -e trace=execve -o <log> <argv>`, with `strace` as the
  **parent** of the harness process.
- *Observable:* no `execve` in the log names any member of the provider-
  invocation surface of §7.7.3. The assertion is over the resolved executable
  path and `argv[0]`, so it is independent of `PATH`.
- *Positive control (required):* the acknowledged `prepare-replay` path must
  produce a matching `execve` record in the same log format. An observer that
  silently records nothing would otherwise pass every negative.

*Feasibility, verified on this host 2026-09-04 rather than assumed:*
`/proc/sys/kernel/yama/ptrace_scope` is `1` (restricted), which permits tracing
**descendants** — and the test is the parent of the harness, so this is the
permitted case. `strace` is present at `/usr/bin/strace`; `auditctl` is absent
and the test user is unprivileged (uid 1000), so an `auditd` rule is **not**
available and must not be specified. `-f` is required: `e40-benchmark.sh`
`exec`s `python3`, which spawns further subprocesses, and an unfollowed trace
would miss every one of them. A trial run captured both an interpreter-based
`execve` (`execve("/usr/bin/python3", ["python3", "…/prov.py"], …)`) and a
file `openat` through a shell wrapper, confirming the mechanism works in the
harness's actual process shape.

*Fallback if `ptrace_scope` is raised to `2` or `3` on some other host:* an
unprivileged `LD_PRELOAD` interposer over `execve`/`openat`, writing the same
log format. The assertions are written against the log format, not against
`strace`, so the observer is swappable without rewriting any test.

**Both proofs are required, and neither may be substituted by the reported
counter.** They fail differently on purpose: Proof 1 catches a call that
resolves through `PATH` to a stubbed name; Proof 2 catches a call that bypasses
the stubbed name entirely — an absolute path, or an interpreter invocation whose
`argv[0]` is `python3`. Escape class E9 (§7.4) covers the third route —
re-injecting `LIFECYCLE_PROVIDER_COMMAND` to redirect the provider — so the
three together close the surface.

#### 7.7.3 The provider-invocation surface (class 6)

Proof 1 alone is insufficient because a `PATH` stub intercepts **only a bare
command name resolved through `PATH`**. The harness does not restrict itself to
that form: `LIFECYCLE_PROVIDER_COMMAND` is parsed as a **JSON argv array**
(`bench/scripts/lifecycle-worker-adapter.sh:108-115`, which rejects anything
that is not "a non-empty JSON string array"), and it is set programmatically at
`bench/scripts/lib/e40_benchmark.py:1933`. An argv array can name anything.

The surface the zero-call proof must cover, enumerated:

| # | Invocation form | Example `LIFECYCLE_PROVIDER_COMMAND` | Caught by |
|---|---|---|---|
| V1 | bare name resolved through `PATH` | `["claude"]` | Proof 1 and Proof 2 |
| V2 | absolute path to a provider binary | `["/usr/local/bin/claude"]` | **Proof 2 only** |
| V3 | relative path from the working directory | `["./claude"]` | **Proof 2 only** |
| V4 | interpreter + script | `["python3","/opt/x/provider.py"]` | **Proof 2 only** |
| V5 | shell wrapper | `["/bin/sh","-c","claude \"$@\""]` | Proof 1 (inner `claude`) and Proof 2 (both `execve`s) |
| V6 | a name not in the stub directory | `["codex"]` | **Proof 2 only** |
| V7 | `--provider-command` CLI argument instead of the env var | `--provider-command '["claude"]'` | Proof 1 and Proof 2 |

**V2, V3, V4, and V6 are invisible to Proof 1.** They are the concrete content
of class 6 and the reason Proof 2 observes `execve` rather than `PATH`.

The stub directory of Proof 1 must contain an executable for **every name
reachable as `argv[0]`** across the configured providers — at minimum `claude`,
`codex`, and `gemini` — and the test must fail if
`LIFECYCLE_PROVIDER_COMMAND` resolves to a name outside that set, rather than
passing because nothing was intercepted. Proof 2's assertion is stated over the resolved executable path **and the
complete `argv` vector** — not the exec path plus `argv[0]`. The verified trace
line for V4 was
`execve("/usr/bin/python3", ["python3", "/tmp/f11probe/prov.py"], …)`: the only
token identifying the provider is **`argv[1]`**, so an assertion domain of
`{exec_path, argv[0]}` would see `/usr/bin/python3` and `python3` and match
nothing. V2 and V3 are caught on the exec path, V4 and V5 on later argv
elements, V1 and V6 on `argv[0]`. The domain is the full vector because no
single position is sufficient across all six forms.

#### 7.7.2 Proof that no live database is read or written (class 5, AC-F11-41a)

**The previous approach was itself a violation.** AC-F11-41a requires that the
live `shark-tasks.db` is neither read nor written. The prior test design proved
this by hashing the live database before and after — which **reads every byte of
the file it is asserting was not read**. A no-read criterion cannot be
discharged by a reader. Hashing also cannot detect a read at all: an unchanged
digest is equally consistent with "not opened" and "opened, read, and not
written".

**The proof is syscall observation, not content comparison.**

- *Setup:* run the seam under
  `strace -f -qq -e trace=openat,open,unlink,rename -o <log> <argv>`, with
  `strace` as the parent. Nothing reads or copies the live database.
- *Observable:* no record in the log names the live `shark-tasks.db` or its
  `-wal`/`-shm` siblings. Matching is on **two** domains, both required:

  1. **Resolved absolute path.** `strace -y` decorates descriptors and
     directory-relative calls with their resolved paths — verified on this host
     2026-09-04, which produced
     `openat(AT_FDCWD</tmp/f11probe>, "dummy.db", …) = 3</tmp/f11probe/dummy.db>`.
     Without `-y`, a plain trace records only the **relative** literal
     (`"dummy.db"`), from which no absolute path is recoverable — so `-y` is
     mandatory, not cosmetic, and a trace taken without it is not evidence.
  2. **Every resolved database path is accounted for**: each one is under the
     scratch project root and outside `REPO_ROOT`. This is the positive half —
     it catches a database opened at an unexpected *third* location, which a
     pure absence check cannot see.

  **A basename match is explicitly rejected as the discriminator.** The scratch
  bootstrap (`scripts/shark-scratch-env.sh:42`) points the isolated project's
  `--db` at `$scratch_dir/shark-tasks.db` — the **same basename** as the live
  one. A rule matching `{shark-tasks.db, -wal, -shm}` "regardless of directory"
  would therefore fire on the scratch database every seam legitimately opens,
  failing closed on healthy runs. The two are distinguishable only by **path**,
  which is why `strace -y` is mandatory: without resolved paths there is no
  discriminator at all.

  Together these close escape classes E1-E3 (§7.4): assertion (1) catches a
  symlinked or relative approach after `-y` resolution, and (2) catches a
  resolution landing outside both expected roots.
- *Positive control (required, and it must not use the live database):* create
  an **independent dummy database** at a scratch path — a file the test itself
  makes — and have a helper deliberately open it inside the same traced run.
  The proof passes only when the log contains the dummy path **and** lacks the
  live path. A log missing both means the observer was not working, and must
  fail rather than pass.
- *Complementary positive assertion:* every database path the harness **does**
  resolve appears in the log under the scratch project root and outside
  `REPO_ROOT`. This turns AC-F11-41a from "the live file is absent" into "every
  resolved path is accounted for", so a database opened at a third unexpected
  location is also caught.

*Verified mechanism, 2026-09-04:* a trial run captured
`openat(AT_FDCWD, "dummy.db", O_RDONLY|O_CLOEXEC) = 3` for a file opened by a
child of a traced shell wrapper — the exact shape of this proof's positive
control.

**No test in this specification hashes, copies, opens, or stats the live
`shark-tasks.db`.** The repository's standing rule against running benchmark
setup against the live project applies unchanged: every run uses
`scripts/shark-scratch-env.sh`.
