# LivenessRecorder: stage-boundary state machine and JSON stderr renderer

## Goal
Create `internal/runner/liveness.go` with the `LivenessRecorder` type's core:
the single-open-stage state machine that derives `stage_start`/`heartbeat`/
`stage_end` boundaries from the existing `RunProgress` stream (spec.md D1),
and the `--json`-mode NDJSON stderr renderer (spec.md D3's JSON table). This
is the foundation every later task in this feature extends — no ticker, no
file writer, no `Finish()` yet.

## Scope
- Files to create: `internal/runner/liveness.go`, `internal/runner/liveness_test.go`
- Do not touch `internal/runner/controller.go` or `internal/runner/transcript.go`
  in this task or any later F04 task — REQ-N-004 requires these files show
  zero diff for the whole feature; the constraint starts here because this is
  where the temptation to "just add a stage-end phase to `RunProgress`" is
  strongest. `RunOptions.Progress`'s existing callback signature is the only
  seam used.

## Acceptance Criteria
See spec.md AC-01, AC-05, AC-08 and test-plan.md TC-011 (stderr half only —
see Notes), TC-015, TC-020, TC-021, TC-029.
- AC-T1: `NewLivenessRecorder(projectRoot, runID, topLevelKey string, jsonMode bool, start time.Time) *LivenessRecorder` exists with exactly this signature — no duration/interval parameter (a later task's TC-026 depends on this).
- AC-T2: `Observe(runner.RunProgress)` implements spec.md D1's phase table: `Phase: "iteration"` closes any open slot (emitting a lazy `stage_start` first if the slot never emitted one) and opens a new slot for `update.EntityKey`; `Phase: "action"` enriches the open slot and emits `stage_start`; other phases are ignored. Shared slot state access is mutex-guarded (REQ-N-003; the dedicated concurrency stress test lands in T-E40-F04-003, but the guard must exist now).
- AC-T3: In `jsonMode=true`, every emitted stderr line unmarshals into spec.md D3's 11-field JSON table (`ts`, `run_id`, `event`, `entity_key`, `iteration`, `status`, `action`, `agent_type`, `provider`, `stage_elapsed_ms`, `total_elapsed_ms`), with `event` closed to `{stage_start, heartbeat, stage_end}`, `agent_type`/`provider` omitted (not empty-valued) when unset, and no `phase` key ever present.

## Test Cases
Write failing tests first, then implement. See test-plan.md TC-011 (schema
field presence and closed enum — **this task owns the stderr-capture half
only**; TC-011's `run.log` file-content half is T-E40-F04-002's
responsibility once the file sink exists), TC-015 (parent→child→parent
cascade labeling, driven exactly as `controller.go`'s sequential cascade-child
loop calls `Observe`), TC-020 (stage pairing rows 1/2/5/6 of the AC-08
decision table — the run-end rows can be exercised here by simply stopping
the `Observe` sequence, since `Finish()` doesn't exist until T-E40-F04-004),
TC-021 (pairing under a non-unique `(entity_key, iteration)` re-dispatch — do
not key your test's own verification by `(entity_key, iteration)`, that would
re-implement the bug under test), TC-029 (closed JSON field set, no leaked
prompt/output content).

## Notes for Agent
- `Observe` is the literal function bound as `opts.Progress = rec.Observe` in
  T-E40-F04-005 (spec.md D6 edit 3) — do not add an adapter layer between it
  and the controller's call shape.
- The `run_end` line and `LogPath()` do not exist yet; do not stub them
  speculatively (Rule 2 — simplicity first).
- TC-011's negative case ("no line ever carries a `phase` key") is a common
  drift point if you mirror `internal/runner/logging.go`'s field names too
  literally — that package uses `phase` for a different concept. Reuse only
  the field names research Decision 5 lists (`entity_key`, `run_id`,
  `status`, `agent_type`, `provider`), not the `phase` key itself.
