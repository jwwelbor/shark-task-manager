# Research report

## Scope

T-E38-F07-001 verifies and closes the parent-owned Rider dispatch contract.

## Capability map

| Capability | Source | Decision |
| --- | --- | --- |
| Canonical `next → claim → dispatch → advance → release` loop | `skills/shark-rider/verbs/run.md` | REUSE |
| Worker ownership preamble and semantic result | `context/task-execution-pattern.md` | EXTEND |
| Workflow routing and prompt assembly | Shark CLI dispatch response | REUSE |
| New runtime, command, or aggregate state | F07 spec | CONTRADICTS |

## Ubiquitous vocabulary

- Parent: the Rider loop that owns the dispatched entity's lease and transition.
- Worker: the craft agent that returns evidence and one configured outcome.
- Kickback: a parent-applied task rewind before its parent advances.

## Findings

The existing procedure already establishes prompt fidelity, parent-owned
mutation, configured outcomes, and release semantics. F07 should make that
boundary mechanically testable without changing the CLI or workflow engine.

## Decisions

Keep `shark next <root> --json` as the sole dispatch source, preserve the
existing directive order, and add only focused contract coverage for the
documented parent and worker responsibilities.
