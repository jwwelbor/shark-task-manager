# Implement workflow-role filtering for sprint next selection

## Goal

Implement the outstanding Shark-side correction that `E38-F06` originally
described: role-aware sprint selection must filter on workflow-resolved role
authority rather than the persisted task `agent_type` field. Preserve current
deterministic ordering and leave claim ownership with `ClaimService`.

## Scope

- Modify the production sprint selection path used by `shark sprint next --agent=<type>`.
- Update the selection data source so the filter reflects workflow-resolved role
  semantics instead of raw `tasks.agent_type`.
- Update focused service/CLI tests to prove non-default role forwarding and
  eligibility behavior.
- Do not add a new command, scheduler, team runtime, or separate claim-next
  implementation.

## Acceptance Criteria

- A worker pulling with `shark sprint next --agent=<workflow-role>` receives
  only items eligible for that workflow role.
- A legacy stored task `agent_type` that disagrees with the workflow-resolved
  role does not incorrectly control eligibility.
- Existing deterministic selection order remains unchanged after filtering.
- Callers that omit `--agent` retain current behavior.
- Claim conflicts, leases, heartbeat, and release behavior remain owned by
  `ClaimService`; this task does not introduce direct claim-next semantics.

## Implementation Notes

- Current gap: `internal/services/sprint_service.go` filters `GetNextTask`
  candidates with `item.AgentType != agentType`, and backlog rows currently
  source `AgentType` from persisted task data.
- The desired behavior was captured in `E38-F06` but not implemented when the
  feature was completed as guidance/contracts.
- Keep the fix surgical. Prefer adjusting the existing backlog selection seam
  and its tests over introducing parallel role-resolution logic elsewhere.
