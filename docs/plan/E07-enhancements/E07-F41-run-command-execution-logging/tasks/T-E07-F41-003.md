# Emit per-stage slog events in RunController

## Goal

Add five structured slog call sites to `internal/runner/controller.go` — one at each meaningful point in the controller loop — so that a complete per-stage execution trace appears in shark.log for every `/run` invocation. Error events must include truncated stderr when the failure originates from an AgentFailedError.

## Scope

- Files to modify:
  - `internal/runner/controller.go` — add slog calls for stage.start, stage.dispatch, stage.complete, stage.transition, stage.error
  - `internal/runner/dispatcher.go` — ensure AgentFailedError carries stdout/stderr (already present; verify truncation helper is accessible)

## Acceptance Criteria

See feature.md Story 2, Story 3, REQ-F-003, REQ-F-004, REQ-F-010, REQ-F-011 for authoritative criteria.

- AC-T1: `run.stage.start` emitted at top of each loop iteration with entity_key, status, iteration, run_id.
- AC-T2: `run.stage.dispatch` emitted immediately before execAndCapture with entity_key, status, agent_type, provider, command, run_id.
- AC-T3: `run.stage.complete` emitted after successful dispatch with entity_key, status, exit_code, duration_ms, next_status, run_id. No stdout field.
- AC-T4: `run.stage.transition` emitted in handleAdvanceStatus with entity_key, from_status, to_status, run_id.
- AC-T5: `run.stage.error` emitted at every result.Error branch; when from AgentFailedError includes exit_code, stderr (capped at LogTruncateBytes), stdout_tail (capped), command, truncated flag.
- AC-T6: Successful dispatch log event stays under 1 KB (no inlined stdout).

## Test Cases

Derive from feature.md Scenario 1 and Scenario 2 (feature-level acceptance).
- Mock controller run producing 2 stages; verify event sequence in slog output.
- Simulate AgentFailedError with large stderr; verify truncation to LogTruncateBytes.

## Design Reference

See feature.md "Requirements — Category: Event Emission" (REQ-F-003, REQ-F-004) and "Category: Agent Subprocess Capture" (REQ-F-010, REQ-F-011). run_id flows from T-E07-F41-002 via RunOptions or context.

## UAT Rejection (2026-04-19, iteration 3)

**Verdict:** REJECT (confidence: HIGH)
**Assessor:** Codex (ChatGPT) via `codex exec` red-team review — sole assessor per UAT skill.
**Results file:** `code_review/20260419-010800-T-E07-F41-003-uat.md`

### Classification

**AC Violation** — The specification was clear; the implementation missed the
constraint.

### What iteration 3 fixed

- REQ-F-003 (iter-2 blocker) is fixed for the common case: `internal/runner/shell_quote.go`
  correctly POSIX-quotes whitespace, embedded single quotes, and every common
  shell metacharacter, and `joinCommand` is shared between `BuildCommand` and
  `Dispatch` so no drift is possible.
- All 6 iteration-1 blockers remain fixed (no regressions).

### Unmet acceptance criteria (blockers)

1. **AC-T6 / REQ-F-010 — Successful dispatch event NOT under ~1 KB.**
   - `internal/runner/logging.go:68-75` (`emitStageDispatch`) passes `p.Command`
     to `slog.InfoContext` with zero truncation.
   - `internal/runner/controller.go:511-519` calls `emitStageDispatch` with the
     full `dispatcher.BuildCommand(input)` string, which includes the agent
     instruction as an argv element.
   - Agent instructions are typically 2–50 KB; the successful-path
     `run.stage.dispatch` event therefore routinely emits 2–50 KB per run.
   - `feature.md:164` is normative: "Successful dispatches produce a log event
     under ~1 KB".
   - **Required fix:** exclude the instruction token from the logged `command`
     string (log a separate digest — byte length + SHA-256 prefix, or first
     256 bytes), or apply `obs.GetLogTruncateBytes()` truncation. Preferred:
     exclusion, so non-instruction args (flags, paths) remain auditable.

2. **REQ-F-003 — NUL-byte incoherence in shell quoting.**
   - `internal/runner/shell_quote.go` passes NUL (`\x00`) bytes through verbatim
     inside single quotes.
   - Go stdlib `syscall/exec_unix.go:81-89` rejects argv elements containing NUL
     with `EINVAL`; POSIX shell grammar cannot represent a literal NUL.
   - A NUL-bearing argv produces a logged command that (a) cannot be pasted into
     any shell, (b) does not match what `os/exec` would execute, violating the
     "exact shell-equivalent invocation" contract at `feature.md:148`.
   - **Required fix:** Reject NUL-bearing input in `shellQuote` (surface as a
     `run.stage.error` with phase `shell_quote`) or substitute with a visible
     sentinel and mark the event as sanitized. Add a NUL-input unit test to
     `shell_quote_test.go`.

### Non-blocker follow-ups

1. **Stale comment at `controller.go:507-510`** — documents an
   instruction-excluded dispatch event that the code does not implement. Fix
   after blocker 1 so the comment matches the new behavior.
2. **Dry-run post-stage blind spot at `controller.go:496-500`** — if
   `GetNextStatus` fails after successful dispatch, the loop completes
   silently without a `run.stage.error`. Violates the "every failure emits an
   error event" invariant in spirit.

### Required work for iteration 4

1. Apply the AC-T6/REQ-F-010 fix (exclude instruction from logged `command`).
2. Apply the REQ-F-003 NUL-byte fix in `shellQuote`.
3. Fix stale comment at `controller.go:507-510`.
4. Emit `run.stage.error` for post-stage `GetNextStatus` failure.
5. Add regression tests:
   - 20 KB instruction → emitted `run.stage.dispatch` < 1 KB.
   - NUL-bearing argv → surfaced as error, not swallowed.
6. Run `make fmt && make lint && make test`.

### Secondary finding (not a fresh blocker but task brief was wrong)

- **Dry-run post-dispatch blind spot claimed closed but not closed.** The

### Non-blocking observations

1. `truncateTail` in `logging.go` truncates on a raw byte boundary, which
   can split a UTF-8 sequence and leave a mojibake tail. Consider
   rune-boundary truncation or a byte-order-aware marker.
2. "Tail" is a misnomer — `truncateTail` keeps the **head** and discards
   the tail. Acceptable once the real 1 KB fix lands (prompt instructions
   usually live at the tail, but commands put the binary and key flags at
   the head, so head-retention is the right default). Recommend renaming
   for clarity.
