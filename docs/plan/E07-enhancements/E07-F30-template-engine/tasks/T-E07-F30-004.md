# Task: Make all ContextData.Metadata fields available to templates

## Goal

Refactor metadata architecture to store all custom fields in `ContextData.Metadata` map and make ALL metadata fields available to templates as variables. This eliminates the confusing dual system (metadata vs context_data) and allows templates to access any user-defined field without code changes.

## Requirements

### Functional Requirements

- [ ] Add `Metadata map[string]interface{}` field to `ContextData` struct
- [ ] Update `*PlaceholdersWithRelated()` to extract ALL metadata fields from `ContextData.Metadata`
- [ ] Flatten metadata fields into placeholder map (e.g., `metadata.complexity_tier` → `complexity_tier`)
- [ ] Support common types: string, int, float64, bool (convert to string for templates)
- [ ] Remove separate `Metadata` field from Task/Feature/Epic models (use ContextData.Metadata instead)
- [ ] Preserve all existing placeholder fields (no breaking changes)

### Non-Functional Requirements

- [ ] No breaking changes to existing templates or placeholder fields
- [ ] No performance impact (simple map iteration)
- [ ] Test Coverage: 90%+ for modified functions
- [ ] Backward compatibility: existing code using Task.Metadata continues to work during migration

## Implementation Plan

### Phase 1: Add Metadata to ContextData

1. [ ] Open `internal/models/context_data.go`
2. [ ] Add `Metadata` field to `ContextData` struct:
   ```go
   type ContextData struct {
       Progress                 *ProgressContext             `json:"progress,omitempty"`
       ImplementationDecisions  map[string]string            `json:"implementation_decisions,omitempty"`
       OpenQuestions            []string                     `json:"open_questions,omitempty"`
       Blockers                 []BlockerContext             `json:"blockers,omitempty"`
       AcceptanceCriteriaStatus []AcceptanceCriterionContext `json:"acceptance_criteria_status,omitempty"`
       Metadata                 map[string]interface{}       `json:"metadata,omitempty"` // NEW: User-defined fields
   }
   ```
3. [ ] Update `ContextData.Validate()` to skip validation for Metadata (it's flexible)

### Phase 2: Extract ALL Metadata in Placeholder Builders

4. [ ] Open `internal/config/template_helpers.go`
5. [ ] Locate `TaskPlaceholdersWithRelated()` function
6. [ ] Parse `task.ContextData` JSON to get `ContextData.Metadata` map
7. [ ] Flatten ALL metadata fields into placeholders:
   ```go
   // Parse context_data to get metadata
   if task.ContextData != nil && *task.ContextData != "" {
       var ctx models.ContextData
       if err := json.Unmarshal([]byte(*task.ContextData), &ctx); err == nil {
           // Add ALL metadata fields as template variables
           for key, value := range ctx.Metadata {
               placeholders[key] = stringifyMetadataValue(value)
           }
       }
   }
   ```
8. [ ] Create `stringifyMetadataValue()` helper to convert common types:
   ```go
   func stringifyMetadataValue(value interface{}) string {
       switch v := value.(type) {
       case string:
           return v
       case int, int64, float64:
           return fmt.Sprintf("%v", v)
       case bool:
           return fmt.Sprintf("%t", v)
       default:
           return ""
       }
   }
   ```
9. [ ] Repeat for `FeaturePlaceholdersWithRelated()` and `EpicPlaceholdersWithRelated()`
10. [ ] Write unit tests for metadata extraction (various types, missing fields, nil metadata)

### Technical Approach

- **Single Source of Truth**: ContextData.Metadata becomes the canonical location for all custom fields
- **Type-Safe Conversion**: Helper function handles string, int, float64, bool → string conversion
- **Graceful Degradation**: Missing/invalid metadata fields return empty string (templates handle gracefully)
- **Backward Compatible**: Existing Task.Metadata continues to work during migration (will be removed in Phase 3)
- **Database Storage**: ContextData already stored as JSON in `context_data` column, no schema changes needed

## Notes

**Architecture Change Rationale:**
- **Before**: Confusing dual system - `metadata` (not persisted) vs `context_data` (persisted JSON)
- **After**: Single source of truth - `ContextData.Metadata` for all custom fields
- **Benefits**:
  - No more `db:"-"` fields with misleading "derived from related data" comments
  - Templates get ALL metadata fields automatically, not just cherry-picked ones
  - Add new template variables without code changes (just set metadata in context_data)
  - Consistent storage location (context_data JSON column already exists)

**Why This Matters:**
- Templates can now use ANY user-defined field:
  - `{{.complexity_tier}}` - Scale output depth (SIMPLE/STANDARD/COMPLEX)
  - `{{.estimated_hours}}` - Show time estimates in instructions
  - `{{.assignee}}` - Personalize orchestrator actions
  - `{{.is_critical}}` - Add urgency indicators
- Example use cases:
  - Feature BA refinement: 1-page PRD for SIMPLE, 6 files for COMPLEX
  - Task instructions: Include assignee name in agent greeting
  - Orchestrator actions: Show time budget if estimated_hours set

**Migration Path:**
- Phase 1 (this task): Add Metadata to ContextData, extract all fields
- Phase 2 (future): Remove Task.Metadata field from models
- Phase 3 (future): Update CLI to set fields in context_data instead of metadata

**No Backward Compatibility Needed:**
- `complexity_tier` was just added in E07-F30-004 (never released)
- No existing templates or code uses it in production
- Can implement cleanly without legacy support

**Integration:**
- Service layer calls `*PlaceholdersWithRelated()` → gets ALL metadata as vars
- `PopulateTemplate(vars)` passes to template engine
- Template uses `{{.field_name}}` for any metadata field
