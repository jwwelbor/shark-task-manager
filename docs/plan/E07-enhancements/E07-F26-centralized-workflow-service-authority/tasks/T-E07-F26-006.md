# Task: Replace direct status string comparisons in commands

## Goal

Eliminate all direct status string comparisons (e.g., `task.Status == "completed"`) in CLI commands and the status package. Replace with semantic `workflow.Service` method calls that express intent rather than checking for specific status names.

## Files to Modify

### `internal/cli/commands/task_deps.go`
- **Lines 437, 443**: `if task.Status == "completed"` → `if ws.IsTerminalStatus(string(task.Status))`

### `internal/cli/commands/task.go`
- **Line ~61**: `cli.Info(fmt.Sprintf("  - %s (now todo)", key))` in auto-unblock → Use `ws.GetDefaultStatus()` instead of `"todo"`
- **Line ~505 area**: `filterTasksByCompletedStatus` function (line 1170+) - check if it hardcodes "completed" and replace with `ws.IsTerminalStatus()`

### `internal/status/action_items.go`
- **Line 41**: `case "ready_for_approval":` → Use phase-based or metadata-based check (e.g., statuses in "approval" phase, or statuses where `blocks_feature == true`)
- **Line 65**: `case "in_progress", "in_development":` → Use phase-based check (e.g., statuses in "development" phase)

## Guiding Principle

Replace **what** (specific status name) with **why** (semantic meaning):
- `== "completed"` → `IsTerminalStatus()` or `IsCompletedStatus()`
- `== "todo"` → `GetDefaultStatus()` or `GetInitialStatus()`
- `== "blocked"` → check metadata phase == "blocked" or a dedicated `IsBlockedStatus()`
- `== "in_development"` → check metadata phase == "development"

## Acceptance Criteria

- [ ] No direct status string comparisons in `cli/commands/task_deps.go`
- [ ] No hardcoded `"todo"` in unblock messages
- [ ] `status/action_items.go` uses phase/metadata queries instead of status name switches
- [ ] `filterTasksByCompletedStatus` uses service methods
- [ ] Behavior is identical before and after (semantic equivalence)
- [ ] `make test` passes
