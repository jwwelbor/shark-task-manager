# Task: Add entity type detection helper

## Goal

Add a `DetectEntityType(key string) string` function to `internal/cli/commands/helpers.go` that returns `"epic"`, `"feature"`, `"task"`, or `"unknown"` from any valid shark key format. This will be used by the unified delete dispatcher (T-E07-F25-005) and potentially future dispatchers.

## Requirements

### Functional Requirements

- [ ] Function signature: `func DetectEntityType(key string) string`
- [ ] Returns `"epic"` for keys matching: `E##`, `E##-slug`
- [ ] Returns `"feature"` for keys matching: `F##`, `F##-slug`, `E##-F##`, `E##-F##-slug`
- [ ] Returns `"task"` for keys matching: `T-E##-F##-###`, `E##-F##-###`, `T-E##-F##-###-slug`, `E##-F##-###-slug`
- [ ] Returns `"unknown"` for unrecognized formats
- [ ] Case insensitive: `e07`, `E07`, `E07-enhancements` all return `"epic"`
- [ ] Handles slugged keys correctly (slug suffix does not change detection)

### Non-Functional Requirements

- [ ] No database calls -- pure string parsing
- [ ] Reuses existing helpers: `IsEpicKey()`, `IsFeatureKey()`, `NormalizeKey()` where possible
- [ ] No new dependencies

## Implementation Plan

### Steps

1. [ ] Read `internal/cli/commands/helpers.go` to understand existing key validation functions
2. [ ] Identify which existing functions can be reused:
   - `IsEpicKey(s string) bool` -- validates E## format
   - `IsFeatureKey(s string) bool` -- validates E##-F## format
   - `IsFeatureKeySuffix(s string) bool` -- validates F## format
   - `NormalizeKey(key string) string` -- uppercases key
3. [ ] Implement `DetectEntityType()` using this logic:
   ```
   normalized = NormalizeKey(key)
   // Strip slug suffix for detection (everything after last known pattern)
   if matches task pattern (T-E##-F##-### or E##-F##-###): return "task"
   if IsFeatureKey(normalized) or IsFeatureKeySuffix(normalized): return "feature"
   if IsEpicKey(normalized): return "epic"
   return "unknown"
   ```
4. [ ] Handle edge cases:
   - Keys with slug suffixes (e.g., `E07-enhancements` -- the `-enhancements` looks like a feature suffix but isn't)
   - The slug detection must differentiate `E07-F01` (feature) from `E07-enhancements` (epic with slug)
5. [ ] Consider: the existing `ParseGetArgs()` in `helpers.go` already delegates to `scopeInterpreterImpl.ParseScope()` which does similar detection. Evaluate whether to wrap that or write standalone logic.

### Technical Approach

The existing `ParseGetArgs` already returns a "command" string that indicates entity type. The new function should either:
- **Option A**: Wrap `ParseGetArgs` and extract the command type (simplest, reuses tested logic)
- **Option B**: Standalone regex-based detection (more self-contained, no side effects)

**Recommendation**: Option A if `ParseGetArgs` is side-effect-free; Option B otherwise.

## Notes

- The tricky case is distinguishing `E07-enhancements` (epic + slug) from `E07-F01` (feature key). The existing `IsFeatureKey()` checks for the `E##-F##` pattern specifically (F followed by digits), so `E07-enhancements` would NOT match `IsFeatureKey()` and would correctly fall through to `IsEpicKey()` matching `E07`.
- The existing `ParseGetArgs` in helpers.go already does entity detection via `scopeInterpreterImpl.ParseScope()`. We should check if wrapping that is simpler than reimplementing.
