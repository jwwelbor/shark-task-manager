## Business Rules

**BR-1: Database is Single Source of Truth**
- All relationship data must come from database tables or database-stored JSON (`context_data`)
- Frontmatter fields in markdown files have NO EFFECT on relationships
- This rule is consistent across all entity types (tasks, features, epics, documents)

**BR-2: Bidirectional Relationship Queries**
- When querying task relationships, both `from_task_id` and `to_task_id` must be checked
- Example: If task A relates to task B, the relationship can be stored either direction
- Placeholder population must return unique task keys (no duplicates)

**BR-3: Relationship Type Validation**
- Only 7 valid relationship types: depends_on, blocks, related_to, follows, spawned_from, duplicates, references
- UAT guide must document what each type means for testing purposes
- Invalid types should fail at database constraint level (CHECK constraint)

## Edge Cases

**Edge Case 1: Task with No Relationships**
- **Scenario**: Task has no rows in `task_relationships` table AND no `context_data`

- **Test Coverage**: UAT must verify no crashes, empty string in instruction template

**Edge Case 2: Self-Referential Relationships**
- **Scenario**: Attempting to create relationship where `from_task_id = to_task_id`

- **Test Coverage**: UAT should document this is invalid (though may not be enforced in MVP)

- **Test Coverage**: UAT should verify orphaned relationships don't appear in placeholders

**Edge Case 4: Malformed context_data JSON**

- **Test Coverage**: UAT should add test case for this scenario

## Technical Specification (Architect Review)

### Architecture Decisions

**Decision 1: Dual-Source Architecture for Task Relationships**
- **Rationale**: Feature E07-F29 uses BOTH `task_relationships` table (formal) AND `context_data` JSON (lightweight)
  - Table approach enables queryable relationships, bidirectional queries, analytics
  - JSON approach provides backward compatibility with existing E10-F05 context system
- **Implementation**: Placeholder function queries table FIRST, falls back to JSON if table empty
- **Alignment**: Matches feature/epic pattern (formal relationship tables), but adds JSON fallback for tasks
- **Source**: Data Design doc (lines 76-98), Architecture doc (line 52), Feature Research (lines 127-158)

**Decision 2: Database-Only Source of Truth**
- **Rationale**: Frontmatter `related_tasks` field does NOT sync to database (by design, sync removed in earlier epics)
- **Clarification**: UAT must explicitly state that editing frontmatter has NO EFFECT
- **Consistency**: Matches related_docs, related_features, related_epics pattern (database-first architecture)
- **Source**: UAT guide lines 316-324 (Architecture Notes for other relationship types)

**Decision 3: Bidirectional Relationship Queries**
- **Rationale**: Task relationships stored directionally but queried bidirectionally
  - Example: If A relates to B, relationship can be stored as (from=A, to=B) OR (from=B, to=A)
  - Query must check BOTH from_task_id and to_task_id columns
- **Implementation**: SQL query uses OR condition: `WHERE from_task_id = ? OR to_task_id = ?`
- **Deduplication**: Placeholder merge removes duplicate task keys when same relationship exists both directions
- **Source**: Data Design doc (lines 117-149), Feature architecture precedent (feature_relationships)

**Decision 4: Test Data Script Pattern**
- **Rationale**: Use task KEYS (not IDs) for portability across databases
- **Implementation Pattern**:
  ```sql
  -- Use subquery to get task IDs from keys
  INSERT INTO task_relationships (from_task_id, to_task_id, relationship_type)
  SELECT t1.id, t2.id, 'depends_on'
  FROM tasks t1, tasks t2
  WHERE t1.key = 'T-E07-F29-001' AND t2.key = 'T-E07-F29-002';
  ```
- **Benefit**: Scripts work regardless of task ID auto-increment values
- **Source**: Existing document setup pattern (UAT lines 38-63)

**Section 3: Architecture Notes Expansion (after line 325)**
```markdown
**Task Relationships - Dual Source Architecture:**
- Task relationships use BOTH `task_relationships` table (primary) AND `context_data.RelatedTasks` JSON (fallback)
- Table is PRIMARY: Queried first, enables analytics and bidirectional relationships
- JSON is FALLBACK: Used for backward compatibility with E10-F05 context system
- Placeholder population: Try table → try JSON → return empty string
- Bidirectional queries: Check both from_task_id and to_task_id columns
- Deduplication: Merge table + JSON results, remove duplicates
- Frontmatter has NO EFFECT: Task frontmatter related_tasks field is NOT synced

**task_relationships Table Schema:**
```sql
CREATE TABLE task_relationships (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    from_task_id INTEGER NOT NULL,          -- Source task (foreign key to tasks.id)
    to_task_id INTEGER NOT NULL,            -- Target task (foreign key to tasks.id)
    relationship_type TEXT CHECK (          -- 7 valid types (CHECK constraint)
        relationship_type IN (
            'depends_on',    -- from_task depends on to_task completing
            'blocks',        -- from_task blocks to_task from proceeding
            'related_to',    -- Tasks share common code/concerns
            'follows',       -- from_task naturally follows to_task
            'spawned_from',  -- from_task created from bugs/UAT in to_task
            'duplicates',    -- Tasks represent duplicate work
            'references'     -- from_task consults/uses output of to_task
        )
    ) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (from_task_id) REFERENCES tasks(id) ON DELETE CASCADE,
    FOREIGN KEY (to_task_id) REFERENCES tasks(id) ON DELETE CASCADE,
    UNIQUE(from_task_id, to_task_id, relationship_type)
);
```

**Indexes (for bidirectional queries):**
- `idx_task_relationships_from` ON (from_task_id)
- `idx_task_relationships_to` ON (to_task_id)
- `idx_task_relationships_type` ON (relationship_type)
- `idx_task_relationships_from_type` ON (from_task_id, relationship_type)
- `idx_task_relationships_to_type` ON (to_task_id, relationship_type)

**Relationship Type Semantics:**
- **depends_on**: from_task cannot complete until to_task is done
- **blocks**: from_task prevents to_task from starting
- **related_to**: Tasks share code, concerns, or context (generic)
- **follows**: from_task logically follows to_task (sequence)
- **spawned_from**: from_task created from UAT/bugs found in to_task
- **duplicates**: Tasks represent same work (merge candidates)
- **references**: from_task uses output/results of to_task

**Constraints:**
- CASCADE DELETE: Relationships auto-delete when either task deleted
- UNIQUE constraint: Prevents duplicate (from, to, type) triples
- CHECK constraint: Enforces 7 valid relationship types at database level
- NO self-references: Application should prevent from_task_id = to_task_id (not DB-enforced in MVP)
```

```sql
SELECT DISTINCT
    CASE
        WHEN tr.from_task_id = t_current.id THEN t_other.key
        ELSE t_from.key
    END AS related_task_key,
    tr.relationship_type
FROM task_relationships tr
JOIN tasks t_current ON (tr.from_task_id = t_current.id OR tr.to_task_id = t_current.id)
JOIN tasks t_from ON tr.from_task_id = t_from.id
JOIN tasks t_other ON tr.to_task_id = t_other.id
WHERE t_current.key = 'T-E07-F29-002'
ORDER BY related_task_key;
