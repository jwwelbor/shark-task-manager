# Task: Refactor TaskPlaceholdersWithRelated to use task_relationships table

## Goal

Replace the `extractRelatedTasksFromContext()` JSON parsing approach in `TaskPlaceholdersWithRelated()` with a database query against the `task_relationships` table. This aligns task relationship handling with the proven repository pattern used for features and epics, improving queryability and consistency.

## Context

**Current Implementation:**
- `TaskPlaceholdersWithRelated()` calls `extractRelatedTasksFromContext()` which parses `task.context_data` JSON field
- Related task keys stored in `ContextData.RelatedTasks` array
- No formal table for task relationships (unlike features/epics which use `feature_relationships` and `epic_relationships` tables)

**Change Driver:**
- Task dependencies already use `task_relationships` table (created in E10-F03)
- Table provides typed relationships: `depends_on`, `blocks`, `related_to`, `follows`, `spawned_from`, `duplicates`, `references`
- Querying relationships via SQL is more performant and maintainable than JSON parsing

**Dependency:**
- T-E07-F29-028 adds `ListRelatedTaskKeys(ctx, taskID) ([]string, error)` method to `TaskRelationshipRepository`
- This method provides the exact data needed to replace `extractRelatedTasksFromContext()`

## Requirements

### Functional Requirements

**FR-001: Replace Context Data Parsing with Repository Query**
- `TaskPlaceholdersWithRelated()` MUST call `TaskRelationshipRepository.ListRelatedTaskKeys()` instead of `extractRelatedTasksFromContext()`
- Repository method returns all related task keys (all relationship types combined)
- Empty array returned if no relationships exist

**FR-002: Inject TaskRelationshipRepository**
- `TaskPlaceholdersWithRelated()` signature MUST be extended to accept `TaskRelationshipRepository` parameter
- Repository instance passed via constructor injection (no global state)
- Function signature: `TaskPlaceholdersWithRelated(ctx context.Context, task *models.Task, docRepo *repository.DocumentRepository, taskRelRepo *repository.TaskRelationshipRepository)`

**FR-003: Maintain Backward Compatibility**
- `{related_tasks}` placeholder MUST continue populating with comma-separated task keys
- Empty string returned if no relationships exist (same behavior as before)
- Existing templates MUST work without modification

**FR-004: Graceful Error Handling**
- Database query errors MUST NOT fail template population
- On error, log warning and return empty string for `{related_tasks}`
- Template population always succeeds (graceful degradation pattern)

### Non-Functional Requirements

**NFR-001: Performance**
- Query MUST use existing indexes on `task_relationships` table
- Single query per task (no N+1 pattern)
- Performance target: < 10ms for up to 20 relationships

**NFR-002: Code Quality**
- Follow repository injection pattern from features/epics (consistency)
- Error logging uses WARNING level for query failures
- No code duplication between task/feature/epic placeholder functions

**NFR-003: Maintainability**
- Remove `extractRelatedTasksFromContext()` helper function (dead code after refactor)
- Update all call sites to pass `TaskRelationshipRepository` parameter
- Document parameter change in function comments

**Implementation Example:**
```go
func TaskPlaceholdersWithRelated(
    ctx context.Context,
    task *models.Task,
    docRepo *repository.DocumentRepository,
    taskRelRepo *repository.TaskRelationshipRepository,  // NEW
) (map[string]string, error) {
    placeholders := TaskPlaceholders(task)

    // Related docs (unchanged)
    docs, err := docRepo.ListForTask(ctx, task.ID)
    if err != nil {
        log.Printf("WARNING: Failed to fetch related docs for task %s: %v", task.Key, err)
        placeholders["related_docs"] = ""
    } else {
        placeholders["related_docs"] = formatDocPathsAsCSV(docs)
    }

    // Related tasks (NEW - uses task_relationships table)
    relatedKeys, err := taskRelRepo.ListRelatedTaskKeys(ctx, task.ID)
    if err != nil {
        log.Printf("WARNING: Failed to fetch related tasks for task %s: %v", task.Key, err)
        placeholders["related_tasks"] = ""
    } else {
        placeholders["related_tasks"] = strings.Join(relatedKeys, ",")
    }

    return placeholders, nil
}
```

- ✅ **Pro**: Consistency with feature/epic relationship handling
- ✅ **Pro**: SQL queryable (enables analytics, reporting)
- ✅ **Pro**: Typed relationships (semantic meaning)
- ⚠️ **Con**: Requires database query instead of in-memory JSON parse (negligible performance difference: ~5ms vs 1ms)
- ⚠️ **Con**: More parameters to inject (acceptable - follows DI pattern)

### Data Models

#### Repository Query Contract (from T-E07-F29-028)

**Method:** `ListRelatedTaskKeys(ctx context.Context, taskID int64) ([]string, error)`

**Returns:**
- **Success:** Array of task keys (e.g., `["E07-F05-001", "E10-F05-002"]`)
- **Empty:** `[]string{}` when no relationships exist (NOT nil, NOT error)
- **Error:** `(nil, error)` only on database failures

**Query Pattern (from dependency task):**
```sql
SELECT DISTINCT t.key
FROM task_relationships tr
JOIN tasks t ON (
    (tr.from_task_id = ? AND tr.to_task_id = t.id) OR
    (tr.to_task_id = ? AND tr.from_task_id = t.id)
)
WHERE t.id != ?
ORDER BY t.key ASC
```

**Semantics:**
- Bidirectional: Returns tasks where input task is EITHER source OR target
- All relationship types: No filtering by `relationship_type`
- Excludes self: Input task's key never in output array
- Ordered: Consistent ordering by key (ASC) for deterministic output

### Architecture Decisions

#### Decision 1: Move to Repository-Based Relationships

**Decision:** Replace `extractRelatedTasksFromContext()` (JSON parsing) with `taskRelRepo.ListRelatedTaskKeys()` (database query)

**Rationale:**
1. **Consistency:** Features and epics already use formal relationship tables (`feature_relationships`, `epic_relationships` from E07-F29 architecture)
2. **Queryability:** SQL-queryable relationships enable analytics and relationship traversal
3. **Typed Relationships:** `task_relationships` table supports 7 relationship types with semantic meaning
4. **Future-Proof:** Prepares for advanced relationship queries (filter by type, detect cycles, generate graphs)

**Trade-offs:**
| Aspect | Context Data (Old) | Repository Query (New) |
|--------|-------------------|----------------------|
| Performance | ~1ms (in-memory JSON parse) | ~5ms (database query with JOIN) |
| Queryability | No (embedded JSON) | Yes (SQL table with indexes) |
| Consistency | Divergent (tasks use JSON, features/epics use tables) | Aligned (all entities use tables) |
| Complexity | Lower (no repository injection) | Higher (inject `TaskRelationshipRepository`) |

**Conclusion:** Performance cost (4ms) acceptable for architectural consistency and queryability benefits.

---

#### Decision 2: Graceful Degradation for Query Failures

**Decision:** On repository query error, log warning and return empty string for `{related_tasks}` placeholder (do NOT propagate error)

**Rationale:**
1. **Template Reliability:** Orchestrator actions MUST always be generated (template population cannot fail)
2. **Missing Relationships Are Valid:** Task may legitimately have no relationships
3. **Degraded Context Better Than No Context:** Agent receives partial placeholders rather than empty instruction

**Implementation Pattern:**
```go
relatedKeys, err := taskRelRepo.ListRelatedTaskKeys(ctx, task.ID)
if err != nil {
    log.Printf("WARNING: Failed to fetch related tasks for task %s: %v", task.Key, err)
    placeholders["related_tasks"] = ""  // Empty string fallback
} else {
    placeholders["related_tasks"] = strings.Join(relatedKeys, ",")
}
```

**Error Handling Standards (from `.claude/rules/go/error-handling.md`):**
- `WARNING` log level for relationship query failures (not critical path)
- Error context includes task key for debugging
- No error propagation from placeholder population functions

### Performance Considerations

#### Query Performance

**Target:** < 10ms for task with up to 20 relationships (typical case)

**Index Utilization:**
- `idx_task_relationships_from` on `from_task_id`
- `idx_task_relationships_to` on `to_task_id`
- Composite indexes enable efficient bidirectional lookup

**Query Plan (from T-E07-F29-028):**
```sql
EXPLAIN QUERY PLAN
SELECT DISTINCT t.key
FROM task_relationships tr
JOIN tasks t ON (...)
WHERE ...
-- Expected: Uses indexes on both from_task_id and to_task_id
```

**No N+1 Queries:**
- Single JOIN query fetches all related task keys
- No loop over relationships (all keys in one database round-trip)

#### Comparison to Current Implementation

| Metric | Context Data (Old) | Repository Query (New) |
|--------|-------------------|----------------------|
| Latency | ~1ms (JSON unmarshal) | ~5ms (DB query + JOIN) |
| Memory | Allocates array during unmarshal | Allocates array during scan |
| Database Load | None (in-memory) | 1 query with 2 index seeks |
| Scalability | O(n) JSON parse | O(n) with indexed JOIN |

**Acceptable Trade-off:** 4ms added latency negligible for orchestrator action generation (not hot path, runs once per task status change).

## Notes

**Why This Change:**
Tasks were the last entity type using JSON context_data for relationships. Features and epics already use formal relationship tables (`feature_relationships`, `epic_relationships`). This refactor brings tasks into alignment with the established pattern.

**Migration Path:**
- No data migration required (relationships remain in `task_relationships` table)
- Context data `RelatedTasks` field can remain for backward compatibility (not actively used after refactor)
- Future: Could add CLI commands to migrate context_data relationships to table

**Performance Impact:**
- Minimal: Repository query (~5ms) vs JSON parse (~1ms)
- Acceptable trade-off for consistency and queryability
- Single query per placeholder population (no N+1 problem)
