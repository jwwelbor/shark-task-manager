# Task: Add ListRelatedTaskKeys method to TaskRelationshipRepository

## Feature Context

This task implements repository support for the `{related_tasks}` template placeholder defined in feature E07-F29. The feature enables AI agents to receive related task keys automatically in orchestrator action instructions, eliminating manual context discovery.

**Feature PRD**: `/docs/plan/E07-enhancements/E07-F29-template-variables-for-related-docs-and-tasks/prd.md`

**Related Requirements**:
- REQ-F-002 (Related Tasks Placeholder) - Template variable population
- REQ-NF-002 (Query Efficiency) - Single query, no N+1 pattern

## Goal

Add a repository method that returns all related task keys (as strings) for a given task ID by querying the `task_relationships` table. This method will be called during template placeholder population to provide the `{related_tasks}` comma-separated value.

**User Story**: As a template placeholder system, I need to retrieve all task keys related to a given task (both incoming and outgoing relationships) so that I can populate the `{related_tasks}` placeholder with a comma-separated list for agent instructions.

## Requirements

### Functional Requirements

#### FR-1: Method Signature and Location
- **Description**: Add `ListRelatedTaskKeys` method to `TaskRelationshipRepository` struct
- **Location**: `internal/repository/task_relationship_repository.go`
- **Signature**: `func (r *TaskRelationshipRepository) ListRelatedTaskKeys(ctx context.Context, taskID int64) ([]string, error)`
- **Returns**: Array of task keys (e.g., `["T-E07-F05-001", "E10-F05-002"]`), not IDs
- **Traces to**: REQ-F-002 (Related Tasks Placeholder)

#### FR-2: Bidirectional Relationship Query
- **Description**: Query must retrieve relationships where the task is EITHER the source (from_task_id) OR target (to_task_id)
- **SQL Pattern**: `WHERE from_task_id = ? OR to_task_id = ?`
- **Rationale**: Related tasks include both dependencies (task depends on) and dependents (tasks that depend on this task)
- **Example**: If E07-F29-001 depends_on E07-F05-001, then both tasks should appear in each other's related list
- **Traces to**: Existing `GetByTaskID()` pattern in TaskRelationshipRepository

#### FR-3: Include All Relationship Types
- **Description**: Return tasks for ALL relationship types, not filtered to specific types
- **Relationship Types** (from schema):
  - `depends_on` - Hard dependency
  - `blocks` - Blocking relationship
  - `related_to` - Soft relationship
  - `follows` - Sequence relationship
  - `spawned_from` - Origin tracking
  - `duplicates` - Duplicate work
  - `references` - Consultation reference
- **Rationale**: Template placeholder consumers need full context of all related work
- **Traces to**: `task_relationships` table CHECK constraint

#### FR-4: Return Task Keys, Not IDs
- **Description**: Method must JOIN with tasks table to retrieve `key` column values
- **Output Format**: Array of string keys: `["T-E07-F05-001", "E10-F05-002"]`
- **NOT**: Array of integer IDs: `[123, 456]`
- **SQL Pattern**: `JOIN tasks ON (tasks.id = task_relationships.from_task_id OR tasks.id = task_relationships.to_task_id)`
- **Rationale**: Template placeholders use human-readable keys, not internal IDs
- **Traces to**: Existing key-based patterns in codebase

#### FR-5: Exclude Self-References
- **Description**: If task appears in both from_task_id and to_task_id columns of result set, only include the OTHER task in output
- **Example**: For task ID 100:
  - Relationship: `from_task_id=100, to_task_id=200` → Include task 200's key
  - Relationship: `from_task_id=300, to_task_id=100` → Include task 300's key
  - Do NOT include task 100's own key in results
- **Implementation**: Use `WHERE tasks.id != ?` in JOIN condition
- **Traces to**: Standard graph traversal pattern

#### FR-6: Empty Array for No Relationships
- **Description**: Return empty array `[]` (not nil, not error) when task has no relationships
- **Rationale**: Empty array is valid result; template placeholder will convert to empty string
- **Error Handling**: Return error only for database failures, not for "no results found"
- **Traces to**: REQ-F-002 Acceptance Criteria (empty string if no context data)

- Query uses existing indexes: `idx_task_relationships_from`, `idx_task_relationships_to`
- JOIN leverages tasks.id PRIMARY KEY index

### Step 3: Execute Query and Scan Results
**Implementation Pattern** (following existing repository methods):

```go
func (r *TaskRelationshipRepository) ListRelatedTaskKeys(ctx context.Context, taskID int64) ([]string, error) {
    query := `
        SELECT DISTINCT t.key
        FROM task_relationships tr
        INNER JOIN tasks t ON (
            (tr.from_task_id = ? AND tr.to_task_id = t.id) OR
            (tr.to_task_id = ? AND tr.from_task_id = t.id)
        )
        WHERE t.id != ?
        ORDER BY t.key ASC
    `

    // Execute query with three taskID parameters
    rows, err := r.db.QueryContext(ctx, query, taskID, taskID, taskID)
    if err != nil {
        return nil, fmt.Errorf("failed to list related task keys: %w", err)
    }
    defer rows.Close()

    // Scan results into string array
    var keys []string
    for rows.Next() {
        var key string
        if err := rows.Scan(&key); err != nil {
            return nil, fmt.Errorf("failed to scan task key: %w", err)
        }
        keys = append(keys, key)
    }

    // Check for iteration errors
    if err = rows.Err(); err != nil {
        return nil, fmt.Errorf("error iterating related task keys: %w", err)
    }

    // Return empty array (not nil) if no relationships
    return keys, nil
}
```

**Error Handling**:
- Database errors wrapped with context: `"failed to list related task keys: %w"`
- `sql.ErrNoRows` is NOT an error (just means no relationships)
- Row iteration errors caught with `rows.Err()`
- Context cancellation respected via `QueryContext`

**Validation**: Implements FR-6, NFR-3, NFR-4

## Architecture Decisions

### Decision 1: Single Query with JOIN vs. Two Separate Queries

**Options Considered**:

**A) Single JOIN Query (CHOSEN)**
```sql
SELECT DISTINCT t.key
FROM task_relationships tr
INNER JOIN tasks t ON (...)
WHERE ...
```
**Pros**:
- Single database round-trip (< 10ms)
- Leverages both indexes in one query
- Simpler code (one query, one loop)
- Satisfies REQ-NF-002 (single query)

**Cons**:
- Slightly more complex JOIN logic
- OR condition in JOIN (but optimized by indexes)

**B) Two Separate Queries (REJECTED)**
```go
// Query 1: Outgoing
keys1 := queryOutgoing(taskID)
// Query 2: Incoming
keys2 := queryIncoming(taskID)
// Merge and deduplicate
return dedupe(append(keys1, keys2...))
```
**Pros**:
- Simpler individual queries
- Could reuse existing `GetOutgoing`/`GetIncoming` methods

**Cons**:
- Two database round-trips (N+1 anti-pattern)
- Additional deduplication logic needed
- Violates REQ-NF-002 (single query requirement)

**Decision**: Option A (Single JOIN Query)
**Rationale**: Performance (single round-trip), simplicity (one loop), requirement compliance

---

### Decision 2: Return Array vs. Comma-Separated String

**Options Considered**:

**A) Return `[]string` (CHOSEN)**
```go
func ListRelatedTaskKeys(...) ([]string, error)
// Returns: []string{"E07-F05-001", "E10-F05-002"}
```
**Pros**:
- Type-safe (Go string array)
- Caller can format as needed (CSV, JSON, newline-separated)
- Consistent with other repository methods
- Empty array (`[]`) vs nil distinction

**Cons**:
- Template placeholder consumer must format as CSV

**B) Return CSV String (REJECTED)**
```go
func ListRelatedTaskKeys(...) (string, error)
// Returns: "E07-F05-001,E10-F05-002"
```
**Pros**:
- Directly usable in template placeholder
- No additional formatting needed

**Cons**:
- Couples repository layer to template formatting (wrong layer)
- Harder to test (string parsing in tests)
- Loses type safety (just a string)
- Cannot distinguish empty vs error easily

**Decision**: Option A (`[]string`)
**Rationale**: Separation of concerns (repo returns data, caller formats), type safety, testability

---

### Decision 3: DISTINCT Keyword vs. Application-Level Deduplication

**Options Considered**:

**A) SQL DISTINCT (CHOSEN)**
```sql
SELECT DISTINCT t.key FROM ...
```
**Pros**:
- Database-level deduplication (fast, optimized)
- Simpler Go code (no dedup loop)
- Guaranteed unique keys in result set

**Cons**:
- Minimal overhead (negligible for < 100 keys)

**B) Application Deduplication (REJECTED)**
```go
seen := make(map[string]bool)
for rows.Next() {
    if !seen[key] {
        keys = append(keys, key)
        seen[key] = true
    }
}
```
**Pros**:
- Full control over deduplication logic

**Cons**:
- More code (map allocation, loop logic)
- Slower than SQL DISTINCT for large result sets
- Unnecessary complexity

**Decision**: Option A (SQL DISTINCT)
**Rationale**: Simpler code, database optimization, no measurable overhead

---

### Decision 4: Error Handling for Empty Results

**Options Considered**:

**A) Return Empty Array (CHOSEN)**
```go
if len(keys) == 0 {
    return []string{}, nil  // Empty array, no error
}
```
**Pros**:
- Consistent with "no results is not an error" pattern
- Template placeholder can distinguish empty (`""`) from error
- Caller doesn't need error checking for common case

**Cons**:
- None (this is standard Go pattern for list methods)

**B) Return Error for No Relationships (REJECTED)**
```go
if len(keys) == 0 {
    return nil, errors.New("no relationships found")
}
```
**Pros**:
- Forces caller to handle "no relationships" case

**Cons**:
- Breaks standard repository pattern
- Makes common case (no relationships) an error
- Template placeholder population would fail unnecessarily

**Decision**: Option A (Empty Array)
**Rationale**: Standard Go pattern, user-friendly, template-compatible

## Business Rules

### Rule 1: Bidirectional Inclusion
All relationships are bidirectional for template purposes. If A relates to B, then B's related tasks include A and A's related tasks include B, regardless of relationship direction semantics.

**Example**:
- Task A `depends_on` Task B
- Task A's related: `[B]`
- Task B's related: `[A]` (even though B doesn't depend on A)

**Rationale**: Agents working on either task benefit from seeing the connection.

### Rule 2: No Relationship Type Filtering
Return ALL relationship types. Future filtering can be added if needed, but MVP includes everything.

**Rationale**: Template consumers can filter if needed; repository provides complete data.

### Rule 3: Task Keys, Not IDs
Always return human-readable keys (T-E07-F29-001) for agent/human consumption, never internal database IDs.

**Rationale**: Template placeholders are used in agent instructions (text format).

## Notes

### Implementation Decisions

**Query Choice**: Using JOIN instead of subquery for performance
- **Rationale**: JOIN allows single-pass scan with index usage
- **Alternative Rejected**: Subquery approach (2 queries, slower)

**DISTINCT Keyword**: Included to handle edge case of duplicate keys
- **Rationale**: Task might appear in multiple relationship types to same related task
- **Example**: Task A both `depends_on` and `references` Task B → only include B once

**Ordering**: Added `ORDER BY t.key ASC` for deterministic results
- **Rationale**: Makes testing easier, consistent output for agents
- **Performance**: Minimal overhead, keys are indexed
