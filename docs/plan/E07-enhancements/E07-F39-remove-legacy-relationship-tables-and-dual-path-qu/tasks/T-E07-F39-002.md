# Replace Viewer Adapter Layer With On-Demand Entity Service Calls

## Goal

The viewer's `Hierarchy()` endpoint uses a bespoke `taskRelAdapter` that bypasses
`EntityRelationshipService` to bulk-load all task relationships in one raw SQL query.
This bypass was premature optimisation that produced real bugs (only task→task links
visible, drift to legacy table). Replace it with on-demand service calls matching
the `shark get {id}` pattern — load relationship detail when an entity is requested,
not on hierarchy load.

## Scope

Files to delete:
- `taskRelAdapter` struct and `ListAll()` in `internal/viewer/server/wire.go`
- `ViewerTaskRelationshipRepository` interface in `internal/services/viewer_service.go`
- `ViewerTaskRelationship` struct in `internal/services/viewer_service.go`
- `taskRelRepo` field and `WithTaskRelRepo()` method on `ViewerService`

Files to update:
- `internal/viewer/server/wire.go` — wire `EntityRelationshipService` into ViewerService
- `internal/services/viewer_service.go` — replace bulk relationship map-building in
  `Hierarchy()` and `FeatureTasks()` with `EntityRelationshipService.GetRelationships()`
  per task, using EntityRegistry to resolve the other entity's key (same pattern as
  `shark link list` in `internal/cli/commands/link.go`)
- `ViewerTask` struct — replace `DependsOn`/`BlockedBy`/`Blocks []string` with a
  `Relationships []ViewerRelatedEntity` field carrying entity type + key + direction,
  so task→bug, task→feature, etc. render correctly in the UI

## Acceptance Criteria

- AC-1: `taskRelAdapter`, `ViewerTaskRelationshipRepository`, `ViewerTaskRelationship`
  are deleted — no references remain
- AC-2: Viewer entity detail includes relationships to all entity types, not just tasks
- AC-3: `shark link add <task> <bug> --type=related_to` result appears in viewer
- AC-4: `make fmt && make lint && make test` passes clean

## Test Cases

- Link a task to a bug and verify the viewer task detail JSON includes the bug key
- Link a task to a feature and verify the same
- Verify existing task→task links still appear correctly
- Run full test suite — zero regressions

## Design Reference

See feature.md for the architectural intent (on-demand loading, not bulk pre-load).
See `internal/cli/commands/link.go:runLinks()` for the exact service+registry pattern
to replicate in the viewer.
Dashboard aggregate queries (if needed) belong in a dedicated handler, not here.
