## Findings

### Finding 1 — BLOCKING: `requireNonNil` does not detect typed-nil pointers; two constructor tests fail

`internal/services/viewer_service.go:435-436` calls:

```go
requireNonNil(entityRelSvc, "ViewerService requires a non-nil EntityRelationshipService")
requireNonNil(entityRegistry, "ViewerService requires a non-nil EntityRegistry")
```

`requireNonNil` in `internal/services/helpers.go:11`:

```go
func requireNonNil(value interface{}, name string) {
    if value == nil {
        panic(fmt.Sprintf("%s must not be nil", name))
    }
}
```

When a typed pointer parameter (e.g. `entityRelSvc *EntityRelationshipService`) holds
a nil pointer, assigning it to `interface{}` yields a non-nil interface (the type
descriptor is set). The `value == nil` check then evaluates false and the panic does
not fire.

Reproduced with a standalone Go program:
```
Foo NOT detected as nil (value=<nil>)
no panic
```

This is observable as two failing tests:
```
--- FAIL: TestNewViewerService_PanicsOnNilEntityRelSvc (0.00s)
    viewer_service_test.go:294: expected panic for nil entityRelSvc
--- FAIL: TestNewViewerService_PanicsOnNilEntityRegistry (0.00s)
    viewer_service_test.go:314: expected panic for nil entityRegistry
FAIL    github.com/jwwelbor/shark-task-manager/internal/services
```

**Impact:** contradicts the design decision in spec.md §3.4 ("Require `entityRelSvc`
in ViewerService (not optional) … Making it required removes a branch and a nil-check
path"). A zero-valued pointer variable would pass the constructor and later nil-panic
inside `resolveTaskRelationships` at request time. The whole point of construction-
time validation is lost.

**Fix (any of):**
- Replace the `requireNonNil` calls for `*EntityRelationshipService` and
  `*EntityRegistry` with typed nil checks, matching the pattern already used for
  `workflowSvc`:
  ```go
  if entityRelSvc == nil {
      panic("ViewerService requires a non-nil EntityRelationshipService")
  }
  if entityRegistry == nil {
      panic("ViewerService requires a non-nil EntityRegistry")
  }
  ```
- Or generalize `requireNonNil` to detect typed nils via `reflect.ValueOf(value).IsNil()`
  (guarded by kind check) so all existing call sites stay safe.

The typed-check form is simpler and local to the two new parameters; recommend that.

### Finding 2 — Observation (non-blocking): error from `entityRelSvc.GetRelationships` silently swallowed

`resolveTaskRelationships` returns an empty slice on error:

```go
rels, err := s.entityRelSvc.GetRelationships(ctx, models.EntityTypeTask, taskID)
if err != nil {
    // Treat as empty — relationship data is informational, not load-bearing.
    return []ViewerRelatedEntity{}
}
```

This is a reasonable call (consistent with the viewer’s "informational" framing) but
`test-plan.md TC-5.4` flags this as a decision to be consistent with REQ-N-004. The
comment makes the choice explicit, which is acceptable. No change required, but worth
noting that errors from the downstream service are not observable from the viewer
response or logs. If future debugging needs this, consider at least a debug-level log.

### Finding 3 — Observation (non-blocking): `entityRelSvc` constructed inside `WireServices` without reusing any pre-existing instance

`internal/viewer/server/wire.go:292-293`:

```go
entityRelRepo := repository.NewEntityRelationshipRepository(db)
entityRelSvc := services.NewEntityRelationshipService(entityRelRepo, taskRepo)
```

Elsewhere in the CLI path, `cli.GetEntityRelationshipService()` is the canonical
accessor (spec.md §3.1.5 reference). For the HTTP viewer, building it fresh in
`WireServices` is fine and matches the existing pattern for `NewViewerService`. No
change required.
