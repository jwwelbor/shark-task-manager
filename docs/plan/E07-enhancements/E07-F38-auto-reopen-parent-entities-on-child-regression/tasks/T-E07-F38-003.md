# Wire Cascade Post-Hook into TaskService and FeatureService

## Goal
Inject cascade dependencies into `TaskService` and `FeatureService` and add the backward-transition post-hook after `TransitionStatus` succeeds. Also refactor the existing `maybeReopenParentFeature` and `maybeReopenParentEpic` helpers to delegate to the unified cascade helper, eliminating duplicate reopen logic.

## Scope
- Files to modify:
  - `internal/services/task_service.go`
  - `internal/services/feature_service.go`

## Acceptance Criteria
Reference spec.md: "See spec.md REQ-F-001, REQ-F-002, REQ-F-003, Section 2.1.2 (task_service.go and feature_service.go rows)"
Additional task-specific criteria:
- AC-T1: The cascade post-hook in `TaskService.TransitionStatus` fires only when `from_status` is terminal per `workflow.Service.IsTerminalStatus(LevelTask)` and `to_status` is non-terminal.
- AC-T2: The cascade post-hook in `FeatureService.TransitionStatus` fires only when `from_status` is terminal per `workflow.Service.IsTerminalStatus(LevelFeature)` and `to_status` is non-terminal.
- AC-T3: `maybeReopenParentFeature` (task_service.go ~line 1054) is refactored to call `cascadeParentReopens`; its old inline logic is removed.
- AC-T4: `maybeReopenParentEpic` (feature_service.go ~line 788) is refactored to call `cascadeParentReopens`; its old inline logic is removed.
- AC-T5: New optional constructor fields for cascade deps follow the existing nil-safe optional-dependency pattern used in `TaskService`.
