## 4. Defect Verification — U-01 through U-06

### U-01 (HIGH) — In-tx re-fetch routed through `*sql.Tx` — Code RESOLVED, Test HAS DEFECT

**Verification of production code fix:**
- `cascade_reopen.go:54` — `GetByIDTx(ctx context.Context, tx *sql.Tx, id int64)` present on `CascadeFeatureRepo`. Confirmed.
- `cascade_reopen.go:65` — same on `CascadeEpicRepo`. Confirmed.
- `cascade_reopen.go:269` — `deps.featureRepo.GetByIDTx(ctx, tx, feature.ID)` used at the in-tx re-fetch site. Confirmed.
- `cascade_reopen.go:319` — `deps.epicRepo.GetByIDTx(ctx, tx, epic.ID)` used at the in-tx re-fetch site. Confirmed.

**Verification of test — DEFECT FOUND:**
`TestCascade_ConcurrentCascadeOnSameAncestorWritesExactlyOneHistoryRow` shares a single `mockCascadeEpicRepo` and a single `mockParentReopenHistoryQuerier` between two goroutines. Both mock structs contain unsynchronized call-counter fields (`getByIDCalls`, `calls`) that are mutated concurrently. The race detector reports two distinct data races:

```
WARNING: DATA RACE
Read at cascade_reopen_test.go:80 by goroutine 10  (GetByID — reads m.getByIDCalls)
Previous write at cascade_reopen_test.go:80 by goroutine 11
```
```
WARNING: DATA RACE
Read at cascade_reopen_test.go:123 by goroutine 10  (GetLastNonTerminalStatus — reads m.calls)
Previous write at cascade_reopen_test.go:123 by goroutine 11
```

**Root cause:** The concurrent test added in U-01 remediation gives both goroutines separate `mockCascadeFeatureRepo` instances (correctly, via `makeFeatureRepo`) but shares one `mockCascadeEpicRepo` and one `mockParentReopenHistoryQuerier`. The `getByIDCalls++` and `m.calls++` increments in those shared mocks run from both goroutines with no mutex protection, producing the races the detector reports.

**The `sharedHistTx` recorder does have a mutex** (wraps `mu.Lock()` in its `CreateTxFunc`) — so the history assertion itself is race-free. The defect is only in the call-counter mutations on the two shared mocks.

**Impact on test intent:** The test still correctly asserts `featureRows == 1` (protected by the mutex). The race is in the call-counter accounting fields of the shared mocks, not in the primary assertion. However, a data race in a test is a defect — it produces undefined behavior and will fail `go test -race`, which is a standard CI gate. This is a real bug that must be fixed.

**Evidence:**
```
go test -v -count=1 -race -run TestCascade_ConcurrentCascadeOnSameAncestorWritesExactlyOneHistoryRow ./internal/services/
--- FAIL: TestCascade_ConcurrentCascadeOnSameAncestorWritesExactlyOneHistoryRow (0.00s)
FAIL
```

**Defect ID:** BUG-QA-001 (see Section 6)

## 5. New Defects Found

### BUG-QA-001 — DATA RACE in `TestCascade_ConcurrentCascadeOnSameAncestorWritesExactlyOneHistoryRow`

**Severity:** HIGH (blocks `go test -race` CI gate; data races produce undefined behavior)
**Category:** Test defect introduced during U-01 remediation
**Blocker?** YES

**Description:**
The concurrent cascade test shares one `mockCascadeEpicRepo` instance and one `mockParentReopenHistoryQuerier` instance between two goroutines launched simultaneously. Both mock implementations increment unsynchronized call counters (`m.getByIDCalls++` on line 80 of the test file; `m.calls++` on line 123) from two concurrent goroutines, producing two data races.

**Steps to reproduce:**
```bash
go test -race -count=1 -run TestCascade_ConcurrentCascadeOnSameAncestorWritesExactlyOneHistoryRow ./internal/services/
```

**Expected result:** Test passes with 0 races.

**Actual result:**
```
WARNING: DATA RACE
Read at cascade_reopen_test.go:80 / Previous write at cascade_reopen_test.go:80
WARNING: DATA RACE
Read at cascade_reopen_test.go:123 / Previous write at cascade_reopen_test.go:123
--- FAIL: TestCascade_ConcurrentCascadeOnSameAncestorWritesExactlyOneHistoryRow (0.00s)
```

**Root cause:** The `makeFeatureRepo` helper correctly creates per-goroutine feature repo instances. However `epicRepo` (line 1660) and `histQuerier` (line 1666) are single shared instances constructed outside `makeDeps`. Their call-counter fields are incremented by both goroutines with no mutex.

**Fix options (choose one):**
1. (Simplest) Move `epicRepo` and `histQuerier` construction inside `makeDeps` so each goroutine gets its own instance, eliminating the concurrency entirely on those mocks.
2. Add mutex fields to `mockCascadeEpicRepo` and `mockParentReopenHistoryQuerier` (matching the mutex already present in `sharedHistTx.CreateTxFunc`) and lock on counter increments.
3. Remove the call-counter assertions from the concurrent test entirely — the test's value comes from the `featureRows == 1` assertion (which is already mutex-protected), not from the unsynchronized counters.

Option 1 is the least invasive and does not affect test coverage or intent.

**Note on test intent:** The `featureRows == 1` assertion — the primary correctness assertion for U-01 idempotency — is **not** affected by this race. It is protected by the explicit `mu.Lock()` in `sharedHistTx.CreateTxFunc` and in the final read at line 1712. The race only touches call-counter fields that are not part of any assertion in this test. The fix is mechanical and does not change the test's meaning.
