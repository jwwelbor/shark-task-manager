## 4. UAT Validation of Codex Findings

Each HIGH/MEDIUM finding was independently verified against the actual code:

### U-01 (HIGH) — AC-T2 Not Met: in-tx re-fetch is not routed through the transaction

**Spec text (AC-T2):** *"cascadeParentReopens re-fetches each ancestor's current status inside the cascade transaction before deciding to update (idempotency per REQ-F-008)."*

**Code (cascade_reopen.go:249):**
```go
freshFeature, ferr := deps.featureRepo.GetByID(ctx, feature.ID)
```

**CascadeFeatureRepo interface (cascade_reopen.go:49-52):**
```go
type CascadeFeatureRepo interface {
    GetByID(ctx context.Context, id int64) (*models.Feature, error)
    UpdateStatusTx(ctx context.Context, tx *sql.Tx, id int64, ...) error
}
```

`GetByID` has no `*sql.Tx` parameter. The read is issued on the repository's shared db handle, not the cascade's tx. Under concurrent cascades on the same feature, both cascades can pre-flight, open independent transactions, re-fetch (both seeing terminal because neither has committed), and both proceed to update+write-history — producing duplicate `auto_reopen:` rows. The idempotency guarantee of REQ-F-008 is therefore only a single-cascade guarantee, not a concurrency guarantee.

This is a **real defect** that prior reviews rated PASS. The three Claude-based reviewers (round-1, round-2, QA) all asserted "re-fetch inside tx" based on the code being *textually* inside the post-BeginTx block, without checking that the read was actually routed through the tx.

### U-02 (HIGH / literal AC-T3 violation) — WARN logs omit ancestor field on history-write failure

**Spec text (AC-T3):** *"the error is logged via slog.Warn with the triggering child key and the ancestor that failed"*

**Code (cascade_reopen.go:279-283, feature history write failed):**
```go
slog.Warn("cascade: feature history write failed",
    "trigger_key", trigger.triggerKey,
    "error", herr,
)
```

**Code (cascade_reopen.go:324-327, epic history write failed):** identical — only `trigger_key` + `error`.

Compare to the feature update-failed path (cascade_reopen.go:262-266), which *does* include `feature_key`. The history-write-failed logs are missing the ancestor field that AC-T3 explicitly requires. This is a literal contract violation, not a style nit.

The commit-failed log (line 336-338) is arguably fine because no specific ancestor failed at commit time — accept as-is.

### U-03 (HIGH / test fraud) — Commit_failure subtest does not exercise the commit path

**The Round 2 reviewer wrote:** *"The Commit_failure subtest correctly exercises the previously unused fakeTx.commitErr field."*

**Actual test behavior:**

`mockTxBeginner.BeginTxContext` (cascade_reopen_test.go:162-170):
```go
func (m *mockTxBeginner) BeginTxContext(ctx context.Context) (*sql.Tx, error) {
    m.beginCalls++
    if m.beginErr != nil { return nil, m.beginErr }
    return nil, nil   // <-- returns a nil *sql.Tx
}
```

Cascade commit block (cascade_reopen.go:334-342):
```go
if tx != nil {
    if cerr := tx.Commit(); cerr != nil {
        slog.Warn("cascade: commit failed", ...)
        return
    }
}
```

Because `BeginTxContext` returns `(nil, nil)`, `tx` is nil, so the `if tx != nil { Commit() }` block is skipped entirely. `fakeTx.commitErr` is never read. `tx.Commit()` is never called. The subtest passes trivially. The "slog.Warn exercised" assertion in the round-2 review is incorrect.

**Consequence for REQ-N-006:** The spec says *"All error paths (BeginTx failure, history-lookup error, repository update failure, **commit failure**) MUST have explicit unit tests."* The commit-failure path is still not explicitly tested. F-01 is not actually resolved on this item.

Additionally, `TestCascade_HistoryRowHasChangedAt`, `TestCascade_EmptyTerminalSetGuard`, and every happy-path test in the file all run with `tx == nil`, so no test anywhere in the suite exercises the commit branch or the defer-rollback branch. The entire `if tx != nil { ... }` envelope is structurally untested.

### U-04 (MEDIUM) — FromStatus uses pre-tx status, audit row can be misleading

**Code (cascade_reopen.go:270, 314):**
```go
fromStatus := string(feature.Status)        // <-- pre-tx read
// ... uses freshFeature.Status to DECIDE to update, but stores feature.Status
```

If the feature status changes from e.g. `completed` → `closed` between phase 1 and phase 3 (both still terminal, so the re-fetch still proceeds), the history row records the stale `completed` as the from-status. Round 1 review called this "cosmetic" (review round 1 lines 52-53). For an audit trail whose entire purpose is correct history, "cosmetic" is the wrong framing. Either `freshFeature.Status` / `freshEpic.Status` should be used for `FromStatus`, or the spec should explicitly document that pre-tx status is the recorded value.

### U-05 (MEDIUM) — Empty terminal set is not guarded inside `resolveReopenTarget`

**Code (cascade_reopen.go:371-373):**
```go
terminalSet := levelWf.GetTerminalStatuses()
target, found, err := historyQuerier.GetLastNonTerminalStatus(ctx, entityType, entityID, terminalSet)
```

If `GetTerminalStatuses()` returns an empty slice (possible under a misconfigured custom profile), the `NOT IN (...)` clause in the underlying SQL is effectively vacuous — every row matches — so the resolver could return a *terminal* status as the reopen target, which is nonsense. `TestCascade_EmptyTerminalSetGuard` asserts that the *current production profile* passes a non-empty set; it does not prove the function is defensive against receiving an empty set.

This is a real REQ-F-005 concern under the "custom workflow profiles" clause in the spec.

### U-06 (LOW) — Interface documentation mismatch

`cascade_reopen.go:81-86`:
```go
// levelWorkflowProvider is the provider interface that returns a scoped
// levelWorkflow for a given entity level string.
// Satisfied by *workflow.Service in production.
type levelWorkflowProvider interface {
    ForLevel(level string) levelWorkflow
}
```

`*workflow.Service.ForLevel` returns `*workflow.Service` (concrete), not `levelWorkflow` (interface). Go does not allow covariant return types on interface methods, so `*workflow.Service` does **not** directly satisfy `levelWorkflowProvider`. The test file proves this — it introduces `workflowServiceAdapter` (cascade_reopen_test.go:197-207) exactly to bridge the gap. Production wiring in T-003 will also need an adapter. The doc comment is misleading but not a code defect for this task. Note for T-003.

## 6. What Prior Reviews Missed

This task passed three Claude-based gates (round-1 code review, round-2 code review after F-01 fix, QA) and codex's red-team found three HIGH issues. That is exactly the monoculture pattern the UAT protocol exists to catch:

1. **Round 1 and Round 2 both asserted AC-T2 PASS** by pointing at code *textually* inside the `BeginTx` block, without checking the interface signature. The read is not routed through the tx.
2. **Round 2 claimed the Commit_failure subtest "correctly exercises" the commit path.** It does not — the tx is nil, Commit is never called, the WARN branch is never reached, `fakeTx.commitErr` is never read. REQ-N-006 is still unsatisfied on the commit-failure item.
3. **All three gates rated AC-T3 PASS.** Two of the six WARN log sites structurally violate the contract by omitting the ancestor field that the AC specifies in prose.
4. **Round 1 explicitly called FromStatus staleness "cosmetic".** For an audit trail whose sole purpose is correctness, this framing is wrong.

## 7. Required Remedy Before Re-submit

Minimum set to resolve REJECT:

1. **U-01 (AC-T2):** Route the in-tx re-fetch through the cascade transaction. Two possible approaches:
   - (a) Add a `GetByIDTx(ctx, tx, id)` method to `CascadeFeatureRepo` / `CascadeEpicRepo` and call it after `BeginTxContext`.
   - (b) Document that SQLite with WAL and the cascade's single-writer invariant is sufficient, and add an explicit test that fires two concurrent cascades on the same ancestor and asserts exactly one history row is written. (This is the harder option but directly tests the idempotency claim of REQ-F-008.)
2. **U-02 (AC-T3):** Add `feature_key` / `epic_key` (or equivalent ancestor identifier) to the `cascade: feature history write failed` and `cascade: epic history write failed` WARN log sites.
3. **U-03 (REQ-N-006):** Fix `mockTxBeginner` so the `Commit_failure` subtest actually reaches `tx.Commit()`. The simplest fix is to restructure the cascade to call `deps.db.Commit(tx)` via a tx-commit-hook interface, or to have `BeginTxContext` return a non-nil `*sql.Tx` sentinel and test the commit-failure indirectly via a different seam. Alternatively, introduce a `commitFn func(*sql.Tx) error` field in `cascadeDeps` whose production implementation is `tx.Commit()` and whose test implementation is the mock — this is the cleanest way to make the commit branch testable without changing production behavior.
4. **U-04 (recommended):** Use `freshFeature.Status` / `freshEpic.Status` for the history row's `FromStatus`, so audit rows reflect the value that was actually used in the in-tx decision.
5. **U-05 (recommended):** Add an explicit guard in `resolveReopenTarget` that treats an empty `terminalSet` as a skip-or-fallback signal, and add a direct test with a mock `levelWorkflow` that returns an empty terminal-set.
6. **U-06 (informational):** Update the doc comment on `levelWorkflowProvider` to note that production wiring requires an adapter (same as the test file). This is for T-003 to consume.

Items 1–3 are **blockers**. Items 4–5 are strongly recommended to close the audit-row and custom-profile risks surfaced by this review. Item 6 is informational for T-003.
