## 2. Acceptance Criteria — Independent Verification

### AC-T1: Parameterized NOT IN, no hardcoded statuses — VERIFIED MET

`internal/repository/entityhistory/repository.go:110-136` constructs the NOT IN clause by:
1. Computing `placeholders[i] = "?"` for each element of `terminalStatuses`
2. Joining with `, ` and embedding via `fmt.Sprintf`
3. Passing actual values via `args = append(args, entityType, entityID); for _, s := range terminalStatuses { args = append(args, s) }`
4. Executing `r.db.QueryRowContext(ctx, query, args...)`

The only thing interpolated into the SQL text is the literal characters `?, ?, ?, ...` — pure placeholder syntax, never user data. Even a maliciously-crafted status string in `terminalStatuses` cannot escape the parameter binding because it never enters the SQL text. Empty-slice branch (line 113-119) takes a static query with no NOT IN clause at all, avoiding a `NOT IN ()` syntax error.

No grep hit for hardcoded status names like `"completed"`, `"cancelled"` in the function body. PASS.

### AC-T3: `UpdateStatusTx` mirrors existing `UpdateStatus` — VERIFIED MET (with documented deviation)

The existing `FeatureRepository.UpdateStatus(ctx, featureID int64, status models.FeatureStatus)` and `EpicRepository.UpdateStatus(ctx, epicID int64, status models.EpicStatus)` take 3 parameters with typed status enums.

The new `UpdateStatusTx(ctx, tx, id, status string, agent *string, notes *string)` deviates from the literal task wording ("adding only the `*sql.Tx` parameter") in two ways:
1. Adds `agent *string, notes *string` parameters
2. Uses `string` instead of `models.FeatureStatus` / `models.EpicStatus`

Both deviations are mandated explicitly by **spec.md Section 2.3.1**, which is the authoritative contract. The cascade helper (T-E07-F38-002) consumes these via the `CascadeFeatureRepo` / `CascadeEpicRepo` interfaces in spec.md Section 2.3.2, which require this exact signature. The cascade resolves status as a string from history-lookup output and the workflow service, so a typed enum here would force unnecessary conversions.

The unused `agent`/`notes` params are explicitly documented at `feature/repository.go:1086-1087` and `epic/repository.go:641-642`:

> `_ *string, // agent — reserved for interface symmetry, not persisted to features table`

Using `_` blanks both suppresses linter complaints and makes the intent unmistakable. The cascade helper (built in T-E07-F38-002) will use these values in the accompanying `entity_history` row, not in the `features`/`epics` table.

**Conclusion:** The literal task-AC wording is technically violated but the spec.md contract — which is the controlling document — is followed exactly. This is a documentation gap in T-E07-F38-001's task spec, not an implementation defect. The code review and QA both correctly flagged and adjudicated this. PASS.

### AC-T4: Index check (REQ-N-005) handled correctly — VERIFIED MET (no-op)

I independently grepped `internal/db/db.go` for `idx_entity_history` and confirmed:

- Line 233: `CREATE INDEX IF NOT EXISTS idx_entity_history_entity_time ON entity_history(entity_type, entity_id, changed_at);`
- Line 2604: same definition (in a secondary schema-init path)

This composite index covers the lookup query:
```sql
WHERE entity_type = ? AND entity_id = ? AND to_status NOT IN (...) ORDER BY changed_at DESC LIMIT 1
```

SQLite seeks `(entity_type, entity_id)` directly, then walks the third index column `changed_at` in DESC order via reverse scan. The `to_status NOT IN (...)` filter is applied during the scan but bounded by `LIMIT 1` plus early termination once a non-terminal row is found. For typical entities (small history) this is essentially a single index seek.

`CurrentSchemaVersion` is unchanged at 11 (`db.go:438`). No migration was added. No `skip_migrations` toggle was needed. The implementer correctly identified the existing index as sufficient and made no schema change. PASS.

## 4. Red-Team Findings

I probed for issues the prior reports may have missed.

### 4.1 SQL injection surface — CLEAN

The only `fmt.Sprintf` use in the new code is at `entityhistory/repository.go:125-130`, embedding pre-validated `?` placeholders only. Status values flow exclusively through parameter binding. No injection vector even with adversarial caller input.

### 4.2 SQL parameter limit — NOT A PRACTICAL CONCERN

A pathological caller passing 1000+ terminal statuses could approach SQLite's parameter limit (default ~999). In practice, the workflow's terminal status set is small (~3-5 entries). The cascade helper (T-E07-F38-002) is the only future caller and will derive this set from `workflow.Service`, which has a bounded number of terminal statuses. Not a defect, but worth noting for the cascade integration tests in T-E07-F38-002.

### 4.3 Empty terminal-set "footgun" — DOCUMENTED CONTRACT

`GetLastNonTerminalStatus` with `terminalStatuses == nil` or `[]string{}` returns the most recent history row regardless of whether its status is terminal. A caller who forgets to populate the set could get back a "completed" status as the "non-terminal" target, causing a no-op or worse a regression-loop in the cascade.

This is a deliberate contract decision — the test `empty_terminal_set_returns_most_recent` codifies it. The doc comment at line 108-109 calls it out:

> When terminalStatuses is empty, the WHERE clause has no NOT IN filter, so all rows are considered non-terminal.

The cascade helper (T-E07-F38-002) MUST guard against this by ensuring `workflow.Service` returns a non-empty terminal set. This is the right separation of concerns — the repository is pure data access; the service enforces the business rule that the terminal set is populated. Acceptable, but flagged for T-E07-F38-002 review.

### 4.4 `agent`/`notes` ignored on `UpdateStatusTx` — INTENTIONAL

The `_ *string` blanks for `agent` and `notes` are deliberate — `features` and `epics` tables have no agent/notes columns. The cascade helper writes those values into the `entity_history` row instead, via `CreateTx`. Verified by reading the cascade helper sketch in spec.md Section 2.3 (lines 511-525, 559-573). The repository correctly does not silently lose data — it accepts the params for interface conformance and the caller knows where they actually go.

### 4.5 `CreateTx` does not set `ChangedAt` automatically — DOCUMENTED CONSISTENCY

Like the existing `Create()`, `CreateTx` requires the caller to populate `history.ChangedAt`. There is no `CURRENT_TIMESTAMP` SQL fallback. The cascade helper sketch in spec.md does set `ChangedAt: time.Now()` explicitly. Consistent with the existing contract; not a defect.

### 4.6 Transaction-vs-non-transaction divergence — CLEAN

Both `Create` and `CreateTx` use the same INSERT statement and the same `history.Validate()` precondition. They differ only in `r.db.ExecContext` vs `tx.ExecContext`. Same goes for `UpdateStatus` vs `UpdateStatusTx` (modulo the unused agent/notes params and the typed-vs-string status). No risk of subtle behavior drift.

### 4.7 No new call sites in production code — EXPECTED

Per spec.md Section 2.5 (Rollout Sequence), this task is step 1 of 7: "Land repository additions. Pure additions; no behavior change." Zero non-test call sites is the intended state. The cascade helper (T-E07-F38-002) is the consumer. The QA report's "E2E Reachability Assessment" already addresses this correctly.

### 4.8 Backward compatibility — CLEAN

The new methods are pure additions. No existing method signatures, behaviors, or queries were modified. `make test` (51/51 packages) passing confirms no regressions in unrelated code paths.
