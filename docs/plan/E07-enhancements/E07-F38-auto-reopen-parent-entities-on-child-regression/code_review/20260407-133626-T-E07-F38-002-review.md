### Design optimization worth calling out (acceptable)
The implementation runs a three-phase sequence (pre-flight lookup → resolve targets → tx phase) rather than the simpler single-phase sketch in `spec.md §2.5.4`. This is a legitimate optimization for the AC-05 "full no-op" path: when neither ancestor is terminal, the cascade never opens a transaction at all. `TestCascade_AllAncestorsNonTerminalNoOp` explicitly asserts `beginCalls == 0` for this case. Approved.

### Minor observation (not a finding)
Lines 270 and 314 populate `EntityHistory.FromStatus` from the *pre-tx* feature/epic status read, not the in-tx `freshFeature`/`freshEpic` status. In practice this is identical because the in-tx re-check only proceeds when the status is still terminal — but the two reads could theoretically see different terminal values across a concurrent edit. Cosmetic; accept as-is.

## Findings

### F-01 (BLOCKER) — REQ-N-006 gap: missing explicit unit tests for commit failure and epic-leg error paths

**Spec text (REQ-N-006, `spec.md:109`):**
> All error paths (BeginTx failure, history-lookup error, repository update failure, commit failure) MUST have explicit unit tests.

**What is tested today (`TestCascade_TxFailureIsNonBlocking`):**
- BeginTx failure — covered
- Feature `UpdateStatusTx` failure — covered
- `resolveReopenTarget` history-lookup error — covered separately

**What is NOT tested (reachable code paths, all logged in `cascade_reopen.go`):**

1. **Commit failure** — `cascade_reopen.go:335` `tx.Commit()` returns an error → `slog.Warn("cascade: commit failed", ...)`. The `fakeTx.commitErr` field is already wired in the mock but no test sets it.
2. **Feature history-write failure** — `cascade_reopen.go:279` `historyTx.CreateTx` error branch.
3. **Epic re-fetch failure inside tx** — `cascade_reopen.go:293` second `GetByID` call error branch.
4. **Epic `UpdateStatusTx` failure** — `cascade_reopen.go:305` — symmetric to the feature case that *is* tested.
5. **Epic history-write failure** — `cascade_reopen.go:315` — symmetric to the feature case that *is* tested.
6. **Feature re-fetch failure inside tx** — `cascade_reopen.go:249` second `GetByID` call error branch.
7. **Initial feature lookup failure (outer phase)** — `cascade_reopen.go:166` — the very first `GetByID` error branch.
8. **Initial epic lookup failure (outer phase)** — `cascade_reopen.go:177` — symmetric.

Each of these is a single-line WARN log that matches REQ-N-003 behavior (cascade logs and returns). Each is independently reachable and testable with the existing mock infrastructure. The absence of tests for the commit-failure path in particular is called out because AC-13 and the Risk Register (`spec.md:661`) both hinge on that guarantee.

**Fix:** Extend `TestCascade_TxFailureIsNonBlocking` with additional subtests (`Commit_failure`, `Epic_update_failure`, `Feature_history_write_failure`, `Epic_history_write_failure`, and lookup-failure cases). The infrastructure is already in place — `fakeTx.commitErr`, `UpdateStatusTxFunc`, `CreateTxFunc`, and `GetByIDFunc` on all mocks can return errors inline. Estimated effort: ~80 lines of test code; should lift `cascadeParentReopens` coverage above the REQ-N-006 80% target and close the explicit-test requirement.

**Why blocker:** REQ-N-006 uses MUST. The cascade is a best-effort, fire-and-forget mechanism — the only way to detect regressions in its error handling is through explicit tests. Relying on "the code looks right" or on integration tests in T-E07-F38-003 would leave the non-blocking guarantee unverified.
