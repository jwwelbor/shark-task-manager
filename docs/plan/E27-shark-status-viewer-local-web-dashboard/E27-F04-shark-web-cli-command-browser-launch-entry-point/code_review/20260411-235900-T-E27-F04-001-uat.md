### AC2 — `shark web --port 8080` uses port 8080 specifically (fail-fast if busy)

**Code evidence (web.go lines 97–103):**
```go
if cmd.Flags().Changed("port") {
    port, err = findFreePort(webPort, webPort)
    if err != nil {
        return fmt.Errorf("port %d is already in use", webPort)
    }
}
```
`cmd.Flags().Changed("port")` is `true` only when the user explicitly passes `--port`. When set, `findFreePort(webPort, webPort)` is called with `start == end`, so the loop executes exactly once on that specific port. If it is busy, the loop produces `"no free port found in range N–N"` which is replaced by the user-friendly `"port N is already in use"`. Auto-increment is not possible because `start == end`.

This was the defect from reviews #1 and #2. The fix is confirmed present in the live code.

**Status: PASS**

### AC3 — When port 7777 is in use, automatically tries 7778, 7779, ... up to 7790

**Code evidence (web.go lines 104–109):**
```go
port, err = findFreePort(webPort, webPort+13)
```
`webPort` defaults to 7777 (line 40), so this call is `findFreePort(7777, 7790)`. `findFreePort` iterates the closed range `[start, end]` (line 49: `for port := start; port <= end; port++`), trying each port with `net.Listen("tcp", "127.0.0.1:<port>")`. 7777 + 13 = 7790. Range is 7777..7790 inclusive = 14 candidates. Matches the spec.

**Test coverage:** `TestFindFreePort` verifies the returned port is within range and bindable. `TestFindFreePort_AllBusy` verifies failure when the entire single-port range is busy (same logic applies to the full range).

## Red-Team Findings

### Finding 1 — TOCTOU race in `findFreePort` (NON-BLOCKING, ACKNOWLEDGED)

**Description:** `findFreePort` probes a port by opening and immediately closing a listener, then returning the port number. The server then re-binds that port in `viewerserver.StartServer`. In the window between the close and the re-bind, another process could claim the port.

**Risk:** Low — this is a developer CLI tool, not a production server. The task spec explicitly acknowledges this: `"net.Listen check for port: open and immediately close; this is a TOCTOU race but acceptable for a developer tool"`.

**Alternative available:** `viewerserver.Options.Listener` accepts a pre-bound `net.Listener`. The web command could have eliminated the race entirely by passing a pre-bound listener (bind once, pass it in). However, the current approach works correctly for its intended use case, and the spec does not require the pre-binding pattern.

**Classification:** Acceptable known trade-off, not a defect.

---

### Finding 2 — Shutdown drain path edge case (NON-BLOCKING)

**Description:** In `runWeb` lines 169–181, after `ctx.Done()` fires, `srv.Shutdown()` is called inside `StartServer`. The web command then reads from `srvErr` to confirm the goroutine exited. Because `srvErr` is buffered (capacity 1) and `StartServer` always sends exactly one value before returning, the drain is safe and cannot block forever.

However, if `StartServer` itself panics (rare), the drain `<-srvErr` would block indefinitely since no value is ever sent. This is a cosmetic concern in an edge case.

**Classification:** Non-blocking observation. No action required.

---

### Finding 3 — No `runWeb` integration test (NON-BLOCKING)

**Description:** `web_test.go` covers `findFreePort` and `openBrowserForOS` as unit tests but does not test `runWeb` end-to-end (would require wiring a mock DB and mock server). The task spec explicitly delegates integration testing to T-E27-F04-003.

**Classification:** By design. T-E27-F04-003 carries this scope.
