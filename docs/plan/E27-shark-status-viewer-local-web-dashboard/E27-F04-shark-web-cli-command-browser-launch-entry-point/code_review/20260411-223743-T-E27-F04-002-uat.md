## Red-Team Findings

### 1. Readiness channel contract — VERIFIED CORRECT

The `web.go` command creates `readyCh := make(chan struct{})` (unbuffered) and passes it as `opts.Ready`. `server.go` closes it at line 161-163 **after binding the listener but before `srv.Serve` blocks** (server.go step 7 of 9). The `runWeb` first `select` (web.go:142-151) unblocks on either `srvErr` (server fails before ready) or `readyCh` (server ready). No deadlock scenario exists — if `StartServer` returns early due to dbinit/bind failure, `srvErr` receives the error and the select unblocks correctly.

### 2. Graceful shutdown timing — ACCEPTABLE

After `ctx.Done()` fires (Ctrl+C), `web.go:177` blocks on `<-srvErr` waiting for `StartServer` to return. `StartServer` internally performs a 30-second graceful shutdown (`shutdownTimeout`). This is the correct and expected behavior — the user sees "Shutting down..." immediately, and the process exits after in-flight requests drain (up to 30 seconds). No goroutine leak.

### 3. URL injection security — CLEAN

The URL passed to `openBrowserForOS` is always `fmt.Sprintf("http://127.0.0.1:%d", port)` where `port` is an integer (web.go:155). No user-controlled string components enter the URL or the exec.Command arguments. The Windows path `exec.Command("cmd", "/c", "start", url)` passes URL as a discrete argument, not via shell string interpolation. No injection vector.

### 4. Package-level flag variable concurrency — NON-ISSUE

`webPort` and `webNoOpen` are package-level variables bound to Cobra flags. Concurrent invocations of `shark web` would be separate processes (CLI is a single-shot command), so there is no race condition here.

### 5. Port 0 edge case — NON-ISSUE

`findFreePort(0, 0)` would succeed (OS assigns a port) but the range `[7777, 7790]` is always used by default. No adversarial input path to port 0 exists since `--port` takes an int and defaults to 7777.

### 6. Goroutine / srvErr channel drain — CORRECT

`srvErr` is a buffered channel of size 1 (web.go:135). `StartServer` always sends exactly one value to it (either nil or an error) before returning. Both select branches at web.go:169-179 drain `srvErr` before `runWeb` returns. No goroutine leak.

### 7. Command name collision — NONE

`"web"` is registered once via `cli.RootCmd.AddCommand(webCmd)` (web.go:42). No other command in `internal/cli/commands/` registers a command named "web".

### 8. Windows `start` command — CORRECTLY IMPLEMENTED

Spec requires: `exec.Command("cmd", "/c", "start", url)`. Implementation at web.go:80 is exactly this. Shell invocation is required because `start` is a `cmd.exe` builtin, not a standalone binary.

## Issues Found

### Non-blocking observations (do not affect verdict)

1. **`--port 0` behavior**: Passing `--port 0` would call `findFreePort(0, 0)`, which successfully binds port 0 (OS assigns ephemeral port) then constructs the URL as `http://127.0.0.1:0`. The server would then bind `opts.Addr = "127.0.0.1:0"` which gives a different OS-assigned port than the probe. The URL printed would be incorrect. This is a corner case that no reasonable user would trigger — port 0 is not a meaningful listen port. No fix required for this task's scope.

2. **Output style note**: Prior reviews correctly identified that `fmt.Printf`/`fmt.Println` is appropriate here. `cli.Success` uses pterm decorators that would corrupt the URL for copy-paste. The spec's "consistent with CLI style" intent is met by using `cli.Warning` for the error case.
