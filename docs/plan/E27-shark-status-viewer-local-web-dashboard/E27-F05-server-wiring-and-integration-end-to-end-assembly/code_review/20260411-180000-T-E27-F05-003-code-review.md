## Findings

### FAIL — TC-011b: OPTIONS preflight with external origin behavior diverges from spec

**Spec requirement (task T-E27-F05-003, AC TC-011b):**
> Status 204 (OPTIONS always short-circuits).
> Access-Control-Allow-Origin header is absent.

**Spec requirement (functional requirements):**
> For OPTIONS requests: return `http.StatusNoContent` (204) and do NOT call `next.ServeHTTP`

The requirement is unambiguous: ALL OPTIONS requests — regardless of origin — must short-circuit with 204 and never call `next.ServeHTTP`.

**Implementation (cors.go lines 29–46):**

```go
if isLocalOrigin(origin) {
    w.Header().Set("Access-Control-Allow-Origin", origin)
    w.Header().Add("Vary", "Origin")

    if r.Method == http.MethodOptions {
        // Handle preflight request.
        w.Header().Set("Access-Control-Allow-Methods", "GET, OPTIONS")
        w.Header().Set("Access-Control-Allow-Headers", "Content-Type, Authorization")
        w.Header().Set("Access-Control-Max-Age", "86400")
        w.WriteHeader(http.StatusNoContent)
        return
    }
}

next.ServeHTTP(w, r)  // ← called for external OPTIONS requests
```

For an external origin OPTIONS request, the code falls through to `next.ServeHTTP(w, r)`. This means:
1. The inner handler IS called (spec says it must NOT be for OPTIONS).
2. The status code is whatever the inner handler sets, not 204.

**Test TC-011b in cors_test.go (lines 142–158):**

The test does NOT assert that the inner handler was not called, and does NOT assert a 204 status. It only verifies the ACAO header is absent. This makes the test incomplete — it passes despite the behavior being wrong.

The comment in the test (lines 153–155) acknowledges the non-conformance:
```go
// For external origins, the OPTIONS request falls through to next (not short-circuited).
// The inner handler is called — behavior depends on the wrapped handler.
```

This comment documents a deliberate deviation from the spec. The deviation is not sanctioned by the task spec or any ADR.

**Impact:** For external-origin preflight requests, the middleware proxies to the inner handler rather than short-circuiting. This means the application handler receives OPTIONS requests it should never see. It is a behavioral correctness issue with potential CORS security implications (though limited because ACAO is not set).

**Required fix:** Move the OPTIONS short-circuit check outside the `isLocalOrigin` block:

```go
func WithLocalCORS(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        origin := r.Header.Get("Origin")

        if origin != "" && isLocalOrigin(origin) {
            w.Header().Set("Access-Control-Allow-Origin", origin)
            w.Header().Add("Vary", "Origin")
            w.Header().Set("Access-Control-Allow-Methods", "GET, OPTIONS")
            w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
        }

        if r.Method == http.MethodOptions {
            w.WriteHeader(http.StatusNoContent)
            return
        }

        next.ServeHTTP(w, r)
    })
}
```

Also update TC-011b to assert `rec.Code == 204` and `called == false`.

## Additional Observations (Non-Blocking)

These are minor deviations from the spec but do not warrant a FAIL by themselves. Fix alongside the above.

### Access-Control-Allow-Headers includes `Authorization`

**Spec:** `Set Access-Control-Allow-Headers: Content-Type`

**Implementation:** `Content-Type, Authorization`

The `Authorization` header is not listed in the task spec. This is extra permissiveness not sanctioned by ADR-E27-007 which mandates scoped-to-localhost-only CORS. Should be trimmed to `Content-Type` only unless there is a use case.

### Access-Control-Max-Age set but not required

**Spec:** Does not mention `Access-Control-Max-Age`.

**Implementation:** Sets `Access-Control-Max-Age: 86400`.

This is harmless but adds untested behavior. Acceptable if intentional; should be noted in a code comment citing the rationale.
