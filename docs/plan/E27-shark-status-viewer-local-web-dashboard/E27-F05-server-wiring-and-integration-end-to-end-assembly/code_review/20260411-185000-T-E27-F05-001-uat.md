## Scope

**Task:** Replace `db.InitDB("shark-tasks.db")` in `cmd/server/main.go` with `dbinit.Init(ctx, dbinit.Options{})` from `internal/dbinit`. Server must honor `.sharkconfig.json`, support local SQLite and Turso backends, and respect `skip_migrations`.

## Acceptance Criteria — Independent Verification

### REQ-F-001: No `db.InitDB("shark-tasks.db")` call in `cmd/server/main.go`

**Status: PASS**

Evidence: Grep of `cmd/server/` confirms the string is absent. `cmd/server/main.go` (40 lines) imports `viewerserver` and delegates directly to `viewerserver.StartServer(ctx, viewerserver.Options{Addr: ":8080"})`. There is no database interaction at all in `cmd/server/main.go`.

### REQ-F-001: `dbinit.Init` called with context and options

**Status: PASS**

Evidence: `internal/viewer/server/server.go:81` calls `dbinit.Init(ctx, dbinit.Options{ProjectRoot: opts.ProjectRoot})`. The call is conditional — it only runs when `opts.DB == nil` (i.e., no pre-initialized DB was passed by the caller). The context flows from the caller through to `dbinit.Init`, ensuring proper cancellation propagation.

### REQ-F-001: `go build ./cmd/server/...` succeeds

**Status: PASS**

Evidence: Build confirmed clean with no output (exit 0).

### REQ-F-001: `make test` passes

**Status: PASS**

Evidence: All 5 tests in `internal/viewer/server/server_test.go` pass. All 14 tests in `internal/dbinit/` pass. The code review report states 55 packages / 0 failures which is consistent with a clean build.

### TC-001: Server starts with dbinit (readyCh closed without error in temp dir)

**Status: PASS**

Evidence: `TestStartServer_TC012_ReadySignal` provides direct coverage. It passes `opts.DB` (a pre-initialized `:memory:` DB) so the `callerOwnedDB` path is exercised, but the ready channel behavior is identical. The test confirms `opts.Ready` is closed before `srv.Serve` blocks and that the `/health` endpoint responds 200 immediately after the signal. Timing: < 30ms, well under the 500ms budget.

Additionally, `TestStartServer_TC018_ReadyWithin500ms` explicitly measures the elapsed time to `ready` signal and asserts < 500ms.

### TC-002: Server starts even when no `.sharkconfig.json` is present

**Status: PASS**

Evidence: `internal/dbinit/init_test.go:TestInit_LocalSQLite` tests `Init()` with an empty temp dir (no config file). `loadDatabaseConfig` returns the safe default `{Backend: "sqlite", URL: "<projectRoot>/shark-tasks.db"}` when the config file is absent — verified at `internal/dbinit/init.go:97-101`. `TestStartServer_DefaultAddr` runs StartServer with only `opts.DB` (no ProjectRoot, no Addr, no config) and confirms the server binds to `:8080` and fires the ready signal.

## Red-Team Findings

### Wiring — Is `dbinit.Init` actually reachable from the deployed entry point?

**Finding: PASS**

`cmd/server/main.go` → `viewerserver.StartServer` → `dbinit.Init` (line 81, conditional on `opts.DB == nil`). Call site exists in production code, not only in tests. No dead code.

### DB ownership contract — could `repoDB.Close()` be called on a caller-provided DB?

**Finding: PASS**

`server.go:76` sets `callerOwnedDB := opts.DB != nil`. The `defer repoDB.Close()` at line 86 is only registered when `!callerOwnedDB`. `TestStartServer_TC014b_CallerProvidedDB` directly validates this: after `StartServer` returns, `repoDB.Ping()` succeeds, proving the DB was not closed.

### Context cancellation before DB init — could a cancelled context hang init?

**Finding: PASS**

`dbinit.Init` propagates `ctx` to `initTurso` which passes it to `db.InitDatabase`. For local SQLite, `ctx` is not used (SQLite init is synchronous and fast). The signal-notified context in `cmd/server/main.go` is only cancelled on SIGINT/SIGTERM, which cannot race with the startup path under normal conditions.

### Health endpoint under DB failure — does it return the correct status code?

**Finding: PASS**

`server.go:118-124`: on `repoDB.Ping()` failure, returns HTTP 503 with a descriptive message. On success, returns 200 "OK". This matches the original behavior specified in the task.

### Error wrapping — are errors from `dbinit.Init` propagated correctly?

**Finding: PASS**

`server.go:82-84`: wraps `dbinit.Init` error with `fmt.Errorf("failed to initialize database: %w", err)`. The error propagates up from `StartServer` to `cmd/server/main.go` which logs it at ERROR level and exits 1. Correct behavior.

### Integrity check log lines preserved?

**Finding: PASS**

`server.go:91-94`: `db.CheckIntegrity(repoDB.DB)` is called and `slog.Info("Database integrity check passed")` is logged on success — matching the task requirement to preserve those lines. Confirmed in test output: `"INFO Database integrity check passed"` appears in all 5 server test runs.

### `defer db.Close()` preserved?

**Finding: PASS**

`server.go:86`: `defer repoDB.Close()` is registered only for server-owned DBs. For caller-provided DBs, the caller retains ownership and must close it themselves (as `cmd/server/main.go` does not pass opts.DB, this path is the live production path where StartServer owns and closes the DB).

### Out-of-scope modifications — do any changes outside task scope introduce regressions?

**Finding: PASS**

The implementation also moved `WireServices`/`ServiceContainer` to `internal/viewer/server/wire.go` and reduced `cmd/server/services.go` to a 26-line re-export wrapper. This is within F05 feature scope (per spec.md §1) and does not change the service graph or break any API contracts. The type alias `type ServiceContainer = viewerserver.ServiceContainer` preserves backward compatibility.
