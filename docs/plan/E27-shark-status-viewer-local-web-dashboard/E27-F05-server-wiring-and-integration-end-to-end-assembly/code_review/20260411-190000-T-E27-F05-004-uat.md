### REQ-F-006 / TC-012: `StartServer` closes `opts.Ready` before blocking on `Serve`

**Verified independently against code.**

At lines 161-175 of `server.go`:
```go
if opts.Ready != nil {
    close(opts.Ready)           // Step 7: signal BEFORE Serve
}
srvErr := make(chan error, 1)
go func() {
    srv.Serve(ln)               // Serve in goroutine — blocks
}()
```

The close happens synchronously in the calling goroutine before the `go func()` that launches `srv.Serve`. This is race-free. No goroutine scheduling hazard because the close completes before the goroutine is even started.

**Test evidence:** `TestStartServer_TC012_ReadySignal` passes (observed: ready signal fires in <30ms, server accepts HTTP within the same test). Test also verifies `/health` returns 200 after the ready signal — i.e., the server is actually accepting connections.

## Red-Team Findings

### Finding 1: Listener leak on post-bind error (non-blocking)

When `opts.Listener` is nil and `StartServer` opens a new listener, if a programming error caused a panic between listener bind (step 6) and `srv.Serve` start, the listener would leak. However:

1. There is no code between the listener bind and `srv.Serve` that can return an error (only `opts.Ready` close, which cannot fail).
2. `srv.Serve` takes ownership of the listener and closes it on graceful shutdown.
3. Comment on line 154 acknowledges this design: "Only close the listener on error paths; srv.Serve takes ownership."

This is an acceptable design trade-off and is consistent with the standard `net/http` usage pattern. Non-blocking.

### Finding 2: `web.go` CLI command (F04) not yet present

This is a known scope boundary, not a defect. Non-blocking.
