## Red-Team Independent Findings

### Finding 1: `repoDB.DB` in cmd/server/main.go — correct promoted field access

`cmd/server/main.go` line 54:
```go
if err := db.CheckIntegrity(repoDB.DB); err != nil {
```

`repository.DB` is a type alias for `dbconn.DB` (repository/repository.go line 14):
```go
type DB = dbconn.DB
```

`dbconn.DB` embeds `*sql.DB` as an unnamed field (dbconn/db.go line 16-18):
```go
type DB struct {
    *sql.DB
}
```

`db.CheckIntegrity` takes `*sql.DB` (db/db.go line 496):
```go
func CheckIntegrity(db *sql.DB) error {
```

`repoDB.DB` accesses the promoted `*sql.DB` field (standard Go embedding promotion).
This compiles and is correct. The code review noted "works as long as `repository.DB`
embeds `*sql.DB`" — confirmed it does.

### Finding 2: `loadDatabaseConfig` uses `configDir` not `projectRoot` for default URL in one branch

When the config file has a `database` section but an empty `url`, the fallback is
(init.go line 151):
```go
dbConfig.URL = filepath.Join(configDir, "shark-tasks.db")
```
where `configDir = filepath.Dir(configPath)`.

When `opts.ConfigPath` is empty (the common case), `configPath = filepath.Join(projectRoot, ".sharkconfig.json")`,
so `configDir == projectRoot` and the behavior is identical. This diverges only when a
caller supplies an explicit `ConfigPath` in a directory different from `ProjectRoot`.
In that case `configDir` (where the config lives) is used rather than `projectRoot`. This
is documented in the code review as acceptable. The `internal/cli/db_init.go` delegate
always passes `ProjectRoot` and `ConfigPath` pointing to the same directory
(lines 21-24 of db_init.go), so no regression in the CLI path.

No issue. Documented for transparency.

### Finding 3: `os.ExpandEnv` on config fields — no injection risk

`os.ExpandEnv` expands environment variables in `backend`, `url`, and `auth_token_file`
fields (init.go lines 127, 131, 135). An adversarial `.sharkconfig.json` could use
`$PATH` or other env vars. However:

- This is a local config file written by the developer — no external input reaches it.
- The same pattern exists in `internal/cli/db_helper.go` (pre-existing parity).
- Environment variable expansion in config files is an intentional feature, not a
  vulnerability in this trust model.

No issue.

### Finding 4: Path traversal in URL field

A config with `"url": "../../etc/passwd"` would be passed to `db.InitDB()`. Since
`db.InitDB` opens an SQLite file, the worst case is an error (not a readable text file
as a SQLite database). This is local configuration — no remote exploit surface.
The same risk existed before this refactor. No regression introduced.

### Finding 5: `findProjectRoot` no-marker fallback vs. spec error

The spec (task file line 67-68) says:
```
Return error with message "dbinit: project root: could not locate project root" if nothing found.
```
The implementation falls back to `startDir` instead. This is consistent with
`cli.FindProjectRoot` behaviour and was accepted by the code review. The QA report
confirms test `TestFindProjectRoot_NoMarkers` validates the fallback.

Consequence: callers cannot distinguish "found root" from "no root, fell back to cwd."
For production use this is safe (falls back to cwd which is correct for standard usage).
This is a spec deviation, not a correctness defect.

### Finding 6: Turso auth path — `Validate()` before network dial

`initTurso` (init.go line 181) calls `dbConfig.Validate()` before `db.InitDatabase`.
This validates the URL format, ensuring malformed URLs fail fast without incurring
network overhead. Correct.

### Finding 7: `SkipMigrations` branch in `initTurso`

The spec (REQ-F-005) requires: when `skip_migrations: true`, call `db.ApplySchemaIfNeeded`;
otherwise call `db.ApplySchemaAndMigrations`.

Implementation (init.go lines 200-208):
```go
if dbConfig.SkipMigrations {
    if _, err := db.ApplySchemaIfNeeded(sqlDB); err != nil {
        ...
    }
} else {
    if err := db.ApplySchemaAndMigrations(sqlDB); err != nil {
        ...
    }
}
```
Correct.

### Finding 8: `internal/cli/db_helper.go` is NOT a thin wrapper to `dbinit`

The spec (section 3, Integration Points) states that `internal/cli/db_helper.go` should
either keep `GetDatabaseConfig` as thin wrappers calling `dbinit` internals, or be removed.
The actual `db_helper.go` retains its own full implementation (duplicated from `dbinit`'s
`loadDatabaseConfig`). This is code duplication.

Assessment: The spec recommends but does not require consolidation in T-E27-F01-001.
The spec says "either stay (as thin wrappers) or are re-exported from dbinit" — the choice
was made to leave `db_helper.go` intact to minimize blast radius (spec's "Option A" approach,
section 4 step 9). The `GetDatabasePathForBackup` still needs `GetDatabaseConfig`, and the
`cloud.go` command uses `InitializeDatabaseFromConfig`. This is a deferred cleanup, not a
blocking defect for T-E27-F01-001.

### Finding 9: `TestInit_Turso_EnvVarAuth_FailsConnect` takes ~2.2 seconds

The test dials a fake Turso endpoint and waits for connection timeout. This slows the test
suite. It is a valid test for the auth path but imposes a 2-second latency per run.
Non-blocking observation — test isolation is fine, just slow.
