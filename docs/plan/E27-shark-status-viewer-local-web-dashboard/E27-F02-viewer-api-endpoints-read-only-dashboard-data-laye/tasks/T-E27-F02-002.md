# Task: Implement ViewerService — read-only dashboard aggregation

## Goal

Create `internal/services/viewer_service.go` — the concrete `ViewerService` that composes existing repositories and workflow services into the seven dashboard-shaped aggregates consumed by the viewer API endpoints. This service is strictly read-only (ADR-E27-003): no mutations, no transactions started.

## Requirements

### Functional Requirements

- [ ] Create `internal/services/viewer_service.go` with `ViewerService` struct and `NewViewerService` constructor
- [ ] `NewViewerService` accepts: `epicRepo EpicRepository`, `featureRepo FeatureRepository`, `taskRepo TaskRepository`, `bugRepo BugRepository`, `changeCardRepo ChangeCardRepository`, `historyRepo EntityHistoryRepository`, `workflowSvc *workflow.Service`, `statusCalc *status.CalculationService`, `projectRoot string`
- [ ] Constructor panics on nil required dependencies (matching existing service constructors)
- [ ] Implement `Summary(ctx) (*SummaryResponse, error)` — entity-type counts with per-status color/phase from workflow.Service; fallback `color="gray"`, `phase="unknown"` for unknown statuses; `tasks.blocked_count` from `blocked=1` DB flag; `bugs.severity_counts` map
- [ ] Implement `Hierarchy(ctx) (*HierarchyResponse, error)` — epics ordered by `execution_order ASC, created_at ASC`; features per epic in same order; each feature includes `task_count` and `blocked_count`; status colors from workflow config
- [ ] Implement `History(ctx, key string) (*HistoryResponse, error)` — detects entity type from key format using `internal/models/validation.go` regexes; looks up entity by key; returns `entityhistory.ListByEntity` results newest-first; returns `NotFoundError` on unknown entity
- [ ] Implement `File(ctx, key string) (*FileResponse, error)` — reads `file_path` from DB; canonicalizes with `filepath.Abs` + `filepath.EvalSymlinks`; verifies canonical path is prefix of `rootCanon + string(os.PathSeparator)`; returns `SecurityError` on escape; returns `FileResponse{Exists:false}` (no error) if file absent; returns `FileTooLargeError` for files > 2 MiB (use `io.LimitReader`); returns `FileResponse{Exists:true, Content:string, Path:relPath}` on success
- [ ] Implement `FeatureTasks(ctx, featureKey string, opts FeatureTaskOptions) (*FeatureTasksResponse, error)` — verifies feature exists; returns all tasks ordered `execution_order ASC, priority DESC, created_at ASC`; applies status/agent/blocked filters; paginates with limit/offset; each task includes `status_color` from workflow; `total` is pre-filter count
- [ ] Implement `RecentActivity(ctx, opts RecentActivityOptions) (*RecentActivityResponse, error)` — clamps Limit (0→50, >200→200); delegates to `historyRepo.ListRecentAcrossEntities`; omits entries where entity was deleted (title empty/nil from JOIN)
- [ ] Implement `WorkflowMeta(ctx) (*WorkflowMetaResponse, error)` — queries `workflow.Service` for all 5 levels (epic, feature, task, bug, change_card); includes `statuses[]` (name+color+phase+progress_weight) and `transitions[]` (from+to+direction); computes `direction` by comparing ordinal positions in the level's status list: lower→higher=forward, higher→lower=backward, same-level-path=lateral; missing levels emitted as empty objects

### Non-Functional Requirements

- [ ] No mutation methods on `ViewerService` — confirmed by code review
- [ ] `status_color` and `phase` values come exclusively from `workflow.Service` — no hardcoded constants
- [ ] File path containment check uses `filepath.EvalSymlinks` to defeat symlink escapes (ADR-E27-008)
- [ ] File reads use `io.LimitReader` with a 2 MiB + 1 byte limit to detect oversized files without reading them fully

## Implementation Plan

### Steps

1. [ ] Define `SecurityError`, `FileTooLargeError` error types in `viewer_service.go` (or `viewer_errors.go`)
2. [ ] Define repository interfaces the service depends on (per ADR-E27-004: interface at consumer — but check if `EpicRepository`, `FeatureRepository`, `TaskRepository` interfaces in `internal/services/` already cover needed methods; add any missing methods to the existing interfaces rather than creating new ones)
3. [ ] Implement `NewViewerService` constructor with nil-guard panics
4. [ ] Implement `Summary` — call `CountByStatus` on each repo; enrich with workflow color/phase
5. [ ] Implement `Hierarchy` — `ListAll` epics, for each epic `ListByEpicID` features, for each feature call task count/blocked-count methods
6. [ ] Implement `History` — write `detectEntityType(key string) (models.EntityType, error)` helper using validation regexes
7. [ ] Implement `File` — write `containsPath(root, target string) bool` helper using canonicalization
8. [ ] Implement `FeatureTasks` — in-process sort + filter (or push filters to repo if repo supports it)
9. [ ] Implement `RecentActivity` — clamp + delegate
10. [ ] Implement `WorkflowMeta` — iterate levels, compute direction ordinals

### Technical Approach

- Response types (`SummaryResponse`, `HierarchyResponse`, etc.) are declared in `internal/api/viewer/types.go` (T-E27-F02-003). During this task, use temporary local type stubs or declare types in `viewer_service.go` and move them to `types.go` during T-E27-F02-003. Coordinate with the developer working on T-E27-F02-003 if parallel.
- `FeatureTaskOptions.Limit` clamping: 0 or negative → use 200; >500 → use 500. Apply at start of `FeatureTasks`.
- The `direction` computation for workflow transitions: build a `statusOrdinal map[string]int` from the level's ordered status list. For each transition `(from, to)`: if `ordinal[to] > ordinal[from]` → "forward"; if `ordinal[to] < ordinal[from]` → "backward"; else → "lateral".
