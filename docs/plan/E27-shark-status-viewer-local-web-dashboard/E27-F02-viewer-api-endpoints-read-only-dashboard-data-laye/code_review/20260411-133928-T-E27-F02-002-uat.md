1. The task spec acceptance criteria reference test-plan.md §4, where TC-S-020 through TC-S-023 are the service-level History tests. None of these test Bug/CC keys.

3. T-E27-F02-005 task spec line 54 explicitly says "write History tests — verify entity type detection by key format (epic/feature/task/bug/change_card keys all tested)", indicating Bug/CC History support is intended to be validated — and therefore completed — at that task boundary.

This is a known architectural gap that surfaces fully in T-E27-F02-005. It does not block T-E27-F02-002 since all specified AC test cases pass. **Flagged for T-E27-F02-005 team awareness.**

## 3. Red-Team Findings

### RT-01: History() cannot serve Bug or ChangeCard keys (non-blocking for this task)

**Severity:** Observation — not a blocker for T-E27-F02-002.

`detectEntityType` (lines 570–585) correctly identifies `B001` as `models.EntityTypeBug` and `CC-001` as `models.EntityTypeChange`. However, `resolveEntityID` (lines 588–620) has no case for `EntityTypeBug` or `EntityTypeChange`, falling to `default` which returns an error. `ViewerBugRepository` and `ViewerChangeCardRepository` expose no `GetByKey` method.

Consequence: `History("B001")` and `History("CC-001")` return errors. At the HTTP handler level (T-E27-F02-003/004), TC-H-023 and TC-H-024 will fail unless this is resolved. T-E27-F02-005 plans to test these cases, so the gap will surface there.

**Recommendation:** When implementing T-E27-F02-005 handler tests, this service gap must be patched first. The fix is: add `GetByKey` to `ViewerBugRepository` and `ViewerChangeCardRepository`, implement the corresponding `case` branches in `resolveEntityID`.

### RT-02: TC-S-020 test description discrepancy (non-blocking)

The test plan describes TC-S-020 as "EpicRepo.GetByKey returns epic" but `ViewerEpicRepository` has no `GetByKey` — only `List`. The implementation uses `epicRepo.List(ctx, nil)` + linear scan. The actual test `TestViewerService_History_Task` only tests a task key, not an epic key. There is no service-level test exercising `History` with an epic key.

This is a test plan documentation inaccuracy and a minor test coverage gap (epic key resolution in History). Neither blocks task acceptance since TC-S-020's spirit (epic key returns correct history) is met by the implementation, and the code path IS exercised for tasks.

### RT-03: `_ = taskSvc` placeholder (non-blocking, known)

Line 508: `_ = taskSvc` suppresses an unused-variable warning for a variable held for potential future enrichment. Acknowledged in code review cycle 2. Not a correctness issue.

### RT-04: Panic message grammatical redundancy (non-blocking, known)

Line 289: `"ViewerService requires a non-nil WorkflowService must not be nil"`. Acknowledged in both code review cycles. No functional impact.

## 4. Security Assessment

**Path traversal protection: SOUND.**

The dual-EvalSymlinks approach (root + target canonicalization before prefix comparison) correctly defends against:
- Simple `../` path traversal in stored `file_path` values
- Symlink escape attacks (symlinks inside root pointing outside)
- Case-normalization tricks on case-insensitive filesystems (EvalSymlinks resolves these)

The `rootCanon + string(os.PathSeparator)` suffix in the prefix check prevents the false-match class where a sibling directory name starts with the project root's name.

**No injection vulnerabilities found.** All repository interactions are via Go interface calls (parameterized queries enforced at the repository layer). No string interpolation into queries in this service.

**No data leaks found.** The service is read-only and returns only what the repositories provide. No sensitive fields (auth tokens, passwords, internal IDs as primary references) are present in the response types.
