## File-by-File Findings

### `service.go`
Clean. `ViewerServicer` interface defines all 7 methods with correct signatures. The compile-time interface check `var _ ViewerServicer = (*services.ViewerService)(nil)` is a strong pattern that catches drift early.

### `types.go`
The file contains only a comment explaining that DTOs live in the `services` package. The task spec originally described this file as owning all DTO declarations, but the developer made a pragmatic architectural decision: since `ViewerService` in `internal/services/` already defines and constructs all response types, duplicating them here as type aliases would create two parallel sources of truth and increase maintenance burden. This is a reasonable deviation from the spec's prescribed phase-A approach. The handler imports `services.*Response` types directly, which is clean and avoids import cycles.

**Observation (non-blocking):** The spec §4.1 table lists `internal/api/viewer/` as owning "request/response DTOs." The current design places them in `internal/services/`. This is architecturally sound but should be noted in the feature retrospective so the spec can be updated to reflect the actual decision.

### `cors.go`
Correct and complete. Covers all 6 behavioral cases from the task spec:
- No `Origin` header → calls next
- Local origin → echoes `Origin` + `Vary: Origin`
- Local origin + OPTIONS → 204 preflight + returns without calling next
- Non-local origin → calls next without CORS headers
- URL parse error → treated as non-local (safe default)

### `handler.go`
Generally clean. Three observations:

**Observation 1 (non-blocking): Confusing parse-then-validate ordering in `FeatureTasks`**

In `FeatureTasks`, `parseIntClamp` is called before the non-integer validation:

```go
limit := parseIntClamp(q.Get("limit"), 200, 1, 500)   // line 177: returns default on bad input
offset := parseIntClamp(q.Get("offset"), 0, 0, maxOffset)

if q.Get("limit") != "" {                              // line 181: validates AFTER clamp
    if _, err := strconv.Atoi(q.Get("limit")); err != nil {
        respondError(w, http.StatusBadRequest, `"limit" must be an integer`)
        return
    }
}
```

The behavior is correct — the 400 is returned and the pre-computed `limit` value is discarded. But the reversed order is confusing. A cleaner approach would validate first, then clamp. Not a functional bug.

**Observation 2 (non-blocking): `isNotFound` uses string matching**

```go
func isNotFound(err error) bool {
    return strings.Contains(strings.ToLower(err.Error()), "not found")
}
```

This is consistent with `api.handleServiceError` in `internal/api/common.go` (same string-based convention). It works given the existing codebase convention but is fragile against error message changes. This is a pre-existing pattern issue, not introduced by this task.

**Observation 3 (non-blocking): `respondError` does not pass variadic `details`**

The viewer's local `respondError` wraps `api.ErrorResponse` directly but never populates `Details []string`. The existing `api.respondError` in `internal/api/common.go` supports a variadic details parameter. The viewer version is intentionally simplified (no multi-detail error cases in the viewer API). This is acceptable for the current use cases.
