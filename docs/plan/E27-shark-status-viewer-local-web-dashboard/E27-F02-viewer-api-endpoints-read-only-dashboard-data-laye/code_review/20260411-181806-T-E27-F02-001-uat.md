## 3. Red-Team Findings

### FINDING-001 — CRITICAL BLOCKER: Interface Contract Mismatch

The `ViewerEntityHistoryRepository` interface defined in `internal/services/viewer_service.go` (line 84) declares:

```go
ListRecentAcrossEntities(ctx context.Context, opts RecentActivityOptions) ([]*models.EntityHistory, error)
```

The concrete `EntityHistoryRepository.ListRecentAcrossEntities` implemented in this task has:

```go
ListRecentAcrossEntities(ctx context.Context, opts ListRecentAcrossEntitiesOptions) ([]*RecentActivityRow, error)
```

Both the parameter type (`RecentActivityOptions` vs `ListRecentAcrossEntitiesOptions`) and the return type (`[]*models.EntityHistory` vs `[]*RecentActivityRow`) differ. The concrete implementation **does not satisfy** the consumer interface.

**Compile-time proof** (interface satisfaction check added to `internal/services/` package, then removed):

```
go vet ./internal/services/...
internal/services/interface_check_test.go:8:39: cannot use
(*entityhistory.EntityHistoryRepository)(nil) as ViewerEntityHistoryRepository value:
*entityhistory.EntityHistoryRepository does not implement ViewerEntityHistoryRepository
(wrong type for method ListRecentAcrossEntities)
    have ListRecentAcrossEntities(context.Context,
         entityhistory.ListRecentAcrossEntitiesOptions) ([]*entityhistory.RecentActivityRow, error)
    want ListRecentAcrossEntities(context.Context,
         RecentActivityOptions) ([]*models.EntityHistory, error)
```

**Impact:** When T-E27-F02-002 (ViewerService implementation) attempts to pass a real `EntityHistoryRepository` as the `ViewerEntityHistoryRepository` dependency, the program will not compile. The entire E27-F02 feature pipeline is blocked at the wiring step.

**Why this was missed by prior reviewers:** The prior code review and QA both noted "no call site exists yet (that is T-E27-F02-002's job)" and did not perform a cross-package interface compatibility check. The build passes today only because `ViewerService` is never instantiated with a real `EntityHistoryRepository` — all tests use function-field mocks that declare their own compatible signatures.

**Classification:** AC Violation. The task spec (§Technical Approach) explicitly required the method to be "callable without further modification to this file" by the ViewerService. The interface mismatch means that is false.

**Required fix:**

Option A (preferred — align the repository to the interface): Change the repository method signature and types to match what `ViewerEntityHistoryRepository` expects:
- Change parameter to `RecentActivityOptions` (from `viewer_service.go`)
- Change return to `[]*models.EntityHistory`
- Update tests accordingly

Option B (acceptable — align the interface to the repository): Update `ViewerEntityHistoryRepository` in `viewer_service.go` to match the concrete implementation:
- Change parameter to `entityhistory.ListRecentAcrossEntitiesOptions`
- Change return to `[]*entityhistory.RecentActivityRow`
- Update `RecentActivity` method in ViewerService to adapt the types

Option C (adapter pattern): Add an adapter struct in `cmd/server/services.go` that wraps `EntityHistoryRepository` and converts between the two type systems. This adds indirection but avoids changing either existing signature.

The choice between options is an architectural decision for the developer, but one of them must be resolved before T-E27-F02-002 can proceed.

### FINDING-002 — Non-blocking observation: RecentActivityOptions missing EntityType and Since fields

The `RecentActivityOptions` struct in `viewer_service.go` (lines 186–189) contains only `Limit` and `Offset`. It is missing the `EntityType` and `Since` filter fields that `ListRecentAcrossEntitiesOptions` provides. The test plan (TC-H-051, TC-H-052) and spec (REQ-F-006) require `entity_type` and `since` query parameter filtering at the API layer.

This is a spec gap in `viewer_service.go` that will also need to be resolved as part of whichever fix option is chosen for FINDING-001. It does not block this specific task (T-E27-F02-001) independently, but it reinforces that the consumer interface was defined before it was complete.

## 5. Verdict

**REJECTED.**

The repository implementation itself is correct and well-tested in isolation. All 7 acceptance test cases pass. However, the method contract delivered (`ListRecentAcrossEntitiesOptions` → `[]*RecentActivityRow`) does not match the consumer interface that the downstream task (T-E27-F02-002) must satisfy (`RecentActivityOptions` → `[]*models.EntityHistory`). Wiring the concrete repository to `ViewerService` will produce a compile error.

This task must return to `ready_for_development` for one of the three fix options to be applied. The developer should also add a compile-time interface satisfaction assertion (e.g., `var _ services.ViewerEntityHistoryRepository = (*EntityHistoryRepository)(nil)`) to the repository package to prevent this class of regression in future.
