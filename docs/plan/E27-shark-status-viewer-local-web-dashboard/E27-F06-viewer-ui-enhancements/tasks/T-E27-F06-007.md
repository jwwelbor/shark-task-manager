# Task: Unify task dependency source in ViewerService — use task_relationships exclusively

## Goal

In `ViewerService.Hierarchy()`, `ViewerTask.DependsOn` is currently populated from the legacy `tasks.depends_on` JSON blob field via `parseDependsOnJSON(t.DependsOn)`. `ViewerTask.BlockedBy` and `ViewerTask.Blocks` are populated from the normalized `task_relationships` table. These two sources can diverge, causing inconsistent dependency data in the viewer's task overview pane.

Replace the `parseDependsOnJSON` call with a lookup into the already-loaded `task_relationships` data (keyed by task ID and relationship type), so all three dependency fields (`DependsOn`, `BlockedBy`, `Blocks`) draw from the single authoritative source.

## Where

- `internal/services/viewer_service.go` — `Hierarchy()` method, the `ViewerTask` construction loop (~line 840)
- `parseDependsOnJSON` helper (same file) — can be removed once unused
- The `blockedByKeys` / `blocksKeys` maps are already built from `task_relationships`; derive `dependsOnKeys` the same way using the appropriate `relationship_type` value

## Why It Matters

Flagged in PR #58 code review (Gemini comment id 3080877099). If a task's `depends_on` JSON and its `task_relationships` rows are out of sync, the Overview tab shows stale/incorrect dependency data. Using `task_relationships` as the single source eliminates this class of inconsistency.

## Notes

- `tasks.depends_on` can remain on the `models.Task` struct for backward compatibility with CLI and other non-viewer callers — this change is scoped to `ViewerService` only.
- Verify the correct `relationship_type` string value used for "depends on" links in `task_relationships`.
