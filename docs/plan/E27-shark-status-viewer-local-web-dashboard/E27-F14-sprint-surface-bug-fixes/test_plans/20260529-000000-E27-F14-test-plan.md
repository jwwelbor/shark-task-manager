## Acceptance Criteria Review

### Ambiguity Findings

- **AC-013** lists `in_development`, `ready_for_approval`, `ready_for_development` as the three named statuses, then adds "(and other active states)" — REQ-F-005 in the spec is the definitive list: `in_development, ready_for_approval, ready_for_development, in_progress, in_review, in_qa, ready_for_refinement_tech, ready_for_refinement_ba, in_refinement`. AC-013 should be read as "all statuses enumerated in REQ-F-005". The test plan uses the full REQ-F-005 list as the authoritative set.
- **AC-019** ("Blocked items in Capacity panel are clickable and open the detail drawer") specifies interactive behavior not described in feature.md. The spec explicitly includes it in REQ-F-007 so it is in scope. However, "open the detail drawer" is the existing viewer behaviour already tested in E27-F13 TC-006 — this AC verifies that the new panel wires through to the existing drawer without regression.
- **AC-022** ("Plan tab passes readability check in dark theme") is deliberately subjective — it is a UX review gate coordinated with the UX designer agent (per spec §1.3). Test case TC-022 treats this as a structured review checklist rather than a binary automated assertion.

### Missing Coverage

None. Every spec requirement has at least one dedicated test case.

## Acceptance Test Cases

### TC-001 — SprintReport returns 200 for a planning sprint

**Feature Requirement:** REQ-F-001 / AC-001  
**Technique Applied:** State Transition (planning is a non-terminal sprint state distinct from completed/archived)  
**ISO 25010:** Functional Suitability, Reliability

**Caller-Path Contract:**
- **Entrypoint:** `s.SprintReport(ctx, "S-planning-fixture")` — `ViewerService` with a wired `mockViewerSprintAnalyticsService`
- **Lowest allowed mock seam:** `mockViewerSprintAnalyticsService.GetSummaryFunc` (existing mock pattern in `viewer_service_test.go`)
- **Forbidden mocks:** do not mock `SprintReport` itself; call the real method so the error-handling change at line ~817 is exercised
- **Counter-factual:** pre-fix, the old `return nil, fmt.Errorf(...)` propagates the error → `err != nil` in the test → assertion fails

**Preconditions:**
- A `ViewerService` with a wired `mockViewerSprintAnalyticsService` where:
  - `GetBurndown` returns a valid `*BurndownResult`
  - `GetVelocity` returns a valid `*VelocityResult`
  - `GetSummary` returns `(nil, fmt.Errorf("sprint summary is available for completed or archived sprints only"))`
- A mock sprint repository containing a sprint in `planning` status with key `"S024"`

**Input:**
- `key = "S024"` (planning sprint)

**Expected Output:**
- `err == nil`
- `response != nil`
- `response.Sprint.Key == "S024"`
- `response.Burndown != nil`
- `response.Velocity != nil`

**Observability Evidence:**
- Existing viewer HTTP handler request log emits `status=200` — verified by manual curl test

**Edge Cases:**
- `GetSummary` returns a different error message format: same behavior expected (any non-nil error → `summary = nil`)
- Sprint key not found: `err != nil` from `resolveSprint`, not from the summary path — the fix does not change this behavior

**Negative Cases:**
- `GetBurndown` returning an error must still propagate (the fix is only for `GetSummary`)
- `GetVelocity` returning an error must still propagate

### TC-006 — Sprint date range renders as "May 8 → May 22" (no time component, same year)

**Feature Requirement:** REQ-F-003 / AC-009  
**Technique Applied:** Boundary Value Analysis (ISO timestamp boundary: `T` separator discards everything at and after it; midnight UTC is the critical value)  
**ISO 25010:** Functional Suitability, Usability

**Caller-Path Contract:**
- **Entrypoint:** `formatDateOnly(isoString)` in `viewer.html`
- **Lowest allowed mock seam:** internal — pure JS function
- **Forbidden mocks:** n/a

**Preconditions:** None
