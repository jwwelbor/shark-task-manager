## Red-Team Findings

### Finding 1: `label2` variable name (shadow of outer loop variable)

**Non-blocking.** Line 1611: `const label2 = escapeHtml(status.replace(/_/g, ' ')) + ' ' + count;` — the name `label2` shadows the outer destructured `label` from `for (const [label, statusCounts] of entityTypes)`. This is cosmetically poor but not a bug because the outer `label` is still in scope and correctly used at line 1617 (`${escapeHtml(label)}`). The shadow does not cause incorrect output. The code review noted this non-blocker.

### Finding 2: No XSS vector from count interpolation

**Not a defect.** Line 1611 appends ` + count` (a number from `Object.entries`) directly without `escapeHtml`. This is safe: `count` comes from `statusCounts` which is an API-returned JSON integer. Integer values have no injection surface. If the API returns a string unexpectedly, the worst outcome is unescaped text in the badge label — which would be a data integrity issue, not an execution vector, because the value is inside an element text node (not `innerHTML`), and because the badge already wraps in a `<span>` where only the `style` attribute is interpolated (and `style` receives `escapeHtml(color)`, not `count`). Not a security issue under the application's threat model (localhost-only, read-only).

### Finding 3: Progress bar `width:${pct}%` with no escaping on `pct`

**Not a defect.** `pct` is produced by `Math.round(...)` — always a safe integer (0–100). No injection possible from a numeric value embedded in a CSS width property. Correct as-is.

### Finding 4: No QA report for T-E27-F03-004

**Observation.** The code review was filed but no QA report exists for this task. The Go smoke tests serve as the automated quality gate, and the code review verified all ACs. However, no exploratory QA was run. For a frontend rendering task, this means there is no human visual verification of the card layout, badge colors, or progress bar widths against the reference screenshots. This is a process gap but not a code defect. The acceptance criteria that can be verified programmatically have all been verified. Visual fidelity is a risk that would require manual browser testing.

### Finding 5: `epics` nesting in `treeData` — one level deep assumption

**Acceptable.** `renderFeatureProgress()` iterates `for (const epic of treeData)` and accesses `epic.features`. This assumes a flat list of epics with `features` arrays. This matches the `apiGetHierarchy` API contract (verified in prior tasks T-E27-F03-002/003). If the hierarchy API changes its shape, this code would silently render no rows. However, this is an API contract that was established upstream and is consistent with prior tasks.
