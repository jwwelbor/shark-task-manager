## Implementation Quality

### Correctness

**Epic expand seeding**: `expandedEpics = new Set(treeData.map(epic => epic.key).filter(Boolean))` is assigned once in `loadAllData()` (line 1464), not inside `renderSidebar()`, so refresh correctly preserves user-expanded/collapsed state. Satisfies the "preserve on refresh" requirement.

**Expand/collapse without select**: Arrow clicks are intercepted first via `closest('[data-arrow-key]')` before the `data-select-key` handler, so clicking an arrow does not trigger node selection. This is the correct approach.

**Selected state CSS**: `rgba(0,0,0,0.35)` background + `3px solid var(--accent)` left border + `color: var(--fg)` on title — matches spec §2.6.5 exactly.

**Status dot**: 9px filled circle using `getStatusColor(status)` — matches spec §2.6.3 ("8–10px filled circle").

**Indentation values** match spec §2.6.2 table precisely:
- Epic: 16px (bold)
- Feature: 40px
- Task: 56px
- Flat section node: 18px
- Doc at epic level: 16px (italic, muted)
- Doc at feature level: 40px (italic, muted)

Selected nodes compensate 3px padding (e.g., epic selected = 13px) to keep visual alignment consistent.

**`scrollSidebarToKey`**: Uses `CSS.escape(key)` for the selector, correctly handling special characters in entity keys. `scrollIntoView({block: 'nearest'})` is correct.

**Event delegation**: Single `onclick` handler on `#sidebar-content` replaced on each `renderSidebar()` call. This avoids accumulating listeners and is correct for innerHTML-based rendering.

### Security

- `escapeHtml()` applied to all user-controlled values inserted into HTML (key, title, status, nodeClass, section titles). No XSS vectors found.
- `nodeClass` is an internal constant string (always one of `tree-node-epic`, `tree-node-feature`, etc.), not from external data, so escaping it is defensive but harmless.
- `CSS.escape()` is used correctly in `scrollSidebarToKey` to prevent CSS injection via entity keys.

### Code Standards

- Section labeled `// === SIDEBAR ===` inside a `// ============================================================` banner — matches project conventions.
- All functions are documented with JSDoc comments.
- Node builders return HTML strings and are purely functional (no side effects), making them easy to test and reason about.
- `buildNodeHtml` extracts shared node rendering logic cleanly, satisfying DRY.

### Minor Observations (non-blocking)

1. **Dead-code block in `renderSidebar()`**: The conditional `if (treeData.length === 0 && !summaryData) { // No data loaded yet — render nothing extra }` is an empty branch that does nothing. It can be removed without any behavioral change. This is cosmetic — it does not affect correctness.

2. **`nodeClass` escaping**: `escapeHtml(nodeClass)` is called on an internally controlled constant string. Harmless but unnecessary. No functional impact.

3. **`buildDocNodeHtml` selected state**: Doc nodes use `data-select-key` and participate in click-to-select, but do not apply the `selected` CSS class. The `buildDocNodeHtml` function uses a manual HTML template (not `buildNodeHtml`), so it doesn't get the `isSelected` check. This means doc nodes will not visually highlight when selected. This is a minor gap — the spec doesn't explicitly require doc nodes to show selected state (they are linked to `doc_view` state, not `entity_view`). Since the spec says "clicking the node body selects the node" for entities, and doc nodes navigate to doc_view rather than entity_view, the behavior of not showing doc nodes as "selected" may be intentional. This is an observation for future tasks, not a blocking issue.
