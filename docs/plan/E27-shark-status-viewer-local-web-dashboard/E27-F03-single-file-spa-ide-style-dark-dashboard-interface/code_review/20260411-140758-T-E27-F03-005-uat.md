## 3. Independent AC Verification

### AC1 — Active Transitions shows up to 25 rows from `recentActivity`, newest first (TC-VIS-06)

**VERIFIED.** Line 1682: `const rows = recentActivity.slice(0, 25);`
Array is pre-sorted by API (documented in comment). Slice correctly caps at 25.

### AC2 — From/to status badges use correct hex colors from `getStatusColor()` (TC-VIS-06)

**VERIFIED.** Lines 1695–1703:
```js
const fromColor = escapeHtml(getStatusColor(fromStatus));
const toColor   = escapeHtml(getStatusColor(toStatus));
```
`getStatusColor()` at line 1153 returns `STATUS_COLORS[status] || '#666666'` — unknown statuses fall back to neutral gray, never crashes.

**Red-team check — CSS injection via style attribute:** `fromColor` and `toColor` are `escapeHtml()`'d before insertion into `style="background:${fromColor}"`. The `escapeHtml` function escapes `&`, `<`, `>`, `"`, `'`. A hex color value (`#rrggbb`) contains none of these, making XSS in this attribute practically impossible even without escaping — but the escaping is present and correct regardless. No issue.

### AC3 — Clicking a key in Active Transitions calls `navigateToEntity()` (TC-NAV-03)

**VERIFIED.** Line 1693 renders `data-navigate-key="${escapeHtml(key)}"` on the key span. Line 1716 does the same on the Open button. `renderDashboard()` at lines 1850–1855 wires a delegated click handler: `content.querySelectorAll('[data-navigate-key]').forEach(el => { ... navigateToEntity(key); })`. Both the Active Transitions key span and the Open button are covered by this single delegated handler — correct.

### AC4 — Stale Entities excludes all terminal statuses (TC-STALE-02)

**VERIFIED.** Lines 1163–1168: TERMINAL Set contains exactly the 9 statuses named in the AC:
`'done', 'cancelled', 'closed', 'wont_fix', 'verified', 'rejected', 'promoted', 'approved', 'completed'`

**Red-team check — case sensitivity:** `isTerminalStatus(task.status || '')` — if `task.status` is `'Completed'` (capital C), it would NOT match the lowercase set entry. However, shark status values are always stored and served as lowercase (enforced by the workflow config and repository layer). Status values in API responses are lowercase. This is consistent behavior across the whole dashboard. Not a defect.

### AC5 — Stale Entities only includes entities with `updated_at` more than 7 days ago (TC-STALE-01)

**VERIFIED.** Threshold at lines 1746, 1761, 1776: `if (days > 7)` — strict greater-than correctly excludes entities updated exactly 7 days ago.

`daysSince()` at line 1200: `Math.floor(ms / (1000 * 60 * 60 * 24))` — uses floor, so an entity updated 7 days and 23 hours ago returns 7, which does NOT pass `> 7`. Entities must be at least 8 full days since update to appear. The spec says "> 7 days ago" which aligns with this behavior.

**Red-team check — timezone handling:** `new Date(isoString)` and `new Date()` both operate in the local JS environment. If the browser and server are in different timezones, `daysSince` could produce off-by-one at midnight boundaries. This is an inherent limitation of client-side day calculation and acceptable — the spec does not require UTC-normalized calculation.

### AC6 — Stale Entities sorted oldest-first (highest daysSince at top) (TC-STALE-03)

**VERIFIED.** Line 1795: `stale.sort((a, b) => b.days - a.days);`
`b.days - a.days` is positive when `b > a`, meaning higher-days items sort earlier — oldest-first. Correct.

### AC7 — "N days ago" text reflects correct days count from `daysSince()` (TC-STALE-03)

**VERIFIED.** Line 1803: `const daysText = escapeHtml(item.days + ' days ago');`
`item.days` is set at collection time from `daysSince(entity.updated_at)`. The `+` operator with a number and string produces the correct numeric prefix (e.g., `"14 days ago"`). `escapeHtml` on this value is safe/redundant but not harmful.

### AC8 — Empty states render without errors when no data present

**VERIFIED.**
- Active Transitions: line 1677: `if (!recentActivity || recentActivity.length === 0)` — guards null, undefined, and empty array.
- Stale Entities: line 1790: `if (stale.length === 0)` — checked after the walk loop, which itself guards `(treeData || [])` on line 1743. If `treeData` is null/undefined the loop body never executes and `stale` remains empty. Empty-state path renders without iterating.

### AC9 — Both sections wired into `renderDashboard()` replacing stubs

**VERIFIED.** Lines 1838–1843 in `renderDashboard()`:
```js
${renderActiveTransitions()}
${renderStaleEntities()}
```
Neither function contains stub text. Both are full implementations. `renderDashboard()` inserts both sections into the DOM and then wires the unified click handler. Correct.

## 4. Additional Red-Team Findings

### Finding 1 (Non-blocking): `recentActivity` capacity request vs. slice cap

`apiGetRecentActivity(25)` is called at load time (line 1469), requesting 25 records from the API. `recentActivity.slice(0, 25)` caps at 25 at render time. These are consistent. However, if the API returns fewer than 25, `slice(0, 25)` gracefully returns what is available — no issue.

### Finding 2 (Non-blocking): Feature walk missing `null` guard on epic-level iteration

Line 1757: `const features = Array.isArray(epic?.features) ? epic.features : [];`
This correctly guards for missing `features` array. All three levels (epic, feature, task) have comparable guards. No missing guard found.

### Finding 3 (Non-blocking): `toBadge` always rendered even if `toStatus` is empty

Line 1703: `toBadge` is always created, even if `toStatus` is `''`. This would render an empty badge with a gray background. In practice, `to_status` is always populated (a status transition must have a destination status). This is defensively fine — an empty badge is visually inert. The `from_status` empty case is correctly handled with the conditional `fromBadge` check.

### Finding 4 (Non-blocking): `Open` button uses `data-navigate-key` but is inside a `<td>` that may intercept row click

The Open button has its own `data-navigate-key`, so the delegated handler fires correctly. The button click reaches the delegated `querySelectorAll('[data-navigate-key]')` handler. No double-fire issue because the outer `<td>` contains the `keyHtml` span (not the button), and the button itself carries the `data-navigate-key` attribute. Correct wiring.
