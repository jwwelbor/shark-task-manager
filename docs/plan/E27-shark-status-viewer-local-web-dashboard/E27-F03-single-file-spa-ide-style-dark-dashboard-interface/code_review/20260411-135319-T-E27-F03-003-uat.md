## Red-Team Findings

### Finding 1: "Hierarchy" string vs "HIERARCHY" label (Non-blocking)

The task spec says "sticky uppercase `HIERARCHY` label." The HTML emits:
`<div class="sidebar-section-header">Hierarchy</div>` (title case).

However, `.sidebar-section-header` has `text-transform: uppercase` (line 225), so the
rendered output IS visually "HIERARCHY." This is the same mechanism used for all flat
section headers. The spec intent is satisfied through CSS, not literal uppercase in the
HTML string. Not a defect.

### Finding 2: Arrow click on collapsed epic with features navigates correctly (Non-blocking, Confirmed)

When the `▶` arrow is on a `.tree-node-epic`, the expand handler correctly checks
`parentNode.classList.contains('tree-node-epic')` and routes to `expandedEpics`.
For all other node types (features), it falls to the `else` branch and routes to
`expandedFeatures`. There is no classification for doc or flat section arrows — but those
nodes do not render arrows (they use `tree-arrow-spacer`), so the else-branch would never
fire for them. Logic is sound.

### Finding 3: `data-key` vs `data-select-key` duplication on nodes (Non-blocking)

`buildNodeHtml` outputs both `data-key="${key}"` and `data-select-key="${key}"` on the
same element. `data-key` is used by `scrollSidebarToKey`. `data-select-key` is used by
click handler. Both are set to the same value. This is redundant but harmless, and the
separation of concerns is valid (scroll uses `data-key`, click delegation uses
`data-select-key`).

### Finding 4: Doc node selected state not highlighted (Non-blocking, Previously noted)

`buildDocNodeHtml` uses a manual template without `isSelected` check (unlike `buildNodeHtml`).
Doc nodes have `data-select-key` and will trigger navigation on click, setting `selectedKey`,
but will not visually show the selected CSS class. The spec does not explicitly require doc
nodes to show selected state, and docs navigate to `doc_view` rather than `entity_view`.
Not a blocking issue for this task. Noted for future improvement.

### Finding 5: No null guard on `treeData` iteration in `renderSidebar()` (Non-blocking)

`renderSidebar()` does `for (const epic of treeData)` where `treeData` is initialized as
`[]` at module scope. If `treeData` were `null` this would throw, but the init value is
a safe empty array and `loadAllData()` always assigns an array. Not a practical risk.

### Finding 6: XSS verification — CLEAN

All user-controlled values passed to HTML (`key`, `title`, `status`, `color`) go through
`escapeHtml()`. `CSS.escape()` used for CSS selector in `scrollSidebarToKey`. No injection
vectors found.
