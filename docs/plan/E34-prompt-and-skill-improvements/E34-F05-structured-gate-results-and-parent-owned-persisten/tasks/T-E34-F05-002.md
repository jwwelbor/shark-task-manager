# Task: Durable GateResult transport, replay, and filesystem safety

## Goal

T-E34-F05-001 (original feature-spanning task) split on 2026-08-31 after
delivering only REQ-F-001 (GateResult model/parser) and REQ-F-004 (semantic
outcome-role validation) — see `internal/gateresult/{gateresult,role}.go`.
This task owns the remaining REQ-F-003 scope: the durable sidecar transport
(`result.json` / `operation-state.json`) under `.shark/runs/<run-id>/`, replay
identity, crash-window recovery, and the filesystem-safety guarantees of
REQ-NF-001. It is the foundation the persistence coordinator (T-E34-F05-003)
and the core/Rider ingestion parity task (T-E34-F05-004) both build on.

Research finding (unchanged from the original task): Shark Rider can lose a
worker terminal response even after the worker writes its artifact, leaving
the parent without reliable completion evidence. This task delivers the
atomic sidecar protocol that makes a lost notification recoverable — see
`lease-session-agent-issues.md` for the full failure-mode catalog (lost final
notification, heartbeat timeout, duplicate terminal result, worker artifact
without retirement, parent restart, provider asymmetry).

## Requirements

### Functional Requirements (REQ-F-003 — Replay safety, feature.md §REQ-F-003)

- [ ] Bind persistence to a stable `run_id`, entity, source status, and
      operation digest. Associate each renewable parent session as provenance
      without making it the replay identity (`lease-session-agent-issues.md`
      issue #2: Shark session identity and provider worker identity differ).
- [ ] Under a per-run lock, create `result.json` once (immutable, no-replace)
      and atomically replace only `operation-state.json` under the existing
      `.shark/runs/<run-id>/` directory. Identical result bytes are idempotent
      success; a different result is rejected without replacing accepted
      bytes.
- [ ] Compute the operation digest as SHA-256 over canonical JSON containing
      the stable bound identity (entity key, entity type, source status, gate)
      and the validated envelope; object keys lexicographically sorted, arrays
      in contract order.
- [ ] Give every target write a deterministic suboperation ID derived from the
      run operation digest, operation kind, and stable item identity (finding
      fingerprint, sweep `class_key`, impact source kind/key, kickback entity
      key, or the singleton gate-summary key). Store it in note metadata or
      bounded entity-history reason metadata (T-E34-F05-003 is the consumer of
      this ID scheme when it writes targets; this task defines and exposes the
      ID-derivation function and the durable record it is stored in).
- [ ] Distinguish `persistence_complete` from `transition_applied` in
      `operation-state.json`. On resume, a durable `transition_applied` state
      plus the expected live target returns success; `persistence_complete`
      resumes the guarded transition; a partial persistence state resumes its
      next operation.
- [ ] Reject a non-identical replay under the same persistence identity (a
      different digest for the same stable identity is a conflict, not an
      overwrite).
- [ ] On resume, reconcile the sidecar from durable target records (note
      metadata and entity history — written by T-E34-F05-003) before applying
      missing operations, closing the target-commit/sidecar-update crash
      window. This task owns the reconciliation *read* path against
      T-E34-F05-003's target records; the two tasks share the suboperation ID
      contract and must land against the same ID-derivation function.
- [ ] Add `shark run <entity-key> --resume-run=<run_id>
      --session=<authorized-session-id>`. It acquires the run lock and
      validates the recorded entity, source status, route, and digest before
      resuming. It accepts no new result bytes.
- [ ] Expose worker phase, nested operation, elapsed time, retirement state,
      and result location for operator/parent polling independent of chat
      notifications (`lease-session-agent-issues.md` issue #1 and #3).

### Non-Functional Requirements (REQ-NF-001 — Bounded and safe data, feature.md §REQ-NF-001)

- [ ] Reuse the Question model's bounded-text and forbidden-marker approach
      (`internal/models/question.go`) for any transport-layer text this task
      persists (e.g., conflict/error records); the GateResult payload's own
      bounds are already enforced by `internal/gateresult` (delivered).
- [ ] Report validation/conflict errors by field and class without echoing
      rejected secrets or entire worker output.
- [ ] Use owner-only run directories (`0700`) and sidecar files (`0600`),
      reject symlink or non-regular targets (no-follow semantics), and fsync
      same-directory atomic writes (temp file + fsync file + fsync directory +
      rename). Result creation is no-replace under the per-run lock.
- [ ] Do not advance Shark workflow state without a verified terminal result
      and worker-retirement guarantee — this task supplies the retirement
      evidence and terminal-result verification primitives that
      T-E34-F05-003/004 call before transitioning.
- [ ] Keep result and progress records bounded, atomic, and safe to inspect
      after parent restart.

Note on the original task's informal "NF-002" label: feature.md defines only
one numbered non-functional requirement, REQ-NF-001. The crash-window /
suboperation-ID / replay-resume bullets the original task grouped under an
unlabeled second NF item are covered by REQ-F-003 above, not a separate
REQ-NF-002 — there is no such ID in feature.md. This task does not invent one.

## Implementation Plan

### Steps

1. [ ] Step 1: Trace the existing `.shark/runs/<run-id>` liveness convention
       (`internal/runner/liveness.go`), the existing `shark run` command
       surface (`internal/cli/commands/run.go`), and the Question handoff's
       exact-replay pattern (`internal/services/question_workflow_service.go`)
       as the closest existing parent-owned, validated, bounded-handoff
       pattern to extend.
2. [ ] Step 2: Define the `result.json` / `operation-state.json` sidecar
       schema (run_id, entity_key, entity_type, source_status, gate,
       operation digest, persistence_complete, transition_applied, completed
       suboperation IDs, worker phase/retirement state, timestamps) and the
       canonical-JSON digest function (SHA-256, sorted keys, contract-order
       arrays).
3. [ ] Step 3: Implement per-run locking, owner-only directory/file creation,
       no-follow symlink/non-regular-target rejection, same-directory atomic
       write (temp + fsync + rename) for both create-once `result.json` and
       replace-only `operation-state.json`.
4. [ ] Step 4: Implement the suboperation-ID derivation function (shared
       contract with T-E34-F05-003) and the resume/reconciliation read path
       that repairs a missing sidecar entry from durable note/history records
       without duplicating work.
5. [ ] Step 5: Add `shark run <entity-key> --resume-run=<run_id>
       --session=<session-id>`, worker-retirement/progress polling surface,
       and operator status output for phase/nested-operation/elapsed-time/
       retirement-state/result-location.
6. [ ] Step 6: Add the full crash-window, race, and filesystem-safety
       regression suite (see Testing Strategy).

### Technical Approach

- [ ] Reuse the existing `.shark/runs/<run-id>` liveness convention and make
      `run_id`, not a renewable parent session, the stable replay identity.
- [ ] Prefer an atomic sidecar result protocol over treating chat
      notifications as the source of truth (per `lease-session-agent-issues.md`).
- [ ] Keep this task's public surface (digest function, suboperation-ID
      derivation, sidecar read/write, resume CLI, retirement/progress state)
      behind injected interfaces so T-E34-F05-003 (persistence coordinator)
      and T-E34-F05-004 (core/Rider ingestion) can consume it without
      duplicating the crash-window logic.
- [ ] Coordinate with B046 (semantic outcome handling) and B052 (transcript
      attribution) where fixes overlap, per the original task's research
      finding.
- [ ] Do not add a note enum, database migration, or a second worker-control
      envelope — the outer `kind: final` envelope already exists (E38-F09,
      PR #149; see `skills/shark-attack/context/worker-control-schema.yaml`).
      This task adds only the sidecar transport around it.

## Deliverables

- [ ] New locked, create-once `result.json` and atomically replaced
      `operation-state.json` sidecars under `.shark/runs/<run-id>/`, holding
      distinct persistence/transition states; no pre-existing result sidecar
      is assumed.
- [ ] Canonical-JSON operation-digest function and deterministic
      suboperation-ID derivation function, exported for T-E34-F05-003's use.
- [ ] `shark run <entity-key> --resume-run=<run_id> --session=<session-id>`.
- [ ] Live parent/operator progress and retirement visibility (phase, nested
      operation, elapsed time, retirement state, result location).
- [ ] Regression evidence for result loss and stalled/non-retired workers.

## Acceptance Criteria

- [ ] A worker artifact remains recoverable when its final response
      notification is lost.
- [ ] A stalled or non-retired worker is distinguishable from an external
      product blocker.
- [ ] A restarted parent with a newly claimed authorized session resumes an
      exact partial result without duplicate sidecar state; a conflicting
      replay (different digest, same stable identity) is rejected.
- [ ] `persistence_complete` and `transition_applied` are each resumable
      exactly once after their respective crash windows.
- [ ] Unsafe paths (absolute, escaping, symlinked, non-regular targets),
      oversized reads, wrong modes, and concurrent writers fail without
      overwrite, partial mutation, or secret echo.
- [ ] Result creation is no-replace: an identical existing digest is
      idempotent success; a different terminal result never overwrites
      accepted bytes.

## Testing Strategy

- [ ] Service tests failure-inject every sidecar write boundary (before/after
      `result.json` create, before/after each `operation-state.json`
      replacement) and prove exact replay/conflict handling.
- [ ] Race two initial results for the same run and require immutable
      first-writer-wins conflict handling.
- [ ] Filesystem tests cover absolute/escaping run IDs and paths, symlinked
      intermediate and leaf components, directory/FIFO/socket targets,
      oversized reads, `0700`/`0600` modes, permissive or non-regular existing
      targets, exclusive temporary-file collisions, fsync/rename cleanup, and
      crash after create-once `result.json` but before operation-state
      initialization.
- [ ] Failure-inject after `persistence_complete`, after transition, and
      before release; assert the resume path completes exactly once (this
      task supplies the sidecar-state assertions; T-E34-F05-003/004 supply the
      corresponding note/transition assertions for their own writes).
- [ ] Execute focused suites and `make fmt`, `make lint`, `make test`, and
      `git diff --check`; retain results against the exact reviewed commit.
