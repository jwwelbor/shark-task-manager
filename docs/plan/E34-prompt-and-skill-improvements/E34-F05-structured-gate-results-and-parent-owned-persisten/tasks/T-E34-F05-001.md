# Task: Implement GateResult persistence, replay, and Rider parity

## Goal

Research finding: Shark Rider can lose a worker terminal response even after the worker writes its artifact, leaving the parent without reliable completion evidence or progress visibility. Recommendation: extend the structured result contract with a run identity and atomic started/heartbeat/result records, parent polling independent of chat notifications, worker retirement detection, nested-operation visibility, and one normalized final-outcome format. Related existing bugs B046 and B052 may be fixed in the same sprint.

## Requirements

### Functional Requirements

- [ ] Preserve a durable worker run identity, add locked create-once
      `result.json`, and atomically replace `operation-state.json` alongside the
      existing started/heartbeat records.
- [ ] Let the parent recover a valid result independently of a lost chat notification.
- [ ] Expose worker phase, nested operation, elapsed time, retirement state, and result location.
- [ ] Implement the single GateResult model/parser with outer outcome/evidence
      ownership and nested gate-specific findings, kickbacks, sweeps, and I-04.
- [ ] Add exact `result_contract` and `outcome_roles` workflow validation,
      canonical adoption entries, and `shark next` exposure.
- [ ] Persist gate `review`, finding `review-finding`, sweep/impact `reference`
      notes and child kickbacks in the feature-defined idempotent order.
- [ ] Provide the same authenticated ingestion/resume coordinator to the core
      runner and Rider adapter.

### Non-Functional Requirements

- [ ] Extend the existing canonical worker-control `kind: final` envelope with
      the bounded GateResult terminal payload; do not add a second envelope.
- [ ] Do not advance Shark state without a verified terminal result and worker retirement guarantee.
- [ ] Keep result and progress records bounded, atomic, and safe to inspect after parent restart.
- [ ] Preserve owner-only, no-follow, regular-file, bounded-read, fsync,
      create-once, lock, and CAS guarantees from `feature.md`.
- [ ] Use deterministic suboperation IDs and reconcile target notes/history
      before replay; no new note enum or database migration is allowed.

## Implementation Plan

### Steps

1. [ ] Step 1: Trace the host adapter, worker wrapper, nested-agent path,
       workflow loader/`shark next`, note/history services, and existing
       `shark run` liveness implementation.
2. [ ] Step 2: Add the canonical model/parser, bounds, forbidden-field rules,
       semantic outcome roles, workflow-schema migration, and shared fixtures.
3. [ ] Step 3: Add create-once result and operation-state transport, target
       persistence coordinator, suboperation reconciliation, and
       retirement-aware replay.
4. [ ] Step 4: Wire core ingestion plus Rider apply-result/resume through the
       same service; migrate gate/planning prompts selected by the canonical
       matrix.
5. [ ] Step 5: Add operator status output and the full parity, security,
       selector, role, lost-response, stall, crash-window, race, and resume
       regression matrices from `feature.md`.

### Technical Approach

- [ ] Reuse the existing `.shark/runs/<run-id>` liveness convention and make
      `run_id`, not a renewable parent session, the stable replay identity.
- [ ] Prefer an atomic sidecar result protocol over treating chat notifications as the source of truth.
- [ ] Add `shark run <entity-key> --resume-run=<run_id>
      --session=<session-id>` and bind a replacement authorized session to the
      recorded entity, source status, route, and digest before any replayed
      write.
- [ ] Add one initial Rider ingestion path through `shark run <entity-key>
      --apply-result=<result-file> --run-id=<run_id> --session=<session-id>`;
      do not retain a separate Rider parser or persistence sequence.
- [ ] Reconcile deterministic suboperation IDs from durable note metadata and
      entity history after a target commit/sidecar crash window.
- [ ] Coordinate with B046 (semantic outcome handling) and B052 (transcript attribution) where fixes overlap.

## Deliverables

- [ ] New locked create-once `result.json` and atomically replaced
      `operation-state.json` containing the GateResult terminal payload and
      distinct persistence/transition states; no pre-existing result sidecar
      is assumed.
- [ ] Live parent/operator progress and retirement visibility.
- [ ] Regression evidence for result loss and stalled workers.
- [ ] Shared GateResult model/parser and workflow selector/role migration.
- [ ] Parent coordinator for typed notes, sweeps, I-04, child kickbacks,
      transition, and target-store reconciliation.
- [ ] Core/Rider initial-ingestion and resume parity fixtures plus migrated
      canonical prompts.

## Acceptance Criteria

- [ ] A worker artifact remains recoverable when its final response notification is lost.
- [ ] A stalled or non-retired worker is distinguishable from an external product blocker.
- [ ] Parent advances only after a verified terminal result and retirement
      evidence are present; restart completes transition/release exactly once.
- [ ] Every semantic role accepts/rejects its table-defined positive and
      counterfactual fixtures, including route-owned versus child-kickback
      rework, obsolete-role rejection, and main-entity kickback rejection for
      every role.
- [ ] Every canonical matrix step resolves structured output, excluded/omitted
      steps stay legacy, and `shark next` exposes identical selectors/roles.
- [ ] Every note, sweep, impact, and child kickback is durable exactly once
      across all target-commit/sidecar and transition/release crash windows.
- [ ] Core and Rider produce identical normalized result, error class,
      persistence order, target writes, and transition for shared fixtures.
- [ ] Unsafe paths, file types, modes, bounds, result conflicts, and concurrent
      writers fail without overwrite, partial mutation, or secret echo.

## Testing Strategy

- [ ] Unit tables cover schema/bounds, duplicate aliases, all semantic roles,
      selectors, outcome-role maps, and opaque outcomes.
- [ ] Service tests failure-inject every target write and sidecar boundary,
      reconcile by stable suboperation ID, and prove exact replay/conflict.
- [ ] CLI/path tests cover authenticated apply/resume, entity/session mismatch,
      no-follow traversal, non-regular files, modes, fsync/rename cleanup,
      create-once conflict, and concurrent writers.
- [ ] Shared runtime fixtures traverse both core and Rider paths and compare
      normalized outputs, errors, writes, operation order, and transitions.
- [ ] Prompt/workflow tests enumerate the full adoption matrix, legacy
      compatibility, whole-file overrides, and `shark next` JSON exposure.
- [ ] Execute focused suites and `make fmt`, `make lint`, `make test`, and
      `git diff --check`; retain results against the exact reviewed commit.
