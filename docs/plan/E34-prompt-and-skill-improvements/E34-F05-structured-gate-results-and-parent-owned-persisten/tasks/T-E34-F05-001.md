# Task: Shared GateResult model, parser, and semantic outcome-role validation

## Goal

**Re-scoped 2026-08-31.** This task originally spanned the entire E34-F05
feature. Task review split it after a developer worker delivered only
REQ-F-001 and REQ-F-004 (commit `bd2700fa`, `internal/gateresult/`) and
correctly declined to mark the task `pass` because the remaining scope
(REQ-F-002, REQ-F-003, REQ-F-005, REQ-F-006, and the REQ-NF-001 filesystem
half not touched by the model package) was undelivered and unowned. This task
now covers exactly what was delivered: the shared `GateResult` v1 Go model,
JSON parser, and semantic outcome-role completeness validation. See Notes
below for the full split record and the new tasks that own the remaining
scope.

Research finding (context, unchanged): Shark gate prompts ask workers to
record findings and kick back tasks, but the Rider contract reserves
lifecycle mutations for the parent, and the current Rider loop and core
runner diverge on what they parse from worker output. The WWGM E04 inventory
found zero durable `review-finding` notes despite 45 recorded review
findings — an observed production-path failure this feature's full scope
(now split across five tasks) exists to fix. This task delivers the shared
contract the other tasks build on.

## Requirements

### Functional Requirements (REQ-F-001 — Shared GateResult model and parser, feature.md §REQ-F-001)

- [x] Define one Go model, JSON decoder, validation contract, and error
      taxonomy used by the core runner and mirrored exactly by Rider guidance.
- [x] Require a non-zero schema version and concise summary, and validate
      bounded collections and unique finding and kickback identities.
- [x] Reject duplicate envelopes (unknown top-level fields — catches the
      outer envelope's fields leaking into the nested payload), unknown
      versions, invalid top-level JSON shapes, and oversized content.

### Functional Requirements (REQ-F-004 — Gate completeness, feature.md §REQ-F-004)

- [x] Every structured step maps each opaque outcome key to exactly one
      semantic role (`success`, `route_rework`, `kickback_rework`, `blocked`,
      `hold`, `cancelled` — role is caller-supplied, per REQ-F-006's
      `outcome_roles`, not carried on the GateResult itself). Every kickback
      must target a different entity from the bound main entity, checked
      role-independently.
- [x] `success` and `route_rework` contain no kickbacks; `kickback_rework`
      requires at least one child/cross-entity kickback; `blocked`, `hold`,
      or `cancelled` requires `no_kickback_reason` when no kickback exists.
- [x] A `success` role cannot contain an open or `severity_conflict` blocking
      finding.
- [x] A finding disposition must be one of the schema-defined values
      (`open`, `fixed`, `already_dispositioned`, `severity_conflict`,
      `not_reproducible`) and must point to a durable decision (a bounded
      `disposition_pointer`) when it is `already_dispositioned` or
      `severity_conflict`.

### Non-Functional Requirements (subset of REQ-NF-001 applicable to the model package)

- [x] Reuse the Question model's bounded-text and forbidden-marker approach
      for every free-text field (summary, findings, kickback reasons, sweep
      and impact text) — see `internal/gateresult/text.go`.
- [x] Report validation errors by field and class (`ValidationError{Field,
      Class, Message}`) without echoing rejected secrets or entire worker
      output.

The filesystem-level half of REQ-NF-001 (owner-only run directories/files,
no-follow, fsync, create-once/lock/CAS guarantees for the sidecar transport)
is out of this task's scope — it belongs to T-E34-F05-002, since it concerns
the sidecar transport, not the in-memory GateResult model.

## Implementation Plan

### Steps

1. [x] Step 1 (subset): Trace the Question model/service
       (`internal/models/question.go`,
       `internal/services/question_workflow_service.go`) as the closest
       existing bounded, validated, parent-owned worker-handoff pattern.
2. [x] Step 2: Add the canonical model/parser, bounds, forbidden-field rules
       (unknown-field rejection), semantic outcome roles, and unit test
       fixtures.

Steps 3–5 of the original plan (sidecar transport, persistence coordinator,
core/Rider wiring, workflow-schema migration, and the full regression
matrices) are owned by T-E34-F05-002 through T-E34-F05-005.

### Technical Approach

- [x] Kept `GateResult` free of any parent-observed field (entity, source
      status, observed gate, outer outcome, outer evidence, lease) — those
      remain the outer worker-control envelope's and the coordinator's
      responsibility, never trusted from worker output.
- [x] `Kickback.TargetStatus` is validated here only as bounded text; its
      workflow-membership check against the target entity's configured
      outcomes is explicitly deferred to the persistence coordinator
      (T-E34-F05-003), per the project convention against hardcoding status
      names in shared models.
