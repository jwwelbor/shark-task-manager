# Task: Parent-owned GateResult persistence coordinator

## Goal

T-E34-F05-001 (original feature-spanning task) split on 2026-08-31 after
delivering only REQ-F-001 (GateResult model/parser) and REQ-F-004 (semantic
outcome-role validation). This task owns REQ-F-002: the coordinator that
turns a validated `internal/gateresult.GateResult` (already built) into
durable Shark notes, sweep/impact references, and task kickbacks, in the
feature-defined idempotent order, before any workflow transition. It is the
component the WWGM E04 inventory finding (45 recorded review findings, zero
durable `review-finding` notes) exists to fix.

## Requirements

### Functional Requirements (REQ-F-002 — Parent-owned persistence, feature.md §REQ-F-002)

- [ ] Persist, in this exact order, per architecture.md "Gate result flow"
      step 7: (1) a gate-summary/evidence `review` note, (2) `review-finding`
      notes per finding, (3) remediation-sweep `reference` notes (I-03), (4)
      I-04 change-impact `reference` notes, (5) task kickbacks, then (6)
      `persistence_complete`.
- [ ] Sweep and impact notes use the existing `reference` note type with
      bounded `record_kind` metadata; no new note enum or database migration
      (confirmed: `internal/models/validation.go` already lists `reference`,
      `review`, and `review-finding` as valid note types — this task adds no
      new type).
- [ ] An I-04 note identifies its source key and operation digest.
- [ ] Store finding metadata for gate, severity, `class_key`, class statement,
      fingerprint, affected acceptance/test identifiers, disposition, and the
      parent session identity (all already present on `gateresult.Finding` —
      this task maps that struct onto note metadata).
- [ ] Keep persistence within the entity and note services; do not let a gate
      worker claim, advance, release, or force-set workflow state — the
      coordinator is the only caller of note/task-kickback/transition APIs for
      a gate result.
- [ ] Each suboperation has the stable ID T-E34-F05-002 derives (run operation
      digest + operation kind + stable item identity: finding fingerprint,
      sweep `class_key`, impact source kind/key, kickback entity key, or the
      singleton gate-summary key). Notes store it in typed metadata; kickback
      reasons/history store its bounded machine token.
- [ ] The target service holds the per-run lock (from T-E34-F05-002) and
      applies an identical suboperation only when no matching durable target
      record exists. A retry first reconciles from note metadata and entity
      history (using T-E34-F05-002's reconciliation read path), skips
      completed identical operations, and resumes the rest.
- [ ] Kickback validation: every kickback's `entity_key` must differ from the
      bound main entity key (already enforced role-independently by
      `gateresult.ValidateRole`, delivered) — this task adds the
      *target-entity* workflow-membership check for `Kickback.TargetStatus`
      that `internal/gateresult`'s package doc explicitly defers to "the
      persistence coordinator": the target status must be a valid configured
      outcome/status for the target entity's own workflow before the kickback
      is applied. Already-applied kickbacks are safe to retry; a conflicting
      target status or reason on retry fails closed.
- [ ] The parent applies the workflow transition exactly once from the
      recorded source to the resolved target, verifies an already-applied
      identical target, then records `transition_applied` (via
      T-E34-F05-002's sidecar). It releases the lease only after terminal
      worker-retirement evidence (from T-E34-F05-002); a crash after
      transition but before release resumes release rather than repeating the
      transition.

## Implementation Plan

### Steps

1. [ ] Step 1: Trace `internal/services` note/task/entity services and
       `internal/status`/`workflow.Service` to identify the exact API surface
       for creating typed notes with metadata, applying task kickbacks, and
       validating a target entity's workflow outcomes/statuses.
2. [ ] Step 2: Implement the persistence coordinator behind injected
       interfaces for notes, task status changes, T-E34-F05-002's
       operation-state lookup/update, and worker-retirement evidence — per
       architecture.md's "Parent result coordinator" component boundary
       (owns entity/run/session binding, replay state, persistence order,
       kickbacks; does not own gate reasoning or workflow outcome
       definitions).
3. [ ] Step 3: Implement the six-step idempotent persistence order (review
       note, review-finding notes, sweep reference notes, I-04 reference
       notes, kickbacks, `persistence_complete`), each suboperation guarded by
       T-E34-F05-002's suboperation-ID reconciliation.
4. [ ] Step 4: Implement target-entity workflow-membership validation for
       `Kickback.TargetStatus` and wire the coordinator's transition-apply
       call (source → resolved target, exactly once, verify-already-applied
       fallback) and lease-release-after-retirement call.
5. [ ] Step 5: Add the full persistence-ordering, partial-failure,
       conflicting-replay, and idempotent-kickback regression suite (see
       Testing Strategy).

### Technical Approach

- [ ] Coordinator depends on T-E34-F05-002's sidecar/digest/suboperation-ID
      functions via injected interfaces — do not reimplement sidecar I/O in
      this task.
- [ ] Coordinator depends on `internal/gateresult.GateResult` (delivered) as
      its only accepted input shape; it must not accept or re-derive
      unvalidated worker output.
- [ ] Reuse existing note/entity/task services; no new persistence table.
- [ ] Cross-entity note and task writes do not need a new distributed
      transaction — validation completes before the first write, every write
      has a stable replay identity, and transition is gated on the completed
      operation set (architecture.md "Gate result flow").

## Deliverables

- [ ] Parent coordinator for typed notes (`review`, `review-finding`,
      `reference`), sweeps, I-04, child kickbacks, transition, and
      target-store reconciliation.
- [ ] Target-entity workflow-membership validation for kickback
      `target_status`.
- [ ] Regression evidence for persistence ordering, partial failure, and
      idempotent retry.

## Acceptance Criteria

- [ ] Every note, sweep, impact, and child kickback is durable exactly once
      across all target-commit/sidecar and transition/release crash windows
      (coordinated with T-E34-F05-002's sidecar state).
- [ ] Persistence occurs in the exact feature-defined order and only after
      full GateResult validation; no partial or out-of-order write is
      observable on inspection after a crash mid-sequence.
- [ ] A kickback targeting an invalid status for its target entity's workflow
      is rejected without partial mutation; an already-applied kickback is
      safe to retry; a conflicting target status/reason on retry fails
      closed.
- [ ] Parent advances only after a verified terminal result and retirement
      evidence are present; restart completes transition/release exactly
      once.
- [ ] A gate worker cannot claim, advance, release, or force-set workflow
      state through this coordinator's surface.

## Testing Strategy

- [ ] Service tests failure-inject every target write (each note type, each
      kickback) and prove exact resume/reconciliation by stable suboperation
      ID with no duplicate note, history entry, or kickback.
- [ ] Table-test target-entity kickback validation: valid target status,
      invalid/unknown target status, retry with identical target
      (idempotent), retry with conflicting target status or reason (fails
      closed).
- [ ] Integration tests exercise the full six-step persistence order against
      a fixture `GateResult` with findings, kickbacks, sweeps, and impacts,
      asserting note content/metadata and kickback application match the
      fixture exactly.
- [ ] Execute focused suites and `make fmt`, `make lint`, `make test`, and
      `git diff --check`.

## Dependencies

  validated GateResult input.
- Depends on T-E34-F05-002 (durable transport) for the sidecar,
  operation-digest, suboperation-ID, and reconciliation-read primitives this
  coordinator writes against and reads from.
- T-E34-F05-004 (core/Rider ingestion parity) depends on this coordinator as
  its persistence call target.
