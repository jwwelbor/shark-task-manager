# Task: Core runner and Rider adapter GateResult ingestion parity

## Goal

T-E34-F05-001 (original feature-spanning task) split on 2026-08-31 after
delivering only REQ-F-001 (GateResult model/parser) and REQ-F-004 (semantic
outcome-role validation). This task owns REQ-F-005: making `shark run` (the
core runner) and Shark Rider's `/shark-rider run` verb call one shared,
authenticated ingestion/resume path — the validated GateResult parser
(delivered) plus the transport (T-E34-F05-002) and persistence coordinator
(T-E34-F05-003) — instead of Rider's separate free-form directive grammar.

**Correction to an earlier draft of this task (re-verified against the Go
source during task-review split, 2026-08-31):** the feature's decision note
on E34-F05 (`shark feature get E34-F05 --json`) says the worker-control
envelope "already shipped in E38-F09 (PR #149)" — but that shipped only as a
**Rider-side prose contract**. `skills/shark-attack/context/worker-control-schema.yaml`
says explicitly: "this file is a schema/prose contract only — it is not a
durable record and F09 introduces no Go type or running processor for it; the
parent renders it as instructions and reads a worker's plain-text reply
against this shape." On the core-runner (Go) side, no `kind`/
`recommended_outcome`/`evidence[]` type exists at all:
`internal/runner/controller.go`'s `recommendedOutcome` (around line 933)
still parses only a single `recommended outcome: <key>` text line or a bare
`{"outcome": "<key>"}` JSON object — there is no outer-envelope Go parser to
extend, and no `evidence[]` handling in Go today. This task therefore owns
**both** halves: (a) writing the Go outer worker-control envelope
parser/type for the core runner (mirroring the existing YAML prose contract
exactly, adding no second envelope or marker) so `shark run` can recognize
`kind: final` with `recommended_outcome`/`evidence[]`, and (b) validating and
persisting the nested `gate_result` payload inside that envelope via
`internal/gateresult` (delivered) plus T-E34-F05-002/003. Rider-side, the
envelope already exists as documentation Rider follows — that half only needs
wiring to the shared `--apply-result`/`--resume-run` CLI surface, not a new
envelope.

## Requirements

### Functional Requirements (REQ-F-005 — Rider and core-runner parity, feature.md §REQ-F-005)

- [ ] Add the Go outer worker-control envelope parser/type for the core
      runner: `kind` (`final|question|needs_council|blocked_external|failed`),
      the opaque `recommended_outcome` (present only for `kind: final`), and
      bounded `evidence[]` (`EvidenceRef` with `kind`, `pointer`, optional
      bounded `summary`, and for executable evidence: `command`,
      `working_directory`, `exit_code`, runner-native `counts`,
      `expected_skips`, `unexpected_skips`). Mirror
      `skills/shark-attack/context/worker-control-schema.yaml` exactly — this
      is the first Go type for that envelope; no Go type or processor for it
      exists today. Do not add a second envelope, marker, or duplicate field
      list.
- [ ] Replace or wrap `internal/runner/controller.go`'s current
      `recommendedOutcome` single-line/bare-JSON parser with (or behind) the
      new envelope parser so existing non-gate/`legacy` behavior (pass-first
      fallback when unspecified, unknown-outcome error) is preserved
      byte-for-byte for steps that do not opt into `gate_result_v1`.
- [ ] Update Rider's run procedure (`skills/shark-rider/verbs/run.md`), task
      execution pattern (`skills/shark-rider/context/task-execution-pattern.md`),
      host adapter result contract
      (`skills/shark-rider/context/host-adapter-contract.md`), and relevant
      gate prompts to emit and consume the same envelope shape validated by
      `internal/gateresult` — no second, Rider-only grammar for structured
      gate steps.
- [ ] Extend `shark run` (`internal/cli/commands/run.go`,
      `internal/runner/controller.go`) to validate the nested `gate_result`
      payload (when the step's `result_contract` is `gate_result_v1` — field
      added by T-E34-F05-005, this task consumes it) and persist it via
      T-E34-F05-003's coordinator before calling `TransitionStatus`. Non-gate
      steps continue through the existing `recommendedOutcome` path
      unmodified during migration.
- [ ] Add one initial Rider ingestion path: `shark run <entity-key>
      --apply-result=<result-file> --run-id=<run_id>
      --session=<authorized-session-id>`. Do not retain a separate Rider
      parser or persistence sequence — Rider calls this CLI surface, which
      calls the same coordinator the core runner calls directly.
- [ ] Wire `--resume-run=<run_id>` (built in T-E34-F05-002) into both the core
      runner's own crash-recovery path and Rider's recovery instructions, so
      both callers use one resume implementation.
- [ ] Add operator status output surfacing worker phase, nested operation,
      elapsed time, retirement state, and result location (uses
      T-E34-F05-002's polling primitives) for both `shark run` foreground
      execution and `shark run --resume-run`.
- [ ] Add parity tests that run identical fixtures through both documented
      paths (core `shark run` ingestion call, Rider's
      `--apply-result`/`--resume-run` CLI) and compare accepted data,
      rejection classes, and persistence order.

## Implementation Plan

### Steps

1. [ ] Step 1: Trace `internal/runner/controller.go`'s current
       `recommendedOutcome`/dispatch-to-transition path (Question handoff at
       `parseQuestionResponseHandoff` is the closest existing bounded,
       validated, parent-owned pattern) and Rider's `run.md` directive
       recognition to identify the exact insertion points for GateResult
       validation and persistence.
2. [ ] Step 2: Add `result_contract`-gated GateResult validation and
       T-E34-F05-003 coordinator invocation into the core runner between
       dispatch success and transition; fail closed (no transition) on any
       validation or persistence error, per REQ-F-006's "a gate explicitly
       configured for structured results must fail closed when the envelope
       is absent or malformed."
3. [ ] Step 3: Add `shark run <entity-key> --apply-result=<result-file>
       --run-id=<run_id> --session=<session-id>` as Rider's ingestion
       surface, sharing the same validation/coordinator call as Step 2.
4. [ ] Step 4: Update Rider's run procedure/task-execution-pattern/host-
       adapter-contract docs to emit the envelope and call
       `--apply-result`/`--resume-run` instead of parsing free-form directive
       lines for `gate_result_v1` steps; retain the existing directive path
       for `legacy` steps during migration.
5. [ ] Step 5: Migrate the gate prompts selected by the canonical adoption
       matrix (T-E34-F05-005 defines the matrix and `result_contract` field;
       this task updates the prompt partials once and renders all consumers)
       to request the `gate_result` payload shape.
6. [ ] Step 6: Add operator status output and the full parity/security/
       lost-response/stall regression suite (see Testing Strategy).

### Technical Approach

- [ ] Both execution paths call one public ingestion boundary backed by the
      same parser (the new Go outer-envelope parser this task adds, plus
      `internal/gateresult` for the nested payload, delivered) and
      coordinator (T-E34-F05-003). Core `shark run` calls it directly; Rider
      invokes `shark run <entity-key> --apply-result=...`.
- [ ] Do not add a second worker-control envelope, marker, or Rider-specific
      persistence sequence — the envelope *shape* already exists as Rider
      prose (E38-F09, `worker-control-schema.yaml`); this task gives the core
      runner a Go type for that same shape rather than inventing a new one,
      and reuses T-E34-F05-002/003's shared transport/coordinator.
- [ ] A run belonging to another entity, an unreachable source, or a
      different envelope digest fails closed (delegates to T-E34-F05-002's
      digest/identity checks).

## Deliverables

- [ ] Go outer worker-control envelope parser/type (`kind`,
      `recommended_outcome`, `evidence[]`/`EvidenceRef`) for the core runner —
      the first Go representation of the existing Rider-prose contract.
- [ ] Core runner GateResult validation + persistence integration
      (`internal/runner/controller.go` or equivalent), gated on
      `result_contract`.
- [ ] `shark run <entity-key> --apply-result=<result-file> --run-id=<run_id>
      --session=<session-id>` CLI surface.
- [ ] Updated Rider run procedure, task execution pattern, host adapter
      contract, and migrated gate prompt partials.
- [ ] Operator status output (phase, nested operation, elapsed, retirement,
      result location).
- [ ] Core/Rider initial-ingestion and resume parity fixtures.

## Acceptance Criteria

- [ ] Core and Rider produce identical normalized result, error class,
      persistence order, target writes, and transition for shared fixtures.
- [ ] A structured gate step with an absent or malformed envelope fails
      closed on both paths; it never falls back silently to legacy directive
      parsing.
- [ ] A non-gate (`legacy`) step continues to transition via the existing
      `recommendedOutcome` path, unaffected by this task's changes.
- [ ] Rendered prompts alone are not accepted as parity evidence — parity
      tests must run shared fixtures through both the core ingestion call and
      Rider's apply-result/resume CLI and compare normalized output.

## Testing Strategy

- [ ] Run shared valid, malformed, conflicting-replay, and partial-resume
      fixtures through both the core ingestion call and Rider's
      apply-result/resume CLI. Compare normalized results, bounded error
      classes, suboperation order, target writes, and selected transition.
- [ ] CLI/path tests cover authenticated apply/resume, entity/session
      mismatch, and the fail-closed behavior for absent/malformed structured
      payloads on a `gate_result_v1` step.
- [ ] Content tests verify every migrated prompt/skill doc references the
      canonical envelope shape and does not duplicate a field list that could
      drift from `internal/gateresult`.
- [ ] Execute focused suites and `make fmt`, `make lint`, `make test`, and
      `git diff --check`.
