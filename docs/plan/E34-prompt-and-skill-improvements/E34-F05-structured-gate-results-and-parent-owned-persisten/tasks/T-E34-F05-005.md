# Task: GateResult workflow-schema migration and regression matrices

## Goal

T-E34-F05-001 (original feature-spanning task) split on 2026-08-31 after
delivering only REQ-F-001 (GateResult model/parser) and REQ-F-004 (semantic
outcome-role validation). This task owns REQ-F-006: adding the route-step
`result_contract` and `outcome_roles` workflow-schema fields, exposing them
through `shark next`, and migrating the 13-entry canonical adoption matrix
named in architecture.md's "Compatibility and migration" section. It also
owns the feature-spanning regression-matrix testing work from feature.md's
"Implementation plan" Step 5 and "Verification plan" that is not already
covered by T-E34-F05-002/003/004's own testing sections (workflow-table
adoption-matrix coverage and `shark next --json` exposure parity).

## Requirements

### Functional Requirements (REQ-F-006 — Compatibility, feature.md §REQ-F-006)

- [ ] Route steps select `result_contract: legacy|gate_result_v1`; omission
      defaults to `legacy`, unknown values fail workflow validation, and
      `shark next` exposes the resolved value to both execution paths (core
      runner and Rider).
- [ ] Structured (`gate_result_v1`) steps declare an exact `outcome_roles` map
      covering every configured outcome, using the roles already defined in
      `internal/gateresult` (`success`, `route_rework`, `kickback_rework`,
      `blocked`, `hold`, `cancelled`). Missing, extra, or unknown roles fail
      workflow validation, and `shark next` exposes the map to both paths.
- [ ] Non-gate steps may continue using `legacy` while migrations proceed.
- [ ] A gate explicitly configured for `gate_result_v1` must fail closed when
      the envelope is absent or malformed (validated at the workflow-schema
      level here; enforced at runtime by T-E34-F05-004).
- [ ] Existing note storage remains readable; no database migration.
- [ ] Migrate the canonical adoption matrix to `result_contract:
      gate_result_v1` with a complete `outcome_roles` map, per
      architecture.md's "Compatibility and migration" section (13 entries):
      - Epic: `feature_review`, `integration_review`
      - Feature: `specification`, `test_planning`, `task_review`,
        `code_review`, `qa`, `approval`
      - Tech-debt: `triaged`, `in_progress`
      - Change-card: `development`, `code_review`, `qa`
      All other steps remain `legacy` unless a later versioned migration
      names them. Question `ready_for_resolution` explicitly stays a human
      `pause` step outside this matrix — its I-04 note comes from the
      validated Question resolution service, not worker output (this task
      does not touch `ready_for_resolution`'s `result_contract`).
- [ ] ADR adoption uses a new parent-owned `shark impact record <entity-key>
      --source-kind=adr --source-key=<ADR-ID> --source-pointer=<path>
      --impact-file=<bounded-I-04-json>` command, backed by the same
      `internal/gateresult` I-04 validator and T-E34-F05-003's typed-reference
      persistence service; workers do not write it directly.
- [ ] Existing projects with no overrides receive unchanged upgrade behavior;
      whole-file project overrides must deliberately adopt the new field
      (Shark never patches project workflow YAML automatically).

## Implementation Plan

### Steps

1. [ ] Step 1: Add `result_contract` and `outcome_roles` to the workflow
       schema loader/types (wherever route-step fields such as `action`,
       `agent`, `outcomes` are defined and validated — see
       `docs/guides/route-based-workflow.md` §1 "One block per step") and to
       `shark admin validate` / the workflow validator, per
       architecture.md §6 Validation-equivalent rules for this feature: start
       step defined, every workable structured step declares exactly the
       required roles, no unknown selector/role.
2. [ ] Step 2: Expose the resolved `result_contract` and `outcome_roles` in
       `shark next --json` output for both entity-key-driven resolution paths
       consumed by the core runner and Rider.
3. [ ] Step 3: Migrate the 13 canonical adoption-matrix entries (embedded
       default workflow YAML under
       `internal/sharkdata/default_data/workflow/*.yaml`) to
       `result_contract: gate_result_v1` with complete `outcome_roles` maps.
4. [ ] Step 4: Add `shark impact record` for ADR I-04 adoption, backed by
       `internal/gateresult`'s `ChangeImpactSet` validator and
       T-E34-F05-003's reference-note persistence.
5. [ ] Step 5: Add the full workflow-table and content-test regression
       matrix: every named adoption-matrix entry and representative excluded
       steps; omitted selector → `legacy`; unknown selector/role; incomplete
       or extra role maps; missing structured payload; Question pause; ADR
       impact ingestion; whole-file overrides; `shark next --json` exposure
       parity between the core runner and Rider consumption paths.

### Technical Approach

- [ ] `outcome_roles` reuses `internal/gateresult.OutcomeRole`'s closed set
      (`success`, `route_rework`, `kickback_rework`, `blocked`, `hold`,
      `cancelled`) as the only valid role tokens — no new role vocabulary.
- [ ] Follow the project's route-based-workflow schema conventions
      (`docs/guides/route-based-workflow.md`): `steps:` block-per-step,
      `outcomes:` routing map already existing per step; this task adds
      sibling fields alongside, not a replacement schema.
- [ ] `shark next` must expose identical `result_contract`/`outcome_roles`
      values to whichever caller resolves them (core runner in-process vs.
      Rider's CLI-driven resolution) — do not let the two paths derive the
      value independently.

## Deliverables

- [ ] `result_contract` and `outcome_roles` workflow-schema fields, loader
      support, and validator rules.
- [ ] `shark next --json` exposure of both resolved fields.
- [ ] 13-entry canonical adoption-matrix migration in the embedded default
      workflow bundle.
- [ ] `shark impact record` command for ADR I-04 adoption.
- [ ] Full workflow-table adoption-matrix and content-test regression suite.

## Acceptance Criteria

- [ ] Every canonical matrix step resolves structured output, excluded/
      omitted steps stay `legacy`, and `shark next` exposes identical
      selectors/roles to both callers.
- [ ] An unknown `result_contract` value or an incomplete/extra
      `outcome_roles` map fails workflow validation with a clear error.
- [ ] `ready_for_resolution` (Question) is unaffected — remains a `pause`
      step, its I-04 note still comes from the Question resolution service.
- [ ] `shark impact record` validates and persists an I-04
      `ChangeImpactSet` for an ADR source without any worker-side write path.
- [ ] Existing projects with no overrides see unchanged behavior after
      upgrade.

## Testing Strategy

- [ ] Workflow-table every named adoption-matrix entry and representative
      excluded steps. Test omitted selector → `legacy`, unknown
      selector/role, incomplete or extra role maps, missing structured
      payload, Question pause, ADR impact ingestion, and whole-file
      overrides.
- [ ] Assert `shark next --json` exposes the same resolved `result_contract`
      and `outcome_roles` to both callers (core runner path and Rider CLI
      path).
- [ ] Content tests verify every producer/consumer prompt references the
      canonical adoption-matrix shape and no duplicate field list drifts from
      `internal/gateresult`.
- [ ] Execute focused suites and `make fmt`, `make lint`, `make test`, and
      `git diff --check`.

## Dependencies

- Depends on `internal/gateresult` (T-E34-F05-001, delivered) for the
  `OutcomeRole` closed set and `ChangeImpactSet`/I-04 validation used by
  `shark impact record`.
- The `shark next` exposure work in Step 2 depends on T-E34-F05-002 (durable
  transport/run identity) and T-E34-F05-003 (persistence coordinator)
  existing, since `shark next`'s consumers (core runner, Rider) need a real
  ingestion/coordinator target for the exposed fields to be meaningful; the
  schema/loader/validator work in Step 1 and the adoption-matrix migration in
  Step 3 can proceed in parallel with T-E34-F05-002/003/004.
- `shark impact record` depends on T-E34-F05-003's reference-note persistence
  service.
- T-E34-F05-004's core-runner `result_contract` gating reads this task's
  schema field; coordinate landing order.
- The recorded `shark task link T-E34-F05-005 --depends-on T-E34-F05-003`
  edge is a conservative whole-task gate — Shark's dependency graph has no
  partial-step dependency, so the automated dispatcher will not start this
  task until T-E34-F05-003 is complete, even though Steps 1 and 3 above
  (schema/loader/validator work, adoption-matrix migration) are themselves
  parallel-safe with T-E34-F05-002/003/004. A human operator may start those
  steps early by hand if they choose; the recorded link only constrains
  automated dispatch.
