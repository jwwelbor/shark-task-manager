# Task: Extend shark admin upgrade with overrides summary

## Goal

Surface drift counts inside the existing `shark admin upgrade` output so
operators see them without a separate command, per spec.md "REQ-F-003
(spec)".

## Scope

- Modify: `internal/cli/commands/sharkdata_cmd.go` — `runSharkUpgrade` calls
  `sharkdata.OverrideStatusAt(dataRoot)` after `UpgradeAt` succeeds (real and
  `--dry-run`) and adds an `overrides` block to JSON and human output;
  `sharkUpgradeCmd`'s `Long` help gains one line pointing at
  `shark admin overrides status`.
- Modify: `internal/cli/commands/sharkdata_cmd_test.go` — existing tests
  expect the new `overrides` key (additive only).
- Modify: `docs/cli-reference/setup-commands.md` — document the extended
  upgrade output (T-E34-F09-004 touches the same file, a different section).

## Acceptance Criteria

See spec.md AC "upgrade output schema", "upgrade byte-identity guarantee".
- AC-T1: the four pre-existing JSON keys are unchanged; `overrides` is
  additive, all five keys always present (zero-valued when none).
- AC-T2: a real upgrade never writes `.shark-override-baselines.json` —
  only `acknowledge` does.

## Test Cases

See test-plan.md TC-009 (schema, `--json`/`--dry-run`) and TC-010
(byte/mode/manifest identity across a real upgrade). Caller-Path Contract:
`runSharkUpgrade` production entrypoint.

## Integration Contracts

### Cross-feature
- I-05: consumes (informational only — this task's `OverrideStatusAt` call
  does not parse I-05's manifest; see spec.md "Cross-feature interactions").

## Brownfield Context

`runSharkUpgrade` (existing, ~lines 257–293) already computes `summary` via
`sharkdata.UpgradeAt`; this task adds one more read-only call after it, per
spec.md "Integration with existing code".

## Notes for Agent

No existing field, key, or output line is removed — this is purely additive.
