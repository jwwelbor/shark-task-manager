# IntegrationCandidate and UpdateCandidate CAS

## Goal
Add `IntegrationCandidate` and `UpdateCandidate`, maintaining the single
atomic accumulated-view file per epic run via compare-and-swap so concurrent
feature completions from independent processes are both eventually
reflected without corruption.

## Scope
- Files to create: `internal/integration/candidate.go`, `internal/integration/candidate_test.go`
- Depends on `internal/integration/event.go` (T-E34-F08-005) for
  `IntegrationEvent` shape; does not modify `event.go`.

## Acceptance Criteria
Reference spec.md AC-4 (candidate half), AC-5, and Durable unresolved
decision Q-F08-01 (single-retry CAS policy).
Additional task-specific criteria:
- AC-T1: `Digest` is `sha256` over the struct's canonical JSON with `Digest`
  itself excluded, matching I-03's existing guard-digest convention.
- AC-T2: Write path is write-to-temp-then-`os.Rename` with an `fsync` on the
  temp file before rename.
- AC-T3: A write against a stale expected-prior digest is rejected with a
  typed conflict error; the on-disk file is byte-identical before and after
  the rejected attempt.
- AC-T4: Exactly one retry is attempted on conflict; a conflict that persists
  through the retry reports the typed conflict error rather than looping a
  third time (Q-F08-01's adopted policy).

## Test Cases
See test-plan.md TC-007's candidate-side assertion (final `EventIDs` contains
both concurrent writers' IDs) and TC-008 (stale-digest CAS rejection via the
test-only synchronization hook described in test-plan.md's Caller-Path
Contracts row for TC-008; do not simulate the conflict by calling a
lower-level unexported function with a hand-constructed stale digest).
