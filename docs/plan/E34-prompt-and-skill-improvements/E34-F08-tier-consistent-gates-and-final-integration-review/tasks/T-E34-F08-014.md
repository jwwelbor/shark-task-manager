# Crash-restart repair and registration reconciliation

## Goal
Close the second half of the REQ-F-004 durability gaps: prove the
registration write path T-E34-F08-012 built survives a crash at every
step, repairs only what is genuinely missing, and fails closed rather than
guessing on tamper or conflict — so a crashed or restarted parent loop
never loses or duplicates the epic's integration identity.

## Scope
- Modify: `internal/integration/run.go` (exact-retry repair of a missing
  note for a matching head; reject a note whose referenced head is
  absent/corrupt; reject a second registration for a different
  `EpicRunID` while one is nonterminal)
- Test files: `internal/integration/run_test.go` (failure-injection,
  tamper, truncation, and reordering subtests)

## Acceptance Criteria
Per feature.md:106-119 and architecture.md:273-316:
- AC-T1: Exact retry (matching head, no note) repairs only the missing
  note. A note whose referenced head is absent/corrupt, or conflicting
  bytes, fails closed without reconstruction; the parent cannot acknowledge
  active entry or dispatch a feature until head and note reconcile.
- AC-T2: A second registration for a different `EpicRunID` while one is
  nonterminal is rejected.

## Test Cases
See test-plan.md TC-017: failure-inject after event fsync, after
archived-head fsync (T-E34-F08-012), and after candidate-head replacement
before note ack; after each restart assert identical retry, no
duplicate/lost event, a recomputable prior-head chain (reading
T-E34-F08-012's `integration-heads/` retention), and rejection of a same
event ID with different bytes. Add tamper, truncation, and reordering
detection against the retained `integration-heads/` chain.

T-E34-F08-012's lock) and `integration_review` (T-E34-F08-010).
