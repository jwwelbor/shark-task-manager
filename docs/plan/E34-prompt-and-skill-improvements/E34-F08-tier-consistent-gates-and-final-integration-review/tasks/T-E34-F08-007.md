# Integration Backfill and shark integration backfill CLI

## Goal
Add `integration.Backfill` (sharing the steady-state
capture/event-write/candidate-update path) and the `shark integration
backfill` CLI command, so an epic already active before this feature shipped
can be registered without a second, independently-maintained code path.

## Scope
- Files to create: `internal/integration/backfill.go`, `internal/integration/backfill_test.go`,
  `internal/cli/commands/integration_cmd.go`, `internal/cli/commands/integration_cmd_test.go`
- Files to modify: CLI command registration (`init()` wiring, per this
  project's existing command-registration convention). Uses
  T-E34-F08-012's run-scoped lock for the registration-note write so
  backfill and steady-state capture share one correctness argument.

## Acceptance Criteria
Reference spec.md AC-6.
Additional task-specific criteria:
- AC-T1: `--dry-run` performs every validation and writes nothing to disk;
  non-dry-run creates exactly one `IntegrationRun`, one `IntegrationEvent`
  per input entry, one `IntegrationCandidate`, and one epic
  `--type=reference` note.
- AC-T2: A second `backfill` attempt against an already-registered epic is
  rejected with zero mutation.
- AC-T3: `--session` is validated against a live claim on `<epic-key>`
  (mocked at the claim-lookup seam in CLI tests, per this repo's
  CLI-tests-mock-repositories convention) — a missing or mismatched claim is
  rejected with zero mutation.
- AC-T4: All input validation (`--base` reachability, no duplicate
  `EventID`, digest/path match against named commits, bounded array size)
  completes before any write (validate-fully-before-first-write).
