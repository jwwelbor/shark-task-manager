# Research report: E34 interaction map and deliverable-boundary policy

## Scope

This task establishes the design-time interaction-map and deliverable-boundary
policy for E34-F03. It extends the existing prompt/template contract for a
per-epic `I-##` map; it does not introduce a database field, workflow state,
or runtime acceptance ledger. The assigned E34-F03-to-E34-F02 row must be
created only in the parent `E34-interaction-map.md`, then mirrored by the
producer and consumer feature documents with one shared contract-test pointer.

The report uses the parent feature's Capability map rather than duplicating it:
`../research-report.md` records the relevant REUSE and EXTEND decisions.

## Research checklist

- [x] `scope_vocabulary` — Evidence: `T-E34-F03-001.md` and `../spec.md` define the interaction map, `I-##`, `live`, `contract-only`, activation owner, closure key, and the producer/consumer boundary.
- [x] `affected_implementation_or_contract` — Evidence: `internal/sharkdata/default_data/prompts/epic/design.md`, `internal/sharkdata/default_data/prompts/epic/decomposition.md`, `internal/sharkdata/default_data/prompts/epic/feature_review.md`, and `internal/sharkdata/default_data/skills/specification-writing/context/interaction-map-template.md` define the affected embedded policy contract.
- [x] `pattern_contract` — Evidence: `internal/sharkdata/default_data/prompts/epic/design.md` assigns stable `I-##` IDs and one shared shape source; `../test-plan.md` requires one shared contract-test pointer and prohibits inventing an ID before the map exists.

## Findings

1. The established interaction-map lifecycle is document-based: epic design
   authors the stable `I-##` row, decomposition assigns an existing producer
   and consumer, and feature review rejects an orphan or mismatched shape
   source. The existing template also registers the map through
   `shark related-docs add`; this task should reuse that path.

2. No `E34-interaction-map.md` exists yet. The E34-F03 specification and test
   plan deliberately prohibit a provisional `I-##` or shared-test pointer.
   Map creation must therefore assign the F03-to-F02 row once, use its assigned
   architecture section as the shared shape source, and mirror the same exact
   ID, source, and single test pointer in both feature specifications.

3. The affected contract is an embedded prompt/template policy, not runtime
   behavior. The implementation extends it with a deliverable boundary
   (trigger, observable result, production path, UAT scenario, prerequisites,
   and consumer outputs) and the declared `live`/`contract-only` disposition.
   A `contract-only` row needs the named counterpart/status, shared evidence,
   activation owner, closure key, and review basis; it cannot waive missing
   live wiring, security, integrity, or a current acceptance criterion.

4. The parent feature Capability map already classifies this as an EXTEND of
   the interaction-map lifecycle and an EXTEND of the E34-F02 producer
   contract. This task does not discover a separate capability, so it does not
   add another Capability map.

## Decisions

1. **Extend the existing interaction-map contract.** Create and register the
   parent E34 map using the shipped template; retain stable IDs, a resolving
   architecture shape source, and one shared contract-test pointer.

2. **Keep the map authoritative.** Assign the F03-to-F02 ID in that map before
   updating the producer-side E34-F03 specification and the E34-F02 consumer
   specification. Do not put an independently invented ID or duplicate test
   pointer in either feature.

3. **Enforce a deliverable boundary as policy content.** Extend the epic
   design, decomposition, and feature-review prompt surfaces to reject a
   feature whose current acceptance depends on later work unless the
   requirement is reassigned or a complete predeclared `contract-only`
   disposition identifies its activation owner and closure.

4. **Preserve non-waivable gates.** A staged declaration changes neither the
   independent assessor verdict nor the requirement for live-path, security,
   integrity, and current-acceptance evidence. The owner decision remains a
   distinct reported fact.
