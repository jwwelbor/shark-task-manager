# Wire HarnessResolver into shark run controller for next/run parity

## Goal
Give `shark run` the same harness-resolution path as `shark next`
(T-E34-F01-004), including the three override flags, so REQ-F-006 holds: a
prompt renders byte-identically under both surfaces for the same entity and
harness inputs, at all three precedence tiers.

## Scope
- Files to modify: `internal/runner/controller.go`,
  `internal/cli/commands/run.go`.
- Files to create: none (extend the controller's existing test file and add
  parity assertions alongside `internal/cli/commands/next_golden_test.go`
  fixtures, per spec.md §3.3).

## Acceptance Criteria
Reference spec.md: "See spec.md AC-08"
- AC-T1: An optional `HarnessResolver` dependency is added to the
  controller's config struct alongside the existing `placeholders` field;
  when nil, the controller injects the zero identity's three empty keys —
  never an absent key (spec.md D-F01-07, §3.3).
- AC-T2: `run.go` registers the same three override flags as `next.go`
  (`--harness`, `--harness-version`, `--harness-model`) beside
  `--workdir`/`--worktree`, and passes them as the resolver's override
  identity. Without this, precedence tier 1 (flags) has no entry point under
  `shark run` (spec.md §3.3, explicit REQ-F-006/AC-08 callout).

## Test Cases
- TC-009/010/011 (test-plan.md): flag/claim/env-tier precedence — `runNext`
  and `RunController.Run` driven against the same entity/claim/step fixture
  produce byte-identical rendered prompts at each tier.
- Mock `EntityTransitioner`, `PlaceholderGenerator`, `ClaimReader` per
  test-plan.md's Caller-Path Contract; do not mock `HarnessResolver.Resolve`
  — each surface must be driven through its own real entrypoint (`runNext`
  vs `controller.Run`).
