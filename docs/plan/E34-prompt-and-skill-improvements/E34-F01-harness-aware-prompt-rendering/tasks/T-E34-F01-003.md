# Add HarnessResolver service and harness FuncMap helpers

## Goal
Introduce the `HarnessIdentity`/`HarnessResolver` types and the
`isHarness`/`isClaude`/`isCodex` template predicates that later tasks wire
into the dispatch surfaces. This task owns the D-F01-07 "always three keys"
guarantee at its source.

## Scope
- Files to create: `internal/services/harness_service.go`,
  `internal/services/harness_service_test.go`.
- Files to modify: `internal/templates/orchestrator_renderer.go`,
  `internal/templates/orchestrator_renderer_test.go`.

## Acceptance Criteria
Reference spec.md: "See spec.md AC-12"
Additional task-specific criteria (if any):
- AC-T1: `HarnessIdentity.Vars()` returns exactly the three keys `harness`,
  `harness_version`, `harness_model`, each mapped to `""` when unset — never
  omitted (spec.md D-F01-07).
- AC-T2: `ClaimReader` is a one-method consumer-side interface
  (`Get(ctx, entityType, entityKey string) (*models.EntityClaim, error)`),
  satisfied as-is by `claim.Repository.Get` — do not redefine that method.
- AC-T3: `isHarness(want, got string) bool` is case-insensitive; `isClaude`
  and `isCodex` are thin wrappers, matching the `isSimple`/`isStandard`
  precedent exactly.

## Test Cases
- TC-015 (test-plan.md): `HarnessIdentity{}.Vars()` asserts `len(m) == 3` and
  each key's presence (not just value), per spec.md D-F01-07.
- TC-019 (test-plan.md): `Render` with `harness` key omitted against
  `{{if isClaude .harness}}A{{else}}B{{end}}` pins the exact failure string
  `at <.harness>: invalid value; expected string` (spec.md D-F01-07).
- Unit tests for `isHarness`/`isClaude`/`isCodex`, alongside the existing
  `isSimple` tests (test-plan.md Test Infrastructure).
