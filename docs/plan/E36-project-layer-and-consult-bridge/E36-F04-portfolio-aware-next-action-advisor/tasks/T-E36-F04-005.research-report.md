# Research report

## Scope

T-E36-F04-005 implements deterministic facts about portfolio precedence. It
accepts already assembled non-terminal candidates and relationship evidence,
then returns hard dependency layers, combined roadmap layers, unlayered keys,
and the four graph warning classes. It does not choose a root, inspect priority
or business value, classify workflow statuses, query data, or repair stored
relationships.

## Capability map

| Capability | Source | Decision | Application |
| --- | --- | --- | --- |
| Portfolio graph DTOs | T-E36-F04-001 and `portfolio_advice.go` | **REUSE** | Accept portfolio epic and relationship evidence and return `models.PortfolioOrdering` with allocated slices. |
| Stored relationship vocabulary | `entity_relationship.go` | **REUSE** | Normalize only `depends_on`, `blocks`, and `follows`; preserve typed contributing values. |
| Creation-time cycle prevention | `EntityRelationshipService.DetectCycle` | **CONTRADICTS** | Do not reuse its repository-backed, same-type DFS. Advice must analyze legacy mixed-type evidence already stored, including `follows` cycles. |
| Stable explicit ordering | E19-F07 and `SprintService.GetNextTask` | **EXTEND** | Reuse explicit tiers, stable comparison, and explainable cause; replace single-winner sorting with lexical graph layers and warnings. |
| Sprint queue and selection reason | E19-F07 | **CONTRADICTS** | Do not use `sprint_order`, execution order, priority, assignment time, or a winner/runner-up score. |
| Hard layering | E36-F04 specification | **NEW** | Run Kahn over unresolved hard precedence among non-terminal candidates. |
| Roadmap layering | E36-F04 specification | **NEW** | Run Kahn independently over unresolved hard precedence plus soft `follows` edges. |
| Contradiction diagnostics | E36-F04 TC-011 | **NEW** | Detect opposing normalized directions and retain the sorted union of contributing relationship types. |
| Missing-order diagnostics | E36-F04 TC-012 | **NEW** | Compare eligible hard first-layer roots with combined-graph reachability; do not turn a layer tie into a hidden total order. |

## Ubiquitous vocabulary

- **Candidate**: one non-terminal epic supplied by the advice service. Every
  candidate appears as a graph node, regardless of eligibility.
- **Eligible root**: a candidate whose `PortfolioEligibility` is exactly
  `eligible`; eligibility affects only missing-order diagnostics here.
- **Normalized edge**: a prerequisite direction `before -> after` derived from
  stored relationship semantics.
- **Hard edge**: an unresolved `depends_on` or `blocks` prerequisite that gates
  eligibility.
- **Soft edge**: a `follows` prerequisite used only in roadmap order.
- **Contributing type**: a stored relationship type that normalizes to a given
  directed edge.
- **Dependency graph**: all candidates plus deduplicated unresolved hard edges.
- **Roadmap graph**: the dependency graph plus deduplicated soft edges.
- **Layer**: every currently zero-indegree node emitted together in lexical key
  order during one Kahn iteration.
- **Unlayered candidate**: a node still unprocessed when the combined roadmap
  Kahn traversal has no zero-indegree frontier.
- **Contradiction**: two distinct keys with normalized precedence in both
  directions.
- **Missing order**: an eligible pair in the first dependency layer for which
  neither key reaches the other in the combined roadmap graph.

## Input and output boundary

The smallest integration-friendly entry point is equivalent to:

```go
func analyzePortfolioGraph(
	epics []models.PortfolioEpicEvidence,
	relationships []models.PortfolioEpicRelationship,
) models.PortfolioOrdering
```

T-E36-F04-006 supplies only non-terminal epics, calculates each epic's
eligibility, resolves relationship endpoints, and calculates hard satisfaction
through configured workflow classifiers. This helper uses only `Key` and
`Eligibility` from epic evidence and `FromKey`, `ToKey`, `RelationshipType`,
and `Satisfied` from relationship evidence. It derives hard-vs-soft semantics
from `RelationshipType` rather than trusting the redundant `Hard` output field.

Only relationships whose two keys are in the candidate set enter either graph.
This excludes terminal-only and dangling endpoints from layers while leaving
their original evidence and service-owned warnings untouched. Candidate keys
are defensively deduplicated, sorted once, and treated as immutable input.

Return `models.PortfolioOrdering` by value with non-nil
`DependencyLayers`, `RoadmapLayers`, `UnlayeredEpics`, and `Warnings`. The pure
function has no context or error because it performs no I/O and every bounded
input has a deterministic result.

## Exact normalization and satisfaction rules

| Stored evidence | Normalized edge | Graph | Satisfaction handling |
| --- | --- | --- | --- |
| `A depends_on B` | `B -> A` | hard and roadmap | Omit when `Satisfied` is non-nil and true; otherwise retain as unresolved. |
| `A blocks B` | `A -> B` | hard and roadmap | Omit when `Satisfied` is non-nil and true; otherwise retain as unresolved. |
| `A follows B` | `B -> A` | roadmap only | Always retain when both endpoints are candidates; `Satisfied` is not applicable. |

A nil `Satisfied` on a hard relationship is treated conservatively as
unresolved rather than silently erasing precedence. The service contract should
normally provide a non-nil value for hard evidence and separately mark unknown
workflow status. Unknown or unsupported relationship types are ignored by this
bounded helper; the repository already filters them.

Self-edges are retained. The live relationship model rejects newly created
self-references, but the advisor must diagnose legacy or directly seeded data
rather than assuming it cannot exist.

## Edge aggregation

Use a directed key such as `{before, after}` and a set of contributing types.
Exact duplicate inputs and different stored types that normalize to the same
direction produce one adjacency edge. An edge is hard when at least one
unresolved hard relationship contributes; the roadmap graph includes that edge
once even if a soft relationship contributes the same direction.

Keep contribution sets separate from adjacency. Contributing types are needed
for diagnostics, but duplicate types must neither increment indegree twice nor
duplicate warnings.

## Deterministic Kahn layering

Build independent indegree and adjacency maps for the dependency and roadmap
graphs. Include every candidate node, even when it has no edges.

For each graph:

1. Initialize the zero-indegree frontier from lexically sorted candidate keys.
2. Emit the entire frontier as one allocated layer.
3. Traverse each frontier key's deduplicated, lexically sorted outgoing keys,
   decrementing indegrees once per edge.
4. Collect newly zero-indegree keys, sort them lexically, and emit them in the
   next iteration.
5. Stop when the frontier is empty. Return allocated partial layers and the
   sorted keys that were never processed.

This is `O(V+E)` graph work plus explicit sorting. It does not depend on map
iteration or stable input order. For three candidates with only
`E03 follows E02` and `E02 follows E01`, dependency layers are
`[[E01, E02, E03]]` and roadmap layers are `[[E01], [E02], [E03]]`.

The two traversals must remain separate. A follows-only cycle may stall roadmap
layers, but it cannot erase or relabel usable dependency layers.

## Cycle classification and partial output

Use Kahn remainders to prove that a graph cannot be fully layered. Use a linear
strongly connected component pass over the relevant graph to classify actual
cycle contributors: a component is cyclic when it has more than one node or
contains a self-edge.

- Emit one `HARD_ORDER_CYCLE` warning when the dependency graph has a non-empty
  Kahn remainder. Its keys are the sorted hard remainder, matching the
  specification's unresolved-node definition.
- Emit one `ROADMAP_ORDER_CYCLE` warning when a cyclic roadmap component
  contains at least one soft contribution. Its warning keys are the sorted
  union of those soft-cycle components. This avoids mislabeling a hard-only
  cycle as a roadmap defect and still permits both warnings when hard and soft
  cycles coexist.
- Set `UnlayeredEpics` to the sorted roadmap Kahn remainder. The roadmap graph
  is the complete ordering graph and its remainder is a superset of any hard
  remainder.

The single `unlayered_epics` field is potentially ambiguous because both
traversals can stall. The data-model definition resolves it as candidate keys
remaining after Kahn traversal, and the combined roadmap graph is the final
ordering graph. This decision preserves every node omitted from roadmap layers;
warning keys separately identify hard and soft cycle classes.

Do not delete an edge, collapse a cycle into an arbitrary winner, or continue
by pretending cycle nodes were processed. A hard cycle between E01 and E02 with
independent E03 returns partial dependency and roadmap layer `[[E03]]`,
unlayered `E01, E02`, and terminates normally. A self-cycle behaves the same for
one key. Larger and disjoint cycles return lexical warning and remainder keys.

## Contradiction diagnostics

After normalization, inspect every distinct unordered key pair once. A
contradiction exists when both directed keys are present, regardless of whether
the contributors are hard, soft, or mixed. Self-edges are cycle evidence, not a
two-key contradiction.

Emit one `CONTRADICTORY_ORDER` warning per contradictory pair. Its `EpicKeys`
contains the two keys lexically. Its stable message names the sorted union of
contributing relationship types from both directions. For
`E01 depends_on E02` and `E01 blocks E02`, that union is `blocks, depends_on`.
Duplicate rows do not duplicate the warning. Both original relationships remain
in the envelope; the graph helper does not choose or remove either direction.

A contradictory pair can also form a hard or roadmap cycle and therefore may
produce the applicable cycle warning. These diagnostics describe different
facts and must not suppress one another.

## Reachability-based missing ordering

Missing-order analysis starts with the first dependency layer, because those
are the hard-ready roots. Filter that layer to epics whose eligibility is
exactly `eligible`; `ineligible` and `unknown` roots do not create this warning.

For each lexical unordered pair, run bounded reachability against the combined
roadmap adjacency with a fresh visited set. Emit one `MISSING_ORDERING` warning
only when neither key reaches the other. A soft path therefore supplies roadmap
order even when the pair shares the first hard layer. This makes the
reachability requirement meaningful and avoids falsely warning whenever only
soft precedence separates hard-ready roots.

Use one warning per incomparable pair. Its two keys are lexical, which keeps a
partially connected larger first layer actionable without implying that every
key in one aggregate warning is mutually incomparable. Adding any path in
either direction removes that pair's warning. Priority, business value,
progress, claims, timestamps, and input order are never inspected.

## Warning construction and ordering

Use fixed, actionable message templates. Messages may include sorted keys and,
for contradictions, sorted contributing types. Do not include SQL or claim
data. Before return, sort warnings by:

1. `Code` ascending;
2. `strings.Join(EpicKeys, ",")` ascending;
3. `Message` ascending.

Allocate every `EpicKeys` slice. The resulting ordering warning array is stable
for every permutation of equivalent inputs. T-E36-F04-006 may merge these with
non-graph warnings for the top-level envelope, but it must preserve the same
global warning comparator.

## Test design

Implement table-driven pure tests in `portfolio_graph_test.go` covering:

1. Each stored type's exact normalized direction and hard/soft membership.
2. Satisfied hard edges omitted, unresolved and nil-satisfaction hard edges
   retained, and follows unaffected by satisfaction.
3. Terminal/non-candidate and unknown-type endpoint evidence excluded from the
   graph.
4. Twenty or more deterministic permutations with identical complete
   `PortfolioOrdering` output.
5. Exact duplicate rows and multiple contributing types without duplicate
   indegree, layer keys, or warnings.
6. A linear DAG, independent nodes, and empty input with allocated slices.
7. A two-node hard cycle with an independent node, a self hard cycle, a larger
   hard cycle, and disjoint cycles under a test timeout.
8. A follows-only cycle with usable hard layers, plus coexisting hard and soft
   cycles that produce both warning codes in stable order.
9. Hard-hard and hard-soft opposing normalized directions with sorted
   contributing types; assert no repair or chosen direction.
10. Two eligible incomparable first-layer roots, an added direct or transitive
    roadmap path, and an ineligible/unknown first-layer root.
11. Map-hostile lexical keys and shuffled relationship order to prove all
    layers, unlayered keys, warning keys, type lists, and warnings are sorted.

Tests should compare complete values, not only membership. They need no mocks,
database, workflow service, context, or clock.

## Findings

1. Relationship creation-time cycle detection is not reusable. It queries one
   stored relationship type at a time and prevents new hard cycles, while
   portfolio advice must explain pre-existing combined semantics and allowed
   follows cycles without I/O.
2. The T001 DTO supplies the required graph input and output vocabulary. A
   separate exported graph DTO would duplicate the stable response contract.
3. Hard satisfaction must be computed before this helper because terminal
   status is workflow-configurable. The graph only filters an already marked
   satisfied hard edge.
4. Candidate membership and satisfaction together remove terminal endpoint
   relationships from layers while retaining them in envelope evidence.
5. Deduplicating by directed normalized endpoints prevents inflated indegree,
   but the edge must retain every contributing type for contradiction messages.
6. Dependency and roadmap Kahn traversals must be independent. Reusing the
   combined remainder for hard-cycle classification would falsely turn a
   follows-only cycle into a hard defect.
7. Strongly connected components provide deterministic soft-cycle
   classification when hard and soft cycles coexist. Kahn remains the source of
   layers and unlayered candidates.
8. Missing-order detection is not a score or lexical winner. It uses the first
   hard layer, exact eligibility, and combined-graph reachability, then leaves
   incomparable keys together.
9. E19-F07 establishes the value of explicit deterministic tiers and
   explanations, but its persisted sprint queue and priority/FIFO tiebreakers
   are explicitly out of scope for portfolio graph order.
10. One wording ambiguity remains visible: the data model defines
    `unlayered_epics` as every candidate remaining after Kahn traversal, while
    TC-010 informally says the keys identify follows-cycle participants. A node
    downstream of a cycle remains unprocessed without belonging to the cyclic
    component. This report follows the data-model definition for
    `UnlayeredEpics` and uses cycle-warning keys for actual contributors; a
    focused test should preserve that distinction rather than silently choosing
    a different meaning.

## Decisions

1. Implement one pure `analyzePortfolioGraph` entry point over T001 model values
   and return `models.PortfolioOrdering` with allocated collections.
2. Normalize the three relationship types exactly as specified, derive
   hard/soft behavior from type, and conservatively retain a hard edge unless
   it is explicitly satisfied.
3. Restrict graph edges to candidate endpoints, deduplicate directed edges, and
   retain sorted unique contributing types.
4. Run Kahn separately for hard and combined graphs with lexical frontiers and
   adjacency; never use map or input order.
5. Use the combined Kahn remainder for `UnlayeredEpics`, the hard remainder for
   `HARD_ORDER_CYCLE`, and soft-containing cyclic components for
   `ROADMAP_ORDER_CYCLE`.
6. Emit one contradiction warning per opposing pair and one missing-order
   warning per incomparable eligible pair. Do not suppress overlapping cycle
   diagnostics.
7. Detect missing order among eligible first dependency-layer roots using
   reachability in the combined roadmap graph.
8. Sort all warnings by code, joined lexical keys, and message. Allocate all
   nested slices.
9. Keep scoring, recommendation, workflow classification, repository access,
   relationship repair, and top-level warning aggregation outside this file.
