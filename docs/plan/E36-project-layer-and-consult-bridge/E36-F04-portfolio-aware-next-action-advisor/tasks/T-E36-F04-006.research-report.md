# Research report

## Scope

T-E36-F04-006 owns the service that converts live epic, descendant,
relationship, claim, and workflow evidence into `PortfolioAdviceEnvelope`.
It consumes the five completed foundation tasks and adds orchestration and
classification only. It does not read product documents, choose the next epic,
perform SQL, initialize keyed-dispatch adapters, or mutate Shark state.

## Ubiquitous vocabulary

- **Core epic evidence**: the epic list required to form any portfolio response.
- **Partial evidence**: a usable envelope whose descendant, relationship, or
  claim read failed after epics loaded.
- **Eligibility**: `eligible`, `ineligible`, or `unknown`, derived only from
  workflow and hard-precedence facts.
- **Active work**: a live, sanitized epic/feature/task claim attached to its
  owning epic.
- **Hard predecessor**: the prerequisite endpoint of an unresolved
  `depends_on` or `blocks` relationship.
- **Evidence completeness**: true only when descendant, relationship, and claim
  reads all succeed and no dangling or unknown-status evidence remains.
- **Advice prompt**: static service-owned instructions for product judgment;
  it is not a keyed dispatch prompt.

## Findings

1. The service needs four narrow dependencies: epic reader, portfolio snapshot
   reader, read-only active-claim reader, and workflow provider. The graph and
   progress helpers are pure package functions rather than injected services.
2. `Advise` captures one UTC time before reading evidence and passes it to the
   claim reader. All expiry decisions in one response therefore share a clock.
3. Epic-list failure and context cancellation are fatal. Child, relationship,
   and claim failures are independent partial-evidence conditions. Each failed
   optional read contributes one typed warning and sets `evidence_complete`
   false without discarding successful evidence from other reads.
4. Terminal epic filtering must use the configured epic workflow. A status
   absent from that workflow keeps the epic visible, marks its eligibility
   unknown, and adds `UNKNOWN_WORKFLOW_STATUS`.
5. Descendant rows provide verified ownership. Direct features determine the
   `all_direct_features_blocked` rule; a blocked child alone is evidence and
   does not disqualify the epic when another non-terminal direct feature can
   proceed. Tasks contribute blockers and active work but do not become roots.
6. Progress groups feature rows by epic and calls the shared formula. The
   public value is clamped to 0-100 and rounded to two decimal places after the
   shared calculation so analytics semantics remain unchanged.
7. Relationship rows with both endpoints resolved become public relationship
   evidence. Missing endpoints generate `DANGLING_RELATIONSHIP`, are excluded
   from graph edges, and make evidence incomplete. Terminal prerequisites
   satisfy hard edges; unresolved hard edges add blocker evidence and
   ineligibility reasons to the dependent epic.
8. Eligibility precedence is: unknown when required descendant/relationship or
   workflow evidence is unavailable; otherwise ineligible for an epic-blocked
   status, unresolved hard predecessor, or all non-terminal direct features
   blocked; otherwise eligible. Active work never changes eligibility.
9. Claims attach directly for epics and through the descendant ownership map
   for features/tasks. Standalone claims are ignored. The service copies only
   entity type/key, holder, UTC heartbeat, and nullable progress into the DTO.
10. All arrays must be allocated and sorted before returning. Epics sort by
    normalized key; relationships by from key, type, and to key; blocker and
    active-work arrays by entity type/key; reason codes lexically; warnings by
    code, joined epic keys, and message.
11. Graph analysis runs after relationship conversion and preliminary
    eligibility. Graph warnings live in `ordering.warnings`; evidence and
    workflow warnings live at the envelope level. No warning is silently used
    to invent a total order.
12. The prompt is stable text owned by this service. It instructs the receiver
    to inspect relevant `docs/product/` files, trust Shark for live state,
    respect hard precedence, recommend exactly one eligible root, compare the
    strongest alternative, report gaps instead of guessing, and stop before
    claim/dispatch/advance.
13. Service tests should mock only the four raw dependencies and call
    `PortfolioAdviceService.Advise` directly. Fail-on-call fakes prove one call
    per dependency and absence of mutation-capable methods. Complete marshaled
    outputs, not helper-only assertions, prove sanitization and sorting.

## Decisions

1. Define consumer-side interfaces in `portfolio_advice_service.go` containing
   only the exact read methods used by `Advise`.
2. Construct the service with required dependencies and return an operation-
   wrapped error for missing core epic evidence; degrade optional evidence into
   typed warnings.
3. Use configured workflow classifiers throughout. Do not hard-code terminal
   or blocked status names, except to recognize an unknown configured status.
4. Build ownership indexes once from set-oriented rows and assemble all epics
   in memory. Do not perform per-epic reads.
5. Keep eligibility as an explainable decision table with stable reason codes.
   Do not combine priority, business value, progress, or WIP into a score.
6. Invoke the pure graph analyzer once with deterministic candidate and
   relationship inputs, then preserve its layers and warnings unchanged.
7. Return the same static prompt for complete, partial, and empty portfolios;
   the prompt itself tells the receiver how to handle those conditions.
8. Cover TC-004 through TC-016 and the populated service partition of TC-019
   through the production `Advise` method. Leave CLI routing to T-007 and the
   full scale/query fixture to T-009.
