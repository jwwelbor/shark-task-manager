# Research report

## Scope

T-E36-F04-003 extracts the arithmetic already implemented by
`EpicAnalyticsService.CalculateProgress` so existing analytics and the future
portfolio service can call one pure helper. This task preserves repository
behavior, existing analytics rounding, and all current status semantics. It
does not make epic progress workflow-configurable or reconcile other progress
implementations.

## Capability map

| Capability | Source | Decision | Application |
| --- | --- | --- | --- |
| Epic progress arithmetic | `EpicAnalyticsService.CalculateProgress` | **EXTEND** | Move only the row-to-average arithmetic into an unexported package helper; keep the public method as the repository-aware wrapper. |
| Raw feature progress projection | `repository.FeatureProgressData` | **REUSE** | Keep the helper input compatible with the existing status and stored-progress row shape. |
| Cancelled-feature exclusion | `EpicAnalyticsService.CalculateProgress` | **REUSE** | Remove cancelled rows from both numerator and denominator, including the cancelled-only partition. |
| Analytics output rounding | `EpicAnalyticsService.GetProgress` | **REUSE** | Preserve `math.Round(progress*100)/100` in the caller; do not move rounding into the shared arithmetic. |
| Progress range guarantee | `Feature.Validate` and the `features.progress_pct` check constraint | **REUSE** | Treat 0-100 as an input invariant. The current arithmetic does not clamp raw rows. |
| Workflow-weighted task progress | `internal/progress.CalculateProgress` | **CONTRADICTS** | Do not reuse it; it consumes status counts and workflow weights, not stored feature percentages. |
| Completed-status helper | `status.IsFeatureCompletedStatus` | **CONTRADICTS** | Do not use it in this extraction because it counts cancelled as 100%, while the live epic formula excludes cancelled. |
| Display-data progress loop | `EpicAnalyticsService.GetDisplayData` | **CONTRADICTS** | Leave it unchanged in this task; it rounds inline and counts cancelled differently, so redirecting it would change behavior. |
| Portfolio epic progress | E36-F04 `spec.md` | **NEW** | Group snapshot feature rows by epic, call the same pure helper, then apply the portfolio output's clamp-and-round rule in T-E36-F04-006. |

## Ubiquitous vocabulary

- **Progress row**: a `FeatureProgressData` value containing one feature status
  and stored progress percentage.
- **Included feature**: any progress row whose status is not `cancelled`.
- **Forced-complete contribution**: 100 for a row whose status is exactly
  `completed` or `archived`, regardless of its stored percentage.
- **Stored-progress contribution**: the row's `ProgressPct` for every other
  included status.
- **Raw epic progress**: the arithmetic mean of included contributions before
  output rounding.
- **Range invariant**: production stored progress is 0-100 because both model
  validation and the database schema enforce that range.
- **Output rounding**: `math.Round(value*100)/100`, currently applied by
  `GetProgress` rather than by the raw calculation.
- **Semantic drift**: any change to cancellation, denominator, completed
  overrides, raw rounding, or repository-error behavior during extraction.

## Findings

1. The current formula is exact and small:
   omit rows with status `cancelled`; count `completed` and `archived` as 100;
   use stored progress for every other status; divide by the number of included
   rows. Nil, empty, and cancelled-only inputs return 0.
2. `CalculateProgress` currently combines two concerns. It calls
   `GetFeatureProgressDataByEpic`, wraps repository errors, and then performs
   pure arithmetic. Only the arithmetic can move into a reusable helper.
3. The live arithmetic does not round or clamp. `GetProgress` rounds the raw
   result to two decimals after `CalculateProgress` returns. The task and test
   plan mention “clamp,” but the live bounds come from `Feature.Validate` and
   the database `CHECK (progress_pct >= 0.0 AND progress_pct <= 100.0)`.
4. Because every valid contribution is in 0-100, the mean is already in
   0-100. Explicit clamping is redundant for repository-produced analytics
   input but remains part of the portfolio JSON output contract in T-E36-F04-006.
   Adding it to the raw helper would change behavior for fabricated or corrupt
   rows and would not be a pure extraction.
5. Status handling is intentionally not workflow-aware in the live formula.
   The generic progress package supports `ExcludeFromProgress` and weighted
   statuses, but it computes task progress from counts. Replacing the literal
   feature rules with workflow classification would change the established
   formula and require a separate product decision.
6. `status.IsFeatureCompletedStatus` is not compatible: it returns true for
   `cancelled`, while `CalculateProgress` excludes cancelled from the
   denominator. Using it would turn a cancelled-only epic from 0 into 100.
7. `GetDisplayData` contains a second inline progress loop with different
   semantics: it uses `IsFeatureCompletedStatus`, includes cancelled rows, and
   rounds immediately. No focused display-progress tests establish permission
   to change it. This task should record the divergence but not broaden the
   extraction into a behavioral fix.
8. The narrow helper can be
   `calculateEpicProgress(data []repository.FeatureProgressData) float64` in
   `epic_analytics_service.go`. It needs no context, repository, workflow
   service, model mutation, or error return.
9. `EpicAnalyticsService.CalculateProgress` should retain its signature and
   error text, fetch once, and return `calculateEpicProgress(data), nil`.
   `EpicService.CalculateProgress` continues delegating through the analytics
   service, so current callers and higher-level tests do not change.
10. The future portfolio service already receives feature rows in its bounded
    child-state snapshot. It must adapt those rows in memory and call the pure
    helper; it must not call `CalculateProgress` per epic because that would add
    N+1 repository reads.

## Decisions

1. Add one unexported pure helper in
   `internal/services/epic_analytics_service.go`:
   `calculateEpicProgress([]repository.FeatureProgressData) float64`.
2. Preserve the current algorithm exactly. Exclude literal `cancelled`, force
   literal `completed` and `archived` to 100, average stored values for all
   other statuses, and return 0 when no row remains.
3. Keep `GetFeatureProgressDataByEpic`, context handling, and wrapped
   repository errors in `EpicAnalyticsService.CalculateProgress`.
4. Keep two-decimal rounding in `GetProgress`. Do not round or explicitly clamp
   inside the pure helper. T-E36-F04-006 owns the portfolio DTO's output
   normalization.
5. Do not pass a workflow service into the helper and do not call
   `status.IsFeatureCompletedStatus` or `internal/progress.CalculateProgress`.
6. Leave the `GetDisplayData` progress loop unchanged because it has different
   live semantics and is outside this refactor's proven boundary.
7. Add `internal/services/epic_analytics_service_test.go` in package
   `services` with table-driven pure cases:
   nil, empty, cancelled-only, completed override, archived override, mixed
   statuses, stored values at 0 and 100, and a repeating-decimal raw average.
8. In the focused test, assert that the helper returns the unrounded raw value.
   Retain `TestEpicService_GetProgress` as the caller-level proof that analytics
   rounds to two decimals. Treat the requested “clamp” case as a 0/100 boundary
   invariant, not as permission to add a new clamp.
9. Keep the existing repository-error, no-feature, completed/archived, mixed,
   and rounded-output regressions in `epic_service_test.go` unchanged.
