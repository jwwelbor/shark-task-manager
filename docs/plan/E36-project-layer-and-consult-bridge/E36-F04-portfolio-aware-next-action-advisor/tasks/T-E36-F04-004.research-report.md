# Research report

## Scope

T-E36-F04-004 adds a query-only read-model repository spanning descendants and
epic relationships. The repository returns raw facts in two set-oriented reads.
It does not classify terminal statuses, calculate eligibility or progress,
normalize precedence, repair relationships, or mutate state. T-E36-F04-009
owns the full assembled 200-epic performance gate.

## Capability map

| Capability | Source | Decision | Application |
| --- | --- | --- | --- |
| Epic authority | `epic.EpicRepository.List` | **REUSE** | The portfolio service continues using the existing epic list as its first read; do not duplicate epic listing in this repository. |
| Hierarchy snapshot | `features.epic_id`, `tasks.feature_id` | **NEW** | Use one `UNION ALL` query to return all feature and task rows with resolved ownership. |
| Relationship storage | `entity_relationships` | **EXTEND** | Add one portfolio-specific endpoint-resolution query; the general relationship repository lacks endpoint keys and statuses. |
| Relationship constants | `models.EntityRelationshipType` | **REUSE** | Bind `depends_on`, `blocks`, and `follows` as parameters. |
| Repository mechanics | `entityrel.Repository` | **REUSE** | Follow `QueryContext`, deferred close, row scan, `rows.Err`, wrapped errors, and allocated-empty-slice patterns. |
| Workflow classification | E36-F04 service contract | **CONTRADICTS** | Do not filter terminal endpoints or interpret statuses in SQL. The service owns configured workflow semantics. |
| Graph normalization | E36-F04 relationship semantics | **CONTRADICTS** | Return stored direction and type unchanged. The service converts them to prerequisite edges. |
| Dangling endpoint evidence | E36-F04 error handling | **NEW** | Preserve stored endpoint IDs and nullable resolved key/status fields so the service can emit `DANGLING_RELATIONSHIP`. |
| Repository integration database | `test.GetTestDB` | **REUSE** | Use the real schema, no repository mocks, no parallel tests, and cleanup before and after every fixture. |
| Full scale proof | T-E36-F04-009 and TC-020 | **DEFER** | Keep methods to one query each and fixture helpers extensible; do not duplicate the later service-level scale gate. |

## Ubiquitous vocabulary

- **Child-state row**: one raw feature or task with its owning epic and direct
  parent resolved from the hierarchy.
- **Owning epic**: `features.epic_id` for a feature, or the epic reached through
  `tasks.feature_id -> features.epic_id` for a task.
- **Direct parent**: the epic key for a feature and the feature key for a task.
- **Feature progress**: the stored `features.progress_pct`; it is absent for a
  task rather than synthesized as zero.
- **Stored relationship direction**: the exact `from` and `to` endpoints in
  `entity_relationships`, before graph normalization.
- **Supported epic relationship**: an epic-to-epic row whose type is
  `depends_on`, `blocks`, or `follows`.
- **Resolved endpoint**: a stored endpoint ID that matches a current `epics`
  row and therefore has a key and status.
- **Dangling endpoint**: a stored epic endpoint ID with no matching epic row.
  The schema permits this because the polymorphic table has no endpoint foreign
  keys.
- **Set-oriented read**: one SQL query that loads the complete relevant set,
  rather than one query per epic.

## Live schema evidence

The current schema provides these exact columns:

- `epics`: `id`, `key`, `title`, `status`, `priority`, and `business_value`
  among the wider epic record.
- `features`: `id`, `epic_id`, `key`, `title`, `status`, and `progress_pct`.
  `epic_id` has a foreign key to `epics.id` with cascade deletion.
- `tasks`: `id`, `feature_id`, `key`, `title`, and `status` among the wider task
  record. `feature_id` has a foreign key to `features.id` with cascade deletion.
- `entity_relationships`: `from_entity_type`, `from_entity_id`,
  `to_entity_type`, `to_entity_id`, and `relationship_type`. The final rebuilt
  table constrains relationship types and uniquely identifies a stored edge by
  both typed endpoints plus type, but it has no foreign key from either
  polymorphic endpoint ID to an entity table.

The lack of endpoint foreign keys is not an unresolved schema issue. It is a
required query consideration: an inner join would silently discard malformed
stored evidence and make the specified `DANGLING_RELATIONSHIP` warning
impossible.

## Raw row contracts

Use narrow repository-owned row structs. No JSON or persistence tags are
needed. The precise shapes should be equivalent to:

```go
type ChildStateRow struct {
	EpicID          int64
	EpicKey         string
	EntityType      models.EntityType
	EntityKey       string
	Title           string
	Status          string
	DirectParentKey string
	ProgressPct     *float64
}

type EpicRelationshipRow struct {
	FromEpicID      int64
	FromKey         *string
	FromStatus      *string
	RelationshipType models.EntityRelationshipType
	ToEpicID        int64
	ToKey           *string
	ToStatus        *string
}
```

`ProgressPct` is non-nil only for feature rows. The relationship IDs are the
stored IDs and remain present even when resolution fails; endpoint key and
status are nullable. A child entity ID is not required by the specification or
the downstream service and should not be added speculatively.

## Query design

### Descendant snapshot

Use one `UNION ALL` query with ownership joins:

```sql
SELECT e.id AS epic_id,
       e.key AS epic_key,
       ? AS entity_type,
       f.key AS entity_key,
       f.title AS title,
       f.status AS status,
       e.key AS direct_parent_key,
       f.progress_pct AS progress_pct
FROM features f
JOIN epics e ON e.id = f.epic_id
UNION ALL
SELECT e.id AS epic_id,
       e.key AS epic_key,
       ? AS entity_type,
       t.key AS entity_key,
       t.title AS title,
       t.status AS status,
       f.key AS direct_parent_key,
       CAST(NULL AS REAL) AS progress_pct
FROM tasks t
JOIN features f ON f.id = t.feature_id
JOIN epics e ON e.id = f.epic_id
ORDER BY epic_key ASC, entity_type ASC, entity_key ASC
```

Bind `models.EntityTypeFeature` and `models.EntityTypeTask`; do not interpolate
even fixed filter values when parameters are available. `UNION ALL` preserves
one row per entity and avoids unnecessary deduplication. Inner joins are correct
here because the schema enforces descendant ownership. Scan progress with
`sql.NullFloat64` and convert valid values to pointers explicitly.

The lexical entity-type order currently places features before tasks. The
contract requires ordering by entity type, not a custom type rank, so no `CASE`
expression is needed.

### Epic relationships

Use one endpoint-resolution query:

```sql
SELECT er.from_entity_id,
       from_epic.key,
       from_epic.status,
       er.relationship_type,
       er.to_entity_id,
       to_epic.key,
       to_epic.status
FROM entity_relationships er
LEFT JOIN epics from_epic ON from_epic.id = er.from_entity_id
LEFT JOIN epics to_epic ON to_epic.id = er.to_entity_id
WHERE er.from_entity_type = ?
  AND er.to_entity_type = ?
  AND er.relationship_type IN (?, ?, ?)
ORDER BY COALESCE(from_epic.key, '') ASC,
         er.relationship_type ASC,
         COALESCE(to_epic.key, '') ASC,
         er.from_entity_id ASC,
         er.to_entity_id ASC
```

Bind, in order, `models.EntityTypeEpic` twice and the three supported
relationship constants. Scan endpoint key and status through `sql.NullString`
and convert them to pointers. The ID tie-breakers make multiple dangling rows
deterministic even when their unresolved keys compare equally.

Do not add endpoint-existence or terminal-status predicates. The repository
must return every stored supported epic-to-epic relationship. The service later
retains relationships with at least one returned non-terminal endpoint,
classifies satisfaction, omits malformed edges from layers, and emits warnings.

## Relationship semantics boundary

The repository preserves all three stored forms exactly:

| Stored row | Later service precedence | Repository behavior |
| --- | --- | --- |
| `A depends_on B` | `B -> A`, hard | Return `A`, `depends_on`, `B` unchanged. |
| `A blocks B` | `A -> B`, hard | Return `A`, `blocks`, `B` unchanged. |
| `A follows B` | `B -> A`, soft | Return `A`, `follows`, `B` unchanged. |

Filtering to these types is repository work. Reversing endpoints, checking
configured terminal state, deciding satisfaction, deduplicating normalized
edges, and building layers are service work.

## Error and empty-result behavior

Each method should:

1. Call `QueryContext` exactly once.
2. Wrap the initial query error with the operation name.
3. Defer `rows.Close` immediately after a successful query.
4. Wrap row-scan errors with the operation name.
5. Check and wrap `rows.Err` after iteration.
6. Initialize the result as an allocated empty slice so JSON-facing service
   assembly does not inherit a nil collection.

Context cancellation flows through `QueryContext` and `rows.Err`. Neither
method should turn partial iteration into a successful partial snapshot.

## Real-database test design

Create focused tests in `internal/repository/portfolio/repository_test.go` with
`test.GetTestDB()` and `dbconn.NewDB(database)`. Do not use `t.Parallel` against
the shared package database.

Use a fixture-specific key prefix rather than `test.SeedTestData`, because the
snapshot methods intentionally read all rows and need multiple independently
controlled epics. Seed with direct parameterized SQL so the fixture can express
stored relationship forms, including a dangling endpoint that the public
relationship service would reject.

### Child-state evidence

Seed at least two epics, multiple features, and multiple tasks in deliberately
non-lexical insertion order. Assert:

- every feature and task appears exactly once;
- each row has the correct owning epic ID/key;
- a feature's direct parent is its epic and a task's direct parent is its
  feature;
- feature progress is non-nil with its exact stored value and task progress is
  nil;
- status, title, type, and key are raw database values;
- two calls return identical `epic key, entity type, entity key` ordering;
- an empty fixture produces an allocated empty slice when no unrelated package
  fixture is present.

### Relationship evidence

Seed epic-to-epic `depends_on`, `blocks`, and `follows` rows in non-lexical
insertion order. Also seed `related_to`, a cross-entity supported type, a row
whose endpoints include terminal statuses, and a supported row with one missing
epic endpoint. Assert:

- all three supported epic-to-epic forms are present in stored direction;
- unsupported and non-epic rows are absent;
- resolved IDs, keys, and statuses are exact;
- terminal endpoints remain present for service-side satisfaction handling;
- the dangling row retains both stored IDs and has nil key/status only for the
  missing endpoint;
- repeated calls return the exact documented order.

Snapshot relevant table counts before and after repeated read calls to provide
a direct no-write regression. Source review establishes one query per method;
T-E36-F04-009 owns the assembled four-read counter and time threshold.

## Fixture cleanup

Call one checked cleanup helper before seeding and through `t.Cleanup`. Use the
fixture key prefix or captured IDs and delete in reverse dependency order:

1. Delete fixture `entity_relationships` rows whose typed endpoints reference
   fixture epic IDs, including rows with the deliberately missing endpoint.
2. Delete fixture tasks.
3. Delete fixture features.
4. Delete fixture epics.

Relationship cleanup must occur first because the table has no endpoint foreign
keys or cascade behavior. Do not ignore cleanup errors; a leaked relationship
can become dangling evidence in a later test. Tests should filter returned rows
to their fixture prefix for exact assertions, while still cleaning before and
after so future T-E36-F04-009 helpers can share the file safely.

## Findings

1. The new repository is justified despite the normal entity-specific package
   split: each result is a read model across multiple tables, and moving these
   joins into the service would create the prohibited per-epic read pattern.
2. `ListChildStates` can meet its contract in one `UNION ALL` statement. The
   hierarchy foreign keys make ownership resolution exact and eliminate a need
   for orphan-child policy in this task.
3. `ListEpicRelationships` cannot use inner joins without violating the
   feature's error contract. The schema intentionally permits dangling
   polymorphic IDs, while the service must identify and warn about them.
4. The general relationship repository returns typed IDs but not endpoint keys
   or statuses. Calling it once and then resolving endpoints individually would
   be N+1; extending it is less cohesive than the bounded portfolio read model.
5. The repository must not prefilter terminal epics. Terminal classification is
   workflow-configurable, and terminal endpoints are required to determine
   whether hard relationships are satisfied.
6. Determinism requires SQL ordering even though the graph service also sorts.
   The child contract provides its exact primary sort, while relationship IDs
   provide stable tie-breakers for unresolved endpoints.
7. No migration or index is required. Both queries read the complete relevant
   set, join hierarchy and endpoint primary keys, and use existing relationship
   indexes for the bounded type filter.
8. A repository-only query-count abstraction is unnecessary for this task and
   would broaden `dbconn.DB`. The implementation itself has one `QueryContext`
   per method, and T-E36-F04-009 provides the full observational read budget.

## Decisions

1. Create `internal/repository/portfolio/repository.go` with a `Repository`
   holding `*dbconn.DB` and a `NewRepository` constructor.
2. Define the two raw row structs in that package with nullable feature progress
   and nullable resolved relationship endpoint fields.
3. Implement child loading as one parameterized `UNION ALL` query with inner
   hierarchy joins and order by epic key, entity type, and entity key.
4. Implement relationship loading as one parameterized query with left joins,
   supported type filtering, no status filtering, and deterministic key/type/ID
   ordering.
5. Preserve stored relationship direction and type. Apply no workflow,
   progress, eligibility, deduplication, or graph rules in the repository.
6. Return allocated empty slices and wrapped query, scan, and iteration errors.
7. Add real-DB tests for exact hierarchy rows, exact relationship rows,
   unsupported/cross-type exclusion, terminal retention, dangling endpoints,
   deterministic calls, no writes, and checked cleanup before and after.
8. Keep fixtures non-parallel and extensible for T-E36-F04-009, but leave its
   full service assembly, exact scale, four-read counter, and one-second gate to
   that task.
