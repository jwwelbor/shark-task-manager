# Make claim/lease TTL configurable via .sharkconfig.json (0 = never expires)

## Description

Claim/lease TTL is hardcoded (DefaultClaimTTL=15min) with an env-var override only (SHARK_CLAIM_TTL_SECONDS). Add a claim_ttl_seconds (or similar) field to .sharkconfig.json read by ClaimService; if set to 0, leases should never expire (skip IsExpired/ReclaimExpired logic for that check). Discovered while explaining why release sometimes appears automatic (TTL expiry + lazy sweep on next claim/list call, not an actual auto-release).

## Justification

Default 15-minute claim TTL (internal/services/claim_service.go DefaultClaimTTL, only overridable via SHARK_CLAIM_TTL_SECONDS env var) may be too short for some workflows; users need a durable, project-level way to tune or disable lease expiry.

## Impact Analysis

**Current behavior** (`internal/services/claim_service.go`):
- `DefaultClaimTTL = 15 * time.Minute` (line 21).
- `NewClaimService(repo, ttl)` treats any `ttl <= 0` as "unset" and falls back
  to `claimTTLFromEnv()` (line 45), which reads `SHARK_CLAIM_TTL_SECONDS` or
  else `DefaultClaimTTL`. This means `0` cannot currently mean "never expire"
  — it already means "use the default."
- `cli.GetClaimService()` (`internal/cli/services_global.go:723`) always calls
  `NewClaimService(claimrepo.NewRepository(db), 0)` — there is no config-file
  plumbing today, only the env var.
- TTL is consumed by `IsClaimable`/`IsExpired` (read-only check used by `shark
  next` and `shark claim`) and by `ReclaimExpired` (sweep run at the top of
  `Claim` and `List`).

**Proposed change:**
- Add a config field (e.g. `claim_ttl_seconds *int` in `internal/config/config.go`,
  following the existing `*int`/`*bool` optional-field pattern used by
  `BackupFiles`/`ColorEnabled`) to `.sharkconfig.json`.
- Resolution order: `.sharkconfig.json` field → `SHARK_CLAIM_TTL_SECONDS` env
  var → `DefaultClaimTTL`.
- Distinguish "not configured" (nil/absent → fall through to next source)
  from "explicitly 0" (never expire) — this requires changing the `ttl
  time.Duration` parameter on `NewClaimService` to something that can carry
  a tri-state (e.g. `*time.Duration`, or a sentinel constant), since today
  `ttl <= 0` is overloaded to mean "unset."
- When TTL resolves to "never expire," `IsExpired`/`ReclaimExpired` must
  short-circuit to "never expired" rather than comparing against a zero
  duration (which would currently mean "always expired instantly").
- Update `claimTTLFromEnv` (or its replacement) and `cli.GetClaimService` to
  read the new config field.
- Docs to update: `docs/guides/route-based-workflow.md` §4 (currently states
  "TTL defaults to 15 minutes (`SHARK_CLAIM_TTL_SECONDS` to override)").

**Risk:** Low — additive config field, backward compatible (absence preserves
today's env-var/default behavior). Main risk is the tri-state plumbing
(nil vs 0 vs positive) touching `NewClaimService`'s signature, which has a
few call sites (`services_global.go`, tests).

## Rollback Plan

Revert the config field and `ClaimService`/`GetClaimService` changes; the env
var and hardcoded default keep working unchanged since they remain the
fallback path. No data migration involved — TTL is resolved in-memory per
process, not persisted per-claim.
