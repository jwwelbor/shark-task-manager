# Hybrid embed/disk content-bundle resolution (embed default → install-shark-data → external bundle)

## Description

Move shark's content-bundle distribution from 'embedded-but-runtime-reads-disk-only' to a hybrid embed/disk model so content (prompts/skills/agents/workflow) and the engine evolve on different clocks. Today the bundle is embedded in the binary (internal/sharkdata/default_data) but materialized to disk via shark init, and the runtime resolver reads ONLY from disk; the committed shark-data/ tree has drifted from the embedded canonical copy.

## Justification

Prompts iterate faster than the engine; embedding forces a rebuild+release per tweak. Embed should be a zero-config seed; explicit extraction makes disk authoritative for active authoring. Structurally eliminates the committed-shark-data drift bug. Version-coupling concern is minor (only the .json->.yaml major boundary).

## Proposed Model

Per-file resolution precedence (generalizes the embed-then-filesystem fallback
already shipping in `internal/templates/loader.go`):

1. Explicit external bundle (`shark_data_path` / absolute `workflow_config`) — wins
2. Extracted `<project>/shark-data/` (if present) — wins
3. Embedded default — backstop

Three modes fall out:
- **Consumer / zero-config:** nothing on disk → pure embed. `go install` works
  offline, no `init` step.
- **Author / customizer:** `shark install-shark-data` extracts the embedded tree
  to disk; disk becomes authoritative per-file (embed backstops missing files),
  editable and git-trackable with no rebuild.
- **Independent-cadence:** point `shark_data_path` at a separate content repo —
  the hybrid extends here later without a second distribution channel now.

## Scope (touch points — breadcrumb, not a spec)

- Make the runtime resolver embed-aware (`internal/templates` loader + the
  workflow loader), applying the precedence above.
- New `shark install-shark-data` command: extract embedded tree → disk
  authoritative (per-file, embed as backstop).
- Diff-first `shark upgrade`: show what a new binary would change vs. the user's
  disk copy; merge selectively rather than silently overwrite/mask.
- `shark skill resolve|get|list`: serve content to the ~6 `/shark` verbs that
  currently `Read` whole skill packages from disk (vision, product-design,
  revalidate, project-init, update-docs, triage). Package-granularity,
  override-merged.
- Default: gitignore `shark-data/` (keep `overrides/`). The committed, drifted
  copy stops masquerading as a source of truth.
- Keep the `/shark` ROUTER files (`skills/shark/SKILL.md`, `verbs/`, `context/`)
  out of scope — they are the harness bootstrap, not content-bundle content.

## Impact Analysis

- Config semantics shift slightly (precedence + meaning of an on-disk
  `shark-data/`). Existing absolute `workflow_config` / `shark_data_path` users
  unaffected (still highest precedence).
- Engine gains an embed dependency in the resolver (already present in the
  `sharkdata` package and in `loader.go` for task templates).
- One ongoing maintenance surface introduced: after extraction, a binary upgrade
  can carry improved embedded content that the disk copy masks — handled by the
  diff-first `upgrade`.
- Two independent advisory reviews (architect + cx-designer) favored the
  self-contained direction; this change-card adopts the user-refined hybrid,
  which downgrades the "version coupling" rationale they leaned on (deemed minor
  here).

## Rollback Plan

Each piece is independently shippable and reversible. The gitignore +
de-commit of `shark-data/` is safe on its own. If the embed-aware resolver
regresses, revert it and fall back to the current init-materialize behavior; the
embedded tree remains the canonical source either way.

## Implementation Notes (added 2026-06-25)

### Current broken state

Two diverged init commands exist and both are wrong:

**`shark admin init`** (`internal/cli/commands/init.go`) — Shark 1.x legacy.
Copied `shark-templates/` from the old root embedded template FS, created
`docs/plan/`, and wrote `.sharkconfig.json`. It was not connected to
`shark-data/` at all.

**`shark init`** (`internal/cli/commands/sharkdata_cmd.go`) — Shark 2.0
(E32-F03). Materializes `shark-data/` from `internal/sharkdata/default_data/`
via `sharkdata.InitAt()`. Correct bundle, wrong model: still disk-first
(refuses to run if `shark-data/` exists, tells you to run `shark upgrade`).
This is not the hybrid embed-backstop model CC-039 calls for.

### What must die: `shark-templates/`

The `shark-templates/` tree and its embedding machinery are entirely
superseded by `shark-data/`. Remove:

- root-level template embed declarations that pointed at the legacy tree
- `shark-templates/` directory tree (`.sharkworkflow*.json`, `task/`,
  `feature/`, `epic/`, `partials/`, etc.)
- `internal/init/templates.go` — the `copyTemplates` function that walked
  the old root template embed and synced it to disk
- `internal/init/types.go`, `initializer.go` to the extent they reference
  the legacy template tree
- `internal/config/config.go` `DefaultTemplateDir = "shark-templates"`
- Legacy fallback in `internal/templates/orchestrator_renderer.go` — the
  `shark-templates/` pass (Pass 2 in `findTemplateDir`) and
  `defaultTemplateDir = "shark-templates"`
- Legacy shim in `internal/templates/includes.go` (the `shark-templates/`
  mode comment block)
- Legacy reference in `internal/cli/commands/next.go` (line ~537)
- Legacy references in `internal/config/aliases.go` (workflow loader
  `shark-templates/.sharkworkflow*.json` fallback paths)
- `shark admin init` itself — its only surviving responsibility (database
  setup + `docs/plan/` folders) should either be absorbed into a slimmed
  `shark admin init` with no content-bundle concerns, or left as a DB-only
  setup subcommand

### What `shark init` becomes

Under CC-039, `shark init` should become `shark install-shark-data` (an
explicit "I want to customize" opt-in), and the runtime resolver should
serve content directly from the embed when no `shark-data/` is present —
no init step required. Until the resolver is embed-aware, `shark init`
stays but its error-on-already-initialized behavior should soften (idempotent
no-op or redirect to `shark upgrade`).

### Sequencing suggestion

1. **Remove `shark-templates/` and its embedding** — standalone, no
   behavioral regression if `shark-data/` is the live resolver path.
   Fixes the `shark admin init` drift immediately.
2. **Make the runtime resolver embed-aware** — `internal/templates/loader.go`
   already has the pattern; extend to workflow loader and prompt resolver.
3. **Rename `shark init` → `shark install-shark-data`** + soft-deprecate
   `shark admin init` (keep as thin DB+folders setup only).
4. **`shark upgrade` diff-first merge** — already partially landed (E32-F03),
   needs the embed-backstop to be meaningful.
