# Prevent back-to-back status advances without executing orchestrator_action

## Description

## Problem

Agents are running `shark status advance` back-to-back without executing the orchestrator_action between transitions. This silently blows tasks through entire workflow phases (refinement → development → code review → QA → approval) with no work actually performed.

## Evidence (from wormwoodGM)

- **T-E15-F02-001**: 4 transitions in **3 seconds** (2026-01-04T04:34:29 → 04:34:32), moving draft → ready_for_refinement → in_refinement → ready_for_development → in_development. Followed by a real 82-minute dev gap — proving the first four were no-ops.
- **T-E17-F08-001**: 9 transitions across the entire pipeline in ~24 minutes. Includes code_review → ready_for_qa in **3 seconds** and qa → ready_for_approval in **3 seconds**.
- **T-E17-F08-002/003/004**: Same pattern — suspicious 2-3 second gaps between supposed work phases.

## Root causes

1. **`advance` dumps orchestrator_action inline in stdout.** Agent reads it as "output of a command I already ran" rather than "next instructions to execute." Too easy to skim and move on.
2. **Instruction body ends with `## EXIT — REQUIRED\n    shark status advance <key>`.** The last line the agent visually processes is "run advance again" — which it does reflexively, skipping the middle.
3. **"RESUME CONTEXT: already in an in_progress status" preamble fires on fresh transitions.** It primes the agent to think "maybe this is already done" even when shark transitioned the entity one second ago. Misleading for non-resume scenarios.
4. **No guard rail.** Nothing prevents `advance` from succeeding twice in 3 seconds with no notes, no activity, and no intervening work.

## Proposed fixes (ranked)

**1. Stop inlining orchestrator_action in `advance` output.** `advance` should print only the transition confirmation. Force agents to run `shark get <key> --field orchestrator_action` as a separate deliberate step. Highest-leverage change: breaks the "glance and re-run" reflex and makes reading instructions a conscious act.

**2. Fix the resume preamble.** Only emit "RESUME CONTEXT" when the transition timestamp is >N minutes old or when the entity was already in the target in_progress status before the CLI call. Freshly-transitioned entities get the normal instruction.

**3. Drop the trailing `## EXIT — REQUIRED: shark status advance` from instruction bodies.** Move exit guidance to the top or frame it as "After completing the work above, exit with: ...".

**4. Optional soft guard in shark.** Refuse `advance` when the previous transition on the same entity was <30s ago and no notes were added between — unless `--force` is passed. Belt-and-suspenders safety net.

## Recommendation

Do #1 and #2 together as the minimum surgical fix. #3 is a cheap cleanup worth bundling. #4 can be added later if behavior still leaks through.

## Acceptance criteria

- `shark status advance` output no longer contains the full orchestrator_action instruction body
- Resume preamble only fires for genuine resume scenarios (not fresh transitions)
- Spot-check of new status history on active wormwoodGM tasks shows no <10s gaps between workflow phases that should involve real work
