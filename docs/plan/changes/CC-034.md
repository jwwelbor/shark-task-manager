# Replace home-rolled migration system with a proper migration library

## Description

The migration system in `internal/db/db.go` is fully home-rolled. Key characteristics of the current implementation:

- ~3,400-line `db.go` file with `runMigrations()` switchboard at line 508 calling individual `migrateXxx` Go functions in implicit order.
- Tracking is a single `schema_version` table holding only the latest version int (no per-migration applied/pending record).
- The `schema_version` table is itself outside the migrations system — created lazily by `setSchemaVersion()` (`db.go:478-493`).
- `CurrentSchemaVersion` constant in Go code is the source of truth for what "current" means; bumping it on the next command triggers `ApplySchemaAndMigrations`.
- Idempotency is the only safety net: every migration uses `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` / `CREATE TRIGGER IF NOT EXISTS`, so re-running is safe.
- `skip_migrations` flag in `.sharkconfig.json` selects between two paths in `internal/dbinit/init.go:200-208`:
  - `false` → `ApplySchemaAndMigrations` (unconditional DDL, ~2-3s on Turso every command)
  - `true` → `ApplySchemaIfNeeded` (one cheap `SELECT version` query; runs full DDL only when stored version is behind `CurrentSchemaVersion`)

## Justification

Maintainability and correctness, no direct user value:

- **No per-migration tracking.** Can't answer "which of the 22+ migrations actually ran on this DB?" — only "are we at version N?"
- **Partial-failure detection is impossible.** If a migration fails halfway, the next run silently retries (relying on idempotency); detecting bad state requires manual inspection.
- **Implicit ordering.** Migration order is whatever order `runMigrations` calls them. No deterministic filename-based sort.
- **No rollback.** No `down` migrations.
- **No CLI affordance.** Can't ask "what's pending?" or "what's applied?" without reading code.
- **Operational confusion.** The semantics of `skip_migrations` and `CurrentSchemaVersion` are non-obvious enough that B013 was filed last week to verify the docs against the code (resolved — docs are correct, but the fact that verification was needed is itself a smell).

## Proposed Direction

Baseline approach (no historical migration conversion):

1. Keep existing schema-creation code as the **baseline** for fresh installs (effectively the v15 schema-create path minus `runMigrations()`).
2. Add chosen migration library with an empty migrations directory.
3. On startup, after baseline creation, stamp the library's tracking table — instant no-op for existing v15 DBs, clean starting point for the future.
4. New migrations from this point forward live as `NNN_name.sql` (or equivalent) under `internal/db/migrations/`.
5. Replace `ApplySchemaIfNeeded` / `ApplySchemaAndMigrations` startup wiring. Delete `setSchemaVersion`, `getSchemaVersion`, `CurrentSchemaVersion`, `skip_migrations` flag, and the `migrateXxx` historical functions.

## Open Research Questions

This change-card is **research-gated**. No implementation until these are answered:

### Tooling

1. **Tool selection.** Candidates: goose (`github.com/pressly/goose/v3`), golang-migrate, atlas. Evaluate against:
   - Pure-Go runtime (no external CLI required at app startup)
   - `embed.FS` support for shipping migrations in the binary
   - Compatibility with `database/sql` + libsql/Turso driver
   - Active maintenance and adoption
2. **libsql/Turso compatibility.** Does the chosen tool work cleanly against Turso's libsql driver, or does it assume vanilla SQLite/Postgres? Spike required.
3. **Startup-cost characteristics.** Today's `skip_migrations: true` path is a single `SELECT` round-trip. Does the chosen tool match that, or does it do more work on every startup? Important for cloud-DB perf.

### Migration authoring model

4. **SQL-first or code-first?** The user's framing question — does the tool work like EF Migrations in C# (code-first, schema inferred from models), or is it schema/SQL-first (you write the DDL by hand)?
   - goose: SQL-first by default (with optional Go migrations for data backfills)
   - golang-migrate: SQL-first
   - atlas: declarative schema-as-code (you describe target state, it diffs)
5. **Generation/scaffolding.** Does the tool generate migration boilerplate (timestamp + name) or is filename creation manual? Does it generate diffs from a model layer (atlas-style) or is every migration handwritten?

### ORM relationship

6. **Does the tool work with an ORM, or is it independent?** Goose/golang-migrate are migration-only — orthogonal to ORMs. Atlas can integrate with ORMs (gorm, ent) for schema-from-models flows.
7. **Should we adopt an ORM at the same time?** Current codebase uses raw `database/sql` with hand-written queries (good Go convention, no ORM). ORM landscape to evaluate:
   - `sqlc` — generates type-safe Go from SQL queries (most idiomatic; not really an ORM)
   - `ent` — Facebook, code-first graph schema, code-generation heavy
   - `gorm` — most popular, runtime reflection, often considered un-Go-idiomatic
   - `bun` — query builder + light ORM, less reflection
   - `sqlboiler` — code-gen from existing schema
8. **Recommendation likely**: keep ORM decision **separate from** migration decision. Migration tool can be picked and shipped without committing to an ORM. ORMs are a much bigger paradigm shift and warrant their own change-card.

### Bridging existing DBs

9. **Stamping strategy.** How exactly do we mark existing v15 DBs as "baselined" without re-running anything? Each candidate tool has a different mechanism (goose has `goose up` with no migrations; golang-migrate has `force` to set version). Spike each.
10. **Test matrix.** Fresh local SQLite, fresh Turso, existing v15 local, existing v15 Turso — all four must pass with no destructive behavior.

### Failure-mode changes

11. **Loss of "re-run is always safe" property.** Today, every migration is idempotent so unconditional re-runs are harmless. A real migration tool enforces exactly-once and a partial failure leaves a known-bad state. This is *correct* behavior but it's a change in failure semantics — what's the operational story when a migration fails on a customer's Turso DB?

## Impact Analysis

**Affected code:**
- `internal/db/db.go` (heavy — `runMigrations`, all `migrateXxx`, `ApplySchemaIfNeeded`, `setSchemaVersion`, `getSchemaVersion`, `CurrentSchemaVersion`)
- `internal/dbinit/init.go:200-208` (startup path)
- `internal/db/config.go` (`SkipMigrations` field)
- `internal/init/types.go`, `internal/init/config.go` (`.sharkconfig.json` schema)
- `.claude/rules/database-critical.md` (docs)
- `CLAUDE.md` (docs)
- Existing `.sharkconfig.json` files in user projects (config migration / removal of `skip_migrations`)

**Affected docs:**
- Database-critical rules — entire "MIGRATIONS AND skip_migrations FLAG" section to be replaced
- `CLAUDE.md` migration-related guidance
- TURSO_QUICKSTART.md / TURSO_MIGRATION.md — any references to `skip_migrations`

**Behavior changes for users:**
- One-time stamp on first run after upgrade (transparent, no action needed)
- `skip_migrations` flag becomes a no-op (warn or silently ignore?)
- New mental model for adding migrations: write `NNN_name.sql`, ship — no `CurrentSchemaVersion` bump, no flag toggle ritual

## Rollback Plan

If the new migration system fails in the wild after rollout:

1. **Pre-rollout safeguard.** Tag the release immediately before this change. Existing DBs at v15 still work with the old code via `git revert`.
2. **Forward-only data risk.** None expected — baseline approach doesn't touch existing data; stamping is metadata-only.
3. **Reverting is safe** as long as no new migrations have been authored under the new system. After the first new migration ships, rollback would require either:
   - Hand-converting that migration into a `migrateXxx` function in the old system, or
   - Forward-fixing rather than reverting.
4. **Recommend:** ship the swap as one PR with no new migrations, soak for one release cycle, then start authoring new migrations under the new system.
