# Restore progress-driven project bootstrap and rename the skill to Shark Rider

## Description

Restore project bootstrap as the progress-driven coordinator for local Shark setup, project parameters, greenfield or brownfield discovery, product-design, and architecture integration. Rename the host skill to Shark Rider so Rider actions remain distinct from Shark CLI commands throughout that flow.

## Decision summary

Amend the completed [E36-F02 project namespace and progress record](../E36-project-layer-and-consult-bridge/E36-F02-project-namespace-and-progress-record/feature.md) instead of creating an unparented feature.

This change makes two connected corrections:

1. `/shark-rider project bootstrap` becomes the single, resumable coordinator for one-time project setup. It prepares the local Shark instance, establishes project parameters, creates or refreshes `docs/product/progress.md`, and coordinates the appropriate product-design, brownfield-analysis, and architecture activities.
2. Rename the host-side `shark` skill to **Shark Rider** (`shark-rider`) so users and agents can distinguish Rider actions from commands sent to the `shark` CLI.

The resulting boundary is:

| Surface | Example | Responsibility |
|---|---|---|
| Shark CLI | `shark <command>` | Own project data, configuration, entities, statuses, leases, workflow routing, content retrieval, and prompt assembly. Within a Rider-controlled flow, the owning Rider action is its adapter. |
| Shark Rider action | `/shark-rider project product-design` | Provide the stable coordination interface. Its `verbs/*.md` implementation owns any required CLI commands. |
| Bundle skill | `product-design` | Provide methodology or workflow content to its owning Rider action. It does not invoke the CLI. |
| Shark agent | Configured agent definition | Provide a role and instructions to its owning Rider action. It does not invoke the CLI. |

`shark admin init` remains the low-level, idempotent CLI mechanism. Rider bootstrap invokes or validates it as part of the larger setup experience; it does not replace or rename it.

Within Rider-controlled execution, coordinators and bundle workflows dispatch Rider actions rather than invoking the CLI or retrieving another skill directly. For example, bootstrap dispatches `/shark-rider project product-design`; the product-design Rider action is the single place that owns how it loads the product-design bundle content. This adapter boundary keeps a CLI command change local to one verb file.

## Justification

E36-F02 shipped `/shark project` as a menu of independent activities and narrowed `bootstrap` to architecture document generation. That interpretation conflicts with the intended startup experience: bootstrap should establish the local project environment and then coordinate product and technical discovery until the project is ready for epic work.

The current separation creates several failures:

- Agents can generate a prescriptive architecture stack before they understand the product problem or user needs.
- Product-design and brownfield-analysis only update `progress.md` after a whole activity completes, so an interrupted run loses its durable setup checkpoint.
- The setup tracker omits most D01-D14 and brownfield-analysis outputs and cannot show meaningful partial progress.
- The current `track` value conflates the state of the repository with the intent of the initiative. An existing monorepo can contain a greenfield capability, and a brownfield initiative can extend, modernize, or replace rather than accept the current stack as fixed.
- The slash skill and the CLI are both called “shark,” which causes instructions such as “run shark” to be interpreted inconsistently.

The change keeps Shark as the source of truth for managed work while restoring `docs/product/progress.md` as the durable, human-facing project setup tracker.

## Current behavior and confirmed gaps

### Project dispatch is a menu, not a coordinator

`skills/shark/verbs/project.md` currently says the three project activities are independent and that bootstrap only generates architecture documents. It seeds or updates the progress record only after an activity completes.

The embedded `research/workflows/bootstrap.md` also defines its purpose and outputs around `docs/architecture/`. It returns `host_state_status`, but no active host procedure interprets that value as a setup coordination state.

### Progress tracking is incomplete

`file_templates/progress.md` currently tracks only:

- the `docs/architecture/` directory;
- `tech-stack.md`;
- D01 vision; and
- D04 feasibility.

The shipped template omits the informative `track`, `stack_summary`, and `artifact_paths` frontmatter planned in E36-F02. The update procedure also omits the planned `[~]` partial state.

Neither the product-design bundle skill nor the standalone brownfield-analysis skill defines a checkpoint update after each durable output. A run can therefore create D01 and D02, stop, and leave `progress.md` unchanged.

### Greenfield architecture commits too early

The current greenfield readiness-3 path can generate a full set of prescriptive architecture documents before D01 has defined the vision. The workflow labels those documents provisional, but the progress parser only recognizes the exact string `Greenfield — Provisional placeholder`. Readiness-3 documents use a different `Provisional` marker, so the progress record can incorrectly label the stack as finalized.

The current loop also reconciles the stack after D04 and resumes product-design at D05. The scaffold can consume D07 user needs, but the normal route commits before D07 exists. In addition, the product-design host triggers reconciliation only for `feasible with changes` or `not feasible`; a `feasible as described` verdict can leave provisional markers in place indefinitely.

### Brownfield is treated as fixed rather than evidenced

D01 asks whether an existing stack is a hard constraint, but D04 currently treats every brownfield stack as fixed and routes gaps to technical debt. This collapses distinct initiative postures. A current stack is observed evidence and a starting baseline; it becomes a binding constraint only when the user or business context makes it one.

## Design principles

1. **Bootstrap owns setup coordination.** Child activities can still run directly, but bootstrap owns the end-to-end, resumable setup experience.
2. **Architecture participates early and commits late.** Technical constraints and options inform discovery; target architecture becomes final only after product evidence supports it.
3. **Separate estate from intent.** Detect `greenfield` or `brownfield` repository estate independently from whether the initiative will create, extend, modernize, or replace a capability.
4. **Derive status from evidence.** Rider refreshes the setup checklist from files, configuration, and other observable state. It never trusts a checkbox as authoritative input.
5. **Record only irreducible decisions.** Human choices, approvals, reasons, and deferrals belong in the append-only decision log.
6. **Checkpoint durable work immediately.** Product-design and brownfield-analysis update the shared tracker after each durable artifact or analysis area, not only at the end of the parent activity.
7. **Keep recurring work in Shark.** Bootstrap tracks one-time project readiness. Infrastructure maintenance, migrations, and other recurring or schedulable work remain epics, features, tasks, bugs, tech debt, or change-cards.
8. **Route through Rider actions.** Coordinators and bundle workflows dispatch `/shark-rider ...` actions. Only the owning `verbs/*.md` action adapter invokes the CLI; bundle skills return content or outcomes without invoking it.
9. **Use one term per control surface.** Documentation says “CLI command,” “Rider action,” “bundle skill,” or “Shark agent”; it does not use “shark verb” when the intended surface is ambiguous. A verb file is the implementation of a Rider action, not a CLI command.

## Target project bootstrap flow

```text
/shark-rider project bootstrap
  0. Inspect and prepare the local Shark instance
  1. Seed or refresh docs/product/progress.md
  2. Confirm project parameters and record decisions
  3. Select the greenfield or brownfield estate branch
  4. Coordinate product and technical discovery with checkpoints
  5. Run the architecture integration and approval gate
  6. Derive setup completion and hand off to the first epic
```

Re-entering `/shark-rider project bootstrap` repeats the inspection and derivation steps, then resumes the first required or explicitly selected activity. It does not restart completed work or rely on the prior checklist text.

When bootstrap selects a child activity, it dispatches the stable Rider action:

```text
/shark-rider project product-design
/shark-rider project brownfield-analysis
```

Bootstrap does not load either bundle skill directly. The corresponding action adapter owns bundle retrieval, argument passing, error handling, checkpoint integration, and any future change to the underlying CLI command.

### Stage 0: Prepare local Shark

Rider performs these checks before product or architecture work:

1. Inspect `.sharkconfig.json`, the configured data store, `docs/plan/`, and the installed content bundle.
2. If Shark is not initialized, invoke the normal `shark admin init` flow and report what it created.
3. If Shark is initialized, validate it and preserve existing configuration and data.
4. Repair missing generated support files only through the normal idempotent CLI path. Never apply `--force` or overwrite an existing data store without explicit approval.
5. If initialization cannot complete, record or report the concrete blocker and stop before generating misleading setup artifacts.

Bootstrap is the user-facing start experience; `shark admin init` remains the mechanism that owns database, configuration, and `docs/plan/` setup.

### Stage 1: Start the progress record

Create `docs/product/progress.md` at the beginning of setup, not after the first large activity. If it exists, preserve its decision log and regenerate its derived sections from current evidence.

This early write makes the setup scope and the next resumable step durable before product-design or codebase analysis begins.

### Stage 2: Establish project parameters

Confirm only parameters that cannot be derived safely:

| Parameter | Values or examples | Purpose |
|---|---|---|
| Repository estate | `greenfield`, `brownfield` | Describes what exists now. Derive from repository evidence, then let the user correct ambiguous cases. |
| Initiative posture | `stack-only`, `new-capability`, `extend`, `modernize`, `replace` | Describes what this initiative intends to do. Never infer it from estate alone. |
| Product-design scope | D01-D07 minimum discovery, D01-D11 design-ready, D01-D14 validated, or named artifacts | Controls how far bootstrap coordinates product-design before handoff. |
| Constraint posture | Named hard constraints, soft preferences, and open questions | Prevents current technology or a stated preference from becoming an accidental permanent constraint. |
| Brownfield depth | Lightweight architecture baseline or comprehensive analysis | Keeps routine startup proportional while allowing a deep enterprise, risk, debt, security, or migration assessment. |
| Setup customization | Content bundle, workflow, or local project conventions | Captures project-specific setup choices without creating a project database entity. |

Store these values as informative pointers and decision-log entries. Actual repository and artifact evidence remains the routing source.

## Greenfield coordination branch

### Normal product initiative

For a rough idea or new product initiative:

1. Record hard constraints and create only the minimum architecture marker or option set needed to support product discovery. Do not create a fully prescriptive foundation before D01.
2. Dispatch `/shark-rider project product-design`, which owns product-design bundle retrieval and checkpoints each D artifact.
3. Treat D04 as preliminary feasibility against observed constraints and proposed technical options, not as final architecture approval.
4. Continue through D07 user needs before the mandatory architecture integration gate.
5. At the gate, reconcile the proposed stack and architecture against D01 vision, D04 feasibility, and D07 needs. Record changes and ask for approval when the target architecture contains a material human choice.
6. Remove provisional status after every successful reconciliation, including when D04 says `feasible as described` and no technical choice changes.
7. Continue through D08-D11 or D08-D14 when that scope was selected. Recheck architecture before epic handoff if later evidence changes a constraint or target design.

If the user explicitly stops before D07, record the deferral and keep architecture in a partial or provisional state. Do not label the project ready for epic handoff as though the normal integration gate completed.

### Explicit stack-only initiative

When the user says the stack itself is the deliverable, bootstrap may bypass product discovery and generate the complete greenfield architecture scaffold. Record the `stack-only` posture and the reason in the decision log so this intentional exception is distinguishable from premature architecture work.

## Brownfield coordination branch

For an existing codebase:

1. Generate a lightweight, observed current-state baseline early enough to inform D01 and D04. This baseline describes the system; it does not approve it as the target.
2. Dispatch `/shark-rider project brownfield-analysis` only when the chosen depth or risk profile requires comprehensive analysis. Its action adapter owns bundle retrieval and checkpoints each completed analysis area and durable document.
3. Feed current-state architecture, integrations, quality, debt, security, and migration evidence into product-design.
4. Classify each relevant constraint as hard, soft, or unresolved. Include its source and owner.
5. Apply the selected initiative posture:
   - `new-capability`: preserve required integration boundaries but evaluate the capability's own implementation options;
   - `extend`: prefer compatible additions while exposing costly inherited constraints;
   - `modernize`: compare current and target states and define an incremental transition;
   - `replace`: treat current behavior and migration obligations as evidence, not the current implementation as a fixed target.
6. Run the architecture integration gate against product evidence and produce a baseline-to-target gap and change strategy.
7. Route genuine deferred remediation to Shark entities. Do not convert every feasibility gap into technical debt merely because the repository is brownfield.

This branch supports cases such as a new service inside an established monorepo: the estate is brownfield while the initiative posture is `new-capability`.

## Progress record contract

### Purpose and authority

`docs/product/progress.md` is the human-facing project setup status record. Its checklist is derived and advisory:

- Rider inspects actual configuration and artifacts whenever bootstrap or a child activity starts, checkpoints, or finishes.
- Routing uses that inspection, not the prior checkbox text.
- Manual checklist edits do not change Shark state or activity routing.
- No project table, project status workflow, or database row is added.
- The append-only decision log preserves choices that cannot be derived from files.

### Informative frontmatter

Restore the E36-F02 convenience pointers and expand them enough to distinguish estate from intent. Expected fields include:

```yaml
type: progress-record
schema_version: 2
estate: greenfield | brownfield
initiative_posture: stack-only | new-capability | extend | modernize | replace
product_design_scope: D01-D07 | D01-D11 | D01-D14 | custom
brownfield_depth: none | lightweight | comprehensive
architecture_state: absent | observed | proposed | provisional | reconciled | approved
stack_summary: <short informative value>
artifact_paths: <informative map or list>
last_refreshed: <timestamp>
```

These fields are hints for people and agents. Missing or stale frontmatter never blocks an operation. During migration, a legacy `track` value may be read as an estate hint, but new logic must not use it as a substitute for `initiative_posture`.

### Checklist states

Use a visible state that matches the evidence:

| Marker | Meaning |
|---|---|
| `[x]` | Required evidence exists and the activity's completion rule is satisfied. |
| `[~]` | Work started, evidence is partial, or an artifact remains provisional. |
| `[ ]` | Required evidence is absent or the activity has not started. |
| `[-]` | Explicitly not applicable or deferred by the confirmed scope; include a decision-log reference. |

Do not infer “final” from one fragile prose string. Derive maturity from explicit artifact metadata where possible and use compatible content detection only while migrating older files.

### Derived setup groups

The setup checklist must cover at least:

1. **Local Shark readiness**
   - `.sharkconfig.json` is present and valid;
   - the configured store is reachable;
   - `docs/plan/` and required bundle content are available.
2. **Setup definition**
   - the progress record is seeded;
   - estate, initiative posture, scope, depth, and constraints are confirmed or explicitly deferred.
3. **Brownfield evidence**
   - lightweight current-state architecture baseline;
   - selected comprehensive analysis areas and their durable outputs;
   - hard, soft, and unresolved constraint classification.
4. **Product design**
   - every D01-D14 artifact in the selected scope, not only D01 and D04;
   - evidence dependencies and approvals needed for each artifact;
   - explicit not-applicable or deferred artifacts.
5. **Architecture integration**
   - current-state evidence for brownfield;
   - proposed or provisional target options;
   - D01/D04/D07 reconciliation;
   - target architecture approval and any transition strategy.
6. **Setup handoff**
   - all required artifacts for the selected scope exist;
   - unresolved blockers and deferred decisions are visible;
   - project setup is ready for first-epic planning.

The existing **Cross-Epic Integration Map** section remains a separate product-level derived section. Epic design owns its rows and decision entries; bootstrap preserves it and does not claim completion based on it.

### Checkpoint protocol

Update the record at these points:

1. Bootstrap entry, after inspection and parameter confirmation.
2. After each D01-D14 artifact is written or materially revised.
3. After each selected brownfield-analysis area or durable output completes.
4. After architecture baseline, proposal, reconciliation, or approval changes.
5. Before pausing, handing control to another activity, or reporting setup completion.
6. When `/shark-rider project product-design` or `/shark-rider project brownfield-analysis` runs directly outside bootstrap.

At every checkpoint:

1. inspect the current evidence;
2. regenerate only derived sections;
3. preserve all existing decision-log entries and unrelated product sections;
4. append a decision only when a choice, approval, reason, or deferral occurred; and
5. write atomically when the host supports it.

If the filesystem is read-only, report a best-effort warning and continue routing from observed evidence. If the progress file is missing, seed it. If it is malformed, preserve the original, report the issue, and avoid destructive rewriting.

## Artifact provenance and maturity

Distinguish what the workflow observed, elicited, proposed, approved, or derived:

| Artifact class | Provenance | Meaning |
|---|---|---|
| Local Shark state | Observed | Configuration, store, bundle, and planning paths found during inspection. |
| Brownfield current-state docs | Observed and generated | Generated documentation of existing evidence; not a target-state approval. |
| Product-design artifacts | Elicited and researched | Product intent and evidence captured with human decisions, sources, and explicit unknowns. |
| Greenfield architecture options | Proposed | Candidate technical direction that can inform feasibility. |
| Provisional target architecture | Proposed and provisional | A coherent direction pending the product integration gate. |
| Reconciled target architecture | Reconciled | Updated against D01, D04, and D07, but not necessarily approved. |
| Approved target architecture | Approved | Human-confirmed target and, for brownfield, an associated transition strategy. |
| Progress checklist | Derived | A view calculated from the above evidence; never an independent source of state. |

Use explicit frontmatter or a consistent header contract for provenance and maturity. Do not rely on exact natural-language phrases such as `Greenfield — Provisional placeholder` to determine state.

## Shark Rider rename

### Canonical name and syntax

- Display name: **Shark Rider**
- Skill slug and source directory: `shark-rider`
- Rider action syntax: `/shark-rider <action>`
- CLI syntax: `shark <command>`

Examples:

```text
/shark-rider project bootstrap
/shark-rider project product-design
/shark-rider project brownfield-analysis
/shark-rider run E03
```

These are the coordinator-facing interfaces. Keep exact low-level CLI syntax in the owning verb adapter and CLI documentation, not in bundle workflows or parent Rider actions.

Use “Rider action” in user-facing documentation instead of the ambiguous “project verb” when the control surface matters. Use “verb file” only for the Rider-layer adapter that implements an action.

### Ownership boundary

The rename must preserve the existing architecture:

- The Shark CLI owns entity data, state transitions, leases, routing decisions, workflow configuration, prompt assembly, skill retrieval, and agent retrieval.
- Shark Rider owns intent translation, host-side interaction, the outer dispatch loop, local file craft, and coordination across retrieved methodologies.
- Each Rider action has one owning verb file. That file is the only Rider-layer source that contains its CLI invocations, translates CLI results, and handles CLI errors.
- Parent Rider actions call child Rider actions. `/shark-rider project bootstrap` calls `/shark-rider project product-design` or `/shark-rider project brownfield-analysis`; it does not copy their retrieval commands.
- Bundle skills and embedded workflows do not invoke the CLI. They return content, outcomes, and next-action signals to the owning Rider action.
- A worker invoked by Rider does not claim, advance, or release Shark entities unless the established host-loop contract explicitly assigns that responsibility. The existing `/shark-rider run` contract remains “CLI owns state; Rider drives the loop.”

Do not use `shark-orchestrator` as the replacement name because the CLI already owns workflow orchestration and routing. Do not use `shark-workflows` or `shark-agent`, which collide with bundle skills and configured Shark agents.

### Migration requirements

1. Rename the active skill directory and frontmatter identity from `shark` to `shark-rider`.
2. Update active Rider action references from `/shark ...` to `/shark-rider ...` across the source skill, embedded bundle content, project guidance, help, examples, tests, and generated/golden fixtures.
3. Move or retain each low-level CLI invocation in exactly one owning verb adapter. Parent actions and bundle workflows reference the Rider action instead of copying the command.
4. Preserve bare `shark ...` references in CLI documentation, verb adapters, and tests that verify those adapters. Remove duplicated invocation instructions from bundle skills and coordinating workflows.
5. Audit each match by meaning. Do not mechanically rewrite archived planning records or quoted historical commands unless they are still used as active instructions.
6. Add validation that the directory, manifest/frontmatter name, displayed invocation, and installed skill identity agree.
7. Add a boundary check that flags CLI invocations in bundle skills or in a parent action when a child Rider action owns that integration.
8. Prefer a one-way rename. If the host platform requires a compatibility shim, make `/shark` a short-lived deprecation route that points to `/shark-rider`; do not expose two permanent skills with divergent content.
9. Keep any intentional `/run` shorthand only if it is explicitly documented as an alias for a Rider action.
10. Update diagrams and prose from “CLI owns, skill drives” to “CLI owns, Rider drives.”

Directory and frontmatter identity can be coupled by skill installers, so the implementation must verify installation and invocation instead of assuming that adding an alias file creates a valid alias.

## Impact analysis

### Benefits

- One clear start action prepares Shark and coordinates product and technical discovery.
- Interrupted setup work becomes resumable at artifact-level granularity.
- Greenfield projects avoid premature architecture lock-in while still getting technical input early.
- Brownfield projects distinguish evidence from constraints and support extension, modernization, and replacement strategies.
- CLI and host-side instructions become easier to read, teach, and test.
- Each CLI integration has one Rider-layer maintenance point instead of being repeated in coordinators and bundle workflows.

### Risks and mitigations

| Risk | Mitigation |
|---|---|
| Rename breaks installed skill discovery or cached references | Validate installed identity, update active references as one migration, and use only a short deprecation shim if the host requires it. |
| Progress record becomes a shadow status machine | Keep all fields advisory, derive every checkpoint from evidence, and prohibit database or routing logic from trusting checkboxes. |
| Bootstrap becomes an inflexible wizard | Derive what can be derived, ask only irreducible questions, preserve direct child actions, and support explicit custom scope. |
| Product-design and architecture loop indefinitely | Define one mandatory integration gate, record material changes, and require explicit approval or deferral before handoff. |
| Existing brownfield constraints are ignored | Preserve observed current-state evidence, classify hard constraints with sources, and require a transition strategy for modernization or replacement. |
| Historical documentation becomes misleading after a broad rewrite | Update active instructions semantically and retain archived records unless they are executed or presented as current guidance. |

## Rollback plan

The change has no schema migration and does not rename the `shark` binary, so it can be rolled back in layers:

1. Restore the prior skill identity and active slash references if Rider discovery fails.
2. Restore the prior project dispatcher and embedded bootstrap routing while leaving user-created product and architecture documents intact.
3. Continue accepting both old and expanded progress files; never delete or truncate a project's decision log during rollback.
4. Revert checkpoint hooks independently if a child skill cannot update the record safely.
5. Keep the CLI, Shark database, entities, statuses, and workflow definitions untouched unless a separate implementation task explicitly changes them.

If a temporary `/shark` compatibility shim ships, removing `/shark-rider` alone is not a complete rollback; restore the canonical skill identity and validate that only one active implementation remains.

## Out of scope

- Renaming the `shark` CLI binary.
- Adding a database-backed project entity, project status workflow, or project registry.
- Making `docs/product/progress.md` authoritative.
- Moving recurring DevOps, deployment, maintenance, or migration execution into the setup checklist.
- Changing the CLI's ownership of prompt assembly, routing, claims, advances, or releases.
- Preventing a person from using the CLI directly. The action-adapter rule applies to Rider-controlled execution paths.
- Creating a feature outside an epic; this card remains linked to E36-F02.
- Redesigning the D01-D14 product-design methodology itself. This card changes coordination, inputs, checkpoints, and architecture integration.
- Requiring comprehensive brownfield-analysis for every existing repository.
- Maintaining permanent dual `/shark` and `/shark-rider` skill identities.
- Rewriting archived plans solely to replace historical command spelling.

## Methodology basis

The flow adapts established consulting and service-design practices rather than treating greenfield and brownfield startup as the same document-generation sequence:

- The [Design Council Double Diamond](https://www.designcouncil.org.uk/our-resources/framework-for-innovation/) separates discovery and problem definition from solution development while allowing iteration across the boundary.
- The [GOV.UK Service Manual discovery guidance](https://www.gov.uk/service-manual/agile-delivery/how-the-discovery-phase-works) emphasizes understanding the problem, users, constraints, and existing landscape before committing to build.
- The [IIBA Business Analysis Standard](https://www.iiba.org/globalassets/business-analysis-resources/the-business-analysis-standard/files/the-business-analysis-standard.pdf) distinguishes current state, future state, risks, and change strategy—especially important for brownfield modernization and replacement.
- [AWS Prescriptive Guidance for modernization strategy](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-modernizing-applications/welcome.html) starts with business outcomes and current-state assessment before selecting a modernization path.

Applied here, those practices produce one rule: gather enough technical evidence to constrain product discovery, but defer target architecture commitment until product needs and the initiative's change posture are explicit.
