# Consolidate bug aggregate multi-query methods into single SQL queries

## Description

Two methods in `internal/repository/bug/aggregate.go` issue multiple sequential queries where a single query would suffice:

**`GetStatusSummary`** fires 4 queries:
1. `SELECT COUNT(*) FROM bugs` — total count
2. `SELECT status, COUNT(*) FROM bugs GROUP BY status` — status breakdown
3. `SELECT severity, COUNT(*) FROM bugs GROUP BY severity` — severity breakdown
4. `SELECT severity, COUNT(*) FROM bugs WHERE status NOT IN (...) GROUP BY severity` — open by severity

**`GetFeatureBugSummary`** fires 3 queries:
1. Total count (filtered by entity)
2. Open count (filtered + status NOT IN terminal)
3. Open by severity (filtered + status NOT IN terminal + GROUP BY)

**Proposed change:** Consolidate each method into 1-2 queries using conditional aggregation (`COUNT(CASE WHEN ... THEN 1 END)`) or a single `GROUP BY status, severity` query that can be post-processed in Go.

## Justification

Each method performs 3-4× the necessary database round-trips. For the CLI tool with small datasets this is low priority, but these methods are called from status dashboards and could become noticeable with larger bug counts or remote (Turso) databases where latency per query is higher.

## Impact Analysis

- **Files modified:** `internal/repository/bug/aggregate.go` (1 file)
- **Risk:** Low — internal refactoring of query implementation, same return types
- **Tests:** `internal/repository/bug/aggregate_test.go` validates return values, not query count; tests continue to pass
- **Performance:** Reduces SQLite round-trips from 4 to 1-2 per method call

## Rollback Plan

Revert `aggregate.go` to restore the multi-query implementation. No schema or API changes involved.
