# Evaluate Google Wire for service-layer DI (spike)

## Description

Evaluate Google Wire (github.com/google/wire) as a replacement for the hand-maintained wiring in internal/cli/services_global.go and internal/viewer/server/wire.go. Today these two files encode the same dependency graph twice; every new service or dep must be edited in both. Entity service constructors are also trending toward parameter sprawl (NewBugService takes 8 positional args after E28-F04; TaskService/FeatureService/EpicService/ChangeCardService are on the same trajectory).

Spike scope:
- Prototype a Wire provider set covering one entity service branch (e.g., BugService + its deps), generate wire_gen.go, and wire it into both CLI and HTTP entry points as a parallel code path
- Measure: lines removed from services_global.go / wire.go, time to add a new dep via Wire vs. current approach, CI/toolchain impact of running 'wire' on dep changes
- Document go/no-go criteria and present findings

Decision outcomes:
- GO: adopt Wire, plan a migration change-card (targets all entity services + entry-point wiring), update CLAUDE.md 'No DI Framework' rule to narrow it to 'no reflection-based DI'
- NO-GO (minor): fall back to deps-struct refactor for entity service constructors
- NO-GO (defer): document findings and revisit when service count or wiring duplication crosses a clear threshold

## Justification

Hand-wiring is becoming the limiting factor as the service layer grows. CLAUDE.md's 'No DI Framework' rule was originally a judgment call to avoid reflection-based frameworks (FX, dig); Wire is compile-time codegen and may satisfy the underlying intent. Worth a time-boxed spike before we either (a) do the deps-struct fallback refactor, or (b) keep paying the maintenance cost. Framed as research so the decision is recorded and reversible, not a pre-committed migration.
