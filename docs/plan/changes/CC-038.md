# Notes CLI: expose IDs and add delete/edit commands

## Description

The notes CLI surface is asymmetric and IDs are hidden:

1. `shark create note <key> "..."` succeeds but does not echo the new note ID.
2. The human-readable `shark <entity> notes <key>` view shows type + timestamp + creator, but no ID:
   ```
   [BLOCKER] 2026-05-04 23:25 (unknown)
   QA FAIL — see docs/plan/bugs/code_review/...
   ```
   IDs only exist in `--json` output (`shark <entity> notes <key> --json` returns `id: 1230` per note).
3. There is no `shark note delete` or `shark note edit` command — `shark create note` exists but has no inverse. The unified `shark delete <key>` only handles entity types (epic/feature/task/bug/change-card/tech-debt/idea), not notes.

The only way to remove a stray note today:
```bash
shark <entity> notes <key> --json | jq '...'   # find the ID
sqlite3 shark-tasks.db "DELETE FROM entity_notes WHERE id = ..."
```

## Justification

Discovered during `/run B018` when QA agents (correctly, for evidence purposes) left test reproduction notes on TD-001 and B018 during their workflow runs. Cleaning them up required dropping into sqlite3 because the CLI exposes no editing path. The asymmetry (`add` but no `delete`/`edit`; IDs hidden in human output) blocks normal cleanup workflows and forces direct DB access.

## Proposed Bundle

1. **Show note ID in human view** — e.g. `[#1230 BLOCKER] 2026-05-04 23:25 (unknown)`. ID is already in the JSON output; just surface it in the formatter.
2. **Echo new ID on create** — `shark create note B018 "..."` should print `Created note #1234 on B018` (matches the pattern of `shark create change` printing the new key).
3. **`shark note delete <id>`** — verb-first canonical form per `feedback_verb_first_unified_commands`.
4. **`shark note edit <id> --content="..."`** — verb-first canonical form. Editing content (and possibly type) is the natural counterpart to `add`.
5. **Naturally entity-agnostic** — notes are polymorphic via the `entity_notes` table, so a single `shark note delete <id>` works for every entity type by default (per `feedback_new_commands_all_entities`). No per-entity dispatch needed.

Optional follow-on (not required for first pass):
- Wire entity-first aliases (`shark <entity> note delete`/`edit`) for parity with the existing `shark <entity> note add` surface, mirroring the pattern of other entity-first commands.

## Impact Analysis

- **Surface area**: small — one new command (`shark note`) with two subcommands (`delete`, `edit`) plus a formatter tweak in the existing `notes` view and an echo line in `create note`.
- **Schema**: no changes. `entity_notes` already has `id` (PK) and `content`/`note_type` fields.
- **Service layer**: needs `NoteService.DeleteNote(ctx, id)` and `NoteService.UpdateNote(ctx, id, content, type)` methods (or whichever existing service owns notes — check `internal/services/note_service.go`).
- **Backward compatibility**: pure additive change — no existing command behavior changes apart from the `notes` view gaining an `[#id]` prefix and `create note` gaining an echo line. Users parsing the human-readable output by regex could be affected by the formatter change; users on `--json` are unaffected.
- **Authorization**: deletion is destructive. Consider whether `shark note delete <id>` should require `--force` (matching the unified `shark delete` pattern) or whether note deletion is low-stakes enough to skip.

## Rollback Plan

Pure additive feature; rollback is `git revert` of the implementation commit. No DB migrations, no schema changes, no data transformation. Existing notes and existing CLI behavior are unaffected by reverting.

## Origin

Surfaced 2026-05-04 during `/run B018` orchestration session. QA agents left two evidence notes on TD-001 (note IDs 1228, 1229) and one on B018 itself (1234) that the user wanted cleaned up; sqlite3 was the only available path.
