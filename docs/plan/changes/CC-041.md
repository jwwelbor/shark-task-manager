# Add guided /shark new work intake

## Description

Introduce /shark new as the canonical guided work-intake verb. It should classify new work, ask at most one clarifying question when needed, search for existing coverage, propose the right entity type and parent/location, and create only after confirmation. Keep /shark create for expert direct CRUD and /shark triage for discovered/deferred work. Also update assessment taxonomy so it can distinguish epic, feature, task, bug, tech-debt, change-card, idea, and note rather than only feature vs task.

## Justification

Users need one intuitive entry point for defining new work without knowing whether it is an epic, feature, task, bug, tech-debt item, change-card, idea, or note.

## Impact Analysis

User-facing CLI and skill documentation would change to make `/shark new` the
recommended guided entry point for defining new work. The implementation should
preserve existing direct commands such as `/shark create`, `/shark triage`, and
`/shark vision` as compatibility or specialized paths. Assessment guidance needs
to expand beyond feature-vs-task scope validation so routed work can land as an
epic, feature, task, bug, tech-debt item, change-card, idea, or note.

## Rollback Plan

Remove the `/shark new` verb and restore documentation to the previous
`/shark vision` plus `/shark triage` entry pattern. Leave existing entities
created through `/shark new` intact, since they use normal Shark entity types.


## Change Summary
 Recommended interface:

  /shark new "agents need a clearer way to create new work"

  Then Shark should:

  1. use socratic method to learn about the scope (import skill from /home/jwwel/.claude/skills/socratic-method/SKILL.md) for refinement if needed.
  2. Search for existing coverage using `shark search <query> <flags>` or search the docs/ folder using cli tools.
  3. Classify using a shared taxonomy.
  4. Propose the entity type, parent/location, rationale, and title.
  5. Create only after confirmation.
  6. For epics/features, hand into spec/workflow generation. For bugs/change/tech-debt, create the
     standalone corrective item. For ideas, capture without commitment. For duplicates, add a note.

  The taxonomy should live in assessment, not only in triage. Right now assessment scope validation only
  returns FEATURE | TASK | SPLIT | CONSOLIDATE in shark-data/skills/assessment/SKILL.md:44, and the
  feature assessment prompt only asks “feature or task” in shark-data/prompts/feature/assessment.md:18.
  That should expand to:

  - Epic: multi-feature initiative with business/user outcome and journey-level coherence.
  - Feature: stakeholder-visible value inside an epic, decomposable into tasks.
  - Task: atomic implementation/docs/test work under a feature.
  - Bug: expected behavior is broken.
  - Tech debt: behavior works, but code/architecture/testing/docs quality creates risk.
  - Change-card: process, infra, config, migration, approval, or operational change.
  - Idea: speculative or not yet committed.
  - Note: context belongs on an existing entity.

**Note: Assessment recently was improved and adjusted, so review the current assessment scope and implementation carefully before making any adjustments.
