# Move status-set idempotency check into service layer

## Description

`runStatusSet` in `status_group.go` makes two service round-trips:

1. Calls `dispatchNextStatus` to get current status (fetches entity from DB)
2. Compares current status with target — if same, returns early (idempotent)
3. If different, calls `dispatchTransition` (fetches entity from DB again)

The idempotency check (step 2) is business logic that belongs in the service layer, not the CLI command. `EntityService.TransitionStatus` already fetches the entity and knows the current status — it should detect the no-op case and return a `TransitionResult` with `Transitioned: false` instead of the CLI having to pre-check.

### Proposed change

In `EntityService.TransitionStatus`:
- After fetching the entity and before performing the transition, check if `currentStatus == targetStatus`
- If idempotent, return `&TransitionResult{Transitioned: false, FromStatus: currentStatus, ToStatus: currentStatus}` without writing to DB
- `runStatusSet` can then remove the `dispatchNextStatus` pre-check and just call `dispatchTransition`, checking `result.Transitioned`

This eliminates one DB fetch per `shark status set` call.

## Justification

- Removes business logic from CLI command (architecture principle: thin commands)
- Eliminates redundant DB fetch on every status set
- Makes idempotency available to HTTP API callers without duplicating the check

## Impact Analysis

- **Files**: `entity_service.go`, `status_group.go`, `entity_service_test.go`
- **Risk**: Low — adding an early return for a no-op case
- **Performance**: Saves one DB round-trip per `shark status set` invocation

## Rollback Plan

Revert the commit. The double-fetch behavior is functionally correct, just inefficient.
