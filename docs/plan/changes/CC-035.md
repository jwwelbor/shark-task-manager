# Replace hardcoded terminal-status SQL in bug/changecard repos with workflow.GetTerminalStatuses

## Description

The bug and change-card repositories hardcode terminal status lists in their SQL List() methods, which breaks for projects that customize the terminal statuses in their workflow config.

Locations:
- internal/repository/bug/repository.go:255 — hardcoded `status NOT IN ('resolved', 'wont_fix', 'duplicate')`
- internal/repository/changecard/repository.go:257 — hardcoded `status NOT IN ('completed', 'declined')`

Today these happen to match the shipped .sharkworkflow.json bug_workflow and change_workflow (which set special_statuses._complete_ to those exact values), so behavior is correct for default projects. The viewer fix that added the show-all checkbox plumbing relies on this filter firing.

But: any project that customizes its workflow config (e.g. adds 'closed' as a terminal bug status, or removes 'duplicate') would have terminal entities leak through the IncludeTerminal=false filter, since the repo never consults the workflow config.

Proposed fix:
- Inject workflow.Service (or just the terminal-status slice) into BugRepository and ChangeCardRepository, or accept the slice as part of the filter struct.
- Replace the hardcoded SQL with a parameterized NOT IN built from workflow.Service.GetTerminalStatuses() for the appropriate level (LevelBug, LevelChange).
- The CLI's bug list / change list paths benefit from the same fix — they hit the same repo method.

Out of scope here:
- The viewer.html JS hardcoded HIDDEN_TERMINAL_BY_TYPE / TERMINAL_STATUSES sets (lines ~1690-1722) have the same class of issue for tree entities (epics/features/tasks). Filed separately if/when it bites someone.

Discovered while fixing the wormwoodGM viewer bug where 'resolved' bugs were showing in the sidebar. The viewer-side plumbing (show-all checkbox -> include_terminal query param -> repo filter) is in place and works for the default workflow; this card tracks fixing the underlying repo hardcoding.

## Justification

The repository layer is the wrong place to encode workflow knowledge. Workflows are user-configurable via `.sharkworkflow.json` (`workflow_config` in `.sharkconfig.json`) — the rest of the codebase respects that contract via `workflow.Service`, but these two SQL clauses don't. Concrete reasons to fix:

1. **Correctness for non-default workflows.** `IncludeTerminal=false` silently lies to callers when a project's terminal set doesn't match the hardcoded list. A project that adds `closed` to bug terminal statuses would see closed bugs in `shark bug list` and in the web viewer sidebar, with no error or warning.
2. **The viewer change just shipped depends on this filter being right.** `apiGetHierarchy(..., includeTerminal)` → `HierarchyOptions.IncludeTerminal` → `BugRepository.List({IncludeTerminal: false})` is a clean chain right up until the SQL, where it diverges from the project's actual workflow.
3. **Single source of truth.** `workflow.Service.GetTerminalStatuses()` already exists and is the authoritative answer (`internal/workflow/service.go:124`). Two more callers should use it instead of forking a copy.
4. **Symmetry with task/epic/feature filtering.** Those layers consult `workflow.Service`; bugs and change cards are the outliers.

## Impact Analysis

**Affected code paths:**
- `internal/repository/bug/repository.go` — `BugListFilters` struct + `List()` method.
- `internal/repository/changecard/repository.go` — `ChangeCardRepoFilter` struct + `List()` method.
- All callers of those `List()` methods:
  - `internal/services/bug_service.go` — CLI `shark bug list`.
  - `internal/services/changecard_service.go` — CLI `shark change list`.
  - `internal/viewer/server/wire.go` — viewer adapters (recently updated).
  - Any other repos/services that construct these filter structs.

**Behavior change:**
- Default-workflow projects: no observable change (the new dynamic list matches the old hardcoded list).
- Custom-workflow projects: terminal-status filtering becomes correct where it was previously broken. This is the desired outcome but is technically a behavioral change for any project currently relying on the bug.

**Risks:**
- If `workflow.Service.GetTerminalStatuses()` returns an empty slice (misconfigured workflow), the filter would become a no-op and return all rows. Mitigation: keep the existing fallback in `GetTerminalStatuses` (`return []string{"completed"}` when `_complete_` is missing) or add a defensive check at the repo layer.
- Constructor-injection refactor: `BugRepository` and `ChangeCardRepository` would gain a dependency. Need to verify all construction sites (CLI wiring in `internal/cli/services_global.go`, HTTP wiring in `cmd/server/services.go`, viewer wiring in `internal/viewer/server/wire.go`, test fixtures) are updated. The alternative — putting the terminal-status slice on the filter struct — keeps the repo dependency-free at the cost of pushing the lookup to every caller.

**Test surface:**
- `internal/repository/bug/*_test.go` and `internal/repository/changecard/*_test.go` will need updates if the repo constructor signature changes.
- Add a regression test with a custom workflow whose terminal set differs from the hardcoded list, asserting the filter respects the config.

**Estimated size:** S — two repos, well-scoped, the workflow service plumbing already exists.

## Rollback Plan

The change is self-contained and trivially revertable:

1. `git revert` the implementing commit. The hardcoded `NOT IN ('resolved', 'wont_fix', 'duplicate')` and `NOT IN ('completed', 'declined')` clauses come back, restoring pre-change behavior for default-workflow projects.
2. No database migrations, no schema changes, no on-disk data touched — this is pure code that runs at query time.
3. If a downstream caller has been updated to pass terminal statuses through the filter struct (option B above), revert those callers as part of the same revert commit so the filter struct field disappears cleanly.
4. Default-workflow projects (the majority) see zero behavior difference on revert. Custom-workflow projects revert to the latent bug.
