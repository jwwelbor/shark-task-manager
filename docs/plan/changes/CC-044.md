# Harden AI-DLC review loop around caller-path compliance, defect-class rejections, and review metrics

## Description

2026-07-09 follow-up to dev-artifacts/2026-07-06-fable-shark-review/findings.md. PR #120 already landed the narrow prompt/UAT/claim/work-session fixes, but the broader process recommendations still lack a backlog home: (1) enforce caller-path contract compliance from task development through QA verification, (2) require class-scoped defect sweeps and broad re-audit on rejection instead of point-fix verification only, (3) decide whether SIMPLE/STANDARD features should collapse code_review + qa into one stronger same-model verification gate, and (4) make review findings queryable so repeated defect classes and gate effectiveness are measurable. Keep this as a single change-card until the policy decision and implementation split are clearer.

## Justification

The remaining 2026-07-06 pipeline review feedback is not a point bug; it is a cross-cutting workflow/process correction. We need one durable item to align dev prompts, QA/UAT verification, rejection handling, and review telemetry without duplicating already-fixed code defects.

## Impact Analysis

This change-card is intentionally cross-cutting. The likely implementation
surface spans:

- Embedded prompts and skills for task development, QA, and UAT
- Review workflow policy for rejection handling and re-verification scope
- Possibly workflow step consolidation for SIMPLE/STANDARD features if the
  code_review + qa split is reduced to one stronger gate
- Telemetry/storage for structured review findings so recurring defect classes
  and gate effectiveness can be measured instead of inferred from prose notes

Expected benefit:

- Fewer repeated review rounds caused by point-fix prompts that do not trigger
  class-wide sweeps
- Better enforcement that tests exercise the declared production entrypoints
  rather than stopping one seam short
- Clearer evidence on whether each review gate is paying for itself

Expected risk:

- Workflow/prompt churn can alter review behavior across multiple entity types
- Any gate merge decision needs explicit policy validation before code changes
- Telemetry additions may touch persistence and reporting surfaces, so they
  should be split into concrete follow-on tasks after the policy is settled

## Rollback Plan

If follow-on implementation proves too disruptive, revert the individual prompt,
workflow, or telemetry changes independently and keep the current multi-gate
review flow. This card itself is only a planning anchor; rollback means closing
or superseding its downstream tasks rather than removing data from Shark.
