# Specification-writing review checklist: require cross-entity state-crossing + mandatory state-transition tables for deferred lifecycles

## Description

Proposed checklist additions for the specification-writing skill's spec/test-plan review workflow(s): (1) any decision table keyed on a status/disposition column must enumerate every OTHER entity's status column reachable from a row in that state, as a second independent axis, not just that row's own field/shape completeness; (2) when a spec declares a lifecycle/status column and defers its full value set/transitions to a downstream feature, that downstream feature's own spec must include a complete state-transition table (every value, every transition, including failure states) before it ships -- a prose 'progression' sentence should fail review on its own; (3) when a later feature adds a state value to an entity that an already-shipped feature's lookup/dedup/short-circuit logic reads, that earlier feature's relevant acceptance criteria must be re-opened and a test case added proving the lookup still behaves correctly against the new state; (4) naming drift on a field shared across two features' specs (e.g. lifecycle_state vs ledger_state for the same concept) should be flagged during review as evidence the two specs were never cross-read on that shared concept.

## Justification

A real cross-feature production bug (WWGM project's B023) survived a hostile Codex red-team pass of the exact decision table that should have caught it, because the review process only crosses a status/disposition column against ITS OWN entity's other fields, never against another entity's status column reachable from it. A second contributing gap: a feature can defer a lifecycle-state's full value set/transitions to a downstream feature and ship with only a prose progression sentence -- no actual state-transition table is required, so the deferred state machine is never fully enumerated by anyone. Full retrospective and evidence: /home/jwwel/projects/wwgm/docs/plan/E04-upload-source-ledger/DB-2026-07-25-b023-spec-process-retrospective.md (a sibling project using this same specification-writing skill).

## Impact Analysis

Located the two most likely existing homes for this reinforcement (not yet
edited — this change card records the finding and candidate locations for
whoever executes it):

1. **`skills/breakdown-test/context/edge-case-catalog.md` §7 "Interaction and
   Dependency"** already has the closest existing bullet: "A related entity
   is in an incompatible state." It's currently a generic, easy-to-skim-past
   prose reminder with no enforcement teeth. Proposed: strengthen it into an
   explicit sub-rule — *"when a criterion's own entity has a status/
   disposition field, identify every OTHER entity reachable from a row in
   that state (via FK or lookup) that has its OWN status/lifecycle field,
   and add one matrix row per combination of [this entity's terminal values]
   × [that other entity's non-happy-path values], not just the happy-path
   crossing."* This directly targets checklist item (1).
2. **`skills/cross-artifact-analysis`** (checks consistency/drift across
   layered epic/feature/task specs) is the natural home for checklist items
   (2)-(4) — a parent spec deferring a state machine's closure to a child
   spec, and that child never actually closing it with a table, is exactly
   the "child spec omits what its parent established" pattern this skill
   already exists to catch. It would need a new rule: when a spec item
   contains language like "downstream owns transitions" or "X will define
   this," the analysis must verify the downstream artifact contains a
   complete, tabular closure (not prose) before treating the deferral as
   resolved.
3. Section 4 "Ordering and Timing" of the same edge-case-catalog.md already
   has "An action arriving before its precondition is met" — also adjacent
   to B023's actual mechanism (a status commit landing durably before the
   work it names has actually succeeded or failed) — worth cross-referencing
   from whichever of the two locations above gets the primary fix.

No breaking change to any existing spec/test-plan — this only strengthens
future review guidance. Does not require re-reviewing already-shipped specs
retroactively (though the owner may choose to, separately).

## Rollback Plan

Documentation-only change to skill content — a plain `git revert` of
whichever commit adds the new rule/section, no data or schema impact.
