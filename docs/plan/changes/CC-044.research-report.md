# CC-044 Research Report

## Scope

This research checks the current contracts for production caller-path compliance, class-scoped rejection and re-review, SIMPLE/STANDARD versus COMPLEX feature gate routing, and review-finding measurement. The affected surface crosses the prompt and skill bundle, the structured gate-result boundary, note persistence and search, and the E40 evaluation harness.

Here, a **caller-path contract** names the production entrypoint and argument shape a test must drive, its lowest allowed mock seam, forbidden mocks, and a counterfactual. A **defect class** is a normalized class identity whose affected sites are enumerated and re-verified as a group. A **review metric** describes confirmed gate outcomes or value; emitted reviewer findings alone are not confirmed results.

## Findings

### Caller-path compliance already has a reusable contract

The quality test-planning prompt requires a Caller-Path Contract for each runtime test case with a production caller. The shared reference defines the entrypoint, argument shape, lowest allowed seam, forbidden mocks, and counterfactual. QA Step 8 mechanically compares committed tests against those fields and makes violations blockers. Feature code review also audits caller-path compliance, while task development requires tests to call the declared production entrypoint and directs rejected work through the established defect sweep.

This is an established contract to extend consistently across relevant task and feature paths. A parallel caller-path vocabulary or separate compliance gate would duplicate existing policy.

### Defect-class rejection already has a canonical workflow and result shape

`skills/quality/workflows/defect-class-sweep.md` is the shared procedure for code-review, QA, approval, UAT re-review, and development rework. Re-review enumerates the declared search scope again and reruns the calling gate's full rubric. Its I-03 result records the class, search scope, matched instances, dispositions, guard, and open count.

GateResult v1 already carries findings and `remediation_sweeps`. The runner validates the worker envelope and result, then the parent persistence coordinator writes structured `review-finding` notes and sweep references before applying transitions. CC-044 should strengthen compliance with this end-to-end contract where evidence reveals a gap; it should not add another rejection state machine or duplicate sweep schema.

### Feature gate consolidation is already a current policy decision

The canonical `feature.yaml` describes `code_review` as a combined review-and-QA gate for SIMPLE and STANDARD and a review-only first gate for COMPLEX. The separate `qa` status is designated for COMPLEX features. E34-F08 documents the same tier matrix and preserves the combined route for the lower tiers.

Thus, the gate-collapse question in the older CC-044 description is already answered in the checked-in workflow. Preserve that routing as the current contract. A later change to the matrix should be based on comparative outcome evidence rather than reopening the policy from prompt prose alone.

### Finding capture exists; operational outcome metrics remain a separate surface

GateResult findings include severity, class key, fingerprint, affected IDs, and disposition. Persistence stores those fields in note metadata. `shark notes search` searches note content and can filter note type and entity/time scope; the repository returns metadata with results, but its search predicate does not filter or aggregate by metadata fields. The current OpenTelemetry instruments cover CLI command and database query behavior, not review quality, recurrence, rework, or gate value.

The E40 benchmark path supplies the stronger measurement pattern. F08 retains raw gate findings; F09 separately normalizes and confirms findings, distinguishes independent frozen-candidate comparisons from sequential delivery, and reports confirmed yield, overlap, recurrence, and escapes. Precision/recall requires a retained truth set. These files and scripts provide an evaluation capability, while the generic Shark note/search and observability surfaces do not currently provide project-wide review outcome aggregates.

The main cross-boundary risk is treating capture as measurement: reviewer-supplied severity, fingerprint, or disposition can be persisted as evidence but does not establish that the finding was correct or that the gate added value. Candidate identity, independent confirmation, gate attribution, and the presence or absence of a truth set must remain explicit in any metric.

## Decisions

1. **Extend existing caller-path and defect-class contracts.** Apply the declared caller signature and complete sweep/re-verification procedures through their existing prompt, skill, and gate owners. Do not introduce parallel terminology, workflow state, or persistence.
2. **Preserve the current tier matrix.** SIMPLE and STANDARD already use the combined code-review/QA gate; COMPLEX uses a separate QA gate. Change this only after a controlled comparison demonstrates a useful tradeoff.
3. **Reuse GateResult v1 and typed note storage.** Keep structured findings and sweep evidence on the existing parent-owned path. No new storage table or second result envelope is warranted by the inspected contracts.
4. **Measure independently of capture.** Use the E40 F08/F09 evidence and comparison rules for gate-value research. Do not treat note counts or reviewer-provided dispositions as precision, recall, or causal evidence.
5. **Treat a live aggregate query/report as a distinct new surface.** If CC-044 requires ongoing project-wide trends in addition to E40 evaluation, scope a read-only query/report after selecting metrics, denominators, and confirmation rules. Prefer querying existing structured notes and run evidence over duplicating persistence.
6. **Split implementation only after the remaining policy decisions are recorded.** The workflow/adoption work and any operational reporting work have different owners and evidence needs; keep the parent card as the policy anchor until those boundaries and acceptance criteria are approved.
