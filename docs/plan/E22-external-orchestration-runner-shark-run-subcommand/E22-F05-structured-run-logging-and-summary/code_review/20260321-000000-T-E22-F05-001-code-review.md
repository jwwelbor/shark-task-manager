## Code Review Findings

### Scope Compliance
Changes are correctly scoped to `internal/runner/` and `internal/cli/commands/run.go`. No unrelated modifications observed.

### Architecture Alignment
The implementation follows project conventions:
- `TruncateOutput` is a pure helper in a dedicated file (`output_format.go`) — appropriate.
- `OutputSummary` is intentionally empty on failed stages (exit != 0), matching the task spec and keeping the JSON schema additive.
- The function is exported (`TruncateOutput`) rather than package-private as the task spec suggested; this is an acceptable deviation since it enables reuse from the `run.go` command layer without internal package tricks, and matches the project pattern of keeping helpers accessible where needed.

### Error Handling
No new error paths introduced. `TruncateOutput` clamps `maxLen < 1` to 1 to prevent panics — correct defensive behavior.

### No-Allocation Fast Path
Short strings with no newlines and `len <= maxLen` return `flat` directly after `strings.ReplaceAll`. The task spec asks for no allocation for short strings; `strings.ReplaceAll` with no occurrences returns the original string unchanged in Go's standard library, satisfying this requirement.

### Test Quality
- `TestRunController_OutputSummary_PopulatedOnSuccess`: verifies correct `Stdout` value flows into `stage.OutputSummary`.
- `TestRunController_OutputSummary_EmptyOnFailure`: verifies failed stages leave `OutputSummary` empty.
- `TestTruncateOutput`: 13 table-driven cases covering all required boundary conditions including unicode rune counting.

### Minor Observations (non-blocking)
- The task spec says `truncateOutput` should be package-private; the implementation exports it as `TruncateOutput`. This is a deliberate and reasonable choice given usage from the CLI command layer. No action required.
