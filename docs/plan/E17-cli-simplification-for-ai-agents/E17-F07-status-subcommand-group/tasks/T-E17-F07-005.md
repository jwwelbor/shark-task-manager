# Task: Write status subcommand group tests

## Goal

Create `internal/cli/commands/status_group_test.go` with comprehensive unit tests for all four status subcommand handlers (`runStatusSet`, `runStatusAdvance`, `runStatusOptions`, `runStatusHistory`). Tests use mocked services -- no real database. All 97 test points from the test plan (`test-plan.md`) must be covered or explicitly documented as handled.

## Context

The test file is `internal/cli/commands/status_group_test.go`. It follows the CLI testing pattern established in the codebase: mock services via function-field structs, inject them, invoke handler functions directly, assert on output and behavior.

The test plan (`test-plan.md`) defines 97 test points across 7 categories:
- TC-SET-01 through TC-SET-13 (13 tests for `runStatusSet`)
- TC-ADV-01 through TC-ADV-10 (10 tests for `runStatusAdvance`)
- TC-OPT-01 through TC-OPT-09 (9 tests for `runStatusOptions`)
- TC-HIST-01 through TC-HIST-07 (7 tests for `runStatusHistory`)
- TC-INT-* (integration tests for entity detection, Cobra coexistence, workflow delegation, idempotency)
- TC-BC-01 (backward compatibility: `make test` must pass)
- TC-EDGE-* (edge cases: invalid keys, missing entities, force mode, concurrent access, argument counts, status values)

### Technical Approach

**Mocking services**: The handlers call `cli.GetTaskService()`, `cli.GetFeatureService()`, `cli.GetEpicService()`, and `cli.GetTaskServiceWithHistory()`. To inject mocks, use one of these approaches based on what the codebase supports:

Option A: If `internal/cli/services_global.go` has override hooks (e.g., package-level variables), set them in `TestMain` or per-test setup with `defer` reset.

Option B: If no override hooks exist, test the `dispatchTransition` and `dispatchNextStatus` helpers directly by replacing them with test-local function variables (if defined as `var` rather than `func`). Alternatively, structure tests to pass mock-derived closures through the adapter.

Option C (preferred if A and B are unavailable): Verify that the handlers can be tested by constructing a minimal Cobra command, calling its `Execute()`, and capturing the output -- the pattern used in other CLI test files in the codebase. Check `internal/cli/commands/` for existing test files to determine the established mock injection pattern.

Inspect existing test files (e.g., `*_test.go` in `internal/cli/commands/`) before writing mocks.

**Capturing os.Exit**: Use the `monkey-patching` approach common in Go CLI tests -- set a package-level `osExit = os.Exit` variable and replace it in tests with a function that panics with the exit code. Recover the panic in the test to assert the exit code. Check if this pattern already exists in the codebase.

**Output capture**: Use `bytes.Buffer` + redirect stdout/stderr via a test helper, or use `testify/assert/output` capture helpers if available.

**Concurrent test (TC-EDGE-CONC-01)**: Use `t.Parallel()` and `sync.WaitGroup` to launch two goroutines, each invoking a handler on a different entity key mock.
