# Task: Implement status advance subcommand

## Goal

Add the `shark status advance <key>` command to the existing `internal/cli/commands/status_group.go` (created by T-E17-F07-001). This command auto-advances an entity to its next workflow status. When multiple transitions are valid, it uses the first (primary) one. The `--to` flag allows disambiguation, and `--force` bypasses validation.

## Context

This task adds `statusAdvanceCmd` and `runStatusAdvance` to `status_group.go`. The file already exists with the shared scaffolding (dispatchTransition, dispatchNextStatus, handleStatusTransitionError, entityTransitionerFunc, init stub) from T-E17-F07-001.

The `runStatusAdvance` handler is the most complex of the four because it must:
1. Query available transitions via `dispatchNextStatus` (calls `GetNextStatus` on the appropriate service)
2. Handle terminal status and no-transitions edge cases gracefully (exit 0 with warning)
3. Resolve target status from available transitions (or `--to` flag)
4. Validate `--to` against available transitions (unless `--force`)
5. Delegate the actual transition to `performEntityTransition` via the `entityTransitionerFunc` adapter

The `buildNextStatusResult`, `performEntityTransition`, and `printEntityTransitions` helpers are already defined in `epic_next_status.go` in the same package -- use them directly.

### Technical Approach

The key complexity is the `entityTransitionerFunc` adapter pattern. `performEntityTransition` (in `epic_next_status.go`) accepts an `entityTransitioner` interface. Rather than passing a concrete service type, use the adapter defined in T-E17-F07-001:

```go
adapter := entityTransitionerFunc(func(ctx context.Context, k, ts string, o services.TransitionOptions) (*services.TransitionResult, error) {
    return dispatchTransition(ctx, entityType, k, ts, o)
})
return performEntityTransition(cmd.Context(), adapter, key, targetStatus, opts, nextStatusResult)
```

This avoids importing concrete service types and keeps the routing table in one place (`dispatchTransition`).

The `buildNextStatusResult(entityType, info)` helper from `epic_next_status.go` constructs the `*EntityNextStatusResult` that `performEntityTransition` expects. Call it after `dispatchNextStatus` returns.

For the `--to` validation loop: iterate over `info.AvailableTransitions`, check `strings.EqualFold(t.TargetStatus, to)`. If no match and not `--force`, call `os.Exit(3)` with an error listing valid transitions. Use `printEntityTransitions(nextStatusResult.AvailableTransitions)` for the list.
