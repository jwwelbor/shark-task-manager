# TD-213 research report — cancellable integration Git operations

## Scope

TD-213 makes the integration package's Git-backed operations cancellable from
their production callers. The affected capability is terminal feature
transition integration capture and its supporting run, candidate, history, and
registration operations. The change must preserve the package's existing
durable state contracts, command argument shapes, and typed errors while using
`exec.CommandContext` for every Git subprocess.

This extends the existing integration API; it does not add a second process
runner, global timeout, or background cancellation mechanism. The architect's
appropriate/proven/simple guidance supports accepting an existing caller
`context.Context` at the package boundary and threading it through helpers.

## Findings

1. **The live transition path has uncancellable Git work.**
   `FeatureService` records an integration event at terminal feature
   transition and calls integration run/candidate/commit helpers synchronously.
   Those helpers and history analysis use `exec.Command`, so a contended Git
   operation can hold the parent command without honoring its cancellation.

2. **The API surface is package-wide, not a single helper.** `CaptureBase`,
   `GetRun`, `CurrentCommit`, `UpdateCandidate`, `GetCandidate`,
   `VerifyBaseReachable`, `AnalyzeHistory`, and `AcquireRegistrationLock`
   either invoke Git directly or call helpers that do. A partial signature
   migration would leave reachable subprocesses uncancellable.

3. **Existing runner code supplies the project pattern.** Runner process
   factories already use `exec.CommandContext`; the integration package should
   use the caller context directly and preserve argument-first commands rather
   than introduce a shell or a package-owned timeout.

### Capability map

| Capability | Existing owner/evidence | Decision | TD-213 action |
|---|---|---|---|
| Parent command cancellation | CLI handlers and services | EXTEND | Pass their existing context through integration entrypoints. |
| Git subprocess cancellation | `internal/runner/*dispatcher*.go` | REUSE | Replace `exec.Command` with `exec.CommandContext`. |
| Crash-safe integration state | `run.go`, `event.go`, `candidate.go`, `history.go` | REUSE | Preserve file/CAS behavior; TD-213 changes only cancellation propagation. |
| Shared publish helpers | TD-214 | EXTEND LATER | Keep this refactor separate until cancellation signatures are stable. |

## Decisions

1. **Context is a required first parameter for every public integration
   operation that can reach Git or wait for a registration lock.** This is the
   repository's established context contract and makes cancellation visible at
   the actual API boundary.

2. **Thread context through private Git helpers and subprocess pipelines.**
   Use `exec.CommandContext(ctx, ...)`; preserve command arguments, working
   directories, typed error interpretation, and output handling.

3. **Keep TD-214 and TD-215 in the same branch but sequentially scoped.**
   First complete and test cancellation propagation. Then extract only the
   common crash-safe publish/temp-file primitive and simplify candidate
   complexity on top of the settled API, avoiding an interleaved migration.

4. **Add cancellation regression tests at production-facing callers.** Tests
   should exercise canceled contexts through integration entrypoints and at
   least one feature/CLI caller chain, not merely a private command helper.
