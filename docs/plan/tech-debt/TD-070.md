# shark task update --depends-on silently no-ops

## Description

'shark task update <key> --depends-on=<keys>' is silently a no-op: it returns SUCCESS/200 and echoes the task's unchanged depends_on, and a follow-up 'shark task get' confirms no DB write happened at all (updated_at is unchanged, byte-identical to created_at, when --depends-on is the only flag passed). Verified directly: ran 'shark task update T-E38-F09-006 --depends-on=T-E38-F09-008 --json' against a task with depends_on=null; the response and a follow-up get both still show depends_on=null and an unchanged updated_at timestamp. Root cause: registerUpdateFlags (internal/cli/commands/task_helpers.go:384) registers the --depends-on flag on the update command, but parseTaskUpdates (internal/cli/commands/task_helpers.go:272-312), which builds the services.TaskUpdates payload actually sent to the service layer, never reads cmd.Flags().Changed("depends-on") or populates a DependsOn field -- the flag is accepted by Cobra and then dropped on the floor. Found while driving E38-F09 task_generation through shark-rider run: the task_generation worker needed to add a dependency to an already-created task, hit this silently-failing path, and had to work around it with task delete+recreate (since task delete requires deleting dependents first in reverse order) -- costing 4 tasks' worth of key churn (T-018..021 became T-024..027) to route around a CLI bug. 'shark task link <key> --depends-on <keys>' (internal/cli/commands/task_link.go) is a separate, working command for creating depends_on relationships and is the correct workaround until this is fixed.

## Impact

Silent no-op on a write path is worse than a read-side gap: the CLI returns
success, so nothing signals the caller that the dependency was never recorded.
Any agent or script relying on `shark task update --depends-on` to patch a
dependency graph in place will produce a task DAG that looks correct in the
command's own echoed output but is wrong in the database — a landmine for
future dependency-graph edits. The workaround (delete + recreate, since delete
requires removing dependents first) burns task keys and, in a live run,
already cost real churn (4 tasks renumbered) while driving E38-F09's
task_generation step.

## Resolution Plan

In `parseTaskUpdates` (internal/cli/commands/task_helpers.go:272-312), add a
branch mirroring the existing `tag`/`size` handling: when
`cmd.Flags().Changed("depends-on")`, read the comma-separated value and
populate a `DependsOn` field on `services.TaskUpdates` (adding that field to
the struct if it doesn't exist), then apply it in the task service's update
path the same way `shark task link --depends-on` does. Add a unit test that
updates only `--depends-on` on an existing task and asserts both the command's
JSON response and a follow-up `get` show the new dependency.
