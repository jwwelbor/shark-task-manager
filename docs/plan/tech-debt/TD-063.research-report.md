# Research report — Cross-feature deps creatable but not updatable (dependency existence check scope mismatch)

## Scope

This report covers the two pathways for creating task dependencies across the codebase, the validation scope inconsistency between them, and the consequences for cross-feature dependency management.

The affected capability is task dependency creation and updates via two separate mechanisms:

1. **Legacy JSON field path** (`task.DependsOn` JSON field): Used by task creation, task updates, and direct repository validation
2. **Entity relationships path** (`entity_relationships` table): Used by the `EntityRelationshipService` for cross-entity relationships including cross-feature dependencies

The proposed remediation aligns the dependency existence validation scope between the two pathways so that cross-feature dependencies created via one path remain updatable via the other.

Shared vocabulary:

- **In-feature validation**: Checking that dependencies exist only within the same feature (current behavior in `ValidateTaskDependencies`)
- **Global validation**: Checking that dependencies exist anywhere in the project across all features (required for consistency)
- **DependsOn JSON field**: Legacy string field storing JSON array of task keys in `tasks.depends_on` column
- **Entity relationships**: Polymorphic table (`entity_relationships`) for managing task dependencies using foreign keys to task IDs rather than task keys
- **Scope mismatch**: The validation logic differs between task creation and task update operations, or between the JSON field path and the entity relationship path
- **Cross-feature dependency**: A task in feature F1 that depends on a task in feature F2

## Findings

1. **The ValidateTaskDependencies method constrains validation scope to a single feature, but does not document this assumption.** The validation at line 40 (`r.ListByFeature(ctx, task.FeatureID)`) restricts the task set to only those in the same feature, and lines 64-67 reject any dependency key not found in that feature-scoped set. No method documentation, comment, or type annotation signals that cross-feature dependencies are not allowed via this path. The method is called during both task creation (line 111 in repository.go) and task update (line 166), establishing in-feature-only validation as the default for the JSON field path.

2. **Cross-feature dependencies CAN be created via the EntityRelationshipService without triggering the JSON field validation.** The entity relationship service at lines 119-129 performs cycle detection across ANY entity type pair (Task→Task, Task→Feature, etc.) without feature scope constraints. A client can use `EntityRelationshipService.CreateRelationship(ctx, TaskType, taskID1, TaskType, taskID2, DependsOn)` to create a cross-feature dependency that bypasses `ValidateTaskDependencies` entirely. This relationship is stored in the `entity_relationships` table (not `tasks.depends_on`), so task creation and update validation never sees it.

3. **Updating a task created with a cross-feature relationship fails during validation.** If a task was created with a cross-feature dependency via entity relationships, and then a user attempts to update other fields of that task (title, status, priority, execution_order, etc.), the call to `ValidateTaskDependencies` at repository.go:166 checks only in-feature tasks. If any dependency in `task.DependsOn` points outside the feature, validation fails with "dependency does not exist" even though the relationship exists in the `entity_relationships` table. The two storage mechanisms (JSON field vs. relationship table) are not reconciled during validation.

4. **The validation scope assumption is not tested in table-driven test cases.** The test file `internal/repository/task_dependency_validation_test.go` uses a single `featureID` from `test.SeedTestData()` for all 13 test cases across both Create and Update scenarios (lines 13-485). All setupTasks and newTask instances use the same FeatureID. No test case explores:
   - Creating a task with a cross-feature dependency in the JSON field
   - Creating a task whose feature contains a task that depends on a task in a different feature
   - Updating a task after a cross-feature relationship has been created via EntityRelationshipService

5. **The current behavior creates an asymmetry between creation and update workflows.** The Create path (via `TaskRepository.Create`) validates dependencies and rejects cross-feature references in the JSON field. However, a user could create a task in feature F1, then use `EntityRelationshipService.CreateRelationship` to link it to a task in feature F2. At that point, the task can no longer be updated (any call to `TaskRepository.Update` will fail validation) unless the cross-feature relationship is removed first. This is not documented and not tested.

6. **The validation captures dependencies by key but has no facility to look up tasks by key across features.** The `ValidateTaskDependencies` method parses dependency keys from the JSON field (e.g., `"T-E07-F02-001"`), then checks if those keys exist in the `existingKeys` map built from `ListByFeature`. To support cross-feature dependencies via the JSON field, the validation would need to call a global "get by key" method, parse the feature from the key string, and validate that the feature exists. This is not currently done.

7. **The entity_relationships table has a foreign key constraint on task IDs, but the JSON DependsOn field uses task keys (strings).** The two storage mechanisms operate at different levels of abstraction: entity_relationships uses `tasks.id` (numeric FK), while DependsOn uses task keys (strings). This contributes to the maintenance burden and the asymmetry between paths. A task dependency can be represented in two places with no enforced consistency.

8. **Circular dependency detection in entity relationships works cross-feature, but JSON validation does not.** The `EntityRelationshipService.DetectCycle` call at line 121 performs graph traversal across entity type and ID pairs, implicitly traversing across features. The legacy `dependency.Detector` used by `ValidateTaskDependencies` only builds a graph from in-feature tasks, so it cannot detect cycles that span features.

## Decisions

1. **Align the validation scope.** Update `ValidateTaskDependencies` to validate dependencies globally (across all features/tasks) rather than limiting to in-feature only. This ensures that tasks created with cross-feature relationships via entity relationships can be updated without validation failures.

2. **Deprecate mixed dependency representation.** The JSON field and entity relationships table should not both store dependencies for the same task. Clearly document which path (JSON field vs. entity relationships) is canonical for new code, or migrate all dependencies to entity relationships over time.

3. **Add scope parameter to validation.** If in-feature-only validation is required for backward compatibility, add a scope parameter to `ValidateTaskDependencies` (e.g., `scope = ScopeInFeature | ScopeGlobal`) so callers can explicitly choose. Default to global scope for safety.

4. **Test cross-feature scenarios.** Add test cases to `task_dependency_validation_test.go` that verify:
   - Creating a task with a cross-feature dependency via JSON field is allowed or explicitly rejected
   - Updating a task with a cross-feature relationship via entity relationships succeeds
   - Circular dependencies spanning features are detected correctly

5. **Document the dependency storage contract.** Update method documentation for `ValidateTaskDependencies`, `TaskRepository.Create`, `TaskRepository.Update`, and `EntityRelationshipService.CreateRelationship` to clearly state which dependency representation (JSON field vs. entity relationships) each path uses and whether cross-feature dependencies are supported.

6. **Reconcile the two storage mechanisms.** Either:
   - Make entity relationships the canonical path and migrate JSON field dependencies to entity relationships, OR
   - Ensure that JSON field validation always accepts cross-feature keys and performs global lookup
