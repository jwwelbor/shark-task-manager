# Extract shared helpers for entity_notes rebuild migrations (rebuildEntityNotesTx pattern repeated 3×)

## Description

internal/db/db.go's migrateEntityNotesExpandNoteTypes (~180 lines, B027 round 2) largely duplicates the table-rebuild scaffolding from rebuildEntityNotesTx and migrateEntityNotesExpandEntityTypes:

- Drop dependent views (epic_display_data, feature_display_data, task_display_data, viewer_task_relationships)
- Create entity_notes_new with the new CHECK constraints
- INSERT SELECT to copy rows
- DROP entity_notes
- ALTER TABLE entity_notes_new RENAME TO entity_notes
- Recreate cascade-delete triggers for all 7 entity types (task/feature/epic/bug/change/idea/tech_debt)
- Recreate the 4 dependent views
- Recreate indexes

Each future migration that needs to expand a CHECK constraint repeats this entire scaffold. Extract:
- dropEntityNotesDependentViewsTx(tx)
- recreateEntityNotesDependentViewsTx(tx)
- recreateEntityNotesCascadeTriggersTx(tx)
- recreateEntityNotesIndexesTx(tx)

Then each migration becomes: build new CREATE TABLE SQL with the desired CHECK + 4 shared helper calls + INSERT SELECT + DROP + RENAME.

Cross-ref CC-034 (replace home-rolled migration system with a proper library) — that's a bigger swing; this TD is the surgical interim. Surfaced during simplify review of commit 6492e45.

## Impact

Each CHECK-constraint migration on `entity_notes` is ~180 lines, almost all boilerplate. The risk is that a future migration forgets to recreate one of the seven cascade triggers or four dependent views, producing a subtle data-loss or query-failure bug only caught at runtime. The boilerplate also obscures the actual change the migration is making (the new CHECK clause is one line buried in scaffolding).

## Resolution Plan

Extract four helpers in `internal/db/db.go`:

- `dropEntityNotesDependentViewsTx(tx) error`
- `recreateEntityNotesDependentViewsTx(tx) error`
- `recreateEntityNotesCascadeTriggersTx(tx) error`
- `recreateEntityNotesIndexesTx(tx) error`

Each future migration then reduces to: build the new `CREATE TABLE entity_notes_new` SQL with the desired CHECK → call the four shared helpers + `INSERT SELECT` + `DROP` + `RENAME`. Refactor the existing `rebuildEntityNotesTx`, `migrateEntityNotesExpandEntityTypes`, and `migrateEntityNotesExpandNoteTypes` to use the helpers (proves the abstraction).

Cross-ref CC-034 (replace home-rolled migration system with a proper library) — that's the larger swing; this TD is the surgical interim.
