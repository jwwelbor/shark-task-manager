# TD-191 Research Report: advance_guard idempotency early-return bypasses guard enforcement/CAS ledger

## Scope

Confirm and characterize the defect in `internal/services/entity_service.go`'s
`transitionStatus`: the idempotency early-return (target already reached)
fires before `enforceAdvanceGuard`/`recordAdvanceGuard`, so a guarded advance
landing on an entity already at its target status returns a successful no-op
with no ledger entry. Determine what invariant the guard protects, whether the
early return is reachable with `GuardAdvance: true` through real callers,
what the correct fix is without breaking replay safety, and the blast radius
across `gatepersist` and `internal/runner/controller.go`.

## Findings

### 1. What the guard protects

`docs/cli-reference/configuration.md` §"Advance Guard" (lines 203-221)
states the contract precisely: when `advance_guard.enabled` is true, a
guarded `shark status advance` call must supply `--session` and
`--from-status`, and Shark rejects the advance when either (a) the entity is
no longer at `from_status`, or (b) the same `entity + session + from_status +
outcome` tuple was already consumed. This is explicitly a **replay-rejection**
mechanism for parent-loop orchestrators (`/shark-rider run`), not an
idempotent-replay-acceptance mechanism — a repeat of the identical tuple is
supposed to fail closed with `ErrAdvanceGuardRepeatRejected` unless the
operator passes `--force-repeat --reason ...` (gated by
`allow_repeat_with_force`).

In code, `enforceAdvanceGuard` (entity_service.go:446-504) implements this:
it requires `SessionID`/`FromStatus` to be non-empty, requires the supplied
`FromStatus` to alias-resolve to the same value as the entity's actual
current status (`ErrAdvanceGuardStaleFromStatus` otherwise), and then calls
`AdvanceGuardRepo.WasConsumed(entityType, entityID, sessionID, currentStatus,
outcome)` — rejecting with `ErrAdvanceGuardRepeatRejected` if that exact tuple
was already recorded. `recordAdvanceGuard` (entity_service.go:506-530) writes
the CAS ledger entry via `RecordConsumed`/`RecordConsumedWithTx` immediately
before the actual `UpdateStatusIfCurrent` call in `updateTransitionStatus`
(entity_service.go:390-440), and `compensateAdvanceGuard` deletes that record
if the subsequent conditional update then fails — so the ledger is meant to
be written in lock-step with, and only for, an attempted state transition.

**What a missing ledger record allows to go wrong downstream:** the guard's
whole value is that every attempted guarded transition leaves a durable,
queryable trace ("session S consumed outcome O from status F for entity E")
that a *later* call with the identical tuple can check against. When the
early return at lines 272-282 fires, none of `enforceAdvanceGuard`'s checks
(session presence, `FromStatus` staleness, prior-consumption) run, and no
`RecordConsumed` call happens. Two concrete downstream failures follow:

1. **The guard's own "reject a repeat" promise silently fails for the
   single most common repeat scenario.** A guarded call is retried after
   having *already succeeded* (network hiccup, orchestrator restart, a
   parent loop resubmitting the same stage). After the first successful
   application, the entity is — by definition — now sitting at the target
   status. The retry's `resolvedCurrentStatus` therefore equals
   `resolvedTargetStatus`, so it takes the idempotency branch and returns
   `Transitioned: false` with **no `WasConsumed` check at all** — it never
   even discovers whether this is a replay it should reject. The documented
   contract ("Shark rejects the advance when ... already consumed") is
   never evaluated for this case. Today's actual behavior is silent accept,
   not documented reject; whether that specific silent-accept is *tolerable*
   depends on nothing else being triggered by the (skipped) history/
   rejection-note steps — which is true, since the early return also skips
   those — but it is not what the guard's own error taxonomy promises, and
   it removes the operator's `--force-repeat` audit trail entirely: there is
   no record that a repeat was ever attempted.
2. **The cross-run race named in the record (verified real, see §2).** A
   second, distinct session's guarded call can land on the idempotency
   branch not because *it* already succeeded, but because a *different* run
   moved the entity to the same target first. That session's attempt is
   reported as a successful transition (`Transitioned: false`, no error) with
   zero trace that this session ever touched the entity. For an
   orchestrator that treats "no error from `shark status advance`" as license
   to proceed to its next stage (heartbeat, release, cascade), this is
   probably the desired end-user-visible behavior (the entity is at the
   right place), but the audit/idempotency ledger — the thing operators are
   told to trust for "was this outcome already consumed by this session" —
   now has a gap for that session, defeating forensic replay analysis and
   `--force-repeat` gating for any *future* legitimate replay under that same
   session/from-status/outcome tuple.

### 2. Is the early return reachable with `GuardAdvance: true`? Yes — verified in two independent call paths.

**`internal/gatepersist/coordinator.go`'s `applyKickback` (lines 467-494)**
is the exact mechanism the tech-debt record names. Its own doc comment
(lines 473-478) states the window explicitly: "the kickback target ... has
no parent-observed SourceStatus the way the main transition does, so its
expected pre-transition status is read fresh here, **immediately before the
guarded Transition call** — the same narrow observe-then-transition window
`guardedTransitionOptions` accepts." Concretely:

```go
fromStatus, err := c.Status.CurrentStatus(ctx, entityType, k.EntityKey)   // read
...
guard := TransitionGuard{SessionID: req.Session.ID, FromStatus: fromStatus, Outcome: req.OutcomeKey, ForceTerminalReopen: true}
if _, _, err := c.Transition.Transition(ctx, entityType, k.EntityKey, k.TargetStatus, reason, req.Session.Agent, guard); err != nil { ... }  // act
```

Sequence that reproduces the bug:
1. Run A (session A) and Run B (session B) both compute a kickback to the
   same target entity/key with the same `k.TargetStatus` (e.g., two parallel
   gate runs both routing a shared dependency back to `code_review`).
2. Run A's `CurrentStatus` read returns the pre-kickback status (say
   `qa`), and its `Transition` call succeeds: `currentStatus=qa !=
   targetStatus=code_review`, so `enforceAdvanceGuard` runs, session A's
   tuple `(entity, sessionA, qa, outcome)` is recorded, and the status
   actually flips.
3. Run B's `CurrentStatus` read — issued after Run A's write commits, in the
   window `applyKickback` itself calls out — now observes `code_review`
   (Run A's write). `guard.FromStatus` is therefore set to `code_review`,
   identical to `k.TargetStatus`.
4. Run B's `Transition` → `TransitionStatus` computes
   `resolvedCurrentStatus == resolvedTargetStatus` (`code_review ==
   code_review`) and takes the early return at entity_service.go:273-282.
   `enforceAdvanceGuard` never runs for session B; `WasConsumed`/
   `RecordConsumed` are never called for `(entity, sessionB, code_review,
   outcome)`. `Transition` returns `(fromStatus="code_review",
   transitioned=false, nil)` — a clean success from `applyKickback`'s point
   of view, with zero ledger trace of session B ever having attempted this
   kickback.

**`internal/runner/controller.go`'s `guardedTransitionOptions`** (lines
1273-1291) is structurally identical: it is called from
`autoAdvanceCascadeParent` (line 927) and `handleAdvanceStatus` (lines 1007
and 1752), each time passing a `fromStatus`/`currentStatus` that was read by
the dispatch loop in a prior step, then used moments later in the
`TransitionStatus` call — the same observe-then-act gap, for the runner's own
parent-driven advances rather than gatepersist's kickback-to-other-entity
case. Any concurrent second runner instance (or a human `shark status
advance` racing the same session's own retry) that observes the post-move
status hits the same idempotency early return with `GuardAdvance: true`.

**`internal/cli/commands/status_group.go:490`** sets `opts.GuardAdvance =
true` whenever `cfg.IsAdvanceGuardEnabled()` — i.e. every `shark status
advance` invocation once the feature is turned on, not just gatepersist/
runner-originated ones. This means a human or script issuing `shark status
advance <key> --outcome X --session S --from-status F` twice in a row (the
second attempt being *exactly* the "repeat this call" scenario the guard's
docs describe as something that should require `--force-repeat`) will, on
the second call, most likely find the entity already at the target and hit
the same silent-success early return — the single most likely manual
reproduction of finding #1 above.

### 3. Candidate fixes and the unresolved replay-safety constraint

Three candidates were named in the task. Evaluated against the constraint
that the fix must not break the resume-safety the ingestion path depends on:

- **Run `enforceAdvanceGuard` before the idempotency check, but do not
  record.** Insufficient and unsafe alone: it would still leave no ledger
  entry for a newly observed guarded no-op, so the audit gap in finding #2
  remains open. Its stale-`FromStatus` rejection would also reject the
  legitimate `PersistenceStateComplete` recovery described below, where the
  current status is already the target but the sidecar still records the
  source.

- **Reject a guarded no-op outright.** Too strong: it would break the
  legitimate resumed-run case the coordinator explicitly designs around.
  `Coordinator.applyGuardedTransition`'s `PersistenceStateComplete` branch
  (coordinator.go:309-347) *tolerates* the transitioned-entity-already-at-
  target case as one of two acceptable outcomes of its own pre-check
  (`current` may equal either `SourceStatus` or `TargetStatus`, per the
  comment at lines 312-320 — "the transition already applied, the sidecar
  just hasn't caught up yet"). If `TransitionStatus` itself now hard-rejects
  every guarded call landing on an already-at-target entity, a legitimately
  resumed run that reaches `PersistenceStateComplete` after a crash between
  the entity's real state-flip and the sidecar's `state.Save` would now fail
  the persistence step it is specifically designed to make idempotent. This
  option breaks replay safety and must be ruled out.

- **Add a guard check to the idempotency path only with stable operation
  identity.** The existing consumption tuple identifies an entity, session,
  source status, and outcome, but it does not distinguish a duplicate call
  from recovery of the same durable operation. `recordAdvanceGuard` records
  consumption before `UpdateStatusIfCurrent` changes the entity
  (`entity_service.go:420-426`). In `PersistenceStateComplete`, recovery may
  then observe that the entity is already at `TargetStatus` after a crash but
  before `MarkTransitionApplied` and the sidecar save, and it calls
  `Transition` again (`coordinator.go:311-347`). The retry therefore encounters
  an already-consumed tuple. The `PersistenceStateTransitioned` branch verifies
  the target without retrying, but it does not cover this earlier
  persistence-complete window (`coordinator.go:348-357`). Rejecting the tuple
  can break recovery; accepting it without an operation identity leaves a
  distinct duplicate call indistinguishable. A future design could add durable
  operation identity so recovery can verify the same operation while rejecting
  a distinct duplicate, but that design is not present today and must be
  approved and tested before implementation.

  Any future guard change must remain gated by
  `s.shouldUseAdvanceGuard(opts)`. That preserves the current idempotent
  behavior for unguarded callers (`shark status set`, `shark task next-status`,
  and API handlers without `guard_advance` in the request body).

### 4. Blast radius

Every caller of `TransitionStatus`/`TransitionStatusWithTx` was enumerated
(`grep -rln "TransitionStatus("`). Only three call sites ever set
`GuardAdvance: true`:

- `internal/gatepersist/adapters.go:153` (`EntityServiceTransitioner.Transition`,
  used by `Coordinator.applyGuardedTransition` and `applyKickback`)
- `internal/runner/controller.go:1289` (`guardedTransitionOptions`, used by
  `autoAdvanceCascadeParent` and `handleAdvanceStatus`, three call sites at
  lines 927, 1007, 1752)
- `internal/cli/commands/status_group.go:490` (`shark status advance`, gated
  on `cfg.IsAdvanceGuardEnabled()`)

All other callers — `internal/services/{bug,change_card,epic,feature,
task,tech_debt,question,sprint}_service.go`, `internal/api/*_handler.go`
(unless the HTTP request body itself sets `guard_advance: true`,
which `task_handler.go`, `feature_handler.go`, `epic_handler.go`, and
`question_handler.go` all thread straight through from the request DTO),
and `internal/cli/commands/{task.go, task_next_status.go, next.go,
next_status_generic.go, change.go, question.go}` — never set `GuardAdvance`,
so `shouldUseAdvanceGuard` is `false` for them and this defect does not
affect their behavior at all, before or after any fix. The HTTP API paths
are a secondary exposure surface worth noting: if any HTTP client sets
`guard_advance: true` on a request, it hits the identical bug through
`task_handler.go:251` / `feature_handler.go:214` / `epic_handler.go:209` /
`question_handler.go:458` — the same `TransitionOptions.GuardAdvance` field,
routed through the same `EntityService.transitionStatus`.

### 5. Does `internal/runner/controller.go`'s `guardedTransitionOptions` need a separate fix?

No — it needs no changes of its own. `guardedTransitionOptions` is a pure
`TransitionOptions` builder; it does not implement the transition or the
idempotency check. The defect lives entirely in
`EntityService.transitionStatus`'s ordering of the idempotency check versus
`enforceAdvanceGuard`/`recordAdvanceGuard`. Fixing that one function fixes
every guarded caller uniformly, including both `guardedTransitionOptions`
call paths in the runner and `gatepersist`'s `applyKickback`/
`applyGuardedTransition`. This matches the task record's own framing
("equally affects `internal/runner/controller.go`'s `guardedTransitionOptions`
pattern") — "equally affects" because it shares the same downstream function,
not because it has its own independent bug to fix.

## Decisions

- **Confirmed real and currently latent in this repo.** `.sharkconfig.json`
  does not set `advance_guard.enabled`, so `shouldUseAdvanceGuard` is always
  `false` here today and no production behavior is currently affected in
  this repository. Severity should be scored as a **real correctness/audit
  gap in a shipped, documented feature**, not a hypothetical — any adopter
  who *does* enable `advance_guard` (the feature exists specifically for
  `/shark-rider run` parent loops, i.e. exactly the environment most likely
  to hit concurrent kickbacks) is exposed today, with the single most likely
  trigger being an ordinary repeat `shark status advance` call with
  identical `--session`/`--from-status`/`--outcome`, not only the rarer
  cross-run kickback race.
- **Existing remediation:** no code fix is present; the idempotency branch
  still returns before guard enforcement and ledger recording. The
  `Resolution Notes` in `docs/plan/tech-debt/TD-191.md` preserve an earlier
  architect decision to retain the idempotent `Transitioner` contract and
  require replay-identity design outside `TransitionStatus`. That is a
  documented design constraint, not a remediation.
- **Affected capability and candidate fit:** advance-guard replay rejection
  and its CAS audit ledger. The in-path check analyzed in §3 would extend
  existing guard behavior only for guarded idempotent calls and leave
  unguarded no-ops unchanged, but it has not shown that it preserves
  `gatepersist` recovery. `PersistenceStateComplete` can re-call the transition
  after the database write and before the sidecar checkpoint; rejecting an
  already-consumed tuple could stop that recovery. A safe implementation must
  account for this path, likely with durable operation identity. Do not treat
  the narrower check as ready to implement.
- **Owner decision remains open:** the earlier architect decision recorded
  in `TD-191.md` requires replay-identity design before changing the
  idempotent `Transitioner` contract. The later triage note adds the ordinary
  CLI `status advance` path, and this report now identifies the
  `PersistenceStateComplete` recovery window that the narrower in-path check
  did not account for. These findings do not ratify that check. The owner must
  choose a replay-identity design or explicitly retain the current idempotent
  behavior and reconcile the documented rejection contract before
  implementation. Revisit `TD-191.md`'s proposed option 1 in light of this
  recovery evidence.
- **Out of scope for this report:** actually implementing the fix (TD-191
  is in research; implementation follows the owner decision).
