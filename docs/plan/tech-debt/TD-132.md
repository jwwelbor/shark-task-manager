# run-lifecycle.sh never populates content_root, leaving evaluate-lifecycle.sh's content-digest crosscheck dead in real runs

## Description

The I-05 producer (bench/scripts/run-lifecycle.sh:246) computes shark_content_digest as sha256(git rev-parse HEAD^{tree}) and never sets content_root/shark_data_root on the I-05 record. evaluate-lifecycle.sh's independent content-digest crosscheck (validate_candidate_snapshots, ~line 273) only fires when content_root is present, so in every real evaluation run the crosscheck is skipped and a forged/corrupted shark_content_digest goes undetected. Only tc075_content-identity_x12_test.sh exercises the branch, by manually injecting content_root into a synthetic I-05 fixture (see comment at top of that test acknowledging this).

Wiring this up for real is a producer behavior change, not a mechanical fix: run-lifecycle.sh's digest is a whole-repo git-tree hash, while content_digest() in evaluate-lifecycle.sh walks a directory and hashes file contents -- two incompatible schemes. Reconciling them requires deciding what content_root should point at in a real run (the installed internal/sharkdata/default_data bundle vs. an installed copy in the scratch project) and switching run-lifecycle.sh's shark_content_digest computation to match content_digest()'s walk-based scheme, or building an explicit two-scheme compatibility path.

Found during E40-F09 finish-feature code review (round 15+).

## Impact

`evaluate-lifecycle.sh`'s content-digest crosscheck (`validate_candidate_snapshots`,
~line 275) only fires when `content_root` is present on the I-05/I-07 join,
and `run-lifecycle.sh` never populated it. Every real evaluation run
therefore skipped this check, so a forged or corrupted `shark_content_digest`
on a live I-07 record went undetected in production runs; only
`tc075_content-identity_x12_test.sh`'s hand-injected synthetic fixture ever
exercised the branch.

## Resolution Plan

ADR-F12-03 (`docs/plan/E40-shark-bench-workflow-benchmarking-harness/E40-F12-live-i-05-evidence-bundle-producer-for-lifecycle-v/spec.md`
§2.7): `content_root` is the installed Shark-data canonical content tree
inside the scratch Shark project (`<scratch_root>/shark-data`, the
`shark admin install-shark-data` default location) -- not the repo's own
`internal/sharkdata/default_data` path, and not a whole-repo git-tree hash.
`run-lifecycle.sh`'s `scenario_identity()` now declares `content_root` at
that path, sets `content_digest_scheme: "walk_v1"`, and computes
`shark_content_digest` with a walk-based digest byte-for-byte identical to
`evaluate-lifecycle.sh`'s own `content_digest()` (same traversal order, same
separator bytes) so the two independently-computed digests can agree. A
record without `content_digest_scheme` is treated as the legacy
whole-repo-tree scheme and is never silently compared against a `walk_v1`
record. The half-wiring this resolution explicitly avoids -- declaring
`content_root` while keeping the legacy digest -- would have made the
crosscheck fire on every run regardless of real corruption.

## Resolution Notes

Resolved by T-E40-F12-005. `bench/scripts/run-lifecycle.sh`'s
`scenario_identity()` (now taking the resolved `scratch` root as a
parameter) sets `content_root`, `content_digest_scheme: "walk_v1"`, and the
walk-based `shark_content_digest`. Guarded by
`bench/scripts/tests/tc116_content_identity_crosscheck_test.sh`
(AC-016/AC-017), driven with `--mode live` end-to-end (a real dispatch,
claim, adapter, and status-advance sequence, not `--mode dry-run`'s
synthetic worker short-circuit): a real live run's
`identity.shark_content_digest` equals `evaluate-lifecycle.sh`'s own
`content_digest()` over the real installed `content_root`, the crosscheck
does not fire on a matching pair or on a legacy-shaped
(scheme-marker-absent) record, and it does fire once a byte under
`content_root` is corrupted after the run -- closing this tech debt.
Verified against `bench/scripts/run-lifecycle-batch.sh dispatch_pair()`
(the real batch driver): the ephemeral scratch copy `content_root` resolves
into is only `rm -rf`'d after `evaluate-lifecycle.sh` has already run
against it, so the crosscheck stays live in the batch pipeline too, not
just in tc116's own harness.

Known limitation, not closed by this task: `content_root` resolves to
`<scratch_root>/shark-data`, the `shark admin install-shark-data` default
location, but nothing in `run-lifecycle.sh` or `run-lifecycle-batch.sh`
installs Shark-data into a configured `scratch_root` -- that is the
operator's own scratch-project template responsibility (`scratch_root` is
already documented elsewhere as "a pre-built scratch Shark project"). When
`shark-data/` is absent, `scenario_identity()` falls back to
`sha256(b"")` for `shark_content_digest` rather than the retired
whole-repo-tree scheme (still tagging the record `content_digest_scheme:
"walk_v1"`) so a half-wiring never masquerades as legacy. Two runs against
scratch projects that both lack an installed `shark-data/` -- or that
install genuinely different content but neither installs it -- will
therefore compare as identical content identity. Closing that gap means an
operator-facing precondition check (e.g. in a scratch-project provisioning
script or an admission-time gate), out of this task's scope.
