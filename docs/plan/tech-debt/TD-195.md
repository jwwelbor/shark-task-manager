# Custom-key resolution logic duplicated 3x (epic/feature/task) with no shared abstraction

## Description

deep-review Angle C/D: the derive-then-validate-custom-key + duplicate-check + suggest-next-available-key pattern is independently implemented in EpicService.CreateEpic, FeatureService.CreateFeature (resolveFeatureCustomKey), and taskcreation.Creator.CreateTask. Same control-flow shape and error-message template repeated 3x. Also contributed to CreateFeature's cyclomatic complexity growing 27->34 and CreateTask's growing 37->41 (gocyclo) by inlining the new logic rather than extracting a helper. Fix: extract a shared duplicate-key-error-with-suggestion helper (e.g. formatDuplicateKeyError(entityKind, key string, suggest func() string) error), and extract each entity's custom-key resolution into its own named helper (mirroring the existing resolveFeatureCustomKey) so CreateFeature/CreateTask's own complexity stays flat.

## Impact

A fourth entity type needing custom-key support requires a fourth copy-paste of the same logic; CreateFeature/CreateTask are now above the project's complexity comfort zone.

## Resolution Plan

Extract a shared duplicate-key-error-with-suggestion helper and per-entity key-resolution helpers so each Create* method's own complexity stays flat.
