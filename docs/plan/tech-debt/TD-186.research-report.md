# TD-186 research report

## Scope

Determine whether `RunLock.Release`'s lack of an ownership token is reachable
in practice given the actual `AcquireRunLock` call sites, what a minimal-risk
fix would look like given this package's no-follow/TOCTOU discipline, and
whether prior art in the repo already solves an equivalent problem.

- [x] `scope_vocabulary` — Evidence: internal/gaterun/lock.go

## Findings

**Same-handle double-release is already guarded.** `Release` (lock.go:78-90)
checks `l.dh == nil` and errors `"already released"` before nilling `l.dh`
and unlinking, so calling `Release` twice on the same `*RunLock` value cannot
double-delete. The record's literal "double-Release" framing is already
addressed; the real gap is cross-holder: the lock file carries no identity,
so a `Release` firing after the file was recreated by a different holder
unlinks that holder's lock unconditionally via `removeAt(dh, lockFileName)`.

**Call-site audit — the discipline is airtight today.** There are exactly two
non-test call sites of `AcquireRunLock`, both in the pattern
"acquire → `defer func() { lock.Release() }()`" with no goroutine handoff and
no path that lets the `RunLock` value outlive the function that acquired it:

- `internal/cli/commands/run_resume.go:419-427` —
  `resolveResumeStatusAndDecision` acquires and immediately defers Release;
  the function returns synchronously (no goroutines spawned, no context
  passed to a background worker holding the lock past this call's return).
- `internal/gatepersist/coordinator.go:102-109` — `Coordinator.Persist`
  acquires via `c.acquireLock(req)` (coordinator.go:155-163, a thin wrapper
  over `gaterun.AcquireRunLock`) and defers Release identically.

Both defers fire on ordinary return AND on panic unwind (Go's `defer`
semantics), so the only way `Release` fires "late" is if the entire OS
process holding the lock hangs indefinitely inside the critical section
(e.g. blocked I/O, deadlock) — not if it crashes. A crashed process cannot
call `Release` at all; nothing survives to fire it. So the cross-holder
window the record worries about requires a specific, narrow combination: an
operator declares a lock stale and removes it (the documented recovery path,
lock.go:48-51) **while the original holder is actually still alive but
hung**, a second process then acquires the freshly-cleared lock, and the
first process's block eventually clears and its deferred `Release` fires —
unlinking the second holder's lock file. This is reachable in theory but
requires an operator misdiagnosing a hung-not-crashed process as dead, which
is exactly the scenario `AcquireRunLock`'s own doc comment assumes won't
happen ("Operators recovering from a genuinely crashed holder must remove
the stale lock file directly," lock.go:49-51). The record's "not exploitable
under current call sites" is correct for the crash case and only
theoretically true for the hung-process case.

**What an ownership-token fix would look like, and its own TOCTOU cost.**
`AcquireRunLock` creates `.run.lock` via `createExclAt(dh, lockFileName,
0o600)` (lock.go:64) and immediately closes it without writing content
(fsio_nofollow_unix.go:88-99 shows `createExclAt` returns a writable `*os.File`
that the caller currently discards). Two candidate fixes:

1. **Content nonce**: write a random token into `.run.lock` on acquire; on
   release, open-relative-to-`dh`, read, compare to the token held in
   `RunLock`, and unlink only on match. This reuses the exact pattern this
   package already applies for `identity.json` — `CreateIdentity` /
   `ReadIdentity` / `VerifyRunIdentity` (identity.go:74-141) is a read-and-
   compare-before-trusting check against directory-handle-relative sidecar
   content, so there is direct, working prior art for this shape in the same
   package. But it does **not** close the race: nothing in POSIX offers an
   atomic "unlink if content still equals X" — between the read and the
   `unlinkat` call (fsio_nofollow_unix.go:125-130), the file could be
   unlinked and recreated with new content, and the pending `unlinkat` would
   still remove the new file by name, unaware content changed underneath it.
2. **Inode/device fencing** (cheaper, same residual race): record `(dev,
   ino)` via `fstatat` at acquire time, compare via a second `fstatat`
   immediately before `unlinkat` at release, and skip the unlink on
   mismatch. This avoids the extra open+read of approach 1 and is the
   standard stale-lock fencing idiom, but has the identical unavoidable gap:
   POSIX has no atomic "unlink this exact inode by name," so a delete-then-
   recreate landing inside the fstatat→unlinkat window still wins the race.

Either fix strictly *narrows* the exposure window (from "always wrong on any
late release" to "wrong only if a recreate lands in a few-microsecond
compare-then-unlink gap") but cannot eliminate it with the primitives this
package already restricts itself to (no flock, no O_TMPFILE rename-swap
usable here since the lock's job is presence/absence, not content). A design
that wanted a truly race-free release would need a different primitive
entirely (e.g. `flock(2)` advisory locking tied to the fd itself, released
automatically on process exit) rather than a presence-marker file, which is
a larger change than this record's scope.

**Prior art for ownership-token concepts, but at a different layer.** The
repo's claim/lease system (`internal/services/question_service.go:31-32`,
`internal/services/question_workflow_service.go:302-340`) uses expected-
status/expected-content compare-and-swap with a session/owner string, and
the route-based workflow's claim/session model (docs/guides/route-based-
workflow.md §4) uses session ids for the same purpose. Both are DB-backed
compare-and-swap, not filesystem locks, so they solve the identical *shape*
of problem (don't let a stale holder mutate state another holder now owns)
but aren't directly reusable here — `gaterun` deliberately avoids a database
dependency and works only through no-follow directory-handle file
operations.

## Decisions

Keep TD-186 open as hardening tech debt rather than closing wont-fix — but
do not treat it as urgent. The call-site audit shows the cross-holder window
requires an operator to misdiagnose a merely-hung (not crashed) holder as
dead, which is outside the documented recovery contract; genuinely crashed
holders can't race a stale-lock cleanup because they have no thread left to
call `Release`. If this is picked up, prefer the inode/device fencing
approach (cheaper than a content nonce, same residual guarantee) implemented
as: `AcquireRunLock` `fstatat`s the file it just created and stores
`(dev, ino)` on `RunLock`; `Release` `fstatat`s the current `.run.lock`
immediately before unlinking and skips the unlink (returning a distinct
"lock file changed underfoot" error) on any mismatch. Do not attempt a fully
race-free design without adopting `flock`-style locking, which is a larger
change than this record's scope.
