# cascadeIntegrationGuard's non-epic no-op branch untested with the real guard type

## Description

cascadeIntegrationGuard.EnsureBaseCaptured (run_cascade_integration_guard.go) no-ops for any entityType != 'epic' -- the scoping that stops a feature-level cascade from re-firing epic-integration capture against the wrong key. No test anywhere drives this branch with the real guard type: both tests in run_cascade_integration_test.go only call ctrl.Run with EntityType: 'epic'. The closest coverage (internal/runner/controller_test.go's feature-level cascades) either passes no IntegrationGuard at all (bypassing the check via the nil-guard branch) or, where a guard is wired (fakeCascadeIntegrationGuard), is only ever driven with an epic root. integration.CaptureBase performs no key-format validation on its argument, so a wrongly-scoped call would silently create a spurious .shark/integration/<feature-key>/run.json rather than error. Fix: add a test constructing runner.RunController with the real cascadeIntegrationGuard{commandLabel:"run"} driving a feature-level cascade (RunOptions{EntityType: "feature"}) in a directory with no resolvable git HEAD, asserting the cascade does NOT block -- i.e. the no-op genuinely fires. This would fail today if the entity-type check were removed or inverted; the current suite would not catch that. From code-review of the E34 (F06-F11) integration diff, finding F10 (non-blocker).
