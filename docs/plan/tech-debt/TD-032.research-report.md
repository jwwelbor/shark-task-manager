# TD-032 research report

## Scope

Replace hard-coded task-status presentation in dependency displays with the task workflow's configured status metadata, without changing dependency semantics or JSON output.

## Research checklist

- [x] `scope_vocabulary` — Evidence: `docs/plan/tech-debt/TD-032.md`; `shark td get TD-032 --json`.
- [x] `affected_implementation_or_contract` — Evidence: `internal/cli/commands/task_deps.go:188-354` renders human dependency output; JSON remains returned before those renderers.
- [x] `pattern_contract` — Evidence: `internal/workflow/service.go:236-345` supplies terminal, blocked, metadata, and ordered-status semantics for a task-level workflow.

## Capability map

| Capability | Decision |
| --- | --- |
| Workflow-aware status rendering | EXTEND the existing workflow service at the dependency-display boundary; do not add a second status-classification source. |

## Findings

`task_deps.go` was the active incorrect presentation surface: its icon switch and every dependency legend named the default statuses. The other files named by the historic entry are not all display-only duplication: their remaining literals implement lifecycle messaging or already consume workflow metadata. The dependency tree shared the same icon helper and now inherits the configured classification too.

## Decisions

Classify icons by configured terminal and blocked semantics, then by metadata phase for development/execution and review/QA/approval. Generate the legend from `GetAllStatuses`, so renamed workflows show only their configured status names. The regression test uses `queued`, `building`, `verifying`, `waiting`, and `shipped`; it would fail if the legacy names or icon switch were restored.
