# gaterun/lock.go: RunLock.Release has no ownership token

## Description

internal/gaterun/lock.go's RunLock.Release has no ownership token; a double-Release on a stale handle could theoretically delete a different holder's lock file. Not exploitable under current call sites (one AcquireRunLock -> one deferred Release, no reuse). Track as hardening tech-debt. From E34-F05 code-review round 1, finding F13.

## Impact

Both current `AcquireRunLock` call sites (`internal/cli/commands/run_resume.go:419`,
`internal/gatepersist/coordinator.go:160`) acquire-then-defer-Release
synchronously with no goroutine handoff, so same-run double-release cannot
happen and a crashed holder cannot race a cleanup (nothing survives to call
`Release`). The only theoretical exposure is an operator manually removing a
lock file that belongs to a holder that is merely hung, not crashed — outside
the documented recovery contract (see lock.go:48-51) — followed by that
holder's `Release` eventually firing and deleting the new holder's lock file.
No production incident or reachable path under current call sites was found;
see the linked research report for the full call-site audit.

## Resolution Plan

Not scheduled as active work. If picked up, add an inode/device fencing
check rather than a content nonce: `AcquireRunLock` records the `(dev, ino)`
of the lock file it just created on `RunLock`; `Release` re-`fstatat`s
`.run.lock` immediately before unlinking and skips the unlink (returning a
distinct error) on any mismatch. This narrows, but per POSIX cannot fully
close, the compare-then-unlink race — a fully race-free design would require
switching to `flock`-style locking, which is out of scope for this record.

## Resolution Notes

Researched 2026-09-18 (TD-186.research-report.md). Left open as low-priority
hardening tech debt rather than closed wont-fix, since the fencing fix above
is cheap and available whenever this file is next touched, but not urgent —
the reachable window requires an operator to misdiagnose a hung (not
crashed) holder as dead.

Implemented 2026-09-18: inode/device fencing (this record's original plan)
was built and tested first, but rejected — on this repo's ext4 checkout, a
plain remove-then-create in the same directory deterministically reuses the
freed inode, so it gave zero protection against the exact scenario this
record targets. Shipped a random content-nonce fence instead (write a token
at acquire, read-and-compare-before-unlink at release), reusing the existing
no-follow read helper.
