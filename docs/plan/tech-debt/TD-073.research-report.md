# TD-073 research report

## Scope

TD-073 covers the shared Question bounded-text denylist in
`models.ValidateQuestionBoundedText`. The validator already rejects its seven
credential, prompt, and transcript markers case-insensitively. It does not
recognize three equivalent credential-label forms when whitespace or punctuation
differs from the current literal markers: `BEARER:`, `password =`, and
`Authorization :`.

This work must strengthen that one validator and its contract coverage. It does
not introduce a second Question validator, change byte bounds or trim/UTF-8
rules, broaden the denylist to unrelated secret formats, or change Question
workflow, persistence, or related-document capabilities.

## Findings

1. **The gap is current and deliberately characterized.** The validator
   lowercases input and uses `strings.Contains` with literal `"bearer "`,
   `"password="`, and `"authorization:"` markers. It rejects case variants,
   but the contract test verifies that `BEARER:`, `password =`, and
   `Authorization :` currently pass. The test labels these as `known_gap` and
   names TD-073 as the required owner.

2. **The validator is the correct remediation seam.** `QuestionState.Validate`
   uses it for all persisted Question identities, responses, and resolution
   pointers. The service also routes terminal reasons and focused read
   identities through the same function. Changing a command-specific caller
   would leave other durable and transport paths inconsistent and would violate
   E38-F09's existing single-validator boundary.

3. **The existing contract has both policy and sink coverage.**
   `TC-SEC-01-01` directly calls the real validator for each marker across
   response summary and evidence pointer, then uses a real CLI and database to
   prove rejection occurs before persistence. `TC-SEC-01-02` separately proves
   case handling and currently pins the three accepting near-misses. TD-073
   should convert the `known_gap` table into rejection expectations and retain
   the direct-call coverage; add one representative CLI persistence assertion
   for a whitespace/punctuation variant so the repaired policy is also proven
   at a public write sink.

4. **A targeted pattern is safer than normalizing all input.** Collapsing or
   deleting whitespace across an entire field can change unrelated text and
   can accidentally widen matching. Three small case-insensitive patterns can
   express the actual variants without transforming stored input:
   `password\s*=`, `authorization\s*:`, and a bearer pattern that accepts a
   whitespace or colon delimiter after `bearer`. The implementation should keep
   the remaining four marker checks unchanged.

5. **No related-document link can be registered for TD-073.** The static CLI
   registration exposes no `--tech-debt` flag or tech-debt service dispatch.
   Adding one would be unrelated capability work. The standard adjacent sidecar
   path, `docs/plan/tech-debt/TD-073.research-report.md`, provides the durable
   discoverability supported today.

## Decisions

1. **Extend `ValidateQuestionBoundedText`; do not add a second validator.**
   Retain the existing trim, UTF-8, byte-bound, and error-message behavior.

2. **Replace only the three vulnerable literal checks with targeted,
   case-insensitive boundary patterns.** The patterns must reject the three
   characterized variants while preserving the current intent: `password` is a
   credential label only when followed by optional whitespace and `=`,
   `authorization` only when followed by optional whitespace and `:`, and
   `bearer` only when followed by a credential delimiter (whitespace or `:`).
   Keep `api_key`, `system prompt`, `user prompt`, and `assistant:` as their
   current literal case-insensitive checks.

3. **Update the contract from characterization to regression protection.**
   Change the `known_gap` subtests to require rejection of all three variants
   and remove language claiming their acceptance is expected. Preserve the
   literal-marker and case-variant tables. Add a real `question respond` path
   case using one repaired variant and assert status and `context_data` remain
   unchanged after rejection.

4. **Use focused unit coverage for the pattern boundary.** Add direct validator
   cases that show ordinary prose such as `password policy` and
   `authorization model` remains acceptable. This prevents the stronger
   matching from treating unrelated words as credentials.

5. **Do not register a related document.** Tech-debt entities are unsupported
   parents for `related-docs`; changing that is outside TD-073.

**Recommended outcome: implement.** Make the narrow shared-validator repair,
replace the accepting characterization with rejecting regression coverage, and
verify both the direct validator and a real Question write path before closing
TD-073.
