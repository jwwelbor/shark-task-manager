# TD-153 research report — terminal-success workflow contract

## Scope

Determine whether custom terminal statuses satisfy dependencies and contribute
to progress when their workflow metadata omits `exclude_from_progress`.

## Ubiquitous vocabulary

A *terminal status* ends a workflow path. A *successful terminal status*
satisfies dependencies and counts toward progress. An *abandonment terminal
status* ends work without credit. `ExcludeFromProgress` currently describes
the latter only when explicitly set.

## Findings

The workflow schema represents `ExcludeFromProgress` as a bool, so omitted
and explicit false cannot be distinguished. Validator rules do not require an
abandonment declaration for custom terminal statuses. Sprint readiness credits
any terminal status not explicitly excluded. `internal/progress/calculator.go`,
`internal/services/feature_progress_service.go`,
`internal/services/aggregate_policy.go`, and
`internal/services/epic_analytics_service.go` share that metadata dependence
and therefore the fail-open behavior. The repeated
`DependsOn` parsing and repository batching nits are safe refactors only after
the terminal-success policy is settled.

The risk crosses the workflow configuration boundary: an omitted custom status
field is accepted by validation, then drives independently deployed readiness
and progress calculations. Fixing only sprint readiness would leave the same
misconfiguration silently changing other progress projections.

## Decisions

Research passes, but implementation is owner-gated. The material architecture
decision is recorded in `docs/council/escalations/e-td153-terminal-success-contract.yaml`:
either add an explicit successful-terminal selector, or validate that every
non-success terminal status explicitly declares exclusion. Do not select one
locally or refactor consumers first.
