# TD-031 research report

## Scope

Make any repository fallback to legacy bug or change-card terminal statuses observable while retaining workflow-derived filtering for normal service callers.

## Research checklist

- [x] `scope_vocabulary` — Evidence: `docs/plan/tech-debt/TD-031.md:1-15`; `internal/repository/bug/repository.go:236-279`; `internal/repository/changecard/repository.go:16-18,319-323`.
- [x] `affected_implementation_or_contract` — Evidence: `internal/services/bug_service.go:430-440`; `internal/services/change_card_service.go:274-286`.
- [x] `pattern_contract` — Evidence: both service list methods supply `workflowSvc.GetTerminalStatuses()` before repository filtering.
- [x] `dependency_impact` — Evidence: `internal/repository/task/dependency.go:489-493` documents the same repository fallback debt shape for task terminal statuses.

## Capability map

| Capability | Source | Decision |
| --- | --- | --- |
| Workflow-derived terminal filtering | bug and change-card services | REUSE — preserve the existing caller contract. |
| Legacy repository fallback | bug and change-card repositories | EXTEND — emit a warning when compatibility fallback is reached. |

## Findings

Normal CLI/service list paths already provide the terminal-status vocabulary from the configured workflow. The fallback remains reachable by direct repository callers and therefore can misclassify custom workflow statuses silently; immediate observability is a safe compatibility step while future callers are audited.

## Decisions

Keep fallback behavior for compatibility but log a structured warning at each fallback site, identifying the entity type and the missing caller-supplied vocabulary. Do not substitute a hard failure in this batch because the repository API is public to tests and non-service callers.
