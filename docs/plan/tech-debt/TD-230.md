# gate_result_v1's coordinator-side (Rider) ingestion path is underdocumented — no runnable example of the apply-result invocation or run_id semantics

## Description

Found while a Shark Rider session (wwgm project) hit its first `gate_result_v1`
step of a multi-hour, 26+ resumption run — every other step in that entire
session used the legacy free-form `RECOMMENDED OUTCOME:` directive grammar,
so this was genuinely the first time the coordinator side of the protocol
had to be exercised in practice, not just read about.

`context/host-adapter-contract.md`'s "`result_contract`-gated dispatch"
section (and `verbs/run.md`'s mirroring section) correctly says a
`gate_result_v1` step requires the adapter to "route the worker's terminal
envelope through the shared ingestion CLI surface instead of interpreting it
directly," and names the underlying boundary
(`internal/runner.IngestGateResult`). What neither doc says:

1. **The actual command.** Nothing in either doc names `shark run
   <entity-key> --apply-result <file> --run-id <id> --session <sid>` as the
   CLI surface. I had to `grep -rn "IngestGateResult"
   internal/cli/commands/` in this repo, find `run_apply_result.go`, and
   read the Go source directly to discover the flag is on `shark run`, not
   a dedicated `shark gate ingest` or similar (I tried `shark gate --help`
   first, reasonably, and got "unknown command").
2. **Where `run_id` comes from.** `run.go`'s `--run-id` flag help text just
   says "Durable run_id for --apply-result" — it doesn't say whether this is
   an existing id you look up somewhere, or one the caller invents fresh for
   this dispatch. I had to read `runApplyResult`/`applyResultIngest` in
   `run_apply_result.go` to confirm it's caller-assigned and opaque (any
   string works; it's just the persistence key for this gate stage's
   sidecar) — there's no `shark next`-returned `run_id` field to consume,
   which a reasonable first guess would expect given `shark next --json`
   returns `prompt_sha256`/`prompt_bytes` alongside everything else needed
   for dispatch.
3. **Whether the lease auto-releases.** `run_apply_result.go`'s own comment
   (a code-review round-7 finding note) documents that a terminal resulting
   status triggers an automatic `RetirementConfirmed`+`RunConcluded`
   re-ingest that releases the lease — but a NON-terminal resulting status
   (e.g. `specification` → `research` mid-feature-workflow, the case this
   session hit) does not say explicitly whether the caller still needs a
   separate `shark release` call afterward. This has to be inferred from
   reading the ingestion code path, not from either coordinator-facing doc.

None of this is wrong, exactly — the underlying design (one shared
`IngestGateResult` boundary, no second Rider-side parser) is sound, and once
worked out, using it was mechanically straightforward. But a coordinator
correctly following the documented Rider procedure hits a dead end at
exactly the point the docs say "call the ingestion command" without naming
it, and has to fall back to reading Go source mid-dispatch to keep going.

## Impact

- Any Shark Rider (or other coordinator) implementation hitting its first
  `gate_result_v1` step cold will stall at the same point: told to use "the
  shared ingestion CLI surface" with no runnable example.
- Increases the activation cost of the newer, better-designed protocol
  relative to the legacy free-form grammar it's meant to replace — ironic,
  since `gate_result_v1` exists specifically to reduce a recurring
  prose-interpretation defect class (this same wwgm session independently
  hit that legacy-grammar failure mode multiple times: a forgotten
  version-bump, ambiguous "no outcome at all" handling, etc. — the exact
  problem `gate_result_v1`'s mechanical `outcome_roles` validation is
  designed to close). If the migration path itself is friction-heavy,
  adoption stalls and the legacy grammar's defect class persists longer
  than it needs to.
- Low severity in the sense that it's a one-time discovery cost per
  coordinator implementation, not a recurring runtime defect — hence
  `severity: medium`, not `high`.

## Resolution Plan

Add a concrete, runnable example to `context/host-adapter-contract.md`'s
`result_contract`-gated dispatch section (mirrored in `verbs/run.md`),
covering:

1. The exact command: `shark run <entity-key> --apply-result <path-to-envelope-file> --run-id <id> --session <sid>`.
2. Explicit statement that `run_id` is caller-assigned and opaque for this
   ingestion path — any durable string the coordinator chooses works, it is
   not looked up from `shark next`'s response or generated by the CLI. State
   what it's *for* (the GateResult persistence sidecar's key, needed for
   `--resume-run` recovery) so a coordinator can choose a sensible one (e.g.
   `<entity-key>-<step-status>-<timestamp>`) rather than a random string.
3. Explicit statement of the lease-release contract for both terminal and
   non-terminal resulting statuses. **Now confirmed empirically** (same
   wwgm session, immediately after filing this item): a non-terminal
   resulting status does NOT auto-release — `shark claims` still showed the
   entity held under the caller's session after a successful `--apply-result`
   that transitioned `specification` -> `test_planning`. The caller must
   issue a separate `shark release <key> --session <sid> --outcome <key>`
   call itself in that case. Only a terminal resulting status triggers the
   automatic `RetirementConfirmed`+`RunConcluded` re-ingest documented in
   `run_apply_result.go`'s code-review-round-7 comment. Document this
   explicitly as part of the fix — it's the one item here that isn't
   readable from the doc-comment alone, only from behavior.
4. A minimal worked example: sample envelope JSON in, sample command, sample
   `applyResultOutput` JSON out.

Consider also: since this is genuinely the first practical exercise of the
coordinator-side path in at least one real multi-hour Rider session, it's
worth grepping for other early adopters' experience (if any exist) before
finalizing the doc, in case there are additional undocumented gotchas this
single session didn't happen to hit.

## Resolution Notes

Two more concrete findings from continued use in the same wwgm session,
both on the **worker-authoring side** rather than the coordinator side this
item started with — worth folding into whatever doc fix addresses this:

1. **`evidence[]` item shape is undocumented in the schema comments/examples,
   and workers reach for the wrong shape by default.**
   `worker-control-schema.yaml`'s every single example (`kind: final`,
   `question`, `needs_council`, etc.) shows `evidence: []` — always empty,
   never once populated. The actual required shape
   (`internal/workercontrol/envelope.go`'s `EvidenceRef` — `kind`, `pointer`,
   optional `summary`/`command`/`working_directory`/`exit_code`) is only
   discoverable by reading the Go struct directly. A worker asked to cite a
   file it wrote naturally emits `"evidence": ["path/to/file.md"]` (a bare
   string array) — which decodes as a shape violation
   ("must be a well-formed JSON object matching the worker-control envelope
   shape") with an error message that doesn't say *which* field is wrong.
   Add at least one non-empty worked example to the schema file showing a
   populated `EvidenceRef` (e.g. `{"kind": "file", "pointer": "<path>",
   "summary": "<one line>"}`).
2. **The 1000-byte `gate_result.summary` bound is easy to blow even when
   explicitly warned.** First occurrence: a worker's spec-review envelope
   summary ran ~2x over the limit despite the dispatch prompt only saying
   "compact verdict statement." Second occurrence, same session: a
   *different* worker's test-planning envelope summary still landed 27
   bytes over 1000 even after the dispatch prompt was updated to explicitly
   state the exact byte cap and say "2-4 sentences." The failure mode is
   binary (whole ingestion rejected, not truncated) with no early warning —
   a worker has no way to self-check byte count before submitting. Consider
   either: relaxing the CLI to truncate-with-a-flag-and-warn instead of
   hard-rejecting, or having the dispatch-prompt guidance include a concrete
   worked-length example (not just a byte number) so workers calibrate
   better, since stating the number alone twice in a row wasn't enough.

Both were worked around at the coordinator level in this session (rewriting
the envelope's `evidence`/`summary` fields before re-submitting) rather than
re-running the worker, since the underlying artifact — the actual test
plan/spec document — was already correct; only the thin envelope wrapper was
malformed.
