## Context

Filed alongside B062 (owner/resolution-kind discoverability). While tracing
that bug, resolving a single Question required, in order:
`shark claim <key> --by=<owner>` → `shark question respond <key> --responder=<owner>
--session=<claim-session>` → `shark question resolve <key> --owner=<owner>
--resolution-kind=<kind> --resolution-pointer=<pointer>` — none of which is
stated as a sequence anywhere in `--help` output, and the `--owner`/
`--resolution-owner` flag naming is inconsistent between commands that refer
to the same underlying `QuestionState.ResolutionOwner` field
(`configure-workflow` uses `--resolution-owner`; `resolve`/`withdraw`/
`supersede` use `--owner`).

## Concrete issues

1. `--resolution-kind`'s valid enum (`local_clarification`, `feature_change`,
   `product_decision`, `architecture_decision`, `follow_up_work`,
   `no_lasting_consequence`) is not printed anywhere in `--help`; each value
   also has its own pointer-format validation rule
   (`internal/services/question_workflow_service.go:201-238`) that is only
   discoverable by trial-and-error or reading source.
2. `--owner` (resolve/withdraw/supersede) and `--resolution-owner`
   (configure-workflow) name the same field differently across sibling
   commands.
3. The claim → respond → resolve ordering dependency is enforced
   (`"active claim does not match responder session"`,
   `"Question must be ready for resolution with all responders completed"`)
   but not documented as a required sequence in any single `--help` output.
4. No command surfaces `ResolutionOwner`/`ResolutionKind`/responder status for
   a Question the caller doesn't already have matching credentials for —
   see B062.

## Ask

A pass over `internal/cli/commands/question.go`'s flag definitions and
long-form help text to: name the same field the same way across commands,
print the resolution-kind enum and its pointer-format rules in
`resolve --help`, and state the claim→respond→resolve sequence in
`resolve --help` (or a `question --help` overview). Consider a
`shark question workflow <key>` (or similar) read command that shows the
current state (claimed-by, responders, resolution owner, kind, pointer) to
a caller regardless of whether they're an authorized actor for the *full*
narrative view — status metadata is lower-sensitivity than the full
projection.
