# questionErrorStatus classifies errors by substring match instead of typed errors

## Description

internal/api/common.go:74 questionErrorStatus() classifies ~19 hardcoded QuestionService error-message phrases via strings.Contains(err.Error(), phrase) into HTTP 400/409, violating docs/architecture/coding-standards.md's 'never string-match error messages' rule. Own doc comment concedes it is interim. Fix: introduce typed/sentinel errors in QuestionService (e.g. ErrQuestionWrongState) and branch with errors.As/errors.Is, mirroring the QuestionFullReadDeniedError pattern two lines above in the same function. Surfaced by round-5 /shark-rider deep-review of E39 (finding F5), 2026-08-01.

## Impact

Fragile HTTP status-code mapping: any future edit to a `QuestionService` error message string silently breaks the 400/409 classification for the HTTP API without a compile-time or obviously-failing-test signal, since the two are coupled only by matching substrings. Standards violation per `docs/architecture/coding-standards.md`'s error-handling section.

## Resolution Plan

Introduce typed/sentinel errors in `QuestionService` (e.g. `ErrQuestionWrongState`, `ErrQuestionFieldRequired`) and branch on them with `errors.As`/`errors.Is` in `questionErrorStatus`, mirroring the existing `QuestionFullReadDeniedError` pattern already used two lines above in the same function.
