# TD-085 research report

## Scope

TD-085 concerns the host-side `/shark-rider run` loop: a worker that has returned
its workflow result can remain alive as an idle native background agent and continue
to emit `idle_notification` pings. The affected capability is completion of one
workflow dispatch, including the parent loop's release of the Shark lease and the
host adapter's retirement of the corresponding native worker.

The tracked entity declares `docs/plan/tech-debt/TD-085.md` as its file path, but
that file is absent from this worktree. This report is therefore the only authored
artifact in this step, at the sidecar path derived from the entity's stored file
path. The report does not change workflow state or add a substitute entity file.

## Findings

- The documented Rider contract already separates ownership correctly: the parent
  claims, dispatches, advances, and releases; the child returns one final outcome
  and must not own Shark workflow state. This is existing remediation for stale
  workflow leases, but it does not require the native host adapter to terminate or
  otherwise retire a worker after the final result.
- The Go `internal/runner` implementation has a different lifecycle boundary. Both
  Claude and Codex dispatchers use `exec.CommandContext`, and the shared
  `execAndCapture` waits for the child process before returning a result. Its
  process-backed path therefore cannot leave a successfully dispatched CLI process
  available to send later idle notifications.
- The observed defect belongs to the host-native adaptation of the documented
  Rider loop, where a spawned background agent can outlive the final response.
  Neither installed provider reference documents a native worker-retirement
  operation, so the contract cannot require one.
- The safe provider-backed fallback is parent-owned awaited execution. Codex
  `exec` and Claude Code print mode both return only after the invocation exits.
  A host that cannot establish equivalent completion must not start the step as a
  background worker. Releasing the Shark lease alone does not suppress later
  host notifications from an already backgrounded worker.
- `shark related-docs` supports epic, feature, task, bug, change-card, and question
  flags only; it has no tech-debt flag or TechDebt document service. Consequently
  this report cannot be registered as a database related-document link without
  extending an unrelated CLI capability. The sidecar is still discoverable by the
  universal research validator through the entity's `file_path` convention.

## Decisions

1. Extend the existing parent-owned Rider dispatch contract; do not replace it or
   move Shark claims/transitions into workers.
2. Require a documented completion guarantee for every terminal envelope before
   advancement: use parent-owned awaited execution by default, or a provider's
   documented retirement operation when one exists. Do not start background
   workers when neither guarantee is available.
3. Keep the Go process-backed dispatcher unchanged unless a reproduction shows the
   same lifecycle leak there. Its `execAndCapture` wait is the existing termination
   guarantee to reuse.
4. Do not claim native-host retirement coverage without an executable adapter
   contract. Keep the existing run-loop transition tests as coverage of the
   separate Shark workflow concern. A future provider integration may add a
   lifecycle harness when it exposes a testable terminal operation.
5. Do not add a fake related-document registration. TD-085 needs either future
   TechDebt document-link support or an explicitly accepted reference-note
   convention; that capability is outside this report-only debt item.
