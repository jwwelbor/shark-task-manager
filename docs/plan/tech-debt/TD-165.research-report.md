# TD-165: shark run harness wiring verification research

## Scope

This research investigates the architectural gap in `shark run` where harness override wiring is verified only through source-text scanning (`internal/cli/commands/run_harness_flags_test.go:88-109`) rather than execution-level testing. The investigation must establish:

1. What the current source-scan test asserts and its fragility
2. Specific test seams that `shark next` provides that `shark run` lacks
3. Feasibility of execution-level testing given cli-test constraints
4. Concrete remediation with trade-offs

## Findings

### 1. Current Source-Scan Test

**What it asserts** (run_harness_flags_test.go:88-109):

The test reads `run.go` source text and checks for three string patterns:

- `harnessOverride, err := harnessOverrideFromFlags(cmd)` (line 93-94) — verifies flags are read
- `HarnessOverride: harnessOverride` (line 95-96) — verifies override is passed to RunOptions
- `HarnessResolver: cli.GetHarnessResolver()` appearing at least 2 times (line 102-108) — verifies resolver is wired into top-level AND cascade-child RunControllerDeps

**Fragility and gaps**:

- **No execution path**: Code could be present but unreachable (e.g., inside a commented block, inside an `if false` guard, misspelled variable name)
- **No type safety**: String matching doesn't verify that `HarnessOverride` field exists on `RunOptions` or that `RunControllerDeps.HarnessResolver` accepts the resolver type
- **Incomplete coverage**: Test passes if resolver is wired into top-level controller but misses cascade children, or vice versa (checked by counting occurrences, but not by coverage path)
- **Refactoring risk**: Renaming `HarnessResolver` to `harnessResolver` or extracting the resolver creation to a variable would silently break the test

### 2. Test Seams in shark next vs shark run

**shark next** (next.go + next_harness_test.go):

The `next` command provides a dedicated test injectable seam: `nextAdapterCache` (next_harness_test.go:81-108).

```go
type nextAdapterCache struct {
    entries map[string]*nextAdapters{
        "task": {
            transitioner: fixedNextTransitioner{...},
            renderer: &action.MockActionService{...},
            resolver: &MockHarnessResolver{...},
        }
    }
}
```

This allows tests (TC-003/TC-004/TC-005/TC-006/TC-007/TC-016/TC-018) to inject a real `templates.OrchestratorRenderer` with a mocked `action.MockActionService` and `HarnessResolver`, and execute `resolveNext()` end-to-end without touching the database. The pattern is: **mocked seam at the entry point (action/resolver) + real orchestration logic**.

**shark run** (run.go + run_test.go):

The `run` command provides ONE injectable seam: `runClaimSvcOverride` (run.go:75-82) for the claim service.

```go
var runClaimSvcOverride runClaimServicer
func getRunClaimService() runClaimServicer {
    if runClaimSvcOverride != nil {
        return runClaimSvcOverride
    }
    return cli.GetClaimService()
}
```

**Missing seams**:

- No injectable override for `cli.GetHarnessResolver()` (called at run.go:334, 414)
- No injectable override for `cli.GetActionService()` (called at run.go:269)
- No injectable override for `narrowActionServiceForEntity()` (called at run.go:273, 318)

These are called directly from `runRun` with no seam to mock them in CLI tests. This is the core architectural gap: **unlike `next` which decouples action/resolver from global accessors, `run` calls the accessors directly**.

### 3. Execution-Level Test Feasibility

**.claude/rules/testing/cli-tests.md golden rule**: *"ONLY repository tests should use the real database. Everything else MUST use mocked repositories."*

**Is an execution-level test feasible for runRun's harness wiring?**

**Partial yes, with caveats**:

The test `TestRunCmd_HarnessFlagsParseIntoOverrideIdentity` (run_harness_flags_test.go:46-61) **already proves end-to-end flag parsing works** by:
1. Calling `runCmd.ParseFlags()` with real Cobra flag set
2. Calling the shared helper `harnessOverrideFromFlags(runCmd)` (same helper `runRun` uses)
3. Asserting the parsed `HarnessIdentity` struct

**To test the full path** (`harnessOverrideFromFlags` → `RunOptions.HarnessOverride` → harness resolution), an execution test would need:
- A mock `RunController` (can be injected; controller is constructed in `runRun`, line 400-416)
- Mock `ActionService` + mock `HarnessResolver` (requires new seams in `runRun`)
- NO real database (satisfied by mocking claim service via existing `runClaimSvcOverride`)

**Feasibility assessment**:

| Step | Feasibility | Constraint |
|------|-------------|-----------|
| Parse flags | ✅ Already tested via `TestRunCmd_HarnessFlagsParseIntoOverrideIdentity` | None |
| Pass to RunOptions | ⚠️ Requires injectable RunController | New seam needed |
| Pass to RunControllerDeps (top-level) | ⚠️ Requires injectable HarnessResolver | New seam needed |
| Pass to RunControllerDeps (cascade-child) | ⚠️ Requires injectable HarnessResolver | New seam needed + controller construction in runChild closure |
| Avoid real DB | ✅ Existing `runClaimSvcOverride` works; no repo calls | Already handled |

**Verdict**: An execution test is **feasible but requires 2–3 new injectable seams** (HarnessResolver override, ActionService override, RunController override). The test would construct a mock runner that validates the resolver was passed with the correct override values without actually executing agents.

### 4. Recommended Approach

**Option A: Minimal — Keep Source Scan + Add Execution Proof (Recommended)**

- **Keep** `TestRunRun_WiresHarnessOverrideAndResolver` as a regression check (source scan is cheap, catches gross refactorings)
- **Add** a focused execution test: `TestRunRun_PassesHarnessOverrideToResolver`
  - Inject a mock `HarnessResolver` that records what override it received
  - Call `runRun` with `--harness=test-claude --harness-version=2.1 --harness-model=opus`
  - Assert the resolver's `Resolve()` method was called with the exact override
  - Inject mock `RunController` to prevent execution beyond controller construction
  - No database, no agent dispatch

- **Pros**: Minimal code, reuses existing `runClaimSvcOverride` pattern, directly tests the gap identified in TD-165
- **Cons**: Requires 1–2 new injectable seams (HarnessResolver, RunController)

**Option B: Deep — Full End-to-End Controller Test**

- Inject mocks for HarnessResolver, ActionService, and RunController
- Execute the full `runRun` path (harness resolution, action lookup, controller construction)
- Assert cascade children also receive the harness override

- **Pros**: Comprehensive, catches interaction bugs between harness resolution and controller wiring
- **Cons**: More complex setup, higher maintenance burden, still can't test actual agent dispatch without a real project

**Option C: Do Nothing — Accept Source Scan**

- Source scan is cheap and catches structural refactorings
- Harness override is also tested indirectly through integration tests (controller_gate_e2e_test.go likely exercises this)
- Investment in a new execution seam is modest but not zero

- **Pros**: No code changes, no new seams to maintain
- **Cons**: Leaves the architectural gap open; test fragility persists

---

## Decisions

**Recommended**: **Option A (Minimal Execution Test)** balances test rigor with architectural simplicity.

1. Keep `TestRunRun_WiresHarnessOverrideAndResolver` as a source-scan regression check (cheap insurance)
2. Add one new injectable seam: `var runHarnessResolverOverride` (parallel to `runClaimSvcOverride`)
3. Write `TestRunRun_PassesHarnessOverrideToResolver` that:
   - Sets `runHarnessResolverOverride` to a recording mock
   - Calls `runRun` with explicit flag values
   - Asserts the resolver received the exact override in both top-level and cascade contexts

The test seam pattern already exists in the file (line 75-82), so implementation is straightforward.
