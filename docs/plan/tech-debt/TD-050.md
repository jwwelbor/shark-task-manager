# Leaf-entity cascade with custom action:cascade step hard-errors under --sequential instead of pausing

## Description

tryCascadeCandidates (internal/cli/commands/next.go) now backs both --sequential and fan-out cascade resolution via PlanHierarchyService.DescribeChildren. For a leaf entity type (task/bug/change-card/tech-debt) with a custom workflow action:cascade step, planhierarchy.Repository.ReadDirectChildren's default branch never sets Snapshot.ParentFound, so DescribeChildren returns a hard not-found error instead of the pre-consolidation graceful pause. Only reachable via custom per-entity workflow YAML (not the shipped default workflows). Fix: have ReadDirectChildren's default branch verify the parent row actually exists, or have DescribeChildren distinguish 'unsupported parent type' from 'missing parent' so tryCascadeCandidates falls through to pause for leaf types. See docs/review/E36-project-layer-and-consult-bridge/E36-F04-portfolio-aware-next-action-advisor/code_review/2026-07-25-E36-F04-portfolio-aware-next-action-advisor-overall-review.md finding F1.

## Impact

Only reachable through a hand-authored per-entity workflow YAML that puts `action: cascade` on a task/bug/change-card/tech-debt step (route-based-workflow.md §1 confirms this is a supported, documented capability). Not reachable through any shipped default workflow, so no current deployment hits it. If it does trigger, `shark next <key> --sequential` fails hard (`"%s %s not found"`) instead of returning the expected `pause` action, which would look like a broken dispatch to the operator rather than "no work available yet."

## Resolution Plan

Either (a) have `ReadDirectChildren`'s `default:` branch in `internal/repository/planhierarchy/repository.go` verify the parent row actually exists (`SELECT 1 FROM <table> WHERE key=?`) before returning, so a genuinely-missing key still errors while an existing leaf entity does not; or (b) have `PlanHierarchyService.DescribeChildren` distinguish "unsupported parent type" from "missing parent" so `tryCascadeCandidates` falls through to `pause` for leaf types. Add a `next_cascade_traversal_test.go` case covering `--sequential` against a leaf entity with a custom `action: cascade` step to close the test gap identified alongside this finding.
