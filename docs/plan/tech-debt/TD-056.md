# Question key-allocation retry detects UNIQUE collision via string match, not typed error

## Description

internal/repository/question/repository.go:91 detects a UNIQUE constraint collision via strings.Contains(strings.ToLower(err.Error()), "unique") instead of a typed driver error -- same standards violation as the companion finding on common.go's questionErrorStatus. Project supports both local modernc.org/sqlite and Turso/libsql backends with potentially different error text. Fix: use errors.As against the driver's typed constraint-violation error, or isolate the string check behind an explicitly-commented driver-compat helper. Surfaced by round-5 /shark-rider deep-review of E39 (finding F6), 2026-08-01.

## Impact

The retry-on-collision logic for Question key allocation depends on recognizing "unique constraint" in the lowercased driver error text. The project supports both local `modernc.org/sqlite` and Turso/libsql backends, which may phrase constraint-violation errors differently -- a backend-specific wording change would silently defeat the retry (treating a real collision as a hard failure) rather than failing loudly.

## Resolution Plan

Use `errors.As` against the driver's typed constraint-violation error type instead of string matching, or if a portable typed error isn't available across both backends, isolate the string check behind an explicitly-commented driver-compat helper so the fragility is visible and testable in one place.
