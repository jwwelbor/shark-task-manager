# B052 follow-ups: loud-fail guard on multi-entity collision, STAGELOG_REQUIRED gap, unpinned entity_key test

## Description

From B052 code review, second pass (docs/review/bugs/b052/code-review-20260828-0437-B052.md), non-blocking findings on the transcript-layout + bench-harness fix (commits bcb3355c, f99b3a6a):

N1 (highest value): run-one.sh's flat transcript-copy destination is safe today only because two independent gates (run-one.sh:271 hard-exits on non-task/bug item types; action: cascade only exists in feature.yaml/epic.yaml) prevent more than one entity directory from ever appearing under a single run's transcripts. If either gate relaxes (e.g. Phase 2 cascade benching), two same-named sibling transcripts would silently truncate at the flat destination with no detection, since reconcile_transcripts keys by bare index only. Recommended: add a loud-fail guard (~3 lines) at the copy site that errors if more than one entity directory is found, turning "safe by reachability" into "safe by construction" before Phase 2 relaxes the gate.

N2: canary-runsurface.sh's STAGELOG_REQUIRED check for entity_key catches the field being renamed or removed from the JSON schema, but does NOT catch entity_key being present-but-unset (empty string) -- since omitempty was dropped, an unset key now serializes as "" rather than being absent, and the REQUIRED check only validates key presence in the JSON object, not value non-emptiness. Recommend a follow-up validation step (in the canary or a Go-side test) that asserts entity_key is non-empty for every StageLog with a spawn_agent-class action.

N3 (found by codex red-team): tc016_canary_runsurface_test.sh never actually asserts entity_key is in the canary's confirmed/pinned field set -- so while F3's fix (adding entity_key to STAGELOG_REQUIRED) is real and verified working, the regression test suite doesn't yet pin it, meaning a future accidental removal from STAGELOG_REQUIRED wouldn't be caught by tc016. Add an explicit assertion.
