# Cascade allParkedQuestionBlock reports first Question block, not all-parked

## Description

internal/runner/controller.go:599 handleCascade's allParkedQuestionBlock records only the first Question block seen among non-progressing children and attaches it to the parent's pause result, without verifying every non-progressing child was actually Question-blocked -- contradicts the adjacent comment ('kept only if every cascade child is parked'). Identical pattern in internal/cli/commands/next.go tryCascadeCandidates. Fix: track a counter of Question-blocked vs total non-progressing children and only surface the block when they're equal, or correct the comment. Surfaced by round-5 /shark-rider deep-review of E39 (finding F3), 2026-08-01.

## Impact

A cascade parent can report the wrong reason for pausing (attributing the pause to a Question block when another, unrelated child actually stalled the cascade), which misleads an operator or the `/shark-rider run` loop about what's actually blocking progress. Low severity because it's a reporting/attribution issue, not a functional block.

## Resolution Plan

Track a counter of Question-blocked vs. total non-progressing children in both `internal/runner/controller.go`'s `handleCascade` and `internal/cli/commands/next.go`'s `tryCascadeCandidates`; only set `allParkedQuestionBlock` on the result when every non-progressing child was Question-blocked. Alternatively, if surfacing the first block seen is the intended behavior, correct the misleading comment instead.
