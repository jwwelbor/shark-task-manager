# TD-013 research report

## Scope

Measure whether the reported list-command startup regression is caused by observability initialization or repeated config loading.

## Research checklist

- [x] `scope_vocabulary` — Evidence: `docs/plan/tech-debt/TD-013.md`.
- [x] `affected_implementation_or_contract` — Evidence: `internal/cli/root.go:48-90`; `internal/cli/observability_global.go:69-106`; `internal/cli/maintainer_global.go:32-60`.
- [x] `dependency_impact` — Evidence: `internal/cli/tag_global.go:14-34` shows tag service construction depends on maintainer/config wiring, so unmeasured caching would alter a shared command path.
- [x] `alternatives` — Evidence: three `bin/shark task list --json` runs measured 1.48s, 1.05s, and 1.02s; three equivalent runs with `SHARK_OTEL_ENABLED=false` measured 1.40s, 1.05s, and 1.18s.

## Capability map

| Capability | Decision |
| --- | --- |
| CLI startup optimization | REUSE current one-process observability initialization; do not add a config cache without evidence of a config/OTel bottleneck. |

## Findings

Disabling observability did not improve the measured list startup. The proposed OTel and repeated-config remedies would add stateful cache behavior while not addressing the measured cost. `task list` also necessarily initializes its database/service graph, which remains the more plausible fixed-cost surface.

## Decisions

Mark won’t-fix. Reopen only with a profiler trace that separates database initialization, query execution, config parsing, and observability work and identifies a material target.
