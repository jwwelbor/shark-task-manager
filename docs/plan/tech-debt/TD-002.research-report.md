# TD-002 research report

## Scope

Verify whether the proposed SQL-side tag filter still matches the current search architecture and identify a bounded, measurable implementation target.

## Findings

The debt description is stale: `SearchAll` queries one unified FTS table rather than a union across source tables. Tags are intentionally resolved by entity type in the service so all registered-name validation and AND semantics are shared with other list surfaces. Moving the filter into SQL therefore is not the stated local join change; it would introduce a new cross-layer contract and dynamic polymorphic filter semantics.

## Decisions

Mark won’t-fix for the current prescription. Reopen with a representative search corpus, query-plan/latency measurement, and a proposed contract that preserves eager unregistered-tag validation and AND behavior. That evidence can justify either repository SQL filtering or a separately scoped tag-resolution API.
