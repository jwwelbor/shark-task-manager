# TD-221 research report — terminal-state gate kickback reopening

## Scope

TD-221 is limited to a gate-result kickback that must move a *different*
entity from a workflow terminal status back to the rework target recorded in
the gate result. The capability is owned by `gatepersist.Coordinator` and its
`EntityServiceTransitioner` adapter. It must preserve normal workflow
validation for kickbacks from non-terminal states, lease/replay protection,
and the coordinator's durable operation-state protocol.

The existing remediation is the gate-persistence boundary itself: it validates
the target entity and status, records the kickback as a suboperation, and
passes the parent run guard to `EntityService`. TD-221 extends that boundary
with the narrowly required terminal-state override; it does not replace the
workflow service or add a CLI-only recovery path.

## Findings

1. **The force flag is absent at the only production transition adapter.**
   `applyKickback` reads the target's current status and carries it in
   `TransitionGuard.FromStatus`. `EntityServiceTransitioner.Transition` then
   supplies that guard for replay protection but builds `TransitionOptions`
   without `Force`. `EntityService` rejects any transition whose current state
   is terminal unless `Force` is true, which leaves a valid recorded kickback
   unable to reopen its target.

2. **The adapter has sufficient, level-correct information to make the
   decision.** The adapter owns the same level-specific workflow service used
   to normalize status reads. `workflow.Service.IsTerminalStatus` recognizes
   configured terminal states rather than relying on literal names such as
   `completed`. It can therefore set `Force` only when the guard's canonical
   source state is terminal.

3. **A blanket force would broaden the contract unnecessarily.** Ordinary
   kickbacks are already valid workflow routes and should continue through
   normal transition validation. The explicit terminal-source check preserves
   those route checks while allowing the exceptional reopen transition that
   the coordinator owns and durably records.

| Capability | Existing owner/evidence | Decision | TD-221 action |
|---|---|---|---|
| Gate kickback sequencing and durable suboperations | `internal/gatepersist/coordinator.go:421-458` | REUSE | Retain the existing pre-transition status read, operation state, and idempotency protocol. |
| Level-specific terminal classification | `internal/workflow/service.go:210-218` | REUSE | Ask the target entity's workflow whether `guard.FromStatus` is terminal. |
| Forced transition audit and validation | `internal/services/entity_service.go:250-315` | EXTEND | Forward `Force: true` only for a terminal-source kickback, with the existing reason and run guard. |

## Decisions

1. **Force only terminal-source kickbacks in
   `EntityServiceTransitioner`.** This makes the exceptional behavior explicit
   at the adapter that translates the coordinator's domain guard into
   `services.TransitionOptions`, without expanding the generic coordinator
   interface.

2. **Use `workflowSvc.ForLevel(...).IsTerminalStatus(guard.FromStatus)`.**
   The guard's source is read immediately before the transition and is already
   canonical in production. A separately named `ForceTerminalReopen` guard
   capability is set only by `applyKickback`, which prevents the shared main
   transition path from inheriting the exception. This supports custom
   terminal vocabulary and avoids treating target names or static status
   literals as authoritative. The forced reopen also uses an unconditional
   source-status CAS, even where the optional replay ledger is disabled, so a
   later non-terminal state cannot inherit the exception.

3. **Prove both boundaries with adapter tests.** A terminal `completed` task
   must be reopened to `in_review`; a non-terminal task must retain the normal
   invalid-route rejection. Both calls retain the existing advance guard, so
   forcing does not bypass replay/CAS ownership.
