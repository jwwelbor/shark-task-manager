# shark run's cascade dispatch surface never calls CaptureBase

## Description

Confirmed via grep during E34-F08's T-008 second UAT rework: shark run's own cascade implementation never calls resolveCascade/resolveEntity/resolveNext (no matches in run*.go), so an epic driven entirely through 'shark run' rather than 'shark next' never captures an integration base at all — a second dispatch surface with zero CaptureBase coverage. T-E34-F08-008's scope named resolveCascade (next.go) only; this is a distinct, unfixed gap. Needs its own task to add equivalent pre-dispatch capture-or-block behavior to shark run's cascade path.

## Impact

An epic driven entirely through `shark run` (rather than `shark next`) never gets an integration base captured, event recorded, candidate folded, or run registered — because `internal/cli/commands/run.go` has its own cascade implementation that never calls `resolveCascade`/`resolveEntity`/`resolveNext`. E34-F08's E2E integration guarantees (idempotent capture, accumulated candidate, discoverable registration, fail-closed `integration_review`) only hold for epics dispatched via `shark next`. If `shark run` is a supported entry point for driving an epic end-to-end, it silently produces the exact "feature work happened without required integration evidence" state E34-F08 exists to prevent.

## Resolution Plan

Add equivalent pre-dispatch capture-or-block behavior to `shark run`'s own cascade path, mirroring `resolveCascade`'s fix in T-E34-F08-008 (round-2 UAT rework, commit `b8d50d48`): call `integration.CaptureBase` before dispatching a feature, and block/park with a durable `integration_capture` finding note on any ordinary I/O or git failure rather than proceeding. Confirm whether `shark run` and `shark next` should share one cascade implementation instead of two independently-maintained ones, to prevent this class of drift recurring.

## Resolution Notes

Filed 2026-09-05 during E34-F08's UAT round-2 rework; not fixed as part of E34-F08 (out of T-E34-F08-008's declared scope, which named `resolveCascade`/`next.go` only). Round-4 code_review (report `code-review-20260905-200500-E34-F08.md`) confirmed via grep that `run.go` genuinely never calls `CaptureBase`/`resolveCascade`/`resolveNext`, and accepted leaving this tracked-not-fixed as reasonable given the task's scope.

**RESOLVED 2026-09-05** during T-E34-F08-008's round-3 UAT rework (`uat-20260905-203832-E34-F08.md` Finding 1). Rather than duplicating `resolveCascade`'s capture-or-block logic inside `run.go`/`runner/controller.go` (this record's original "mirror the fix" suggestion), the fix extracts the ONE shared implementation both dispatch surfaces now call:

- `internal/cli/commands/next.go` gained `ensureEpicIntegrationBaseCaptured(ctx, commandLabel, epicKey) error` — the exact capture/corrupt-warning/durable-note logic `resolveCascade` already had, generalized to accept a `commandLabel` instead of hardcoding `"next"`. `resolveCascade` now calls this shared function instead of inlining the logic.
- `internal/runner/controller.go` gained a new `CascadeIntegrationGuard` interface and an optional `RunControllerDeps.IntegrationGuard` dependency. `RunController.handleCascade` calls it first, before `childrenSvc` is ever consulted or any child dispatched, and blocks (records a `stageOutcome{done:true}` with `Outcome:"failed"`) on any non-nil error.
- `internal/cli/commands/run_cascade_integration_guard.go` adapts `ensureEpicIntegrationBaseCaptured` to `runner.CascadeIntegrationGuard` (`cascadeIntegrationGuard{commandLabel:"run"}`), scoped to `entityType == "epic"` exactly like `resolveCascade`. `run.go` wires this into both `RunControllerDeps` constructions (the top-level controller and the nested `runChild` closure's child controller).

So `shark next` and `shark run` now share exactly one capture-or-block implementation (`ensureEpicIntegrationBaseCaptured`), not two independently-maintained copies — directly addressing this record's "confirm whether `shark run` and `shark next` should share one cascade implementation" question with "yes, they now do, for the guard specifically."

Verified via:
- `internal/runner/controller_test.go`: `TestRunController_CascadeAction_BlocksDispatchOnIntegrationGuardFailure` and `TestRunController_CascadeAction_IntegrationGuardSuccessAllowsDispatch` (mocked guard, proves `handleCascade`'s call-order and block behavior).
- `internal/cli/commands/run_cascade_integration_test.go`: `TestRunControllerCascadeCapturesEpicIntegrationBaseBeforeChildDispatch` and `TestRunControllerCascadeBlocksChildDispatchOnCaptureFailure` — production-path tests driving a real `runner.RunController` (the exact production `ActionCascade` wiring) through a real temp git project, asserting `.shark/integration/<epic>/run.json` exists before any child-dispatch lookup, and that a genuine capture failure (non-git directory) blocks all child dispatch with a deduped durable note — mirroring `shark next`'s TC-011 and Finding-1 tests. Both tests were confirmed to fail without the fix (removal counterfactual).

Defect-class sweep (skills/quality/workflows/defect-class-sweep.md) confirmed no other cascade dispatch entrypoint exists: `shark plan` and `run.go`'s `preflightCascadeQuestionBlock` both enumerate cascade children but are read-only (never dispatch, never side-effect the filesystem) and are correctly out of scope; no HTTP API (`cmd/server`/`internal/api`) or viewer (`internal/viewer`) cascade dispatch controller exists; all other "cascade" hits in the repo are unrelated DB-level cascade-delete or parent-reopen logic.
