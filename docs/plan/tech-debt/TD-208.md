# shark run's cascade dispatch surface never calls CaptureBase

## Description

Confirmed via grep during E34-F08's T-008 second UAT rework: shark run's own cascade implementation never calls resolveCascade/resolveEntity/resolveNext (no matches in run*.go), so an epic driven entirely through 'shark run' rather than 'shark next' never captures an integration base at all — a second dispatch surface with zero CaptureBase coverage. T-E34-F08-008's scope named resolveCascade (next.go) only; this is a distinct, unfixed gap. Needs its own task to add equivalent pre-dispatch capture-or-block behavior to shark run's cascade path.

## Impact

An epic driven entirely through `shark run` (rather than `shark next`) never gets an integration base captured, event recorded, candidate folded, or run registered — because `internal/cli/commands/run.go` has its own cascade implementation that never calls `resolveCascade`/`resolveEntity`/`resolveNext`. E34-F08's E2E integration guarantees (idempotent capture, accumulated candidate, discoverable registration, fail-closed `integration_review`) only hold for epics dispatched via `shark next`. If `shark run` is a supported entry point for driving an epic end-to-end, it silently produces the exact "feature work happened without required integration evidence" state E34-F08 exists to prevent.

## Resolution Plan

Add equivalent pre-dispatch capture-or-block behavior to `shark run`'s own cascade path, mirroring `resolveCascade`'s fix in T-E34-F08-008 (round-2 UAT rework, commit `b8d50d48`): call `integration.CaptureBase` before dispatching a feature, and block/park with a durable `integration_capture` finding note on any ordinary I/O or git failure rather than proceeding. Confirm whether `shark run` and `shark next` should share one cascade implementation instead of two independently-maintained ones, to prevent this class of drift recurring.

## Resolution Notes

Filed 2026-09-05 during E34-F08's UAT round-2 rework; not fixed as part of E34-F08 (out of T-E34-F08-008's declared scope, which named `resolveCascade`/`next.go` only). Round-4 code_review (report `code-review-20260905-200500-E34-F08.md`) confirmed via grep that `run.go` genuinely never calls `CaptureBase`/`resolveCascade`/`resolveNext`, and accepted leaving this tracked-not-fixed as reasonable given the task's scope.
