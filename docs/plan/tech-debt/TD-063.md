# Cross-feature deps creatable but not updatable (dependency existence check scope mismatch)

## Description

internal/repository/task/dependency.go:40,64-67 - update validates dependency existence in-feature only while create validates globally, so cross-feature deps are creatable but not updatable. Found during B048 code review, NB4.

## Impact

Investigation (including a live repro build) found the literal title
description does not hold: `TaskRepository.Create`, `CreateWithTx`, and
`Update` all call the same `ValidateTaskDependencies`
(`internal/repository/task/dependency.go:25-86`), which is feature-scoped via
`r.ListByFeature(ctx, task.FeatureID)` (line 40) in every case. A cross-feature
`depends_on` key is rejected on create exactly as it is on update — there is
no create/update scope mismatch in the JSON `depends_on` field path.

The real, confirmed defect: `internal/taskcreation/validator.go:132` performs
a *global* existence pre-check (`v.taskRepo.GetByKey`, no feature filter)
during create, before `CreateWithTx` runs the stricter feature-scoped check.
For a dependency key that exists in a different feature, the global check
passes, then the feature-scoped check rejects it with `"dependency does not
exist: <key>"` — a factually wrong message, since the task does exist, just
not in this feature. That confusing error is the actual, low-severity
code-quality issue: the two checks disagree, and the losing check's error
message doesn't say why.

Separately (and correctly, by design): `depends_on` (JSON field) intentionally
only supports same-feature dependencies. Cross-feature dependencies are fully
supported via the `entity_relationships` table (`shark task link
--depends-on` → `EntityRelationshipService.CreateRelationship`), which is
disjoint from `depends_on` and unaffected by this validation.

## Resolution Plan

1. Document the feature-scope contract on `ValidateTaskDependencies` so the
   restriction is explicit rather than an undocumented side effect of
   `ListByFeature`.
2. When a dependency key fails the in-feature existence check, distinguish
   "exists, but in a different feature" from "does not exist anywhere" with
   an accurate error message that points at `shark task link --depends-on`
   for the cross-feature case.
3. Add a repository test covering a task in feature A depending on a task
   that exists in feature B, asserting the corrected message.

Deliberately out of scope: widening `depends_on` validation (existence +
cycle detection) to a global scope. That would require also widening
`dependency.Detector`'s graph construction (currently in-feature only) to
avoid missing cross-feature cycles, and would add project-wide query cost to
every task create/update — disproportionate to a `low`/`code-quality` ticket,
and `entity_relationships` already owns cross-feature dependency support.

## Resolution Notes

- `internal/repository/task/dependency.go`: added a doc comment on
  `ValidateTaskDependencies` stating the feature-scope contract, and a new
  `dependencyNotFoundError` helper that does a global `GetByKey` lookup only
  on the error path (no cost on the success path) to distinguish "exists
  elsewhere" from "does not exist" and produce an accurate message for each.
- `internal/repository/task_dependency_validation_test.go`: added
  `TestTaskRepository_ValidateTaskDependencies_CrossFeature`, seeding a
  second feature/epic and asserting the corrected message for both the
  cross-feature case and the genuinely-missing-key case.
- Left `internal/taskcreation/validator.go`'s global pre-check unchanged — it
  still serves a purpose (validates key format and existence before other
  create-time checks run) and is now consistent with the corrected
  feature-scoped error, since callers only ever see the more specific message
  from `dependency.go` when both checks run.
- Filed TD-068 for a distinct, unrelated defect surfaced during this
  investigation: `shark task update --depends-on` is a registered but
  completely unread CLI flag (silent no-op, no DTO field to carry the value).
  Not fixed here — it's a CLI-visible behavior change (new validation/errors
  or flag removal) outside this ticket's scope.
- Quality gate: `make fmt && make lint && make test` all pass.
