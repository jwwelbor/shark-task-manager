# advance_guard: idempotency early-return bypasses guard enforcement/CAS ledger

## Description

internal/services/entity_service.go's TransitionStatus idempotency early-return (around line 269-280) fires before enforceAdvanceGuard/recordAdvanceGuard ever run, so a guarded transition landing on an already-at-target entity succeeds without touching the replay ledger. Cross-run race: a different run can move a kickback target from the observed source to the same target in the window after Coordinator.applyKickback reads status and before its guarded call, causing TransitionStatus to return a successful no-op with no guard record. Pre-existing from PR #133 (2293f198), predates E34-F05 (10a298b5), and equally affects internal/runner/controller.go's guardedTransitionOptions pattern -- not introduced or fixable by any E34-F05 task. Found by Codex red-team during E34-F05 code-review round 5, verified as real and out of scope.

## Impact

Latent in this repo — `.sharkconfig.json` does not enable `advance_guard`, so
nothing is currently mis-transitioning. It becomes live for anyone who turns the
flag on.

With the flag on, the guard's **documented** second rejection condition is
unreachable. `docs/cli-reference/configuration.md` (Advance Guard) states Shark
rejects an advance when "the same `entity + session + from_status + outcome` was
already consumed." But a repeat of that exact tuple arrives at an entity already
sitting at the target status, so `TransitionStatus`'s idempotency early-return
(`internal/services/entity_service.go:273-282`) fires and returns success before
`enforceAdvanceGuard` (:315) runs. The replay is silently accepted instead of
rejected with `ErrAdvanceGuardRepeatRejected`, and no CAS ledger entry is
written, so there is no audit trace either.

Three guarded call paths reach it: `gatepersist/coordinator.go`'s `applyKickback`
(the cross-run race named in the original description),
`internal/runner/controller.go`'s `guardedTransitionOptions`, and — not in the
original description — `internal/cli/commands/status_group.go:490`, which sets
`GuardAdvance = true` for **every** `shark status advance` once the flag is on.
That last one makes an ordinary repeated advance, the textbook retry the guard
exists to reject, hit the bug.

## Resolution Plan

**Blocked on an owner decision — there is a documented conflict.** See
Resolution Notes below: a prior architect review explicitly instructed "do not
move advance-guard enforcement ahead of the idempotency return," holding that a
proper fix needs a replay-identity design outside `TransitionStatus`.

The 2026-09-18 research (`TD-191.research-report.md`) reaches the opposite
conclusion and proposes a narrower change that does not reorder the return:
perform the guard check *within* the idempotent-return path — record consumption
on first observation, and reject a true repeat via the existing
`ErrAdvanceGuardRepeatRejected`. The report argues this preserves the replay
tolerance `gatepersist` and `--resume-run` depend on, because
`gatepersist`'s `PersistenceStateTransitioned` branch never re-calls
`Transition` for the same-run resume case and so does not rely on the early
return's current silent-accept.

What the architect note does **not** appear to weigh is the
`status_group.go:490` path and the resulting contradiction with the documented
contract in `configuration.md`. That is new information, which is why this is
being routed back for a decision rather than either implemented or closed.

Options for the owner:
1. Accept the research's in-path guard check (narrow, preserves resume safety).
2. Reaffirm the architect note and instead correct
   `docs/cli-reference/configuration.md` so the documented rejection condition
   matches actual behaviour.
3. Do the full replay-identity design the architect note calls for.

Blast radius is small either way: only `gatepersist`, `runner`'s
`guardedTransitionOptions`, `status_group.go`, and the four HTTP handlers that
thread a `guard_advance` request field ever set it. Every other
`TransitionStatus` caller is unaffected. `runner/controller.go` needs no
separate fix — `guardedTransitionOptions` only builds options, so one change in
`EntityService` covers all guarded callers.

## Resolution Notes

Architect review retained the `Transitioner` contract that an already-target
transition succeeds as an idempotent verification. The suspected race is real,
but resolving it requires a replay-identity design outside `TransitionStatus`;
do not move advance-guard enforcement ahead of the idempotency return.
