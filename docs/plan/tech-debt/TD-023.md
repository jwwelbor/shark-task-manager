# Read .sharkconfig.json once in defaultWorkflowDataLoader (currently read 2-3× per call)

## Description

internal/config/aliases.go:262 — defaultWorkflowDataLoader calls os.ReadFile(configPath) twice for the same .sharkconfig.json:

- once in resolveWorkflowDir
- once in readLegacyWorkflowConfigValue when the legacy-file error fires

Then internal/config/workflow/parser.go LoadMultiLevelWorkflowOrDefault re-reads the same file a third time.

ActionService is cached behind sync.Once at the CLI layer, so the loader runs once per process — bounded blast radius. But the redundancy is gratuitous and shows up on the cold-startup path that TD-013 is investigating.

Fix: read bytes once at the top of the loader, pass them down to readLegacyWorkflowConfigValue and the parser. Or memoize via a package-level cache keyed by (path, mtime).

Cross-ref TD-013 (broader investigation into shark list startup slowdown) — this is a surgical sub-task of that. Surfaced during simplify review of commit 6492e45.

## Impact

`.sharkconfig.json` is read 2-3× per `ActionService` construction. The cost is bounded — `ActionService` is `sync.Once`-cached per process, so total reads stay small — but the redundancy is gratuitous on the cold-startup path that TD-013 is investigating. It also makes the loader harder to reason about: the same file is parsed under three different code paths, each potentially making slightly different assumptions about presence/legacy semantics.

## Resolution Plan

- Read `.sharkconfig.json` bytes once at the top of `defaultWorkflowDataLoader` in `internal/config/aliases.go`.
- Plumb the bytes (or the parsed `rawConfig` map) through `readLegacyWorkflowConfigValue` and `LoadMultiLevelWorkflowOrDefault` as a parameter; deprecate the read-by-path entry point internally.
- Alternative: add a package-level cache keyed by `(path, mtime)` if call sites can't easily be threaded.
- Cross-ref TD-013 — this is a surgical sub-task of that broader investigation, not a substitute.

## Resolution Notes

Resolved via the pass-bytes-down approach. `defaultWorkflowDataLoader` now calls `os.ReadFile(configPath)` exactly once at the top via a `readConfigFile` package-level seam, then threads the bytes through:

- `resolveWorkflowDir(projectRoot, configBytes)` — signature changed from `(projectRoot, configPath)` to accept bytes; no longer reads the file.
- The legacy-file error branch — now calls `readWorkflowConfigField(configBytes)` directly, eliminating the `readLegacyWorkflowConfigValue` helper.
- `workflow.LoadMultiLevelWorkflowOrDefaultFromBytes(configPath, configBytes)` — new exported variant in `internal/config/workflow/parser.go` that mirrors `LoadMultiLevelWorkflowOrDefault` but parses pre-read bytes. The original `LoadMultiLevelWorkflow` is now a thin wrapper that delegates to `LoadMultiLevelWorkflowFromBytes` after a single `os.ReadFile`. Cache semantics are preserved on both paths.

Pinned by two tests in `internal/config/td023_single_read_test.go`:

- `TestTD023_DefaultWorkflowDataLoader_ReadsConfigFileOnce` — covers the happy path with an inline workflow.
- `TestTD023_DefaultWorkflowDataLoader_LegacyFileErrorPathReadsOnce` — covers the previously-second-read legacy-JSON error branch.

Both wrap the `readConfigFile` seam with a counter filtered by configPath and assert exactly one read per loader invocation. A regression that reintroduces a redundant read fails CI.

`resolveWorkflowDir`'s existing test set in `workflow_config_resolve_test.go` was migrated to the new bytes signature via a small `readConfig` test helper.
