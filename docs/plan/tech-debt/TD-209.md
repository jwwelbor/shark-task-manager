# Fresh-init overrides/.gitkeep scaffold misclassified as orphaned

## Description

OverrideStatusAt (T-002/T-003) classifies a freshly-initialized project's overrides/.gitkeep scaffold file (shipped by shark admin install-shark-data / shark init) as 'orphaned' with suggested_action 'consider removing this override', since it has no canonical counterpart. T-005 wired this classifier into the high-traffic 'shark admin upgrade' command, so every fresh project now shows orphaned:1 out of the box with a misleading removal suggestion for a file shark placed deliberately. Fix in overrides_status.go (exclude .gitkeep from classification) or ship it with a real canonical counterpart in default_data/.

## Impact

Cosmetic/UX only, not a correctness or safety issue. Every fresh `shark admin init`/`install-shark-data` project shows `orphaned: 1` in `shark admin upgrade`'s new overrides summary (E34-F09 T-005), with a suggested action to remove a file shark itself deliberately shipped. Confirmed non-blocking by E34-F09's code_review (round 1, `code-review-20260905-180759-E34-F09.md`).

## Resolution Plan

In `internal/sharkdata/overrides_status.go`'s classification logic, either (a) special-case `.gitkeep` (or any file matching a documented scaffold-marker pattern) to skip classification entirely, or (b) ship `.gitkeep` with a matching canonical counterpart under `default_data/` so it classifies as `current` instead of `orphaned`. Prefer (a) since `.gitkeep` is a directory-existence marker, not real override content.
