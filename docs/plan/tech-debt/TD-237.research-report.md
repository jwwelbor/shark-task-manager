# TD-237 research report

## Scope

Determine whether `shark next <key> --json` violates its JSON output contract when a caller merges stderr into stdout, identify the existing warning and structured-data behavior, and recommend a low-risk resolution for dispatch harnesses. The affected capability is keyed dispatch output consumed by automation. This research covers the command implementation, its existing contract test, related requirement, and current dispatch and JSON-output documentation.

## Findings

- `shark next <key>` is documented in the command help as the canonical harness-side dispatch entry point. Its implementation always serializes the response as JSON to stdout; JSON output is implicit for this command (`internal/cli/commands/next.go:418-430,1515-1524`).
- When unresolved prompt placeholders exist, the command also emits the required `[shark-stats] WARN` diagnostic to stderr. It calls the warning function before writing the JSON response, but uses separate streams (`internal/cli/commands/next.go:672-674,1503-1512`). The JSON response additionally includes the placeholder identities in `unresolved_placeholders`; that structured field does not replace the warning (`internal/cli/commands/next.go:385-395`).
- E32-F07 REQ-F-003 explicitly requires the stderr warning and structured placeholder field as additive outputs. Suppressing the warning globally would change that existing requirement (`docs/plan/E32-shark-20-single-artifact-consolidation/E32-F07-dispatch-instrumentation-file-jsonl-exporter-shark/feature.md:128-141`).
- An existing unit test captures stdout and stderr separately, asserts the warning on stderr, and parses stdout as JSON. It confirms Shark's separate-stream behavior; it does not exercise a parent process that merges the descriptors (`internal/cli/commands/next_unresolved_placeholders_test.go:32-62`).
- The generic JSON-output guide demonstrates the same safe consumer pattern: `subprocess.run(..., capture_output=True)` followed by parsing `result.stdout` (`docs/cli-reference/json-output.md:149-168`). The canonical dispatch architecture document is `docs/architecture/shark-dispatch-prompt-assembly.md`; it describes the keyed JSON contract but does not currently spell out stdout/stderr handling (`docs/architecture/shark-dispatch-prompt-assembly.md:1-9,64-75`). The TD resolution plan names `shark-rider-dispatch-prompt-assembly.md`, which is not present at that path.
- Merging stderr into stdout with `2>&1` can make the combined byte stream invalid as a single JSON document when the warning is emitted. This is a consumer-boundary failure mode; evidence shows Shark's stdout remains valid JSON when consumed separately. The existing dispatch test and generic Python example already use stream separation.
- Other `shark next` paths also write diagnostics to stderr, including unresolved-token errors and unknown-status or agent-body warnings (`internal/cli/commands/next.go:601-610,939-951,1477-1482`). A bounded search of `next.go`, the CLI root, and the global-flags reference found no `--quiet` option in those locations. Adding one would need to account for E32-F07's unconditional warning requirement. A first-`{` extraction workaround would need to define how it finds and validates exactly one complete response while preserving or separately recording diagnostics; stream separation avoids that framing ambiguity.

## Decisions

- **Existing remediation and affected capability:** E32-F07 previously addressed machine-readable placeholder identity by adding `unresolved_placeholders` to the JSON response while retaining the required stderr warning. This is an existing remediation for structured diagnostics, not for callers that merge streams. The affected capability is keyed dispatch JSON consumed by host harnesses.
- **Recommended disposition — extend:** Extend `docs/architecture/shark-dispatch-prompt-assembly.md` and the `shark next` CLI reference with the stream contract: the complete JSON document is on stdout; diagnostics are on stderr; automation should capture and parse stdout separately. Include a shell or subprocess example that preserves the two streams. Keep the E32-F07 warning behavior intact.
- **Alternative:** If a harness cannot keep the streams separate, implement extraction in that harness at the process boundary and validate exactly one complete JSON response while handling diagnostics explicitly. Document the limitations of this fallback. Do not add a warning-suppression flag without reconciling the E32-F07 requirement and documenting its scope.
- **Documentation path correction:** Update the resolution plan to point to the existing `docs/architecture/shark-dispatch-prompt-assembly.md` before implementation; the named `shark-rider-...` file does not exist.
- **Confidence and limitation:** The code and test establish the separate-stream behavior. This research did not run a shell-level reproduction that merges file descriptors; the invalid combined stream follows from the warning and JSON being emitted to the two descriptors in sequence.
