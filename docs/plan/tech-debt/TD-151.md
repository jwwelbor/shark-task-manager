# B044 sprint-claim filter: reuse entitytype helper, batch claim lookups

## Description

From B044 code review (docs/review/bugs/b044/code-review-20260828-0011-B044.md), non-blocking findings on the SprintService claim-aware filter (commit ca4701b8):

F1 (should-fix): claimEntityTypeForBacklogType (sprint_service.go) reimplements entitytype.WorkflowLevelOrSelf, a package already imported in the same file for the inverse direction (line ~1279). Should call that helper instead of hand-rolling the mapping -- correctness is fine today, but this is decay risk if a new entity type is added and only one of the two mappings gets updated.

F2 (should-fix): GetNextTask now issues one IsClaimable query per candidate (N+1) instead of a batch lookup. Batch precedent exists: ListActiveReadOnly/FilterActiveReadOnly, used by PortfolioAdviceService. Same pre-existing pattern already used by StandalonePlanningService, so not a regression, but both call sites could move to the batch API together.

F3 (minor): two branches added by the fix are untested -- the "all candidates claimed" case (should return nil/empty rather than erroring) and IsClaimable's own error path (should the whole GetNextTask call fail, or skip-and-continue?). Worth explicit coverage.

F5 (informational, separate from this fix): the claim lookup's key axis is unnormalized (keys.Normalize is ToUpper only) -- pre-existing, repo-wide, not introduced by B044. Filed here as a pointer; may warrant its own bug if it's ever a live issue.
