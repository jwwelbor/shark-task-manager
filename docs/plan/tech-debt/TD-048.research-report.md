# Research report — Four plan/next test gaps admit real regressions

## Scope

This report covers the four independent test gaps recorded as PR #139
deep-review findings N9, N10, N13, and N14:

1. claim-expiry and task-claim SQL in the plan-hierarchy repository;
2. plan-specific same-entity recursion after an agentless auto-advance;
3. non-terminal list filters used by standalone planning; and
4. parent-type to child-workflow mapping in hierarchy filtering.

The affected capability is correct work eligibility and selection across the
`shark plan` and default fan-out `shark next` paths. The four boundaries
convert persisted lease state, workflow configuration, provider filters, and
status transitions into either a claimable candidate, a promptless hierarchy
selection, or exclusion from the plan.

The remediation extends the test suite introduced with `shark plan` in commit
`31250b90` and strengthened during PR #139. It does not replace the production
capability or change runtime behavior. Each new test must drive the production
entry point at the correct layer: a real database only in the repository test,
mocked providers in service and CLI tests, and a real workflow service over a
test configuration for workflow semantics.

Shared vocabulary:

- **Fresh claim**: a lease whose heartbeat is at or after the configured
  cutoff and is therefore active.
- **Expired claim**: a lease whose heartbeat precedes the cutoff and is
  therefore claimable again when TTL is positive.
- **Never-expiring policy**: claim TTL zero, under which every persisted claim
  remains active regardless of heartbeat age.
- **Mode-preserving recursion**: same-entity resolution after auto-advance
  continues with plan's one-level cascade strategy rather than next's
  descendant traversal.
- **Provider filter contract**: standalone planning requests default
  non-terminal lists by keeping `ShowAll` false; the entity service/repository
  owns the actual terminal filtering.
- **Child-workflow mapping**: epic parent uses the feature workflow; feature
  parent uses the task workflow.
- **Counterfactual test**: a test whose assertions fail under the exact
  plausible mutation named by the debt record.

## Findings

1. **All four gaps remain present in the live suite.** Commit `31250b90`
   introduced the plan hierarchy repository, services, command, and their
   initial tests. Commit `543ea021` added stronger keyed-fork tests and removed
   unrelated unreachable branches, and squash commit `2a5719e0` shipped the
   complete PR #139 work. None of those revisions adds the four counterfactual
   cases described by TD-048.

2. **N9: the epic claim fixture proves only “row exists and fresh means
   claimed.”** `TestReadDirectChildrenEpicReturnsOrderedFeaturesAndClaimState`
   inserts one feature claim with `last_heartbeat == evaluatedAt` and reads
   with a 15-minute TTL. The unclaimed feature proves `c.id IS NULL` maps to
   false, but replacing the SQL with `WHEN c.id IS NULL THEN 0 ELSE 1` still
   passes. No case distinguishes a heartbeat before the cutoff, the
   `claimTTL == 0` never-expiring branch, or the direction of the
   `julianday(last_heartbeat) >= julianday(cutoff)` comparison.

3. **N9: the separate task query has no claim evidence at all.**
   `TestReadDirectChildrenFeatureReturnsTasksAndAllDependencySources` exercises
   stable ordering and both dependency sources, but inserts no
   `entity_claims` row and makes no `Claimed` assertion. The task query repeats
   the claim CASE expression and passes seven positional parameters spanning
   claim policy, dependency relationship types, claim entity type, and parent
   key. Its dependency assertions constrain some binds, but not the claim
   entity-type bind or the task `Claimed` projection.

4. **N10: the plan recursion distinction is documented but not observed by a
   counterfactual.** `applyPlanWireAction` exists because agentless
   `advance_status` must recurse through `resolvePlanEntity`, preserving
   one-level plan selection if the new status maps to `cascade`.
   `TestTryPlanHierarchyAutoAdvancesCascadeCompleteParentWithNoNewSideEffects`
   tests the other auto-advance path and lands on a `spawn_agent` action.
   `TestResolvePlanEntityLeafMatchesKeyedNextRenderedResponse` tests leaf
   parity. Neither lands on a tied cascade after `advance_and_recurse`, so
   substituting `resolveNext` for `resolvePlanEntity` remains green.

5. **N10 overlaps TD-045 and should protect semantics, not a helper name.**
   TD-045 recommends replacing the duplicated next/plan resolvers and wire
   helpers with a common core carrying an explicit cascade strategy. A test
   that calls `applyPlanWireAction` directly would become obsolete during that
   remediation. The durable entry point is `resolvePlanDispatch`: begin at an
   agentless `advance_status`, transition into `cascade`, expose two tied
   direct children, and assert a one-level `HierarchyPlanSelectionResponse`
   rather than a descendant dispatch.

6. **N13: all standalone provider fakes discard the production argument.**
   `standaloneNextBugStub.ListBugs`,
   `standaloneNextChangeStub.ListChangeCards`, and
   `standaloneNextTechDebtStub.ListTechDebts` leave their filter parameters
   unnamed and return canned slices. Their fixture entities omit status.
   `StandalonePlanningService` correctly passes zero-value filters today, and
   each entity service maps `ShowAll` to its repository's include-terminal
   option, but changing any call to `ShowAll: true` leaves the standalone suite
   green. Claim/dependency filtering cannot recover because it does not inspect
   candidate status.

7. **N13 is an argument-contract test, not a request to duplicate status
   classification.** A strict or capturing fake should assert that
   `ShowAll` is false for each of bugs, change cards, and tech debt. The
   existing entity-service and repository suites remain responsible for
   proving that false excludes their configured terminal statuses. Adding a
   second workflow terminal classifier inside `StandalonePlanningService`
   would duplicate provider behavior and create another drift surface.

8. **N14: the only existing-parent service test exercises feature to task.**
   `TestPlanHierarchyServiceFiltersInMemoryAfterOneSetRead` calls
   `DescribeChildren("feature", ...)`, so it exercises the
   `feature -> workflow.LevelTask` arm. The epic invocation in
   `TestPlanHierarchyServiceParentNotFoundErrors` exits before workflow
   classification. No existing test reaches the
   `epic -> workflow.LevelFeature` arm with children.

9. **N14 is masked by symmetric terminal vocabularies in broader fixtures.**
   `b029CustomWorkflowConfig` and `planEdgeWorkflowConfig` both use `shipped`
   as the task and feature terminal status. Swapping the two mapping arms still
   classifies `shipped` as terminal and passes. A dedicated workflow fixture
   must use different feature and task terminal names; testing only the
   shipped default vocabulary cannot detect a wrong level selection.

10. **The four focused tests collectively cross every production seam without
    violating test architecture.** Repository claim cases belong in
    `internal/repository/planhierarchy` with isolated SQLite. The CLI recursion
    case belongs in `internal/cli/commands` with transitioner, action, and
    child-service fakes. The filter and workflow-level cases belong in
    `internal/services` with mocked readers and a real workflow service.
    A single full-stack database CLI fixture would be slower, harder to
    diagnose, and prohibited by the CLI testing rule.

## Decisions

1. Close N9 in `internal/repository/planhierarchy/repository_test.go` using the
   real isolated database. Add a small claim-insert helper so heartbeat,
   entity type, and entity key remain explicit in each case.
2. For epic children, use one fixed `evaluatedAt`: an unclaimed feature, a
   fresh claim, and a claim from 30 minutes earlier. With TTL 15 minutes,
   assert only the fresh claim is active. Re-read with TTL zero and assert both
   persisted claims are active. These assertions fail if cutoff comparison,
   never-expiring handling, or no-row handling is removed.
3. In the existing feature-to-task repository test, insert a fresh task claim
   on exactly one of the three tasks and assert the complete claimed-flag
   vector. Keep the dependency assertions so the seven-parameter query is
   constrained from both claim and dependency sides.
4. Close N10 through `resolvePlanDispatch`, not
   `applyPlanWireAction`. Configure an initial agentless `advance_status`, a
   forward transition into `cascade`, and two tied direct children. Make the
   next-style descendant path observably different, then assert plan returns
   one-level selection. Add the no-safe-transition case and assert pause with
   no transition.
5. Coordinate N10 with TD-045: whichever item is implemented first adds the
   semantic regression test; do not duplicate it or preserve a plan-specific
   helper solely for TD-048.
6. Close N13 with argument-capturing fakes for all three provider interfaces.
   Invoke `Plan` once per collection and assert the received filter has
   `ShowAll == false`. Do not add terminal-status filtering to
   `StandalonePlanningService` or encode workflow terminal lists in the fake.
7. Close N14 with a dedicated asymmetric workflow configuration. Prefer one
   table-driven test that exercises both `epic -> feature` and
   `feature -> task`, with distinct feature and task terminal statuses, so
   swapping either mapping arm fails.
8. Preserve existing layer boundaries: only repository tests use SQLite;
   service and CLI tests mock repositories/services while using real pure
   workflow classification where that is the contract under test.
9. Do not add a permanent mutation-testing framework for these four cases.
   The named mutations are precise design checks for assertion quality; focused
   counterfactual tests provide durable coverage at substantially lower scope.
10. During implementation, run targeted tests for
    `./internal/repository/planhierarchy`, `./internal/services`, and
    `./internal/cli/commands`, then run the mandatory `make fmt`, `make lint`,
    and `make test` gate.
