# AnalyzeHistory/replacementRecordPath accepts epicRunID with no format allowlist

## Description

internal/integration/history.go's AnalyzeHistory(projectRoot, epicRunID, base, head, events) and buildAndPersistReplacementRecord/replacementRecordPath join epicRunID directly into a .shark/runs/<epicRunID>/... filesystem path with no character allowlist -- the same defect class fixed in T-E34-F08-007's Backfill (backfill.go: unvalidated --epic-run-id enabled path traversal outside .shark/runs/). AnalyzeHistory currently has zero production call sites anywhere in the repo (verified via repo-wide grep during T-E34-F08-007's code-review defect-class sweep on 2026-09-05), so this is a latent instance, not currently exploitable. Whichever task first wires AnalyzeHistory to a caller that accepts an externally-supplied epicRunID (CLI flag, service input, etc.) must call integration.ValidateEpicRunID(epicRunID) (internal/integration/backfill.go) on that value before invoking AnalyzeHistory -- the exported validator already exists and is reused by Backfill and (pending) T-E34-F08-015's CLI layer for the identical class.

## Impact

Not currently exploitable: `AnalyzeHistory` has no production call site
anywhere in the repository today (verified with a repo-wide `grep -rn
"AnalyzeHistory(" --include="*.go" .`, matching only its own definition).
The risk is latent — if a future task wires `AnalyzeHistory` to a caller
that passes an externally-supplied `epicRunID` (e.g. a new CLI flag or
service input) without first validating it, the same path-traversal
class T-E34-F08-007's code review caught in `Backfill` (an unvalidated
identifier joined directly into a `.shark/runs/<epicRunID>/...`
filesystem path) reopens at this site.

## Resolution Plan

Before (or as part of) wiring `AnalyzeHistory` to any caller that accepts
an externally-supplied `epicRunID`, call
`integration.ValidateEpicRunID(epicRunID)` (exported from
`internal/integration/backfill.go`) on that value and reject before
calling `AnalyzeHistory`/`buildAndPersistReplacementRecord`. No new
validator is needed — this one already exists and is reused by `Backfill`
and (pending T-E34-F08-015) the `shark integration backfill` CLI layer for
the identical defect class.
