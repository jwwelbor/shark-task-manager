# E34-F10 guard-test helpers: stale hardcoded status list and minor DRY duplication

## Description

`internal/templates/includes_test.go`'s E34-F10 guard-test additions (T-001,
T-003) have four small, non-blocking craft issues flagged at the E34-F10
feature-level code-review gate (round 1, `code-review-*-E34-F10.md`), found
independently by the reviewer and confirmed by an independent codex
red-team pass:

1. `TestProductCriticalPathGuardPartial_RendersStandalone`'s hardcoded
   `forbiddenStatusNames` list (~line 485) omits the workflow step key
   `specification` (present at
   `internal/sharkdata/default_data/workflow/feature.yaml:176`), unlike
   T-003's `workflowStepKeysUnion` helper, which derives the same kind of
   negative-token list programmatically and correctly. The guard's actual
   shipped text does not currently contain the word "specification", so
   this is a latent test gap, not a live false-pass — `specification` IS
   already covered end-to-end by T-003's
   `TestTwelvePromptRendersGuardBlockContainsNoStatusOrCLIVerb`, which uses
   the correct, dynamically-enumerated key set against the real rendered
   guard block in every one of the twelve wired prompts (including
   `feature/specification.md`'s own render). But this standalone test's own
   list should not silently drift from the live schema.
2. The five REQ-F-034 evidence-class terms are declared as two separate
   literals: an inline slice in `TestProductCriticalPathGuardPartial_RendersStandalone`
   (~line 473-480) and the package-level `productCriticalPathGuardEvidenceClassTerms`
   var (~line 939-945) used by T-003's tests. Same list, two sources.
3. `NewOrchestratorRenderer(canonicalPromptsDir)` + `require.NoError` setup
   is duplicated between `TestSpecificationTestPlanningApprovalRendersNameEvidenceClassesInGuardBlock`
   and `TestTwelvePromptRendersGuardBlockContainsNoStatusOrCLIVerb` (~line
   954-955, 995-996).
4. `extractProductCriticalPathGuardBlock`'s start/end markers ("PRODUCT
   CRITICAL-PATH GUARD" / "makes the choice for you.") are prose substrings
   from the guard's own text, and the helper does not assert either marker
   occurs exactly once in the full rendered prompt before slicing — if
   surrounding prompt content ever independently contained either
   substring, extraction could silently grab the wrong span.

## Impact

Cosmetic/maintainability only — no production behavior is affected, and the
real AC-5/REQ-NF-002 invariant (no bare workflow status leaking into any
wired prompt's guard block) is already fully and correctly verified by
T-003's dynamically-enumerated test. Left unaddressed, item 1 could
re-introduce a stale hand-maintained list if `workflowStepKeysUnion` is
ever removed or bypassed; items 2-3 are minor duplicate-source-of-truth
risk in test code; item 4 is a low-probability test-extraction fragility.
Confirmed non-blocking by E34-F10's code_review (round 1,
`docs/review/E34-prompt-and-skill-improvements/E34-F10-product-critical-path-guard-for-delivery-workflows/code-review-*-E34-F10.md`).

## Resolution Plan

In `internal/templates/includes_test.go`:
1. Replace `forbiddenStatusNames` in `TestProductCriticalPathGuardPartial_RendersStandalone`
   with a call to `workflowStepKeysUnion(t, canonicalWorkflowDir)` (reorder
   the helper above this test, or extract it to a shared test-helpers file).
2. Have `TestProductCriticalPathGuardPartial_RendersStandalone` reuse the
   package-level `productCriticalPathGuardEvidenceClassTerms` var instead of
   its own inline literal.
3. Extract a small `newCanonicalOrchestratorRenderer(t *testing.T) *OrchestratorRenderer`
   test helper and use it in both call sites.
4. Add `require.Equal(t, 1, strings.Count(rendered, marker), ...)` (or
   switch to dedicated non-prose sentinel comments in the partial) before
   slicing in `extractProductCriticalPathGuardBlock`.
