# resolveCascade's cache parameter silently ignored in planResolutionMode branch

## Description

entityResolutionStrategy.resolveCascade(ctx, cache *nextAdapterCache, ...) in internal/cli/commands/next.go takes cache explicitly, but the planResolutionMode branch ignores it entirely and instead reads s.planCache (whose embedded *nextAdapterCache happens to equal the value the caller already passed, since resolvePlanDispatch calls resolveEntity(ctx, cache.nextAdapterCache, planResolutionStrategy(cache), ...)). The two values are identical today by construction of the call sites, but nothing enforces that; a future edit to either call site could desync them silently without a compiler or test signal. See code review finding F5.

## Impact

Low. No observed divergence today; risk is purely latent — a future edit to `resolveCascade` or `resolvePlanDispatch`'s call sites could silently desync the passed `cache` from `s.planCache` with no compiler error or failing test to catch it, since the `planResolutionMode` branch never reads its own parameter.

## Resolution Plan

Either drop the unused `cache` parameter from `resolveCascade`'s signature in `internal/cli/commands/next.go` and derive it from `s` in both branches (`s.planCache.nextAdapterCache` for plan mode), or store the `*nextAdapterCache` once on the strategy so there is a single source of truth instead of two names that happen to agree.
