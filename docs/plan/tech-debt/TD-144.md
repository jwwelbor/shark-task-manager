# Add duplicate-flag first-occurrence-wins regression case for run-review-comparison.sh in tc080

## Description

Round 9 code review (UAT-R2-01 fix): bench/scripts/tests/tc080_spend_gate_refusal_test.sh's duplicate-flag regression (lines 703-748, a deliberately repeated --max-cost-usd with two different values, proving first-occurrence wins in the materialized --limits file and the real I-07 record) exercises only the batch driver (run-lifecycle-batch.sh). run-review-comparison.sh shares the identical mechanism (same _spend_gate_flag_value call against ORIGINAL_ARGV) so current risk is low, but no test would catch a future comparison-driver-specific reparse regressing this. Fix: add one duplicated --max-cost-usd end-to-end case through run-review-comparison.sh mirroring the existing batch-driver case. Independently identified by codex red-team (finding 3) during tech-lead craft review; not a blocker because the shared-function design makes the batch-driver proof representative of both call sites today.

Related, advisor-prompted addendum (same round): the existing comparison-driver assertion (`verify_operator_limits_won` at tc080_spend_gate_refusal_test.sh:698-699) checks `$CAPTURED_LIMITS_FILE`, which the wrapper overwrites on each of the two `dispatch_gate()` invocations (qa, then deep_review) -- so it directly proves only the *last* gate's snapshotted content. The separate `grep -c -- "--limits" ... -eq 2` proves both invocations carried the flag, but not independently that both carried the *same* value. This is correct today only because both gates share the single `$OPERATOR_LIMITS_FILE` materialized once per invocation (a design fact, not something this assertion itself verifies). When adding the duplicate-flag case for the comparison driver above, also snapshot and assert both gates' captured limits content independently (e.g. two capture files, one per gate) so the test proves the invariant rather than assuming it.
