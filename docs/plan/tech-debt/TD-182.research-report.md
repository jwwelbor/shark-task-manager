# TD-182 research report — gate lease lifetime across steps

## Scope

Verify the reported premise that a `gate_result_v1` stage releases an entity
lease merely because its worker has retired, while the same `shark run`
invocation may still dispatch a later stage for that entity. This is a
lease-lifetime question, not a request to change the E34 gate-result contract
without proving its current behaviour.

## Findings

`Run()` supports sequential stages under the same entity lease. Current gate
ingestion first persists with `RetirementConfirmed: false`; only a terminal
target causes a second persistence call with both `RetirementConfirmed: true`
and `RunConcluded: true`. The coordinator releases only when both signals are
true. Direct controller and coordinator regression tests cover a non-terminal
stage retaining the lease and a terminal stage releasing it exactly once; the
end-to-end test separately proves that `Run()` dispatches the two-stage path.

History shows the reported defect pre-dated that implementation: the
two-signal fix merged in PR #211 (commit `6c1bce64`) and the later historical
closure evidence was carried by PR #233 (commit `188f8e8c`). TD-182 remained
open because its tracker transition was missed, not because a current release
race remains.

## Decisions

Reuse the existing two-signal gate-persistence contract. No code remediation
is required. TD-182 should proceed through its normal workflow as already
remediated; it is not a `wont_fix` because the original defect was real and is
now covered by current implementation and regression tests.

The research prompt requests related-document registration, but the installed
`shark related-docs add` surface accepts only epic, feature, task, bug,
change, and question parents; it has no tech-debt parent flag. The report path
is therefore recorded in TD-182's tracker evidence instead of fabricating an
unsupported relationship.
