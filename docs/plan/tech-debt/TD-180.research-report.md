## Scope

TD-180 as filed claimed the canonical `gate_result_v1` adoption matrix in
`docs/plan/E34-prompt-and-skill-improvements/architecture.md` was missing a
"deferred to E34-F08" note for epic `integration_review`. Verify that premise
against HEAD, and correct the doc to match the shipped workflow YAML rather
than assuming the premise still holds.

## Research checklist

- [x] `scope_vocabulary` — Evidence: docs/plan/E34-prompt-and-skill-improvements/architecture.md
- [x] `affected_implementation_or_contract` — Evidence: internal/sharkdata/default_data/workflow/epic.yaml

## Findings

- The record's premise was stale. `epic.integration_review` now exists in the
  shipped workflow (added by E34-F08, which has since landed), so "the step
  doesn't exist yet" is no longer true. But architecture.md's adoption-matrix
  sentence had drifted in the *opposite* direction from what TD-180 assumed:
  it listed epic `integration_review` alongside `feature_review` as opting
  into `gate_result_v1`, which is not and was never true.
- `internal/sharkdata/default_data/workflow/epic.yaml`: `feature_review`
  (line 144) carries `result_contract: gate_result_v1` plus a complete
  `outcome_roles` map. `integration_review` (lines 155-170) carries neither
  `result_contract` nor `outcome_roles` — it defaults to `legacy`.
- `internal/config/workflow/result_contract_adoption_matrix_test.go` is the
  canonical enforcement point. Its `canonicalAdoptionMatrix` map lists only
  `epic: {"feature_review"}` (not `integration_review`), with a code comment:
  "architecture.md's 'Compatibility and migration' 13-entry canonical
  adoption matrix (T-E34-F05-005), minus the one entry this task cannot land
  yet: epic `integration_review` does not exist in the shipped epic workflow
  — it is added by E34-F08 ... Until that step exists, this test asserts the
  12 entries that do." This is the exact code comment TD-180 refers to — but
  it was written when `integration_review` didn't exist yet, and the codebase
  has since moved past that state without the comment or the doc being
  reconciled.
- Checked whether E34-F08's own docs record an intent to later adopt
  `gate_result_v1` for `integration_review`: `E34-F08.../spec.md` REQ-F-004
  and `tasks/T-E34-F08-009.md` (the task that added the step to
  `epic.yaml`) both specify only `outcomes: {pass, fail, blocked, on_hold}`
  and `action: spawn_agent` — neither mentions `result_contract` or
  `outcome_roles`. No document records a plan to migrate the step later.
  Conclusion: the correct wording is "remains legacy," not "deferred to
  E34-F08" — E34-F08 is what *added* the step, not a promise to migrate its
  contract.
- Sanity-checked the rest of the adoption-matrix sentence against the shipped
  YAML for every other entity: feature `specification`, `test_planning`,
  `task_review`, `code_review`, `qa`, `approval` (all carry
  `result_contract: gate_result_v1` in `feature.yaml`); tech-debt `triaged`,
  `in_progress` (both carry it in `tech-debt.yaml`); change-card
  `development`, `code_review`, `qa` (all carry it in `change.yaml`). All 11
  of those entries are correct as documented — only the epic
  `integration_review` entry was wrong.

## Decisions

- Corrected `architecture.md`'s adoption-matrix sentence to list only the 12
  steps that actually carry `result_contract: gate_result_v1`, and added a
  clause stating epic `integration_review` (added by E34-F08) remains
  `legacy` because no document records an intent to migrate it later.
- Did not add a "deferred to E34-F08" note as TD-180 originally proposed,
  since that phrasing would misstate cause and effect (E34-F08 added the
  step; it did not defer the step's `result_contract` adoption to itself).
- Filled in TD-180.md's Impact/Resolution Plan/Resolution Notes sections,
  recording that the original premise was stale and describing the actual
  fix.
