# Add non-empty OPERATOR_LIMITS_FILE guard at the dispatch_pair/dispatch_gate consumption site, not only at materialization

## Description

Round 9 code review, raised by advisor second-look: OPERATOR_LIMITS_FILE="" is the unconditional default in both run-lifecycle-batch.sh and run-review-comparison.sh; it is only assigned a real mktemp path inside the 'if mode==pilot||baseline' spend-gate block. dispatch_pair() (run-lifecycle-batch.sh:739-741) and dispatch_gate() (run-review-comparison.sh:691-693) pass --limits "$OPERATOR_LIMITS_FILE" unconditionally with no guard of their own. run-lifecycle.sh's limits_from() (run-lifecycle.sh:299-306) does 'if path:' -- an empty string is falsy, so --limits "" silently reverts to the scenario's own resource_policy default, bit-for-bit the original UAT-R2-01 failure mode, with no diagnostic. Traced exhaustively this round (code-review-2026-08-21T1954-E40-F10.md, Part 1): today this is NOT reachable -- mode is validated to exactly {preview,pilot,baseline}, the preview branch unconditionally exit()s before either dispatch function's call site in both scripts, so dispatch_pair/dispatch_gate can only execute when the spend-gate block already ran and materialized a non-empty file (or the script already exited via refusal). Non-blocker today because unreachable, but positional (true only because of current control-flow shape), not structural -- exactly the distinction commit 238df1da's own guard at the materialization site was written to close. Fix: assert non-empty $OPERATOR_LIMITS_FILE immediately before each dispatch_pair/dispatch_gate RUN_LIFECYCLE_BIN call (named diagnostic, mirroring 238df1da's pattern), or have the dispatch call omit --limits entirely when the variable is empty so run-lifecycle.sh's own required-flag path decides, rather than silently accepting an empty value.
