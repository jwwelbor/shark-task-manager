# TD-188: run.go GateIngest wiring guard is AST-only, feasibility of execution-level test

## Scope

This research investigates whether `TestRunRunRunControllerDepsAlwaysSetsGateIngest` in `internal/cli/commands/run_test.go` (line 818) should be extended with an execution-level test to supplement its source-invariant AST check. The investigation must establish:

1. What the current AST test asserts and its relationship to the test-plan decision
2. What execution-level coverage already exists in `controller_gate_e2e_test.go`
3. Whether execution-level coverage of run.go's own GateIngest wiring is reachable without violating CLI-test constraints
4. Whether D7 (the source-invariant convention) sanctions the AST approach as correct

## Findings

### 1. Current AST Test

**What it asserts** (run_test.go:818-850):

The test `TestRunRunRunControllerDepsAlwaysSetsGateIngest` uses `go/parser` to inspect the source text of `runRun` and assert that:

- Every `runner.RunControllerDeps{...}` composite literal (there are two: top-level controller at line ~400-416 and cascade-child controller inside runChild closure) sets `GateIngest` to a non-nil value
- Neither site sets `GateIngest: nil` (which would cause `ingestGateResultForDispatch` to fail closed with "requires a configured GateResult persistence coordinator")

**Purpose** (as documented in comment at line 810-815):

The bug this guards against: before the fix, neither construction site set `GateIngest` at all, so `RunController.gateIngest` stayed nil. Every `gate_result_v1` step (including the shipped `change.code_review` and `change.qa` steps) would fail closed inside `ingestGateResultForDispatch` the moment a real operator ran `shark run` in the foreground. The fix was discovered during E34-F05-004 code-review.

**Why AST, not execution-level** (line 815-816):

The comment references "D7 source-invariant convention for a function with no mock seam" and points to the "AST source-guard test infrastructure" comment at line 631.

---

### 2. Existing Execution-Level Coverage

**controller_gate_e2e_test.go** (TestRunController_Run_GateResultV1StepRoutesThroughGateIngest, line 90+):

This test drives the full controller.Run() loop end-to-end for a step whose resolved result_contract is `gate_result_v1`. It:

- Constructs an e2e harness that implements `runner.EntityTransitioner`, `gatepersist.Transitioner`, and `gatepersist.StatusReader`
- Builds a `gatepersist.Coordinator` manually (hand-constructed, not via run.go's builder)
- Calls `controller.Run()` with the coordinator and verifies that `ingestGateResultForDispatch` actually processes the gate result and transitions the entity through the coordinator

**What it proves**: The controller-side integration is end-to-end; gate result ingestion works when the coordinator is present.

**What it does NOT prove**: That run.go's own `buildRunControllerGateIngestDeps` correctly constructs and passes a non-nil coordinator to `RunControllerDeps`.

---

### 3. Execution-Level Test Feasibility for run.go's Construction

**The blocking constraint** (from `.claude/rules/testing/cli-tests.md`):

*"ONLY repository tests should use the real database. Everything else MUST use mocked repositories."*

**Why run.go's construction cannot be tested at execution level without seam changes:**

1. `buildRunControllerGateIngestDeps` (line 817-823) calls `buildGateCoordinator(ctx)`
2. `buildGateCoordinator` internally calls services that need repositories (inspecting line 260-263 context, the gateIngestDeps is used inside the dispatch loop where `buildTransitioner` is called unconditionally)
3. `buildTransitioner` (line 830+) calls `cli.GetTaskService()`, `cli.GetFeatureService()`, `cli.GetEpicService()`, etc. for each entity type
4. All `cli.Get*Service()` accessors internally call `cli.GetDB()`, which returns a real database connection
5. Testing `runRun` end-to-end would require:
   - A real database (violates CLI-test golden rule), OR
   - Injectable seams for all `cli.Get*Service()` calls (6+ call sites), plus possibly a mock `RunController` to prevent actual dispatch

**The seam refactoring cost**:

From run_test.go's comment (line 633-636): The test-plan's "Considered and rejected" section explicitly evaluated extending `runClaimSvcOverride`-style injection to `buildTransitioner` and `cli.Get*Service` and **rejected it as disproportionate for a STANDARD-scored feature (six-plus call sites would need refactoring)**.

**TD-165 parallel finding**:

TD-165.research-report.md §3 concluded that an execution test for similar wiring gaps would require "2–3 new injectable seams" and is "feasible but requires refactoring the global accessor pattern". The same conclusion applies to TD-188.

---

### 4. D7 Source-Invariant Convention

**What D7 sanctions** (run_test.go:631-640):

D7 explicitly authorizes `go/parser` source-invariant checks for:

- Functions with no injectable mock seam (because extending injection would be disproportionate)
- Checking syntactic/structural properties (wiring order, field presence, writer targets)
- NOT checking behavioral properties

The comment states: *"D7 sanctions go/parser source-invariant checks for exactly this class of property (wiring order, writer target) — syntactic properties, not behavioral ones, following the codebase's existing source-invariant validator convention (e.g. internal/services/portfolio_advice_service_test.go)."*

**Applied to `buildRunControllerGateIngestDeps`**:

The AST test checks the syntactic property: "is `GateIngest` field always set to a non-nil value in both `RunControllerDeps` construction sites?"

This is precisely the class of check D7 sanctioned.

---

### 5. Residual Gap Assessment

**Is there a gap that execution-level testing would close?**

Yes, but it is constrained by architecture, not oversight:

- The AST test cannot detect if `buildGateCoordinator` itself fails or returns nil (though `buildRunControllerGateIngestDeps` wraps the error; inspecting line 819-821)
- The AST test cannot detect if the coordinator is used incorrectly downstream
- However, `controller_gate_e2e_test.go` already proves that IF a coordinator is constructed and passed, it works end-to-end

**What would execution-level test close?**

An execution test could prove that `runRun` → `buildRunControllerGateIngestDeps` → `RunControllerDeps{GateIngest: ...}` actually happens, not just that the source code says so. But:

- This test is blocked by the CLI-test golden rule (can't use real DB)
- Fixing the block requires 6+ seams (disproportionate per test-plan)
- D7 explicitly sanctions the AST approach as correct for this class of property

---

## Decisions

**Recommendation**: **Keep the AST guard as-is; do not add execution-level test.**

**Rationale**:

1. **D7 explicitly sanctioned this approach** for syntactic wiring properties in functions with no injectable seam
2. **The test-plan already evaluated and rejected** the seam-refactoring cost (6+ call sites)
3. **Execution-level coverage of gate ingestion already exists** in controller_gate_e2e_test.go; it proves the gate coordinator works end-to-end when constructed
4. **The AST test catches the specific bug** that shipped undetected (GateIngest set to nil or unset), and re-runs on every test suite
5. **No new behavioral property is worth the seam cost**: the test cannot distinguish between "wrong coordinator" and "right coordinator"; that's already tested by controller_gate_e2e_test.go

The architecture is sound: the AST guard is the project's correct answer for this class of property.
