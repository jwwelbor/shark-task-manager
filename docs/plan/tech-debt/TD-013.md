# Investigate shark list startup slowdown from observability and repeated config loads

## Description

`shark list` has regressed from a near-instant command to a noticeably slower startup path. The current code path does repeated bootstrap work before rendering any list output:

- `PersistentPreRunE` reloads config and initializes observability on every invocation.
- `GetTagService()` calls `GetMaintainerGate()`, which re-runs project-root discovery and reloads config.
- List dispatchers for epics, features, tasks, and related entity types all construct fresh service graphs even for read-only listing.
- The project config enables observability with `exporter: "otlp"` and file logging, which may add startup overhead even when tracing and metrics are disabled.

The observed symptom is not limited to `shark list` itself; it affects the shared startup path that every list command uses. The suspicion is that the OTLP/observability path and repeated config loads are paying a fixed cost on every CLI invocation.

## Impact

Read-only CLI commands feel slow and heavy, especially on the common `list` path. That hurts AI-agent workflows because the command is often used in tight polling loops, so even a one-second regression becomes expensive quickly.

## Resolution Plan

1. Measure startup phases separately: config load, observability init, DB init, workflow init, and service construction.
2. Confirm whether OTLP provider setup is the dominant cost when `observability.enabled` is true but tracing/metrics are false.
3. Cache or reuse config and project-root discovery within a single process where safe.
4. Consider making maintainer/tag wiring lazy for read-only list commands so they do not pay gate/config startup cost unless needed.
5. If observability is the culprit, avoid initializing OTLP exporters when there are no active spans or metrics to export.
