# internal/db/db.go: ALTER TABLE + CREATE INDEX pairs in runPreQuestionMigrations aren't independently guarded

## Description

db.go:744,761,793 each pair one ALTER TABLE ADD COLUMN with a CREATE INDEX IF NOT EXISTS inside a single-column guard. A crash between them leaves the index permanently uncreated on rerun (performance regression, not a read failure — table reads still succeed, just unoptimized). Same guard shape as the migration-atomicity defect class fixed in T-E34-F01-001 but a different consequence class; deliberately deferred there. Consider using the same columnExistsInTable-style independent guard, or a separate index-existence check.
