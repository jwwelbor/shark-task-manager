# Dangling entity_relationships row wedges a keyed shark next fork

## Description

internal/services/plan_hierarchy_service.go:421 — resolveEdgeEndpoint errors hard when a relationship endpoint no longer exists, and attachForkCandidateEdges (internal/cli/commands/next.go) treats any edge-load error as fatal. So one orphaned entity_relationships row makes keyed 'shark next <epic|feature>' fail outright at a fork.

Orphans are a real state: entity_relationships has polymorphic ids with no foreign keys, and shark delete removes rows without cleaning them up. The portfolio path already treats this as expected — see PortfolioWarningDanglingRelationship and recordPortfolioDanglingRelationship in portfolio_relationship_evidence.go, which warn instead of failing.

The fatal behaviour is deliberate for the OTHER case: silently empty edges are indistinguishable on the wire from 'this candidate has no dependencies', which would invite a rider to launch genuinely coupled work in parallel. So the fix is to distinguish 'edge store unavailable' (stay fatal) from 'endpoint no longer exists' (drop the edge, attach a warning).

BLOCKED ON: no typed not-found error exists. Every repository returns an untyped fmt.Errorf('<type> not found with id %d'), so separating the two cases needs either a typed error introduced across repositories or string matching. String matching is too fragile to ship. The prerequisite is larger than this item.

Source: /shark-rider deep-review high on PR #139 (finding N7).
