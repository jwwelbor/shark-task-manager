# sequential_dispatch swaps the whole child-enumeration engine

## Description

internal/cli/commands/next.go — the sequential_dispatch config and --sequential flag switch 'shark next' between two different child-enumeration engines, not merely two traversal shapes. CascadeService does per-child IsClaimable with a fail-soft stderr warning and GetTaskDependencies; PlanHierarchyService evaluates claim expiry in SQL with no error surface and unions json_each/entity_relationships. Same command, same entity, two possible answers, and the fail-soft claim behaviour exists in only one of them.

The synchronization tax was already paid at introduction: this branch had to edit cascade_service.go to keep the two engines agreeing on dependency terminality. TestSequentialModeUsesLegacyCascade only asserts which seam is consulted, not that the two agree.

Fix: have one engine feed both modes, with 'sequential' controlling only whether a tie collapses to the first candidate or surfaces as a fork. If both engines must coexist, add a differential test asserting identical child sets and ordering from one fixture database.

Source: /shark-rider deep-review high on PR #139 (finding N5).
