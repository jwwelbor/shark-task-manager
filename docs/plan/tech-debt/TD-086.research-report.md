# TD-086 research report

## Scope

TD-086 concerns metadata collection for the read-only folder-listing capability:
`ViewerService.FolderFiles` reads a directory, and `folderFileEntries` projects
each `os.DirEntry` into the JSON returned by `GET /api/v1/viewer/folder-files/{path...}`.
The entry name, relative path, and directory classification are the primary
listing contract. File size is supplementary metadata used only to render a
size label in the viewer.

Today, `DirEntry.Info()` failure retains the entry and emits `size: 0`. That
response is available, but it makes unavailable metadata indistinguishable from
a real empty file. This report decides the response policy; it does not change
path containment, missing-directory behavior, sorting, or the endpoint route.

## Findings

1. **The behavior predates E27-F16.** `git blame` attributes the `Info()` call
   and zero-value fallback in `folderFileEntries` to commit `80233c740`
   (E27-F07, 2026-04-12). E27-F16 later extracted the helper while preserving
   that behavior. The E27-F16 review explicitly records the pre-existing
   best-effort behavior in TD-086, so this debt extends existing remediation
   rather than replacing the configured-folder work.

2. **`Info()` can fail after a successful directory read.** The Go `io/fs`
   contract allows `DirEntry.Info()` to fail with `ErrNotExist` when the entry
   is removed or renamed between `ReadDir` and `Info`. The current code keeps
   the entry, which is appropriate for a browsing response, but leaves `Size`
   at Go's zero value for both an error and an actual zero-byte file.

3. **The API and viewer can tolerate optional size metadata.** The handler
   returns the service DTO without transforming it. The viewer displays a size
   label only for a non-directory entry whose `size` is greater than zero;
   therefore a missing size already has the same visible result as the current
   fallback and does not block navigation or opening the file.

4. **The current test coverage does not exercise an `Info()` failure.** The
   service test covers normal files and directories, and the handler test
   asserts normal JSON serialization. Neither supplies a failing `os.DirEntry`
   nor distinguishes unknown metadata from `0` bytes. This leaves the intended
   policy undocumented and unprotected.

5. **Propagating one metadata error would weaken the established listing
   contract.** `readFolderEntries` already treats a directory that disappears
   as an available empty response, and the E27-F16 specification requires a
   missing navigation directory to show the existing empty listing rather than
   an error. Failing the whole request because one child disappeared is less
   useful and does not improve containment or correctness.

6. **No supported related-document link exists for tech debt.** The current
   `shark related-docs add --help` and `internal/cli/commands/related_docs.go`
   expose epic, feature, task, bug, change-card, and question parents only.
   A TD-086 link cannot be registered without extending that unrelated CLI and
   document-service capability. This report uses the established adjacent
   sidecar path instead.

## Decisions

1. **Keep folder listing best-effort.** Preserve each entry when `Info()`
   fails; do not turn a metadata race into a `500` response and do not omit the
   entry solely because its size is unavailable.

2. **Represent unavailable size explicitly.** Change `FolderFileEntry.Size`
   to an optional `*int64` with `json:"size,omitempty"`. Set it only after a
   successful `Info()` call for a non-directory entry. A real zero-byte file
   must serialize as `"size": 0`; unavailable metadata must omit `size`.
   This extends the existing DTO rather than creating a second endpoint or a
   diagnostic response shape.

3. **Do not add a per-entry error message to the public response.** The client
   has no corrective action for a transient metadata race. Omitting optional
   size is sufficient, preserves the compact listing contract, and avoids
   exposing filesystem error details through the viewer API.

4. **Add focused regression coverage at the helper and HTTP boundaries.** Use
   a test `os.DirEntry` whose `Info()` returns an error to prove the entry still
   appears and its `size` is omitted. Also prove a successful zero-byte file
   still emits `size: 0`, then keep the existing normal-listing and handler
   tests as caller coverage.

5. **Keep existing E27-F16 navigation remediation unchanged.** The capability
   continues to reuse `FolderFiles`, including its canonical containment check;
   this resolution changes only supplementary metadata semantics.
