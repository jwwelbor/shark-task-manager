# B046 JSON outcome parsing: last-line scan, legacy-workflow fail-closed behavior untested

## Description

From B046 code review (docs/review/bugs/b046/code-review-20260828-0037-B046.md), non-blocking findings on the JSON outcome parsing fix (commit 1cffcba8):

MAJ-1: recommendedOutcome()'s new JSON branch only fires when the ENTIRE trimmed stdout is valid JSON. The most likely real-world worker output shapes -- prose followed by a trailing JSON object, or a JSON object inside a markdown code fence -- still fall through to pass-first, i.e. the fix closes the narrow "pure JSON stdout" case but not the more common "prose + JSON" case. Recommended follow-up: parse the LAST non-empty line specifically (borrowing the parseQuestionResponseHandoff idiom already in internal/runner/controller.go), not a whole-stdout parse and not an all-lines scan (which would newly accept a JSON object appearing inside a documentation/example fence -- a real regression risk).

MAJ-2: on a legacy (non-route-based) workflow with an empty Outcomes map, a JSON-emitting worker now hard-fails the run ("agent recommended unknown outcome") where it previously silently advanced via pass-first fallback. This fail-closed behavior is architecturally correct for a workflow gate, but it's a genuine behavior change with no test coverage for that specific legacy-workflow + JSON-outcome combination.

Minor: one new test's comment references a function name that doesn't exist in the codebase (garbled during authoring) -- cosmetic, worth fixing on next touch.
