# TD-027 research report

## Scope

Replace service-layer workflow-status literals with configured level workflows without changing display-only vocabulary that is not a workflow decision.

- [x] `scope_vocabulary` — Evidence: `docs/plan/tech-debt/TD-027.md:1-15`; `internal/workflow/service.go:364-367`.

- [x] `dependency_impact` — Evidence: `internal/services/epic_analytics_service.go:82-90`; `internal/services/viewer_service.go:747-903` consume status values at distinct entity levels.
- [x] `cross_boundary_risks` — Evidence: `internal/services/sprint_analytics_service.go:121-141,281-286,527-537` combines sprint filtering with terminal-status presentation.
- [x] `alternatives` — Evidence: `workflow.Service.ForLevel` supports exact phase/terminal queries; literal replacement without entity-level context would alter unrelated display semantics.

## Capability map

| Capability | Source | Decision |
| --- | --- | --- |
| Workflow phase classification | `workflow.Service` | REUSE — classify blocked and terminal states by level. |
| Service display rollups | feature, epic, display services | EXTEND — inject/use the correct level workflow at each decision point. |

## Findings

Some literals are workflow rules (blocked/terminal determination), while status labels used as fixed UI buckets are separate product vocabulary. The affected services already have or can receive a workflow service; their fixes must classify rather than substitute one configured status string.

## Decisions

Replace only semantic checks with `GetStatusesByPhase`, `GetTerminalStatuses`, or `IsTerminalStatus` at the owning entity level. Leave fixed UI bucket names for separately scoped follow-up work.
