# TD-028 research report

## Scope

Move task dependency auto-block, reopen, and auto-unblock status choices out of repository-owned hardcoded literals while retaining atomic task/history writes.

## Research checklist

- [x] `scope_vocabulary` — Evidence: `docs/plan/tech-debt/TD-028.md:1-15`; `internal/repository/task/dependency.go:308-317,454-463,527-645`.
- [x] `affected_implementation_or_contract` — Evidence: `internal/repository/task/repository.go:1498-1508`; `internal/services/task_service.go:1558-1759` owns task workflow access.
- [x] `pattern_contract` — Evidence: `internal/repository/task/dependency.go:489-509` already accepts caller-supplied terminal statuses for related dependency logic.
- [x] `dependency_impact` — Evidence: `internal/services/task_service.go:1622-1759` supplies terminal status data to repository mutation parameters.
- [x] `cross_boundary_risks` — Evidence: dependency writes insert task history in the same transaction; a service-side rewrite must preserve that transaction boundary.
- [x] `alternatives` — Evidence: caller-supplied status policy extends the existing terminal-status contract without injecting a workflow service into repositories.

## Capability map

| Capability | Source | Decision |
| --- | --- | --- |
| Dependency cascade transaction | `TaskRepository` | REUSE — retain repository atomicity. |
| Workflow classification | `TaskService` | EXTEND — pass an explicit task status policy into dependency mutations. |

## Findings

The repository cannot derive configurable workflow semantics safely. It already receives terminal statuses from TaskService, establishing the correct dependency direction. The remaining block, reopen, and unblocked targets require an explicit policy object instead of individual string parameters.

## Decisions

Add a task dependency status policy supplied by TaskService: blocked vocabulary/target, terminal vocabulary, and entry/reopen target. Repository code will apply the policy but not interpret workflow configuration.
