# TD-236 research report

## Scope

This research covers the human-readable empty result from `shark list <epic> <feature>` and `shark task list` when default completed-task filtering leaves no visible tasks. It follows the dispatcher, task-list command, query service, and table empty-output path. It also records B074's existing JSON empty-array remediation. The intended change extends task-list guidance while preserving default filtering, `--all`, and the JSON contract.

Vocabulary: **source tasks** are tasks returned for the selected feature before list filters; **visible tasks** are tasks remaining after the requested filters, including default completed-task hiding; **hidden completed tasks** are completed source tasks that would otherwise match the non-completion filters.

## Findings

1. The source path matches the reported behavior. The unified `list` dispatcher routes feature-scoped task requests into `runTaskList`; the task command calls `ListTasks`, emits JSON directly when requested, and otherwise passes rows to `cli.OutputTable`. That shared helper prints `No results found` for any empty row set and has no task-filter context.

2. `TaskQueryService.ListTasks` returns only the filtered tasks. It applies the requested status and other filters, then removes completed tasks when `ShowAll` is false. The returned slice does not include a count or reason for omitted rows, so the command cannot currently distinguish a feature with no tasks from a feature whose matching tasks are all hidden as completed.

3. B074 already remediated the machine-readable empty result. The current service initializes its filtered slice as non-nil, and the B074 regression tests assert an all-completed feature returns `[]` while `--all` preserves completed tasks. This report treats that as existing capability and keeps the planned terminal hint scoped to human-readable output.

4. `OutputTable` has a generic empty branch that only receives headers and rows, so it has no task-filter context. Other list renderers also call it (`internal/cli/commands/bug.go:646`; `internal/cli/commands/idea.go:790`; `internal/cli/commands/tech_debt.go:594`). Adding task-specific `--all` guidance to its unconditional empty case would give those lists a misleading hint. The task-list path needs enough contextual information to print a count only when matching tasks were hidden by completed filtering; otherwise it should keep the ordinary empty-result message. Preserve JSON output as an empty array without extra text.

5. No current result metadata exposes the hidden completed count. A narrow summary returned with the query results would make that count explicit. A second query with the same filters and `ShowAll` enabled is another feasible option, but it adds work on the empty-result path and must keep all other filters identical to avoid a false hint or count.

## Decisions

1. Extend the existing task-list capability with a human-readable hint that reports the number of matching completed tasks hidden and points to `--all`. Keep the normal `No results found` response when the count is zero or when other filters leave no matching tasks.

2. Keep the change task-list-specific. Do not replace B074's JSON empty-array remediation or alter the completed-task default, `--all` semantics, or output shape for JSON callers.

3. Before choosing the implementation seam, define how the query reports the hidden count while applying the same non-completion filters. Prefer explicit result metadata if it fits the service contract; if using a second query, reuse the exact filter set and only perform it when the visible result is empty.
