# research-report checklist validator misses Evidence: on soft-wrapped bullet lines

## Description

parseChecklist in internal/research/validator.go iterates strings.Split(section, "\n") and only inspects lines starting with "- [" for the checklist-module ID, then separately requires the literal substring "Evidence:" to appear on that SAME physical line. A checklist bullet written as normal prose that soft-wraps across multiple lines (e.g. an editor/agent producing readable ~80-char lines for a long module description) puts "Evidence:" on a later physical line that does NOT start with "- [" -- so the parser silently treats the bullet as present-but-missing-evidence, failing shark status advance with the confusing error: research checklist module "<module_id>" is missing evidence. The bullet visually contains an Evidence: clause to any human reviewer (it renders as one paragraph in Markdown), making this a bug-factory: an agent or human writing a well-formatted, wrapped research-report.md gets a validator failure that looks like missing content when the content is actually present, just line-wrapped. Confirmed reproduction 2026-08-03 in project wwgm: E04-F04's research-report.md scope_vocabulary bullet spanned lines 69-81 with Evidence: on line 78; shark status advance --outcome pass failed with the exact error above. Reflowing the bullet to one long unwrapped physical line (no interior newlines) fixed it with zero content change -- confirming the parser, not the content, was the defect. Already documented as a recurring quirk (point 5 and new point 15) in a wwgm-side memory note before this ticket; filing here so the fix lives with the actual parser code.

## Impact

Costs at least one wasted `shark status advance` round-trip (claim → dispatch
→ write report → advance → fail → diagnose → reflow → advance again) per
affected research-report, and the error message ("missing evidence") actively
misdirects the fix toward adding content that is already there. In automated
run loops (shark-rider `/run`), this consumes an extra dispatch cycle and,
worse, risks an agent "fixing" it by fabricating a NEW evidence citation
rather than reformatting, since the error looks like an evidence gap. Affects
any research-report author (human or agent) who writes readable, soft-wrapped
markdown instead of one long unwrapped line per bullet — the more
human-readable the source, the more likely it triggers this.

## Resolution Plan

Preferred fix: in `parseChecklist`, join each checklist bullet's full text
block (from its `- [` line up to, but not including, the next line starting
with `- [` or a blank line that precedes a non-continuation line) before
scanning for the module ID and the `Evidence:` substring, instead of scanning
only the single physical line the bullet starts on. This matches how a human
reader and any Markdown renderer already interpret the bullet (as one
list-item paragraph, soft-wraps included).

Alternative (cheaper, weaker) fix: keep single-line scanning, but improve the
error message when a bullet's continuation lines (checked separately) DO
contain "Evidence:" — e.g. `research checklist module "X" has an Evidence:
clause on a wrapped continuation line; write it as a single unwrapped line`
— so at least the fix is discoverable without external context.
