# ExcludeFromProgress fails open for custom workflows; duplicated DependsOn guard in sprint_service.go

## Description

From B058 code review, second pass (docs/review/bugs/b058/code-review-20260828-0111-B058.md), non-blocking findings on the sprint-readiness dependency fix (commits 2d58ed5a, 94a02d49):

1. ExcludeFromProgress fails open: the workflow-config validator never requires this field on terminal statuses, so a CUSTOM workflow declaring a terminal abandonment status without setting exclude_from_progress: true would silently be credited as satisfied by B058's fix -- reproducing the exact cancelled-dependency bug the fix closed, for a misconfigured custom workflow. This is a pre-existing contract gap shared by four other production consumers of ExcludeFromProgress (internal/progress/calculator.go:55, internal/services/feature_progress_service.go:318, internal/services/aggregate_policy.go:23, internal/services/epic_analytics_service.go:92) -- all four would already mis-report progress under the same misconfiguration, so this is a workflow-package design gap, not specific to sprint readiness. Recommended remedy: an explicit "successful terminal" selector distinct from bare IsTerminalStatus, or a workflow-config validator rule requiring exclude_from_progress on every terminal status that isn't the canonical success one.

2. Minor (from first-pass review, still open): computeDependencySatisfactionFactor and computeExternalDependencyTerminalStatus each independently guard/parse the DependsOn JSON field -- roughly 12 lines of duplicated logic across the two passes. Acceptable as shipped; worth factoring into a shared helper on next touch.

From the PR #201 pre-merge deep-review (dispatched-six-angle, commit 176add87 -- fail-loud + chunked external-dependency lookups):

3. Non-blocker (Angle D, complexity): `computeExternalDependencyTerminalStatus` (internal/services/sprint_service.go:2800) measures cyclomatic complexity 20 via `gocyclo -over 10`, over the project's threshold. It mixes three concerns: collecting distinct external dependency keys from `depends_on` JSON, chunked batch-fetching via `GetByKeys`, and filtering fetched tasks down to terminal-and-successful statuses. Recommended split: `collectExternalDepKeys(assignments, assignedKeys) []string`, `fetchTasksInBatches(ctx, taskRepo, keys) (map[string]*models.Task, error)`, `filterTerminalSuccessful(tasks, wf) map[string]bool`. Not blocking since the function is well-commented and covered by `TestSprintService_GetSprintReadiness_Factor2_ManyExternalDependencies_ChunkedLookup`.

4. Nit (Angle D, DRY): the new `GetByKeys` chunking loop (internal/services/sprint_service.go, `externalDepBatchSize` batches) is hand-rolled at the call site because `internal/repository/task/repository.go:1864` `GetByKeys` itself builds an unbounded `key IN (?,?,...)` clause with no internal limit, and no shared chunking helper exists anywhere in `internal/`. Consider pushing the batching down into `TaskRepository.GetByKeys` (or a shared repository-layer chunking helper) so every other unbounded-`IN` caller in the codebase benefits, rather than each caller reimplementing the loop.

5. Nit (Angle E, tests): `TestSprintService_GetSprintReadiness_Factor2_ManyExternalDependencies_ChunkedLookup` proves the multi-batch merge works (`externalDepBatchSize + 50` keys) but doesn't pin the chunk loop's exact boundary arithmetic (e.g. exactly `externalDepBatchSize` keys with no remainder, or `externalDepBatchSize + 1`). Optional: add those two boundary cases on next touch.

## Impact

Item 1 (ExcludeFromProgress fails open): a custom workflow that adds a terminal
abandonment status (e.g. "cancelled", "wont_fix") without also setting
`exclude_from_progress: true` is silently credited as satisfied by every
consumer of bare `IsTerminalStatus` — `internal/progress/calculator.go`,
`internal/services/feature_progress_service.go`,
`internal/services/aggregate_policy.go`,
`internal/services/epic_analytics_service.go`, and sprint readiness
(`internal/services/sprint_service.go`). This reproduces the exact
cancelled-dependency bug B058's fix closed, for any misconfigured custom
workflow — a config authoring error, not a code defect, but one with no
warning at validate time.

Item 2 (duplicated DependsOn guard): ~12 lines of duplicated
guard/parse logic across `computeDependencySatisfactionFactor` and
`computeExternalDependencyTerminalStatus` in `internal/services/sprint_service.go`.
Not a runtime bug; increases the risk that a future edit updates one copy and
not the other, silently diverging the malformed-JSON reporting split.

## Resolution Plan

Item 1: remedy (b) — a workflow-config validator rule, not remedy (a) (a new
runtime "successful terminal" selector). Rationale: every shipped entity
workflow (task/feature/epic/bug/change/tech-debt) already tags its one
success terminal `primary: true` and every other terminal
`exclude_from_progress: true` — the runtime selector this need requires
already exists as `WorkflowConfig.ArchiveTerminalStatus()`, validated
unambiguous by the existing `validatePrimaryDesignations` check. Remedy (b)
reuses that selector purely at validation time: `validateTerminalProgressExclusion`
(internal/config/workflow/validator.go) requires every terminal status other
than the one `ArchiveTerminalStatus()` designates to carry
`exclude_from_progress: true`, with no candidates to disambiguate when there
is only one terminal status. This closes the gap with zero changes to any of
the five runtime consumers (remedy (a) would have touched all five and
changed live selection semantics) — strictly a fail-closed guard on config
authoring, matching the shipped convention exactly.

Item 2: extracted `parseAssignmentDependsOn` (internal/services/sprint_service.go)
to share the guard + `json.Unmarshal` between both call sites, while
preserving the pre-existing division of responsibility: `computeExternalDependencyTerminalStatus`
still skips a parse error silently (malformed JSON is surfaced once, by the
other function), and `computeDependencySatisfactionFactor` still counts it.

## Resolution Notes

2026-09-18: Both items resolved.

Item 1 (ExcludeFromProgress fails open): closed via a new validator rule,
`validateTerminalProgressExclusion`, wired into `validateRouteBased`
(internal/config/workflow/validator.go) right after the existing
`validatePrimaryDesignations` check. Verified the gap is closed with
`TestValidateWorkflow_AbandonmentTerminalMissingExcludeFromProgress`
(internal/config/workflow/validator_primary_test.go): a designation fixture
with a non-canonical terminal missing `exclude_from_progress` fails
validation naming the offending status and the missing flag; restoring the
flag validates clean again. Confirmed the guard bites: temporarily commented
out the `validateTerminalProgressExclusion` call, re-ran the test, watched it
fail red (`An error is expected but got nil`), then restored the call and
re-ran the full `internal/config/workflow` suite green.

Fixing the rule surfaced one real pre-existing gap in the shipped bundle:
`internal/sharkdata/default_data/workflow/question.yaml` had three terminal
statuses (withdrawn, superseded, archived) alongside its primary success
terminal (resolved), none marked `exclude_from_progress`. Added the flag to
all three — this workflow is exercised by `shark admin workflow validate`
(`TestWorkflowValidateDefaultWorkflow` et al. in internal/cli/commands) even
though it sits outside the narrower `ValidateWorkflowFiles` entity map, and
the new rule caught the gap immediately. Also added
`ExcludeFromProgress: true` to the "aaa_wrong_archived" non-canonical
terminal in `designationFixture()` (validator_primary_test.go) so the
existing fixture keeps validating clean under the tightened rule.

Item 2 (duplicated DependsOn guard): factored into `parseAssignmentDependsOn`;
confirmed `internal/services` sprint-readiness tests (including the
malformed-JSON split cases) pass unchanged.

Full quality gate (`make fmt && make lint && make test`) passes.
