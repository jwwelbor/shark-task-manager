# ExcludeFromProgress fails open for custom workflows; duplicated DependsOn guard in sprint_service.go

## Description

From B058 code review, second pass (docs/review/bugs/b058/code-review-20260828-0111-B058.md), non-blocking findings on the sprint-readiness dependency fix (commits 2d58ed5a, 94a02d49):

1. ExcludeFromProgress fails open: the workflow-config validator never requires this field on terminal statuses, so a CUSTOM workflow declaring a terminal abandonment status without setting exclude_from_progress: true would silently be credited as satisfied by B058's fix -- reproducing the exact cancelled-dependency bug the fix closed, for a misconfigured custom workflow. This is a pre-existing contract gap shared by four other production consumers of ExcludeFromProgress (internal/progress/calculator.go:55, internal/services/feature_progress_service.go:318, internal/services/aggregate_policy.go:23, internal/services/epic_analytics_service.go:92) -- all four would already mis-report progress under the same misconfiguration, so this is a workflow-package design gap, not specific to sprint readiness. Recommended remedy: an explicit "successful terminal" selector distinct from bare IsTerminalStatus, or a workflow-config validator rule requiring exclude_from_progress on every terminal status that isn't the canonical success one.

2. Minor (from first-pass review, still open): computeDependencySatisfactionFactor and computeExternalDependencyTerminalStatus each independently guard/parse the DependsOn JSON field -- roughly 12 lines of duplicated logic across the two passes. Acceptable as shipped; worth factoring into a shared helper on next touch.

From the PR #201 pre-merge deep-review (dispatched-six-angle, commit 176add87 -- fail-loud + chunked external-dependency lookups):

3. Non-blocker (Angle D, complexity): `computeExternalDependencyTerminalStatus` (internal/services/sprint_service.go:2800) measures cyclomatic complexity 20 via `gocyclo -over 10`, over the project's threshold. It mixes three concerns: collecting distinct external dependency keys from `depends_on` JSON, chunked batch-fetching via `GetByKeys`, and filtering fetched tasks down to terminal-and-successful statuses. Recommended split: `collectExternalDepKeys(assignments, assignedKeys) []string`, `fetchTasksInBatches(ctx, taskRepo, keys) (map[string]*models.Task, error)`, `filterTerminalSuccessful(tasks, wf) map[string]bool`. Not blocking since the function is well-commented and covered by `TestSprintService_GetSprintReadiness_Factor2_ManyExternalDependencies_ChunkedLookup`.

4. Nit (Angle D, DRY): the new `GetByKeys` chunking loop (internal/services/sprint_service.go, `externalDepBatchSize` batches) is hand-rolled at the call site because `internal/repository/task/repository.go:1864` `GetByKeys` itself builds an unbounded `key IN (?,?,...)` clause with no internal limit, and no shared chunking helper exists anywhere in `internal/`. Consider pushing the batching down into `TaskRepository.GetByKeys` (or a shared repository-layer chunking helper) so every other unbounded-`IN` caller in the codebase benefits, rather than each caller reimplementing the loop.

5. Nit (Angle E, tests): `TestSprintService_GetSprintReadiness_Factor2_ManyExternalDependencies_ChunkedLookup` proves the multi-batch merge works (`externalDepBatchSize + 50` keys) but doesn't pin the chunk loop's exact boundary arithmetic (e.g. exactly `externalDepBatchSize` keys with no remainder, or `externalDepBatchSize + 1`). Optional: add those two boundary cases on next touch.
