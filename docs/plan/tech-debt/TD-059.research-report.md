# TD-059 research report

## Scope

TD-059 hardens the Question repository-adapter test for the emulated
`UpdateContextData` path. Questions store `context_data`, but their typed
repository does not expose dedicated context-data methods. The generic adapter
therefore loads the Question, calls `SetContextData`, and must persist the
mutated entity through `QuestionAdapterRepository.Update`.

The current fake returns the same `*models.Question` from every read and its
`Update` method is a successful no-op. Because `SetContextData` changes that
shared pointer before the no-op, the final read passes even if the adapter's
`repo.Update` call is removed. This work changes only test infrastructure and
its assertion; it does not change production adapter behavior or the
Question-repository interface.

## Findings

1. **The production write is correctly present.** For a repository without
   `entityContextDataRepo`, `entityAdapter.UpdateContextData` loads by ID,
   updates the model's context pointer, and calls `repo.Update`. The Question
   adapter deliberately chooses that emulation because the real typed
   repository has no dedicated context-data API.

2. **The current test cannot detect the write being removed.**
   `fakeQuestionAdapterRepository.GetByID` returns `r.question`,
   `BaseEntity.SetContextData` mutates that pointer, and `Update` returns nil
   without recording anything. Thus the post-call `GetContextData` assertion
   observes in-memory mutation, not a repository persistence interaction.

3. **A direct interaction assertion is the smallest correct oracle.** The
   existing epic, feature, task, bug, and change-card adapter tests capture the
   context value passed to their update seam. The Question fake should capture
   the entity passed to `Update`, including a copied context-data string, and
   count calls. This directly fails if the `repo.Update` line disappears.

4. **Do not add a database test or change the production interface.** The
   test targets generic adapter orchestration; a mock repository is the
   required service-test seam. Adding dedicated Question repository methods or
   changing `EntityRepository` would broaden a one-test hardening into an
   unrelated design change.

5. **No related-document registration is available for tech-debt entities.**
   The current `related-docs` transport has no tech-debt parent flag. The
   adjacent report is the supported durable record.

## Decisions

1. **Extend only `fakeQuestionAdapterRepository`.** Add `updateCalls int` and
   a captured update record. In `Update`, increment the count, verify or
   retain the received Question ID, and copy `question.GetContextData()` into
   a separate string value before returning nil. Copying avoids another shared
   pointer from weakening the assertion.

2. **Assert the interaction in
   `TestQuestionRepositoryAdapterProvidesTypedContextSeam`.** After
   `UpdateContextData`, require exactly one update, Question ID `1`, and
   captured context data equal to
   `{"progress":{"current_step":"collect"}}`. Retain the existing
   `GetContextData` assertion as read-seam coverage, but do not treat it as
   persistence proof.

3. **Do not add a hook unless the fake needs error-path coverage later.** A
   captured call count and copied value are enough for the present positive
   regression. Add an `updateFunc` only when a caller needs to inject an update
   error; otherwise it is unused test abstraction.

4. **Verify with the focused adapter test.** Run
   `go test ./internal/services -run
   '^TestQuestionRepositoryAdapterProvidesTypedContextSeam$' -count=1` and
   `git diff --check`. The counterfactual is clear: deleting
   `a.repo.Update(ctx, entity)` in `entityAdapter.UpdateContextData` must make
   the new call-count assertion fail.

**Recommended outcome: implement.** Add the small fake capture and exact
single-write assertion. The existing test covers only in-memory mutation; the
hardened test will cover the persistence call it was intended to protect.
