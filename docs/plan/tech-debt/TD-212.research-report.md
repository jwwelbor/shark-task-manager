# TD-212 research report

## Scope

Determine whether a presence check before `UpdateCandidate` safely repairs a
crashed `Backfill` retry, and identify every partial-write window that the
recovery contract must cover.

## Findings

`Backfill` validates its full input before writing, then creates or reuses a
run record, records each immutable event, folds each event into the candidate,
and finally writes the epic registration note. The registration note rejects a
later full backfill after it exists, but it does not make a pre-registration
partial execution recoverable.

The steady-state `foldIntegrationEventIfMissing` helper avoids refolding an
event already present in a candidate. Mirroring that helper in `Backfill`
would address only the narrow case where the candidate is already valid and
contains the event. It does not decide safely what to do after any of these
crash windows:

1. A run record exists but no event was published.
2. One or more event files exist but their candidate fold did not publish.
3. A candidate published only a prefix of the requested events.
4. Every event and candidate fold published but registration-note insertion
   did not complete.
5. A candidate claim/archive/publish attempt failed part way through and left
   recovery-relevant retained state.

The candidate CAS already rolls back an unpublished claim after archive or
rename failure. That prevents one permanent conflict class, but it does not
define ownership, input equivalence, or resume behavior for `Backfill` as a
whole.

## Decisions

Do not ship the originally proposed one-line presence check as TD-212's
resolution. It cannot distinguish a safe already-folded event from a partial
backfill whose candidate, event set, and registration ownership have diverged.

Implement a dedicated fail-closed recovery protocol. It must define:

- the persisted identity of an authorized recovery input and who owns it;
- reconciliation rules for every event, candidate, and registration state;
- rejection behavior for mismatched retry input or corrupt partial state;
- the durability ordering required before the registration note is visible;
- restart tests for every partial-write window, including a complete event set
  with a missing registration note.

### Recovery protocol

Persist an immutable backfill manifest before the first mutable write.  It
must bind the epic key, run ID, base commit, and canonical digest of every
input event (including path lists).  A retry may proceed only when that
manifest is byte-for-byte equivalent to its validated input; retained files
without a matching manifest are a conflict, not evidence that it is safe to
guess an owner.

After manifest publication, reconciliation is deterministic and fail-closed:

1. Reuse only an exactly matching run record; reject a different run identity
   or base.
2. For every manifest event, read any existing immutable event and compare all
   durable fields to the manifest.  Reject a mismatch; publish a missing event
   through `RecordEvent`.
3. Read the candidate.  It may contain only manifest event IDs, have the same
   run/base identity, and have a valid digest.  Fold each manifest event not
   present through `UpdateCandidate`; reject an extra or corrupt candidate.
4. Require the resulting candidate to contain exactly the manifest event set,
   then call the existing idempotent `RegisterRun` path.  A retry after a
   published candidate but before note insertion therefore repairs only the
   missing registration.

The manifest remains durable after success as the provenance record for the
registered backfill.  Do not delete it during recovery: deletion would reopen
the ambiguity this protocol is intended to remove.

Required restart tests: crash after manifest, run, each event, each candidate
fold, and before/after registration persistence; mismatched retry input;
corrupt or extra event/candidate state; and a legacy partial state without a
manifest.  Every ambiguous legacy state must fail without mutation.
