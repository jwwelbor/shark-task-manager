# TD-025 research report

## Scope

Bound viewer hierarchy task hydration to a small, fixed number of simultaneous
feature-task requests while preserving the best-effort compatibility behavior.

## Capability map

| Bulk or lazy endpoint design | DEFER; outside this focused performance repair. |

## Findings

`hydrateHierarchyTasks` launches one request per feature and awaits every one
with `Promise.all`, so a large hierarchy can start dozens of HTTP and database
operations at once. The helper is deliberately best-effort and initializes
every `feature.tasks` before fetching; the cap must preserve both properties.

## Decisions

Use a six-worker pool. It limits in-flight requests without changing the API,
keeps a successful response on its original feature, and leaves failed or
keyless features with the existing empty array. Add an embedded-viewer contract
test that pins the cap and worker-based scheduling.
