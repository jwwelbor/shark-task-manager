# Epic/task custom-key duplicate-check swallows non-not-found repository errors

## Description

B063's deep-review (all 6 angles) and code-review round 2 (NB-B) both flagged: EpicService.CreateEpic (epic_service.go:519) and taskcreation.Creator.CreateTask (creator.go:157) only branch on `err == nil && existing != nil` when probing whether a custom key already exists. A genuine repository error (not just 'not found') falls through silently and the code proceeds as if the key were free. FeatureService.CreateFeature was fixed in this same diff (feature_service.go, checks !errors.Is(err, sql.ErrNoRows) and propagates other errors) but the identical fix was not backported to epic and task. Low risk for task (tasks.key has a DB UNIQUE constraint as a safety net) but still masks transient DB errors as silent success. Fix: mirror feature_service.go's pattern in both epic_service.go:519 and taskcreation/creator.go:157.

## Impact

A transient DB error during a custom-key duplicate check is silently treated as "key is free," letting the create proceed on unverified data instead of surfacing the failure.

## Resolution Plan

Apply the same `!errors.Is(err, sql.ErrNoRows)` propagation FeatureService.CreateFeature already uses to EpicService.CreateEpic and taskcreation.Creator.CreateTask.
