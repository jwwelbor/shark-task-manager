# TD-234 Research Report

## Scope

Resolve TD-234: `loadClosableQuestion()`'s owner-mismatch error
(`internal/services/question_workflow_service.go:340`) hardcoded
`--resolution-owner=%q` CLI flag syntax into a message shared by both the CLI
(`internal/cli/commands/question.go`) and the HTTP API's
resolve/withdraw/supersede handlers (`internal/api/question_handler.go`),
which return `err.Error()` verbatim in JSON error bodies. Scope is limited to
this one error path plus a sweep of the same file for sibling flag-syntax
leaks; no other Question error surfaces were in scope.

## Findings

- `loadClosableQuestion` (question_workflow_service.go:339-341) builds the
  owner-mismatch error with `fmt.Errorf("...; retry with --resolution-owner=%q", ...)`,
  wrapped once by `questionConflictError` into a `*services.QuestionRuleError{Class: QuestionRuleConflict}`.
- `internal/api/common.go`'s `handleServiceError`/`questionErrorStatus`
  classify `*services.QuestionRuleError` by `Class` (409 for Conflict, 400
  for Validation) and then call `respondError(w, status, err.Error())` —
  the CLI-flag text passed straight into the JSON `message` field verbatim.
- `internal/cli/commands/question.go`'s `runQuestionResolve/Withdraw/Supersede`
  previously just `return err` from the service call, relying entirely on
  the service's message text for the CLI hint — there was no CLI-side
  formatting layer to separate from.
- `.claude/rules/go/error-handling.md` documents this codebase's existing
  pattern for caller-correctable errors: typed errors (`NotFoundError`,
  `InvalidStateError`) checked with `errors.As` at each transport, with the
  transport translating the typed error into its own status code / message
  shape rather than trusting a shared string. `QuestionFullReadDeniedError`
  in `internal/services/question_service.go:57-63` is a live example of this
  exact shape already used elsewhere in the Question service (a typed,
  no-payload-leak error consumed via `errors.As` in `handleServiceError`).
- Grepping `question_workflow_service.go` and `question_service.go` for `--`
  found exactly one hardcoded flag-syntax occurrence (the one above); no
  sibling leaks of this specific pattern exist in these files. TD-158 (CLI
  flag-surface naming inconsistency) is a related but distinct, already-
  tracked concern and was left untouched.

## Decisions

- **Chosen: Option 1 (typed error, per-transport rendering).** Added
  `QuestionOwnerMismatchError{ConfiguredOwner string}` to
  `internal/services/question_service.go`, matching the existing
  `QuestionFullReadDeniedError` typed-error convention in the same file.
  Its `Error()` is transport-neutral: `resolution owner does not match
  configured owner "<owner>"` — no CLI flags, no JSON field name, but the
  owner value stays present so any caller can self-correct. It is wrapped
  by the existing `questionConflictError` so the `QuestionRuleError{Class:
  QuestionRuleConflict}` 409 classification in `internal/api/common.go` is
  unchanged and required no handler edits.
  - Rejected Option 2 (fully neutral message, no typed error): would have
    satisfied the API requirement but loses the CLI's actionable
    `--resolution-owner=` hint entirely, since nothing would let the CLI
    reconstruct flag syntax from a plain string without re-parsing prose.
  - Rejected Option 3 (neutral service message + CLI string-wraps): works,
    but has the CLI pattern-matching on error text rather than a typed
    value, which is exactly what `.claude/rules/go/error-handling.md` and
    the existing `QuestionFullReadDeniedError` precedent in this file argue
    against. Option 1 costs one small struct + one `errors.As` call in the
    CLI, which is proportionate given the precedent already exists in the
    same file.
- Added `internal/cli/commands/question.go`'s `withQuestionOwnerMismatchHint`
  helper, which `errors.As`-unwraps `*services.QuestionOwnerMismatchError`
  and appends `; retry with --resolution-owner=%q` for CLI display only. It
  wraps the return of `Resolve`, `Withdraw`, and `Supersede` — the three
  commands that call `loadClosableQuestion` indirectly.
- Updated (not weakened) the three tests that pinned the old wording:
  `question_service_test.go:737,949` now assert the mismatch is still
  detected (`QuestionRuleConflict`, write never reached) and that the
  configured owner is still named, while asserting the CLI flag string is
  *absent* from the service-level message. `question_handler_test.go:425`
  was rebuilt to construct the error via the real
  `*services.QuestionOwnerMismatchError` type and assert the JSON body
  both omits `--resolution-owner` and still names the configured owner.
  Added `TestQuestionResolveOwnerMismatchAddsCLIFlagHint` in
  `question_test.go` to cover the CLI-side hint for all three verbs.
- Verified the API test actually bites: temporarily reintroduced
  `--resolution-owner=%q` into `QuestionOwnerMismatchError.Error()`, reran
  `TestQuestionHandlerResolveOwnerMismatchReturnsConflict`, confirmed it
  failed with the leaked syntax visible in the body, then restored the fix
  and confirmed the suite passed again.
