# E40-F10: quarantine_pair()'s dedup loop uses -e (not -L), so a dangling symlink at a candidate slot hard-fails instead of being skipped

## Description

bench/scripts/run-lifecycle-batch.sh's quarantine_pair() dedup loop (while [[ -e "$incomplete_root/rep-$rep-$seq" ]]; do seq=$((seq+1)); done) uses -e, which returns false for a dangling (broken-target) symlink even though -L would report one. A pre-existing dangling symlink at a would-be dedup slot is therefore treated as 'free' by the loop, and the subsequent mv "$dir" "$dest" (no -T) is attempted against that dangling symlink. Empirically verified (E40-F10 round-5 code review): GNU mv of a real directory onto a pre-existing symlink (dangling or live) fails loudly (mv: cannot overwrite non-directory ... with directory, nonzero exit) rather than writing through -- quarantine_pair() correctly returns failure, the pair is recorded failed, and the batch proceeds (REQ-NF-007-safe, no silent data misplacement). This is a robustness/availability gap (requires manual cleanup of the stray dangling symlink before that exact dedup slot becomes usable again), not a security or data-integrity defect. Recommend the dedup loop test '[[ -e ... || -L ... ]]' so it skips past a dangling symlink slot instead of colliding with it. Found during E40-F10 round-5 code review (tech-lead), consistent with codex's independent same-function analysis (fails closed under the established non-concurrent threat model).
