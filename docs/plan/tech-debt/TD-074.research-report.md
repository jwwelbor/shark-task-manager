# Research report: admit.sh evaluate() exceeds 50-line function guideline

## Scope

TD-074 covers the `evaluate()` function in `bench/scripts/admit.sh` (lines 516–651, 136 lines total), which manages the five-check admission gate for a single corpus item. The function is 2.7× the project's 50-line guideline and performs multiple sequential concerns: setup and preparation, checkout and file staging, running the five checks in order (F2P-red-at-base, P2P-green-at-base, patch-apply, F2P-green-post-patch, P2P-green-post-patch), cleanup, and verdict assembly.

The affected capability is the admission gate's core evaluation logic for a single candidate item. The function correctly handles all evidence-forgeability properties, test-isolation boundaries, and the cascading check-failure early-exit pattern. The debt is readability and maintainability only—no correctness or functional defect exists.

This report does not propose changing the five checks themselves, the early-exit on-first-failure flow, the temp-directory cleanup semantics, or the verdict JSON shape. It addresses whether helper functions can extract distinct concerns while preserving the current control flow and error semantics.

## Findings

1. **The function executes a well-defined, linear five-check gate with early exit on failure.**
   Lines 552–636 form a single try-finally block that initializes a `checks` dict, runs five sequential assertions (each a separate if-block that short-circuits to set `failing_check` on failure), and then cleans up temp directories. The control flow is clear: proceed to the next check only if the prior one passed. No nested branches or complex logic exist within the checks themselves—each delegates to a helper (`run_go_tests()` or `check_p2p_green()`). The function's length is almost entirely due to the repetition of the five check blocks and their setup/cleanup, not tangled control flow.

2. **Setup and teardown are separable from check execution.**
   Lines 524–550 parse the item, resolve the p2p_set, compute derived values (`f2p_packages`, `exclude_from_p2p`), and initialize the checks dict. Lines 562–638 manage the temp directory lifecycle (mkdtemp, try block, finally rmtree). These bookkeeping steps could be extracted as a wrapper function that accepts a callback to run the checks in isolation, following the pattern of `check_p2p_green()` itself (which iterates packages in a stateless way).

3. **Each of the five checks has a similar shape but is embedded inline.**
   Each check: (a) calls a subprocess-orchestration helper (`run_go_tests()` or `check_p2p_green()`); (b) extracts a boolean from the result; (c) records it in the `checks` dict; (d) conditionally sets `failing_check` and breaks the cascade if the check failed. This shape repeats five times but cannot be fully unified into a loop because the subprocess calls differ (different packages, different run selectors, different expected/observed test names). A helper that accepts a check name, a callback, and a failure code would reduce the boilerplate.

4. **The verdict assembly at the end is orthogonal to check orchestration.**
   Lines 640–651 determine status based on whether `failing_check` was set, decide on `repro_confirmed` based on item type, and build the return dict. This is a data-transformation step that could be extracted or remain inline without affecting readability—the current placement is acceptable.

5. **Refactoring constraints are well-established by the evidence-forgeability property.**
   The function's header and `check_p2p_green()` document the trust model: every check is a fresh subprocess against a fresh checkout, and the checks must be isolated so that one can never alter the substrate for another. The temp-directory lifecycle (one mkdtemp, all checks run in its subdir, finally rmtree) is fundamental to that isolation. Any refactoring must preserve:
   - One temp directory for the entire evaluate() call
   - Fresh subprocess calls per check
   - Early exit on first failure
   - The existing checks dict structure and semantics

6. **Comparable extracted patterns exist in the same file.**
   `check_p2p_green()` (lines 398–490, 93 lines) manages per-package iteration and three nested conditions per package (expected vs. observed test names, failure scanning, exit code corroboration). It is longer than 50 lines but is justified by its single, well-defined loop over a set of packages. `run_go_tests()` (lines 320–360, 41 lines) and `enumerate_tests()` (lines 384–395, 12 lines) are extracted subprocess helpers that `evaluate()` calls. These are models for how to break down `evaluate()`'s own concerns.

7. **Existing tests exercise evaluate() through both the --item and full-corpus paths.**
   TC-004 (`tc004_admit_full_set_test.sh`) runs `admit.sh <corpus_yaml>` with no `--item` flag, admitting the full corpus in one pass and directly exercising `evaluate()` for every item. TC-005 (rejection branches) uses `--item <id>` with reference-patch overrides to test failure modes. TC-006 (reproducibility) runs the full corpus twice against fresh checkouts and compares byte-identical output, exercising `evaluate()` via the `main()` loop. All tests pass green currently. Refactoring must maintain green tests with no behavioral changes to the five checks or the verdict shape.

8. **The code-review non-blocker acknowledged this is a readability/maintainability debt, not a functional risk.**
   Code review round 2 finding 3 states: "Non-blocking then and now — every branch is fully exercised by TC-004/TC-005/TC-006 (all still green), so this remains a readability/maintainability tech-debt item, not a correctness risk." No urgency exists to block admission-gate work on this refactoring.

## Decisions

1. **Extract a `_run_check()` helper to reduce boilerplate of the five check blocks.**
   The helper accepts:
   - `check_name`: the key in the `checks` dict (e.g., `"f2p_red_at_base"`)
   - `callback`: a function that runs the check and returns `(bool_result: str | error_desc: str)`
   - `failure_code`: the constant to set in `failing_check` if the check fails (e.g., `FAIL_F2P_GREEN_AT_BASE`)
   
   The helper handles: recording the result in `checks[check_name]`, setting `failing_check` if needed, and returning early. This reduces each check block from ~6 lines to ~2 lines, cutting 20+ lines from the function.

2. **Keep the five checks inline with their subprocess orchestration.**
   `run_go_tests()` is already extracted and handles the -run/-skip patterns for F2P and P2P scoping. The `check_p2p_green()` helper is already extracted for its three-condition validation logic. The two check blocks that call these helpers (F2P-red-at-base and P2P-green-at-base, and again post-patch) should call them directly—no additional wrapper needed. Extracting the subprocess calls themselves would not reduce line count meaningfully and would obscure the data flow.

3. **Extract a `_prepare_checkout()` helper for lines 562–577.**
   This helper accepts the item and returns the checkout_dir path (or raises on failure). It encapsulates:
   - mkdtemp
   - subprocess.run for checkout-fixture.sh
   - copy_f2p_files
   
   The function would return the checkout_dir path; the caller remains responsible for the try-finally cleanup. This improves readability by moving provisioning details out of the main flow.

4. **Preserve the temp-directory try-finally at the evaluate() level.**
   The current structure (try block with all five checks, finally rmtree) is correct and clear. Moving it into a helper would require either passing a callback (verbose) or using a context manager (requires refactoring Python control flow). The try-finally is already clean and should remain.

5. **Verdict assembly can remain inline, as it is currently clear and depends only on the `checks` dict and `failing_check` variable.**
   Lines 640–651 are self-documenting and do not justify extraction.

6. **Target refactoring goals:**
   - Reduce lines from 136 to ~100–110 (modest goal: ~20% reduction, focused on boilerplate)
   - Keep the five checks' order and early-exit control flow clearly visible
   - Preserve all existing test coverage (TC-004, TC-005, TC-006)
   - No changes to the checks themselves, the subprocess boundaries, or the verdict shape

## Remediation & Affected Capability

**Existing remediation**: None. The code is currently production-quality and green in all tests.

**Affected capability**: The admission gate's evaluation of a single item. Refactoring has zero impact on the gate's correctness (no check logic changes), the candidate's admission verdict, or the reproducibility property (subprocess isolation and deterministic ordering are unchanged). The change is purely a readability enhancement.
