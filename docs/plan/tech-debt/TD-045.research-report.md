# Research report — plan.go duplicates three next.go resolvers and has already drifted

## Scope

This report covers the shared workflow-step resolution performed by
`shark next <key>` and keyed `shark plan <key>`, with specific attention to
`resolveNext`/`resolvePlanEntity`,
`autoAdvanceCascadeParent`/`autoAdvancePlanCascadeParent`, and
`applyWireAction`/`applyPlanWireAction`. It traces the commands, adapter cache,
cascade-policy seams, tests, and prior remediation that define the safe
refactoring boundary.

The affected capability is per-entity dispatch resolution: read current
workflow state, detect terminal and archived states, render placeholders and
the configured action, degrade an unknown legacy status to a diagnostic pause,
normalize the internal action to the wire contract, perform safe same-entity
auto-advances, and assemble the final agent prompt. This capability is intended
to be identical for `next` and `plan`; only their handling of a `cascade`
action differs.

The proposed remediation extends the helper extraction completed for TD-017
and reuses the adapter cache completed for TD-020. It replaces the duplicated
plan-specific resolver and recursion helpers with one shared resolver plus an
explicit cascade strategy. It does not replace either command, the
`NextResponse`/hierarchy-selection wire shapes, the sequential or fan-out
child-selection engines, or plan's one-level selection policy.

Shared vocabulary:

- **Shared resolution pipeline**: all status, action, diagnostic, wire
  normalization, same-entity recursion, and prompt-assembly behavior before
  and after the command-specific cascade branch.
- **Cascade strategy**: the command-specific handler for a populated action
  whose internal verb is `cascade`.
- **Same-entity recursion**: resolution after an automatic status transition;
  it must retain the initiating command's cascade strategy.
- **Next strategy**: `tryCascadeFanout` by default or `tryCascade` in
  sequential mode.
- **Plan strategy**: `tryPlanHierarchy`, which returns direct-child selection
  and never drills into a selected child.
- **Leaf parity**: a leaf or parent-owned agent step resolved through
  `shark plan` returns the same dispatch response as `shark next` for that
  entity.

## Findings

1. **PR #139 created a second copy of a pipeline that TD-017 had already
   decomposed.** Commit `215ed526` extracted `tryCascade`,
   `applyWireAction`, and prompt attachment from `resolveNext`. Commit
   `2a5719e0` then added `resolvePlanEntity`,
   `autoAdvancePlanCascadeParent`, and `applyPlanWireAction` by copying the
   corresponding next path so plan could substitute one-level hierarchy
   selection. The new plan path does reuse `actionRequiresInstruction`,
   `normalizeWireAction`, `assembleDispatchPrompt`, and the embedded
   `nextAdapterCache`, but it duplicates the orchestration surrounding those
   helpers.

2. **The duplicated resolver has already changed observable behavior.**
   `resolveNext` handles `action.StatusNotFoundError` by returning
   `action="pause"` with `resp.Error` and emitting the B022 warning to stderr.
   `resolvePlanEntity` returns the same pause and error text but emits no
   warning. `git blame` attributes the next warning to commit `0db8a4a4` and
   the copied plan branch to `2a5719e0`, so this is copied-code drift at the
   introduction point rather than a theoretical maintenance risk.

3. **The intended semantic difference is confined to the cascade strategy.**
   Both resolvers use the same adapter triple, status reader, terminal/archive
   rules, placeholder generation, action service, instruction guard, wire
   normalization, response fields, and prompt assembly. At `cascade`,
   `resolveNext` chooses `tryCascadeFanout` or `tryCascade` from
   `cache.fanout`; `resolvePlanEntity` chooses `tryPlanHierarchy`. The plan
   cache embeds `*nextAdapterCache` and adds only `maxParallelItems`, so it does
   not require a second copy of the common resolver.

4. **Both copied helpers differ only because recursion must preserve that
   strategy.** The two auto-advance helpers have the same guard, transition
   target, reason, agent, error behavior, and status mutation; only the final
   resolver call differs. The two wire-action helpers likewise differ only in
   the resolver called after an agentless `advance_status`. A shared helper
   must therefore carry the selected strategy through same-entity recursion.
   Calling `resolveNext` unconditionally would silently turn a plan
   auto-advance that lands on `cascade` into descendant dispatch or a keyed
   fork instead of plan's one-level selection.

5. **The affected callers are bounded, but they include mutation and host wire
   contracts.** `runNext` calls `resolveNext`; keyed `runPlan` calls
   `resolvePlanDispatch`; and standalone plan resolution uses `resolveNext` to
   assemble concrete leaf dispatch candidates. Rider's run loop consumes
   keyed-next responses as the canonical worker payload, while Rider plan
   treats hierarchy selections as promptless advice. The refactor must preserve
   both envelope families and the existing automatic status transitions.

6. **Current tests prove selected outcomes, not one shared contract.**
   `TestResolvePlanEntityLeafMatchesKeyedNextRenderedResponse` compares the
   main dispatch fields for one `spawn_agent` leaf, and
   `TestTryPlanHierarchyAutoAdvancesCascadeCompleteParentWithNoNewSideEffects`
   covers plan's all-children-terminal transition. The next suites cover depth,
   cascade traversal, fan-out, and simple wire mapping. No plan test captures
   the B022 stderr warning, and TD-048 finding N10 records that the plan
   `advance_and_recurse` branch is untested; changing its recursive target back
   to `resolveNext` leaves the current suite green.

7. **A shared resolver with an explicit strategy is the smallest remediation.**
   Keep thin `resolveNext` and `resolvePlanDispatch` entry points for callers
   and focused tests, but route both into one unexported resolution function
   that accepts the embedded `*nextAdapterCache` and a small strategy value.
   The strategy supplies the cascade handler, command name for diagnostics,
   and plan's candidate bound where needed. The common function, generic
   auto-advance helper, and generic wire-action helper recurse back into that
   same function with the same strategy. This deletes the drift surface without
   merging the intentionally different child-selection engines tracked
   separately by TD-046.

## Decisions

1. Introduce one private resolution core parameterized by an explicit
   command-resolution strategy. Keep `resolveNext` and
   `resolvePlanDispatch` as thin entry points so production callers and
   strategy-specific tests remain readable.
2. Keep the strategy narrow. It selects the cascade handler, carries plan's
   parallel bound where required, and supplies the diagnostic command label.
   Status reads, terminal checks, placeholder rendering, populated-action
   lookup, instruction validation, wire mapping, same-entity transitions, and
   prompt assembly remain in the shared core.
3. Make auto-advance and `advance_and_recurse` call the shared core with the
   same strategy. Do not use `resolveNext` as the common recursion target,
   because that violates plan's one-level selection contract after a status
   transition.
4. Remove the three plan-specific copies once the shared path is wired:
   `resolvePlanEntity`, `autoAdvancePlanCascadeParent`, and
   `applyPlanWireAction`. Retain `tryPlanHierarchy`,
   `tryCascade`, and `tryCascadeFanout`; unifying their child-enumeration
   semantics belongs to TD-046, not TD-045.
5. Surface B022 consistently from both commands. Assert that each command
   returns the same pause/error contract and emits a warning bearing the
   initiating command's label (`[shark next]` or `[shark plan]`).
6. Replace the narrow leaf comparison with table-driven shared-contract tests
   over both entry points for terminal/archive, missing action, legacy unknown
   status, simple spawn fields including `effort`, unknown internal action,
   empty required instruction, and same-entity auto-advance. Keep the existing
   next cascade/fan-out and plan hierarchy suites as strategy tests.
7. Add TD-048 N10's counterfactual during this remediation: an agentless
   `advance_status` transitions a plan root into a cascade with two tied
   children and must return one-level `hierarchy_selection`, while a missing
   safe target must pause without a transition.
8. Preserve all existing JSON envelopes, `resolved_via` behavior, transition
   reasons/agents, cache lifetime, and command ownership. After implementation,
   run the mandatory `make fmt`, `make lint`, and `make test` gate.
