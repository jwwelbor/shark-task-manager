# TD-227 research report — dead prelude lineage helper

## Scope

TD-227 is confined to feature-scenario replay lineage in
`bench/scripts/run-lifecycle.sh`. The affected capability is the E40-F08
lifecycle runner's I-05 stage-evidence output: for a feature scenario with an
I-06 prelude, each stage snapshot must carry the consumed I-06 entry digests as
`replay_lineage[]` records of `{replay_reference, entry_digest}`. It does not
change replay matching, I-06 bundle/result schemas, or non-feature scenarios.

The current implementation contains a deterministic `prelude_lineage(record)`
helper, but no caller. `I05BundleWriter.record_stage()` instead emits an empty
`replay_lineage` placeholder for every feature scenario. This is a
documentation-and-runtime contradiction: the adjacent comment says F07 owns
the field interior, while the completed F07 contract assigns E40-F08 the
consumer write.

## Findings

1. **The helper is dead and the placeholder is live.** `prelude_lineage()`
   reads the lifecycle record's `prelude.replay` result, collects every
   `consumed_entries[].entry_digest`, pairs each with the replay bundle path,
   and sorts the result. Repository search finds no call site. Conversely,
   `record_stage()` writes `snapshot["replay_lineage"] = []` for every feature
scenario, so a real I-06 prelude cannot reach an I-05 snapshot.

## Resolution

The initial TD-227 wiring used `prelude_lineage(self.record)`. That record is
a diagnostic representation whose `prelude.replay` value passes through
`bounded()`. The helper therefore omitted consumed entries after index 31.

The runner projects `replay_lineage` from the parsed, scenario-bound prelude
before it writes the bounded diagnostic record. The projection reads only
`stages[].consumed_entries`, the resolver-owned ledger named by I-06
REQ-F-009. It preserves the replay bundle reference and sorts the typed
`{replay_reference, entry_digest}` records deterministically.

`I05BundleWriter` retains only that projection and emits it for feature stage
snapshots. It does not retain the unbounded prelude or provider payload.
Artifact-scoped `consumed_entries` claims remain optional and
non-authoritative, so they cannot create I-05 replay lineage.

`tc065_prelude_question_isolation_test.sh` runs the production lifecycle
entrypoint with all 40 consumed entries in the stage-level ledger. It verifies
every digest reaches the snapshot while the persisted diagnostic replay copy
has exactly 32 entries. A second artifact-only counterfactual verifies that 40
artifact claims produce no I-05 replay lineage. Together, these cases prevent
later code from using a bounded diagnostic copy or an artifact claim as the
semantic source.

2. **The intended contract is already remediated upstream.** E40-F07 is the
   existing producer-side remediation: it defines `entry_digest` as the sole
   I-06/I-05 join key, specifies the exact `{replay_reference, entry_digest}`
   shape, and explicitly names E40-F08 as the sole consumer that writes it.
   The B064/PR #219 change introduced the helper and retained the placeholder,
   leaving that final consumer connection incomplete.

3. **The runner already has the correct integration pattern.**
   `finalize_stage_evidence()` derives I-07 `input_lineage` through the shared
   `stage_input_lineage()` call and then asks `I05BundleWriter.record_stage()`
   to materialize its I-05 counterpart. Replay lineage belongs in the latter
   snapshot writer; it is not an input-lineage source and should not be folded
   into `stage_input_lineage()`.

4. **Related capability is active and must be reused.** E40-F07's replay
   result, bundle-path provenance, and consumption ledger are authoritative.
   TD-227 should consume their recorded values only; it must not recompute
   digests or inspect replay bundles independently.

### Capability map

| Capability | Existing owner/evidence | Decision | TD-227 action |
|---|---|---|---|
| I-06 replay entry digest and consumption ledger | `bench/scripts/replay-answer.sh`; E40-F07 spec REQ-F-003/009 | REUSE | Read only `stages[].consumed_entries[].entry_digest`; do not recalculate it or trust artifact claims. |
| I-05 stage `replay_lineage[]` join | E40-F07 spec REQ-F-003; `I05BundleWriter.record_stage()` | CONTRADICTS | Replace the feature-only empty placeholder with the existing helper output. |
| I-07 input lineage | `stage_input_lineage()` and `finalize_stage_evidence()` | REUSE | Leave it separate; replay lineage is a distinct cross-contract join. |

## Decisions

1. **Use the unbounded prelude and the stage-level ledger at the source
   boundary.** Derive the typed projection immediately after the runner parses
   and validates the prelude, then pass it to `I05BundleWriter`. Do not derive
   semantic lineage from `self.record`, because that diagnostic record
   intentionally bounds nested collections. Do not read artifact claims;
   I-06 assigns authority only to `stages[].consumed_entries`.

2. **Keep `prelude_lineage()` as the single local projection.** Its input is
   the parsed prelude and its output is the exact F07-owned row shape. The
   writer retains this projection only, avoiding a second traversal, duplicate
   digest rule, or an unbounded diagnostic payload.

3. **Do not add lineage to `stage_input_lineage()`.** That function records
   typed external inputs (`prelude_result` is already one such source), whereas
   `replay_lineage` records consumption joins. Combining them would change two
   established schemas and blur their meanings.

4. **Add a focused regression case before implementation is accepted.** A
   feature prelude fixture with at least one consumed entry should assert that
   each emitted I-05 stage snapshot contains sorted,
   `{replay_reference, entry_digest}` lineage; a no-prelude/non-feature case
   should retain its current absence/empty behavior as the applicable contract
   requires. The existing F07 contract test remains the shape authority.
