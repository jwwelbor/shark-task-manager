# Four test gaps in the plan/next selection path let real regressions pass

## Description

Four coverage gaps found by /shark-rider deep-review high on PR #139 (findings N9, N10, N13, N14). Each was verified to admit a specific silent regression.

N9 — internal/repository/planhierarchy/repository_test.go:57,62: the epic tier inserts exactly one claim with a FRESH heartbeat, so claimNeverExpires, claimCutoff and the julianday comparison direction are all unverified; 'WHEN c.id IS NULL THEN 0 ELSE 1' would pass. The task tier inserts no claim at all, so readFeatureTasks' duplicated CASE block and its 7-parameter bind order are entirely untested — a wrong entity_type bind either hands a leased task to a second agent or hides an unclaimed one. Add: heartbeat now-30m with TTL 15m expecting Claimed==false; claimTTL 0 with an hours-old heartbeat expecting Claimed==true; a claim on one of three tasks asserting exactly that task reports claimed.

N10 — internal/cli/commands/plan_dispatch_test.go: applyPlanWireAction's advance_and_recurse branch, the sole documented reason the function was forked from applyWireAction, has no test. Swapping its recursion back to resolveNext breaks nothing. Add a case with PopulatedAction{Action:'advance_status'}, empty AgentType, and a forward transition into a cascade status with 2+ tied children, asserting a one-level selection rather than a grandchild dispatch. Cover transitionalTarget=='' -> pause too.

N13 — internal/services/standalone_planning_service_test.go: all three list stubs take the filters parameter unnamed and return a canned slice, so the non-terminal contract (which rests entirely on BugFilters{}.ShowAll defaulting false) is never observed; no fixture item carries a Status. Switching to ShowAll:true keeps every test green while 'shark plan bugs' starts offering closed bugs. filterClaimable cannot compensate — it checks dependencies and claims only.

N14 — internal/services/plan_hierarchy_service_test.go:91: DescribeChildren is never tested with an existing epic parent, so the epic->LevelFeature mapping is uncovered and swapping the two arms fails nothing. The integration fixture cannot catch it either, because planEdgeWorkflowConfig gives feature and task the same terminal status. Add an epic-parent case with feature-terminal != task-terminal.
