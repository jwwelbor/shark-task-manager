# TD-235 Research Report — evaluating triage dispositions and rerun deduplication

## Scope

Determine what the existing review and triage checks prove about five
model-selected dispositions (bug, fix-now task, duplicate link, tech debt, and
no-action nit), repeat finding deduplication by stable fingerprint, and the
finish-feature stop when unresolved findings remain. Identify whether the
current checks can verify those outcomes, what related harness capabilities
exist, and what remains owner-gated. This research does not change the prompts
or test infrastructure.

The shared terms are: a **disposition** is the triage action selected for a
review finding; a **fingerprint** is the stable
`<relative_file_path>#<rule>#<slug>` identifier used to find the same finding
across review runs; **rerun deduplication** means linking or updating the
existing work item instead of creating another one; a **prompt contract test**
checks the prompt text and output shape without executing a model.

## Findings

1. The existing regression checks cover prompt wording and declared fields.
   `TestEmbedded_ReviewFindingsRouteThroughTriage` and
   `TestConsolidatorRoutesNonBlockersThroughTriage` require the triage decision
   tree wording and reject direct severity-to-entity wording. The paired
   fingerprint tests require the `fingerprint` field and its placement in the
   output contract. They read files and inspect strings; they do not run a
   model against disposition scenarios or verify that a second triage run
   links an existing item.

2. B068 implemented the previously missing fingerprint contract: producers
   emit `<relative_file_path>#<rule>#<slug>`, and the triage skill searches that
   exact value before its broader duplicate search. Its report identifies the
   new tests as file-read assertions. That closes the missing-instruction gap;
   it does not establish that a model consistently chooses the right
   disposition or follows the duplicate link on a later run.

3. The current triage procedure supplies concrete behavior for a future
   evaluation: Step 0 handles trivial current-branch fixes, Step 3 searches for
   a matching fingerprint and existing work item, and Step 4 classifies the
   result. Those decisions depend on the model applying the procedure to
   context and tracker state. Static prompt tests cannot prove those decisions
   or their side effects.

4. The finish-feature gate is a separate deployment boundary. TD-232 records
   the wording update in the user-global `~/.claude/skills/finish-feature/SKILL.md`;
   that skill is outside this repository and its behavior cannot be covered by
   a test in this repository's Go suite. The E40 lifecycle runner is also not
   a current substitute: its README says the default provider is a headless
   call that does not load the Shark Rider skill or drive Rider verbs.

5. E40 does provide reusable evaluation infrastructure: versioned scenarios,
   isolated evaluator inputs, and a calibrated LLM judge for applicable
   planning artifacts. Its documented target is workflow execution and
   artifact evaluation, not the Rider skill's triage decisions. A provider
   adapter that loads the skill, fixed disposition fixtures, a controlled
   tracker state, and checks for created/linked entities would be additional
   capability. E40 is a plausible foundation to extend if an owner approves
   that scope; the current harness does not already satisfy TD-235.

6. The Workstream plan named in TD-235.md is not present in this checkout.
   The tracked TD-235 description and B068 record still provide the disposition
   cases and fingerprint acceptance statement needed for this research. The
   missing source limits verification of other plan details but does not change
   the gap visible in the tracked prompts and tests.

7. TD-235 cites `CLAUDE.md Rule 16` as the approval basis, but the checked-in
   `CLAUDE.md` contains Rules 1–5 and 7–13, with no Rule 16 or testing-platform
   approval clause. The need to decide whether to add an LLM evaluation
   capability is recorded in TD-235's Resolution Plan; its cited governance
   rule should be verified before treating that specific citation as current.

## Decisions

- Treat the existing prompt tests as necessary structural guards, not evidence
  that an LLM selects all five dispositions correctly or deduplicates a second
  run. Do not replace the prompt tests with model tests.
- If an owner approves the capability, extend the E40 scenario/evaluator
  patterns only after specifying the skill-loading adapter, pinned model and
  skill identity, fixture tracker state, expected outcome for each disposition,
  two-run fingerprint behavior, grading method, and bounded provider cost. Keep
  the user-global finish-feature case explicitly outside repository-only
  coverage unless its execution environment is brought into that test boundary.
- If the owner declines the harness, retain the current prompt-contract tests
  and record the semantic classification, finish-feature progression, and
  cross-run dedup outcomes as unverified rather than marking those acceptance
  cases covered.
- Research is complete. Implementation scope remains owner-gated as recorded in
  TD-235.md. The source citation to `CLAUDE.md Rule 16` needs correction or
  confirmation; this report does not infer a replacement policy.
