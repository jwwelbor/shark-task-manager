# Research report: `sequential_dispatch` swaps the whole child-enumeration engine

## Scope

TD-046 concerns keyed `shark next <epic|feature>` while its current workflow
action is `cascade`. The command currently selects one of two end-to-end
cascade implementations:

- **Sequential mode** means `--sequential` or `sequential_dispatch: true`.
  `tryCascade` enumerates through `CascadeService`, checks claims per child in
  the CLI, and linearly returns the first descendant dispatch.
- **Fan-out mode** is the default. `tryCascadeFanout` enumerates through
  `PlanHierarchyService`, selects an equally ranked tier, and returns a fork
  when multiple members of that tier remain dispatchable.
- **Enumeration policy** is the ordered child snapshot plus terminal, claim,
  and hard-dependency eligibility.
- **Emission policy** decides whether a surviving tie is represented as a
  `hierarchy_selection` / `parallel_candidates` fork or collapsed to its first
  candidate.

The intended remediation makes the existing set-oriented plan-hierarchy path
the one enumeration policy for both keyed-next modes. Sequential selection
continues to be available with its existing flag/config precedence, but it
changes only emission policy. This report does not redesign tier ranking
(TD-047), consolidate the broader plan/next resolvers (TD-045), fill the
separate test gaps catalogued by TD-048, or perform the broad comment and
documentation sweep in TD-049.

`CascadeService` also drives the in-process `shark run` controller. Removing or
migrating that consumer is not required to remove the mode-dependent engine
swap from keyed `next`; its execution and child-lease behavior form a separate
compatibility boundary.

## Findings

1. **The mode switch is above two complete traversal implementations.**
   `resolveNext` branches on `cache.fanout` before calling either `tryCascade`
   or `tryCascadeFanout`. The functions separately own enumeration, recursion,
   pause/archive fall-through, error propagation, parent trail construction,
   and terminal-child auto-advance. A change to either path can therefore alter
   more than fork presentation.

2. **The enumerators have materially different data and error contracts.**
   `CascadeService` calls `ListByFeatureKey` or `GetByKey` plus `ListByEpic`,
   and performs `GetTaskDependencies` for each non-terminal task. The CLI then
   calls `ClaimService.IsClaimable` for each returned child and deliberately
   treats claim lookup errors as claimable with a stderr warning.
   `PlanHierarchyService` instead reads the parent, children, active claims,
   legacy JSON dependencies, and task-to-task `depends_on` relationships in
   one set-oriented query at one evaluation time. A snapshot query or decode
   failure aborts the whole lookup. Mode therefore changes availability,
   consistency, and round-trip behavior.

3. **The two paths can return different child sets from the same persisted
   rows.** Both dependency readers union legacy `tasks.depends_on` with outgoing
   task-to-task `entity_relationships`, but their failure surfaces differ.
   `GetTaskDependencies` fails when a legacy JSON key names a missing task;
   the plan-hierarchy SQL inner join omits that missing endpoint. Claim checks
   are evaluated one child at a time on the sequential path and at one SQL
   snapshot time on the fan-out path. These are dispatch decisions, not
   presentation differences.

4. **Ordering is duplicated and is not exactly identical at every tier.**
   Task repository order and plan-hierarchy task order both use execution
   order, priority, creation time, and key. Feature `ListByEpic` stops at
   execution order and creation time, while the plan-hierarchy query also uses
   key as a deterministic final tie-break. Fan-out additionally groups the
   leading run by execution order, task priority, or lack of both; sequential
   mode simply scans the legacy repository order. The fork mode can therefore
   affect which candidate is first.

5. **The existing sequential test protects the defect.**
   `TestSequentialModeUsesLegacyCascade` asserts that the plan-hierarchy seam is
   not called and the CascadeService seam is called. Its fixture never runs the
   same rows through both engines, and it cannot detect claim, dependency,
   order, or count divergence. `TestSequentialDispatchPrecedence` is still
   valuable because it independently pins the public flag/config precedence.

6. **`PlanHierarchyService` is the reuse-first canonical engine.** It is already
   the default keyed-next engine, already supplies the metadata required for
   tie selection, and performs one bounded query per hierarchy edge. Feeding
   fan-out from `CascadeService` instead would require adding claim state,
   execution-order and priority metadata, set-oriented dependency loading, and
   deterministic tie information to the older service—recreating the
   plan-hierarchy capability under another name.

7. **Unification requires one traversal owner, not merely one child service.**
   Replacing only `nextDescribeDispatchableChildren` while leaving
   `tryCascade` and `tryCascadeFanout` intact would retain duplicated
   fall-through, auto-advance, `ResolvedVia`, nested-selection, and error
   behavior. The keyed-next cascade should obtain one
   `PlanHierarchyChildrenState`, repeatedly evaluate its leading tier, and use
   a mode value only where the function decides between returning the first
   surviving dispatch and attaching a multi-candidate selection.

8. **The canonical semantics should be the shipped default fan-out semantics,
   made explicit as an intentional behavior change for sequential mode.**
   After remediation, sequential mode will inherit set-oriented claim expiry,
   dependency treatment, deterministic ordering, and fail-loud snapshot errors.
   Retaining the old per-child fail-soft claim branch would preserve two
   answers and defeat TD-046. Release notes and focused configuration text
   should describe sequential mode as collapsing a fork, not enabling a legacy
   engine.

9. **Traversal must not eagerly mutate siblings just to collapse a tie.**
   `resolveNext` can auto-advance a child parent while probing it. The unified
   function should preserve ordered short-circuiting in sequential mode:
   resolve candidates until the first live dispatch/nested selection is found.
   Fan-out mode may resolve the whole leading tier to remove parked candidates
   before deciding whether a fork survives. Both modes still share enumeration,
   tier construction, fall-through classification, and response helpers; mode
   need not cause speculative resolution of siblings that sequential execution
   will not return.

10. **`shark run` is a related but distinct boundary.** `RunController`
    enumerates through `CascadeChildrenService`, then actually acquires and
    releases a lease around each nested child run. It does not surface planning
    forks. Keeping that execution-specific consumer does not leave two engines
    behind the keyed-next mode switch, but code comments in
    `cascade_service.go`, `services_global.go`, and
    `plan_hierarchy_service.go` must stop claiming CascadeService still
    enumerates keyed `next`. If product policy requires `next` and in-process
    `run` to select identical effective children, migrate the runner in a
    follow-up with production-shaped lease tests rather than silently widening
    TD-046.

11. **A single differential fixture is useful during migration but is not the
    durable primary guard.** Before deleting the keyed-next legacy seam, a real
    SQLite fixture can expose current differences and verify the intended
    canonical outcomes for terminal, claimed, expired-claim, blocked,
    explicitly ordered, prioritized, and unordered children. After unification,
    the durable counterfactual test should invoke both public modes against the
    same plan-hierarchy seam and assert identical first-candidate eligibility
    and ordering; otherwise a future branch could reintroduce a second engine
    while all single-mode tests stay green.

## Decisions

1. **Use `PlanHierarchyService.DescribeChildren` for every keyed-next cascade.**
   It becomes the sole enumeration source before the sequential/fan-out choice.
   Do not create a third “shared” repository or enrich CascadeService until it
   duplicates PlanHierarchyService.

2. **Collapse the two keyed-next functions into one traversal.** The function
   should own snapshot lookup, leading-tier construction, parked-child
   fall-through, nested cascade recursion, error propagation, parent
   `ResolvedVia`, and all-terminal parent auto-advance. Pass an emission-policy
   value such as `surfaceForks`; do not pass an engine selector.

3. **Keep the public mode precedence unchanged.** Preserve
   `resolveSequentialDispatch` and its precedence test. Internally translate the
   result to “surface a surviving tie” versus “return its first surviving
   candidate.”

4. **Adopt the plan-hierarchy claim/dependency/order contract in sequential
   mode.** Remove the keyed-next `GetCascadeService` seam, per-child
   `IsClaimable`, and fail-soft stderr branch. A failed canonical snapshot
   remains a `cascade lookup failed` error in both modes. This is the necessary,
   explicit compatibility choice; disguising the old behavior behind
   `--sequential` would leave the debt unresolved.

5. **Preserve short-circuit execution semantics.** Sequential mode resolves
   leading candidates in deterministic order and returns at the first live
   result. Fan-out mode resolves the leading tie sufficiently to remove parked
   candidates and only loads relationship edges when two or more live
   candidates will actually be surfaced. Neither mode changes parent status
   merely to inspect an unreturned sibling.

6. **Replace `TestSequentialModeUsesLegacyCascade` with mode-invariance
   coverage.** One shared plan-hierarchy fixture must prove:
   terminal, live-claimed, dependency-blocked, and parked children are skipped
   identically; expired claims remain eligible; explicit execution order,
   priority, and deterministic unordered order agree; a singleton dispatch and
   all-terminal auto-advance agree; and the only wire difference for a
   surviving tie is first dispatch versus fork selection.

7. **Retain focused existing guards.** Keep
   `TestSequentialDispatchPrecedence`, fork-edge failure behavior,
   paused-tier fall-through, nested-fork `resolved_via`, maximum-parallel
   handling, and custom-terminal workflow coverage. Add a structural assertion
   or direct seam counterfactual proving sequential mode consults
   `planDescribeDispatchableChildren`, so another engine-specific branch cannot
   return unnoticed.

8. **Keep `CascadeService` only for its current runner consumer in this
   remediation.** Remove keyed-next-specific comments and the
   `nextDescribeDispatchableChildren` CLI seam, but do not migrate
   `RunController` without explicit acceptance of its child lease and
   stop-on-failure behavior. Record a follow-up only if cross-command selection
   equivalence is a required product contract.

9. **Update only the directly invalidated configuration contract here.**
   Change `Config.SequentialDispatch`, `--sequential`, and the
   `sequential_dispatch` reference text from “legacy single-track cascade” to
   “collapse a keyed-next fork to its first eligible candidate.” Leave the
   broader stale-comment and route-guide inventory to TD-049.

10. **Reject the alternatives.** Keeping both engines plus a differential test
    leaves permanent synchronization cost and mode-dependent failure behavior.
    Making CascadeService canonical duplicates the metadata and set-oriented
    repository already present in PlanHierarchyService. Removing sequential
    mode breaks a documented compatibility control. Migrating `shark run` in
    the same change expands an M-sized keyed-selection debt into execution and
    lease orchestration without evidence that the broader change is required.
