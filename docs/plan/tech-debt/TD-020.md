# Cache transitioner/placeholder generator/actionSvc per resolveNext invocation

## Description

internal/cli/commands/next.go resolveNext rebuilds three adapters on every recursion:

- buildTransitioner(ctx, entityType) — constructs a fresh services adapter via cli.GetTaskService() etc.
- buildPlaceholderGenerator(ctx, entityType) — similar
- actionSvcRoot.ForEntity(entityType) — narrows the action service

For an epic -> feature -> task cascade chain, that's 3 redundant adapter constructions per top-level call. None of these are expensive in absolute terms (the underlying DB connection and workflow service are singletons), but the work is genuinely redundant.

Fix: hoist a small per-call cache map[string]struct{transitioner, generator, actionSvc} inside runNext, pass it through resolveNext recursion. Reset between top-level shark next calls.

Severity low because cascade depth is bounded at 4 (typically 2). Surfaced during simplify review of commit 6492e45.

## Impact

Small constant-factor overhead per cascade hop. Cascade depth is bounded at 4 (typically 2 — epic → feature → task), so the practical cost per `shark next` call is 3-6 extra adapter constructions over the underlying singleton DB / workflow / action service. Not user-visible, but it shows up as redundant work in profiling and adds clutter to the recursion's call graph.

## Resolution Plan

- Define a small per-call adapter cache `type nextAdapters struct { transitioner ...; generator ...; actionSvc ... }` keyed by `entityType` inside `runNext`.
- Pass `*nextAdapters` (or a `map[string]*nextAdapters`) through `resolveNext` recursion; populate lazily on first use per entity type.
- Reset between top-level `shark next` calls (no cross-invocation caching — keeps semantics identical to current code).

## Resolution Notes

Introduced `nextAdapterCache` in `internal/cli/commands/next.go`: a per-invocation
`map[string]*nextAdapters` keyed by entity type, hoisted into `runNext` and
threaded through `resolveNext` recursion. The cache populates lazily on first
use of each entity type and reuses the same triple (transitioner, placeholder
generator, narrowed action service) for every subsequent recursion hop on the
same type. The root `action.ActionService` is also resolved once at cache
construction and shared across all entity-type views.

Effect on an epic → feature → task cascade: 3 transitioner builds → 3,
3 generator builds → 3, 3 `ForEntity` calls → 3, 3 root-service resolutions
→ 1. Recursion on the same entity type (e.g. an `advance_status` auto-advance)
costs zero additional adapter constructions.

Builder hooks (`nextBuildTransitioner` / `nextBuildPlaceholderGenerator`) are
package-level function variables so tests can substitute counting wrappers
without a real database. Three tests in `next_cache_test.go` verify:

- `TestNextAdapterCache_BuildsEachAdapterOncePerEntityType` — 4 simulated
  hops across 3 entity types produce exactly 3 builds of each adapter.
- `TestNextAdapterCache_ReturnsSameInstanceOnRepeatedGet` — repeated lookups
  return the same `*nextAdapters` pointer.
- `TestNextAdapterCache_PropagatesBuilderError` — failed builds aren't
  cached and don't pollute the cache for other entity types.
