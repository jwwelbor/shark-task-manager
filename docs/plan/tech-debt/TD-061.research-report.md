# TD-061 research report

## Scope

TD-061 removes the duplicate `ValidateTaskDependencies` branch bodies in
`TaskRepository.updateInternal` after TD-065 restored validation for the
`UpdateNoResequence` (`--parallel`) path. The required invariant is unchanged:
every task update validates the model, then validates legacy task dependencies
before any row write; a no-resequence update still avoids sibling resequencing
and a transaction.

This is a repository-local refactor. It does not alter dependency validation
rules, task update DTO parsing, direct-row SQL, or the legacy JSON versus
entity-relationship dependency boundary.

## Findings

1. **The duplicate code is exact and safe to hoist.** Both branches call
   `ValidateTaskDependencies(ctx, task)` and return the identical
   `dependency validation failed` wrapper before proceeding. A single call
   immediately after `task.Validate` preserves the same return value and
   ordering for both paths.

2. **Validation must stay before the branch.** Hoisting it below the
   `forceSkipCascade` return would recreate the TD-065/B048 bypass. Hoisting
   it after `GetByID`, `BeginTxContext`, or `updateRowDirect` changes the
   observable order: invalid dependencies could cause additional reads,
   transaction activity, or a write before rejection. Place it directly after
   model validation and before the branch.

3. **The fast-path semantics remain intact.** `UpdateNoResequence` continues
   to call `updateInternal(..., true)`, which after the hoisted validation
   returns `updateRowDirect`. It still avoids `GetByID`, sibling resequencing,
   and `BeginTxContext`; a nil, empty, or `[]` dependency list makes the
   validator return immediately.

4. **The existing B048 regression test covers the important counterfactual.**
   It proves ordinary `Update` and `UpdateNoResequence` both reject an invalid
   dependency before the row changes, then proves the no-resequence path
   succeeds after clearing the task field. That test fails if the hoisted call
   is omitted or positioned only in the normal branch.

5. **Related-document registration is unsupported for tech-debt entities.**
   Keep this report as the durable evidence rather than adding an unsupported
   related-document operation.

## Decisions

1. **Recommend IMPLEMENT.** This is a low-risk cleanup that removes a future
   drift point without changing the TD-065 safety contract.

2. **Hoist precisely one call.** After `task.Validate()` succeeds, add one
   `ValidateTaskDependencies(ctx, task)` call with the existing error wrapper.
   Delete the two branch-local calls. Leave the `forceSkipCascade` branch as
   a direct return to `updateRowDirect`; leave all normal-path cascade and
   transaction code in place.

3. **Do not add an abstraction or alter the validator.** A helper would add
   another indirection around one shared statement, and changing validation
   policy would exceed TD-061. The existing common orchestration method is
   the appropriate shared seam.

4. **Keep the current regression test and add only a narrow order guard if
   needed.** Run `TestTaskRepository_UpdateNoResequence_ValidatesDependencies`
   plus the normal dependency-validation tests. It should show invalid input
   leaves order unchanged and nil dependencies permit the direct update. A new
   test is only warranted if a practical test seam can prove no transaction
   was opened; the existing test correctly avoids claiming that database pool
   statistics distinguish transaction use. Finish with `git diff --check`.
