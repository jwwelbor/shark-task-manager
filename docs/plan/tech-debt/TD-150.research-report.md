## Scope

Revalidate the B047 feature-list progress sort against the production workflow
configuration path, rather than only its synthetic workflow-config unit path.

## Ubiquitous vocabulary

*Live progress* is the weighted percentage calculated from the current task
status breakdown and the canonical task workflow. *Cached progress* is the
persisted `ProgressPct` fallback and must not silently substitute for live
progress when the canonical workflow is available.

## Findings

The B047 follow-up already precomputes sort keys and orders equal percentages
by feature key. The production feature-list path still loads workflow metadata
from `.sharkconfig.json`; that configuration has no inline workflow steps, so
the parser returns nil and the feature list falls back to cached progress.
The canonical embedded workflow is available through `workflow.Service`, but
the presentation path does not use it. Existing tests only exercise the
live-progress branch with a synthetic config.

## Decisions

TD-150 remains a bounded implementation item. Replace all three independent
legacy presentation loads with one canonical task-workflow acquisition path
shared by sort, table, and JSON rendering. Consolidate the duplicated
status-count conversion where it is safe to do so, and add a zero-config
production-path regression that proves displayed and sorted progress remain
identical before resolving the debt.
