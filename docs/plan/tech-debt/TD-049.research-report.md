# Research report: Six documentation and typed-constant inconsistencies in the plan/next surface

## Scope

TD-049 is a bounded consistency cleanup for the `shark plan` and keyed
`shark next` surfaces introduced or changed by PR #139. It covers six
non-behavioral defects:

1. a portfolio-advice DTO comment names the retired bare-`next` caller;
2. a hierarchy-service comment promises a result its implementation cannot
   return;
3. a standalone-planning comment attributes terminal filtering to the wrong
   boundary;
4. a plan entrypoint comment cites a nonexistent sibling symbol;
5. a severity-ranking helper compares magic strings despite existing typed
   constants; and
6. keyed-next help and the route-based workflow guide omit the default fork
   response.

The affected capability is the read-only selection versus keyed-dispatch
contract: `shark plan` recommends roots or tiers without claiming, while
`shark next <key>` either returns one dispatch response or, at a default
fan-out cascade tie, a `hierarchy_selection` / `parallel_candidates` response
with no worker prompt. The runtime behavior and wire structs already exist and
are not changed by this debt.

This report does not unify the plan/next resolvers (TD-045), change sequential
enumeration semantics (TD-046), simplify tier selection (TD-047), add the
broader missing tests (TD-048), or revise the portfolio-advice implementation
(TD-043).

## Findings

1. **The portfolio DTO comment names a command path that no longer exists.**
   `PortfolioAdviceEnvelope` says it is assembled for bare `shark next`
   selection. `requireNextEntityKey` rejects a missing key before planning
   services are constructed, while `runPortfolioPlan` obtains the advice for
   bare `shark plan`. The data type and JSON tags are correct; only the
   two-line comment is stale.

2. **Unsupported hierarchy parents return an error, not an empty success.**
   `PlanHierarchyService.DescribeChildren` documents “return (nil, nil)” for an
   unsupported `parentType`. Its snapshot reader returns
   `ParentFound: false` for unknown types, after which the service returns
   `"<type> <key> not found"`. `TestPlanHierarchyServiceParentNotFoundErrors`
   already protects the service’s fail-loud behavior. The lowest-risk fix is to
   update the comment, not weaken the implementation.

3. **The standalone-planning terminality nit is real as an ownership
   description, but the debt text overstates the runtime gap.**
   `StandalonePlanningService.Plan` directly performs list, hard-dependency,
   claimability, ranking, and grouping operations. In production, its injected
   bug, change-card, and tech-debt list services receive zero-value filters,
   whose `ShowAll: false` behavior excludes terminal records before candidates
   enter the planner. `runStandalonePlan` then calls `resolveNext` and retains
   only `spawn_agent` responses, providing the final workflow-action readiness
   check. Therefore production output is non-terminal, but the planner
   abstraction itself neither classifies terminal status nor declares that
   requirement on its reader interfaces. Its method comment should describe
   service-owned behavior instead of claiming the stronger invariant.

4. **`resolvePlanDispatch` is useful as a named boundary, but its rationale is
   stale.** The function deliberately distinguishes a top-level keyed plan
   invocation from recursive `resolvePlanEntity`, and command tests invoke it
   directly. Its comment says it mirrors
   `next.go`’s `resolveNext/resolveNextDispatch` naming, but
   `resolveNextDispatch` does not exist. Removing the pass-through would overlap
   TD-045 and provide no user-visible benefit. Reword the comment to describe
   the entrypoint boundary without citing a nonexistent symbol.

5. **The severity helper violates the project’s constrained-value rule without
   changing current results.** `severityRank` switches on `"critical"`,
   `"high"`, `"medium"`, and `"low"`. Both `models.BugSeverity*` and
   `models.TechDebtSeverity*` define exactly those stored values, and
   `coding-standards.md` requires typed constants instead of magic strings in
   comparisons. The sibling `epicPriorityRank` demonstrates the local pattern:
   convert the incoming string to its model enum, then switch on typed
   constants. Existing bug and tech-debt grouping tests cover common values but
   do not pin every rank or the unknown-value fallback.

6. **The runtime, tests, configuration reference, and Rider agree on the fork;
   two high-visibility descriptions do not.** Default keyed-next fan-out stops
   when two or more live children survive the leading tier and emits
   `mode: "hierarchy_selection"`, `action: "parallel_candidates"`,
   `parallel_execution: "available"`, root identity, selection reason,
   `resolved_via`, and candidate entities. It carries no `prompt` or
   `agent_type` because it is a selection, not a claimable dispatch.
   `nextCmd.Long` advertises only the single-dispatch JSON object, and
   route-based workflow section 4 unconditionally says keyed next cascades to
   the first dispatchable descendant. That statement is now true only when no
   fork survives, fan-out is disabled by its cap, or sequential mode is chosen.

7. **The Rider procedure is existing remediation and the correct documentation
   source.** `skills/shark-rider/verbs/run.md` already lists
   `parallel_candidates` as a wire action, defines the hierarchy-selection
   fields, states that the response has no prompt, and instructs the parent to
   evaluate integration safety before following one or more candidate keys.
   TD-049 should reuse that vocabulary in concise CLI/guide text rather than
   invent another response model or duplicate the full orchestration procedure.

8. **Documentation assertions should be proportional to the risk.** Four fixes
   are Go doc comments and one is a constant substitution covered by focused
   service tests. The CLI long help is executable user-facing text and already
   has a small `next_test.go` assertion pattern. A focused assertion that the
   help names both `hierarchy_selection` and `parallel_candidates` prevents the
   wire alternative from disappearing again. The route guide has no rendered
   documentation test harness; a repository text/golden check would be
   disproportionate unless the project establishes one broadly.

## Decisions

1. Change `PortfolioAdviceEnvelope`’s comment to “read-only evidence assembled
   for bare `shark plan` epic selection.” Do not change its type, mode, fields,
   or constructors.

2. Change `DescribeChildren`’s unsupported-parent bullet to state that an
   unsupported or missing parent returns a not-found error. Preserve the
   existing `ParentFound` check and its test.

3. Rewrite `StandalonePlanningService.Plan`’s comment around what the service
   owns: dependency-satisfied, claimable roots grouped by stored priority tier.
   If mentioning terminality, explicitly attribute it to the production list
   readers and final `resolveNext` readiness filtering. Do not add redundant
   workflow dependencies or terminal filtering to the planner.

4. Keep `resolvePlanDispatch` as the named top-level boundary, but remove the
   `resolveNextDispatch` reference. A sufficient comment is that it starts
   keyed plan resolution at depth zero while `resolvePlanEntity` is the
   recursive core.

5. Replace the literal comparisons in `severityRank` with typed model
   constants, following `epicPriorityRank`. Keep the public/stored values, rank
   order `critical < high < medium < low < unknown`, and return type unchanged.
   Use one model enum as the normalized comparison vocabulary and document that
   bug and tech-debt severities share these values; do not introduce a third
   public severity type for this S-sized cleanup.

6. Extend `nextCmd.Long` with a second, compact JSON shape for a cascade fork.
   Include `mode`, `action`, `root_key`, `root_type`, `selection_reason`,
   `resolved_via`, `parallel_execution`, and `entities`, and state explicitly
   that the response has no worker prompt. Keep the existing single-dispatch
   shape as the other valid result.

7. Update route-based workflow section 4 to say keyed next cascades until it
   reaches either one dispatchable descendant or a default fan-out fork.
   Explain that the fork is read-only, does not claim candidates, and requires
   invoking `shark next <child-key>` for the chosen candidate(s). Link to the
   sequential-dispatch configuration detail rather than reproducing its
   precedence rules.

8. Add a focused `next_test.go` help-contract assertion for
   `hierarchy_selection`, `parallel_candidates`, and the no-prompt distinction.
   Expand the standalone severity table to cover all four known severities plus
   unknown fallback through both bug and tech-debt call paths. Existing
   plan-hierarchy not-found and fan-out response tests need no behavioral
   changes.

9. Coordinate the overlapping wording with TD-046. TD-049 owns documenting the
   existence and shape of the fork. TD-046 owns replacing “legacy
   single-track engine” language with the eventual canonical statement that
   sequential mode collapses the same eligible tie. Implementing the reports
   together avoids changing the same help/config comments twice.
