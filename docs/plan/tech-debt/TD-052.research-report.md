# TD-052 research report

## Scope

Remove the unused `resolveCascade` cache parameter from plan-mode dispatch while retaining the next-mode adapter cache contract.

## Research checklist

- [x] `scope_vocabulary` — Evidence: `docs/plan/tech-debt/TD-052.md:1-24`; `internal/cli/commands/next.go:413-460`.
- [x] `affected_implementation_or_contract` — Evidence: `next.go:429-458` shows next mode consumes the parameter while plan mode consumes `s.planCache`.
- [x] `pattern_contract` — Evidence: `next.go:614-616` is the single cascade call site, so a strategy-owned cache can be made explicit and compiler-checked.
- [x] `dependency_impact` — Evidence: plan cascade forwards a `planAdapterCache` to `tryPlanHierarchy`; next cascade forwards `nextAdapterCache` and `surfaceForks` to `tryCascadeCandidates`.

## Findings

The present plan-mode parameter is redundant and can drift from its strategy cache. The smallest durable fix is a strategy method split or strategy-owned adapter accessor, so each mode reads precisely one source.

## Capability map

| Capability | Source | Decision |
| --- | --- | --- |
| Sequential cascade adapter path | `internal/cli/commands/next.go` | REUSE — retain its next adapter cache and fork surface. |
| Plan hierarchy cascade path | `internal/cli/commands/next.go` | REUSE — retain its strategy-owned plan cache. |
| Cascade dispatch signature | `internal/cli/commands/next.go` | EXTEND — eliminate the ambiguous redundant parameter. |

## Decisions

Remove the cache argument from `resolveCascade`; derive the next adapter cache only in the next-mode branch from a strategy field supplied by `nextResolutionStrategy`, and continue to use `planCache` in plan mode. Cover both constructors/cascade paths.
