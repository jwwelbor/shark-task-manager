## Scope

TD-230 reports that `gate_result_v1`'s coordinator-side (Rider) ingestion
path — `shark run <key> --apply-result ...` and `shark run <key>
--resume-run ...` — is documented only as "route the worker's terminal
envelope through the shared ingestion CLI surface," with no runnable
example, no statement of `run_id` provenance, and no statement of the
lease-release contract. Scope is documentation-only: verify the record's
claims (and the coordinator's supplied first-hand findings) against the Go
source, then extend `skills/shark-rider/context/host-adapter-contract.md`'s
existing `result_contract`-gated dispatch section with a runnable example
and the missing semantics. No Go code changes.

## Findings

1. **The command and required flags are as the coordinator stated.**
   `internal/cli/commands/run_apply_result.go`'s `runApplyResult` requires
   `--run-id` and `--session` together with `--apply-result`, in that
   validation order. `--session` is checked against the entity's live
   claim via `verifyClaimSession` (`internal/cli/commands/run.go:53-73`)
   before the envelope file is even opened — a mismatched, missing, or
   expired session produces zero writes.

2. **`run_id` is caller-minted and opaque for `--apply-result`.** There is
   no lookup and no `shark next --json` field to reuse; the string becomes
   this gate stage's persistence key under `.shark/runs/<run-id>/`.
   Confirmed by reading `applyResultIngest` and `run.go`'s flag help text.

3. **Correction to the coordinator's finding #4 (per-stage run_id
   format).** The coordinator asserted `<shark.log run_id>-g<stage-iteration>`
   from `run.go:127`'s flag help text. The actual construction, in
   `internal/runner/controller.go`'s `gateStageRunID`, is
   `fmt.Sprintf("%s-%s-g%d", runID, entityKey, stageN)` —
   `<invocation-run-id>-<entity-key>-g<stage-iteration>`. The flag help
   text is stale: it omits the entity-key component, which
   `gateStageRunID`'s own doc comment says was added specifically to stop
   cascade siblings dispatching the same stage number from colliding on the
   same run directory. The doc now states the correct three-part format and
   tells the adapter to read the value back from `GateStatus.run_id` /
   `applyResultOutput.run_id` rather than reconstruct it by hand, since
   `--resume-run` treats the id as opaque either way
   (`run_resume.go`'s package doc comment).

4. **Correction to the coordinator's finding #8 (lease release
   "inconsistency").** This is deterministic, not inconsistent.
   `applyResultIngest` (`run_apply_result.go`) sets
   `RetirementConfirmed`/`RunConcluded` on the confirming re-ingest call
   only when `deps.WorkflowSvc.IsTerminalStatus(result.ToStatus)` is true.
   A terminal target status releases the lease as part of ingestion (a
   later `shark release` correctly reports "No matching claim to
   release"); a non-terminal target status does not release it, and the
   caller must call `shark release` itself. This matches TD-230.md's own
   Resolution Plan item 3, confirmed empirically in the same session. The
   two observations the coordinator called "inconsistent" are the two
   branches of one rule. `run_resume.go`'s doc comment further confirms
   `ClaimService.Release` is idempotent (`released: false`, not an error,
   on a second call), so documenting "call release anyway, it's harmless"
   is correct and now included.

5. **The 1000-byte summary cap is real and matches the coordinator's
   report.** `internal/gateresult/gateresult.go` defines
   `SummaryMaxBytes = 1000`; `text.go`'s `boundedText` produces the exact
   error string `"must contain 1 through 1000 UTF-8 bytes"` under
   `ErrorClassBounds`, and rejects the entire envelope (no partial
   persistence, no truncation). This bound applies to every bounded
   free-text field sharing `boundedText`, not only `gate_result.summary`.

6. **`evidence[]` item shape.** `internal/workercontrol/envelope.go`'s
   `EvidenceRef` requires `kind`/`pointer` with optional
   `summary`/`command`/`working_directory`/`exit_code`; every example in
   `worker-control-schema.yaml` (both the standalone copy under `skills/`
   and its embedded mirror) shows only `evidence: []`, matching the
   coordinator's report that no populated example exists in that file. Per
   the advisor consult, the schema file was **not edited** for this task:
   it exists both at `skills/shark-attack/context/worker-control-schema.yaml`
   and at the embedded, explicitly out-of-scope
   `internal/sharkdata/default_data/skills/shark-attack/context/` mirror,
   and `host-adapter-contract.md` itself states shark-rider content sits
   outside that skill's parity gate specifically *because* shark-attack
   files are subject to one. Editing only the unembedded copy would desync
   the pair and only surface as a `make test` failure the parent runs, not
   this worker. The populated `EvidenceRef` shape is instead demonstrated
   inline in the new `host-adapter-contract.md` worked example. Adding a
   non-empty example to the schema file itself remains open — flagged
   below as a follow-up, not fixed here.

7. **Outcome-role gating matches the coordinator's finding #10.**
   `internal/gateresult/role.go`'s `ValidateRole` confirms: `success`
   rejects any `kickbacks` and any `open`/`severity_conflict` finding;
   `route_rework` rejects any `kickbacks`; `kickback_rework` requires at
   least one; `blocked`/`hold`/`cancelled` require a kickback or a
   non-empty `no_kickback_reason`. `Disposition` is a closed enum (`open`,
   `fixed`, `already_dispositioned`, `severity_conflict`,
   `not_reproducible`); `severity` is bounded free text, not a closed enum.

8. **Successful output shape matches the coordinator's finding #7.**
   `applyResultOutput` (`run_apply_result.go`) and `gaterun.StatusProjection`
   (`internal/gaterun/status.go`) together produce exactly the field set
   described: `run_id`, `entity_key`, `entity_type`, `outcome_key`, `role`,
   `to_status`, `transitioned`, and a nested `status` object
   (`persistence_state`, optional `worker_phase`/`nested_operation`,
   `retirement_state`, `elapsed_seconds`, optional `result_location`,
   `completed_suboperation_count`).

9. **`transitioned: false` is not failure.** Confirmed: this is the
   idempotent already-at-target case, matching the coordinator's finding
   #9 and `run_resume.go`'s `already_transitioned` handling.

10. **Verification corrections made during drafting (caught before
    publishing, not left for a future reader):**
    - The worked example initially paired a task key with `to_status:
      resolved`, which task-level workflow has no such status for
      (`resolveApplyResultWorkflowService`'s own doc comment warns against
      exactly this class of error). Switched to `TD-231` /
      `entity_type: tech_debt` / `in_progress` -> `resolved`, matching
      `internal/sharkdata/default_data/workflow/tech-debt.yaml` exactly —
      a real, already-shipped `gate_result_v1` step.
    - The "read the per-stage `run_id` back" guidance initially named
      `GateStatus.run_id` off a `shark run --resume-run` poll, copied from
      `run.go:127`'s same stale flag help corrected in Finding 3.
      `GateStatus` is real (`RunResult.Stages[].GateStatus`,
      `internal/runner/controller.go`, JSON key `gate_status`) but belongs
      to `shark run`'s own per-stage result, not `--resume-run`'s output
      (`resumeRunOutput` has no such field). Corrected to point at
      `stages[].gate_status.run_id`.
    - Confirmed the worked example's step (`action: check_or_resume` in the
      raw workflow YAML) does not contradict this same doc's Request-fields
      table, which says `action: spawn_agent` is the only action an adapter
      spawns for: `internal/cli/commands/next.go`'s `normalizeWireAction`
      folds `check_or_resume` into wire `action: spawn_agent` before
      `shark next --json` reaches an adapter. Added one parenthetical to
      the example so a reader who greps the raw YAML (as this research
      did) isn't left to resolve the apparent mismatch themselves.
    - `related_work` flipped from an initial `false` (a filename-only scan)
      to `true`: `grep -l "gate_result_v1\|apply-result\|IngestGateResult"
      docs/plan/tech-debt/*.md` surfaces sibling implementation-gap records
      in the same subsystem (TD-178, TD-184, TD-188, TD-189, TD-190,
      TD-193, TD-222) — none overlapping TD-230's specific documentation
      claim, so no cross-links were added.

## Decisions

- Extend `skills/shark-rider/context/host-adapter-contract.md`'s existing
  `result_contract`-gated dispatch section, rather than creating a new
  document or duplicating content into `verbs/run.md`. `verbs/run.md`
  already delegates to this file for the dispatch field list, so a
  coordinator following the run loop reaches the new content without a
  second edit. This diverges from TD-230.md's Resolution Plan wording
  ("mirrored in `verbs/run.md`"), traded off against the worktree
  constraint restricting this pass to one doc plus TD-230's own files, and
  against the observation that `run.md`'s own resume section (~line 449)
  already just says "call the resume CLI surface" without naming it or
  linking anywhere — a second, smaller documentation gap in the same
  family, left as a follow-up rather than folded into this change.
- Correct, rather than repeat, two specific numeric/behavioral claims
  from the coordinator's original write-up (per-stage run_id format;
  lease-release "inconsistency") once the source disagreed with them —
  see Findings 3 and 4.
- Do not touch `worker-control-schema.yaml` (either copy). The populated
  `EvidenceRef` example is demonstrated in the new host-adapter-contract.md
  content instead; adding it to the schema file(s) is left as an explicit,
  separate follow-up so as not to touch files this worker was told are out
  of scope and to avoid desyncing the embedded/unembedded pair without a
  test run to catch it.
- TD-230.md's `## Impact`/`## Resolution Plan`/`## Resolution Notes`
  sections contain no `[...]` placeholders; left unchanged except for the
  added `related-docs:` front-matter entry pointing at this report.
- `related_work: true` — content-grepped sibling records exist in the same
  subsystem (TD-178, TD-184, TD-188, TD-189, TD-190, TD-193, TD-222); see
  Finding 13. None target TD-230's specific documentation gap, so no
  cross-links were added beyond noting them here.
