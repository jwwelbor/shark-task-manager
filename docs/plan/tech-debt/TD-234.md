# Question owner-mismatch error message leaks CLI flag syntax into HTTP API responses

## Description

loadClosableQuestion()'s owner-mismatch error (internal/services/question_workflow_service.go:340) hardcodes '--resolution-owner=%q' CLI flag syntax. This message is shared by both the CLI (internal/cli/commands/question.go) and the HTTP API's resolve/withdraw/supersede handlers (internal/api/question_handler.go), which return err.Error() verbatim in JSON error bodies. API callers see CLI-only flag syntax in their error responses instead of the JSON field name ('owner'). Found by deep-review (canonical-six-angle) on B062 fix branch as non-blocker F1; triaged rather than fixed in-branch to keep the B062 fix surgical (question_service_test.go:737,939 and question_handler_test.go:425-435 already assert this exact wording as part of B062's fix). Related to TD-158 (question CLI flag-surface inconsistency).

## Impact

HTTP API callers hitting `POST /api/v1/questions/{key}/{resolve,withdraw,supersede}`
with a mismatched `owner` field received a 409 JSON body containing
`--resolution-owner="<owner>"` — a CLI flag they cannot pass to an HTTP
request. This made the error non-actionable for any client that only talks
to the API (no CLI available) and leaked an implementation detail of one
transport into another's contract.

## Resolution Plan

Add a typed `QuestionOwnerMismatchError{ConfiguredOwner string}` in
`internal/services/question_service.go` whose `Error()` is transport-neutral
(names the concept and the configured owner value, no CLI flag syntax, no
JSON field name). `loadClosableQuestion` in
`internal/services/question_workflow_service.go` wraps it with the existing
`questionConflictError` (`QuestionRuleError{Class: QuestionRuleConflict}`),
preserving the 409 classification `internal/api/common.go`'s
`questionErrorStatus` already relies on. The HTTP handlers
(`internal/api/question_handler.go`) needed no change — they already surface
`err.Error()` verbatim, so the neutral message flows through automatically.
The CLI (`internal/cli/commands/question.go`) adds a
`withQuestionOwnerMismatchHint` wrapper around `Resolve`/`Withdraw`/`Supersede`
that unwraps `*services.QuestionOwnerMismatchError` via `errors.As` and
appends the `--resolution-owner=%q` retry hint only for CLI callers. A sweep
of `question_workflow_service.go` and `question_service.go` for other
hardcoded `--` flag syntax found no sibling leaks (TD-158 remains a separate,
already-tracked concern about CLI flag-surface naming consistency, not this
leak pattern).

## Resolution Notes

Implemented as planned. Existing regression tests that asserted the old CLI
wording were updated, not weakened:

- `internal/services/question_service_test.go:737` and `:949` — the
  owner-mismatch-is-detected-and-rejected guarantee (`QuestionRuleConflict`,
  repository write never called) is unchanged; only the string assertion
  changed from `--resolution-owner="release-owner"` to asserting (a) the
  configured owner `"release-owner"` is still named and (b) `--resolution-owner`
  is absent from the service-level message.
- `internal/api/question_handler_test.go:425` — rebuilt to construct the
  error via the real `*services.QuestionOwnerMismatchError` type (not a
  hand-written string) and assert the JSON body both omits
  `--resolution-owner` and still names `release-owner`.
- Added `internal/cli/commands/question_test.go`'s
  `TestQuestionResolveOwnerMismatchAddsCLIFlagHint` to lock in the CLI-side
  half: `resolve`/`withdraw`/`supersede` still print the
  `--resolution-owner="release-owner"` retry hint for a human CLI operator.

Verified the API assertion actually bites: temporarily reverted
`QuestionOwnerMismatchError.Error()` to include `--resolution-owner=%q`,
re-ran `TestQuestionHandlerResolveOwnerMismatchReturnsConflict`, confirmed it
failed with the leaked flag syntax in the body, then restored the fix and
confirmed it passed again.
