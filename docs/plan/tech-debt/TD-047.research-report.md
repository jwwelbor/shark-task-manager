# Research report — selectPlanChildTier repeats the same leading-tier scan

## Scope

This report covers `selectPlanChildTier` in
`internal/cli/commands/plan.go`, the ordered child evidence it consumes, its
two production callers, its selection-reason contract, and its direct and
end-to-end tests. It does not redesign hierarchy eligibility, repository
ordering, dependency or claim filtering, fork resolution, parallel candidate
bounding, or sequential cascade traversal.

The affected capability is deterministic selection of the first eligible
hierarchy tier. Given children already ordered by the plan-hierarchy
repository and filtered by `PlanHierarchyService`, the selector returns the
leading contiguous run that shares the first child's effective tier:
execution order first, then task priority when execution order is absent, then
the unordered fallback. A multi-child run is reported as `parallel_tie`; a
singleton reports the dimension that selected it.

The proposed remediation replaces the selector's three copy-pasted scans with
one comparable tier-identity helper and one leading-run scan. It preserves and
extends the existing hierarchy-tier capability; it does not replace the
capability or move ordering responsibility out of the repository/service
pipeline.

Shared vocabulary:

- **Tier identity**: a comparable value containing the applicable dimension
  and value: ordered execution value, unordered-task priority value, or
  unordered fallback.
- **Leading run**: the contiguous prefix whose tier identity equals the first
  child's identity. It is intentionally not every matching item in the slice.
- **Underlying reason**: `execution_order`, `priority`, or
  `repository_order` for a singleton tier.
- **Parallel reason**: `parallel_tie`, which replaces the underlying reason
  whenever the leading tier contains more than one child.
- **Ordered task**: a task with `ExecutionOrder != nil`; its priority does not
  split an execution-order tie.
- **Unordered task**: a task with no execution order; a non-nil priority then
  becomes its tier dimension.
- **Unordered feature**: a feature with no execution order; priority is not a
  feature-tier dimension.

## Findings

1. **The complexity title reflects the pre-remediation function, while the
   remaining debt is current.** Running the checked-in Go `gocyclo` tool
   against the current `plan.go` reports complexity 19 for
   `selectPlanChildTier`. Running it against `543ea021^` reports 20. Commit
   `543ea021` removed the unreachable `len(selected) == 0` fallback and
   documented why the first child always survives the unordered branch. That
   partial remediation should be retained; the three repeated scans still
   dominate the function.

2. **The selector is a shared plan/next policy surface, not a plan-only
   helper.** `tryPlanHierarchy` calls it to construct `shark plan
   <epic|feature>` selection. `tryCascadeFanout` calls it repeatedly while
   re-tiering default keyed-next candidates after parked children are removed.
   Legacy sequential `tryCascade` does not use it. A behavioral regression
   therefore affects both read-only plan advice and the canonical Rider run
   loop's fork decisions.

3. **All three branches implement the same algorithm over different keys.**
   The execution-order branch takes the leading run with equal non-nil
   execution order. The task-priority branch takes the leading run of
   execution-order-nil tasks with equal non-nil priority. The fallback takes
   the leading run with no execution order and, for tasks, no priority. Each
   branch allocates a result, scans until the first mismatch, and converts a
   run of length greater than one to `parallel_tie`.

4. **Input order is part of the contract.**
   `planhierarchy.Repository.readEpicFeatures` orders features by non-null
   execution order first, then execution order, creation time, and key.
   `readFeatureTasks` orders tasks by non-null execution order first, then
   execution order, priority, creation time, and key.
   `PlanHierarchyService.DescribeChildren` filters terminal, claimed, and
   dependency-blocked rows without reordering survivors. The selector must
   therefore consume a leading run; sorting again or collecting equal keys
   from beyond the first mismatch would allow later work to bypass an earlier
   tier.

5. **A tier identity must encode the dimension as well as its numeric value.**
   Execution order 3 and task priority 3 are not the same tier. A small
   comparable struct such as `{kind, value}` avoids string encoding and
   pointer-identity mistakes. Equality must compare the pointed-to integer
   values. For an ordered task, the key must exclude priority so tasks with the
   same execution order but different priorities remain in one parallel tier,
   matching current behavior.

6. **Selection reasons are a separate projection of tier identity.** A
   singleton ordered child returns `execution_order`; a singleton unordered
   prioritized task returns `priority`; a singleton fully unordered child
   returns `repository_order`. Any corresponding run of two or more returns
   `parallel_tie`. The extraction should compute the first child's identity
   and underlying reason once, scan equal identities once, then apply the
   length-based reason override.

7. **Current tests protect the highest-risk unordered correction but do not
   form a complete decision table.** `TestUnorderedSiblingsTieIntoAFork`
   covers unordered feature ties, singleton fallback, ordered-to-unordered
   separation, and unordered-task-to-prioritized-task separation.
   `TestResolvePlanDispatchSelectsOneDirectTaskTierWithoutRecursing` covers an
   execution-order tie through plan, and the fan-out suites cover its
   end-to-end fork consequence. There is no focused selector table covering
   empty input, singleton priority, priority tie and boundary, equal execution
   order with different task priorities, equal values stored behind different
   pointers, or a matching key after an intervening mismatch.

8. **No global complexity policy or cross-planner abstraction is required.**
   `.golangci.yml` does not enable a cyclomatic-complexity linter. TD-037 and
   TD-038 record the same local readability class in other functions, but
   portfolio, standalone, and sprint planning use different evidence types,
   rank dimensions, and output contracts. The safe remediation is a private
   hierarchy-child helper, not a generic ranking framework or a new lint gate.

## Decisions

1. Add one private comparable tier-identity type and a helper that classifies a
   `services.PlanHierarchyChild` as execution-order, task-priority, or
   unordered and returns the corresponding singleton selection reason.
2. Rewrite `selectPlanChildTier` as: handle empty input; classify the first
   child; scan the remaining prefix until the first unequal identity; return
   that prefix with `parallel_tie` when its length exceeds one, otherwise
   return the helper's underlying reason.
3. Compare integer values, not `*int` addresses. Include a dimension tag in
   the identity so an execution-order value cannot compare equal to the same
   numeric task priority.
4. Preserve execution-order dominance: when `ExecutionOrder` is non-nil,
   ignore entity type and priority for tier equality. Consult priority only
   for tasks whose execution order is nil. Treat all other no-order children
   as unordered.
5. Preserve leading-contiguous-run semantics and caller order. Do not sort,
   regroup later matches, consult creation time/key, or move this policy into
   the repository.
6. Preserve exact reason strings:
   `execution_order`, `priority`, `repository_order`, and `parallel_tie`.
   Do not expose the internal tier-kind representation on the JSON wire.
7. Consolidate direct selector coverage into a table that includes empty
   input, each singleton reason, each multi-child tie, each dimension boundary,
   equal values behind distinct pointers, ordered tasks with differing
   priorities, and a later matching identity after a mismatch. Retain the
   existing plan and keyed-next end-to-end fork tests.
8. Keep the helper in the commands package beside the only two callers.
   Portfolio, standalone, and sprint planners have different tier contracts
   and should not be generalized into this change.
9. During implementation, verify the selector's cyclomatic complexity falls
   below 6 with `gocyclo`, then run the mandatory `make fmt`, `make lint`, and
   `make test` gate.
