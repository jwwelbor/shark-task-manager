# E40 bench: no test ever runs a real shark binary through run-lifecycle.sh into verify-lifecycle-run.sh

## Description

The F08 lifecycle harness (`bench/scripts/run-lifecycle.sh`,
`bench/scripts/verify-lifecycle-run.sh`, `bench/runs/i07-schema.yaml`)
landed in one commit (`32e98734`, "feat(bench): add replayable
product-design lifecycle harness (#183)") with test coverage at every tier,
but every test substitutes a mock at exactly the boundary where the schema
and the two scripts would have to agree with each other and with the real
`shark` CLI:

- **TC-060 through TC-068** (`bench/scripts/tests/tc06{0,1,2,4,5,6,8}_*.sh`,
  the "F08 contract tier" `bench/README.md` points readers at) run
  `run-lifecycle.sh` for real, but against a **PATH-stubbed fake `shark`
  binary** — a hand-written script that pattern-matches argv and prints
  canned JSON the test author typed in, never anything the real CLI's
  `omitempty` response contract would actually produce.
- **`verify-lifecycle-run.sh` is never invoked by any TC-060–068 test.**
  Nothing in the suite pipes a `run-lifecycle.sh`-produced record through it.
  (`tc082_retention_layout_test.sh` claims to exercise it via
  `verify-retention-root.sh`, but that path runs against a hand-built
  "golden" retained-artifact fixture too, not live `run-lifecycle.sh`
  output.)
- **The Go contract test's fixture is hand-authored to satisfy the
  validator, not to reflect reality.**
  `tests/contracts/testdata/e40_i07/valid/complete.jsonl` has `effort`,
  `resolved_via`, `unresolved_placeholders`, and `reviewer.effort` all
  populated — the opposite of what real `shark next`'s `omitempty` contract
  and `run-lifecycle.sh`'s hardcoded `""` reviewer placeholder actually
  produce — and its `candidate` block has exactly the validator's 6-field
  digest formula, not the producer's 7-field one (see B057).

## Impact

Unit-level coverage is real (loop mechanics, resource limits, prelude
isolation, individual field presence), but the schema and the two scripts
were each tested against their own assumptions about the other side, never
against the other side's actual output, and never against a real `shark`
binary running a real workflow. The first genuine end-to-end run
(`bench/scripts/smoke-lifecycle.sh` against `py-bug-due-date-boundary`,
2026-08-26) hit five consecutive producer/validator contract mismatches on
its very first invocation — none caught by any existing test:

- `i07-schema.yaml` required `/dispatches[]/response/effort`,
  `/response/resolved_via`, and `/response/unresolved_placeholders`
  unconditionally, though `shark next --json` marks all three `omitempty`.
- `i07-schema.yaml` required `/workflow_policy/reviewer/effort`, though
  `run-lifecycle.sh` always writes it as `""`.
- `verify-lifecycle-run.sh`'s null check never consulted the
  `nullable_string` type before rejecting `/limits/first_exceeded`.
- `verify-lifecycle-run.sh` unconditionally indexed
  `response["resolved_via"]` after it became legitimately optional.
- `candidate.identity_digest` formula disagreement between the two scripts
  (filed separately as B057; not yet fixed).

The first four are fixed (commit `de0d3552`). Without a real end-to-end
test, any future change to `shark next`'s response shape, `run-lifecycle.sh`,
or `i07-schema.yaml` can silently reintroduce the same class of drift, and
nothing in CI or `bench/scripts/tests/run-all.sh` would catch it.

## Resolution Plan

Add at least one test case — ideally as its own TC in
`bench/scripts/tests/run-all.sh` — that runs the real, built `shark` binary
(no PATH stub) through `run-lifecycle.sh --mode dry-run` against a real
admitted scenario package, then pipes the resulting `lifecycle.jsonl`
straight into `verify-lifecycle-run.sh --schema bench/runs/i07-schema.yaml`
and asserts it passes. This does not need provider spend (`--mode dry-run`
fakes the worker result) and does not need the fixture submodules beyond
what scenario admission already requires, so it can run in the same tier as
the existing TC-060–068 cases. `bench/scripts/smoke-lifecycle.sh` (added
alongside this tech-debt item) already demonstrates the exact sequence and
can likely be adapted or referenced directly rather than re-derived.

Once that test exists and passes, regenerate
`tests/contracts/testdata/e40_i07/valid/complete.jsonl` from a real captured
record (or otherwise reconcile it with real `shark next` output) so the Go
contract test stops validating against a fixture that contradicts the CLI's
actual response contract.
