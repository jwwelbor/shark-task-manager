# Expose MultiLevelWorkflow.GetByType(string) and drop aliases.go entityFallback/slotWorkflow duplication

## Description

internal/config/aliases.go has two parallel entity-type dispatchers that need to stay in sync:

- entityFallback map at aliases.go:244-252 — entity-type → fallback workflow
- slotWorkflow switch at aliases.go:418-441 — entity-type → MultiLevelWorkflow.<Slot>

The switch hardcodes case 'task': return mlw.Task; case 'feature': return mlw.Feature; etc. for all 7 entity types. The fallback map enumerates the same 7 entity types separately.

Fix: add MultiLevelWorkflow.GetByType(entityType string) *WorkflowConfig in internal/config/workflow/multilevel.go (parallel to the existing GetWorkflowForLevel, but returning the slot directly without the fallback default). Then slotWorkflow collapses to a single call and entityFallback iterates the same source.

Surfaced during simplify review of commit 6492e45.

## Impact

Adding a new entity type requires touching at least three places (`MultiLevelWorkflow` struct, `entityFallback`, `slotWorkflow` switch) and keeping the entity-type strings spelled identically across all three. The dispatcher logic lives in `aliases.go`, not on the type it dispatches over — violating the "behavior lives with data" principle.

## Resolution Plan

- Add `func (m *MultiLevelWorkflow) GetByType(entityType string) *WorkflowConfig` in `internal/config/workflow/multilevel.go`. Parallels the existing `GetWorkflowForLevel` but returns the slot pointer directly (may be nil) instead of falling back to a default.
- `slotWorkflow` in `aliases.go` collapses to a single `return mlw.GetByType(entityType)`.
- `entityFallback` either iterates the slot list via reflection-free helper (e.g., a `EntityTypes()` returning `[]string{"task", "feature", ...}`), or is dropped entirely if callers can use `GetWorkflowForLevel` (which already handles fallback).

Recommend pairing this with TD-021 so the entity-type vocabulary is consolidated in one go.
