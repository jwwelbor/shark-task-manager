# Research report: Dangling relationship rows wedge keyed forks

## Scope

TD-044 concerns the edge-enrichment stage of a keyed
`shark next <epic|feature>` cascade fork. A **fork** is the
`hierarchy_selection` / `parallel_candidates` response returned when two or
more dispatchable children survive the leading selection tier. A **dangling
relationship** is an `entity_relationships` row for which the fork candidate
still exists but the endpoint on the other side of that row no longer resolves
through the registered entity repository.

The intended change extends the existing keyed-fork edge capability: retain
all resolvable `depends_on`, `blocks`, and advisory links; exclude only the
dangling row; and attach structured evidence that prevents the missing edge
from being interpreted as proof of independence. Relationship-store,
registry-wiring, scan, and other infrastructure failures remain fatal.

This report covers the persisted relationship row, endpoint resolution,
hierarchy response, and Rider consumer contract. It does not change
relationship creation, workflow state, claims, deletion behavior, bare
`shark plan`, or the separately documented dangling legacy
`tasks.depends_on` JSON behavior.

## Findings

1. `EntityRelationshipRepository.GetOutgoing` and `GetIncoming` return raw
   rows without joining endpoint tables. This is appropriate for a polymorphic
   store, but a successful relationship query proves only that the relationship
   row exists; it does not prove either endpoint still exists.

2. `PlanHierarchyService.describeEntityEdges` resolves every far endpoint
   through `EntityRegistry` and `EntityRepository.GetByID`. Any endpoint error
   is returned immediately by `resolveEdgeEndpoint`, discarding the candidate's
   otherwise valid edges.

3. `attachForkCandidateEdges` deliberately treats the service error as fatal.
   That is correct for an unavailable relationship reader, registry failure,
   query/scan error, or any unclassified resolution error: emitting empty edge
   arrays would otherwise look like evidence that all candidates are
   independent. The defect is the absence of a classified, non-fatal
   endpoint-missing result.

4. The TD description overstates the not-found prerequisite. A shared
   `repoerr.ErrNotFound` sentinel already exists. Feature, bug, change-card,
   tech-debt, sprint, and idea `GetByID` paths wrap it, and their adapters
   preserve the error. Epic and task `GetByID` still return untyped formatted
   errors. Because production registers all eight entity types and relationship
   endpoints may be cross-type, completing epic/task endpoint classification
   is the minimum prerequisite for an entity-generic fix.

5. The persistence design makes orphans possible by construction. The
   polymorphic IDs cannot have ordinary foreign keys to multiple endpoint
   tables, and the current entity delete methods do not remove matching
   `entity_relationships` rows. The later schema migration also removes the
   entity-type allowlist while preserving raw IDs, so registry-based
   resolution remains the authoritative existence check.

6. Portfolio advice already handles the same data condition without hiding
   infrastructure failures. Its repository uses `LEFT JOIN` to retain rows
   whose epic endpoint is missing; service assembly excludes that row, emits
   `DANGLING_RELATIONSHIP`, marks evidence incomplete, and makes the known
   candidate's eligibility unknown. Query and scan failures still return
   errors. TD-044 extends this remediation policy; it does not replace it.

7. The portfolio warning DTO cannot be reused unchanged for hierarchy forks:
   it is epic-specific (`EpicKeys`) while a fork edge may target any registered
   entity type. The stable warning code and fail-soft policy are reusable, but
   the hierarchy response needs an entity-neutral warning projection.

8. `HierarchyPlanSelectionResponse` and `HierarchyPlanCandidate` currently
   expose only candidates and resolved edges. There is no warnings field or
   evidence-completeness signal. Merely swallowing `repoerr.ErrNotFound` inside
   `resolveEdgeEndpoint` would therefore recreate the dangerous edge-less wire
   state that the fatal behavior was designed to prevent.

9. Rider currently says `parallel_execution=available` proves only workflow
   and stored-dependency concurrency, then evaluates `depends_on`, `blocks`,
   and `links`. It does not define dangling-edge warnings. The producer and
   Rider consumer must change together: a `DANGLING_RELATIONSHIP` warning is an
   integration/dependency evidence gap and rules out independent parallel
   launch until the row is repaired or the operator follows one candidate
   sequentially.

10. The existing real-database hierarchy tests cover task and feature edges,
    canonical keying, unwired readers, and a separate dangling legacy JSON
    dependency. They do not create an `entity_relationships` row with a deleted
    endpoint. The CLI test proves arbitrary edge-load errors remain fatal, but
    it does not pin warning propagation.

11. The legacy `tasks.depends_on` case should remain outside TD-044. It stores
    keys in JSON, fails through a different repository path, and has an
    explicit test pinning current fatal behavior. Combining it here would
    expand the data-repair and warning identity contract beyond the reported
    defect.

## Decisions

1. **Classify endpoint misses with the existing sentinel.** Use
   `errors.Is(err, repoerr.ErrNotFound)` after registry resolution. Do not use
   string matching, and do not convert registry, query, scan, context, or
   unknown errors into warnings.

2. **Complete the narrow prerequisite before changing fork behavior.** Make
   epic and task `GetByID` wrap `repoerr.ErrNotFound`, with repository tests
   asserting `errors.Is`. Broader cleanup of all untyped not-found operations
   remains related work under T-E19-F02-006, not a reason to invent a TD-044
   private error classifier.

3. **Extend the existing edge result rather than add a parallel resolver.**
   Preserve `PlanHierarchyEdges` and its relationship direction/type
   classification, add entity-neutral warning evidence associated with the
   affected candidate, and continue resolving the remaining rows. The warning
   should carry a stable `DANGLING_RELATIONSHIP` code and bounded endpoint
   identity sufficient to repair the row; it must not claim the missing
   endpoint had a key or status.

4. **Carry warnings onto the keyed hierarchy-selection wire response.** A
   missing endpoint must never become an unannotated empty edge list.
   `attachForkCandidateEdges` should remain fatal when the service returns an
   actual error and should attach both resolved edges and warnings on success.

5. **Update the Rider contract in the same change.** Rider must report the
   warning and choose sequential/evidence-gap handling rather than independent
   parallel agents. `parallel_execution=available` by itself must not override
   incomplete edge evidence.

6. **Add production-shaped counterfactual tests.** In
   `plan_hierarchy_edges_test.go`, create a real relationship, delete one
   endpoint, and prove the surviving candidate returns its other valid edges
   plus one warning. Add cases for outgoing and incoming rows, hard and
   advisory types, and epic/task endpoint repositories. In
   `next_fanout_test.go`, prove warning propagation while retaining the existing
   arbitrary edge-load failure test unchanged.

7. **Treat cleanup as defense in depth, not the primary remediation.**
   Delete-time cleanup or an orphan-repair command can prevent/reconcile rows,
   but it cannot guarantee that imported, manually edited, legacy, or
   interrupted state is clean. The keyed read path must remain robust.

8. **Reject the other alternatives.** Continuing to fail every fork preserves
   safety but leaves one stale row as a global availability wedge; silently
   dropping rows loses required evidence; string matching is brittle; and a
   polymorphic SQL `LEFT JOIN` resolver would duplicate registry knowledge
   across entity tables. Typed registry resolution plus structured warnings is
   the smallest reuse-first change.
