## Code Quality Assessment

### Readability
- Clear, descriptive comments on the regex pattern and the ordering requirement
- Comment on TD- before T- collision prevention is well-placed in both `DetectEntityType` and `ParseScope`
- Godoc on `IsTechDebtKey` follows established convention

### Consistency with Existing Patterns
- `IsTechDebtKey` follows the exact same pattern as `IsBugKey`, `IsChangeKey`, `IsChangeCardKey`, `IsIdeaKey`
- `scopeTechDebt` constant follows the naming convention of `scopeBug`, `scopeChange`, etc.
- Detection order in both `DetectEntityType` and `ParseScope` is consistent (TD before task)
- Error suggestions for invalid TD format include helpful examples

### Correctness
- The regex `^TD-\d{3}$` correctly enforces exactly 3 digits (matching spec Section 2.4)
- Case insensitivity is achieved via `Normalize()` (uppercase) before regex match
- No risk of false positive: `TD-001` will not match bug (`^B\d+$`), change (`^C\d+$`), or task (`T-E##-F##-###`) patterns
- The T-prefix collision is properly handled: `TD-001` normalized to `TD-001` will not match `isTaskKey()` which expects `T-E##-F##-###` format. However, placing the check before task checks is the correct defensive approach.

### Error Handling
- Invalid TD format (e.g., `TD-01`, `TD-0001`) produces a helpful error message with examples
- Error suggestion block for TD keys added before the generic T-prefix catch-all
