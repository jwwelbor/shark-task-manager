# Task: Extend show-actions command for multi-level display

## Goal

Extend the `shark workflow show-actions` command to display orchestrator actions for all three entity levels (epic, feature, task) instead of only task-level actions. Add a `--level` flag for filtering to a single level. The JSON output must use a new `MultiLevelActionsDisplay` wrapper that groups results by level while preserving the existing `buildActionsDisplay()` function for per-level rendering. When no `epic_workflow` or `feature_workflow` is configured, sections for those levels indicate "using defaults, no actions configured."

## Requirements

### Functional Requirements

- [ ] FR-1: `shark workflow show-actions` displays three sections: epic, feature, and task workflow actions
- [ ] FR-2: Add `--level` flag accepting values `epic`, `feature`, or `task` to filter output to a single entity level
- [ ] FR-3: When `--level` is omitted, all three levels are displayed (new default behavior)
- [ ] FR-4: JSON output wraps per-level results in a `MultiLevelActionsDisplay` struct with `epic_actions`, `feature_actions`, `task_actions`, and `summary` top-level keys
- [ ] FR-5: Per-level results reuse the existing `WorkflowActionsDisplay` struct (returned by `buildActionsDisplay()`)
- [ ] FR-6: A cross-level `MultiLevelActionsSummary` provides per-level total and action counts
- [ ] FR-7: Existing `--status` and `--action-type` filters apply independently to each visible level
- [ ] FR-8: When a level uses its default workflow (no `epic_workflow` or `feature_workflow` in config) and that default has no actions, the human-readable output shows "(using defaults, no actions configured)" for that section
- [ ] FR-9: `--level=task` produces output equivalent to the current single-level behavior (backward compatibility)
- [ ] FR-10: Invalid `--level` values produce a clear error message and exit code 1

### Non-Functional Requirements

- [ ] NFR-1: No additional file I/O beyond what `LoadMultiLevelWorkflowOrDefault` already performs (single config read)
- [ ] NFR-2: Existing `show-actions` tests continue to pass without modification (may need minor updates for new struct wrapping)
- [ ] NFR-3: The `buildActionsDisplay()` function signature and behavior remain unchanged; it is called three times with different `*WorkflowConfig` inputs

### Steps

1. [ ] **Add `--level` flag and validation**: Register the `--level` string flag on `workflowShowActionsCmd` in the `init()` function. Validate it accepts only `""`, `"epic"`, `"feature"`, or `"task"`.

2. [ ] **Define new display types**: Add `MultiLevelActionsDisplay` and `MultiLevelActionsSummary` structs in `workflow_show_actions.go`:

   ```go
   type MultiLevelActionsDisplay struct {
       EpicActions    *WorkflowActionsDisplay  `json:"epic_actions,omitempty"`
       FeatureActions *WorkflowActionsDisplay  `json:"feature_actions,omitempty"`
       TaskActions    *WorkflowActionsDisplay  `json:"task_actions,omitempty"`
       Summary        MultiLevelActionsSummary `json:"summary"`
   }

   type MultiLevelActionsSummary struct {
       EpicTotal          int `json:"epic_total"`
       EpicWithActions    int `json:"epic_with_actions"`
       FeatureTotal       int `json:"feature_total"`
       FeatureWithActions int `json:"feature_with_actions"`
       TaskTotal          int `json:"task_total"`
       TaskWithActions    int `json:"task_with_actions"`
   }
   ```

3. [ ] **Refactor `runWorkflowShowActions` to use multi-level loading**: Replace the single `config.LoadWorkflowConfig()` call with `config.LoadMultiLevelWorkflowOrDefault(configPath)`. Conditionally build per-level displays based on the `--level` flag:

   ```go
   multi := config.LoadMultiLevelWorkflowOrDefault(configPath)
   display := &MultiLevelActionsDisplay{}

   if showActionsLevel == "" || showActionsLevel == "epic" {
       epicWf := multi.GetWorkflowForLevel("epic")
       display.EpicActions = buildActionsDisplay(epicWf, showActionsStatus, showActionsActionType)
   }
   if showActionsLevel == "" || showActionsLevel == "feature" {
       featureWf := multi.GetWorkflowForLevel("feature")
       display.FeatureActions = buildActionsDisplay(featureWf, showActionsStatus, showActionsActionType)
   }
   if showActionsLevel == "" || showActionsLevel == "task" {
       taskWf := multi.GetWorkflowForLevel("task")
       display.TaskActions = buildActionsDisplay(taskWf, showActionsStatus, showActionsActionType)
   }

   display.Summary = buildMultiLevelSummary(display)
   ```

4. [ ] **Implement `buildMultiLevelSummary` helper**: Extract per-level totals and action counts from the `WorkflowActionsDisplay` objects:

   ```go
   func buildMultiLevelSummary(display *MultiLevelActionsDisplay) MultiLevelActionsSummary {
       summary := MultiLevelActionsSummary{}
       if display.EpicActions != nil {
           summary.EpicTotal = display.EpicActions.Summary.TotalStatuses
           summary.EpicWithActions = display.EpicActions.Summary.StatusesWithActions
       }
       if display.FeatureActions != nil {
           summary.FeatureTotal = display.FeatureActions.Summary.TotalStatuses
           summary.FeatureWithActions = display.FeatureActions.Summary.StatusesWithActions
       }
       if display.TaskActions != nil {
           summary.TaskTotal = display.TaskActions.Summary.TotalStatuses
           summary.TaskWithActions = display.TaskActions.Summary.StatusesWithActions
       }
       return summary
   }
   ```

6. [ ] **Update status filter check**: The current code checks `if showActionsStatus != "" && len(display.WorkflowActions) == 0` for a single level. For multi-level, the status filter applies per-level. If `--status` is set and ALL visible levels return empty results, show an appropriate message. Do not exit(1) if at least one level has results for the given status.

7. [ ] **Update `--action-type` validation**: The existing action-type validation remains unchanged; it runs before multi-level loading.

8. [ ] **Update command Long description**: Add `--level` flag documentation to the command help text and examples:

   ```
   Flags:
     --status <status>      Show action for specific status only
     --action-type <type>   Filter by action type (spawn_agent, pause, wait_for_triage, archive)
     --level <level>        Filter by entity level (epic, feature, task)

   Examples:
     shark workflow show-actions                        Show all levels
     shark workflow show-actions --level=epic           Show only epic actions
     shark workflow show-actions --level=task --json    Task actions in JSON (backward compatible)
   ```

### Technical Approach

- **Reuse `buildActionsDisplay()`**: This function already takes a `*WorkflowConfig` and returns a `*WorkflowActionsDisplay`. It is fully level-agnostic. Call it once per visible level with the appropriate config from `MultiLevelWorkflow.GetWorkflowForLevel()`.

- **Detect default workflows**: When `multi.Epic == nil` (no `epic_workflow` in config), `GetWorkflowForLevel("epic")` returns the default epic workflow. Default workflows typically have no `orchestrator_action` entries, so `buildActionsDisplay()` returns zero actions. The human-readable output detects this and shows the "using defaults" message. To distinguish "configured workflow with no actions" from "using defaults with no actions," check whether the field on `MultiLevelWorkflow` is nil before calling `GetWorkflowForLevel`. Store a boolean `isDefault` per level for display purposes.

- **Backward compatibility**: The underlying `buildActionsDisplay()` and `groupByPhase()` functions are not modified. The `WorkflowActionsDisplay` and `StatusActionDisplay` structs remain unchanged. Only the top-level output format changes (from flat to wrapped). The `--level=task` flag explicitly produces single-level behavior for consumers that depend on the current JSON shape.

## Notes

- The `buildActionsDisplay()` function is the core reuse point. It takes a `*WorkflowConfig` and two filter strings and returns a `*WorkflowActionsDisplay`. It does not know or care about entity levels. This task calls it three times with different configs.

- To distinguish "configured workflow with zero actions" from "unconfigured level using defaults," check whether `multi.Epic`, `multi.Feature`, or `multi.Task` is nil before calling `GetWorkflowForLevel()`. Pass this `isDefault` boolean to the human-readable display function so it can show the appropriate message.

- The existing `displayActionsHumanReadable()` function can be reused per-level within the new `displayMultiLevelActionsHumanReadable()` wrapper. Alternatively, the wrapper can call `groupByPhase()` and render tables directly. Choose the approach that minimizes code duplication.

- This task does NOT change the `validate-actions` command. That is handled by a separate task (T-E16-F02-007, Wave 4).

- The `PhaseOrder` map may need additional phases for epic/feature workflows (e.g., "research"). If the architecture defines new phases for epic workflows, they should be added to `PhaseOrder` in this task to ensure correct display ordering.
