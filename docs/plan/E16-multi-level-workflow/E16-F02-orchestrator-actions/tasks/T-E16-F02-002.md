# Task: Add OrchestratorAction field to TransitionResult and NextStatusInfo

## Goal

Extend the shared transition response types in `internal/services/transition_types.go` to carry orchestrator action data. This enables epic and feature transition responses to include the orchestrator action that should be executed for the new status, following the same pattern already used at the task level. The changes are purely additive -- adding new fields and a new type -- so all existing code that constructs these structs without the new fields continues to compile and behave identically (the new pointer field defaults to nil and is omitted from JSON).

### Technical Approach

**Struct modifications in `internal/services/transition_types.go`:**

The file currently defines two types and imports only the `workflow` package. After this task it will import both `workflow` and `config`, define three types (`TransitionResult`, `TransitionInfoWithAction`, `NextStatusInfo`), and include the orchestrator action pointer fields.

Target state of the file:

```go
package services

import (
    "github.com/jwwelbor/shark-task-manager/internal/config"
    "github.com/jwwelbor/shark-task-manager/internal/workflow"
)

// TransitionResult represents the outcome of a status transition.
type TransitionResult struct {
    EntityType         string                 `json:"entity_type"`
    EntityKey          string                 `json:"entity_key"`
    FromStatus         string                 `json:"from_status"`
    ToStatus           string                 `json:"to_status"`
    Transitioned       bool                   `json:"transitioned"`
    Message            string                 `json:"message,omitempty"`
    OrchestratorAction *config.PopulatedAction `json:"orchestrator_action,omitempty"`
}

// TransitionInfoWithAction extends workflow.TransitionInfo with the
// orchestrator action that would trigger if this transition is taken.
type TransitionInfoWithAction struct {
    workflow.TransitionInfo
    OrchestratorAction *config.PopulatedAction `json:"orchestrator_action,omitempty"`
}

// NextStatusInfo contains the available transitions for an entity.
type NextStatusInfo struct {
    EntityType           string                     `json:"entity_type"`
    EntityKey            string                     `json:"entity_key"`
    CurrentStatus        string                     `json:"current_status"`
    CurrentPhase         string                     `json:"current_phase,omitempty"`
    AvailableTransitions []TransitionInfoWithAction  `json:"available_transitions"`
    IsTerminal           bool                       `json:"is_terminal"`
}
```

**Key design decisions:**

- **Pointer type (`*config.PopulatedAction`)**: Using a pointer ensures `omitempty` works correctly -- nil pointers are omitted from JSON output. A value type would always serialize as an empty object `{}`.
- **Embedding `workflow.TransitionInfo`**: Embedding rather than duplicating fields ensures `TransitionInfoWithAction` stays in sync with any future additions to `TransitionInfo`. The embedded fields flatten into the JSON output (Go's standard behavior for embedded structs with JSON tags).
- **Backward compatibility**: Existing code that constructs `TransitionResult{}` without specifying `OrchestratorAction` will have it default to nil. Existing code that constructs `NextStatusInfo` with `AvailableTransitions: []workflow.TransitionInfo{...}` will need to change to `[]TransitionInfoWithAction{...}`, but this only affects F01 code in `EpicService` and `FeatureService` which are being built concurrently and will adopt the new type from the start. No existing committed code constructs these types yet.

## Testing Strategy

All tests are pure unit tests -- no database, no mocks, no file I/O. Tests verify JSON serialization behavior using `encoding/json.Marshal` and `encoding/json.Unmarshal`.

**Test file**: `internal/services/transition_types_test.go`

### Test Cases

**Test 1: `TestTransitionResult_JSONWithAction`**
- Construct a `TransitionResult` with a non-nil `OrchestratorAction` containing `Action: "spawn_agent"`, `AgentType: "developer"`, `Skills: []string{"coding"}`, `Instruction: "Implement feature E16-F01"`
- Marshal to JSON
- Assert the JSON contains `"orchestrator_action"` key
- Assert nested fields `"action": "spawn_agent"`, `"agent_type": "developer"`, `"skills": ["coding"]`, `"instruction": "Implement feature E16-F01"` are present
- Unmarshal back to `TransitionResult` and assert round-trip equality

**Test 2: `TestTransitionResult_JSONWithoutAction`**
- Construct a `TransitionResult` with `OrchestratorAction: nil`
- Marshal to JSON
- Assert the JSON does NOT contain the string `"orchestrator_action"` (omitempty behavior)
- Assert all other fields (`entity_type`, `entity_key`, `from_status`, `to_status`, `transitioned`) are present

**Test 3: `TestNextStatusInfo_JSONWithMixedActions`**
- Construct a `NextStatusInfo` with `AvailableTransitions` containing three `TransitionInfoWithAction` entries:
  - First: has `OrchestratorAction` set (non-nil)
  - Second: has `OrchestratorAction` as nil
  - Third: has `OrchestratorAction` set (non-nil, different values)
- Marshal to JSON
- Assert the first and third transitions contain `"orchestrator_action"` key
- Assert the second transition does NOT contain `"orchestrator_action"` key
- Verify the array length is 3

**Test 4: `TestTransitionInfoWithAction_EmbedsTransitionInfo`**
- Construct a `TransitionInfoWithAction` with embedded `TransitionInfo` fields set (`TargetStatus: "in_development"`, `Description: "Development phase"`, `Phase: "development"`)
- Marshal to JSON
- Assert that `"target_status"`, `"description"`, and `"phase"` appear as top-level keys in the JSON (not nested under a sub-object) -- this confirms correct embedding serialization
- Assert `"orchestrator_action"` is present or absent based on whether it was set

**Test 5: `TestTransitionResult_JSONOmitsEmptyMessage`**
- Construct a `TransitionResult` with `Message: ""` and `OrchestratorAction: nil`
- Marshal to JSON
- Assert neither `"message"` nor `"orchestrator_action"` keys appear in the output
- This confirms both `omitempty` tags work correctly together

## Notes

- This is a purely additive change to existing types. No existing fields are removed or renamed.
- The `TransitionInfoWithAction` type uses Go struct embedding, which means all `TransitionInfo` fields serialize as top-level JSON keys. This is the standard Go JSON behavior for embedded structs and does not require any custom marshaler.
- Since `transition_types.go` was created by F01 and only exists on the E16 branch, there is no risk of conflicting with main branch code.
- Downstream consumers of these types (T-E16-F02-003 EpicService action resolution, T-E16-F02-004 FeatureService action resolution) will populate the new `OrchestratorAction` field. Until those tasks are complete, the field will always be nil in practice.
