# Task: Extend validate-actions command for multi-level validation

## Goal

Extend the existing `shark workflow validate-actions` command to validate orchestrator actions for all three entity levels (epic, feature, task) independently and report per-level results. Currently, the command validates only a single `WorkflowConfig` (task-level). After this task, it loads all three level configs via `config.LoadMultiLevelWorkflowOrDefault()`, validates each independently using the existing `validateWorkflowActions()` function, and aggregates results into a `MultiLevelValidationReport`.

## Requirements

### Functional Requirements

- [ ] FR-1: `shark workflow validate-actions` (no flags) validates all three workflow levels (epic, feature, task)
- [ ] FR-2: Add `--level` flag accepting `epic`, `feature`, or `task` to validate only a single level
- [ ] FR-3: Per-level validation results are independent -- each has its own `valid` boolean, `error_count`, `warning_count`, and `results` array
- [ ] FR-4: Overall `valid` field is the logical AND of all included levels (false if ANY level fails)
- [ ] FR-5: `--strict` mode applies per-level -- in strict mode, ALL statuses at included levels must have an action defined
- [ ] FR-6: JSON output (`--json`) includes `epic_report`, `feature_report`, `task_report` fields using existing `ValidationReport` structure
- [ ] FR-7: Human-readable output displays level-labeled sections with per-status validation results and an overall summary
- [ ] FR-8: Default workflows (no `epic_workflow`/`feature_workflow` in config) pass validation when they have no actions defined (non-actionable statuses without actions are valid)
- [ ] FR-9: `--level=task` produces behavior identical to the current (pre-change) command behavior
- [ ] FR-10: All existing `validate-actions` tests continue to pass without modification

### Non-Functional Requirements

- [ ] NFR-1: No additional file I/O beyond what `LoadMultiLevelWorkflowOrDefault` already performs (single config load)
- [ ] NFR-2: Validation of all three levels completes in under 5ms (sub-microsecond per status -- map iteration and field checks only)
- [ ] NFR-3: Exit code semantics preserved: 0 = valid, 1 = invalid (errors found or warnings in strict mode)

## Implementation Plan

### Steps

1. [ ] **Add `--level` flag and `validateActionsLevel` variable** in the `init()` function of `workflow_validate_actions.go`, following the same pattern used by `show-actions` (T-E16-F02-006):
   ```go
   var validateActionsLevel string
   workflowValidateActionsCmd.Flags().StringVar(&validateActionsLevel, "level", "", "Filter by level (epic, feature, task)")
   ```

2. [ ] **Define `MultiLevelValidationReport` struct** in `workflow_validate_actions.go`:
   ```go
   type MultiLevelValidationReport struct {
       Valid         bool              `json:"valid"`
       StrictMode    bool              `json:"strict_mode"`
       EpicReport    *ValidationReport `json:"epic_report,omitempty"`
       FeatureReport *ValidationReport `json:"feature_report,omitempty"`
       TaskReport    *ValidationReport `json:"task_report,omitempty"`
   }
   ```
   The existing `ValidationReport` and `StatusValidationResult` structs remain unchanged.

3. [ ] **Refactor `runWorkflowValidateActions`** to load `MultiLevelWorkflow` and validate each included level:
   - Replace the current single `config.LoadWorkflowConfig(configPath)` call with `config.LoadMultiLevelWorkflowOrDefault(configPath)`
   - For each level (epic, feature, task), if the level is included (no `--level` flag or matching `--level` value):
     - Call `multi.GetWorkflowForLevel(level)` to get the level's `*WorkflowConfig`
     - Call the existing `validateWorkflowActions(wf, strictMode)` to get a `*ValidationReport`
     - Assign to the appropriate field in `MultiLevelValidationReport`
     - If the level's report has `Valid == false`, set the overall `Valid` to false
   - The existing `validateWorkflowActions()` function is completely level-agnostic (operates on `*WorkflowConfig`) and requires zero changes

4. [ ] **Update JSON output** to return `MultiLevelValidationReport` when no `--level` flag is specified, or return the single-level `ValidationReport` when `--level` is specified (preserving backward compatibility for consumers expecting the flat structure)

5. [ ] **Implement `displayMultiLevelValidationReport`** for human-readable output:
   - Print a header: "Validating workflow orchestrator actions..."
   - For each included level, print a section header (e.g., "--- Epic Workflow ---") followed by the existing `displayValidationReport` logic adapted for per-level display
   - Print an overall summary section showing per-level pass/fail status and counts
   - Print the overall valid/invalid result

6. [ ] **Update exit code logic** to use the `MultiLevelValidationReport.Valid` field for the exit decision

7. [ ] **Add level flag validation**: If `--level` is provided but not one of `epic`, `feature`, `task`, return an error

### Technical Approach

- [ ] Reuse the existing `validateWorkflowActions()` function verbatim -- it already accepts `*WorkflowConfig` and returns `*ValidationReport`, making it level-agnostic by design
- [ ] Reuse the existing `validateStatusAction()` function verbatim -- it validates individual statuses regardless of entity level
- [ ] Load config once via `LoadMultiLevelWorkflowOrDefault(configPath)` which handles missing sections by falling back to defaults
- [ ] The `MultiLevelValidationReport` wraps three `*ValidationReport` instances and computes an aggregate `Valid` boolean
- [ ] When `--level` is specified, only one level is validated and the report contains only that level's data (other fields are nil/omitted from JSON via `omitempty`)
- [ ] Extract the human-readable display into a helper function (`displayLevelValidationReport`) that can be called per-level within the multi-level display

### Key Design Decisions

1. **Aggregate struct wraps per-level reports**: Rather than modifying `ValidationReport` to be multi-level-aware, create a new `MultiLevelValidationReport` that composes three `*ValidationReport` instances. This keeps the existing struct untouched and reusable.

2. **`--level` flag returns flat report for single level**: When the user specifies `--level=task`, JSON output should be the existing flat `ValidationReport` structure (not wrapped in a `MultiLevelValidationReport`). This ensures `--level=task` is a drop-in replacement for the pre-change behavior.

3. **Overall `Valid` is conservative**: The top-level `Valid` is `false` if ANY included level has `Valid == false`. This prevents false confidence when only one level has issues.

    epicWf := &config.WorkflowConfig{

                    AgentType:           "researcher",
                    Skills:              []string{"discovery", "research"},

            },
        },
    }
    featureWf := &config.WorkflowConfig{...}
    taskWf := &config.WorkflowConfig{...}

        StrictMode:    false,
        EpicReport:    epicReport,
        FeatureReport: featureReport,
        TaskReport:    taskReport,
    }

    if !report.Valid {
        t.Error("Expected overall valid when all levels are valid")

## Notes

- The existing `validateWorkflowActions()` function is the core validation engine. It is already level-agnostic because it takes a `*WorkflowConfig` parameter and iterates `StatusMetadata`. This task does NOT modify it -- it calls it three times with different configs.
- The `displayValidationReport()` function will need to be refactored slightly to extract per-level display logic into a helper that can be called from both the existing function and the new multi-level display function. Alternatively, the multi-level display function can inline the per-status display logic.
- When no `epic_workflow` or `feature_workflow` is configured, `LoadMultiLevelWorkflowOrDefault` returns default workflows. These defaults have statuses but no orchestrator actions. Non-actionable statuses without actions are valid in non-strict mode, so default workflows pass validation.
- The `--level` flag value should be validated before processing. Accept only `epic`, `feature`, or `task` (case-insensitive). Return a clear error for invalid values.
