# Task: Expand PopulateTemplate and template validation for multi-level placeholders

## Goal

Extend the `PopulateTemplate` method and template validation logic in `internal/config/orchestrator_action.go` to support multi-level entity placeholders (`{id}`, `{epic_id}`, `{feature_id}`) alongside the existing `{task_id}`. This is a prerequisite for the E16 multi-level workflow system where orchestrator actions apply to epics, features, and tasks. The change is fully backward compatible -- existing `{task_id}` templates continue to work unchanged.

## Requirements

### Functional Requirements

- [ ] FR-1: `PopulateTemplate` replaces `{id}` placeholder with the entity key passed as argument
- [ ] FR-2: `PopulateTemplate` replaces `{epic_id}` placeholder with the entity key passed as argument
- [ ] FR-3: `PopulateTemplate` replaces `{feature_id}` placeholder with the entity key passed as argument
- [ ] FR-4: `PopulateTemplate` continues to replace `{task_id}` placeholder (backward compatibility)
- [ ] FR-5: All four placeholders are replaced with the same value (the entity key) -- multiple names exist for readability
- [ ] FR-6: `validateTemplateSyntax` accepts `{id}`, `{epic_id}`, `{feature_id}` as known placeholders without producing warnings
- [ ] FR-7: `validateTemplateSyntax` warns when a template contains no known placeholder (changed from checking only `{task_id}`)
- [ ] FR-8: `validateTemplateSyntax` continues to warn on truly unknown placeholders (e.g., `{unknown}`)
- [ ] FR-9: `ValidateWithContext` suggests `{id}` as the recommended placeholder in its error message for missing `instruction_template`

### Non-Functional Requirements

- [ ] NFR-2: No new dependencies introduced (only uses existing `strings` package)

### Technical Approach

**Change 1: `PopulateTemplate` expansion (line 135-137)**

Replace the current single-replacement implementation:
```go
func (oa *OrchestratorAction) PopulateTemplate(taskID string) string {
    return strings.Replace(oa.InstructionTemplate, "{task_id}", taskID, -1)
}
```

With four replacements:
```go
func (oa *OrchestratorAction) PopulateTemplate(entityID string) string {
    result := oa.InstructionTemplate
    result = strings.Replace(result, "{id}", entityID, -1)
    result = strings.Replace(result, "{task_id}", entityID, -1)
    result = strings.Replace(result, "{epic_id}", entityID, -1)
    result = strings.Replace(result, "{feature_id}", entityID, -1)
    return result
}
```

Note: The parameter name changes from `taskID` to `entityID` but this is not a breaking change since Go function signatures only care about types, not parameter names. All existing call sites pass the entity key and get correct behavior.

**Change 2: `validateTemplateSyntax` known placeholder expansion (line 161-192)**

Expand the `knownPlaceholders` map from:
```go
knownPlaceholders := map[string]bool{
    "{task_id}": true,
}
```

To:
```go
knownPlaceholders := map[string]bool{
    "{id}":         true,
    "{task_id}":    true,
    "{epic_id}":    true,
    "{feature_id}": true,
}
```

Change the "no placeholder" check from checking only `{task_id}` to checking if ANY known placeholder is present. Update the warning messages to list all four placeholders.

**Change 3: `ValidateWithContext` suggested fix message (line 89)**

Change:
```go
SuggestedFix: "Add instruction_template with {task_id} placeholder",
```

To:
```go
SuggestedFix: "Add instruction_template with {id} placeholder (also supports {task_id}, {epic_id}, {feature_id})",
```

## Notes

- The parameter name change from `taskID` to `entityID` in `PopulateTemplate` is a documentation improvement only. Go does not include parameter names in the function signature, so this is not a breaking change at the binary or API level.
- The order of `strings.Replace` calls matters if a placeholder name is a substring of another. In this case, none of `{id}`, `{task_id}`, `{epic_id}`, `{feature_id}` are substrings of each other (the braces make them distinct), so order does not matter.
- The existing test `TestValidateTemplate_UnknownPlaceholder` (line 360-374) uses `{epic_id}` as the "unknown" placeholder example. After this change, `{epic_id}` becomes known. The test must be updated to use a genuinely unknown placeholder like `{custom_field}` to maintain its intent.
- This task is sized XS because it involves changing ~15 lines of production code and adding ~80 lines of tests, all in pure functions with no external dependencies.
