# Code Review: T-E16-F02-002 - Add OrchestratorAction field to TransitionResult and NextStatusInfo

**Reviewer:** TechLead
**Date:** 2026-02-08
**Verdict:** APPROVED

## Summary

This task adds `TransitionInfoWithAction` type to the services layer, wrapping `workflow.TransitionInfo` with an optional `OrchestratorAction`. It updates `NextStatusInfo.AvailableTransitions` to use the new type and updates `EpicService.GetNextStatus` and `FeatureService.GetNextStatus` to wrap transitions accordingly. All related tests have been updated.

## Findings

### Type Definitions (transition_types.go)

- `TransitionInfoWithAction` correctly uses Go struct embedding of `workflow.TransitionInfo`, which gives JSON flattening of the embedded fields.
- `OrchestratorAction *config.PopulatedAction` uses `omitempty` properly -- nil pointer is omitted from JSON.
- The comment about JSON flattening is accurate and helpful.
- `NextStatusInfo.AvailableTransitions` correctly updated from `[]workflow.TransitionInfo` to `[]TransitionInfoWithAction`.
- No business logic leaked into the type definitions.

### GetNextStatus Wrapping (epic_service.go, feature_service.go)

- Both `EpicService.GetNextStatus` and `FeatureService.GetNextStatus` use the same pattern:
  ```go
  wrapped := make([]TransitionInfoWithAction, 0, len(transitions))
  for _, t := range transitions {
      wrapped = append(wrapped, TransitionInfoWithAction{TransitionInfo: t})
  }
  ```
- Pre-allocating with `len(transitions)` capacity is good practice.
- The wrapping correctly defaults `OrchestratorAction` to nil (zero value for pointer).
- If `transitions` is nil, `make([]TransitionInfoWithAction, 0, 0)` produces an empty non-nil slice, which is safe.
- The pattern is identical in both services, which is consistent.

### JSON Serialization

- Verified through tests: embedded `TransitionInfo` fields are flattened (no `TransitionInfo` key in JSON).
- `omitempty` works correctly for nil `OrchestratorAction` -- omitted when nil, included when populated.
- Round-trip serialization/deserialization is tested and passes.
- Mixed actions (some transitions with actions, some without) are tested.

### Layer Compliance

- Type definitions live in the services layer, which is the correct location for composite domain types that combine workflow and config concerns.
- CLI commands layer (`epic_next_status.go`) correctly consumes the new type via `buildNextStatusResult`, accessing embedded fields like `t.TargetStatus`, `t.Description`, `t.Phase` through promotion.
- No business logic in CLI commands; they only map service types to CLI output types.
- No repository involvement in this change.

### Test Quality

- **transition_types_test.go**: Thorough coverage of JSON serialization edge cases -- nil action omission, populated action inclusion, embedded field flattening, round-trip integrity, mixed actions. Tests verify real JSON behavior, not mock behavior.
- **epic_service_test.go**: Tests GetNextStatus for non-terminal, terminal, and not-found scenarios with correct assertion on `AvailableTransitions` type.
- **CLI tests**: Both epic and feature next-status tests correctly construct `TransitionInfoWithAction` with embedded `TransitionInfo` initialization syntax.
- All tests compile and pass.

### Potential Concerns (None Blocking)

- The wrapping loop in `GetNextStatus` currently always sets `OrchestratorAction` to nil. The actual population of actions is presumably handled by a later task in this feature (T-E16-F02-003 or later). This is acceptable for incremental delivery -- the type is ready to be populated.
