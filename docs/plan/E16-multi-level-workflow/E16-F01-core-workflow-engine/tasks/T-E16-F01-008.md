# Task: Add OrchestratorAction placeholder to TransitionResult

## Goal

Add an `OrchestratorAction` field (set to nil) to the `TransitionResult` and `NextStatusInfo` structs created by T-E16-F01-004. This prepares the response types for E16-F02 (Orchestrator Actions) which will populate this field with resolved action data during transitions.

This task addresses a cross-feature dependency identified in the E16-F02 BA review (Finding 2.2 / Blocking Condition 2): F02 needs to populate orchestrator actions in transition responses, but the structs must be designed with this field from the start to avoid merge conflicts and breaking changes.

## Requirements

### Functional Requirements

- [ ] `TransitionResult` struct includes `OrchestratorAction *config.PopulatedAction` field with `json:"orchestrator_action,omitempty"` tag
- [ ] `NextStatusInfo` struct includes `OrchestratorAction *config.PopulatedAction` field with `json:"orchestrator_action,omitempty"` tag (or per-transition actions via `TransitionInfoWithAction`)
- [ ] Field is nil by default in all F01 code paths (F02 will populate it)
- [ ] JSON serialization omits the field when nil (omitempty)

### Non-Functional Requirements

- [ ] No behavioral change to any F01 command output (field is nil, omitted from JSON)
- [ ] No new imports beyond `config` package for the `PopulatedAction` type

## Implementation Plan

### Steps

1. [ ] Verify `config.PopulatedAction` struct exists in `internal/config/orchestrator_action.go` (it does from E13)
2. [ ] Add `OrchestratorAction *config.PopulatedAction \`json:"orchestrator_action,omitempty"\`` to `TransitionResult` in `internal/services/transition_types.go`
3. [ ] Add `OrchestratorAction` field to `NextStatusInfo` or create `TransitionInfoWithAction` wrapper type for available transitions
4. [ ] Verify all F01 code that constructs `TransitionResult` leaves the field as nil (zero value)
5. [ ] Run existing tests to confirm no output changes

### Technical Approach

The `PopulatedAction` struct already exists from E13 (task-level orchestrator actions):

```go
// Already exists in internal/config/orchestrator_action.go
type PopulatedAction struct {
    Action      string   `json:"action"`
    AgentType   string   `json:"agent_type,omitempty"`
    Skills      []string `json:"skills,omitempty"`
    Instruction string   `json:"instruction,omitempty"`
}
```

Add to transition types:

```go
type TransitionResult struct {
    EntityType         string                 `json:"entity_type"`
    EntityKey          string                 `json:"entity_key"`
    FromStatus         string                 `json:"from_status"`
    ToStatus           string                 `json:"to_status"`
    Transitioned       bool                   `json:"transitioned"`
    Message            string                 `json:"message,omitempty"`
    OrchestratorAction *config.PopulatedAction `json:"orchestrator_action,omitempty"`
}
```

F01 code never sets this field. F02 will add `resolveAction()` methods to EpicService and FeatureService that populate it after transitions.

## Deliverables

- [ ] `OrchestratorAction` field added to `TransitionResult`
- [ ] `OrchestratorAction` field added to `NextStatusInfo` (or `TransitionInfoWithAction` wrapper)

## Acceptance Criteria

- [ ] `TransitionResult` JSON output does NOT include `orchestrator_action` when field is nil (verified by existing tests)
- [ ] `NextStatusInfo` JSON output does NOT include per-transition actions when nil
- [ ] `config.PopulatedAction` is the referenced type (not `config.OrchestratorAction` which has `instruction_template` instead of `instruction`)
- [ ] No F01 code path sets the field - it remains nil in all responses until F02

## Testing Strategy

- [ ] Add one explicit test: marshal `TransitionResult` with nil action, verify JSON does not contain `orchestrator_action` key
