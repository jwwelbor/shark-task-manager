# Task: Extend workflow.Service with Level Awareness

## Goal

Add entity level constants and extend `workflow.Service` with `level` and `multiLevel` fields, a `ForLevel()` factory method, and level-agnostic helper methods (`GetLevel()`, `GetInitialStatusString()`, `ValidateTransition()`). The existing `NewService()` constructor loads multi-level configs but defaults to task level for backward compatibility.

## Success Criteria

- [ ] Level constants `LevelEpic`, `LevelFeature`, `LevelTask` defined in new `internal/workflow/levels.go`
- [ ] `Service` struct gains `level` (string) and `multiLevel` (*config.MultiLevelWorkflow) fields
- [ ] `NewService(projectRoot)` loads multi-level configs via `config.LoadMultiLevelWorkflowOrDefault()`
- [ ] `NewService()` returns a task-level service by default (backward compatible)
- [ ] `ForLevel(level)` returns a new `*Service` wrapping the level-specific `WorkflowConfig`
- [ ] `GetLevel()` returns the current level string
- [ ] `GetInitialStatusString()` returns first start status as plain string (not `models.TaskStatus`)
- [ ] `ValidateTransition(from, to)` delegates to `config.ValidateTransition()` with descriptive errors
- [ ] All existing `Service` methods (`IsValidTransition`, `GetValidTransitions`, `GetStatusMetadata`, etc.) work correctly on level-specific services
- [ ] Epic-level service and task-level service are isolated (no cross-contamination)

## Implementation Guidance

### Overview

This task covers architecture Waves 2.5-2.6 (items T-005, T-006). The key insight is that `ForLevel()` returns a new `*Service` instance wrapping a different `WorkflowConfig`, so all existing methods automatically become level-aware without modification.
