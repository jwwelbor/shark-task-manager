# Task: Multi-Level Config Parser and Cache

## Goal

Create `LoadMultiLevelWorkflow()` and `LoadMultiLevelWorkflowOrDefault()` functions that parse `epic_workflow`, `feature_workflow`, and the existing top-level task workflow from `.sharkconfig.json` into a `MultiLevelWorkflow` container. Replace the single-config cache with a multi-level cache while maintaining full backward compatibility through `GetWorkflowOrDefault()`.

## Success Criteria

- [ ] `LoadMultiLevelWorkflow(configPath)` parses all three workflow sections from config file
- [ ] Missing `epic_workflow` section results in nil (not an error)
- [ ] Missing `feature_workflow` section results in nil (not an error)
- [ ] Missing top-level `status_flow` does NOT prevent loading epic/feature workflows (BA Review EC-5)
- [ ] Empty sections (`"epic_workflow": {}`) treated as unconfigured (BA Review EC-2)
- [ ] `LoadMultiLevelWorkflowOrDefault()` returns `*MultiLevelWorkflow` that never fails
- [ ] Existing `GetWorkflowOrDefault()` delegates to multi-level loader (returns task workflow)
- [ ] Thread-safe cache with `sync.RWMutex` (same pattern as existing cache)
- [ ] Cache invalidation works when config path changes
- [ ] All existing task workflow tests continue to pass unchanged

## Implementation Guidance

### Overview

This task covers architecture Wave 1.4 (item T-004). The key challenge is replacing the global single-config cache with a multi-level cache while ensuring `GetWorkflowOrDefault()` continues to return only the task workflow for backward compatibility.

### Key Requirements

- **Parser design**: See [Architecture - Section 7.1](../architecture.md#71-config-parsing-flow) for the parsing flow diagram
- **Cache replacement**: See [Architecture - Section 8.5](../architecture.md#85-config-caching) for the cache design with `multiLevelCache`, `multiLevelCacheLock`, `multiLevelCachePath`
- **Backward compatibility**: See [Architecture - Section 8.4](../architecture.md#84-existing-command-compatibility) for the compatibility matrix
- **BA Review EC-5**: Current parser exits early if top-level `status_flow` is missing. The new parser must handle epic/feature sections even when task workflow is absent
- **BA Review EC-3**: Status in `status_flow` but not in `status_metadata` should warn, not error
