# Task: Epic and Feature Service Layer with Transition Types

## Goal

Create `EpicService` and `FeatureService` in `internal/services/` with `TransitionStatus()`, `GetNextStatus()`, and `ValidateStatus()` methods, plus shared `TransitionResult` and `NextStatusInfo` types. These services encapsulate all workflow transition business logic, keeping CLI commands thin.

## Success Criteria

- [ ] `TransitionResult` and `NextStatusInfo` shared types defined in `internal/services/transition_types.go`
- [ ] `EpicService` created with `TransitionStatus(ctx, epicKey, targetStatus, force)` method
- [ ] `EpicService.GetNextStatus(ctx, epicKey)` returns available transitions for current status
- [ ] `EpicService.ValidateStatus(status)` delegates to workflow service
- [ ] `FeatureService` created with identical method signatures (substituting feature types)
- [ ] Valid transitions update entity status in repository
- [ ] Invalid transitions return descriptive error with valid options listed
- [ ] `--force` bypasses workflow validation
- [ ] Not-found entities return clear error
- [ ] Terminal status entities return `IsTerminal: true` with empty transitions
- [ ] All service methods tested with mocked repositories (no real database)

## Implementation Guidance

### Overview

This task covers architecture Wave 3 (items T-007, T-008, T-009). Services follow the constructor injection pattern from the architecture guidelines, receiving repositories and workflow service via constructors.

### Key Requirements

- **EpicService**: See [Architecture - Section 3.3](../architecture.md#33-new-epicservice-and-featureservice) for complete struct definition, constructor, and method signatures
- **FeatureService**: Same pattern as EpicService - see same architecture section
- **Transition types**: See [Architecture - Section 3.4](../architecture.md#34-shared-transition-types) for `TransitionResult` and `NextStatusInfo` struct definitions
- **BA Review**: F01 returns `orchestrator_action: null` always (F02 populates it later)
- **BA Review EC-7**: Entity at unrecognized status should produce clear error from `next-status`
- **BA Review EC-8**: `--force` should accept any string as status (bypass all validation)

**Create:**

- `internal/services/epic_service.go` - `EpicService` with constructor and methods
- `internal/services/feature_service.go` - `FeatureService` with constructor and methods

**Tests:**

### Integration Points

- Uses `workflow.Service.ForLevel()` from T-E16-F01-003
- Uses existing `repository.EpicRepository` and `repository.FeatureRepository` (verify they have `GetByKey()` and `Update()`)
- Downstream: T-E16-F01-006 (CLI commands) calls these services
- `TransitionResult` and `NextStatusInfo` will be serialized to JSON by CLI commands

## Validation Gates

- `go build ./...` succeeds
- All tests pass with mocked repositories (no real DB in service tests)
- `TransitionStatus()` with valid from/to succeeds
- `TransitionStatus()` with invalid from/to returns error listing valid options
- `TransitionStatus()` with force=true bypasses validation
- `GetNextStatus()` on non-terminal status returns transitions
- `GetNextStatus()` on terminal status returns `IsTerminal: true`
- `GetNextStatus()` on non-existent entity returns not-found error
- JSON serialization of `TransitionResult` and `NextStatusInfo` produces expected output
