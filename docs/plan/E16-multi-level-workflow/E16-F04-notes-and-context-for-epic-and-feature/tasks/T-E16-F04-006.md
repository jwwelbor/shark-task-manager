# Task: Context Data for Epic and Feature Repositories

## Goal

Add `GetContextData` and `UpdateContextData` methods to `EpicRepository` and `FeatureRepository`, following the same JSON serialization pattern used for task `context_data`. This enables persistent key-value context storage on epics and features.

## Requirements

### Functional Requirements

- [ ] `EpicRepository.GetContextData(ctx, epicID) (*ContextData, error)` reads and deserializes JSON from `epics.context_data`
- [ ] `EpicRepository.UpdateContextData(ctx, epicID, *ContextData) error` serializes and writes JSON to `epics.context_data`
- [ ] `FeatureRepository.GetContextData(ctx, featureID) (*ContextData, error)` reads and deserializes JSON from `features.context_data`
- [ ] `FeatureRepository.UpdateContextData(ctx, featureID, *ContextData) error` serializes and writes JSON to `features.context_data`
- [ ] NULL `context_data` column returns nil `*ContextData` (not an error)
- [ ] Merge semantics: `UpdateContextData` replaces the entire JSON blob (service layer handles merging)

### Non-Functional Requirements

- [ ] JSON serialization/deserialization uses `models.ContextData.ToJSON()` / `FromJSON()`
- [ ] No new SQL queries for existing operations (context_data loaded with entity when needed)

## Implementation Plan

### Steps

1. [ ] Add `GetContextData` method to `internal/repository/epic_repository.go`:
   - Query: `SELECT context_data FROM epics WHERE id = ?`
   - If NULL, return nil
   - If non-NULL, deserialize via `models.ContextData.FromJSON()`
2. [ ] Add `UpdateContextData` method to `internal/repository/epic_repository.go`:
   - Serialize via `contextData.ToJSON()`
   - Query: `UPDATE epics SET context_data = ? WHERE id = ?`
3. [ ] Add identical methods to `internal/repository/feature_repository.go`
4. [ ] Write repository tests for both epic and feature context data

### Technical Approach

- Reuse existing `models.ContextData` struct unchanged - same fields (progress, implementation_decisions, open_questions, blockers, etc.) are meaningful for epics and features
- Follow the exact same serialization pattern as task `context_data` handling in `task_repository.go`
- Context data is stored as a JSON string in a single TEXT column
- Merge operations happen at the service layer (T-E16-F04-007), not at the repository layer

## Deliverables

- [ ] `GetContextData` and `UpdateContextData` on `EpicRepository`
- [ ] `GetContextData` and `UpdateContextData` on `FeatureRepository`
- [ ] Repository tests for both

## Acceptance Criteria

- [ ] `GetContextData` on epic with NULL context_data returns nil, nil
- [ ] `UpdateContextData` on epic writes JSON, subsequent `GetContextData` returns it
- [ ] Same behavior for features
- [ ] Round-trip test: set context -> get context -> values match
- [ ] `make fmt && make lint && make test` passes

## Testing Strategy

- [ ] Repository tests (real DB): Set and get context data on test epics
- [ ] Repository tests (real DB): Set and get context data on test features
- [ ] Test NULL handling: get context on entity with no context_data set
- [ ] Test overwrite: set context twice, verify latest value returned
- [ ] Clean up test data before/after tests

## Dependencies

- **T-E16-F04-004**: Database Schema and Migration (provides `context_data` columns on epics/features)

## Notes

- The existing `models.ContextData` struct with its `ToJSON()`/`FromJSON()`/`Merge()` methods works perfectly for all entity types. No model changes needed.
- This task can be done in parallel with T-E16-F04-005 since they modify different files.
