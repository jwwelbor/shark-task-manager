# Task: Add entity-type filter to notes search command

## Goal

Add an `--entity-type` filter flag to the existing `shark notes search` command so users can scope searches to specific entity types (epic, feature, or task). The polymorphic `entity_notes` table architecture makes this straightforward.

## Context

From E16-F04 Architecture Open Design Question #3:
> The feature PRD lists "Note search/filtering across entities" as out of scope. However, the polymorphic `entity_notes` table makes this trivial to add later. The existing `notes search` command could gain an `--entity-type` filter in a follow-up.

Decision: This needs to be addressed. With notes now spanning epics, features, and tasks, users need the ability to filter search results by entity type.

## Requirements

### Functional Requirements

- [ ] `shark notes search "<query>" --entity-type=epic` filters to epic notes only
- [ ] `shark notes search "<query>" --entity-type=feature` filters to feature notes only
- [ ] `shark notes search "<query>" --entity-type=task` filters to task notes only
- [ ] Without `--entity-type`, search returns results across all entity types (current behavior)
- [ ] Search results include entity type in output (both JSON and human-readable)

### Implementation Plan

1. [ ] Update `EntityNoteRepository.Search()` to accept optional `entityType` filter
2. [ ] Add `--entity-type` flag to `notes search` CLI command
3. [ ] Update search result display to show entity type column
4. [ ] Update JSON output to include `entity_type` field in results

### Dependencies

- Requires entity_notes table migration (E16-F04 Task 1 in architecture)
- Requires EntityNoteRepository (E16-F04 Task 2 in architecture)

## Acceptance Criteria

- [ ] Search with `--entity-type=epic` returns only epic notes
- [ ] Search without filter returns all entity types
- [ ] JSON output includes entity_type field
- [ ] Human-readable output shows entity type column
- [ ] Tests cover filtered and unfiltered search paths

## Notes

- The polymorphic entity_notes table with composite index on (entity_type, entity_id, note_type) already supports efficient filtered queries
- This is a natural extension once the entity_notes migration is complete
