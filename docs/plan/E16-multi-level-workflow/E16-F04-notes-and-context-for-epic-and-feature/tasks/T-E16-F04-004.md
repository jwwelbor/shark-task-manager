# Task: Database Schema and Migration - entity_notes table and context_data columns

## Goal

Create the `entity_notes` polymorphic table that replaces `task_notes`, migrate existing data, and add `context_data` TEXT columns to the `epics` and `features` tables. This is the foundational database work that all other E16-F04 tasks depend on.

## Requirements

### Functional Requirements

- [ ] Create `entity_notes` table with `entity_type` + `entity_id` polymorphic pattern
- [ ] `entity_type` constrained to `('epic', 'feature', 'task')` via CHECK
- [ ] `note_type` constrained to same 10 types as current `task_notes` (comment, decision, blocker, solution, reference, implementation, testing, future, question, rejection)
- [ ] `metadata` TEXT column for rejection metadata JSON
- [ ] Migrate all existing `task_notes` rows into `entity_notes` with `entity_type = 'task'`
- [ ] Rename old `task_notes` table to `task_notes_backup` (not dropped)
- [ ] Add `context_data TEXT` column to `epics` table
- [ ] Add `context_data TEXT` column to `features` table
- [ ] All migrations are idempotent (safe to run multiple times)

### Non-Functional Requirements

- [ ] Migration completes in < 1 second for typical databases (< 10K notes)
- [ ] Indexes cover all expected query patterns
- [ ] Migration preserves all existing data with zero loss

## Implementation Plan

### Steps

1. [ ] Add `entity_notes` table creation to `createSchema()` in `internal/db/db.go`
2. [ ] Add 5 indexes on `entity_notes`: `(entity_type, entity_id)`, `(note_type)`, `(created_at)`, `(entity_type, entity_id, note_type)`, `(note_type, entity_type, entity_id)`
3. [ ] Add migration in `runMigrations()` that:
   - Checks if `entity_notes` table already exists (idempotent guard)
   - Creates `entity_notes` if missing
   - Copies all rows from `task_notes` into `entity_notes` with `entity_type = 'task'`
   - Renames `task_notes` to `task_notes_backup`
4. [ ] Add migration to add `context_data TEXT` column to `epics` table (with column-exists check)
5. [ ] Add migration to add `context_data TEXT` column to `features` table (with column-exists check)
6. [ ] Write migration tests verifying:
   - Fresh database gets `entity_notes` table with correct schema
   - Existing database with `task_notes` data migrates correctly
   - Running migration twice is safe (idempotent)
   - `context_data` columns exist on epics and features after migration

### Technical Approach

- Follow existing migration pattern in `runMigrations()`: check for table/column existence before altering
- Use `INSERT INTO entity_notes SELECT ... FROM task_notes` for bulk data migration
- Use `ALTER TABLE task_notes RENAME TO task_notes_backup` for safe rename
- Migration order: create `entity_notes` -> copy data -> rename old table -> add columns

### SQL Schema

```sql
CREATE TABLE IF NOT EXISTS entity_notes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    entity_type TEXT NOT NULL CHECK (entity_type IN ('epic', 'feature', 'task')),
    entity_id INTEGER NOT NULL,
    note_type TEXT CHECK (note_type IN (
        'comment', 'decision', 'blocker', 'solution', 'reference',
        'implementation', 'testing', 'future', 'question', 'rejection'
    )) NOT NULL,
    content TEXT NOT NULL,
    created_by TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    metadata TEXT
);

CREATE INDEX IF NOT EXISTS idx_entity_notes_entity ON entity_notes(entity_type, entity_id);
CREATE INDEX IF NOT EXISTS idx_entity_notes_type ON entity_notes(note_type);
CREATE INDEX IF NOT EXISTS idx_entity_notes_created_at ON entity_notes(created_at);
CREATE INDEX IF NOT EXISTS idx_entity_notes_entity_type ON entity_notes(entity_type, entity_id, note_type);
CREATE INDEX IF NOT EXISTS idx_entity_notes_type_entity ON entity_notes(note_type, entity_type, entity_id);
```

## Notes

- The `metadata` column is used by rejection notes to store JSON with history_id, from_status, to_status, rejected_by, etc.
- No foreign key on `entity_id` because SQLite doesn't support polymorphic FKs. Referential integrity enforced at repository layer (Task T-E16-F04-005).
- The `task_notes_backup` table should be dropped in a future cleanup task after one release cycle.
