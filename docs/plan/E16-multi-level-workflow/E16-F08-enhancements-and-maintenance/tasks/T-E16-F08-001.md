# Task: Auto-update epic/feature status when child entities are added

## Goal

When a new child entity is created under a parent entity that is in a terminal status (e.g., `completed`, `cancelled`), automatically reopen the parent by transitioning it to the first `_aggregation_` status (typically `active`). This prevents stale terminal states from persisting when new work is introduced beneath them.

**Traces to**: E16 Epic PRD -- FR-6 (Aggregation Threshold Behavior), Open Question #3 (auto-detection of epic completion/reopening).

Converted from E16-F07 during scope validation -- this is a single behavioral enhancement, not a multi-capability feature.

## User Stories

### Story 1: Auto-reopen feature on task creation

As a developer or orchestration agent,
I want a completed feature to automatically reopen when I create a new task under it,
so that the feature status accurately reflects that there is still outstanding work.

### Story 2: Auto-reopen epic on feature creation

As a product manager or orchestration agent,
I want a completed epic to automatically reopen when I create a new feature under it,
so that the epic status accurately reflects that there are still features to deliver.

### Story 3: Audit trail for automatic reopening

As a project stakeholder reviewing history,
I want automatic status changes to be logged with a system-generated note explaining why the change happened,
so that I can distinguish intentional manual transitions from automatic ones.

## Requirements

### Functional Requirements

#### FR-1: Auto-reopen feature when task is created under a terminal feature

- When `TaskService.CreateTask()` completes successfully:
  1. Look up the parent feature (via `featureService.GetFeature()` using the feature key from the created task).
  2. Obtain a feature-level workflow via `s.workflowSvc.ForLevel(workflow.LevelFeature)`.
  3. Check if the parent feature's current status is in the `_complete_` special statuses list via `featureWf.IsTerminalStatus()`.
  4. If yes, determine the target reopen status via `featureWf.GetAggregationStatuses()[0]` (fallback: `"active"`).
  5. Update the feature status via `s.featureService.UpdateFeature()` with the new status.
  6. The update creates a history/audit entry automatically. Log message: `"auto-reopened: new task {taskKey} created under terminal feature"`.
- The task creation itself must still succeed even if the parent status update fails (log a warning, do not fail the overall create).

#### FR-2: Auto-reopen epic when feature is created under a terminal epic

- When `FeatureService.CreateFeature()` completes successfully:
  1. The parent epic is already retrieved (`epic` variable at line 801 of `feature_service.go`).
  2. Obtain an epic-level workflow via `s.workflowSvc.ForLevel(workflow.LevelEpic)`.
  3. Check if the parent epic's current status is in the `_complete_` special statuses list via `epicWf.IsTerminalStatus()`.
  4. If yes, determine the target reopen status via `epicWf.GetAggregationStatuses()[0]` (fallback: `"active"`).
  5. Update the epic status directly on the `epic` model and persist via `s.epicLookupRepo.Update()`.
  6. Log an audit note: `"auto-reopened: new feature {featureKey} created under terminal epic"`.
- The feature creation itself must still succeed even if the parent status update fails (log a warning, do not fail the overall create).

#### FR-3: Respect workflow configuration

- Terminal statuses MUST be read from the parent entity's workflow `special_statuses._complete_` list (not hardcoded).
- Target reopening status MUST be read from the parent entity's workflow `special_statuses._aggregation_` list, using the first entry.
- If `_aggregation_` is not configured for the parent level, fall back to `"active"` (matching the default in both `DefaultEpicWorkflow` and `DefaultFeatureWorkflow`).
- If `_complete_` is not configured, fall back to `["completed"]` (existing `GetTerminalStatuses()` fallback).

#### FR-4: Skip when parent is not terminal

- No status change occurs if the parent entity is already in a non-terminal status (e.g., `active`, `draft`, `in_refinement_ba`).
- This is a no-op, not an error.

### Non-Functional Requirements

#### NFR-1: Both workflow profiles

- Must work with the `basic` profile (5 task statuses, hardcoded epic/feature defaults).
- Must work with the `advanced` profile (19 task statuses, custom epic/feature workflows).

#### NFR-2: Custom workflow configurations

- Must work with arbitrary user-defined `_complete_` and `_aggregation_` values in `.sharkconfig.json`.

#### NFR-3: Performance

- Parent status check is a single DB read (the feature/epic is already loaded during entity creation in the normal path).
- No additional queries beyond what is already done during creation, except the update call when a reopening occurs.

#### NFR-4: Graceful degradation

- If the parent status update fails (DB error, constraint violation), log a warning and return the successfully created child entity.
- Do not rollback the child creation.

## Acceptance Criteria

### AC-1: Task creation reopens completed feature

**Given** a feature `E01-F01` with status `completed`
**When** a new task is created under `E01-F01` via `shark task create E01 F01 "New task"`
**Then** the feature status changes to `active`
**And** the task is created successfully with status `draft` (or the configured start status)
**And** a history record is created for the feature with notes containing `"auto-reopened"`

### AC-2: Task creation reopens cancelled feature

**Given** a feature `E01-F01` with status `cancelled`
**When** a new task is created under `E01-F01` via `shark task create E01 F01 "Revived task"`
**Then** the feature status changes to `active`
**And** the task is created successfully

### AC-3: Feature creation reopens completed epic

**Given** an epic `E01` with status `completed`
**When** a new feature is created under `E01` via `shark feature create E01 "New feature"`
**Then** the epic status changes to `active`
**And** the feature is created successfully with status `draft`
**And** a history record is created for the epic with notes containing `"auto-reopened"`

### AC-4: No-op when parent is already non-terminal

**Given** a feature `E01-F01` with status `active`
**When** a new task is created under `E01-F01`
**Then** the feature status remains `active` (unchanged)
**And** no history record is created for the feature

### AC-5: No-op when parent is in planning status

**Given** a feature `E01-F01` with status `in_refinement_ba` (a planning status, not terminal)
**When** a new task is created under `E01-F01`
**Then** the feature status remains `in_refinement_ba` (unchanged)

### AC-6: Works with custom _complete_ and _aggregation_ values

**Given** a custom workflow where `_complete_` = `["done", "abandoned"]` and `_aggregation_` = `["tracking"]`
**When** a task is created under a feature with status `done`
**Then** the feature status changes to `tracking` (not hardcoded `active`)

### AC-7: Graceful degradation on parent update failure

**Given** a feature `E01-F01` with status `completed`
**And** the feature repository update will fail (e.g., simulated DB error)
**When** a new task is created under `E01-F01`
**Then** the task is still created successfully
**And** a warning is logged about the failed parent update

### AC-8: Both creation paths handled for tasks

**Given** a feature `E01-F01` with status `completed`
**When** a task is created via either:
  (a) `TaskService.CreateTask()` fallback path (no `creatorSvc`), or
  (b) `TaskService.CreateTask()` primary path (via `creatorSvc`)
**Then** the feature auto-reopen logic executes in both cases (the check runs after the task is successfully persisted, regardless of which creation path was used)

## Technical Specification

### Architecture Decisions

#### ADR-1: Use `featureService` for feature status update (not `featureRepo`)

**Decision**: TaskService uses the already-wired `s.featureService` field to look up and update the parent feature status, rather than extending `AnalyticsFeatureRepository` with write methods.

**Rationale**:
- `TaskService` already has `featureService *FeatureService` wired via `SetFeatureService()` in all CLI global accessors and HTTP wiring.
- `FeatureService.UpdateFeature()` already exists (line 871 of `feature_service.go`) and accepts a `FeatureUpdates` struct with an optional `Status` field.
- Using the service layer for the update ensures validation and consistency.
- Follows the existing precedent: `recalculateFeatureProgress()` already delegates to `featureService`.

**Consequence**: No new repository interface methods needed on the task-service side.

#### ADR-2: Extend `FeatureEpicLookup` with `Update` for epic status update

**Decision**: Add `Update(ctx context.Context, epic *models.Epic) error` to the `FeatureEpicLookup` interface so `FeatureService` can persist epic status changes directly.

**Rationale**:
- `FeatureService.epicLookupRepo` is typed as `FeatureEpicLookup` (currently read-only: `GetByKey`, `GetByFilePath`, `UpdateFilePath`, `List`).
- The concrete `*repository.EpicRepository` already implements `Update(ctx, *models.Epic) error` (line 289 of `epic_repository.go`), so adding the method to the interface requires zero new repository code.
- An alternative was adding a separate `epicService` dependency to `FeatureService`, but that creates a cross-service dependency that would complicate wiring and testing. The direct repo call is simpler and sufficient since the auto-reopen is a simple field update with no epic-level business logic beyond the status assignment.

**Consequence**: One-line interface addition to `FeatureEpicLookup`. No new code in `EpicRepository`.

#### ADR-3: Use `workflow.Service.ForLevel()` for cross-level workflow access

**Decision**: Call `s.workflowSvc.ForLevel(workflow.LevelFeature)` from `TaskService` (and `s.workflowSvc.ForLevel(workflow.LevelEpic)` from `FeatureService`) to access parent-level workflow config at runtime.

**Rationale**:
- `workflow.Service` stores `multiLevel *config.MultiLevelWorkflow` internally and `ForLevel()` is a public method that returns a new `*Service` scoped to the requested level.
- This works regardless of the current scoping of `s.workflowSvc` because `ForLevel()` reads from the shared `multiLevel` config, not from the current scoped `workflow` field.
- No constructor changes needed. No new fields needed.
- Already proven: `FeatureProgressService` uses a similar pattern (receives the workflow service and calls `ForLevel` internally).

**Consequence**: Zero structural changes to service constructors or wiring.

#### ADR-4: Add `GetAggregationStatuses()` to `workflow.Service`

**Decision**: Add a new public method `GetAggregationStatuses() []string` that reads `special_statuses._aggregation_` and falls back to `["active"]`.

**Rationale**:
- Mirrors the existing `GetTerminalStatuses()` method which reads `_complete_`.
- The `_aggregation_` key is already defined as `config.AggregationStatusKey` and used in default workflows.
- Provides a clean API for retrieving the reopen target status without services needing to understand the config structure.

**Consequence**: New public method on `workflow.Service`. New test in `service_test.go`.

#### ADR-5: Best-effort pattern for auto-reopen (log warning, do not fail)

**Decision**: Auto-reopen is non-fatal. If the parent status update fails, log a warning via `log.Printf` and return the successfully created child entity.

**Rationale**:
- Follows the exact pattern of `recalculateFeatureProgress()` (line 1248-1256 of `task_service.go`): it silently ignores errors when `featureService` operations fail.
- The child entity creation is the primary operation; the parent status update is a secondary side effect.
- Users would be confused if task creation failed due to an unrelated feature status issue.

**Consequence**: Uses `log.Printf` for warnings (same as existing patterns). No error return path from the auto-reopen helper.

### API Contracts

#### New Method: `workflow.Service.GetAggregationStatuses()`

```go
// GetAggregationStatuses returns the aggregation statuses for this workflow level.
// Reads from special_statuses._aggregation_ in workflow config.
// Falls back to ["active"] if not configured.
func (s *Service) GetAggregationStatuses() []string {
    aggStatuses, exists := s.workflow.SpecialStatuses[config.AggregationStatusKey]
    if !exists || len(aggStatuses) == 0 {
        return []string{"active"}
    }
    return aggStatuses
}
```

**Location**: `internal/workflow/service.go`
**Input**: None (reads from internal config).
**Output**: `[]string` -- ordered list of aggregation statuses; first entry is the reopen target.
**Fallback**: `["active"]` when `_aggregation_` is missing or empty.

#### New Private Method: `TaskService.maybeReopenParentFeature()`

```go
// maybeReopenParentFeature checks if the parent feature is in a terminal status
// and reopens it to the first aggregation status. Best-effort: logs a warning
// on failure, never fails the caller.
//
// Parameters:
//   - ctx: context for cancellation
//   - featureKey: key of the parent feature (e.g., "E01-F01")
//   - taskKey: key of the newly created task (for audit logging)
func (s *TaskService) maybeReopenParentFeature(ctx context.Context, featureKey string, taskKey string)
```

**Location**: `internal/services/task_service.go`
**Called from**: `CreateTask()`, after both the `creatorSvc` path (line 364) and the fallback path (line 426).
**Behavior**:
1. Guard: return immediately if `s.featureService == nil`.
2. Get feature via `s.featureService.GetFeature(ctx, featureKey)`. If error, log warning and return.
3. Get feature-level workflow: `featureWf := s.workflowSvc.ForLevel(workflow.LevelFeature)`.
4. Check: `featureWf.IsTerminalStatus(string(feature.Status))`. If false, return (no-op).
5. Get target status: `featureWf.GetAggregationStatuses()[0]`.
6. Update: call `s.featureService.UpdateFeature(ctx, featureKey, FeatureUpdates{Status: &targetStatus})` where `targetStatus` is `models.FeatureStatus(aggStatus)`.
7. If update error, `log.Printf("warning: auto-reopen of feature %s failed: %v", featureKey, err)`.

**Error handling**: All errors are logged, never returned.

#### New Private Method: `FeatureService.maybeReopenParentEpic()`

```go
// maybeReopenParentEpic checks if the parent epic is in a terminal status
// and reopens it to the first aggregation status. Best-effort: logs a warning
// on failure, never fails the caller.
//
// Parameters:
//   - ctx: context for cancellation
//   - epic: the parent epic model (already retrieved during feature creation)
//   - featureKey: key of the newly created feature (for audit logging)
func (s *FeatureService) maybeReopenParentEpic(ctx context.Context, epic *models.Epic, featureKey string)
```

**Location**: `internal/services/feature_service.go`
**Called from**: `CreateFeature()`, after the `repo.Create()` call (line 855).
**Behavior**:
1. Get epic-level workflow: `epicWf := s.workflowSvc.ForLevel(workflow.LevelEpic)`.
2. Check: `epicWf.IsTerminalStatus(string(epic.Status))`. If false, return (no-op).
3. Get target status: `epicWf.GetAggregationStatuses()[0]`.
4. Update epic model: `epic.Status = models.EpicStatus(aggStatus)`.
5. Persist via `s.epicLookupRepo.Update(ctx, epic)`.
6. If update error, `log.Printf("warning: auto-reopen of epic %s failed: %v", epic.Key, err)`.

**Error handling**: All errors are logged, never returned.

#### Interface Extension: `FeatureEpicLookup`

```go
// FeatureEpicLookup defines the minimal epic repository interface needed by FeatureService.
type FeatureEpicLookup interface {
    GetByKey(ctx context.Context, key string) (*models.Epic, error)
    GetByFilePath(ctx context.Context, filePath string) (*models.Epic, error)
    UpdateFilePath(ctx context.Context, epicKey string, newFilePath *string) error
    List(ctx context.Context, status *models.EpicStatus) ([]*models.Epic, error)
    Update(ctx context.Context, epic *models.Epic) error  // NEW: needed for auto-reopen
}
```

**Location**: `internal/services/feature_service.go` (line 39-46)
**Change**: Add one method: `Update(ctx context.Context, epic *models.Epic) error`
**Satisfying implementation**: `*repository.EpicRepository` already has `Update(ctx, *models.Epic) error` (line 289). No new repository code needed.

### Security Considerations

- **No new attack surface**: This change only adds logic within existing service methods. No new CLI commands, no new API endpoints, no new inputs.
- **No privilege escalation**: The auto-reopen respects the same repository-level access as existing status updates.
- **Audit trail**: All status changes are logged. The auto-reopen note text distinguishes automatic changes from manual ones.

### Performance Considerations

- **Zero additional queries for the common case** (parent not terminal): The feature/epic is already loaded during entity creation. `IsTerminalStatus()` is an in-memory check against a small list of strings.
- **One additional write for the rare case** (parent terminal): A single `UPDATE` query to change the parent's status. This is O(1) and indexed.
- **No cascading recalculations**: The auto-reopen only changes the parent status. It does not trigger progress recalculation or further cascading. Progress will be naturally recalculated when the child entity's status later changes.

## Edge Cases

1. **Feature has no `_aggregation_` configured**: Fall back to `"active"`.
2. **Feature has no `_complete_` configured**: Fall back to `["completed"]` (existing `GetTerminalStatuses()` behavior).
3. **Feature is in `cancelled` status**: Still terminal per `_complete_`, so it gets reopened to `active`. This is intentional -- if you're adding work to a cancelled entity, it's no longer cancelled.
4. **Multiple tasks created rapidly**: Each creation independently checks and potentially updates. The second creation may see the feature already at `active` (from the first), which is a no-op. No race condition concern since the check-and-update is a simple status comparison.
5. **Task creation via CLI vs HTTP API**: Both go through `TaskService.CreateTask()`, so both trigger the auto-reopen. No separate handling needed.
6. **Parent entity doesn't exist**: Should not happen since both creation flows validate parent existence before creating the child. If it does happen (data corruption), the GetFeature/GetByKey call returns an error, which is logged and ignored.
7. **`archived` status**: In the default config, `archived` is in `_complete_` for epics/features (`["completed", "archived"]`). Creating a child under an archived parent will reopen it to `active`. This is correct -- users who don't want this can remove `archived` from `_complete_`.
8. **Basic profile with no epic/feature workflow**: Default workflows apply. Default `_complete_` = `["completed", "archived"]`, default `_aggregation_` = `["active"]`. Works correctly.

## Notes

- Original F07 description asked: "maybe we should consider a state machine for the final status? How would that work with custom workflow? maybe _final_ states require all tasks to be complete?"
- Answer: Use the existing `_complete_` special statuses from workflow config to identify terminal states. The `_aggregation_` status (typically `active`) is the target for reopening. Final states requiring all tasks complete is already handled by the aggregation threshold concept in E16.
- The auto-reopen is intentionally best-effort (does not fail the child creation). This follows the same pattern as the existing `RecalculateAndSetProgress` auto-complete, which updates feature status as a side effect of task status changes without failing the primary operation.
