# Code Review: T-E16-F03-005 - Calculation Service Planning Mode Bypass

## Files Reviewed

1. `internal/status/calculation_service.go` - Planning mode bypass logic
2. `internal/status/calculation_service_test.go` - 4 new tests for planning mode

## Summary

This task adds planning mode awareness to the `CalculationService`. When a feature or
epic is in a planning-phase status (where `is_planning=true` in the workflow metadata),
status derivation from children is bypassed. The entity retains its own workflow status
rather than being overwritten by aggregation logic.

## Review Findings

### Strengths

1. **Clean bypass pattern**: The planning mode check at the top of `RecalculateFeatureStatus`
   and `RecalculateEpicStatus` is an early return that avoids executing any downstream
   logic (task breakdown queries, derivation). This is efficient and clear.

2. **Backward compatibility**: When `featureWorkflow` or `epicWorkflow` is nil (not set),
   `isFeatureInPlanningMode()` / `isEpicInPlanningMode()` return false, ensuring that
   existing behavior (always aggregate) is preserved. The test
   `TestCalculationService_NoFeatureWorkflowDefaultsToAggregation` explicitly validates
   this contract.

3. **Proper use of StatusChangeResult**: The bypass correctly populates `WasSkipped=true`
   and `SkipReason` with an informative message, and sets `PreviousStatus == NewStatus`
   to indicate no change. This allows callers like `RecalculateAll` to correctly increment
   `FeaturesSkipped` counters.

4. **Setter pattern**: Using `SetEpicWorkflow()` and `SetFeatureWorkflow()` setters keeps
   the constructor signature unchanged, avoiding breaking changes for existing callers
   that do not need multi-level workflow support.

5. **Test coverage**: All four tests are well-structured:
   - `TestCalculationService_FeaturePlanningModeBypass` - verifies skip when feature in draft
   - `TestCalculationService_FeatureAggregationModeStillWorks` - verifies normal aggregation
     for non-planning status
   - `TestCalculationService_NoFeatureWorkflowDefaultsToAggregation` - backward compat
   - `TestCalculationService_EpicPlanningModeBypass` - verifies skip for epic in draft

   Tests use real in-memory database (appropriate for status package which is a service-layer
   package). Each test creates its own DB instance via `setupTestDB(t)`, ensuring isolation.

### Observations (No Action Required)

1. **Helper config factories**: The `createFeatureWorkflowConfig()` and
   `createEpicWorkflowConfig()` test helpers are well-crafted, including `StatusFlow`,
   `StatusMetadata` with `IsPlanning` and `AggregatesFrom`, and `SpecialStatuses`.
   These are realistic workflow configs.

2. **`_ = taskRepo` suppression**: Lines 484, 536, 588, and 636 suppress unused variable
   warnings. This is a minor style consideration -- the variables could simply be removed
   from the declaration in those specific tests. However, this is cosmetic and passes the
   linter, so no action is required.

3. **Thread safety of setters**: `SetEpicWorkflow` and `SetFeatureWorkflow` are not
   synchronized. This is acceptable because they are called during initialization (service
   setup) before any concurrent usage, following the same pattern as the constructor.
