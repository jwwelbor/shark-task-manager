## Summary

This task enriches the status dashboard with planning mode metadata. After the
dashboard is built by `StatusService.GetDashboard()`, the command calls
`enrichEpicSummaries()` to annotate each `EpicSummary` with display mode, planning
flag, and phase. The formatter then renders planning-mode epics differently from
aggregation-mode epics.

## Review Findings

### Strengths

1. **Clean architectural separation**: The enrichment is done via `DisplayService` (service
   layer), not by adding business logic to the CLI command. The `enrichEpicSummaries`
   function is a thin bridge that calls `displaySvc.GetEpicDisplayInfo()` and maps the
   result onto the `EpicSummary` struct. This follows the project's layering rules.

2. **Graceful degradation**: If `GetEpicDisplayInfo()` fails for any epic, the code defaults
   to `DisplayModeAggregation` and continues. This is a good resilience pattern -- a
   failure in display enrichment should not crash the entire dashboard.

3. **Model additions are backward-compatible**: The three new fields on `EpicSummary`
   (`DisplayMode`, `IsPlanning`, `Phase`) all use `omitempty` JSON tags, so existing JSON
   consumers will not see them unless they are populated. This is correct for incremental
   rollout.

4. **Formatter output is clean**:
   - Planning-mode epics show `(planning)` in the Progress column (cyan-colored in
     terminal, plain text with `--no-color`).
   - Phase is shown in the Health column.
   - Tasks and Features columns show `-` for planning-mode epics (since those metrics
     are not meaningful in planning mode).
   - The aggregation-mode rendering path is completely unchanged.

5. **Consistent with existing patterns**: The `GetDisplayService()` accessor in
   `service_accessors.go` follows the same pattern as `GetEpicService()` and
   `GetFeatureService()` -- creates a new instance per call, panics on DB failure.

### Minor Observations (No Action Required)

1. **N+1 query pattern in enrichEpicSummaries**: For each epic, `GetEpicDisplayInfo`
   performs a DB lookup by key. If there are many epics, this is N additional queries.
   However, the status dashboard typically shows a manageable number of epics (typically
   fewer than 20), and this is a CLI tool (not a high-throughput API), so the performance
   impact is negligible. A batch lookup could be added later if needed.

2. **`progressBarWidth` variable unused for planning epics**: The `progressBarWidth`
   variable is declared on line 132 of `formatter.go` but is only used in the aggregation
   branch. This is fine because it is a simple int allocation with no side effects.

3. **No direct unit tests for `enrichEpicSummaries`**: The function is a thin bridge
   between two well-tested components (`DisplayService` and `EpicSummary`). The status
   command tests already cover the integration path. Adding a unit test with a mocked
   `DisplayService` would require introducing an interface; this is a reasonable tradeoff
   for a function that has only 15 lines of logic.

4. **`GetDisplayService()` creates a new instance each call**: This is consistent with the
   other service accessors in the file. For the status command, it is called once per
   invocation, so there is no performance concern.
