## Summary

These three tasks add planning mode awareness to the `shark get` command for epics and features. When an entity is in a planning state (determined by DisplayService), the get command renders a workflow-position view instead of child-aggregation progress. A fourth piece adds `(planning)` labels on features listed within the epic aggregation view.

- **T-E16-F03-002 (Epic Get Planning Mode):** APPROVED
- **T-E16-F03-003 (Feature Get Planning Mode):** APPROVED

## Detailed Review

### Architecture and Layering

**PASS.** The implementation correctly follows the thin-command-wrapper pattern:
- `runEpicGet` and `runFeatureGet` call `cli.GetDisplayService()` to obtain the service, then call `DetermineEpicDisplayMode` / `DetermineFeatureDisplayMode` on the result.
- No business logic is placed in the CLI layer. The mode determination algorithm lives in `DisplayService.determineDisplayMode()` in the service layer.
- The planning renderers (`renderEpicPlanning`, `renderFeaturePlanning`) only handle output formatting -- they read fields from the `*services.EpicDisplayInfo` / `*services.FeatureDisplayInfo` structs and print them.
- JSON output paths serialize the same info structs directly via `cli.OutputJSON(info)`.

### Planning Mode Routing

**PASS.** The routing logic is correct:
1. Get the entity from the repository.
2. Call `displaySvc.DetermineXxxDisplayMode(entity)`.
3. If `DisplayModePlanning`, call `displaySvc.GetXxxDisplayInfo(ctx, key)` and render planning view.
4. Otherwise, fall through to the existing aggregation code path.

This is clean and preserves the existing aggregation behavior entirely. The early return ensures no aggregation code is executed for planning mode entities.

### Backward Compatibility

**PASS.** When no workflow is configured (nil workflow), `DetermineEpicDisplayMode` and `DetermineFeatureDisplayMode` both return `DisplayModeAggregation`, which routes to the existing aggregation rendering. This is tested in `TestDetermineDisplayMode_NilWorkflow` and `TestBackwardCompat_NilEpicWorkflow_AlwaysAggregation`.

Existing epics and features with no level-specific workflow configs will see identical behavior to before these changes.

### Error Handling

**PASS.** Both epic and feature planning paths handle errors from `GetEpicDisplayInfo` / `GetFeatureDisplayInfo` with appropriate exit codes (`os.Exit(2)` for service errors). Path resolution errors are gracefully handled (resolved path left empty on failure, not fatal).

### FeatureWithDetails Struct (T-004)

**PASS.** The `FeatureWithDetails` struct has been extended with `IsPlanning bool` and `Phase string` fields, both with `omitempty` JSON tags. This ensures backward-compatible JSON output -- existing consumers that do not know about these fields will simply not see them when they are empty/false.

### Rendering Quality

**PASS.** Both `renderEpicPlanning` and `renderFeaturePlanning` follow the same rendering pattern:
- Section header with entity key
- Info table with title, status "(workflow)" suffix, phase, description
- Workflow position with ">" marker for current status and "(done)" suffix for passed statuses
- Informational message when no children exist

The rendering is consistent between epic and feature, which follows the principle of least surprise.

### T-004: (planning) Label in Aggregation View

**PASS.** In `renderEpicDetails`, the features loop now checks `feature.IsPlanning` and renders `(planning)` for progress and `-` for task count. This is clean and minimal.

### Observation (Non-blocking)

In `epic.go` line 502, the `BuildWorkflowPosition` call passes `nil` as the workflow config:

```go
if wfPos := displaySvc.BuildWorkflowPosition(string(feature.Status), nil); wfPos != nil {
    featurePhase = string(feature.Status)
}
```

Since `BuildWorkflowPosition` returns `nil` when `wfCfg` is `nil`, the `featurePhase` variable will always remain empty string. This means the `Phase` field on `FeatureWithDetails` will never be populated in the aggregation view.

This is functionally harmless -- the `Phase` field is `omitempty` so it simply will not appear in JSON output, and the text rendering only uses `IsPlanning` (not `Phase`) to decide whether to show `(planning)`.

However, the dead code path is misleading. The correct approach would be either:
- Remove the `BuildWorkflowPosition` call entirely and just set `featurePhase = string(feature.Status)` directly when `isPlanning` is true, or
- Access the feature workflow config from the display service to get the actual phase metadata.

This is a minor code clarity issue, not a correctness issue. The `(planning)` label renders correctly regardless. Recommend cleaning this up in a follow-up.
