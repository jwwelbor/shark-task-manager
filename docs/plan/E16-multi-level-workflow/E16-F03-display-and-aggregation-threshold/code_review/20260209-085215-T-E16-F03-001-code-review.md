### MINOR-1: DisplayServiceDeps uses concrete types instead of interfaces (Testability)

**Severity**: Minor
**File**: `display_service.go`, lines 90-96
**Location**: `DisplayServiceDeps` struct

```go
type DisplayServiceDeps struct {
    EpicRepo     *repository.EpicRepository
    FeatureRepo  *repository.FeatureRepository
    TaskRepo     *repository.TaskRepository
    DocumentRepo *repository.DocumentRepository
}
```

**Issue**: The deps struct uses concrete repository types rather than interfaces. This deviates from the pattern established by `EpicService` and `FeatureService` in the same package, which define local interfaces (e.g., `type EpicRepository interface { ... }`) and accept those instead of concrete types.

**Impact**: The `GetEpicDisplayInfo`, `GetFeatureDisplayInfo`, and all `populate*` methods are currently untested (0% coverage) because mocking concrete types is not possible. The mode determination and workflow position logic are well-tested, but the data assembly methods cannot be unit tested without a real database.

**Recommendation**: In a follow-up task, define interfaces for the needed repository methods and accept those instead. This would allow the `populate*` methods to be tested with mocks, consistent with the testing architecture golden rule ("ONLY repository tests should use the real database").

### MINOR-2: buildOrderedStatuses uses substring matching for status filtering

**Severity**: Minor
**File**: `display_service.go`, lines 219-221

```go
if !strings.Contains(t, "blocked") && !strings.Contains(t, "on_hold") && !strings.Contains(t, "cancelled") {
```

**Issue**: This uses substring matching rather than exact matching or checking against the `SpecialStatuses` configuration. A hypothetical status named `unblocked_review` would be incorrectly filtered out because it contains "blocked".

**Impact**: Low risk in practice since status names in the project follow clear naming conventions. However, it couples the function to naming conventions rather than configuration.

**Recommendation**: Consider checking against the terminal/special statuses from the workflow config instead, or use exact equality. Not blocking since current status naming conventions make this unlikely to cause issues.

**Severity**: Minor
**File**: `display_service.go`, lines 307-311

```go

if err != nil {
```

## Algorithm Correctness Review

### determineDisplayMode (lines 137-160)

The algorithm correctly implements the three-tier decision:
1. **nil workflow -> aggregation** (backward compat, line 138-140)
2. **Status in `_aggregation_` special statuses -> aggregation** (explicit override, lines 143-150)
3. **Status has `is_planning: true` -> planning** (metadata check, lines 153-155)
4. **Default -> aggregation** (safe default for unknown/terminal statuses, line 159)

The ordering is correct: checking `_aggregation_` before `is_planning` ensures that even if a status has `is_planning: true` AND is in the aggregation list, aggregation wins. This is the right priority order.

### buildOrderedStatuses (lines 189-232)

The algorithm correctly:
- Starts from `_start_` special status
- Follows the first non-blocked/on_hold/cancelled transition at each step
- Uses a `seen` set to prevent infinite loops from cycles in the status flow
- Handles edge cases: nil config, missing start status, terminal statuses (empty transitions)

The "happy path" approach is appropriate for display purposes where you want a linear ordering.
