# Task: Implement Calculation Service Planning Mode Bypass

## Goal

Update `internal/status/calculation_service.go` to skip status derivation from children when an entity is in planning mode. Entities in planning states own their own status and should not have it overridden by child progress aggregation.

## Requirements

### Functional Requirements

- [ ] Add `isFeatureInPlanningMode(feature)` helper to CalculationService
- [ ] Add `isEpicInPlanningMode(epic)` helper to CalculationService
- [ ] In `RecalculateFeatureStatus()`: if feature is in planning mode, skip derivation and return `StatusChangeResult{WasSkipped: true, SkipReason: "..."}`
- [ ] In `RecalculateEpicStatus()` (if exists): same planning mode bypass
- [ ] Define `StatusChangeResult` type with `WasSkipped` and `SkipReason` fields (or extend existing result type)
- [ ] Planning mode check reads `is_planning` from workflow config status metadata

### Non-Functional Requirements

- [ ] No change when no epic/feature workflow is configured (backward compat)
- [ ] Minimal performance impact - config lookup is cached
- [ ] Clear skip reason for debugging/logging

## Implementation Plan

### Steps

1. [ ] Add or extend result type with `WasSkipped` and `SkipReason` fields
2. [ ] Implement `isFeatureInPlanningMode()` reading from feature workflow config
3. [ ] Add planning mode check at top of `RecalculateFeatureStatus()`
4. [ ] Implement `isEpicInPlanningMode()` reading from epic workflow config
5. [ ] Add planning mode check at top of epic recalculation (if applicable)
6. [ ] Add unit tests with mocked config

### Technical Approach

```go
func (s *CalculationService) RecalculateFeatureStatus(...) (*StatusChangeResult, error) {
    // NEW: Check if feature is in planning mode
    if s.isFeatureInPlanningMode(feature) {
        return &StatusChangeResult{
            WasSkipped: true,
            SkipReason: "feature in planning mode (is_planning=true)",
        }, nil
    }
    // ... existing aggregation logic unchanged ...
}
```

- The `isFeatureInPlanningMode` reads the feature's current status, looks up `is_planning` in the feature workflow's status metadata
- If no feature workflow config exists, returns `false` (not in planning mode = aggregate as before)

## Deliverables

- [ ] Modified `internal/status/calculation_service.go` with planning mode bypass

- [ ] Unit tests for bypass logic

## Acceptance Criteria

- [ ] Feature in planning status is NOT overridden by task-derived status
- [ ] Feature in aggregation status IS derived from tasks as before
- [ ] No workflow configured = no change in behavior (always aggregates)
- [ ] Skip reason is available for debugging/logging
- [ ] All existing calculation tests still pass

## Testing Strategy

- [ ] Test feature in planning mode - verify status NOT recalculated
- [ ] Test feature in aggregation mode - verify status IS recalculated (existing behavior)
- [ ] Test with no feature workflow configured - verify aggregation (backward compat)
- [ ] Test edge case: feature transitions from planning to aggregation threshold

## Dependencies

- **T-E16-F03-001**: DisplayService core (uses same mode determination logic, but this task modifies CalculationService directly)
- **E16-F01**: Provides `is_planning` field in status metadata config

## Notes

- This is the key behavior change that makes planning mode work correctly
- Without this, the calculation service would try to derive feature status from its tasks, overriding the feature's own planning workflow status
- Architecture doc recommends adding this as an early exit in the cascade logic
