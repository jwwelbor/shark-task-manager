# Task: Implement DisplayService Core with Mode Determination Logic

## Goal

Create the `DisplayService` in `internal/services/display_service.go` that determines whether an entity (epic or feature) should be shown in "planning" mode or "aggregation" mode based on workflow configuration and the entity's current status.

## Requirements

### Functional Requirements

- [ ] Define `DisplayMode` type with constants: `DisplayModePlanning` ("planning") and `DisplayModeAggregation` ("aggregation")
- [ ] Define `EpicDisplayInfo` struct containing: Epic, Mode, Phase, PhaseDescription, WorkflowPosition (planning fields), and Progress, Features, FeatureRollup, TaskRollup (aggregation fields)
- [ ] Define `FeatureDisplayInfo` struct with analogous planning/aggregation fields
- [ ] Define `WorkflowPosition` struct with: CurrentStatus, Phase, NextStatuses, PreviousStatuses, IsTerminal
- [ ] Implement `determineEpicDisplayMode(epic)` - checks `is_planning` metadata from status config; defaults to aggregation if no epic workflow configured (backward compat)
- [ ] Implement `determineFeatureDisplayMode(feature)` - same logic for feature level
- [ ] Implement `GetEpicDisplayInfo(ctx, epicKey)` - fetches epic, determines mode, assembles appropriate data
- [ ] Implement `GetFeatureDisplayInfo(ctx, featureKey)` - fetches feature, determines mode, assembles appropriate data

### Non-Functional Requirements

- [ ] Backward compatible: no epic/feature workflow configured = always aggregation mode
- [ ] Planning mode is cheaper than aggregation (no child queries needed)
- [ ] Uses constructor injection for repositories and workflow config

## Implementation Plan

### Steps

1. [ ] Create `internal/services/display_service.go` with type definitions
2. [ ] Implement `NewDisplayService(repoDb, configPath, projectRoot)` constructor
3. [ ] Implement `determineEpicDisplayMode` reading from `is_planning` field in status metadata from E16-F01 config
4. [ ] Implement `determineFeatureDisplayMode` with same pattern
5. [ ] Implement `GetEpicDisplayInfo` that routes to planning data assembly or aggregation data assembly
6. [ ] Implement `GetFeatureDisplayInfo` with same routing pattern
7. [ ] Add unit tests with mocked repositories and config

### Technical Approach

- Read `is_planning` field from `StatusMetadata` in workflow config (provided by E16-F01)
- Check if current status is in `_aggregation_` special status group
- If no level-specific workflow exists, default to aggregation (100% backward compat)
- Service wraps existing `status.CalculationService` for aggregation mode data

## Deliverables

- [ ] `internal/services/display_service.go` - Core service implementation
- [ ] `internal/services/display_service_test.go` - Unit tests with mocks
- [ ] Type definitions: `DisplayMode`, `EpicDisplayInfo`, `FeatureDisplayInfo`, `WorkflowPosition`

## Acceptance Criteria

- [ ] `GetEpicDisplayInfo` returns planning mode when epic status has `is_planning: true`
- [ ] `GetEpicDisplayInfo` returns aggregation mode when epic status has `is_planning: false` or no epic workflow exists
- [ ] `GetFeatureDisplayInfo` follows same logic for features
- [ ] Backward compatible: existing projects with no epic/feature workflow see no behavior change
- [ ] All tests passing with mocked dependencies

## Testing Strategy

- [ ] Unit tests with mock workflow config returning various `is_planning` values
- [ ] Test default behavior when no epic workflow configured (aggregation)
- [ ] Test default behavior when no feature workflow configured (aggregation)
- [ ] Test mode determination for each status in a sample workflow
- [ ] Test WorkflowPosition assembly with next/previous statuses

## Dependencies

- **E16-F01** (Core Workflow Engine): Provides `LoadEpicWorkflow()`, `LoadFeatureWorkflow()`, `StatusMetadata.IsPlanning`, `SpecialStatuses["_aggregation_"]`

## Notes

- This is the foundation task - all other E16-F03 tasks depend on the types and mode determination logic defined here
- The aggregation data assembly can largely delegate to existing `status.CalculationService`
- Planning data assembly is simpler: just entity + workflow position, no child queries
