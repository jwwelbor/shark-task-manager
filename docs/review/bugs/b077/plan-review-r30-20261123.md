## Open blockers

**R30-01 · A successful configuration read can be ignored.** The four-row summary on plan lines 28–33 and step 3 on line 73 require the same executable and configuration for discovery and dispatch. In the C01–C30 index, C02 changes the provider while holding the mapped model fixed. Its different-model control is an *exact* request, which bypasses mapped discovery. C04, C05, C14 and C16 can consequently agree on the same stale model. The source and evidence columns of C02 point to the earlier mapping authority and earlier reviews. They do not connect the successor rule in 4011/4273 to a discriminating discovery check.

For example, run the correct CLI and check the provider and exit code, but always select the first mapped model seen by the host. A fixture with that single mapped model still gets the expected argv, observation, actor, claim and receipt. The current recording test shows the practical risk. Its helper returns the Markdown table cell, now literally `discovered model from selected CLI config/read`. The fixture injects that string as `SELECTED_MODEL` and compares the capture with the injected value. Its recorder never supplies a discovery response. See `tests/contracts/b077_codex_route_attestation_test.go:60`, `:108` and `:144`.

In C02, bind the expected value to the recording CLI's independent configuration response. Drive the same mapped request twice with two distinct configured models, keeping the original request, provider, effort and host eligibility fixed. Record the executable and configuration context at the read and at the receiving process. Make ambient discovery distinguishable from discovery through the selected executable/profile. Require the second discovered value in the actual selector, claim, matching producing turn and, on the relevant caller, persisted actor. A successful read with no concrete model must also reject before claim, even when a cached value exists. Connect C04/C05/C14/C16 to this check, the successor decisions and the separate evidence record.

**R30-02 · A model-access denial after successful discovery can trigger another launch.** Decision 4011 requires normal rejection without fallback on access failure. C02 denies the local configuration read or returns the wrong provider. C05 rejects missing or mismatched worker identity. C13 exercises timeout and lease loss. These controls can all pass if Rider handles a provider's model-access error by launching another model only on that error. C12 exercises a separate nested review retry policy. It cannot count the outer Rider's replacement launch.

Add an indexed control at the mapped Rider caller. Give the selected CLI a successful local read and an authenticated session. Have the first explicitly selected invocation report model-access denial, with another model or adapter available to expose an unauthorized retry. Check the bounded failure and original session cleanup, one attempted dispatch, zero alternate submissions, zero admitted results and zero advances. Preserve any observed usage or cost on the denied attempt and keep absent amounts unknown. A success control with the same preflight must still admit the matching worker once. This can use recorders throughout.
