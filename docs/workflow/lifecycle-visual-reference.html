06 · Review stack

Feature QA is not finish-feature deep review

They overlap on code and tests, but answer different questions. QA asks whether a complex feature works as specified through production-shaped paths. Finish-feature asks whether the entire branch is structurally safe to publish and then carries it through PR, CI, merge, and cleanup.

Where QA earns its keep

It can catch a feature that has green unit tests but no production call site, a test that drives the wrong signature, a missing contract edge, or a frontend that was never rendered. Those are behavior-proof gaps that a diff-only craft review may miss.

Where duplication is real

Both inspect implementation and tests. SIMPLE/STANDARD feature review already combines craft, AC, wiring, targeted tests, and caller-path checks; finish-feature then performs another broad code review. COMPLEX adds separate QA before UAT and the final branch review.

Known finish-feature coverage hazard: the current deep-review collector builds its scope from git diff main...HEAD. That excludes uncommitted and untracked candidate files. Before treating its PASS as branch-wide evidence, inspect the working-tree diff, status, and untracked feature paths or commit the complete intended scope.
07 · Decision aid

Make every gate prove its value

The repository defines extensive evidence production, but it does not yet prove that each artifact reduces defects or delivery risk enough to justify its cost. The next improvement should measure unique value by gate and remove duplicate work.

Keep as hard evidence

  • One coherent business and architecture contract for work that is genuinely feature- or epic-sized.
  • TDD and the project quality gate at implementation time.
  • Production-path, caller-signature, integration-edge, and frontend-render proof when those risks exist.
  • Live required CI immediately before merge.
  • Human approval for product tradeoffs, sprint mutation, and risk acceptance.

Measure, merge, or make conditional

  • Repeated research reports when the child adds no evidence beyond the parent capability map.
  • Separate spec, test-plan, task-review, code-review, QA, UAT, and final deep-review passes for low-risk work.
  • D08–D14 when there is no user-facing journey, prototype, or real participant evidence.
  • Review reruns over an identical commit SHA and unchanged evidence set.
  • Full-form reports for clean passes; the current compact-pass policy is the right direction.

1 · Add review identity

Record reviewed commit SHA, diff fingerprint, gate, duration, and finding fingerprints. Reuse a clean result when the evidence set is unchanged.

2 · Track yield

For each gate, count unique blockers, duplicates of prior findings, false positives, and defects that escape to a later gate or production.

3 · Set retirement rules

After a representative sample, merge or remove a gate that finds no unique blockers, is rarely consumed downstream, or duplicates another gate at high rates.

Practical first experiment: for the next 10 completed features, log minutes and unique defect fingerprints for feature code review, QA, UAT, and finish-feature deep review. Do not redesign the workflow from intuition alone. The likely overlap is visible; the actual defect yield still needs measurement.
