## Summary

T-E18-F05-003 implements the `shark change approve` command and requires typed error-to-exit-code mapping at the CLI layer. The approve command calls the service correctly, but the error handling in `runChangeApprove` provides no typed error inspection. As a result, invalid state errors (exit code 3) and not-found errors (exit code 1) are not distinguished - all errors produce exit code 1 (Cobra's default for returned errors). The acceptance criteria require specific exit codes with specific messages.

## Findings

### DEFECT 1 (Required Fix): No typed error-to-exit-code mapping

The current implementation of `runChangeApprove`:

```go
func runChangeApprove(cmd *cobra.Command, args []string) error {
    key := args[0]
    notes, _ := cmd.Flags().GetString("notes")

    svc := cli.GetChangeCardService()
    card, err := svc.ApproveChangeCard(cmd.Context(), key, notes)
    if err != nil {
        return fmt.Errorf("failed to approve change-card %s: %w", key, err)
    }
    // ... output
}
```

This wraps all errors identically and returns them to Cobra, which maps all non-nil errors to exit code 1.

The PRD (Story 6, AC6.2) and the task spec (T-E18-F05-003 success criteria) require:

- **Exit code 1** when the change-card key is not found (NotFoundError)
- **Exit code 3** when the change-card is not in `proposed` status (InvalidStateError / workflow transition error)
- The error message for exit code 3 must include the current status of the card

The correct pattern (as established in other commands throughout the codebase):

```go
func runChangeApprove(cmd *cobra.Command, args []string) error {
    key := args[0]
    notes, _ := cmd.Flags().GetString("notes")

    svc := cli.GetChangeCardService()
    card, err := svc.ApproveChangeCard(cmd.Context(), key, notes)
    if err != nil {
        var notFoundErr *repository.NotFoundError
        if errors.As(err, &notFoundErr) {
            cli.Error(fmt.Sprintf("Change-card not found: %s", key))
            os.Exit(1)
        }

        var invalidStateErr *services.InvalidStateError
        if errors.As(err, &invalidStateErr) {
            cli.Error(fmt.Sprintf("Cannot approve change-card %s: current status is '%s'", key, invalidStateErr.CurrentStatus))
            os.Exit(3)
        }

        cli.Error(fmt.Sprintf("Failed to approve change-card: %v", err))
        os.Exit(2)
    }
    // ... output
}
```

Note: `os.Exit()` is acceptable here as exit code mapping is a CLI presentation concern. Alternatively, error wrapping with a sentinel exit code via the root command handler is also valid, but `os.Exit()` in the command handler is the pattern used elsewhere in this codebase.

---

## What Is Correct

- The approve command is registered correctly.
- It calls `svc.ApproveChangeCard()` as a thin wrapper.
- The `--notes` flag is bound and passed to the service.
- JSON output mode is supported.

---

## Required Changes

1. Add typed error inspection in `runChangeApprove` using `errors.As()`.
2. Map `repository.NotFoundError` to `cli.Error(...)` + `os.Exit(1)`.
3. Map invalid state / workflow transition errors to `cli.Error(...)` including current status + `os.Exit(3)`.
4. Map generic errors to `cli.Error(...)` + `os.Exit(2)`.

---

## Principle of Least Surprise

Callers (AI agents, shell scripts, CI pipelines) rely on exit codes to determine what corrective action to take. An exit code 1 meaning "not found" requires a different response than exit code 3 meaning "wrong state". Returning undifferentiated exit code 1 for all errors violates the Principle of Least Surprise and breaks any automation that depends on these commands.

---

## Conclusion

The approve command structure is correct but lacks the mandatory exit code differentiation. This must be fixed before the task can be approved.
